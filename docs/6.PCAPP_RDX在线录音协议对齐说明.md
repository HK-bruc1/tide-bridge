# 6. PC App 与设备 RDX 在线录音协议对齐说明

版本：V1.3

日期：2026-08-06

状态：PC App 命令映射根因已确认；手机/PC 原始 ATT 写入已完成同固件 A/B 对比，命令字节和长度已定稿

适用固件：T2620 / AC701N / BR28，RDX + HOGP composite GATT profile

## 1. 对齐结论

设备长按按键只负责向 App 上报“开始/结束在线录音触发”，不会直接启动录音。App 必须在收到触发后，通过 RDX 私有写特征回写录音控制命令，固件解析成功后才会创建录音 JLStream 并发送实时音频帧。

当前对比结果：

- 手机 App：回写后出现 `record_msg_parse`、`cmd_handle`、`RECORD START`、`JLSTREAM create_stream`，实时音频正常。
- PC App：已经正确收到设备开始触发 `*DEV#devrec#1#0#2#`，但错误回写 `*APP#devrec#0#`，随后没有任何录音命令解析和 `RECORD START` 日志。

因此根因已经收敛到 PC App 的命令映射：PC App 把设备上行 `devrec` 触发错误地当成了同名应答协议。设备上报和设备录音链路不需要修改；PC App 必须把开始/结束触发转换为 `*APP#record#<onoff>#<mode>#<sample>#` 下行命令。2026-08-06 的固件原始 ATT 日志进一步确认，成功手机命令固定为 18 字节且不带尾部 `NUL (00)`；不应再优先排查 ADC、编码器或 JLStream。

最新 PC App 日志直接证据：

```text
13:38:30  DEV *DEV#devrec#1#0#2#
13:38:30  Device record state: 1
13:38:30  APP acknowledged the device recording start with *APP#devrec#0#.
13:38:32  DEV *DEV#devrec#0#0#2#
13:38:32  Device record state: 0
```

其中设备开始/结束触发均正确；错误发生在第三行 PC App 构造的回写命令。`devrec` 只用于 Device -> App 触发，不存在本次场景下的 `*APP#devrec#...` 应答。并且 PC App 在“开始”事件中发送值 `0`，语义也与开始相反，同时缺少 `mode/sample` 两个参数。

### 1.1 同固件原始 ATT A/B 证据（2026-08-06）

联调固件已在 `rdx_ble_server_att_write_callback()` 的 RDX Value `0x0006` 入口加入 `[RDX_APP_RX]` 日志。该位置位于 owner claim 和闭源协议解析之前，打印的是 App 实际写入 ATT 的原始 payload，不依赖上层应用日志推断。

手机 App 使用 `con=0x0051 / wrapper=1`，按键开始后写入：

```text
[RDX_APP_RX] con=0x0051 att=0x0006 mode=0 offset=0 len=18
2A 41 50 50 23 72 65 63 6F 72 64 23 31 23 30 23 31 23
ASCII: *APP#record#1#0#1#
```

随后固件立即出现：

```text
_rdx_protocol_record_msg_parse --> onoff = 1, mode = 0, sample = 1
rdx_record_cmd_handle_internal --> cmd = 0
rdx_record_process --> RECORD START
```

手机松键后写入同样为 18 字节的停止命令：

```text
[RDX_APP_RX] con=0x0051 att=0x0006 mode=0 offset=0 len=18
2A 41 50 50 23 72 65 63 6F 72 64 23 30 23 30 23 31 23
ASCII: *APP#record#0#0#1#
```

PC App 使用 `con=0x0050 / wrapper=0`，与 HOGP 形成 composite owner 后，按下和松开却两次写入完全相同的 14 字节 payload：

```text
[RDX_APP_RX] con=0x0050 att=0x0006 mode=0 offset=0 len=14
2A 41 50 50 23 64 65 76 72 65 63 23 30 23
ASCII: *APP#devrec#0#
```

两次错误写入后都没有 `record_msg_parse`、`cmd_handle` 或 `RECORD START/STOP`。这证明问题不在 GATT handle、双 wrapper 路由、HOGP 复用 ACL 或固件录音模块，而在 PC App 构造了闭源 RDX parser 不接受的下行命令。

同一日志还显示手机初始化写入 `*APP#ostype#0#`，PC App 写入 `*APP#ostype#3#`。当前公开头文件仅声明 Android=`0`、iOS=`1`、Harmony=`2`；Windows 的 `3` 尚未在固件头文件中冻结。它是需要另行对齐的协议版本信号，但不是本次录音未启动的直接原因。

### 对齐原则：手机 App 是黄金参考

当前固件已经由手机 App 验证通过，因此 PC App 应以同版本手机 App 的实际 BLE 交互作为第一优先级的参考，按原始 ATT 行为逐字节复现，不要根据协议表或 HID 逻辑重新猜测一套封装。协议头文件用于确认 UUID、命令含义和能力位；当协议表描述与手机 App 的实际抓包不一致时，先暂停联调并确认固件与手机 App 版本是否一致。

需要复现的是手机 App 的完整行为：RDX 特征选择、Notify CCC 配置、Write Without Response 类型、payload 字节、长度、分包方式、触发后的时序以及音频帧解码。手机日志中的 `wrapper=1` 与 PC 日志中的 `wrapper=0` 只是连接 wrapper 不同，PC App 不需要复制 wrapper 编号，但必须对当前触发连接完成同样的 RDX 写入。

当前固件已经确认：GATT UUID/句柄、Write Without Response、Notify CCC、按键触发帧 `*DEV#devrec#...`、录音状态帧 `*DEV#record#...`，以及录音命令解析器读取 `onoff/mode/sample` 三个参数。`[RDX_APP_RX]` 又直接确认了手机 App 成功路径的原始 ATT payload、长度和无尾部 NUL 规则，因此本说明中的开始/停止命令可以作为 PC App 的逐字节实现依据。

## 2. GATT 通道（必须使用 RDX，不要使用 HID）

| 用途 | UUID | 属性 | 固件句柄 | PC App 操作 |
|---|---|---|---:|---|
| RDX 私有服务 | `06068D0C-6B97-11EF-B864-0240AC120002` | Primary Service | `0x0004` | 服务发现 |
| RDX 命令写入 | `06068D1C-6B97-11EF-B864-0241AC120002` | Write Without Response | Value `0x0006` | 写录音控制命令 |
| RDX 数据/状态通知 | `06068D2C-6B97-11EF-B864-0242AC120002` | Notify | Value `0x0008` | 接收状态和音频帧 |
| RDX 数据通知 CCC | 标准 CCCD | Read/Write | `0x0009` | 写入 `01 00` 开启 Notify |

HID 服务 `0x1812` 及其 `0x2A4D` Report 特征只用于键盘输入/输出，不能用于 RDX 录音控制。特别是不要把 `*APP#record#...` 写到 HID Output Report。

## 3. 连接初始化要求

1. 发现 RDX 服务和上述两个 RDX 特征，不要硬编码仅依赖句柄；句柄可用于抓包核对。
2. 在 RDX Notify Value 的 CCCD（`0x0009`）写入小端 `01 00`。
3. 使用与录音触发相同的连接完成命令写入。设备支持最多两个 Peripheral ACL，但 RDX owner 是单例；响应必须发回发送触发通知的那个连接。
4. 录音控制命令使用 Write Without Response。不要等待 Write Response 作为录音启动确认，启动确认以设备状态通知和后续音频 Notify 为准。

## 4. 设备到 App 的录音触发

设备长按按键时会在 RDX Notify 通道发送 `devrec` 触发帧。`scene=0` 时固件发送：

```text
按下：*DEV#devrec#1#0#2#
松开：*DEV#devrec#0#0#2#
```

字段顺序为：

```text
*DEV#devrec#<reason>#<scene>#<format>#
```

- `reason`：`1` 表示按键开始触发，`0` 表示按键结束触发。
- `scene`：本次日志为 `0`，PC App 应回写相同场景对应的录音模式。
- `format`：当前固件发送固定值 `2`；PC App 应完整接收，不要截断或重新解释该字段。

下面的 `record` 帧是设备已经接受 App 命令后的**录音状态通知**，不能当作按键触发：

```text
启动状态：*DEV#record#1#0#1#1#1#0#
停止状态：*DEV#record#0#0#1#1#1#0#
```

如果 PC App 等待 `*DEV#record#1#...` 后才发送开始命令，会形成时序死锁：设备正在等待 App 命令，而 App 正在等待设备启动状态。

## 5. App 到设备的录音控制命令

命令主体是 ASCII 字符串，使用 `#` 分隔，末尾必须保留 `#`。当前在线录音成功路径的解析器读取三个参数：

```text
*APP#record#<onoff>#<mode>#<sample>#
```

| 命令 | 含义 | 当前在线录音用途 |
|---|---|---|
| `*APP#record#1#0#1#` | 开始录音，Chat/会议模式，`sample=1` | 本次 `scene=0` 手机成功路径 |
| `*APP#record#1#1#1#` | 开始录音，Call/通话模式，`sample=1` | 仅在触发场景为 Call 时使用，仍须用手机抓包复核 |
| `*APP#record#0#0#1#` | 停止录音，保留本次 `mode/sample` | 本次手机成功路径 |

本次手机成功路径对应的关键解析结果是：

```text
onoff = 1, mode = 0, sample = 1
内部 cmd = 0               // RECORD START
```

停止时对应：

```text
onoff = 0, mode = 0, sample = 1
内部 cmd = 3               // RECORD STOP
```

注意：线上命令的 `record#1#...` 是“开始请求”，固件内部日志的 `cmd=0` 才是开始状态；不要直接按内部数字含义构造命令。

`mode` 与触发场景对应，不是 PC App 自行选择的麦克风数量；`sample` 必须保留手机成功路径中的值 `1`，不能因为头文件中存在简写命令就省略。当前固件对 Chat 和 Call 都选择 OPUS 16 kHz stereo，具体编码格式以设备后续状态通知为准。

暂停/恢复不属于本次按键开始/停止故障的对齐范围。PC App 不应在本次验收中发送 `onoff=2/3`，后续如需支持，必须另行按照能力位和手机抓包确认完整参数。

### PC App 事件处理规则

1. 建立连接并开启 RDX Notify CCC，保存当前 RDX connection，不使用 HID connection 代替。
2. 收到完整 `*DEV#devrec#1#<scene>#2#` 后，根据 `scene` 构造三参数开始命令；本次 `scene=0` 必须发送 `*APP#record#1#0#1#`。
3. 收到 `*DEV#record#1#...` 只更新 UI/录音状态，不再次发送开始命令。
4. 收到完整 `*DEV#devrec#0#<scene>#2#` 后，使用本次会话保存的 `mode/sample` 发送停止命令；本次发送 `*APP#record#0#0#1#`。
5. 收到 `*DEV#record#0#...` 后结束本次会话并停止音频解码，不再次发送停止命令。
6. 同一条 `devrec` 触发只能产生一次 WNR。重连后必须清空旧会话、旧 connection handle 和未完成的触发状态。

禁止使用下面这种对称拼接方式：

```text
错误：收到 *DEV#devrec#... 后，把 DEV 替换成 APP 并回写 *APP#devrec#...
```

`devrec` 与 `record` 不是请求/应答同名命令，而是两个方向、两个职责不同的协议命令。正确映射为：

| 设备触发 | PC App 动作 |
|---|---|
| `*DEV#devrec#1#0#2#` | WNR 写入 `*APP#record#1#0#1#` |
| `*DEV#devrec#0#0#2#` | WNR 写入 `*APP#record#0#0#1#` |

### 编码和发送规则

- 编码：UTF-8/ASCII 字节，当前命令全部为 ASCII。
- 不要发送 JSON、Base64、十六进制字符串或 HID Report 包装。
- 不要附加 `CR` 或 `LF`。
- 不要附加尾部 `NUL (00)`。同固件手机成功路径的 `[RDX_APP_RX]` 已确认 `buffer_size=18`，hex dump 在最后一个 `23`（`#`）结束。
- 一条命令一次 Write Without Response；当前命令长度小于常用 ATT MTU，不要人为拆成多次 Write。
- 如果底层 BLE 库返回“写入成功”，只代表 ATT 层接受，不代表 RDX parser 已接受；必须继续等待设备状态通知。

示例（开始，`scene=0`）：

```text
ASCII：*APP#record#1#0#1#
HEX：  2A 41 50 50 23 72 65 63 6F 72 64 23 31 23 30 23 31 23
ATT payload 长度：18 字节
```

示例（停止）：

```text
ASCII：*APP#record#0#0#1#
HEX：  2A 41 50 50 23 72 65 63 6F 72 64 23 30 23 30 23 31 23
ATT payload 长度：18 字节
```

## 6. 完整时序

```text
PC App                                      设备
   |                                          |
   |<-- Notify: *DEV#devrec#1#0#2# -----------|  长按按下触发
   |--- WNR: *APP#record#1#0#1# ------------->|  开始命令
   |<-- Notify: *DEV#record#1#... -------------|  RECORD START 状态
   |<-- Notify: *DEV#stream#... + binary ------|  实时音频帧
   |                                          |
   |<-- Notify: *DEV#devrec#0#0#2# -----------|  长按释放触发
   |--- WNR: *APP#record#0#0#1# ------------->|  停止命令
   |<-- Notify: *DEV#record#0#... -------------|  RECORD STOP 状态
```

设备收到有效开始命令后，固件日志应依次出现：

```text
_rdx_protocol_record_msg_parse -> onoff = 1, mode = 0, sample = 1
rdx_record_cmd_handle_internal -> cmd = 0
rdx_record_process -> RECORD START
JLSTREAM create_stream
```

设备收到有效停止命令后，应出现：

```text
_rdx_protocol_record_msg_parse -> onoff = 0, mode = 0, sample = 1
rdx_record_cmd_handle_internal -> cmd = 3
rdx_record_process -> RECORD STOP
```

## 7. 实时音频接收要求

PC App 必须持续监听 RDX Notify Value（UUID `06068D2C...0242...`）。RDX Notify 通道同时承载状态文本和音频数据，PC App 应使用与手机 App 相同的 RDX packet/frame 解码器，不能把音频帧当作 HID Report 或普通 UTF-8 文本处理。

当前固件封装的音频数据格式为：

```text
*DEV#stream#<len1>#<len2># + binary audio payload
```

头部是 ASCII，后面直接拼接二进制音频数据。两个长度字段的校验、分帧、重组和 OPUS 解码必须复用手机 App 的实现或以手机抓包为准，不能通过搜索 `#` 把整包当作纯文本拆分。

固件只有在以下条件同时满足时才发送音频帧：

- 录音状态已经进入 START/RESUME；
- 当前在线录音 session 仍绑定当前 RDX owner；
- RDX Notify CCC 已开启且发送路径 ready；
- BLE 链路未断开、没有 stream discontinuity。

因此，PC App 不应在收到按键触发后直接等待音频，而要先完成 RDX Notify CCC 配置，再回写开始命令。

## 8. PC App 当前日志与正确日志对照

| 阶段 | 手机 App（正常） | PC App 当前行为（异常） |
|---|---|---|
| 设备开始触发 | 收到 `*DEV#devrec#1#0#2#` | 已正确收到 `*DEV#devrec#1#0#2#` |
| App 开始回写 | `*APP#record#1#0#1#` 对应解析结果 | 错误构造为 `*APP#devrec#0#` |
| 设备结束触发 | 收到 `*DEV#devrec#0#0#2#` | 已正确收到 `*DEV#devrec#0#0#2#` |
| App 停止回写 | `*APP#record#0#0#1#` 对应解析结果 | 错误地再次写入 `*APP#devrec#0#` |
| 原始 ATT 开始写入 | `con=0x0051 len=18`：`*APP#record#1#0#1#` | `con=0x0050 len=14`：`*APP#devrec#0#` |
| 原始 ATT 停止写入 | `con=0x0051 len=18`：`*APP#record#0#0#1#` | 再次写入相同的 `*APP#devrec#0#` |
| RDX 解析 | `onoff=1 mode=0 sample=1` | 缺失 |
| 录音状态 | `cmd=0`、`RECORD START` | 缺失 |
| 音频任务 | `JLSTREAM create_stream` | 缺失 |

PC App 的应用日志和设备侧 `[RDX_APP_RX]` 原始 payload 已经相互印证命令构造错误。`att_write` 只能证明 ATT 写回调被调用，不能把错误的 `*APP#devrec#0#` 解释为 RDX 录音命令已被接受。

### 快速故障判定

| 最后一个已确认节点 | 现象 | 优先检查 |
|---|---|---|
| 没有收到 `*DEV#devrec#...` | 按键后 PC App 无触发事件 | RDX Notify CCC、Notify 分发、当前 RDX owner |
| 已收到 `devrec`，没有 WNR | PC App 未回写 | PC App 触发帧匹配和事件状态机 |
| 已收到 `devrec`，回写 `*APP#devrec#...` | 使用了错误的对称命令映射 | 改为 `devrec` 触发到 `record` 控制的显式映射 |
| 已出现 `att_write`，没有 `record_msg_parse` | 固件 parser 未接受 | Value handle `0x0006`、WNR、payload HEX、固定 18 字节、是否误写 HID |
| 已出现 `record_msg_parse`，没有 `RECORD START` | 命令语义未进入启动状态 | `onoff/mode/sample`、设备忙状态和命令返回路径 |
| 已出现 `RECORD START`，没有音频 Notify | 录音已启动但发送链路不通 | RDX CCC、`stream_tx_ready`、connection owner、Notify 接收与分帧 |
| 已收到 `*DEV#stream#...` 但无可播放音频 | PC 已拿到流但解码失败 | 二进制帧重组、长度字段、OPUS 16 kHz stereo 解码 |

## 9. 抓包和联调必须记录的字段

请 PC App 在一次按下/释放过程中输出以下信息，并与手机 App 逐字段比较：

```text
timestamp
connection handle
service UUID
characteristic UUID
attribute/value handle
write type（Write Without Response）
offset
payload length
payload hex
payload ASCII
```

以同一台设备、同一固件和同一录音场景进行对照时，除 connection handle、wrapper 和时间戳外，PC App 与手机 App 的 characteristic UUID、Write 类型、payload 长度及 payload 字节必须一致。

预期关键写入应类似：

```text
con=0x005x
char=06068D1C-6B97-11EF-B864-0241AC120002
handle=0x0006
type=Write Without Response
ascii=*APP#record#1#0#1#
body_len=18
payload_len=18
payload_tail=23（字符 `#`，不得追加 `00`）
```

如果日志显示 handle 为 HID `0x0024`、HID UUID `0x2A4D`、写类型为 Write With Response，或 payload 主体不是以上 ASCII 命令，应先修正 PC App 协议适配层。

## 10. 验收标准

### 必过项

- PC App 的开始/停止 ATT 写入除连接标识外，与同版本手机 App 抓包逐字节一致。
- 连接后 RDX Notify CCC 写入 `01 00` 成功。
- 长按开始收到 `*DEV#devrec#1#0#2#`，不能误等 `*DEV#record#1#...`。
- 收到开始触发后 1 次 WNR 写入 18 字节 `*APP#record#1#0#1#`，最后一个字节为 `23`，不得追加 `00`，不得重复发送旧命令。
- 全链路不得再构造或写入 `*APP#devrec#...`。
- 固件出现 `onoff=1`、`cmd=0`、`RECORD START` 和 `JLSTREAM create_stream`。
- 开始后持续收到 RDX Notify 音频帧，且不是 HID Report。
- 松开收到 `*DEV#devrec#0#0#2#` 后，1 次 WNR 写入 18 字节 `*APP#record#0#0#1#`，最后一个字节同样为 `23`。
- 固件出现 `onoff=0`、`cmd=3`、`RECORD STOP`，音频帧停止。

### 回归项

- 连续按住/释放至少 10 次，不能出现开始无响应、停止无响应或重复启动。
- PC App 与手机 App 同时连接时，只有收到设备录音触发的 RDX owner 可以控制本次录音。
- 断开重连后重新发现特征并重新配置 CCC，不复用旧连接句柄。
- 连接存在但未开启 CCC 时，不应把“无音频”误判为录音命令失败；此时先检查 `stream_tx_ready`。

## 11. 固件侧辅助日志（当前联调固件已启用）

当前联调固件已经在 `rdx_ble_server_att_write_callback()` 的 RDX Value `0x0006` 分支打印：

```text
[RDX_APP_RX] con=<connection_handle> hdl=<wrapper> att=0x0006
             mode=<transaction_mode> offset=<offset> len=<buffer_size>
[RDX_APP_RX] ASCII: <length-bounded decoded payload>
```

该诊断由 `TCFG_RDX_APP_RX_TRACE_ENABLE` 控制。T2620 在 `apps/earphone/include/t2620_project_config.h` 中默认设为 `1`；未定义该项目覆盖的其他产品在 RDX server 中安全默认为 `0`。量产时可只在项目覆盖层把该宏改为 `0`，无需修改协议实现文件。

该日志只抓 RDX App 下行 Value，不混入 HID CCC、HID Output Report、RDX Notify CCC 或 OTA Value 写入。ASCII 输出严格按 `buffer_size` 解码，不要求 ATT payload 以 NUL 结尾；不可打印的二进制字节显示为 `.`，超过 64 字节时分行输出。手机与 PC 使用相同标签，比较时只允许 connection handle 和 wrapper 不同；handle、offset、长度和 payload 必须按本说明一致。

确认顺序必须是：

```text
att_handle=0x0006
 -> rdx_ble_server_gatt_receive_data()
 -> rdx_protocol_packet_recv()
 -> _rdx_protocol_record_msg_parse
```

如果第一步不是 `0x0006`，是写入路径错误；如果是 `0x0006` 但不是固定的 18 字节 `record` 命令，先修正 PC App payload；如果原始字节已经一致但仍没有 parser 日志，再检查分包或协议库版本。只有 parser 和 `RECORD START` 都出现后，才需要继续排查音频 Notify/编码问题。
