# RDX 框架 P12 文件传输状态与 WiFi Service Ownership 收口重构文档

> 版本：v1.2
>
> 日期：2026-08-04
>
> 上游依据：`docs/3.RDX框架JL平台复用性优化大纲.md`
>
> 实施定位：P11 完成 record/storage ownership 收口后，继续清偿大纲“阶段 5：框架精化与边界债务清偿”中遗留的文件传输状态边界。
>
> **第一硬约束：不得破坏、替换、重编译或重新打包 `librdxApp.a`，不得破坏该静态库依赖的任何 ABI、对象布局、符号、返回语义和调用时序。**

## 1. 文档目的与当前结论

P11 已建立 record/storage service、internal domain、legacy compat、JL port 和长期 Host 门禁。当前剩余的最高风险耦合，不再是 service public header 暴露 legacy 类型，而是文件传输的可变 legacy 状态 `ReqFileInfo` 仍被多个外围模块直接取得、解引用和修改。

其中 `rdx_wifi_service.c` 的 WiFi TX-complete 路径同时承担：

- 读取和修改 `ReqFileInfo`；
- 协议发送状态推进；
- uxfile 发送缓冲区清理；
- protocol busy timer 控制；
- WiFi transport timer 重启；
- JL task queue 投递；
- 失败后的固定 tick 重试。

这使 WiFi service 同时知道 transport、protocol legacy layout、文件分包状态机和 JL task message 约定，形成 P11 后最需要收口的 ownership 缺口。

P12 的结论是：

1. `ReqFileInfo` 必须继续原样存在，并继续由 legacy protocol/core 持有稳定对象；
2. 普通业务模块只应使用窄 query 或语义 command，不得继续持有可写 `ReqFileInfo *`；
3. 对 `ReqFileInfo` 的直接读写必须集中到 file-transfer internal domain / compat 边界；
4. WiFi service 只负责 transport 编排，不能成为 protocol 文件传输状态的 owner；
5. TX-complete 的同步顺序、task、消息参数、对象地址和 retry 行为必须逐项保持；
6. P12 不以全仓 `ReqFileInfo` 零命中为目标，legacy owner、静态库兼容边界和经确认的数据面允许精确保留。

P12 是独立的实施切片，不是 `docs/3.*` 中新增的“阶段 12”。它承接该大纲的阶段 5、静态库边界稳定、高风险边界可控和可验证要求。

## 2. 第一硬约束：`librdxApp.a` ABI 绝对兼容

### 2.1 静态库本体

P12 全周期禁止：

- 修改 `librdxApp.a`；
- 用其他 archive 替换它；
- 解包后重新打包；
- 重新编译其内部对象；
- 通过链接顺序或同名强符号改变其既有实现选择；
- 为实现新架构而要求静态库接受新的 DTO、snapshot 或 callback 类型。

静态库指纹属于生产验收证据，不属于默认 Host 测试。P12.0 必须在正式生产环境重新计算并归档 SHA256，P12.5 使用同一方法复核。

### 2.2 外部符号 ABI

凡 `librdxApp.a` 已引用或可能回调的旧外部符号，必须保持：

- 符号名；
- external linkage 和可见性；
- 参数数量、类型和顺序；
- 返回类型和返回值口径；
- 调用约定；
- 同步/异步属性；
- 调用线程或目标 task；
- 回调发生时机。

旧入口可以改为 thin wrapper，但不得删除、改名、改签名或改为 `static`。

P12 应重点确认并保护：

```c
ReqFileInfo *rdx_protocol_get_uploadfileInfo(void);
void rdx_protocol_file_sync_busy_timer_stop(void);
void rdx_protocol_prepared_data_clean(void);
void rdx_protocol_uploadFileInfo_clean(void);
void rdx_protocol_send_buffer_reinit(void);
void rdx_uxfile_recordFileData_send_finish(ReqFileInfo *rf_info);
```

以上清单不是完整静态库符号清单。最终保留范围以 JL 符号工具或 clean link map 的真实依赖为准。

### 2.3 `ReqFileInfo` 布局 ABI

当前兼容结构定义为：

```c
typedef struct{
    int ack;
    int file_num;
    u8 is_first_pack;
    int pack_num;
    int orig_pack_num;
    int sent_size;
    int auto_del;
    int file_offset;
    u32 total_pack;
    u32 chunk;
    u32 block_cnt;
    u8 file_send_busy;
    u8 loop;
    u8 interrupt;
    u8 send_stop;
    u8 ble_upload_cancel;
} ReqFileInfo;
```

P12 禁止：

- 增删、重排或改名字段；
- 修改字段类型；
- 将 `int` 替换为枚举、`bool` 或固定宽度类型；
- 将 `u8` 状态压缩为 bitfield；
- 增加或删除 `packed`；
- 改变 alignment、padding、`sizeof` 或任一 `offsetof`；
- 将 getter 改为返回 `const ReqFileInfo *`；
- 用第二份可写镜像替换 legacy owner 对象；
- 改变被投递到协议 task 的对象地址和生命周期。

当前 Host public contract 只保护字段名称和顺序，不能证明字段类型、offset、alignment 和整体大小。完整布局证明必须由 JL 生产工具链的编译期断言、map 或等价产物完成。

### 2.4 稳定对象与消息 ABI

当前 TX-complete 路径会把 getter 返回的同一个 `ReqFileInfo *` 作为协议发送 task 的消息参数。P12 默认把以下性质视为兼容契约：

- getter 返回 legacy owner 的真实对象；
- 对象地址在相关异步处理完成前稳定；
- task 接收方仍获得同一个对象地址；
- 消息目标仍为 `RDX_PROTOCOL_SEND_TASK_NAME`；
- 消息参数个数和解释方式不变。

在没有静态库符号、接收侧实现和目标板证据证明安全前，不得改为 snapshot 指针、临时栈对象、复制对象、索引或 event payload。

### 2.5 返回语义和行为 ABI

兼容不仅是“能链接”。以下同样不得漂移：

- legacy success/failure 数值；
- `true`/`false` 字段写入时机；
- pack 递增和回绕条件；
- ACK 清零或置位时机；
- cleanup 调用顺序；
- timer stop/start 顺序；
- delay tick 数；
- 首次 post 失败后的 retry 次数；
- 同步调用不可机械改成异步 event；
- 异步 task post 不可机械改成当前线程直接调用。

## 3. P12 范围与非目标

### 3.1 纳入范围

P12 只聚焦以下边界：

1. `ReqFileInfo` 的 owner、getter 和 caller 分类；
2. 普通业务只读 query 收口；
3. file-transfer internal domain / compat facade；
4. WiFi TX-complete 状态推进和 retry command 收口；
5. file-transfer cleanup lifecycle 边界复核；
6. JL task post 经既有 OSAL 或专用兼容入口收口；
7. 与上述改动直接相关的长期静态约束、生产构建和目标板回归。

### 3.2 明确非目标

P12 不做：

- 不修改 `librdxApp.a` 或静态库兼容头的 ABI；
- 不删除 `ReqFileInfo` 或 legacy getter；
- 不重新设计文件上传协议、分包算法、ACK 算法或 retry 策略；
- 不升级 JL SDK；
- 不改变 APP 与设备之间的协议字节流；
- 不改变 task 名称、优先级、消息格式和 timer 单位；
- 不建立第二份长期可写 file-transfer 状态；
- 不把 TX-complete 路径整体改造成 event bus；
- 不将所有 `rdx_uxfile_*` 粗暴迁入一个“大 storage service”；
- 不为消除 grep 命中而使用 `void *` 强转或宏隐藏依赖；
- 不为行数指标迁移 owner 数据面；
- 不顺带重构 `RdxProtocolIndicateOps`、WiFi info ownership 或所有 service 裸 `extern`；这些应单独审计和立项；
- 不把 production build、map、archive hash 或目标板行为塞入默认 Host 验证入口。

## 4. 当前调用拓扑与 caller 分类

### 4.1 当前高风险拓扑

```text
SPI TX done
  -> rdx_wifi_service::wifi_tx_done_cb()
     -> rdx_protocol_get_uploadfileInfo()
     -> direct ReqFileInfo mutation
     -> protocol timer / uxfile buffer cleanup
     -> WiFi transport timer stop/start
     -> delay
     -> os_taskq_post_msg(protocol send task, ReqFileInfo *)
     -> failed post delay + retry
```

这里存在四个不同 ownership：

| 对象/动作 | 正确 owner |
|---|---|
| SPI/WiFi TX-complete 回调注册、transport control | WiFi service / WiFi transport port |
| `ReqFileInfo` 和 pack/ack/loop/interrupt 状态 | file-transfer legacy domain / compat |
| uxfile send buffer lifecycle | uxfile owner / file-transfer compat |
| JL task queue 投递 | JL OSAL，兼容语义由 file-transfer compat 保持 |

WiFi service 可以发起“处理 TX complete”语义命令，但不应继续解释 legacy 字段。

### 4.2 当前 caller 表

| 文件 | 当前访问 | 分类 | P12 处理原则 |
|---|---|---|---|
| `service/rdx_wifi_service.c` | 读写 `file_send_busy`、`send_stop`、`interrupt`、`loop`、`total_pack`、`pack_num`、`ack`，并投递 owner 指针 | 最高风险状态机 | 迁入 file-transfer internal domain / compat，严格保持顺序和对象地址 |
| `rdx_app.c` quadruple-click | 读取并打印 `file_send_busy`，busy 时直接返回 | 普通业务 query | 改用窄 busy query，保持“WiFi on 优先、busy 时返回”的顺序 |
| `rdx_app.c` DUT entry | 读取并打印 `file_send_busy`，busy 时先发 STOP 再进入 DUT | 普通业务 query + command coordination | 改用窄 query；保持 OTA、record、busy 判断顺序，以及 STOP 后继续 DUT |
| `rdx_led_ctrl.c` | WiFi on 短路后读取 `file_send_busy` | UI 只读 query | 改用窄 query，保持 WiFi-on 优先和短路行为 |
| `rdx_ota.c` | `rdx_ota_proc()` 创建 `rf_info`，当前函数体未使用 | 死局部候选 | 先确认预处理结果，再作为独立机械清理 |
| `rdx_vm.c` | 仅发现 getter 的 `extern` 声明 | 死声明候选 | 全文件确认无使用后独立删除本地声明；不得据此删除 ABI 符号 |
| `rdx_record.c` local pipeline | 录音开始前读取 busy，busy 时发 STOP | owner 数据面/联动控制 | 迁移到语义 query 的候选；必须保持 STOP 发生在 buffer/timer/模式初始化之前 |
| `rdx_record.c` alternate pipeline | 与 local pipeline 相同 | 条件编译分支 | 两个构建分支必须同步迁移并分别编译验证 |
| `rdx_spi.c` exception/stuck/idle 路径 | 通过 WiFi service 查询 send-stop/busy，并发起 TX-done 或 stuck retry | 间接 file-transfer caller | 纳入 caller cutover；冻结 normal/exception/stuck 三类锁上下文；旧 WiFi API 在切换完成前保留 wrapper |
| `rdx_spi.c` low-power idle gate | 通过 WiFi busy wrapper 阻止文件发送期间进入低功耗 | 间接只读 query | P12.1 保留 wrapper 路径和 unavailable=not-busy 语义；随 SPI command cutover 一并迁移 |
| `service/rdx_device_service.c` | factory reset、user reset、system reset、unbind 等流程通过 WiFi service 查询 file busy | 间接业务 query | 改用 file-transfer public query，保持各 gate 的判断顺序和返回行为 |
| `service/rdx_storage_service.c` | format gate 通过 WiFi service 查询 file busy | 间接业务 query | 改用 file-transfer public query，保持 busy 时禁止格式化的行为 |
| `service/rdx_wifi_service.h` 既有 query/command | 被 SPI、device、storage 等 caller 使用 | 迁移期兼容 facade | 全部 caller cutover 前保留为 thin wrapper；未经外部契约审计不得删除 |
| `rdx_uxfile.h` 及 legacy 实现 | 定义结构和接收 `ReqFileInfo *` | ABI owner/compat | 精确保留，不以零命中为目标 |
| `librdxApp.a` 内部 | `rdx_protocol.c.o` 定义 getter 和 local send task；`rdx_uxfile.c.o` 定义 send-finish；`xxpUart.c.o` 引用 getter | 不可变 third-party core | 已知符号关系纳入基线；task 消息槽位解析、对象存储和生命周期仍须 P12.0 取证 |

caller 审计必须同时覆盖两类依赖：

1. 直接声明 getter、取得或解引用 `ReqFileInfo *` 的 caller；
2. 通过 `rdx_wifi_service_is_file_send_busy()`、`rdx_wifi_service_is_send_stopped()`、`rdx_wifi_service_retry_on_stuck()`、`rdx_wifi_service_on_tx_done()` 间接访问 file-transfer 状态或命令的 caller。

P12 不得只以 `ReqFileInfo` 文本命中作为 caller 完整性的判断依据。旧 WiFi service API 在全部直接和间接 caller 完成 cutover 前必须保留为 thin wrapper；删除或改签名必须另有外部契约和链接证据。

### 4.3 已确认的录音联动顺序

`rdx_record_run_init()` 的两个条件编译实现都在初始化录音数据之前执行：

```text
get upload info
  -> if file_send_busy: file command STOP
  -> clear audio buffer/length
  -> UI notify
  -> stop record max timer
  -> decide online/offline mode
  -> continue storage/record initialization
```

P12 若迁移该 caller，只替换“如何查询 busy”，不得顺带调整上述调用顺序或改变 NULL 行为。两个实现必须作为一个行为单元处理，不能只改当前默认分支。

### 4.4 死代码清理边界

`rdx_ota.c` 的未使用局部和 `rdx_vm.c` 的未使用 extern 仅是本地源码清理候选：

- 删除局部变量或本地声明不等于删除 legacy 符号；
- 必须确认所有相关条件编译组合；
- 应独立提交，避免与 TX-complete 行为迁移混杂；
- 不将“编译器当前未报 warning”当作使用证据。

## 5. WiFi TX-complete 行为冻结

P12.0 必须把当前行为记录为迁移前基线。P12.3 的新实现必须逐项等价。

### 5.0 执行上下文与锁语义

当前三个入口具有不同的锁上下文：

```text
normal SPI write-complete:
  hold spi_manager.pxMutex
    -> synchronous TX-done callback
    -> state advance / cleanup / delay / task post
    -> callback returns
  -> spi_mutex_unlock

SPI exception:
  -> clear SPI state
  -> spi_mutex_unlock
  -> synchronous TX-done callback

SPI stuck retry:
  -> lock and clear SPI state
  -> spi_mutex_unlock
  -> file-transfer retry command
```

P12 必须冻结：

- normal callback 发生在 SPI mutex unlock 之前；
- exception callback 和 stuck retry 发生在 unlock 之后；
- 三个入口均保持当前同步属性；
- normal 路径中的 cleanup、transport timer control、delay 和 task post 相对 unlock 的位置不变；
- 不得为了缩短锁持有时间而在本轮将状态推进迁到其他 task、event bus 或 unlock 之后。

当前持锁执行 delay 是否值得优化，不属于 P12；若后续需要优化锁粒度，必须独立立项并证明并发和 timing 等价。

### 5.1 NULL owner

```text
get ReqFileInfo owner
  -> NULL: 立即返回
```

不得在 NULL 时执行 buffer cleanup、timer control、delay 或 task post。

### 5.2 公共前置动作

```text
if file_send_busy == true
  -> file_send_busy = false
```

该动作发生在 `send_stop` 和 `interrupt` 分支判断之前。不得移动到 normal 分支，也不得改成延后清理。

### 5.3 `send_stop` 分支

精确顺序：

```text
protocol file-sync busy timer stop
  -> record file send buffer free
  -> prepared data clean
  -> if WiFi transport control exists:
       data-transfer timer stop
       data-transfer timer start
  -> interrupt = false
  -> return
```

约束：

- timer stop/start 是两个有序调用，不得合并为“restart”而缺少等价证明；
- transport/control 为 NULL 时仍须继续清 `interrupt`；
- `interrupt=false` 发生在 cleanup 和 transport timer control 之后；
- 此分支不投递 protocol send task；
- 不增加对 `loop` 的判断。

### 5.4 `interrupt` 分支

精确顺序：

```text
if interrupt == true
  -> interrupt = false
  -> if loop == true
       post protocol send task with the same ReqFileInfo owner pointer
  -> end
```

约束：

- 必须先清 `interrupt`，再判断/投递；
- 当前该分支不 delay、不检查 post 结果、不 retry；
- 不得为“统一错误处理”改变这一行为。

### 5.5 normal loop 分支

精确顺序：

```text
if loop == true
  -> if total_pack > pack_num
       pack_num++
       ack = 0
     else
       pack_num = 0
       ack = 0
  -> delay 2 ticks
  -> first post(protocol send task, same owner pointer)
  -> if first post != OS_NO_ERR
       delay 1 tick
       second post(protocol send task, same owner pointer)
```

约束：

- 比较条件必须保持严格大于 `total_pack > pack_num`；
- `ack=0` 在两个 pack 分支中都执行；
- 先更新状态，后 delay，再 post；
- 只对第一次 post 的返回值进行判断；
- 第二次 post 的返回值当前被忽略，P12 不擅自增加额外 retry；
- 两次投递参数都必须是同一个稳定 owner 指针。

### 5.6 stuck retry command

当前行为：

```text
get owner
  -> owner exists
  -> loop == true
  -> send_stop == false
  -> interrupt == false
  -> ack = 1
  -> post protocol send task with the same owner pointer
```

约束：

- 不增加 delay；
- 不清 `file_send_busy`；
- 不修改 pack number；
- 不对 post 失败追加 retry；
- 条件和写入顺序保持不变。

### 5.7 OSAL 迁移特别约束

仓库已存在 `rdx_os_task_post_msg()`，但它与当前 legacy pointer-message 存在两层不等价：

1. 公开参数使用 `u32 arg`，实现还会将值转换为目标 `int`，指针是否可无损承载必须由 JL ABI 证明；
2. 当前 legacy 调用 `os_taskq_post_msg(task, 1, owner)` 投递一个参数，owner 位于第一个消息参数槽；现有 OSAL 使用 `os_taskq_post_type(..., Q_MSG, 2, {msg, arg})` 投递两个参数，会改变参数个数和槽位布局。

因此 P12 不得机械替换为：

```c
rdx_os_task_post_msg(task, msg, (u32)owner);
```

仅证明 `sizeof(void *) == sizeof(u32)` 仍不足以采用该 API。P12.0 还必须确认 archive 内 `rdx_protocol_send_task` 对消息参数个数和槽位的解释。

优先方案是提供语义精确的 compat wrapper，例如：

```c
int rdx_file_transfer_compat_post_owner(
    const char *task_name,
    ReqFileInfo *owner);
```

其 JL 语义必须保持等价于：

```c
os_taskq_post_msg(task_name, 1, owner);
```

也可以扩展 OSAL 为明确的单 pointer 参数 API，但 jl7018 与 shadow port 必须保持：

- 参数个数仍为 1；
- owner 仍位于接收侧原消息槽；
- 返回值仍可按 `OS_NO_ERR` 判断；
- 不经过未经证明的 `u32`、`int` 或索引转换。

service 源码最终不再直接调用 JL task API，但不能以改变 receiver 消息布局或丢失指针语义为代价。

## 6. 目标架构

### 6.1 依赖方向

```text
Application / LED / Record coordination
        ↓ narrow query / semantic command
WiFi Service
        ↓ TX-complete semantic notification
File-transfer Internal Domain
        ↓ legacy-state operation contract
File-transfer Compat
        ↓ unchanged symbol/layout/task-message ABI
librdxApp.a / rdx_uxfile legacy owner

File-transfer Compat
        ↓ pointer-safe task post
JL OSAL or dedicated JL compat port

WiFi Service
        ↓ timer control only
rdx_wifi_transport_ops_t
```

### 6.2 职责划分

#### 普通业务 caller

只允许依赖无 legacy 类型的 public 语义 API。由于当前 caller 的 NULL 行为并不一致，不能在设计阶段默认将 owner NULL 等同于 idle。推荐采用可区分 unavailable/idle/busy 的查询契约，例如：

```c
typedef enum {
    RDX_FILE_TRANSFER_STATE_UNAVAILABLE = 0,
    RDX_FILE_TRANSFER_STATE_IDLE,
    RDX_FILE_TRANSFER_STATE_BUSY,
} rdx_file_transfer_state_t;

rdx_err_t rdx_file_transfer_get_state(
    rdx_file_transfer_state_t *state);
```

也可以使用项目风格一致的等价 API，但实施前必须明确选择并记录以下策略之一：

1. 证明 getter 在相关 caller 执行期永不为 NULL，并把 non-NULL 作为初始化后的硬前提；
2. 将 NULL-safe 行为作为独立批准的 bugfix，单独提交和回归；
3. 使用可区分 unavailable/idle/busy 的 query，由 caller 显式处理 unavailable。

不得将 owner NULL 静默映射为 idle 后仍声称行为完全不变。public service header 不得暴露 `ReqFileInfo`。

#### WiFi service

负责：

- 注册 RX/TX transport callback；
- 提供 transport control 能力；
- 在 TX-complete 时调用 file-transfer 语义入口；
- 保持 WiFi power、connection 和 LED 编排。

不负责：

- 解释 `pack_num`、`ack`、`loop`、`interrupt`、`send_stop`；
- 取得 `ReqFileInfo *`；
- 直接调用 uxfile cleanup；
- 直接向 protocol task 投递 legacy owner；
- 成为 file-transfer 状态 owner。

#### File-transfer internal domain

负责：

- 对外提供 narrow query 和 command；
- 定义 TX-complete 的语义分支；
- 确保只有受控实现能发起 legacy 状态变更；
- 协调 compat cleanup 与 WiFi timer control，但不暴露 legacy DTO；
- 不创建第二份 authoritative transfer state。

#### File-transfer compat

负责：

- 调用 legacy getter；
- 读取/修改真实 `ReqFileInfo` owner；
- 保持 getter、结构体、uxfile 和 protocol task 的 ABI；
- 保持 cleanup、pack、ACK、delay、post、retry 的精确顺序；
- 隔离 legacy symbol 和 legacy result；
- 必要时接收窄小的 transport timer callback/vtable，避免反向依赖整个 service。

### 6.3 API 与头文件分层原则

推荐采用明确的三层头文件边界：

```text
service/rdx_file_transfer_service.h
    对 app / LED / SPI / device / storage / record 暴露无 legacy 类型的 query/command

internal/rdx_file_transfer_domain.h
    仅供 file-transfer service implementation 与 domain 内部使用

compat/rdx_file_transfer_compat.h
    仅供 domain/compat 使用；允许识别 ReqFileInfo 和 legacy symbol
```

普通业务模块不得直接 include `internal/` 或 `compat/` header，否则 private API 实际会成为跨模块公共契约，长期门禁也无法准确表达边界。

P12 文档不提前冻结具体函数名，但实现必须满足：

- query 不返回内部指针；
- command 不接受 `ReqFileInfo *`；
- snapshot 如确有需要只能是只读语义副本，不能成为第二状态源；
- TX-complete command 必须能够同步完成当前状态推进和投递动作；
- transport timer capability 应窄化，不让 compat include WiFi service implementation；
- 普通 caller 只依赖 public file-transfer service/query header；
- internal/compat header 不进入普通业务 include 链；
- legacy getter 继续保留供静态库/compat 使用。

**目标**：建立唯一 legacy 状态访问边界，但暂不切换高风险 callback。

## 9. 长期静态约束设计

P12 完成迁移后，再收紧 `tests/host/test_rdx_architecture.ps1`。规则必须保护模块边界，不冻结实现文本或调用次数。

### 9.1 推荐约束

1. `ReqFileInfo` 只允许出现在：
   - `rdx_uxfile.h`；
   - 明确的 legacy owner 源码；
   - `internal/rdx_file_transfer_*`；
   - `compat/rdx_file_transfer_*`；
   - 经 P12.0 证明必须保留的静态库兼容文件。
2. getter 只允许由 file-transfer owner/compat 调用。
3. service public header 禁止出现：

```text
ReqFileInfo
rdx_protocol_get_uploadfileInfo
uxfile_* type
OS_* / JL private type
```

4. service 源码不得直接调用：

```text
os_taskq_post_msg
os_taskq_post_type
sys_timeout_*
sys_timer_*
```

当前 Host service OSAL 规则未覆盖 `os_taskq_post_msg`，因此迁移前的 WiFi service 会假通过；该缺口必须在 P12.3 完成后修复，启用前先确认精确 allowlist，避免阻断未纳入 P12 的真实 owner 数据面。

5. `rdx_wifi_service.c` 不得直接调用 `rdx_uxfile_*`。
6. 普通业务模块不得 include file-transfer `internal/` 或 `compat/` header。

### 9.2 Public contract 增强

继续保留当前 `ReqFileInfo` 字段顺序检查，并补充关键 declaration：

```c
ReqFileInfo *rdx_protocol_get_uploadfileInfo(void);
void rdx_uxfile_recordFileData_send_finish(ReqFileInfo *rf_info);
```

但不得把 PowerShell 文本匹配描述成完整二进制 ABI 证明。

### 9.3 启用时机

- 不在生产代码迁移前提前启用导致历史路径全部失败；
- 每完成一个 caller 类别，就缩小对应 allowlist；
- final 规则只保留真实 owner/compat；
- 不追求结构名全仓零命中。

## 11. 风险登记与停止条件

| 风险 | 典型后果 | 缓解/停止条件 |
|---|---|---|
| 误改 `ReqFileInfo` layout | 静态库错读字段、内存破坏 | 任何 layout 差异立即停止；恢复原定义 |
| 用 snapshot 替换 owner 指针 | task 消费陈旧状态、生命周期错误 | 禁止替换；必须继续投递稳定 owner |
| pointer 强转为 `u32` 未证明 | 截断或消息解析漂移 | 无 JL ABI 证据不得采用 |
| cleanup 重排 | 重复释放、timer 竞态、残留状态 | 行为表逐项对比，任一差异停止 |
| event 化 TX-complete | 线程和 timing 改变 | P12 禁止整体 event 化 |
| 统一 retry 行为 | interrupt/normal 分支行为漂移 | 各分支保持原 retry 规则 |
| query 引入 NULL 新语义 | 掩盖或改变历史故障模式 | P12.0 先确定 non-NULL 前提、独立 bugfix 或三态 query；不得静默映射为 idle |
| 忽略间接 caller | 删除 wrapper 后编译失败或 ownership 残留 | 同时审计 SPI/device/storage 等 WiFi facade caller |
| 改变 SPI mutex 上下文 | timing、ring buffer 或握手并发变化 | 冻结 normal callback 在 unlock 前，exception/stuck 在 unlock 后 |
| 只证明指针宽度 | task argc/slot 漂移，receiver 读错参数 | 同时证明参数个数、槽位和 receiver 解析；优先专用 pointer wrapper |
| Host OSAL 规则假通过 | service 仍直连 JL API 却显示 PASS | P12.3 后将 `os_taskq_post_msg` 纳入精确门禁 |
| 只编译默认分支 | alternate record pipeline 失效 | 两个条件编译实现都必须验证 |
| 过早收紧门禁 | 历史 owner 路径阻塞迁移 | caller cutover 后逐步缩 allowlist |
| 以 Host 检查替代 ABI 证明 | 假通过 | final 必须有 JL clean link/map/layout/hash |
| 大提交混合多个边界 | 无法定位回归和回滚 | 每个 commit 只有一个 ownership 主题 |

出现以下任一情况，应停止当前切片并回到 P12.0 补证据：

- getter 定义或对象 owner 不明确；
- task 接收侧无法确认参数个数、owner 所在槽位或参数解释；
- query 的 NULL policy 未明确；
- normal/exception/stuck 的同步与 SPI mutex 上下文未冻结；
- static library hash 发生变化；
- legacy symbol 减少或签名变化；
- `sizeof/offsetof` 变化；
- TX-complete trace 顺序变化；
- 默认 CC clean ELF 链接失败；
- 目标板出现重复包、漏包、死锁、重复释放或异常重启；
- Flash/RAM 超出阶段预算且无法解释。

## 12. 提交与回滚策略

### 12.1 推荐提交序列

```text
P12.0  docs/test: 冻结 file-transfer ABI 与行为基线
P12.1a refactor: 增加 file-transfer 窄 query
P12.1b refactor: 切换 app/LED/record 只读 caller
P12.1c cleanup: 删除确认无用的 OTA/VM 本地引用
P12.2  refactor: 建立 file-transfer domain/compat 边界
P12.3  refactor: 收口 WiFi TX-complete 与 retry ownership
P12.4  test: 固化 file-transfer ownership 和 public contract
P12.5  docs: 归档生产构建与目标板验收
```

实际提交信息以最终 diff 为准。不得把未完成验证的多个阶段压成一个大提交。

### 12.2 回滚原则

- 每个 caller cutover 可独立回滚；
- 新 facade 落地时先保持旧入口，后切 caller；
- 不在同一提交中同时删除旧实现并切换所有调用者；
- TX-complete 切片异常时可直接恢复 WiFi service 原 callback，不影响前置 query 收口；
- 不通过修改静态库解决外围回归；
- 不使用全局行为开关长期维持两套 authoritative state machine。

### 架构

- [ ] 普通业务和 service public header 不暴露 `ReqFileInfo`；

## 15. 最终原则

P12 的目标不是让 legacy 消失，而是让 legacy **被正确地关在兼容边界内**。

正确方向：

```text
保留真实 ReqFileInfo owner 和全部 ABI
  + 用 domain/compat 集中解释 legacy 状态
  + 普通业务使用窄 query/command
  + WiFi service 回归 transport 职责
  + 用生产证据证明布局、符号、时序和行为不变
```

错误方向：

```text
复制状态
  / 修改结构
  / 强转隐藏依赖
  / 机械 event 化
  / 机械 OSAL 化
  / 为零 grep 命中迁移 owner 数据面
  / 用 Host 文本检查替代 JL ABI 和目标板验证
```

在静态库不可变的前提下，**加法式 facade、稳定 owner、窄语义接口、逐切片验证**是 P12 唯一可接受的推进方式。
