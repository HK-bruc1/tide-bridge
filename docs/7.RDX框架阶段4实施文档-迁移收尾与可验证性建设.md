## 1. 阶段目标

阶段 4 做三件事：

1. **阶段 3 应用层迁移收尾**：把阶段 3 checkpoint 转交的剩余 handler、event bus 业务 cutover、WiFi/LED 残留清理完成，让 `rdx_app.c` 真正退化为协调器。
2. **构建矩阵验证**：补齐阶段 3 因环境缺失未跑的 clean build，验证 board/chip family 隔离性。
3. **可验证性体系建设**：落地 host mock、统一错误码、启动诊断日志、本地/CI 验证脚本，使后续复用修改可追踪、可回归。

阶段 4 不是单纯测试阶段，而是 **"迁移收尾 + 验证闭环"**。先做必要的架构收口，再把测试体系建立在已收敛的边界上。

## 3. 设计原则

1. **先收口再测试**：不把测试体系建立在未完成的迁移中间态上。先完成 BLE event bus、剩余 handler、LED/WiFi 残留清理，再围绕稳定边界写 mock 和脚本。
2. **ABI 继续保留**：所有阶段 3 遗留的旧符号（`rdx_app_wifi_handle`、`rdx_app_emmc_*`、`rdx_led_ctrl_*`）继续保留 thin wrapper，不能删除或改签名。
3. **禁止双路径长期存在**：BLE event bus 要么完成 cutover，要么回滚；不能长期"直接调用 + 业务订阅"并行。
4. **测试要可本地执行**：host mock、配置校验脚本、静态边界检查脚本必须能在无目标板环境下运行。
5. **构建矩阵是硬验收**：阶段 4 必须验证至少三个构建组合，这是阶段 3 未完成的硬债务。

## 4. 任务分解

### 4.1 任务 A：阶段 3 应用层迁移收尾

#### A.1 剩余 handler 迁出

`rdx_app.c` 仍注册 11 个 handler。阶段 4 先把 `RTC` 和 `OFFTIME_SET` 迁出，再迁移剩余 handler：

| Handler | 目标归属 | 优先级 | 关键依赖/风险 |
|---|---|---|---|
| `RECORD_MODE_QUERY` | `rdx_record_service` | P1 | 低风险查询 |
| `BT_NAME_QUERY/SET` | `rdx_device_service` | P1 | 名称管理，可能涉及 `librdxApp.a` 回调 |
| `BLE_NAME_QUERY/SET` | `rdx_device_service` | P1 | 同上 |
| `SD_MEM_QUERY` | `rdx_storage_service` | P1 | 异步查询，需 event 或 callback 反馈 |
| `FILE_DELETE` | `rdx_storage_service` | P1 | 简单透传 |
| `RTC` | `rdx_time_service`（新） | P0 | 跨模块：设置 RTC + 修正录音 `uxfile start_time`；依赖 `rdx_rtc_*` 和 `rdx_record_get_status` |
| `OFFTIME_SET` | `rdx_device_service` | P1 | 关机策略，低风险 sys API |
| `AUDIO_STREAM` | `rdx_record_service` | P1 | 录音数据路径 |
| `FLASHNOTE` | `rdx_record_service` | P2 | 条件编译，使用率低 |

**决策**：
- P0 `RTC` 优先迁到新建的 `rdx_time_service`，因为它不是纯查询，涉及 time ops 和 record 状态协作。
- `OFFTIME_SET` 迁到 `rdx_device_service`，与设备生命周期/关机策略一致。
- 名字类查询统一归 `rdx_device_service`。
- 每个 handler 迁出前必须检查 `librdxApp.a` 是否通过回调结构体依赖其实现；若依赖，保留 `rdx_app_*` wrapper 转发。

**RTC 跨模块协作机制**：
- 新增事件 `RDX_EVENT_TIME_SYNCED`，由 `rdx_time_service` 在 RTC 设置成功后发布。
- payload 必须包含 `timestamp`（至少 4 字节，类型 `time_t` / `u32`）。
- `rdx_record_service` 订阅该事件，在回调中修正录音 `uxfile start_time`。
- `rdx_time_service` 内部使用 `rdx_event_publish_async()` 发布事件，避免在协议处理上下文执行重逻辑。
- `rdx_record_service` 的事件回调只更新状态/时间戳，不直接触发传输或阻塞操作。

> **阶段 4 执行结果**：`RTC` handler 已迁入 `rdx_time_service.c`。`RDX_EVENT_TIME_SYNCED` 事件已实现：
> - `rdx_time_service.c` 在 RTC 设置成功后通过 `rdx_event_publish_async()` 发布事件。
> - `rdx_record_service.c` 订阅该事件并在回调中修正录音 `uxfile start_time`。
> - 时序敏感的状态读取仍保留在 `rdx_time_service.c` 内直接调用 `rdx_record_get_status()`，用于决策是否发布事件。


#### A.2 BLE event bus 业务 cutover

当前状态：`rdx_ble_service.c` 直接调用 record 接口，同时发布事件；`rdx_record_service.c` 订阅事件但只 logging。

阶段 4 必须二选一：

**方案 A：完成 cutover（推荐）**
1. 在 `rdx_record_service.c` 事件回调中实现原 `rdx_ble_service.c` 直接调用的等价业务逻辑。
2. 删除 `rdx_ble_service.c` 中的直接调用。
3. 验证 BLE 连接/断开后的录音行为与阶段 2 一致。
4. 执行 BLE 录音 30s 冒烟测试。

**方案 B：回滚 event bus**
1. 如果 cutover 风险过高或时间不足，删除 `rdx_record_service.c` 的 BLE 事件订阅和 `rdx_ble_service.c` 的事件发布。
2. 保持阶段 2 的直接调用路径。
3. 把 event bus cutover 整体推迟到后续专门阶段。

**禁止**：长期保留"直接调用 + 业务订阅"双路径。

> **阶段 4 执行结果**：采用方案 A **部分完成**。`rdx_ble_service_on_connected/disconnected()` 的 record 直接调用已删除，业务逻辑移入 `rdx_record_service` 的 BLE 事件订阅者。**但 `rdx_ble_service_stop_recording()` 仍直接操作 `RecordStatus` 并调用 `rdx_record_process()`，`cleanup_protocol_state()` 仍直接操作 `uxfile/protocol`**。完整 cutover 延期到阶段 4B 或 Stage 5。

#### A.3 WiFi transport / app 残留清理

目标：
1. 引入 `rdx_wifi_transport_ops_t` 小 vtable，把 `xxp_esp32_wifi_open/close/control/tx/rx_done` 等直接硬件调用收口到 port 层。
2. `rdx_wifi_service.c` 通过 vtable 操作 WiFi transport，不再直接 extern 调用 `xxp_esp32_*`。
3. `rdx_app.c` 中的 WiFi event consumer 和历史 extern 声明清理或迁移到 `rdx_wifi_service.c`。
4. `rdx_app_wifi_handle()` 保留为 ABI wrapper，但内部只转发到 `rdx_wifi_service_*`。

范围控制：
- vtable 只覆盖 RDX 当前真实调用的 5-7 个函数，不覆盖 `xxpUart` 内部细节。
- 不追求一步到位的通用 WiFi 抽象，先解决 JL ESP32 桥接这一具体场景的依赖方向问题。

#### A.4 LED 场景控制 full hook

当前状态：`rdx_app.c:1371` 仍直接调用 `rdx_led_ctrl_restore_system_state()`；`rdx_hook_led_*` 只用于 init。

阶段 4 目标：
1. 在 [`service/rdx_default_hooks.h`](../SDK/apps/common/third_party_profile/rdx_protocol/service/rdx_default_hooks.h) 扩展弱符号钩子：
   - `rdx_hook_led_set_scene(u8 scene)`
   - `rdx_hook_led_restore_system_state(void)`
2. 替换业务层直接调用点：`rdx_ble_server.c`、`rdx_charge.c`、`rdx_dut.c`、`rdx_record.c`、`rdx_ota.c`、`rdx_wifi_service.c` 等。
3. 保留 `rdx_led_ctrl.c` 内部自调用和板级驱动细节，只把业务触发点改走 hook。
4. 默认 weak 实现为空，产品覆盖时实现具体灯效。

> **阶段 4 执行结果**：hook API 已扩展（新增 `rdx_hook_led_set_scene` / `rdx_hook_led_restore_system_state` / `rdx_hook_led_set_charge_state_by_battery` 三个 weak hook），业务层调用点（`rdx_app.c`、`rdx_wifi_service.c`、`rdx_ble_server.c`、`rdx_dut.c`、`rdx_record.c`、`rdx_ota.c`、`rdx_charge.c`）已替换。`rdx_led_ctrl.c` 内部驱动细节保留，不属于业务层绕过 hook 的问题。


#### A.5 RTC path 宏收口

当前 `RDX_RTC_PATH_SEL` 等宏仍出现在 `rdx_app.c` 中。阶段 4 目标：
1. 把 RTC path 选择收口到 `rdx_time_ops_t` 或 `rdx_time_service` 初始化。
2. 启动日志通过 time ops 获取当前 RTC path，不再直接访问 board/product 宏。
3. board config 只提供"是否支持硬件 RTC"等能力开关，不提供路径策略宏。

#### A.6 `rdx_app.c` 指标收口

目标：
- `rdx_app.c` 行数 ≤ 2000。
- `rdx_app.c` 函数数 ≤ 50。

如果完成 A.1-A.5 后仍未达标：
1. 列出剩余函数清单。
2. 对每个函数给出保留原因（ABI wrapper、跨 service 编排、产品特定入口）。
3. 明确哪些函数必须保留到 Stage 5（如果有）。

#### C.3 启动诊断日志

当前启动日志已打印 transport、storage、rtc_path。阶段 4 补齐并固化：

```text
RDX: product=xxx board=xxx chip=xxx sdk_ver=xxx transport=xxx storage=xxx rtc_path=xxx
```

   - 统计通过率。
   - 入口：`tests\host\run_tests.bat`。

4. **运行时要求**：
   - 本地脚本总运行时间 ≤ 10 分钟。
   - 无目标板依赖。
   - 不依赖 Python。

## 7. 风险与缓解

| 风险 | 严重度 | 缓解 |
|---|---|---|
| BLE event bus cutover 改变同步语义 | 高 | 分两层验证：host mock 验证事件链路，目标板验证时序/硬件行为；必须伴随 BLE 录音 30s 冒烟测试。若风险不可控则回滚。 |
| RTC handler 跨模块依赖复杂 | 中 | 先扫描 `rdx_rtc_*`、`rdx_record_*`、`rdx_uxfile_*` 依赖关系；新 `rdx_time_service` 通过 event 通知 record service 修正 `start_time`。 |
| WiFi transport vtable 设计过度 | 中 | 只抽象当前真实调用的 5-7 个函数；不覆盖 `xxpUart` 内部。 |
| 构建矩阵验证环境仍缺失 | 高 | 阶段 4 把 make 工具安装/环境配置作为前置任务；若仍无法解决，必须在文档中明确标注并制定替代验证方案。 |
| host mock 与目标代码行为不一致 | 中 | mock 只验证业务逻辑路径，不模拟时序和硬件；关键时序路径仍依赖目标板冒烟测试。 |
| `rdx_app.c` 行数难降到 2000 | 中 | 允许保留必要的 ABI wrapper 和编排函数；未达标时必须有剩余函数清单和 Stage 5 计划，不得强行迁移边界不清的逻辑。 |
