# 10-2.离线在线模式转换时的体验优化

## 1. 文档目的

本文记录离线录音接入 APP、APP 双路录音断连转离线、KEY5 纯在线录音断连结束，以及模式转换期间的灯效体验优化，并定义控制回执与验收边界。

当前状态（2026-09-22）：本次优化已完成，用户确认录音转换流程及灯效正常。最终业务影响评估和验证范围见第 16 节；前文问题及阶段性待验收项保留为过程记录。

本文关注以下流程：

```text
离线开始录音 → APP 建立 BLE 连接 → APP 显示录音状态和时长
                         ├─ 暂停
                         ├─ 恢复
                         ├─ 录音标记
                         └─ 停止
```

目标是让 APP 对每一个控制命令都能得到明确、及时且可关联到当前录音会话的结果，同时保持原有离线录音文件连续追加能力。

## 2. 当前问题

实机日志 `COM3_2026-09-22_13-48-59.log` 显示，离线录音连接 APP 后：

- `*APP#record#2#0#1#` 被正确解析，日志进入 `RECORD PAUSE`，说明暂停动作已经执行。
- 暂停后文件保持打开，日志为 `keep open ... will resume append same raw`，说明录音文件没有被错误切断。
- 暂停后没有及时出现对应的 `*DEV#record#...` 状态回执，APP 随后约每 0.5 秒重复发送同一暂停命令，最终表现为“暂停指令错误”或超时。
- 第一次 `*APP#recmark#` 已经写入本地标记：`added: sn=2 ... idx=1`，但同时出现 `local mark has no RDX uplink`，说明标记成功了，却没有回传给 APP。
- 直到停止录音时才出现最终的 `*DEV#record#0...`，因此停止操作的反馈相对正常。

因此，当前主要缺陷不是暂停或标记动作完全失败，而是离线录音会话在连接 APP 后没有完整接入在线 RDX 会话反馈链路。

## 3. 根因判断

### 3.1 离线录音和在线连接状态没有完成会话绑定

离线录音开始时不存在 APP 对应的在线 RDX owner/session token。APP 后续连接时，设备可以同步当前录音状态，但录音模块仍可能把自己视为本地离线会话。因此标记操作只能落地到本地，无法找到有效的 BLE 回执目标。

### 3.2 暂停和恢复缺少命令级确认

暂停、恢复属于异步录音控制操作。当前实现执行了录音状态切换，但没有保证每次状态切换都向当前 APP owner 发送一次可识别的状态回执。APP 无法区分“命令仍在处理”和“命令失败”，于是重复下发命令。

### 3.3 重复命令没有按幂等操作处理

APP 因未收到回执而重复发送暂停时，设备应返回当前已经处于 PAUSE 的状态，而不是让重复请求继续进入错误路径。恢复命令也应遵循同样规则。

## 4. 目标行为

### 4.1 离线转在线

1. 保留原录音文件、文件序号、开始时间、已录音时长和已有标记。
2. APP 完成合法 BLE/RDX 连接后，将当前录音会话绑定到当前 RDX owner/session token。
3. 绑定只改变控制和回执归属，不重新创建录音文件，不重置计时，不把离线录音改成另一种文件格式。
4. 绑定完成后主动发送一次当前录音状态快照，至少包含运行状态、文件序号、文件名和当前有效录音时长。

### 4.2 暂停和恢复

- 录音中收到暂停：切换为 PAUSE，停止采集流但保留文件句柄和会话上下文，并立即发送 PAUSE 状态回执。
- 已经是 PAUSE 时再次收到暂停：按幂等成功处理，再发送当前 PAUSE 状态，不报告未知错误。
- 暂停状态收到恢复：继续向同一文件追加，扣除暂停时长后恢复有效录音时长，并立即发送 RESUME 状态回执。
- 已经在录音时再次收到恢复：按幂等成功处理，再发送当前录音状态。
- 每个回执必须使用当前有效的 RDX owner，禁止发送到已经断开的旧连接。

### 4.3 录音标记

- 录音处于 START/RESUME 时，APP 标记应写入当前会话并回传成功结果。
- 标记结果应包含文件序号、文件名、标记序号、扣除暂停后的有效偏移和来源。
- 录音处于 PAUSE 或 STOP 时，返回明确的 `BAD_STATE` 结果，不让 APP 等待超时。
- 标记达到上限或命中去重窗口时，返回 `FULL` 或 `BUSY`，并保留现有本地 LED/存储行为。
- 离线阶段产生的本地标记在 APP 尚未连接时可以不回传；APP 连接并绑定后，不应把旧标记重复上报为新的标记事件。

## 5. 实现边界

建议沿用现有接口和状态定义：

- `SDK/apps/common/third_party_profile/rdx_protocol/rdx_record.c`：负责录音状态、暂停累计时长、标记存储和会话 token 校验。
- `SDK/apps/common/third_party_profile/rdx_protocol/rdx_app.c`：负责 APP 命令投递到 `app_core`，并保证命令生命周期安全。
- `SDK/apps/common/third_party_profile/rdx_protocol/rdx_ble_server.c`：负责当前 RDX owner、连接变化和状态同步时机。
- `SDK/apps/common/third_party_profile/rdx_protocol/rdx_protocol.h`：沿用 `*APP#record#2#/3#`、`*APP#recmark#` 以及对应 `*DEV#` 回执格式，不新增第二套录音控制协议。

实现时必须满足：

1. 会话 token 在离线转在线绑定、断连、重连和停止录音时保持单调有效性检查。
2. 异步录音任务完成状态切换后再发送成功回执，不能在动作尚未完成时提前报告成功。
3. 断连后产生的旧回执必须丢弃，不能发送给新连接或新录音会话。
4. 录音文件仍使用现有暂停后追加策略，停止时统一完成保存、DAT 标记持久化和最终状态上报。

## 6. 验收标准

### 6.1 正常流程

- 离线录音 30 秒后连接 APP，APP 能看到正确文件和有效时长。
- 点击暂停后 1 秒内显示 PAUSE，设备停止采集但不关闭当前文件。
- 点击恢复后 1 秒内显示 RESUME，录音继续追加到原文件。
- 暂停期间点击标记，APP 收到明确的 `BAD_STATE`，不显示模糊的“指令错误”。
- 恢复录音后点击标记，APP 收到一次成功回执，标记偏移扣除暂停时长。
- 点击停止后文件可正常保存、回取和播放。

### 6.2 重复和竞态流程

- 连续发送两次暂停，只产生一个状态转换，但两次请求都能得到当前 PAUSE 结果。
- 连续发送两次恢复，只产生一个状态转换，但两次请求都能得到当前 RESUME 结果。
- 暂停、恢复或标记过程中断开 BLE，不得崩溃、死锁或破坏文件；旧回执必须丢弃。
- 断开后重新连接 APP，状态快照应绑定新 owner，不能泄漏旧连接的 CCC 或回执。
- 录音停止后再发送暂停、恢复、标记，均返回明确的非活动状态结果。

### 6.3 日志要求

量产调试日志至少应能区分：

- 离线录音会话绑定在线 owner；
- PAUSE/RESUME 状态转换及回执；
- 标记成功、拒绝、去重和达到上限；
- stale token 回执丢弃；
- 停止保存完成及最终状态回执。

## 7. 结论

这项优化的重点是把“离线录音已经执行的本地动作”转换成“APP 可以确认的在线会话结果”。暂停、恢复和标记都应具备明确回执、幂等处理和当前连接归属。完成后，用户在离线转在线场景下看到的录音状态、计时、暂停、标记和停止结果应保持一致，不再因缺少回执而误报指令失败。

## 8. 2026-09-22 回归：断开后继续录音无法重连

### 8.1 实机证据与原因

日志：`COM3_2026-09-22_15-25-31.log`。用户确认首轮离线转在线控制已可用。

- 15:26:37 暂停成功并发送 `*DEV#record#2#...`；15:26:42 恢复成功并发送 `*DEV#record#3#...`。
- 15:26:58 APP 主动断开，设备继续录音并恢复广播，但运行时报告 `busy: record state=2` 和 `runtime RESETTING: old workers still busy`。
- 15:27:17、15:27:35 BLE 物理连接均成功；RDX 接入仍被同一录音状态阻塞，随后 APP 再次断开。

根因是 RDX 重连复用了存储空闲检查，要求录音必须 STOP。本地录音按设计跨断连继续运行，因此旧 RDX 运行时无法进入 READY。这是首轮实现遗漏的“离线录音 → APP 接管 → APP 断开 → 再次接管”边界。

### 8.2 本次修复范围

1. RDX 断开时清除旧录音上报 token，取消延迟恢复推流定时器并使其 token 失效；START、RESUME、PAUSE 均标记传输中断，本地录音状态保持不变。
2. 仅对 RDX 运行时重置放行已脱离旧传输的本地录音：要求旧上报 token 已清除、传输已中断、非纯推流会话，且处于 START、RESUME 或 PAUSE。
3. 录音切换任务、文件传输、索引、格式化、OTA 和协议发送任务仍须满足原有空闲条件；FIFO 屏障及旧 epoch 校验保持生效。
4. 新 owner 完成接入后重新绑定录音并同步状态；绑定入口禁止覆盖尚未撤销的其他会话 token。离线开始的录音不发送实时音频，见第 9 节。
5. USB 存储、格式化和解绑仍要求录音停止，不能使用重连的本地录音放行条件。

### 8.3 软件验证与待回归项目

- 主机测试使用模拟外设，不能替代实际 BLE 时序、音频连续性及文件播放验收。文档第 6 节全部目标尚未逐项完成实机验收。

## 9. 离线录音接入 APP 只接管控制，不上传实时音频

用户确认：离线录音已经开始，接入后发送的实时流缺少此前音频，不能代表完整录音，因此不应自动推流。

- 离线开始的录音，整个会话仅在设备本地保存；连接 APP 后同步状态、时长，并支持暂停、恢复、标记、停止。
- 暂停恢复和反复断开重连均不得改变录音起始模式，也不得开启实时音频上传。
- 完整音频在停止保存后通过文件下载获取；连接时不补传历史音频。
- 在线开始的录音保留既有实时音频功能及会话、订阅和传输中断校验。

实现：音频回调增加起始模式判断；当前连接模式与起始模式分开维护，起始模式仅在新录音代次初始化时设置，避免恢复时被在线连接覆盖。控制回执仍使用当前有效会话。

新增主机行为测试执行生产模式更新及音频回调，覆盖离线接入、恢复初始化、三轮断开重连无推流且持续写入，以及新在线录音与纯推流会话的发送和原有门控。实机需确认 APP 音频通道无实时数据、控制正常，并在停止后下载播放完整文件。

软件验证：统一主机测试 13 项通过；Windows 固件构建、打包成功，仍有既有编译和链接告警。已更新 `output/update.ufw`，未烧录，实机回归待完成。

## 12. KEY5 纯在线流录音断连收尾
