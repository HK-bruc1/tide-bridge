# HFP 经典蓝牙麦克风原理与方案选型（原理篇）

> 适用项目：Beanstalk RKB / T2620 / JL AC701N（BR28）
>
> 文档定位：讲清楚“按键说话、PC 出字”的端到端原理、候选方案差异、分期选择及理由
>
> 配套设计篇：[HFP 经典蓝牙麦克风模块化设计](./2.HFP麦克风模块化设计.md)
>
> 配套执行篇：[HFP 经典蓝牙麦克风分阶段实施与验收](./3.HFP麦克风分阶段实施与验收.md)

## 1. 原理、选型与最终结论

### 1.1 端到端原理：一条音频链路 + 一条信令链路

产品目标分两期实现：一期在 Windows 上由 KEY5 调起系统语音输入，二期再升级为“按住说话、松开结束”的真 PTT。两期都包含两个相互独立的平面：

```text
┌────────────────────────────────────────────────────────┐
│ 音频平面（数据面）                                        │
│   设备 Mic → eSCO/mSBC → Windows 麦克风音频端点           │
│   载体：Classic HFP（JL SDK 现成能力）                    │
│   HID 键盘协议没有音频通道，声音不可能走 HID               │
├────────────────────────────────────────────────────────┤
│ 控制平面（信令面）                                        │
│   一期：KEY5 长按 → HID Win+H click → Windows 语音输入    │
│   二期：KEY5 长按/松开 → HID F24 down/up → PC Agent      │
│   载体：已验证冻结的 BLE HOGP 键盘；只传意图，不搬运音频     │
└────────────────────────────────────────────────────────┘
```

两个平面在设备端保持解耦，在 PC 侧的语音输入工作流中汇合：

- 设备端：按键模块只发 HID 信令，从不打开/关闭 SCO 或录音；SCO 由 PC 侧 Audio Gateway 驱动，音频生命周期由 SDK 的 `phone_call.c` 唯一拥有。
- PC 端：音频端点常在（HFP 连接即存在）。一期由 `Win+H` 调起 Windows 语音输入并取用系统默认麦克风；二期由 Agent 根据 F24 明确选择并取用本设备对应的 HFP 麦克风。

这正是[设计篇](./2.HFP麦克风模块化设计.md) §3.2 非目标和 §4.4 复用门禁的原理来源：**语音触发/PTT 不依赖 HFP/SCO，HFP 状态不控制 HID**。

### 1.2 PC 不会自动转写：一期复用 Windows，二期才需要 Agent

HFP 连上后，Windows 只是多出一个可用的麦克风端点，如同插上一个 USB 麦克风；仅连接 HFP 不会自动录音或转文字。但目标 Windows 已提供 `Win+H` 语音输入，因此一期不开发 PC Agent：

1. 用户在 Windows 中把本设备 HFP Mic 设为默认输入设备；
2. 当前应用提供可输入文本的焦点；
3. KEY5 长按发送一次 `Win+H` 组合键 click；
4. Windows 负责打开默认麦克风、语音识别和向焦点窗口输入文字。

一期的边界是：麦克风选择、听写启停、语言支持、联网要求和文本注入行为均由 Windows 决定，固件无法确认听写是否真的启动，也不能保证在多麦克风环境中自动选中本设备。

二期若要求真 PTT 和精确麦克风绑定，则增加 PC Agent：全局捕获并消费 F24 down/up，稳定关联 Keyboard 与本设备 HFP Mic，down 开始采集、up 停止，再完成 STT 和文本注入。Agent 是二期能力，不是一期交付依赖。

### 1.3 信令选型：一期 Win+H，二期 F24

“一个按键触发语音输入”在行业里已有标准做法：新式键盘上的麦克风/听写键是 HID Consumer Page（0x0C）的 Usage 0x0CF “Voice Command”（HID Usage Tables 1.2 定义）。在目标 Windows 版本上，其预期行为是触发系统听写（等价于 `Win+H`）；Apple 键盘的听写键走 Apple 私有路径。以上均为 OS 行为判断而非本仓库代码事实，若该选型需要复议，必须在目标 OS 版本上实测。微软 Copilot 键则是 `Shift+Win+F23` 组合宏——用高位 F 键做信令，与本方案同款思路。

候选对比：

| | Consumer 0x0CF（键盘麦克风键） | `Win+H` 组合键（一期选定） | F24 + 自研 Agent（二期增强） |
|---|---|---|---|
| PC 侧开发 | 无（依赖 OS 内置听写，需实测） | 无（依赖 OS 内置听写，需实测） | 必须开发 Agent |
| Report Map 改动 | 需新增 Consumer collection + 新 Report ID，破坏已冻结契约 | 无 | 无（现有 Usage 0–255 数组已覆盖 F24=0x73） |
| 交互语义 | 开关式听写 | 开关式听写 | 真 PTT（按住说话、松开结束） |
| 麦克风选择 | 系统默认，不保证用 HFP Mic | 系统默认 | Agent 精确绑定本设备 HFP Mic |
| STT 引擎 | OS 的，不可控 | OS 的，不可控 | 自选引擎，可控 |
| 平台范围 | Windows/macOS 行为预期不一致，需分别实测 | 一期仅 Windows | 二期先支持 Windows，其他平台取决于 Agent 实现 |

一期选定 `Win+H` 的理由：

1. **无 PC 研发**：直接复用 Windows 语音输入、STT 和文本注入闭环。
2. **零 Report Map 改动**：现有 Keyboard Report 格式已能发送 GUI modifier + `H`，只需在公共 usage 头补 `H=0x0B` 符号常量，不新增 Consumer collection 或 Report ID。
3. **一期目标匹配**：产品当前只要求 KEY5 触发 Windows 语音输入，接受系统默认麦克风和 Windows 定义的启停行为。

二期保留 F24 的理由也明确冻结：F24（usage 0x73）已在现有 Report Map 的 Usage 0–255 范围内，Agent 可以消费其 down/up 并实现真 PTT，也可以通过稳定标识选择本物理设备对应的 HFP Mic。F24 不作为一期实现或验收内容。

### 1.4 音频通道选型：为什么是 Classic HFP

| 候选 | 结论 | 理由 |
|---|---|---|
| Classic HFP（选定） | ✅ | JL SDK 完整提供配对/回连/SLC/SCO/mSBC/AEC；Windows/macOS 原生识别为麦克风端点；设备端零音频协议开发 |
| BLE GATT 自定义音频通道 | ❌ | 带宽与实时性不足，PC 无原生驱动，Agent 需自建音频栈；设计篇 §3.2 明令禁止 |
| LE Audio | ❌ | 目标 PC 存量支持差，工程配置未启用（`TCFG_LE_AUDIO_APP_CONFIG=0`） |
| USB Audio | ❌ | 需要连线，违背无线产品形态 |

HFP 的代价：它是全双工 Headset profile，附带下行播放端点，且与 A2DP 共存会在 Windows 上产生额外音频端点。该代价由设计篇 §8.4（Profile 枚举）、§9.3（下行处理）和执行篇 Phase 6（量产配置冻结）承接；本项目保留产测、DUT 和无线升级依赖的现有 Classic Profiles，不在 HFP 麦克风方案中裁剪。

### 1.5 触发语义选型：为什么是长按 LONG 而非物理 down/up

现有 key driver 的 `LONG（约 750 ms）/HOLD/UP` 事件语义可以同时服务两期：一期在 LONG 时只发送一次 `Win+H` click，HOLD 不重复发送，UP 仅结束本次已接管手势；二期在 LONG/UP 上建立 F24 down/up。短按 CLICK 不产生 UP，可以继续保留原短按行为。新增底层物理 down/up observer 意味着 fork key adapter，违反复用门禁。约 750 ms 的触发阈值必须在执行篇 Phase 0 冻结。

### 1.6 最终结论

一期产品采用以下链路：

```text
同一台 T2620 设备
├─ BLE RDX + HOGP：同一广播、同一 GATT Server 和单连接；同时承载配置、键盘输入与 KEY5 语音触发
├─ Classic HFP HF：麦克风上行，由 PC Audio Gateway 打开 SCO/eSCO
├─ KEY5 LONG：发送一次 Win+H click，由 Windows 语音输入使用系统默认麦克风
└─ RDX 与 HOGP 按当前链路访问和 HID ready 状态独立激活，不存在 CONFIG/HOGP owner 或模式切换
```

BLE HOGP 与 Classic HFP 虽然来自同一台物理设备，但属于两个独立 transport，各自建立连接、安全关系和 bond。当前架构不能依赖一次 Windows 配对操作同时完成 HID 与经典蓝牙麦克风连接，显示名称相同也不会合并两条链路。因此一期首次安装需分别配对 `Beanstalk RKB`（BLE RDX + HOGP）和 `Beanstalk RKB MIC`（Classic HFP）；完成 bond 后由两条链路各自自动回连，不要求用户每次使用都手动连接两次。

基于这一约束，名称采用“共同产品名 + 功能区分”而不是两个完全相同的显示名：保留 `Beanstalk RKB` 作为 BLE 产品端点，为 Classic 音频端点增加 `MIC` 后缀。这样既能表明两者属于同一产品，也能让用户在两次配对和 Windows 默认输入选择时识别麦克风端点。

工程不需要重新实现 HFP 麦克风协议栈，也不需要新建一套 Classic 配对、回连、bond 或 SCO 状态机。JL SDK 已经提供：

- Classic Controller 和 Profile 生命周期；
- 配对、开机回连、超距回连、Inquiry/Page Scan；
- Link Key/bond 数据；
- HFP SDP、RFCOMM/AT 和 SLC；
- SCO/eSCO、mSBC/CVSD；
- `esco_player`、`esco_recoder`、AEC/CVP 和通话音频切换。

本项目真正需要新增的只有：

1. 让 T2620/RDX 产品不再在 BT 初始化后关闭 Classic Stack；
2. 将 Classic 开关与 SD/DAC 板级电源动作解耦；
3. 提供只读、可复用的 HFP 麦克风状态监视和诊断接口；
4. 冻结 T2620 Profile、名称和 HOGP/HFP 共存配置；
5. 复用现有 `LONG/HOLD/UP` 按键事件，让 KEY5 每次长按只触发一次 `Win+H`；
6. 在目标 Windows 版本上冻结默认麦克风、语音输入、焦点、语言和网络条件，不开发一期 Agent。

二期在一期稳定基础上可选增加 F24 真 PTT、PC Agent 和本设备 HFP Mic 精确绑定；该增强不能反向扩大一期固件的交付范围。具体模块和代码边界见[设计篇](./2.HFP麦克风模块化设计.md)，阶段门禁和测试矩阵见[执行篇](./3.HFP麦克风分阶段实施与验收.md)。
