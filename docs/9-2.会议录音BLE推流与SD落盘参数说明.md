# 会议录音 BLE 推流与 SD 落盘参数说明

> 更新时间：2026-11-16
>
> 适用范围：T2620 CHAT 会议录音，包括普通在线录音、离线录音和 stream-only。CALL 仍保留原双声道链路，不在本文当前默认参数范围内。
>
> 关联文档：[9-0 双声道流程](9-0.会议录音双声道流程.md)、[9-1 双声道改单声道方案](9-1.会议录音双声道改单声道实施方案.md)、[6-3 录音功耗分析](6-3.T2620录音功耗分析与逐项测试方案.md)、[6-2 BLE 连接参数](6-2.T2620BLE连接后低功耗设计.md)。

## 1. 结论

当前 CHAT 会议录音的 Opus 编码帧为 20 ms 一帧。原双声道方案每帧 80 B、32 kbps；当前默认双路择优单声道方案每帧 40 B、16 kbps。

BLE 推流与 SD 落盘使用同一份编码数据，因此两者的**音频数据速率相同**：

| 项目 | 原双声道 | 当前会议单声道 |
|---|---:|---:|
| 编码帧间隔 | 20 ms | 20 ms |
| 编码帧率 | 50 帧/s | 50 帧/s |
| 每帧 Opus 数据 | 80 B | 40 B |
| 编码码率 | 32 kbps | 16 kbps |
| 音频数据速率 | 4000 B/s | 2000 B/s |

但两者发送或写入的粒度不同：

- BLE 当前每次音频回调发送一个 RDX `stream` 业务包，没有做 2 帧、4 帧或多帧聚合。业务层发送周期约 20 ms，即约 50 包/s。
- SD 落盘先在内存中累计，达到固定的 8000 B 后才写入一次。原双声道约 2 s 写一次，当前单声道约 4 s 写一次。

可以把关系概括为：

```text
同一路 20 ms Opus 编码帧
        |
        +-- BLE：约每 20 ms 发送一帧
        |
        +-- SD ：累计到 8000 B 后写一次
```

## 2. 参数分层

排查或抓包时必须区分以下四个层次，它们不是同一种“包”：

| 层次 | 当前参数 | 含义 |
|---|---:|---|
| PCM 输入 | 16 kHz、16 bit、20 ms | 每路每帧 320 个样点、640 B |
| Opus 编码帧 | 20 ms | 单声道 40 B/帧，历史双声道 80 B/帧 |
| RDX `stream` 业务帧 | 当前日志观测为 58 B | 40 B Opus 数据加约 18 B RDX 文本协议与帧结构开销 |
| BLE ATT/RF 包 | 由实际协商结果决定 | 受 ATT MTU、DLE、连接事件、重传和控制器调度影响 |

`58 B` 是 RDX 业务字符串的完整长度，不是 BLE 空口单包固定长度。BLE 协议栈可能根据实际 ATT 载荷把一条业务消息拆成多条通知；接收端应以 `*DEV#stream#` 起始，并按 RDX 帧结束规则重组，不能把一条 ATT 通知直接等同于一个 Opus 包。

## 3. 当前 BLE 推流参数

### 3.1 编码和发送节奏

| 参数 | 当前值 | 依据 |
|---|---:|---|
| 采样率 | 16 kHz | `OPUS_SR` |
| 声道数 | 1 | CHAT 动态择优单声道 |
| 帧时长 | 20 ms | `OPUS_FS` |
| 码率 | 16 kbps | `16 kHz × 1 ch × 2 B / 0.02 s` |
| 编码复杂度 | 1 | `opuset.complexity = 1` |
| 音频帧率 | 50 帧/s | `1 / 20 ms` |
| BLE 业务发送节奏 | 约 20 ms/包 | 一次音频回调调用一次音频发送入口 |
| BLE 业务包数量 | 约 50 包/s | 当前未做多帧聚合 |

在线会话满足连接有效、当前会话有效、流未标记不连续且 BLE 发送就绪后，`rdx_record_run_data_handle()` 直接调用 `rdx_protocol_audio_data_indicate()`。当前补丁库检查结果为 `pack_count=1`，因此这一层没有把多帧合并发送。

### 3.2 包长与数据量

当前单声道日志中的典型记录为：

```text
RDX_TX_PROBE kind=stream len=58
```

它对应：

```text
40 B Opus 音频 + 约 18 B RDX stream 协议/帧开销 = 58 B
```

按业务字符串计算：

| 项目 | 原双声道 | 当前会议单声道 |
|---|---:|---:|
| Opus 音频载荷 | 80 B/包 | 40 B/包 |
| RDX `stream` 完整业务包 | 约 98 B/包，按 18 B 开销计算 | 当前日志约 58 B/包 |
| 业务包频率 | 约 50 包/s | 约 50 包/s |
| Opus 音频数据速率 | 4000 B/s | 2000 B/s |
| 含 RDX 字符串开销的业务数据量 | 约 4900 B/s | 约 2900 B/s |

表中的速率用于比较业务层数据量。实际 BLE 空口还会增加 L2CAP、ATT、链路层头、重传、连接事件和其他协议流量，不能直接把 2900 B/s 当作射频吞吐或功耗指标。

### 3.3 BLE 连接和载波参数

| 参数 | 当前策略 |
|---|---|
| 连接参数目标 | `{6, 12, 49, 600}` |
| 连接间隔 | 7.5–15 ms，主机实际协商 |
| Slave latency | 49 |
| Supervision timeout | 6 s |
| 本地 ATT MTU 上限 | 517 B |
| ATT 发送缓存 | 4096 B |
| 主动 DLE 请求开关 | 当前 `TCFG_T2620_BLE_DLE_REQUEST_ENABLE = 0`，默认不主动请求 |
| 启用 DLE 时的请求值 | 251 B、2120 us |
| 2M PHY | 当前产品策略不主动请求；也不强制 1M |

连接间隔是链路调度参数，不是音频采样周期。即使连接间隔为 7.5–15 ms，业务层仍按约每 20 ms 产生一帧；实际发送时刻会落在后续可用的连接事件中。

Att MTU、DLE 和 PHY 主要影响单次空口承载能力、分片和重传效率，不改变 Opus 20 ms 一帧的逻辑节奏。最终参数必须以主机协商事件或 HCI 抓包为准。

## 4. 当前 SD 落盘参数

### 4.1 聚合和写入

| 参数 | 当前值 | 说明 |
|---|---:|---|
| 单帧大小 | 当前单声道 40 B | 历史双声道 80 B |
| 聚合块大小 | 8000 B | `RS_BLOCK_BYTES` |
| 单声道写盘间隔 | 约 4 s | `8000 / 2000` |
| 双声道写盘间隔 | 约 2 s | `8000 / 4000` |
| 停止尾块 | 立即 flush | 停止时不等待 4 s |
| 典型单次写耗时 | 约 25–40 ms | 含 DAT 更新，来自 2026-11-10 日志 |
| 写 SD 占空比 | 小于 1% | 按该稳态日志和 4 s 周期估算 |

`RS_FRAMES = 128` 是异步存储队列的帧数容量，对应的音频时长为：

```text
128 帧 × 20 ms = 2.56 s
```

该队列用于吸收文件系统写入长尾，不代表 SD 每 2.56 s 写一次。真正的循环写入条件仍是 `8000 B` 聚合块已满。

### 4.2 完整落盘路径

```text
20 ms Opus 帧
  -> 异步存储队列
  -> 8000 B 聚合缓存
  -> rdx_uxfile_raw_write()
  -> 更新 RAW/DAT 等相关状态
```

音频回调只负责把当前编码帧复制到有界存储队列，文件写入由独立存储 worker 完成。文件格式和 DAT 元数据仍按现有 RDX 文件协议处理，不同时改变 APP 文件格式。

停止录音时，worker 处理完已接收帧后立即刷新不足 8000 B 的尾块。因此“单声道 4 秒写一次”描述的是稳定连续录音时的满块节拍，不是停止流程的等待时间。

## 5. BLE 与落盘的相同点和不同点

### 5.1 相同点

- 使用同一份 Opus 编码输出，编码帧均为 20 ms。
- 当前单声道均为 40 B/帧、2000 B/s。
- 音频内容与帧边界来源一致。
- 两者都不依赖“每 20 ms 定时打印”或每帧日志才能工作。

### 5.2 不同点

| 项目 | BLE 推流 | SD 落盘 |
|---|---|---|
| 触发粒度 | 每个音频回调一帧 | 累计满 8000 B |
| 典型周期 | 约 20 ms | 单声道约 4 s，双声道约 2 s |
| 每单位数据 | 单声道 Opus 40 B，业务包约 58 B | Opus 40 B 原始存储字节，无 BLE 字符串头 |
| 缓冲目的 | BLE 协议栈排队、分片和重传 | 吸收 SD/FAT/DAT 写入延迟 |
| 中断影响 | 断流、CCC、连接或发送就绪状态 | 存储关闭、队列排空和尾块 flush |
| 额外开销 | RDX 文本协议、ATT/L2CAP/RF | RAW 文件及 DAT/MTA 等文件元数据 |

因此“BLE 参数和落盘参数一样”准确的说法是：**底层音频帧参数和平均音频数据速率相同，发送/写入周期与容器开销不同。**

## 6. 场景对应关系

| 场景 | BLE 推流 | SD 落盘 |
|---|---|---|
| CHAT 在线，`recsave=1` | 有，约 20 ms/包 | 有，满 8000 B 写一次 |
| CHAT 在线，`recsave=0` | 有，约 20 ms/包 | 无 |
| CHAT 离线 | 无 | 有，满 8000 B 写一次 |
| CHAT stream-only | 有，约 20 ms/包 | 无 |
| CALL | 保留原链路 | 不按本文的 CHAT 单声道参数推断 |

## 7. 日志核对

单声道 BLE 推流应重点核对：

```text
[opus] sr=16000 br=16000
RDX_TX_PROBE kind=stream len=58
```

前者确认 16 kHz、16 kbps 编码参数；后者确认 RDX `stream` 业务包完整长度为 58 B。若业务包长度发生变化，应先区分是 Opus 帧长、声道数、RDX 头格式还是 APP 兼容处理发生变化。

SD 落盘应重点核对：

```text
wRet: 8000
```

这表示一次满块写入 8000 B。正常情况下，单声道约每 200 帧、即约 4 s 出现一次；停止录音时还会出现一次不足 8000 B 的尾块刷新。

实现位置：

- `SDK/audio/framework/nodes/effect_dev2_node.c`：Opus 采样率、码率和帧长配置。
- `SDK/apps/common/third_party_profile/rdx_protocol/rdx_record.c`：CHAT 单声道选路、在线 BLE 发送和本地存储分流。

- `SDK/apps/common/third_party_profile/rdx_protocol/rdx_ble_server.c`：连接参数、MTU/DLE 策略和发送状态。

`librdxApp` 不在普通应用源码内。当前 `pack_count=1` 是对现有补丁库检查得到的结论；升级或替换 `librdxApp` 后，应重新确认一次回调是否仍只生成一个 `stream` 包。

本文中的“2 s”“4 s”均由 8000 B 聚合阈值换算得到，不应实现为额外定时器。后续若修改采样率、码率、声道数、Opus 帧长、`RS_BLOCK_BYTES`、连接策略或 RDX 库版本，必须同步更新本文的参数表、数据量公式和日志判据。
