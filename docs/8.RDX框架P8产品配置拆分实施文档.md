# RDX 框架 P8 产品配置拆分实施文档

> 日期：2026-07-20
> 当前状态：P7 已完成代码收口并通过回归测试

> P8 定位：在不修改 `librdxApp.a`、不改变现有产品行为的前提下，将产品选择、产品参数和产品能力从 `rdx_app_config.h` 及业务 `.c` 中集中到配置层。

## 1. 结论

P8 采用一次提交完成，不拆分多个提交。工作区内仍按“基线记录、配置拆分、能力收口、验证”顺序实施，全部验收通过后统一提交：

```text
重构：P8拆分RDX产品配置并收口产品宏
```

P8 不是单纯移动头文件，完成后必须同时达到：

- 一个产品构建档位统一决定 APP、DEVICE、BOARD，chip family 保留可覆盖能力。
- `rdx_app_config.h` 只保留兼容 include，不再承载具体产品参数。
- 每个已支持产品有独立配置头。
- 业务 `.c` 不再按具体 `APP_*`、`DEVICE_*` 分支。
- 新增产品只修改 `config/` 和构建档位，不修改业务 `.c`。
- 当前默认 Zenchord CC 行为、ABI 和静态库保持不变。

## 2. 当前基线

### 2.1 已完成前置项

- P7 旧 BLE server record/protocol 跨层调用已收口。
- P7 已完成回归测试，P8 不再把 P7 验证列为前置阻塞。
- `librdxApp.a` 保持原二进制和旧 ABI。

### 2.2 当前配置问题

`rdx_app_config.h` 当前约 733 行，混合了五类内容：

1. APP 和 DEVICE ID。
2. 当前 APP、DEVICE 的硬编码选择。
3. 全局公共默认值。
4. DEVICE 派生的产品形态和硬件能力。
5. 17 个实际产品参数块。

当前构建选择存在两个入口：

- `rdx_app_config.h` 硬编码 `RDX_AI_SEL_APP`、`RDX_SEL_DEVICE`。
- `SDK/Makefile` 独立选择 `RDX_BOARD`、`RDX_CHIP_FAMILY`。

这四个值可以互相不匹配。例如选择 `t2616_ep` board 时，C 配置仍可能保持 `DEVICE_ZENCORD_CC_T2616`。

当前还存在以下边界问题：

- 定义了 27 个 `APP_*` ID，但只有 17 个产品配置块。
- `rdx_config_validate.h` 只确认 APP mask 有命中，不能拒绝“已定义但没有产品配置”的 APP。
- 单 APP 校验被 `#ifndef RDX_MULTI_FUNC_INTERFACE` 屏蔽；`RDX_MULTI_FUNC_INTERFACE` 是 OLED/eMMC 硬件接口选择，不是多 APP 开关。
- RDX 相关业务代码仍有 8 处具体 APP 条件和 4 处具体 DEVICE 条件。
- 两处 AITIR 条件分支中只有已删除 OLED 功能的注释，没有运行时代码。

## 3. 目标与非目标

### 3.1 目标

- 统一产品构建入口。
- 拆分产品配置文件。
- 用语义能力替代业务代码中的产品名单。
- 建立有效/无效配置组合验证。
- 建立静态边界规则，防止产品宏重新进入业务条件编译。
- 保留旧头文件入口，避免修改现有 22 个 include 调用点。

### 3.2 非目标

P8 不做以下工作：

- 不修改、替换或重编译 `librdxApp.a`。
- 不修改旧 ABI 函数、全局变量和协议结构体布局。
- 不清理与产品配置拆分无关的业务逻辑。
- 不把预处理配置改造成运行时对象、配置表、工厂或 vtable。
- 不重建 board 层。
- 不为没有生产参数来源的产品猜测 WiFi、版本号、产品码等配置值。
- 不顺手修正现有产品形态语义；行为修正另立任务。

## 5. 配置文件职责

### 5.1 `rdx_config_ids.h`

只保存稳定标识和公共常量：

- `APP_*_EN`
- `DEVICE_*`
- `RDX_SUPPORT_OLED`、`RDX_SUPPORT_EMMC` 等枚举式常量
- RTC path、传输类型等不会因具体产品变化的常量

旧 ID 即使暂时没有产品配置也保留，避免破坏源码兼容；选择无配置 ID 时由 validator 明确报错。

### 5.2 `rdx_build_select.h`

接收 Makefile 传入的 APP、DEVICE 选择，并保留历史默认值：

```c
#ifndef RDX_AI_SEL_APP
#define RDX_AI_SEL_APP APP_ZENCHORD_EN
#endif

#ifndef RDX_SEL_DEVICE
#define RDX_SEL_DEVICE DEVICE_ZENCORD_CC_T2616
#endif
```

默认值只用于兼容 IDE、单文件编译和未经过 `SDK/Makefile` 的旧入口；正式生产构建由产品档位传入。

### 5.3 `rdx_config_common.h`

保存现有公共默认配置和由 DEVICE 派生的公共定义，例如：

- `FIRMWARE_NAME`
- `RDX_PRODUCT_IS_CHARGE_CASE`
- `RDX_SUPPORT_MOTOR`
- `RDX_MULTI_FUNC_INTERFACE`
- `RDX_SUPPORT_ALGORITHM`
- `RDX_RTC_PATH_SEL`
- `RDX_DEFAULT_SHUT_DOWN_TIME`
- WiFi 通信方式和 AP 默认策略

P8 只迁移现有定义，不重新判断这些配置应该归 product、board 还是 feature。后续有真实复用需求时再继续拆。

### 5.4 `rdx_product_select.h`

只根据唯一 APP 选择一个产品配置头：

```c
#if RDX_AI_SEL_APP == APP_ZENCHORD_EN
#include "product/zenchord.h"
#elif RDX_AI_SEL_APP == APP_NEVIEW_EN
#include "product/neview.h"
/* existing configured products */
#else
#error "RDX_AI_SEL_APP has no product config"
#endif
```

不继续使用 `RDX_AI_SEL_APP & APP_xxx_EN` 的优先级链。当前产品参数通过 `#elif` 互斥，多个 APP bit 不可能形成可靠的组合配置，因此 P8 将多 APP 选择定义为非法组合。

### 5.5 `config/product/*.h`

每个文件只保存该产品参数和语义能力：

- 产品类型、产品码、厂商码
- BLE 名称
- 固件/硬件版本
- WiFi AP 参数
- 翻译、录音路径、按键行为等产品能力
- 同一客户下不同 DEVICE 的必要分支

迁移时保留现有宏值、字符串、版本号和条件顺序，不做格式统一或配置纠错。

### 5.6 `rdx_app_config.h`

最终只作为兼容入口：

```c
#ifndef __RDX_APP_CONFIG_H__
#define __RDX_APP_CONFIG_H__

#include "rdx_common.h"
#include "config/rdx_config_ids.h"
#include "config/rdx_build_select.h"
#include "config/rdx_config_common.h"
#include "config/rdx_product_select.h"
#include "rdx_config_validate.h"

#endif
```

现有调用点继续 include `rdx_app_config.h`，P8 不批量修改 22 个调用文件。

## 6. 构建档位

### 6.1 Makefile 入口

`SDK/Makefile` 新增：

```make
RDX_PRODUCT ?= zenchord_cc
ifneq ($(value RDX_PRODUCT),zenchord_cc)
ifneq ($(value RDX_PRODUCT),zenchord_ep)
$(error RDX_PRODUCT must be a supported literal)
endif
endif
ifneq ($(origin RDX_PRODUCT_MK),undefined)
$(error RDX_PRODUCT_MK is internal; select a profile with RDX_PRODUCT)
endif
override RDX_PRODUCT_MK := apps/common/third_party_profile/rdx_protocol/config/build/$(value RDX_PRODUCT).mk

ifeq ($(wildcard $(RDX_PRODUCT_MK)),)
$(error Unknown RDX_PRODUCT: $(RDX_PRODUCT))
endif

include $(RDX_PRODUCT_MK)
```

产品档位通过不可覆盖的内部变量追加到最终编译参数，即使命令行整体传入 `DEFINES=...` 也不能删除 APP/DEVICE 选择：

```make
override RDX_DEFINES := \
    -DRDX_AI_SEL_APP=$(value RDX_AI_SEL_APP) \
    -DRDX_SEL_DEVICE=$(value RDX_SEL_DEVICE)
override DEFINES += $(RDX_DEFINES)
```

### 6.2 Zenchord CC 档位

档位在定义常量前检查其来源，命令行或环境预设内部常量时直接失败：

```make
ifneq ($(origin RDX_EXPECTED_APP),undefined)
$(error RDX_EXPECTED_APP is internal to RDX_PRODUCT)
endif
ifneq ($(origin RDX_EXPECTED_DEVICE),undefined)
$(error RDX_EXPECTED_DEVICE is internal to RDX_PRODUCT)
endif
ifneq ($(origin RDX_EXPECTED_BOARD),undefined)
$(error RDX_EXPECTED_BOARD is internal to RDX_PRODUCT)
endif
```

```make
override RDX_EXPECTED_APP := APP_ZENCHORD_EN
override RDX_EXPECTED_DEVICE := DEVICE_ZENCORD_CC_T2616
override RDX_EXPECTED_BOARD := t2616_cc
RDX_AI_SEL_APP := $(RDX_EXPECTED_APP)
RDX_SEL_DEVICE := $(RDX_EXPECTED_DEVICE)
RDX_BOARD := $(RDX_EXPECTED_BOARD)
RDX_CHIP_FAMILY ?= jl7018
```

### 6.3 Zenchord EP 档位

```make
override RDX_EXPECTED_APP := APP_ZENCHORD_EN
override RDX_EXPECTED_DEVICE := DEVICE_ZENCORD_EP_T2616
override RDX_EXPECTED_BOARD := t2616_ep
RDX_AI_SEL_APP := $(RDX_EXPECTED_APP)
RDX_SEL_DEVICE := $(RDX_EXPECTED_DEVICE)
RDX_BOARD := $(RDX_EXPECTED_BOARD)
RDX_CHIP_FAMILY ?= jl7018
```

构建示例：

```sh
make -C SDK RDX_PRODUCT=zenchord_cc
make -C SDK RDX_PRODUCT=zenchord_cc RDX_CHIP_FAMILY=jl7018_shadow
make -C SDK RDX_PRODUCT=zenchord_ep
```

`RDX_PRODUCT_MK`、`RDX_EXPECTED_*` 和 `RDX_DEFINES` 是档位内部常量，外部传入时立即报错。`RDX_PRODUCT`、APP、DEVICE、BOARD 和 chip family 只接受已支持的原始字面量，比较时使用 `$(value ...)`，不展开调用方传入的 Make 函数。chip family 允许 `jl7018` 和 `jl7018_shadow`，并由配置检查确认对应 port 源文件存在。

## 7. 业务产品宏收口

只移动产品参数不能满足“新增产品业务 `.c` 零改动”。P8 必须同步清理业务层具体产品判断。

### 7.1 APP 条件替换

按现有行为提取最少的语义能力，建议名称如下：

| 当前具体产品判断 | 替换能力 |
|---|---|
| `rdx_record.c` 的长 APP 名单 | `RDX_RECORD_USE_LOCAL_PIPELINE` |
| BLE 断连后切离线模式的长 APP 名单 | `RDX_RECORD_DISCONNECT_TO_OFFLINE` |
| Turing 断连时不设置 rerun | `RDX_RECORD_DISCONNECT_RERUN` |
| sink 初始化时的四产品名单 | `RDX_RECORD_SINK_AUTO_INIT` |
| Tingnao idle 长按唤醒 | `RDX_IDLE_WAKE_ON_LONG_PRESS` |

能力宏由每个产品配置显式定义为 `0` 或 `1`。不使用“未定义等于零”作为产品能力默认值，避免新增产品静默选错行为。

### 7.2 DEVICE 条件替换

按实际行为使用能力，而不是继续维护 DEVICE 名单：

| 当前判断 | 替换方向 |
|---|---|
| BJ T2403 才 include `sk4558.h` | `RDX_HAS_SK4558_CHARGER` |
| BJ/CC 产品开放按键 DUT | `RDX_SUPPORT_KEY_DUT_ENTRY` |
| BJ/CC 产品自动关机前检查 RDX 活动 | `RDX_NEEDS_POWER_ACTIVITY_GUARD` |

若能力本质属于板级硬件，定义放入现有 `board/<name>/rdx_board_config.h`；产品头只保存产品行为能力。

### 7.3 删除无效分支

`rdx_charge.c` 中两处 AITIR 条件的两个分支都只剩 OLED 删除注释，没有可执行语句。P8 直接删除该产品条件，保留外层现有流程，不为注释建立能力宏。

### 7.4 静态门禁

在 `tools/check_rdx_boundaries.ps1` 增加规则：

- RDX 业务 `.c` 的 `#if/#elif` 不得引用 `RDX_AI_SEL_APP`、`RDX_SEL_DEVICE`。
- RDX 业务 `.c` 的 `#if/#elif` 不得引用具体 `APP_*_EN`、`DEVICE_*`。
- `config/`、`board/`、validator 和兼容赋值位置不属于业务条件规则扫描范围。
- `rdx_app_config.h` 不得重新出现产品参数定义块。

`rdx_app.c` 将 APP/DEVICE 数值写入协议配置结构的普通赋值仍允许；禁止的是按具体产品分叉业务实现。

## 8. 配置校验

`rdx_config_validate.h` 在所有产品配置 include 完成后执行。

### 8.1 必须校验

- APP 只能选择一个 bit。
- APP 必须有对应产品配置头。
- DEVICE 必须属于已定义 DEVICE ID。
- APP/DEVICE 必须是已支持组合。
- 产品配置必须定义其运行路径需要的必要参数。
- 构建档位中的 DEVICE 和 BOARD 必须匹配。
- 能力宏只能为 `0` 或 `1`。

### 8.2 非法组合用例

至少保留以下编译失败用例：

1. 未配置的 APP ID。
2. 未知 DEVICE ID。
3. `APP_ZENCHORD_EN + DEVICE_RDX_BJ_T2403`。
4. 多 APP bit 组合。
5. Zenchord CC DEVICE 配 T2616 EP board。
6. 命令行覆盖 `RDX_PRODUCT_MK` 指向其他产品档位。
7. 同时覆盖 `RDX_EXPECTED_*` 和 APP/DEVICE/BOARD 选择值。
8. 选择值中嵌入 `$(eval ...)` 等递归 Make 表达式。
9. 不存在的 chip family。

同时保留一个成功用例：命令行传入 `DEFINES=USER_SUPPLIED` 时，最终展开参数仍必须包含档位 APP/DEVICE 宏。

### 8.3 必要产品字段

对当前编译路径真实使用的字段做 `#ifndef/#error` 检查，例如：

```c
#ifndef BLE_LOCAL_NAME
#error "Product config must define BLE_LOCAL_NAME"
#endif

#ifndef PRODUCT_CODE
#error "Product config must define PRODUCT_CODE"
#endif

#ifndef FIRMWARE_VERSION
#error "Product config must define FIRMWARE_VERSION"
#endif
```

只检查实际消费者要求的字段，不建立新的配置 schema。

## 9. 单提交实施顺序

以下步骤在同一工作区完成，中间不创建提交。

### 步骤 1：记录基线

- 记录 `HEAD`。
- 记录 `librdxApp.a` SHA256 和 symbol dump。
- 记录默认 Zenchord CC 的预处理宏结果。
- 记录当前静态边界检查、host test 和生产回归结果。

### 步骤 2：引入构建档位

- 增加 `RDX_PRODUCT`。
- 增加 `config/build/*.mk`。
- Makefile 将 APP、DEVICE 注入 CFLAGS。
- 保留默认 Zenchord CC 兼容选择。

### 步骤 3：机械拆分配置

- 拆出 ID、build select、common、product selector。
- 将 17 个产品块原样迁入独立头。
- 将 `rdx_app_config.h` 缩减为兼容 include。
- 调整 validator 到 include 链末尾。

### 步骤 4：收口业务产品判断

- 定义产品行为能力。
- 替换 8 处 APP 条件和 4 处 DEVICE 条件。
- 删除两处无运行时代码的 AITIR 条件。
- 增加防回退规则。

### 步骤 5：补配置矩阵测试

- 增加一个最小配置矩阵测试脚本或 host 编译目标。
- 验证有效组合通过。
- 验证至少 3 个非法组合失败。
- 不引入新的测试框架。

### 步骤 6：统一验收后提交

- 执行静态检查、host test、生产 clean build、ABI 检查和回归测试。
- 对比默认产品关键宏、产物和 map。
- 全部通过后创建一个提交。

## 10. 验收方案

### 10.1 静态边界

```powershell
pwsh -ExecutionPolicy Bypass -File tools/check_rdx_boundaries.ps1
```

期望：全部 PASS，包含 P8 产品宏边界规则。

补充扫描：

```sh
rg -n '#\s*(if|elif).*\b(RDX_AI_SEL_APP|RDX_SEL_DEVICE|APP_[A-Z0-9_]+_EN|DEVICE_[A-Z0-9_]+)' \
  SDK/apps/common/third_party_profile/rdx_protocol \
  SDK/audio/framework/nodes/sink_dev1_node.c \
  SDK/apps/earphone/mode/bt/poweroff.c \
  --glob '*.c' \
  --glob '!**/board/**' \
  --glob '!**/port/**'
```

期望：业务产品条件命中为 0。

### 10.2 Host 测试

```sh
make -C tests/host all CC=cc
```

配置矩阵至少验证：

- Zenchord CC 配置编译通过。
- Zenchord EP 配置编译通过。
- C 配置矩阵中的四个非法组合按预期编译失败。
- Make 档位矩阵拒绝 BOARD 错配、内部变量覆盖、递归 Make 表达式和非法 chip family。
- `DEFINES` 被命令行整体替换时，最终展开参数仍包含档位 APP/DEVICE 宏。
- `jl7018_shadow` 对应的 port 源文件存在并可被配置入口选择。

矩阵通过 `make -n pre_build` 检查真实预构建 recipe 的展开结果，不只检查 `rdx_config_check` 的退出码。

配置矩阵作为 `tests/host/Makefile` 的 `rdx_config_matrix` 目标接入 `all`，不再依赖单独执行脚本完成 P8 验收。

### 10.3 生产组合

至少执行：

```text
zenchord_cc + jl7018
zenchord_cc + jl7018_shadow
zenchord_ep + jl7018
```

要求：

- clean build 通过。
- 默认 Zenchord CC 产物行为不变。
- RDX Flash/RAM 变化可解释，不因配置拆分引入运行时代码。

### 10.4 ABI

```sh
shasum -a 256 SDK/apps/common/third_party_profile/rdx_protocol/librdxApp.a
git diff -- SDK/apps/common/third_party_profile/rdx_protocol/librdxApp.a
```

并执行：

```powershell
pwsh -ExecutionPolicy Bypass -File tests/host/test_rdx_static_library_abi.ps1
```

要求：

- archive SHA256 不变。
- symbol dump 不变。
- `rdx_protocol.h`、`rdx_record.h` 的 ABI 相关预处理结果不变。
- 回调结构体字段顺序、大小和签名不变。

### 10.5 目标板回归

P8 不改变运行逻辑，但配置宏会影响大量条件编译，因此当前主力 Zenchord CC 至少回归：

- 启动日志中的 product、board、chip、版本信息正确。
- BLE 名称、广播厂商数据、产品码正确。
- BLE 连接、断开、重连正常。
- 在线/离线录音及断连处理正常。
- WiFi AP 名称、密码策略和连接正常。
- OTA 版本比较正常。
- 自动关机、DUT、充电和 LED 行为与 P8 前一致。

## 11. 风险与控制

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 宏覆盖顺序变化 | BLE 名称、版本号或 WiFi 参数变化 | 先记录预处理基线，产品块原样迁移，validator 最后执行。 |
| 构建选择不一致 | CC DEVICE 配 EP board | 一个产品档位同时选择 APP、DEVICE、BOARD，并增加非法组合检查。 |
| 最终编译宏被覆盖 | Make 校验通过但 C 预处理使用其他 APP/DEVICE | 通过 `override RDX_DEFINES` 强制追加，并在配置检查目标中核对最终 `DEFINES`。 |
| Make 递归表达式修改内部值 | 外部选择值在比较时执行 `eval` | 公开选择只接受原始字面量，校验使用 `$(value ...)`。 |
| 未配置 APP 被误认为有效 | 编译到后段才出现缺失宏 | product selector 和 validator 立即 `#error`。 |
| 能力命名错误 | 新产品配置无法表达旧行为 | 按现有调用语义定义最少能力，不按客户名复制宏。 |
| ABI 条件发生变化 | 静态库调用结构不匹配 | 对比 archive、symbol、ABI 头预处理结果。 |
| 一次提交 diff 较大 | review 难定位行为变化 | 配置迁移保持机械 diff，能力替换限制在现有 12 个条件点。 |
| EP 历史参数不完整 | EP 档位缺必要产品宏 | 只从现有生产配置补值，不猜测；缺值直接报错。 |

## 12. 回滚

P8 只有一个提交，出现配置或目标板回归时整体回滚该提交，不保留半迁移状态。

禁止通过以下方式规避问题：

- 修改 `librdxApp.a`。
- 修改协议 ABI 结构体。
- 在业务 `.c` 重新增加客户名单。
- 同时维护新旧两份产品参数。
- 给缺失产品参数填写未经确认的占位值。
