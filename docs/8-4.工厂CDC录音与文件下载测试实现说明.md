## 1. 目标与文档边界

本专题是 CDC 实施主线的后续音频/文件阶段：先完成 8-2 的串口识别与原样回显，再完成 8-3 的既有 DUT 普通控制项接入，最后补齐本文能力。这里的“后续”描述实施先后，不表示当前尚未实现。录音复用既有 RDX/DUT 业务，新增的是 CDC 来源授权、数据传输与工站验证链路，不另建一套录音业务。

现有双击终端工具的“普通测试”已接入两项独立测试：

1. **录音测试**：真实麦克风采集、编码，录音期间经 CDC 持续传到电脑，同时保存在设备；停止后播放电脑收到的流，人工确认声音。
2. **文件下载测试**：等待本次录音保存完成，按确定的文件标识经 CDC 下载，校验后独立播放，人工确认声音。

实时传输不要求实时播放。首期采用录音期间接收缓存、停止后播放，避免电脑扬声器回声进入麦克风。两份音频分别保留，不能以下载文件替换缺失的实时流，也不能把流缓存当成设备文件下载结果。

8-2 继续维护 USB 枚举、generation、DMA、背压与关机；8-3 继续维护通用文本命令、公共 DUT 准入、ID/LAST、普通控制与包装衔接。本文集中维护音频与文件业务，避免三处重复定义。

首期只覆盖普通录音；REC_CALL、SPP MIC 频响、边录边听、任意路径文件访问和跨重启自动续传不纳入本次。SMT 与组装可复用该流程，不新增两套录音实现。CDC 验收证明 USB 路径，不能替代 BLE 射频及吞吐验收。

## 4. RDX 接入与资源边界

### 4.1 来源、授权及任务分工

复用 `rdx_dut.c`、`rdx_record.c` 已有录音、编码、本地保存及 stop_request/poll ticket 屏障。CDC 协议适配由 `rdx_factory_cdc.c` 接入 app_core 公共仲裁，不在 USB 类驱动内执行业务。

原有 `rdx_record_dut_authorize()` 优先捕获 BLE token，无 BLE 时退回绑定许可；这不等于未绑定新机已支持 CDC 录音。本版新增 `rdx_record_dut_authorize_usb()`，提供明确的 CDC 厂测录音授权，绑定 USB generation 和录音实例，在 DUT 内通过公共准入生效；不得伪造 BLE token 或放宽普通用户录音绑定限制。

音频按录音来源发送：CDC 发起只送该 CDC 会话，不能因另有 RDX owner 在线就自动送往 BLE。BLE 原在线流、本地保存、状态上报及下载行为保持兼容。BLE 断线不能停止 CDC 所属录音，反之亦然。

具体改造必须同时覆盖授权创建、有效性判断和撤销：原 `rdx_dut_test_session_revoke()` 在 BLE 撤销入口直接调用 `rdx_record_dut_authorization_revoke()`；本版改为按来源撤销的 `rdx_record_dut_ble_revoke()`，不能只在后续 app_core 清理时检查来源。新增录音授权应保存不可变的来源及所属会话，撤销时先匹配来源和会话代次；迟到的旧会话撤销不得清除新会话授权。USB 撤销执行同样规则；DIP OFF 等设备级退出仍可撤销所有来源。现有 `rdx_record_run_data_handle()` 的流发送受 BLE 在线会话及就绪条件限制，CDC 数据分发须以录音来源选择出口，不能借用 BLE 在线标志取得发送资格。

录音回调只向有界缓冲交付帧，不等待 USB、电脑或播放器；协议发送统一调度，usb_stack 仍拥有端点 I/O 与释放。不得新建绕过现有传输所有权的直接 `cdc_write_data()` 路径。

### 4.2 动作与结果

录音开始、停止分别分配公共动作 ID；开始真正生效后可 DONE，但 ACTIVE 保持 REC。停止后等待编码结束、本地保存和资源回收，全部完成才允许停止动作 DONE。保存失败或清理超时明确失败，未释放资源继续隔离，迟到回调不把失败改成功。

每次开始另关联稳定的录音实例。LAST 会被停止、退出等后续动作覆盖，因此录音结果须独立保留，包含开始/停止 ID、实例、保存状态和文件标识；不能仅凭 LAST_CMD 或“列表最后一个”认领文件。

文件下载阶段在正常退出 DUT 后执行，CDC 会话保持。下载与录音写入、格式化、包装及 MSC 排他，使用既有存储生命周期和文件服务准入；不得按主机任意路径直接访问 SD。

下载开始时，在同一次文件服务占用内校验本轮保存结果与文件身份，取得长度和校验值，并保持该文件的读取保护直至结束或取消。保护覆盖元数据计算及所有分块之间的等待，不能每读一块就释放；期间拒绝目标文件删除、替换及其他冲突操作，BLE 和 CDC 入口执行同一规则。若文件已被删除或身份不匹配，明确失败，不回退到最新文件。本版元数据及 CRC 扫描由 `rdx_cdc_file` 文件工作任务有界推进，不长时间阻塞 app_core。完成、取消、断线及下载空闲超时均释放本轮句柄和占用；异步释放完成前仍拒绝冲突操作。空闲超时及传输上限在协议冻结时明确，避免主机保持连接却停止请求造成永久占用。

### 4.3 信息与校时

沿用 8-3 的身份查询。电量/容量等补充信息仍由 8-3 定义，不在此重复扩展 GET_INFO。

本版要求在同一 CDC generation 内通过 `SET_TIME` 校时成功后才能启动录音；脚本使用电脑 UTC 秒值并检查持久化结果。纯 CDC 验收不依赖 BLE 校时。appkey/ostype 属 BLE 初始化，CDC 不模拟登录、不隐式建立用户绑定。文件关联依靠实例与文件标识，不依靠时间戳排序。

## 5. AUDIO=1 首版接口

### 5.1 协商与兼容

`GET_INFO` 保持 `PROTO=1`。普通文本命令及 `OK`/`ERR` 响应不变，新增 `GET_AUDIO_CAPS` 查询能力，再用 `AUDIO_OPEN 1` 显式开启 AUDIO=1 扩展。异步音频及文件帧只在协商后的会话中发送，未协商的旧脚本不会收到音频。

首版采用全部为 ASCII 的带类型文本帧，二进制负载以大写十六进制编码；不引入二进制模式切换。每帧以 CRLF 结束，最大仍为 258 字节，复用现有 USB FIFO/短写/DMA/超时处理。协商绑定 USB generation，断线、DTR 撤销或复位后重新协商；同一会话没有退出扩展模式的命令。主机保持一个在途控制请求，独立读取线程持续分流控制响应与 `@A`/`@E`/`@F`。

### 5.2 命令与响应

| 命令 | 响应及约束 |
|---|---|
| `GET_AUDIO_CAPS` | `OK AUDIO=1;CODEC=OPUS;RATE=16000;CHANNELS=1;FRAME=40;MS=20;MAX_MS=15000` |
| `AUDIO_OPEN 1` | `OK AUDIO=1`；录音或下载活动时拒绝 |
| `SET_TIME <UTC秒>` | `OK TIME=1`；范围 1577836800～2145916799，须已协商且无录音/下载，校时持久化失败返回 IO |
| `*APP#custom#ft_rec_chat#1/0#` | 开始/停止，工站与 BLE APP 统一使用 `ft_rec_chat`；`LAST_CMD` 同样返回 `ft_rec_chat`，不再接受 `ft_rec` 别名；复用公共 ID/RUNNING/DONE。开始收到首个有效编码帧才 DONE；停止等待录音 FIFO 保存及清理屏障 |
| `GET_RECORD_RESULT` | `OK REC=<开始ID>;STOP=<停止ID>;STATE=RUNNING或DONE或FAILED;SAVED=0或1;SN=<编号>;NAME=<文件名或NONE>;FRAMES=<生产帧数>;ERROR=<错误码>;REASON=<停止原因>` |
| `FILE_OPEN <REC>` | `OK STATE=RUNNING`；仅本轮已保存的确定文件，退出 DUT、流结束信息已交付发送队列、存储空闲后可接受。每个录音实例在同一会话仅允许一次打开尝试，不隐式重试 |
| `GET_FILE_STATUS` | `OK REC=<实例>;STATE=OPENING或READY或FAILED或CLOSED;SIZE=<字节数>;CRC=<整文件CRC十进制>;OFFSET=<已交付字节数>` |
| `FILE_READ <REC> <OFFSET>` | `OK STATE=RUNNING`；仅顺序读取，偏移必须等于设备当前偏移，一次至多 80 字节，随后返回一个 `@F` 帧；当前块未交付前拒绝下一请求 |
| `FILE_CLOSE <REC>` | `OK STATE=RUNNING`；正常结束或取消均可使用。轮询 CLOSED 确认读句柄及占用已释放；关闭失败报告 FAILED 并保留文件服务隔离直至重启，不删除文件 |

录音实例直接使用本次开始动作 ID，独立保留到下一次录音开始；退出 DUT 不清除结果。自动到时或异常停止优先经公共仲裁分配停止 ID；开始尚未完成或原 generation 已失效时直接触发已有清理屏障，STOP 可为 0，此时不据缺失的动作确认判定通过。ERROR：0 无错误、1 流或传输失败、2 保存/收尾失败、3 启动无有效帧。REASON：0 主机停止或未单独分类、2 设备到时、3 会话失效。具体错误与 SAVED 分别检查。

文件由录音时捕获的 SN、文件名及 start_time 关联，不根据列表顺序选择。工作任务验证 MTA、首帧指纹、单声道格式、非零且为 40 整数倍的长度，并计算整文件 CRC；最大文件 40000 字节。首期没有文件列表、任意路径、随机读或跨断线续传接口。

### 5.3 异步数据帧

```text
@A,<REC>,<SEQ>,40,<80个HEX字符>*<8位CRC32>\r\n
@E,<REC>,<生产帧数>,<发送字节数>,<流错误码>,<流CRC十进制>*<8位CRC32>\r\n
@F,<REC>,<OFFSET>,<LEN>,<2×LEN个HEX字符>*<8位CRC32>\r\n
```

数字字段为无符号十进制；音频 SEQ 从 0 连续递增，每包一个 40 字节 Opus 帧（16 kHz、单声道、20 ms）。文件 LEN 为 1～80。包尾 CRC 覆盖从 `@` 至 `*` 前的全部 ASCII 字节，不包含星号、CRC 文本及 CRLF。采用 CRC-32/ISO-HDLC：反射多项式 0xEDB88320，初始值及最终异或均为 0xFFFFFFFF；校验向量 `123456789` 为 CBF43926，与 Python `zlib.crc32` 一致。流 CRC 和整文件 CRC 分别覆盖原始解码前负载字节，均从 0 的外部增量状态开始。

控制响应只在完整帧边界优先。`@E` 是音频顺序屏障，必须在生产停止及本轮所有排队音频按序交付 USB FIFO 后发送，之后不得再发送该实例音频。生产计数独立于队列接纳及发送计数，溢出或未接纳帧不能被统计掩盖。保存失败单独记入结果，不把它伪装成流校验错误；本轮整体仍不通过。

停止 DONE 仅证明编码、本地保存及设备资源收尾完成，不证明主机已收齐。主机继续等 `@E`，核对实例、序号、生产帧数、字节数、错误与 CRC 后才允许流完整通过。没有结束信息、零帧或尾帧缺失均不得 PASS。设备不等待电脑播放或确认才释放录音资源。

### 5.4 调度、背压与资源预算

- 编码回调使用 64×40 字节有界队列（2560 字节，约 1.28 秒编码数据），只作有界拷贝/计数/CRC，不等待 USB。app_core 每 10 ms 服务一次，空闲控制时每轮最多交付一个音频帧和一个文件帧；控制处理仍保留原 256 输入字节/4 响应预算。USB 栈有待发送包/DMA 时轮询周期为 2 ms，空闲恢复 10 ms；每次仍只推进一个 USB 包，不在 IRQ 中处理业务。
- 文件工作任务优先级 2、栈配置 768，单个读块 80 字节；CRC 扫描缓冲 240 字节，每块让出调度并喂狗。工作任务独占私有读句柄，借助现有格式服务准入封锁库文件接口及其他业务；不借用 BLE 下载句柄、不改闭源库二进制。
- 队列溢出或 2 秒发送无进展触发流失败并请求安全停止，保存结果另记；沿用底层传输超时及 generation 撤销。文件 10 秒无有效传输进展自动取消，状态查询不续期；释放真正完成前保持占用。
- USB 短写不改变上层帧边界。主机处理拆包、粘包及 CRC，半行或超过 258 字节视为通信异常，不猜测性恢复或自动重发修改命令。
- 16 kbit/s 原始负载约 2 kB/s，十六进制加帧头后约 6 kB/s；实际突发、RAM 总量、调度延迟和 USB 吞吐待板测。115200 line coding 不等于 USB bulk 带宽上限。

## 6. 解码、播放与报告

电脑分别保存流缓存和下载文件，配套 Opus 解码与播放。日志文件扩展名为 `.raw`，不能假定其为裸 PCM 或可直接播放的标准 Ogg Opus；实现前核对 RDX 帧封装、帧长及设备文件格式，再确定解码/重封装方式。

源码核对入口为 `rdx_record_format.c/h` 和 `rdx_record_storage.c/h`：现有格式层检查 Opus 16K 单声道 40 字节、双声道 80 字节帧，维护 `.mta` 元数据及文件校验处理。首期应复用其格式和文件身份依据，核对本地写入字节、流回调字节、首帧过滤及尾帧处理后再确定主机解码规则，避免重复建立另一套文件索引或凭扩展名推断。已有 CRC 函数也不自动等于新协议的校验规范；必须核对算法参数、覆盖范围及主机一致性，帧校验与整文件校验分别定义。

首版 Windows 工具依赖 `imageio-ffmpeg==0.6.0`，首次双击运行时按 requirements 安装；录音前确认解码程序可执行。流和文件各自按 40 字节帧重新封装 Ogg Opus，解码为 16 kHz 单声道 WAV，经 Windows 播放，y/n 判定、r 重听。串口持续读取与键盘输入、播放控制分离，等待用户输入时不能停止消费实时流。

JSON 报告保留完整设备身份，并分别记录：

- 录音实例、开始/停止动作 ID、音频格式及保存结果。
- 实时流帧数/字节数、缺包/校验错误、缓存路径、解码及人工回放结果。
- 下载文件标识、预期/实际长度、完整性校验、文件路径、解码及人工回放结果。
- 各阶段 PASS/FAIL/BLOCKED/UNKNOWN、失败原因及时间。

流与文件可能存在头部、尾帧或封装差异，未证明两条路径字节完全一致前，不强制二者原始文件哈希相等；分别验证各自完整性及本次录音关联。主机保存的文件哈希可用于证据追溯，不能单独证明它等于设备源文件。

动作 DONE、文件存在、解码成功均不等于音质合格。保留人工听感判定；自动音量/静音阈值若后续加入，需单独定义标准。音频通过不自动把整体 `overall_factory_pass` 改为 true，仍按完整工站覆盖范围判定。

## 7. 异常与生命周期

| 场景 | 要求 |
|---|---|
| USB 断线、DTR 撤销、总线复位或发送超时 | 旧 generation 失效；停止自身流并触发录音停止保存，等待资源收尾；不清理 BLE 所属动作 |
| 停止应答丢失、进程退出 | 工站结果未知，不自动重发；设备按自身清理规则推进，不向新会话补发旧数据 |
| 存储满、保存失败、停止超时 | 流和保存分别报告；本轮音频整体不通过，保留故障及资源隔离 |
| 正常退出 DUT | 等待停止/保存屏障，CDC 保持；保留本轮文件结果供后续下载 |
| 下载中断/取消 | 释放本轮文件读取资源；半文件不作为完成结果，不删除设备录音 |
| DIP OFF | 沿用平台关机及独立保护，不等待电脑接收或播放完成 |
| 重启或重连 | 不自动恢复旧测试；旧 ID、时间戳或列表位置不能证明结果归属 |

未知结果后的恢复必须先确认设备状态及资源准入；重启不是把旧结果改成通过的依据。

## 8. 实施顺序与验收

1. 核对 RDX 音频输出及保存文件格式，冻结协议扩展、实例关联、容量和解码依赖。
2. 接入 CDC 独立录音授权、开始/停止与保存结果；回归 BLE 原行为及跨来源隔离。
3. 接入实时流分帧、有界发送、终端接收及回放，单独验证录音测试。
4. 接入本次文件元数据、分块下载、完整性校验和独立回放。
5. 合入普通测试交互及报告，执行必要主机回归、默认构建和实板验收。

| 验收项 | 通过标准 |
|---|---|
| 无 BLE、未绑定新机 | CDC 可经 DUT 授权完成两项测试，普通用户录音权限未放宽 |
| 流测试 | 录音期间有连续数据，停止后结束信息完整、可解码且人工听感通过 |
| 文件测试 | 真实保存后下载本轮确定文件，长度/校验及回放通过 |
| 连续两轮及历史文件存在 | 实例与文件正确关联，不误取上轮或列表最后一个文件 |
| 主机慢读、缓冲溢出、缺帧/坏帧 | 明确失败并安全收尾，不阻塞录音任务或关机，不以下载结果掩盖 |
| 保存迟延、空间不足、写入失败 | 停止不提前 DONE，失败可查，冲突动作受阻 |
| 录音/停止/下载各阶段断线及 OFF | 旧数据不串会话，清理不泄漏资源，未知结果不重发 |
| BLE/CDC 共存及分别断线 | 不串音频、不抢授权、不误清理另一来源；BLE 原流程可用 |
| 包装与 MSC 竞争 | 保存/下载占用时拒绝冲突，文件结果确认前不自动包装 |
| 停止时仍有音频排队 | 结束信息不越过尾帧，DONE 不导致主机提前停读；缺尾帧或结束信息不得 PASS |
| 脚本卡住但串口保持连接 | 设备独立时长上限触发停止及保存，不永久录音 |
| 下载分块间删除/替换/格式化及主机停发请求 | 保护持续有效，冲突被拒绝；空闲超时最终释放资源，不拼接不同文件内容 |
| BLE 撤销与 CDC 启动交错、旧会话延迟撤销 | 撤销只作用于匹配的来源和会话，不能误撤销新录音授权 |
| 操作员判失败、播放依赖缺失 | 如实报告，不以动作成功替代音质通过 |

测试沿用统一主机入口与 SDK VS Code 构建任务，只补关键行为验证，避免重复实现细节的测试。软件检查不能替代真实麦克风、USB 时序、播放听感及断电验收。

### RDX / JL 边界复查及收尾补强

此次实现复用 RDX 的采集、Opus 编码、本地保存、DUT 公共仲裁和停止 ticket；CDC 仅增加来源授权、在线流封装与传输、本次文件读取及电脑端判定。app_core 处理命令/发送，编码回调向有界队列交付帧，独立文件任务拥有私有读取句柄。未重写录音引擎，也未修改 JL 编码器或闭源库。

SDK 层仅在 Makefile 注册模块，并调整已有自定义 `usb_factory_cdc.c` 的传输轮询：繁忙 2 ms、空闲 10 ms，端点操作仍归 usb_stack，协议业务不进入 IRQ。该改动服务于多包音频帧吞吐，属于必要且范围可控的接入。

复查发现原 `rdx_factory_audio_shutdown()` 等待文件任务无自身期限，且关闭失败时仍会清除占用。现改为在途操作与最终关闭共用 500 ms 等待预算；失败保留忙状态和隔离，不覆盖仍在运行的工作命令、不重试失败关闭、不允许迟到完成解除隔离。关机和空闲调用方检测失败后执行 `cpu_reset()` 并返回，禁止继续释放文件服务和执行 SD 断电；正常关闭才继续原有流程。这里的 500 ms 是文件任务收尾等待预算，不包含此前既有录音任务退出时间，也不能替代底层 I/O 的故障测试。

回归覆盖正常关闭、在途打开取消、关闭失败、工作任务卡住、最终关闭卡住、计时回绕、共享期限及超时后迟到完成。默认固件构建及统一 15 组主机测试均通过，结果记录于 `cache/cdc_audio_shutdown_build.log` 和 `cache/cdc_audio_shutdown_host.log`。这项收尾补强发生在上述三轮实板验证之后，新固件的故障复位路径仍待专项板测，不追溯标记为已实测。

当前格式层对 CDC 文件占用与 CRC 接口仍有直接依赖；这是局部可维护性折衷，不影响现有职责与存储排他规则。未来扩展其他传输载体时再统一抽取公共校验及文件占用接口，本次不增加一套并行存储管理框架。
