# 量产产线问题积累

记录试产、量产过程中已定位的问题、原因、解决方案和验收依据，供后续产线排查与版本回归复用。

## 1. 试产后新机启动卡死、首次录音不可用

| 项目 | 记录 |
| --- | --- |
| 产品 | T2620，JL AC701N / BR28，板载 SD NAND |
| 触发场景 | 新机 FAT 可正常挂载，但尚未生成 `UXFILE.DAT`，UXFILE 扫描完成标志未建立 |
| 影响 | 启动索引初始化长期不结束，首次本地录音不可用；原始实现还存在扫描与录音并发访问 FAT 的死锁风险 |
| 闭环状态 | 已修复；原记录于 **2026-08-19** 完成实机回归闭环 |
| 详细依据 | [4-2.SD_NAND_FLASH_格式化策略设计.md](4-2.SD_NAND_FLASH_格式化策略设计.md) 第 6.4～6.8 节 |

### 1.1 现场现象与定位依据

异常机器开机日志先确认 FAT 挂载成功，随后进入 RDX 业务索引重建：

```text
[SD-FMT] sd0 mount ok, skip format on boot
[UPGRADE] DAT scan flag mismatch (vm_ret=-251, flag=0xFF, expect=0xAA), will rebuild
DAT file not found, init empty cache.
[UPGRADE] Old cache: 0 entries loaded
[SCAN] Start fscan: storage/sd0/C/
```

原始异常现场中，扫描尚未结束便进入 `rdx_record_run_init()`，`app_core` 与 `uxfile` 并发操作 FAT，连续出现 `timer_no_response`。录音初始化重复注册已在线的 SD0，还会输出 `dev online aready` / `sd add fail`。

第一阶段增加录音忙保护后，实机仍从约 2.955 秒开始扫描，到约 92 秒都没有 `fscan returned` 或 `Rebuild complete`；约 52 秒收到 App 录音命令也无法启动录音。说明防止并发只能控制死锁风险，不能解决扫描本身长期阻塞的问题。

**定位结论：问题在 RDX 业务索引初始化与存储访问协调层。** 现场日志已证明 FAT 可挂载，不能据此判为 NAND 硬件损坏或没有格式化。新机尚无 `UXFILE.DAT` 是合法初始状态，不应要求产线预置该文件。

### 1.2 问题原因

1. **启动策略错误。** 原始 RDX 库把“无 DAT + 空缓存”送入递归全盘 `fscan()`，部分新机扫描长期不返回，将业务索引重建变成普通启动和首次录音的阻塞点。已有记录证实了阻塞位置，未进一步确认 `fscan()` 底层长期不返回的内部原因。
2. **扫描忙状态失效。** `rdx_uxfile_is_scan_active()` 原为固定返回 `0` 的桩函数；本地录音开始前又没有正确检查 UXFILE 同步状态，导致扫描与录音并发访问 FAT。
3. **完成标志处理不完整。** 扫描结果为 0 条时未持久化 UXFILE 完成标志；主动格式化成功后反而将该标志清零，导致后续开机重复触发重建。DAT 保存失败仍返回正记录数，也会使上层误判成功。
4. **重复注册干扰诊断。** 常在线 SD0 已完成注册和挂载，录音初始化仍调用 `dev_manager_add("sd0")`。这是附带缺陷，不是卡死主因。

这里的 UXFILE 扫描标志是 **VM ID `159`，完成值 `0xAA`**，与开机格式化记录 **VM ID `63`，完成值 `0xA5`** 相互独立，不能混用。

### 1.3 最终解决方案

| 修复项 | 处理方式 |
| --- | --- |
| 空索引快速初始化 | DAT 不存在且缓存为空时，直接提交合法的 0 条索引，跳过递归全盘 `fscan()`，写入 VM ID `159 = 0xAA`；首次录音结束后由正常保存流程生成有效 DAT |
| 恢复真实忙状态 | 同时检查 `g_sync_state` 与 `g_dat_need_upgrade_rebuild`，覆盖 `RUNNING/PAUSING/PAUSED` 和首次重建等待期，避免延迟同步启动前出现保护空窗 |
| 本地录音访问保护 | 修改录音运行状态前检查 UXFILE 忙状态；App 本地录音每 2 秒重试，最多 5 次，等待期间 STOP 可取消；设备按键本地录音忙时拒绝，稍后重试；STOP/PAUSE 不受阻塞 |
| 修正持久化结果 | 主动格式化成功后提交空盘状态及 `0xAA`；扫描或缓存重建返回非负值时写 `0xAA`，失败写 `0`；DAT 保存失败返回 `-3` |
| 清理重复注册 | `TCFG_SD_ALWAY_ONLINE_ENABLE = 1` 时，录音初始化不再重复注册 SD0 |

纯在线流式长按录音不访问 FAT，不受上述本地录音门禁影响。空索引快速路径与忙状态保护必须同时保留：前者解决新机启动，后者防止后续存储操作并发。

修复落点位于 `SDK/apps/common/third_party_profile/rdx_protocol/`：

- `patch_librdxApp.ps1`：校验原始库哈希，对 `rdx_uxfile.c.o` 做精确 LLVM IR 补丁并生成 `librdxApp_patched.a`，保留原始 `librdxApp.a`。
- `rdx_record.c`：本地录音忙保护及常在线 SD0 防重复注册。
- `SDK/Makefile`：链接补丁库；第三方原始库升级时必须重新审查补丁匹配及最终链接来源。

### 1.4 实机验收结果

以下为 4-2 留存的 **2026-08-19 历史实机验证结果**：

1. **新机首次启动：** 无 DAT、空缓存时不再出现 `[SCAN] Start fscan`，正常完成空索引初始化。
2. **首次录音落盘：** 生成 `42b595.raw`（15120 字节），DAT 保存日志为 `Stream OK: 163 bytes, 1 records`，并校验磁盘实际写入字节数。
3. **关机重启：** 日志显示 `flag=0xAA`，从磁盘加载 487 字节 DAT，恢复 3 条录音记录，包含首次录音；未再次进入全盘扫描。
4. **App 读取列表：** `getlist/listreq` 成功分包读取完整 3 条记录，输出 `record dat file send finish!`。
5. **相关异常：** 未出现重复注册 SD0 的报错或 DAT 保存失败。激活、USB 角色切换、正常关机阶段的已知定时器超时，应与本次持续 UXFILE/FAT 阻塞区分。

验收结论：新机空索引初始化、首次录音、DAT 持久化、重启加载及 App 列表读取已完成闭环。

### 1.5 产线排查与后续回归要点

- 遇到类似卡死，先保留从开机到录音操作的完整日志，按“块设备可读 → FAT 可挂载 → 业务索引可用”逐层排查；不要仅凭 DAT 不存在就判定 NAND 故障或执行格式化。
- 新机验收应覆盖“可挂载 FAT + 无 DAT + UXFILE 标志未建立”的真实初始状态，验证首次录音、关机重启和 App 读列表；不能只使用已有 DAT 的研发样机。
- 确认量产固件实际链接了包含本次修复的补丁库。手工复制空 DAT、单纯延长录音等待时间都不能作为根本解决方案。
- 主动格式化后的空盘再次启动也要回归，确认不会因完成标志被清零而重复全盘扫描。
- **数据恢复边界：** 已使用设备若 DAT 丢失或损坏、但 raw 录音仍在，当前普通启动路径不会自动扫描找回孤立录音，也不会主动删除这些 raw 文件。显式维护恢复仍是后续功能，需具备超时、取消和进度反馈，不在本次新机问题的验收范围内。

本条为历史故障留存，不重新定义当前开机格式化策略；当前产品策略以 `t2620_project_config.h` 和存储生命周期实现为准。

## 2. 无 USB 拨码开机后卡死，蓝灯常亮，反复拨码无法关机或重新开机

| 项目 | 记录 |
| --- | --- |
| 记录日期 | 2026-09-22 |
| 现场条件 | 未插 USB，通过拨码开关开机 |
| 故障现象 | 正常开机为蓝灯闪烁；异常后蓝灯持续常亮，反复拨动 OFF/ON 无法关机或恢复开机 |
| 当前状态 | **卡死原因尚未查清，未修复、未完成回归闭环** |
| 已确认结论 | 拨码只提供 GPIO 状态，不切断主芯片供电，不能用于死机后的强制断电重启 |
| 硬件依据 | [T2620-MMI-V00_20260608.pdf](../T2620-MMI-V00_20260608.pdf) 第 1 页，S1、PB1 及 VBAT 接线 |

### 2.1 为什么反复拨码无法恢复

按上述版本原理图，S1 是普通机械拨动开关，但它在电路中承担的是**开关状态输入**，并未串接在主芯片供电路径上：

- S1 的 2 脚接主芯片 PB1（20 脚），通过切换接点改变 PB1 是否接地；D9 为该信号的对地保护器件。
- 电池 `VBAT+` 连接主芯片 `VBAT`（13 脚），这条供电线路不经过 S1。
- 因此，拨到 OFF 不会直接切断主芯片电源，拨回 ON 也不等同于重新上电或硬件复位。

固件与该接法一致：`get_power_on_status()` 读取 PB1，低电平表示 ON；`rdx_dip_switch.c` 设置输入上拉，通过 100 ms 软件定时器采样、消抖，并在无 USB 的正常业务路径下发送软关机请求。P33 拨码中断回调本身不执行强制关机或复位。

**所以，拨码开关能否完成关机依赖软件继续运行。若采样、消息处理或关机流程被阻塞，反复拨动只会改变 PB1 电平，无法强制重启设备。** 这是本次“拨码无法恢复”的设计层面解释，不是卡死根因已经定位的结论；关键在接线方式，不能仅凭“普通机械开关”判断它是否能够断电。

### 2.2 卡死原因与当前证据边界

蓝灯闪烁由 20 ms 软件定时器驱动。卡死后蓝灯常亮，可能是灯效停止刷新并停留在最后的亮灯状态；结合拨码也无响应，应优先排查 `app_core`、定时器回调及关机路径是否阻塞。**仅凭灯色不能确认具体阻塞位置，也不能证明整个 CPU 已停止运行。**

本次未插 USB，不能直接归因于带 USB 收尾失败路径；也没有证据证明它与第 1 条的 SD NAND / UXFILE 初始化卡死属于同一原因。目前尚无本次故障的串口日志、任务现场或蓝牙响应信息可用于定根因。

### 2.3 后续处理

1. 保留从拨码开机到卡死的完整串口日志，记录蓝灯停止闪烁的时点、卡死后蓝牙能否扫描/连接，以及是否发生自动复位。
2. 排查应用任务阻塞、关机流程和看门狗喂狗机制，确定卡死触发条件后再制定修复方案。
3. 单独评估异常恢复保障：现有拨码不具备硬件强制断电能力；若要求软件卡死后仍可由用户强制恢复，需要独立于阻塞任务的复位或断电机制。

本条暂不记录“已解决”。后续取得根因、修复版本及实机回归结果后补充闭环。

## 3. 频繁拨码开关机后死机、蓝灯常亮，仅插拔 USB 后恢复（新问题，实机待闭环）

| 项目 | 记录 |
| --- | --- |
| 记录日期 | 2026-09-23 |
| 触发场景 | 反复拨动拨码开关进行开机、关机 |
| 故障现象 | 设备卡死、蓝灯常亮；此后再拨动开关已无作用 |
| 现场恢复方式 | 用户确认：插入 USB 进入充电，再拔出 USB 后恢复 |
| 原始日志 | [频繁开关机，设备死机，蓝灯常亮.txt](../频繁开关机，设备死机，蓝灯常亮.txt) |
| 当前状态 | **作为此前未排查过的新死机方式单独存档；已按后续要求补齐代码复核发现的缺口，实机尚未闭环，不宣称已解决** |
| 已有处理 | 已实现关机时序保护，主机测试及构建通过；实际故障是否消除尚未验证 |

### 3.1 现象与问题区分

本条的明确触发条件是频繁开关机，且有“死机后拨码失效、插入 USB 充电再拔出可恢复”的现场反馈及异常日志。作为新问题独立记录，不能因蓝灯常亮就与第 1 条的 UXFILE 初始化阻塞或第 2 条的无 USB 开机卡死合并归因；第 2 条仍保留原有未定位状态。

拨码开关只改变 PB1 输入，不切断主芯片供电。异常后如果软件无法继续采样或处理关机请求，拨动开关便无法恢复设备。USB 插拔是用户已验证的现场恢复办法，但是否通过复位或其他电源状态变化恢复，尚无对应日志确认。

### 3.2 原因分析与证据边界

日志末次异常中，`00:00:01.183` 执行 `rdx_ble_server_init`，`00:00:01.221` 进入 `sys_enter_soft_poweroff`，`00:00:01.302` 执行 `rdx_app_all_exit` / `rdx_ble_server_exit`，`00:00:01.410` 进入 `btstack_exit`，随后出现 `Chip Exception`、`cpu0 write mmu excption`，CPU0 RETI 为 `0x060E28B0`。

已确认修改前业务启动后的 USB OFF 会经过存储收尾屏障，而电池供电 OFF 因 `!vbus && !s_wait_busy` 直接返回，绕过已有存储生命周期收尾屏障，进入原生蓝牙栈退出流程。结合日志，怀疑快速关机时后台初始化或安全计算与资源销毁发生时序冲突。这是当前的产品层风险判断，**尚未确认 JL 闭源栈内的具体异常根因**；日志固件与 ELF 未确认完全匹配，不能指定故障源码行或断言某个对象被提前释放。

蓝灯常亮与异常后灯效停止更新相符，但灯色本身不能定位根因；`timer_no_response` 也不能单独证明死锁。

### 3.3 已实现的处理方案及限制

> 2026-09-24 策略修订：本节保留历史方案和当时的验证记录。下述“存储屏障决定能否关机、失败后停留错误状态、忙状态无限等待”不再作为后续产品要求，统一由第 5 节整改方案替代。历史构建和测试通过不代表第 5 节已经实施，也不能证明当前工作树仍包含本节全部历史改动。

1. 仍以 100 ms 周期采样，连续两次一致才认可开关变化。
2. 已进入业务模式但 RDX 产品任务和接口尚未初始化完成时，OFF 暂缓处理，不发送原生栈关机请求。
   使用 `rdx_app_business_ready()` 检查任务初始化完成标志，不能将 `business_started` 当作完成标志。
   此标志也不代表蓝牙栈所有后台计算已经结束，因此仍保留收尾后复位的策略。
3. 业务运行中的 OFF，无论 USB 还是电池供电，都关闭业务准入，等待录音关闭、
   真实 BLE 断连及 RDX 工作队列收尾，再等待文件工作任务屏障完成。
4. 收尾期间保留蓝牙栈资源，完成后执行已有 `rdx_cpu_reset()`。
   冷启动重新读取 DIP/VBUS：OFF 且无 USB 进入冷关机；ON 则重新启动业务；
   OFF 且有 USB 保持原有充电/可选存储服务策略。
5. 收尾开始后不能原地恢复业务。反复拨回 ON 只影响下一次冷启动选择，
   不重新启动录音、不重复排队收尾，也不销毁尚在工作的蓝牙栈。
6. 不稳定的输入继续使用上次消抖结果推进已有收尾，避免持续抖动饿死完成检查或超时检查。

OTA、格式化、未完成封箱的 DUT 等待策略现在也适用于电池 OFF：开始收尾前等待这些操作结束，
稳定拨回 ON 可以取消等待。等待阶段尚未开始 30 秒收尾计时。
封箱格式化及所有参数持久化成功后，单独设置提交完成标志，允许仍处于 DUT 模式的设备
通过拨码进入正常收尾；任一步失败都不能设置该标志。普通 DUT 模式仍需先退出再关机。
USB 拔出等独立的正常关机请求统一检查产品关机保护：业务模式且实际拨码为 OFF 时，
即使首次采样尚未发生，也不进入原生栈退出；交由拨码消抖及收尾处理。
无业务冷关机、ON 状态且无收尾等待时的普通关机，以及低电压紧急关机保持原路径。
收尾阶段失败或超过 30 秒仍保持禁止业务和错误灯效，不强制复位丢弃未保存的数据。
初始化等待和 OTA/格式化/DUT 等待没有强制超时复位；如果初始化或忙状态不能结束，
OFF 可能持续等待。这是当前恢复能力边界，不能将本修改表述为所有死机均可由拨码恢复。
低电压紧急关机路径不因此次修改被改写。

上述方案用于降低触发异常的风险，并不提供程序已经异常停住后的拨码强制恢复能力。现有固件改动保留，不因此前搁置而回退。

- 电池与 USB OFF 都必须等完整屏障后才能复位。
- 单次短 OFF 脉冲不会启动关机；初始化未完成时不会直接退出栈。
- 收尾期间每次回调都发生输入变化，仍可完成，或按时进入失败状态。

- OTA/格式化/DUT 等待可以在稳定 ON 后取消。
- 联合执行真实封箱提交、DUT 关机准入及存储生命周期代码，验证成功后完整收尾再复位，
  格式化失败和三个持久化步骤失败均不放行。
- 执行真实 `sys_enter_soft_poweroff()`，验证首次采样前、初始化等待及收尾期间的独立请求被拦截，
  冷关机、ON 状态普通关机和低电压紧急保护不受误拦截。
- 排队失败、存储失败、超时及计时器回绕保持失败保护。

主机测试不执行 JL 二进制蓝牙栈，也不模拟硬件供电，不能证明设备故障已消除。

| 场景 | 验收重点 |
| --- | --- |
| 纯电池，开机后 0.5–2 秒内 OFF/ON，交替快慢拨动 | 无 MMU 异常、无蓝灯卡死；最终 ON 可连接，最终 OFF 真正关机 |

| OTA、格式化、DUT 中 OFF，再 ON | 等待策略符合预期，恢复 ON 可取消未开始的收尾 |
| 封箱提交成功后，拔除 USB 并拨 OFF | 红灯完成状态可进入收尾并最终关机，不长期等待 DUT 退出 |

预期业务关机日志包含 `[USB-SWITCH] admission closed`、`recording closed`、
`saved and quiet; controlled reset`（沿用旧日志前缀，也用于电池关机）。
最终冷启动的 OFF 通过无业务的关机路径结束，不应再次进入 `rdx_app_all_exit -> btstack_exit`。

### 4.3 VCM 复位原理

VCM 复位通过芯片的硬件检测与复位通路工作。外部信号施加到 VCM 检测节点，满足硬件触发条件后，P33 产生复位请求。SDK 将该来源定义为 `P33_VCM_RST`，注释为“vcm高电平短接复位”。本次启动日志显示，P33 进一步触发 P11 复位，再由 P11 触发主系统（MSYS）复位：

```text
VCM 节点满足触发条件 → P33 → P11 → 主系统复位 → 重新执行启动初始化
```

这条硬件通路不需要应用任务轮询 VCM、处理按键消息或调用 `cpu_reset()`，因此可作为业务任务卡死时的外部恢复入口。它需要外部施加触发信号，不会自动判断软件是否卡死；具体卡死场景下能否恢复仍需实测。

复位会中断当前程序执行，随后重新初始化任务及外设。它不执行正常关机收尾，也不等于恢复出厂或格式化；录音及存储写入可能被打断，复位后仍需检查文件与索引完整性。

本次 `0x4` 是日志中的 P33 复位来源值，不能当作 `VCM_DET_EN` 使能位。触发电压阈值、最小保持时间和允许接入电源需以 AC701N 芯片资料及板级电路为准，不能从“高电平”注释推导出任意电源均可直接短接。

### 5.2 当前检查机制与错误传播链

`rdx_record_format_boot()` 是录音格式与索引恢复机制，不是 FAT 挂载检查，也不是自动格式化。其目的是保存单声道/双声道信息，并协调 RAW 音频、MTA 元数据与 `uxfile.dat` 索引，避免重启后以错误的 40/80 字节帧规格处理录音。

当前机制主要执行：

1. 重放 `rfmt.tmp / rfmt.cmt` 的索引提交事务。
2. 扫描 MTA，检查名称、长度、magic、SN、ready、格式及元数据校验值。
3. 检查对应 RAW 的首帧校验和长度是否按帧对齐，检查重名、重复 SN 和数量上限。
4. 修正已有 DAT 条目的格式，恢复缺失条目；必要时读取整段录音计算 CRC 并提交新索引。

当前的关键错误是故障作用域：某一条录音或索引协调失败，会设置全局 `rf_error=-1`；`rdx_app_tasks_init()` 只在检查成功时执行 `rdx_uxfile_init()`；`rdx_storage_lifecycle_business_blocked()` 又把此错误当作全局业务禁止条件，最终统一广播被关闭，APP 无法连接来处理异常录音。这个全局错误还会影响后续录音准入。

```text
历史文件/索引检查失败
  → 全局录音格式错误锁存
  → 文件服务初始化被跳过、业务被禁止
  → 统一 BLE 广播被抑制
  → APP 无法连接，更无法删除导致问题的录音
```

整改决定：**去掉“录音启动检查失败就不让设备开机”的门禁，保留按文件校验与必要的安全恢复。** 不能只删除函数调用或强行返回成功，否则可能把损坏 DAT 直接交给库，或按错误声道格式播放；也不能只跳过异常文件，使它们从 APP 消失。

### 5.3 产品行为和故障隔离边界

| 情况 | 设备与连接 | 文件操作 | 新录音 |
| --- | --- | --- | --- |
| 单个录音未完整结束、尾帧残缺 | 正常开机、广播、APP/HOGP 可用 | 列表保留该录音并标识未完整结束；可删除；可信格式下可提供完整帧部分的播放/导出 | 存储和写入条件正常时允许 |
| MTA 缺失/损坏、格式未知、首帧校验失败 | 正常开机与连接 | 提供可删除条目；不猜测声道或伪造时长，不把未知格式送入解码器 | 不因历史单文件错误永久禁止 |
| DAT 损坏或提交事务无法重放 | BLE、APP 和 HOGP 保持可用 | 文件服务进入恢复模式，保留原文件和事务证据，重建可管理目录；未完成时明确“整理中” | 仅在写入和编号分配安全后开放，不阻断设备启动 |
| 当前介质读写失败或无法挂载 | 保留连接、状态查询和拨码关机 | 明确存储不可用；无法执行的删除必须返回失败，不能假报成功；不自动格式化 | 暂停本地写入，不能伪装录音已成功 |
| 整理超时或资源不足 | 已开放的连接继续工作 | 有界重试/暂停并保留进度，不能永久转圈或无限重启 | 根据实际可写能力独立判断 |

“不让用户感觉设备异常”的落地标准是正常开关机和主要交互不中断。确实不完整的录音只在该条目呈现状态，不用全局红灯、停止广播或整机锁死代替错误处理。真正的存储故障仍需如实反馈，不能显示虚假的录音或删除成功。

### 5.4 开机及 APP 文件管理整改

**A. 将设备启动与文件整理分离。** 先完成 DIP/电源管理和 BLE 控制服务的最小初始化，再运行有界的文件检查。不得让全盘扫描、全文件 CRC 或索引重写同步阻塞 `app_core`。广播资格只检查电源状态和传输自身条件，历史录音健康状态不再参与；HOGP 仍保留原有加密、订阅和会话条件。

文件整理迁出启动关键路径不等于允许并发访问索引。必须由同一个存储执行者串行拥有 RAW/MTA/DAT 与库缓存；恢复未交接时，文件命令返回明确的准备状态，不能直接调用未初始化的库。待有效索引或恢复目录就绪后再交接文件服务，禁止后台 `rf_merge()` 与运行中的库同时改 DAT。底层单次 I/O 若不可中断，必须评估驱动超时和看门狗边界，不能仅在外层循环加时间判断就宣称有界。

**B. 将结果拆成单文件健康状态、索引恢复状态和当前存储 I/O 状态。** 单个文件错误记录后继续处理其他文件；历史失败不能污染新录音会话。超过现有 300 条处理上限时分页/分批处理，不允许因第 301 条阻止开机，也不允许静默丢失列表中的剩余录音。旧版无 MTA 的 RAW 同样需要兼容，不能只扫描 MTA 后把其他文件遗漏。

**C. 异常录音必须有 APP 可管理条目。** 目录枚举与可播放索引分离：即使无法生成完整的正常录音元数据，也要提供稳定、唯一的管理标识、原始文件名、实际大小和健康状态。重复 SN 的文件不能共用删除身份；不能凭损坏的 MTA 推导任意路径。时间、格式等不可确认的字段显示未知，不伪造有效值。现有协议和 APP 是否能承载异常条目需要联调确认；若必须扩展，明确版本兼容，并验证旧 APP 至少能列出和删除，不能假定升级固件后自然成立。

**D. 删除不依赖录音检查成功。** 在正常挂载且允许写入的前提下，APP 可删除指定异常 RAW 及其确认关联的 MTA，并更新恢复目录与正常索引。孤立 MTA 也应纳入可清理对象，不恢复为虚构音频。删除须串行化并可重试，以稳定身份处理重复请求；处理中断后不得误删其他录音或因旧事务重放让条目复活。仅在删除和必要持久化完成后回复成功，失败须能再次操作。关联文件和索引的删除顺序、事务重放去重规则必须在实现时一起设计与测试。

**E. 索引恢复失败不能毁掉恢复入口。** 校验失败的 DAT/提交标记不能直接交给闭源库解析；保留原件，构建独立的安全目录/新索引，验证完成后再提交。严禁为让开机通过而清空 DAT、删除 RAW、自动格式化或反复重启。没有可靠旧索引时，APP 的连接和恢复管理仍需可用。校验通过的完整帧可以作为可播放范围，原始尾部数据默认保留，不在开机阶段静默截断。

库适配涉及 `rdx_uxfile.h`、`librdxApp` 及其补丁脚本/IR，不能仅在 `rdx_record_format.c` 修改返回值。必须核实实际 list/delete 路径、异步完成回调、缓存所有权和协议字段，沿用已有哈希校验的库补丁流程。

### 5.5 软拨码关机整改

PB1 拨码是普通 GPIO 输入，不会物理切断供电。因此软件必须负责响应最终位置并进入对应电源状态，不能要求用户用断电重启来退出错误状态。

本次工作树复核仍发现：DIP 使用 `app_core` 的 100 ms 定时器和两次一致采样，P33 回调为空；DIP 处理会先经过存储生命周期；存储失败态可持续吞掉后续处理，OTA/格式化/DUT 忙等待没有统一截止期限，30 秒收尾失败后仍留在失败态；原生关机还有存储否决条件、音频等待及 idle 中 LED 重试。这些是源码风险，异常启动日志本身没有证明逐一触发。

本次提供的仓库指导已要求“OFF 进入 JL 原生软关机、业务不能否决、录音尽力停止、保留平台反初始化和 RTC 保存”。实际工作树及磁盘旧说明仍有差异，实施前必须对照目标提交与最终烧录固件核实，不能把指导中的目标行为当作已实现事实。

整改状态流如下，具体入口以 JL SDK 允许的上下文实现：

```text
ON 启动/运行
  → 稳定 OFF 被接受
  → 关机请求锁存，停止接受新业务，尽力通知录音停止
  → JL 原生软关机与平台清理
  → 最终重读 DIP/VBUS
      OFF + 电池：软关机
      OFF + USB：充电待机，默认不启用 BLE/MSC
      ON：通过受控重启进入全新运行时
```

1. **OFF 不以保存成功为条件。** 从关机准入中移除录音/文件/BLE 导出屏障和存储错误否决；录音停止仅为尽力通知，不建立必须完成的保存协调器。业务保存失败记录原因，不能拒绝关机。USB 存储所有权保护只服务于显式 MSC 导出，不继续承担关机职责。
2. **全部关机等待有总截止时间。** 提示音缺失、播放回调不返回、LED 未 idle、音频不退出、初始化不结束或业务忙均不能无限延期。统一用首次接受 OFF 的时间计算期限，重试或抖动不能刷新期限。正常路径保留 platform uninit、硬件 RTC 保存与 GPIO/唤醒配置；紧急兜底无法执行的清理需单独记录并验证。
3. **异常恢复不能完全依赖 `app_core`。** 建立 P33 边沿事件/独立计时的异常保护，ISR 只做最小采样、锁存和唤起，不执行 FAT、蓝牙栈销毁或阻塞操作。若主任务未在期限内推进，使用经 SDK 验证的独立复位/电源恢复路径；复位后优先读取 DIP，OFF 不再启动业务。必须测试任务阻塞、长关中断和看门狗喂狗条件；普通 GPIO 软件处理不能承诺覆盖所有硬件/CPU 故障，第 4 节 VCM 仍是服务兜底。
4. **快速 OFF→ON 按最后稳定位置收敛。** 未通过消抖的短脉冲不关机；关机一旦接受，不原地复活正在销毁的 RDX/蓝牙运行时。最终 ON 通过受控重启启动。软关机前重新核对电平和唤醒边沿，并解决“已为 ON、没有新边沿”的竞态，不能关机后等用户再拨一次。
5. **启动早期也能关机。** 从初始化开始就建立电源控制与超时保护；若蓝牙资源尚未达到可退出阶段，走经验证的早期关机/复位入口，避免对半初始化栈调用常规销毁。不能以无限等待 `business_ready` 代替这个分支。第 3 节 MMU 异常必须用匹配 ELF 回归，不能只删除存储屏障后宣称完成。
6. **统一 USB 和特殊业务行为。** 电池与 USB 均响应 OFF；OFF 冷启动默认充电待机，ON 允许充电与业务共存。CDC/MSC 不得重新阻塞关机，MSC 继续只在安全的冷启动所有权下按配置开放。OTA 必须使用 SDK 可恢复的中断/提交边界；若短暂提交不能打断，应给出经过验证的有限上界。格式化/DUT 不得保留无限等待；中断后不得伪报完成，下次开机仍保留连接与诊断入口。

建议本轮工程验收目标：稳定拨码识别不超过 200 ms；正常 OFF 后 1 s 内进入目标电源状态，故障兜底不超过 3 s；ON 后 2 s 内可被扫描。以上是待实测校准的目标，非当前固件能力声明。若 SDK 的安全时序无法满足，必须记录具体阶段和有限上界，不接受无限等待；电池软关机需测量电流，USB 待机按充电状态验收。
