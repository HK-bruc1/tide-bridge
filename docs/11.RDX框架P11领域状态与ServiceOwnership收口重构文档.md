# RDX 框架 P11 领域状态与 Service Ownership 收口重构文档

> 日期：2026-07-26
> 当前状态：实施基线 v0.6；P10 已由用户确认验收，但仓库内缺少生产归档的可追溯链接。P11.0 静态文本基线、ABI/ownership、精确 allowlist/public-header 门禁和 Host trace scaffold 已完成 Mac 静态审核；可执行 caller golden trace、真实 context、Windows/JL linkage/map 与 P10 证据链接尚未闭环。因此 P11.0 阶段验收未完成，暂不授权 P11.1，且未迁移生产业务行为。
> 上游依据：`docs/10.RDX框架P10持久化边界收口实施文档.md`、`docs/3.RDX框架JL平台复用性优化大纲.md`、提交 `128eb8d` 的当前源码盘点。
> P11 定位：在 P10 已稳定的持久化边界之上，收口录音与文件控制面的状态所有权，用 record/storage/device service 的语义命令和只读查询替代跨模块裸指针与直接状态改写。
> **P11 第一硬约束：RDX 静态库 ABI 不破坏。** `librdxApp.a` 二进制、其依赖的旧符号、`RecordStatus`/`ReqFileInfo` 等静态库可见数据布局、回调表布局、旧返回值和时序副作用均不得改变。

## 1. 结论

P11 不重写录音状态机，也不把 `RecordStatus` 换成新的内部对象。P11 建立的是一条可防退化的控制依赖链：

```text
app / charge / dut / led / ota / device service / storage service
                         |
                         | 语义命令、只读快照、明确 busy 查询
                         v
                  rdx_record_service
                         |
                         | 私有 domain adapter
                         v
                  rdx_record.c
             record_status + legacy engine
                         |
                         | 旧 ABI 原样保留
                         v
                    librdxApp.a
```

文件控制面采用相同原则：

```text
device / record service / app / dut
                         |
                         | format、窄查询、cleanup、lifecycle
                         v
                  rdx_storage_service
                         |
                         | legacy uxfile adapter
                         v
             rdx_uxfile_* / ReqFileInfo compatibility boundary
```

P11 完成后应满足：

1. `rdx_record.c` 仍是 `record_status` 的唯一物理存储者，`rdx_record_service` 是业务控制面的唯一逻辑所有者。
2. `rdx_record_get_status()`、`rdx_record_process()` 及 `RecordStatus` 完整保留，但只服务静态库兼容和受控 adapter，不再作为普通业务 API 扩散。
3. `rdx_app.c`、charge、DUT、LED、OTA、device/storage service 不再取得可写 `RecordStatus *`。
4. 停止、启动、切换、模式更新等操作使用语义命令；只读判断使用快照或窄查询。
5. `rdx_storage_service` 收口 P11 触及的文件控制面；`rdx_record.c` 实时写入热路径和 WiFi TX completion 等 P12 转交项作为精确例外保留。
6. device service 只负责跨领域流程编排，不直接拥有、改写或猜测 record/storage 内部状态。
7. event bus 只发布“已经发生”的状态通知，不承载必须立即得到结果的同步命令和查询。
8. APP 协议字节流、录音状态转换、线程上下文、定时器、文件写入顺序、断连清理顺序、关机/reset 顺序保持不变。

P11 必须按“P10 关闭与 ABI 冻结 -> 查询面 -> 低风险只读调用点 -> 停止命令 -> Record service 内部写访问 -> Storage 控制面 -> 最终门禁”的顺序执行。禁止先全局禁止旧指针，再集中修复编译错误。

## 2. 启动门槛、范围与非目标

### 2.1 P11 启动门槛

P11 代码迁移开始前，P10 必须实际满足而不是仅在文档中计划满足：

- 最终 CC 生产 clean build 已完成并固化 firmware、ELF、map、构建日志和 SHA256。
- P10 持久化专项回归及核心冒烟已通过并完成归档。
- `librdxApp.a` SHA256 仍为 `c540d70540dc4d61e15d1ca13579cd2342d4ea972ff0a74a1afccc04b1ef4aca`。
- 固定 P8 ABI 基线仍为 `5d0284f17006bd333de992ed22d5a1c7484c37a0`，没有被 P10/P11 当前提交替换。
- P10 最终 CC map 可作为 P11 Flash/RAM 与调用关系基线。
- P10 验证归档中的遗留问题已分为“阻塞 P11”或“可后续处理”。

P10 未关闭时，P11 允许新增本设计文档、只读盘点和不接入生产构建的测试草案；不得修改 `rdx_record.c`、service 调用链或生产 Makefile。

本轮启动记录（2026-07-26）：用户已明确确认 P10 验收，P11 因此进入 P11.0。当前执行环境为 Mac、生产环境为 Windows/JL；本轮只建立源码静态证据，不在 Mac 尝试替代生产编译、link/map 或目标板验证。P11.0 结果归档于 `docs/verification/2026-07-26-rdx-p11-p0-baseline.md`。

### 2.2 P11 范围

P11 处理以下控制面边界：

- `RecordStatus *` 的跨模块获取、读取和直接字段写入。
- 对 `rdx_record_process()` 的跨模块直接调用和任务投递。
- record service 内对 legacy record engine 的访问方式。
- app、charge、DUT、LED、OTA、device/storage service 的录音状态查询和命令。
- record/device/app/DUT 当前活跃流程必需的 `rdx_uxfile_*` 控制面调用，包括格式化、`is_formatting` 窄查询、录音文件时间修正、BLE 清理和必要的 runtime init/exit 薄封装。
- device service 对 record、storage、WiFi、OTA 各 owner 的窄查询与既有流程编排；不把跨领域 busy 状态汇总到 storage service。
- `ReqFileInfo *`、`RdxWifiInfo *` 只在 P11 触及的 device busy gate 中改用既有 WiFi 窄查询；其余裸状态访问与 WiFi 数据发送状态机转 P12。
- P11 静态边界脚本、ABI 检查扩展、host 状态契约 mock 和生产回归归档。

### 2.3 明确非目标

P11 不处理：

- 不修改、重编译、替换、重新打包或反编译 `librdxApp.a`。
- 不改变 `RecordStatus`、嵌入它的 `rdx_tws_sync_record_t`、`Record_info`、`ReqFileInfo`、`uxfile_data_t`、`RdxProtocolCallbacks`、`RdxProtocolIndicateOps` 的布局。
- 不删除或改签名 `rdx_record_get_status()`、`rdx_record_process()`、`rdx_uxfile_*` 等旧符号。
- 不重写 `rdx_record.c` 内部录音状态机、音频 task、编码链、暂停超时、MIC gain 或异常恢复逻辑。
- 不把 `record_status` 搬到 service，也不维护 service 状态副本作为第二真相源。
- 不迁移 `rdx_record.c` 中 `rdx_uxfile_raw_write()`、DAT 生成/保存等实时数据面热路径。
- 不把同步 stop/start 命令改成 event bus 广播。
- 不顺带统一全部 WiFi/OTA/VM 裸状态，不以清零所有 `extern` 为本阶段目标。
- 不在 P11 收口 WiFi TX completion 内部的 `ReqFileInfo *` 状态机或其 uxfile cleanup；该路径作为精确兼容例外转 P12。
- 不建立跨 record/storage/WiFi/OTA 的全局 `system_busy` 或 activity 位图；device service 必须分别询问各 owner。
- 不迁移或启用 `rdx_device_service_emmc_poweroff_check()` 后方当前不可达的 eMMC 自动下电 activity 策略；入口必须继续立即返回，恢复该策略需另立硬件行为项目。
- 不新增动态分配、通用状态机框架、大型 vtable、反射或消息中间件。
- 不以 `rdx_app.c` 行数下降作为完成条件。

## 3. 第一硬约束：静态库 ABI 完整保护

### 3.1 保护面

| 层次 | P11 必须保持 | P11 禁止操作 |
|---|---|---|
| archive 二进制 | `librdxApp.a` Git blob 与固定 SHA256 | 重编译、替换成员、重新打包、更新基线掩盖变化 |
| 外部符号 | 静态库 undefined symbol 对应的名称、可见性、调用约定、参数、返回类型 | 删除、改名、改签名、改 `static`、条件编译掉 |
| 指针身份 | `rdx_record_get_status()` 继续返回原 `record_status` 稳定地址 | 返回临时快照、新对象或 service 镜像；改变对象生命周期 |
| 数据布局 | `RecordStatus`、嵌入它的 `rdx_tws_sync_record_t`、`ReqFileInfo`、协议回调结构等字段顺序、类型、大小、对齐 | 增删字段、调序、改类型、改变 packing/alignment |
| 回调 payload | `rdx_protocol_record_trigger_indicate(RecordStatus *, ...)` 看到的 legacy payload | 改成新 snapshot、用不兼容强转、缩短对象生命周期 |
| 行为 | 旧入口的同步/异步上下文、返回值、协议 indicate 与副作用顺序 | 用统一异步队列改变时序；把 `rdx_err_t` 直接穿透旧 ABI |

### 3.2 允许的兼容实现

P11 只允许以下加法式改造：

1. 新增不暴露 legacy 结构的 service public API。
2. 新增 `rdx_record` 私有 domain adapter/header，供 record service 调用。
3. 旧函数继续导出；如果内部转发，旧签名、对象身份、返回口径和副作用必须完全保留。
4. 需要向静态库传递 `RecordStatus *` 时，仍构造完整 legacy 对象并在回调结束前保持有效。
5. `rdx_record_get_status()` 即使源码调用点降为零，也不得删除、改为 `const` 返回、改名或隐藏。
6. `rdx_record_process()` 即使业务调用点全部迁移，也不得删除、改签名或改变原线程要求。

### 3.3 P11 ABI 门禁

P11.0 必须先扩展 ABI 脚本并通过，之后才允许新增任何生产 API 或迁移调用点。扩展项至少包括：

1. 从固定 P8 基线提取并比对 `rdx_app.h::rdx_tws_sync_record_t`，防止嵌套 `RecordStatus` 的 TWS 同步布局漂移。
2. 检查 `rdx_record_get_status()` 和 `rdx_record_process()` 定义仍为外部可见，不能仅检查 header 声明。
3. 在 Host 可链接条件下连续调用 `rdx_record_get_status()`，确认返回同一非 NULL 对象；该检查证明稳定身份契约，不比较不同固件运行时的绝对地址。
4. 读取 P10 最终 archive undefined symbols 或最终 CC map 交叉引用，形成 record/uxfile/protocol 触及符号清单。
5. 对 `RecordStatus`、`rdx_tws_sync_record_t`、`MicGainPara` 和协议回调结构执行大小、关键 `offsetof` 与基线文本双重检查；JL 实际大小仍以生产工具链为准。
6. 将当前已确认、且与 P11 直接相关的旧 wrapper 加入固定检查：
   - `void rdx_record_mode_active_check(bool show)`。
   - `u8 rdx_app_get_record_mode(void)`。
   - `RdxWifiInfo *rdx_app_get_wifi_info(void)` 及返回对象稳定身份。
   - `void rdx_app_emmc_poweroff_check(void)`。
   - `void rdx_app_emmc_poweroff_check_timer_stop(void)`。
   - `void rdx_app_emmc_poweron(u8 check_en)`。
   - `rdx_record_clear_marks()`、`rdx_record_get_marks()` 和 record reboot flag 旧入口。

完成上述前置扩展后，每个代码提交在 clean build 前必须：

1. 比对 archive Git blob 和 SHA256。
2. 执行 `test_rdx_static_library_abi.ps1 -BaselineRef 5d0284f17006bd333de992ed22d5a1c7484c37a0`。
3. 比对 `rdx_record_get_status()` 对象身份契约、`RecordStatus`/`rdx_tws_sync_record_t` 布局和 legacy record 函数签名。
4. 从 P10 最终 map/undefined symbol 表核对 P11 触及的 record/uxfile/protocol 符号仍存在。
5. 检查 `rdx_protocol.h` 与固定 P8 基线完全一致。
6. 禁止用新的 P11 commit 更新 ABI baseline。

ABI 失败是阶段停止条件；clean build、链接成功或板测正常都不能替代 ABI 证明。

## 4. 当前耦合基线

### 4.1 `RecordStatus` 当前访问

在提交 `128eb8d` 的文本盘点中，`rdx_record_get_status()` 符号命中主要分布如下；约数可能包含前置声明，最终实施前需在 P11.0 用 active-preprocessor 口径刷新为真实调用数：

| 模块 | 调用点约数 | 当前用途 | P11 归属 |
|---|---:|---|---|
| `rdx_record.c` | 15 | owner 内部状态机和数据面 | 保留，属于物理 owner |
| `service/rdx_record_service.c` | 14 | 命令编排、直接改字段、协议 payload | 迁到私有 adapter；legacy payload 作为精确例外 |
| `rdx_app.c` | 13 | 按键、消息、idle、恢复、模式切换 | 改为 query/command；旧 ABI wrapper 保留 |
| `service/rdx_device_service.c` | 7 | 关机/reset/busy，以及不可达 eMMC 历史代码 | 活跃路径改 query/command；eMMC 禁用路径不迁移 |
| `rdx_charge.c` | 3 | OLED 条件和 charge prepare stop | query/stop command |
| `rdx_dut.c` | 3 | DUT 录音与进入条件 | query/start/stop command |
| `rdx_led_ctrl.c` | 2 | 灯效优先级判断 | 只读 `is_active()` |
| `rdx_ota.c` | 2 | 当前存在无实际消费的局部变量 | P11.0 确认后独立删除死读取 |
| `service/rdx_storage_service.c` | 1 | format busy 判定 | 只读 `is_active()` |

当前外部模块不只读取状态，还直接写 `run`、`scene`、`mode`、`orig_mode`、`is_switch`、`key_trigger`、`rerun` 等字段。单纯将 getter 返回值改为 `const` 会破坏旧 ABI，也不能解决静态库可能写入的问题，因此禁止采用。

### 4.2 `rdx_record_process()` 当前外部调用

除 owner 内部外，当前直接调用/投递存在于 app、charge、DUT、device service 和 record service。不同调用点有三种语义：

- 当前线程内立即执行状态机。
- 先改 `run`，再投递到 `app_core`。
- 先向 APP 发送消息，由 APP 消息入口执行。

P11 不能用一个“统一异步 stop”机械替换三类调用。P11.0 必须为每个调用点记录调用上下文、是否允许阻塞、返回语义和副作用顺序。

### 4.3 `rdx_uxfile_*` 当前控制面访问

当前 `rdx_record.c` 约 23 处 uxfile 调用属于录音数据面或紧耦合 legacy engine，P11 明确保留。需要收口的是：

- app 的 init/free/formatting query。
- DUT 和 device service 的 format 请求。
- record service 的 BLE cleanup 和 active file 时间修正。
- storage service 内部作为 adapter 的 uxfile 调用继续允许。

wifi service 的传输完成 buffer cleanup 与 `ReqFileInfo *` 状态机必须一起迁移，P11 不拆半套边界；该调用在 P11 固定为精确兼容例外并转 P12。

device service 中 sync/list/scan/format 聚合判断位于当前不可达的 eMMC auto-poweroff 历史路径，P11 不为这些命中设计 activity API，也不迁移该禁用代码。

`rdx_uxfile_*` 很可能同时属于静态库实现和兼容头边界。P11 只减少外围直接调用，不删除旧函数，不修改 `rdx_uxfile.h` 的既有声明。

### 4.4 当前 archive 初步证据

2026-07-26 在当前 Mac 使用系统 `nm -u librdxApp.a` 可读出以下与 P11 直接相关的静态库依赖：

- `rdx_record_get_status`
- `rdx_record_process`
- `rdx_record_mode_active_check`
- `rdx_record_clear_marks`、`rdx_record_get_marks`、`rdx_record_err_reboot_flag_write_into_vm`
- `rdx_app_get_record_mode`
- `rdx_app_get_wifi_info`
- `rdx_app_emmc_poweroff_check`、`rdx_app_emmc_poweroff_check_timer_stop`、`rdx_app_emmc_poweron`
- `rdx_uxfile_sd_format`、`rdx_uxfile_sd_format_status_check`、`rdx_uxfile_get_operateFile_info`、`rdx_uxfile_raw_read` 以及多项 uxfile buffer/file API

其中 archive 内 `rdx_uxfile.c.o` 也引用 `rdx_record_get_status`。当前输出未发现 `rdx_record_service_*` undefined symbol，因此 service 空壳目前没有静态库直接依赖证据，但在 P11.0 完成最终 map/全部调用者扫描前仍按旧源码接口保护。

该结果只证明符号依赖，不证明 getter 返回对象在静态库中只读，也不替代 P10 最终 CC map 和 JL 工具链证据。

## 5. 所有权模型

### 5.1 物理所有权与逻辑所有权分离

| 领域 | 物理状态/legacy owner | 业务控制面 owner | 允许的外部访问 |
|---|---|---|---|
| Record | `rdx_record.c::record_status` | `rdx_record_service` | 语义 command、只读 query、事件通知 |
| Record ABI | `rdx_record_get_status()` / `rdx_record_process()` | compatibility adapter | 仅静态库和精确 allowlist |
| Storage/file | `librdxApp.a` 中 uxfile/协议对象 | `rdx_storage_service` | format、活跃窄查询、cleanup、lifecycle API |
| WiFi runtime | `rdx_wifi_service` | `rdx_wifi_service` | 窄 query/command，不返回给新调用者可写指针 |
| Device lifecycle | JL/app 生命周期和多个 service | `rdx_device_service` 仅编排 | 调用各领域命令，不跨领域写内部字段 |

P11 不追求把物理状态搬到 service。静态库 ABI 要求旧地址和旧结构继续存在，因此 service ownership 的含义是“所有新业务决策必须通过 service 入口”，不是“移动内存对象”。

这是一种受 ABI 约束的“受控所有权”，不是语言层面的完全封装：静态库仍可能通过旧符号观察或操作 legacy 对象。P11 的可验证目标是阻止新增源码绕过，并保持所有旧 ABI 行为，而不是宣称已消除静态库内部访问。

### 5.2 单一真相源

禁止以下实现：

- 在 record service 再维护一个可写 `RecordStatus` 镜像。
- 命令先改 service snapshot，再异步同步到 `record_status`。
- event bus subscriber 各自维护权威录音状态。
- 用 cache 避免调用 legacy getter，却没有原子失效机制。

只读 snapshot 是瞬时观察值，不可回写，不可持有为权威状态，也不可跨异步边界后用于条件更新。

### 5.3 命令、查询和事件的边界

| 类型 | 用途 | 返回 | 是否走 event bus |
|---|---|---|---|
| Command | start/stop/switch/mode change/format/cleanup | 接受、拒绝或明确错误 | 否；必须调用 owner API |
| Query | active、scene、mode、storage formatting 等窄状态 | 当前只读结果 | 否；同步读取 |
| Event | record started/stopped、format done 等已完成事实 | 不作为命令成功依据 | 是；payload 必须自包含 |

event callback 禁止取得 owner 的可写裸指针。需要同步决定“是否允许 reset/关机/格式化”时，调用 query；需要改变状态时，调用 command。

### 5.4 并发与一致性模型

P11 不预设 `record_status` 的全部写入都发生在 `app_core`。P11.0 必须先产出 writer-context 表：

| 字段/字段组 | 写入函数 | 实际执行上下文 | 并发来源 | snapshot 一致性要求 | 保护策略 |
|---|---|---|---|---|---|
| `run/scene/formate` | 待 P11.0 刷新 | app message/task/timer 等 | 待确认 | 必须同一观察点 | 待上下文冻结后确定 |
| `mode/orig_mode/rerun` | 待 P11.0 刷新 | BLE/app_core 等 | 待确认 | 必须同一观察点 | 待上下文冻结后确定 |
| `is_switch/key_trigger/noshow` | 待 P11.0 刷新 | key/timer/app_core 等 | 待确认 | 单字段或同组一致 | 待上下文冻结后确定 |
| pause/time 字段 | 待 P11.0 刷新 | record/audio/timer 等 | 待确认 | P11 普通 caller 不读取 | 留在 owner 内部 |
| 静态库访问 | `librdxApp.a` 成员经 `rdx_record_get_status()` | archive 内部 | 读/写未知 | 不能仅靠源码推断 | member 级反汇编/map 反推；未确认前按可能访问处理 |

一致性规则：

1. 在 writer-context 表完成前，不得实现 snapshot，不得假设 getter 调用天然原子。
2. 优先复用现有 owner 串行上下文；只有确认存在跨上下文并发且 caller 确实需要多字段一致性时，才增加最短 critical section。
3. 不新增 mutex，不在临界区执行日志、协议 indicate、task post、文件操作或状态机处理。
4. 若需要 critical section，先给 OSAL 增加成对、不可阻塞的 enter/exit wrapper，并做嵌套和中断上下文契约测试；业务 public header 不暴露 JL primitive。
5. 窄 query 只读取一个语义事实；snapshot 用于确实需要同一观察点的多字段消费者，禁止为方便而让所有 caller 依赖大快照。
6. snapshot 是 best-before-now 的只读观察值；离开函数后状态可能变化，caller 不得用旧 snapshot 做条件写回。
7. archive undefined symbol 只能证明静态库调用了 getter，不能证明只读；P11.0 必须把调用 getter 的 archive member 加入 writer-context 证据，无法证明只读时不得宣称 writer 已全覆盖。

## 6. 目标接口设计

以下接口为推荐形态，P11.0 完成调用上下文表后可微调命名，但不可放宽 ABI 和所有权规则。

### 6.1 Record 只读视图

新增 `service/rdx_record_service_types.h` 存放不依赖 `rdx_record.h` 的 clean 语义类型，`rdx_record_service.h` 与 private domain header 均只依赖该 types header，避免 internal 层反向 include 完整 service API：

```c
typedef enum {
    RDX_RECORD_ACTIVITY_IDLE = 0,
    RDX_RECORD_ACTIVITY_ACTIVE,
    RDX_RECORD_ACTIVITY_PAUSED,
} rdx_record_activity_t;

typedef enum {
    RDX_RECORD_SCENE_CHAT = 0,
    RDX_RECORD_SCENE_CALL,
} rdx_record_scene_t;

typedef enum {
    RDX_RECORD_PATH_OFFLINE = 0,
    RDX_RECORD_PATH_ONLINE,
} rdx_record_path_t;

typedef struct {
    rdx_record_activity_t activity;
    rdx_record_scene_t scene;
    rdx_record_path_t path;
    bool switching;
    bool key_triggered;
    bool rerun_pending;
} rdx_record_snapshot_t;

bool rdx_record_service_is_running(void);          /* 既有签名，保留 */
bool rdx_record_service_can_auto_shutdown(void);   /* 既有签名，保留 */
bool rdx_record_service_is_offline_active(void);
rdx_err_t rdx_record_service_get_scene(rdx_record_scene_t *out);
rdx_err_t rdx_record_service_get_snapshot(rdx_record_snapshot_t *out);

/* 既有兼容入口：签名不得从 u8 改为 bool，内部转发到真实 query。 */
u8 rdx_record_service_is_active(void);
```

规则：

- public header 不 include `rdx_record.h`，不暴露 `RecordStatus`、JL task 或 OS 类型。
- 复用既有 `is_running()` 与 `can_auto_shutdown()`；当前空壳 `u8 rdx_record_service_is_active(void)` 必须保持原符号和返回类型并落地为兼容 wrapper，禁止用 `bool` 同名替换。
- 窄 query 是默认接口；只有一个 caller 同时需要多个字段且要求同一观察点时才使用 snapshot。
- snapshot 只包含外部决策真正需要的语义；不镜像全部 legacy 字段，也不作为新增字段的便利集合。
- legacy `START` 与 `RESUME` 统一为 `ACTIVE`，只有兼容 adapter 可读取精确 legacy `run` 用于协议 indicate。
- snapshot 按 5.4 节 writer-context 结论读取：优先复用 owner 串行上下文，只有证明存在并发撕裂风险时才使用最短 critical section；不得通过新增 mutex 改变原状态机调度。
- null 输出返回 `RDX_ERR_INVAL`；普通 query 不产生副作用。

### 6.2 Record 命令接口

以下 stop reason 同样定义在 `rdx_record_service_types.h`，供 service 与 private domain 共用；它是 P11 clean 类型，不改变任何 legacy enum 数值：

```c
typedef enum {
    RDX_RECORD_STOP_APP_REQUEST = 0,
    RDX_RECORD_STOP_BLE_DISCONNECT,
    RDX_RECORD_STOP_CHARGE_PREPARE,
    RDX_RECORD_STOP_DUT,
    RDX_RECORD_STOP_POWEROFF,
    RDX_RECORD_STOP_IDLE,
    RDX_RECORD_STOP_UPLOAD_FALLBACK,
} rdx_record_stop_reason_t;

rdx_err_t rdx_record_service_device_toggle(rdx_record_scene_t scene);
rdx_err_t rdx_record_service_stop_now(rdx_record_stop_reason_t reason);
rdx_err_t rdx_record_service_stop_post(rdx_record_stop_reason_t reason);
rdx_err_t rdx_record_service_switch_scene(rdx_record_scene_t original_scene);
rdx_err_t rdx_record_service_set_path(rdx_record_path_t path);
rdx_err_t rdx_record_service_mark_key_triggered(void);
```

命令契约：

- `_now` 只能用于 P11.0 上下文表确认“先执行原字段更新、再在当前上下文调用 legacy process”的调用点；它不得隐藏 task post 或 APP message。
- `_post` 必须按原调用点顺序先执行原有 pre-post 字段更新，再向冻结的 `app_core` 路径投递 legacy process 一次；queued callback 不得再次执行 `_now`，避免重复状态转换。
- `_post` 投递失败后是否保留已更新字段、是否回滚以及日志口径都按原 caller 冻结，不能统一改成事务式回滚。
- 历史路径经 APP message 执行时继续保留原 APP message；消息 handler 再按其原逻辑选择 `_now` 或 `_post`，禁止为了减少一层调用改变队列层级。
- `RDX_OK` 对 `_now` 表示已按旧同步路径处理或已处于目标状态；对 `_post` 表示成功入队。
- `RDX_ERR_BUSY` 表示现有业务规则拒绝；`RDX_ERR_INVAL` 表示参数非法；投递失败返回 `RDX_ERR_IO`。
- stop reason 只用于选择现有副作用和诊断，不得在 P11 引入新的产品策略。
- `device_toggle()` 不接收 trigger/source：现有 `rdx_app_device_record_handle(u8)` 同时被 APP message 与 DUT 调用，旧调用链不能可靠推导来源；来源仅由 caller-side golden trace 记录，不参与 command 策略。
- 禁止在命令内部查询或猜测“当前 task”后自动选择 now/post；每个 caller 在迁移表中固定唯一入口。
- start/toggle 和 switch 不是简单字段写入：使用保留现有 connected/offline、protocol payload、pool、timer 和 local process 分支的场景化 `device_toggle()` / `switch_scene()`，禁止抽象成对称的通用 `start_now()` / `switch_now()`。
- 既有 `void rdx_record_service_device_record_handle(u8)` 和 `void rdx_record_service_switch(u8)` 签名保留为兼容 wrapper，分别转发到新场景化命令并按旧 `void` 口径记录错误。
- 旧 `void` wrapper 继续保持 `void`，内部错误只记录日志；不得把 `rdx_err_t` 穿透给静态库。

基于提交 `128eb8d` 的初步映射如下，最终以 P11.0 实际调用上下文表为准：

| caller/path | 当前可见顺序 | 目标入口 | P11.0 必须确认 |
|---|---|---|---|
| charge prepare | 写 STOP -> 当前上下文 process | `stop_now(CHARGE_PREPARE)` | 实际调用 task、是否允许同步 process |
| DUT record stop | 写 STOP -> 当前上下文 process | `stop_now(DUT)` | DUT 消息执行上下文 |
| device soft poweroff | 写 STOP -> 当前上下文 process -> 后续下电 | `stop_now(POWEROFF)` | 文件收尾完成点与下电顺序 |
| app idle | 写 STOP -> 当前上下文 process -> file/WiFi/task cleanup | `stop_now(IDLE)` | idle 入口上下文与 cleanup 顺序 |
| `APP_MSG_RECORD_OFF` handler | 写 STOP -> post `app_core` process | `stop_post(APP_REQUEST)` | post 失败后字段是否保持 STOP |
| upload fallback、BLE 已连接 | 写 STOP -> post protocol trigger，不 post local process | `prepare_stop(UPLOAD_FALLBACK)` -> protocol adapter | payload/factor/pool/timer 顺序 |
| upload fallback、BLE 未连接 | 写 STOP -> post `app_core` process | `stop_post(UPLOAD_FALLBACK)` | post 失败后字段保持语义 |
| BLE disconnect/key/switch/recovery | 多条混合 direct/post/message 路径 | P11.0 后逐调用点固定 | rerun、noshow、key_trigger、indicate/timer 顺序 |

表中目标入口不是批量替换授权。任何 caller 的真实上下文或顺序与表不一致时，先更新设计和基线，再迁移代码。

#### 6.2.1 `device_toggle()` 决策表

以下行为以提交 `128eb8d` 的 `rdx_record_service_device_record_handle()` 为冻结起点；P11 只移动所有权，不统一分支：

| 条件 | owner 字段动作 | protocol/local 动作 | timer/pool | 失败语义 |
|---|---|---|---|---|
| scene 非 CHAT/CALL | 无 | 无 | 无 | 新 API 返回 `RDX_ERR_INVAL`；旧 wrapper 直接返回 |
| BLE 已连接且 OTA active | 无 | 无 | 无 | 新 API 返回 `RDX_ERR_BUSY`；旧 wrapper 保持静默返回 |
| BLE 已连接、当前 STOP | 不直接把 owner 改为 START | 构造 START legacy payload 并 post trigger indicate | 先成功分配 pool，再启动 upload timer | pool 满时不启动 timer；trigger post 失败释放 slot，但已启动 timer 的历史行为保持 |
| BLE 已连接、当前非 STOP、`orig_mode` 为 OFFLINE | 先写 owner STOP | post local process；再构造 STOP payload 并 post trigger indicate | 使用 pool | 任一 post 失败后的 owner/pool/timer 状态按基线保留 |
| BLE 已连接、当前非 STOP、非 OFFLINE | owner 不直接变更 | 用当前 format/scene/mode 构造 STOP payload并 post trigger indicate | 使用 pool | pool/post 失败不得新增 local stop |
| BLE 未连接、当前 STOP | 写 owner START/format/scene | post local process | 不使用 protocol pool | post 失败后的字段保持/回滚按基线冻结 |
| BLE 未连接、当前非 STOP | 写 owner STOP | post local process | 不使用 protocol pool | post 失败后的字段保持/回滚按基线冻结 |

特别约束：connected 分支中的 payload 是静态库 ABI 对象，不是 owner snapshot；不得用 `rdx_record_snapshot_t` 替换，也不得把 payload 写回 owner。

#### 6.2.2 `switch_scene()` 决策表

| 顺序 | 当前行为 | P11 规则 |
|---:|---|---|
| 1 | DUT 或 OTA active 时返回 | gate 与返回口径保持；新 API 可返回 `RDX_ERR_BUSY`，旧 wrapper 静默 |
| 2 | 如 indicate ops 有效，先上报当前 scene/run | 上报顺序不能移动到字段变更后 |
| 3 | restart switch keep timer | timer restart 时机保持 |
| 4 | 当前 STOP 时不再执行切换动作 | 不新增 scene 字段写入或 payload |
| 5 | 非 STOP 时先写 `noshow = 1` | 字段顺序保持 |
| 6 | BLE 未连接时写 STOP 并当前上下文执行 local process | 不改成 post；实际上下文由 P11.0 确认 |
| 7 | 写 `is_switch` 与 `switch_orig_scene` | 必须发生在 local process 分支之后、pool 分配之前 |
| 8 | 分配 pool 并构造 STOP payload | pool 满立即返回，不启动 switch keep timer |
| 9 | post trigger indicate | post 失败释放 slot；不得回滚 owner 切换字段 |
| 10 | post switch keep timer start | 保持即使 trigger post 失败仍继续该投递的历史顺序，除非 P11.0 证据证明当前代码不同 |

P11.0 必须把上述表转成可执行 golden trace。任何想“修正”现有失败语义的改动均属于独立行为修复，不得混入 ownership 迁移。

### 6.3 Record 私有 adapter

P11 必须物理拆分 domain adapter 与静态库协议 adapter，禁止只在 `rdx_record_service.c` 内用注释划一个“兼容区域”：

```text
internal/rdx_record_domain.h
internal/rdx_record_domain.c
compat/rdx_record_protocol_adapter.h
compat/rdx_record_protocol_adapter.c
```

职责固定为：

- `rdx_record_domain.*`：通过稳定 legacy owner 入口执行 snapshot copy、语义字段更新和 process 调度；header 只暴露 clean semantic type，不暴露 `RecordStatus`。
- `rdx_record_protocol_adapter.*`：唯一负责构造 `rdx_protocol_record_trigger_indicate()` 的 legacy `RecordStatus` payload，持有四槽 pool 与 busy 位图，并保证 callback 生命周期。
- `rdx_record_service.c`：只做业务决策和编排，文件中不得出现 `RecordStatus`、`rdx_record_get_status()` 或 `rdx_record_process()`。
- `rdx_record_get_status()`、`rdx_record_process()` 的旧定义继续留在 `rdx_record.c`，不得为了 adapter 分层移动、改名或隐藏。

`internal/rdx_record_domain.h` 的最小 clean 合约建议固定为：

```c
typedef struct {
    u8 run;
    u8 format;
    u8 scene;
    u8 mode;
    u8 original_mode;
} rdx_record_domain_state_t;

rdx_err_t rdx_record_domain_get_state(rdx_record_domain_state_t *out);
rdx_err_t rdx_record_domain_get_snapshot(rdx_record_snapshot_t *out);
rdx_err_t rdx_record_domain_prepare_stop(rdx_record_stop_reason_t reason);
rdx_err_t rdx_record_domain_stop_now(rdx_record_stop_reason_t reason);
rdx_err_t rdx_record_domain_stop_post(rdx_record_stop_reason_t reason);
rdx_err_t rdx_record_domain_toggle_post(rdx_record_scene_t scene);
rdx_err_t rdx_record_domain_set_path(rdx_record_path_t path);
rdx_err_t rdx_record_domain_mark_key_triggered(void);
rdx_err_t rdx_record_domain_prepare_switch(rdx_record_scene_t original_scene,
                                           bool ble_connected);
```

`rdx_record_domain_state_t` 是一次性只读值，只服务 service 决策和 legacy payload 构造；不得缓存、回写或作为第二真相源。字段虽然保持 legacy 数值，但不暴露结构布局和指针。

domain command 不得猜测当前 task：`prepare_stop()` 只做基线字段 transition、不执行或投递 process；`stop_now()` 为 prepare + 当前执行，`stop_post()` 为 prepare + 单次投递；`toggle_post()` 先按基线更新字段再只投递一次 process；`prepare_switch()` 仅按传入的 connected 事实执行决策表中的 owner 动作，不读取 BLE service 全局状态。

`compat/rdx_record_protocol_adapter.h` 使用 clean payload，不得声明 `RecordStatus *`：

```c
typedef enum {
    RDX_RECORD_TRIGGER_PAYLOAD_UPLOAD = 0,
    RDX_RECORD_TRIGGER_PAYLOAD_DEVICE,
    RDX_RECORD_TRIGGER_PAYLOAD_SWITCH,
} rdx_record_trigger_payload_kind_t;

typedef struct {
    rdx_record_trigger_payload_kind_t kind;
    u8 run;
    u8 format;
    u8 scene;
    u8 mode;
    u8 factor;
} rdx_record_trigger_payload_t;

rdx_err_t rdx_record_protocol_post_trigger(
    const rdx_record_trigger_payload_t *payload);
```

adapter 根据 `kind` 精确复现当前 pool slot 写法：

- DEVICE：像当前 device path 一样先清零完整 slot，再写 run/format/scene/mode。
- UPLOAD：不额外清零复用 slot，只覆写当前代码实际写入的 run/format/scene；不得顺带归零 mode 或其他字节。
- SWITCH：不额外清零复用 slot，只覆写 run/format/scene。
- `factor` 原样传给静态库 callback；提交 `128eb8d` 中 UPLOAD/DEVICE/SWITCH 的 callback arg2 均传 `NULL`，初步基线均为 `0`，P11.0 需用 trace 再确认；禁止用新的 command source enum推导。
- post 失败只按原路径释放 slot；是否已有 timer/owner 字段变化由 caller 决策表决定。

这两个私有目录不得加入业务通用 include path，不得被 app/charge/DUT/LED 直接 include。`RecordStatus` 只允许出现在：

- `rdx_record.c/.h` 兼容边界。
- `internal/rdx_record_domain.c` 的精确 owner adapter 实现。
- `compat/rdx_record_protocol_adapter.c` 的静态库 payload 实现。
- 冻结的兼容头（如 `rdx_app.h::rdx_tws_sync_record_t`）。
- P11 明确列出的 ABI 测试基线。

pool 大小、分配顺序、post 失败释放行为和 callback 生命周期不得在 P11 顺带优化。静态门禁按“具体 `.c` + 具体符号”放行，不识别同一文件中的注释区域。

### 6.4 Storage 控制面接口

```c
/* clean service header：复用既有签名，不引入 activity 位图。 */
u8 rdx_storage_is_formatting(void);
rdx_err_t rdx_storage_service_format_for_app(void);
rdx_err_t rdx_storage_service_runtime_init(void);
rdx_err_t rdx_storage_service_runtime_exit(void);
rdx_err_t rdx_storage_service_cleanup_ble_buffers(void);
rdx_err_t rdx_storage_service_adjust_active_record_time(int delta_seconds);
```

DUT/unbound 当前必须接收 legacy `u8` result callback。该过渡接口放入 `compat/rdx_storage_format_compat.h/.c`，不进入长期 clean service header：

```c
typedef void (*rdx_storage_legacy_format_cb_t)(u8 legacy_result);

rdx_err_t rdx_storage_format_compat_for_dut(
    rdx_storage_legacy_format_cb_t cb);
rdx_err_t rdx_storage_format_compat_for_unbind(
    rdx_storage_legacy_format_cb_t cb);
```

规则：

- P11 不新增 storage activity 位图。活跃 caller 使用 `rdx_storage_is_formatting()` 等已有窄查询；当前无活跃 caller 的 `rdx_storage_is_syncing()` 空壳保持旧签名，不借 P11 猜测或启用策略。
- `rdx_storage_service_format_for_app()` 内部固定使用现有 app format completion，不接受任意 callback。
- 既有 `void rdx_storage_service_format_handle(void)` 与 `void rdx_storage_service_format_cb(u8)` 保持签名，作为 APP 路径兼容 wrapper/固定 completion；不得因新增 clean 入口删除或改返回类型。
- DUT/unbound 兼容入口只薄转发 legacy 单参数 callback，不保存 `ctx`，不成为长期 clean public API；调用线程、调用次数和 result 数值保持原 uxfile 契约。
- device service 分别调用 record、storage、WiFi、OTA 窄 query 后执行既有策略；storage service 不反向调用 device service，也不提供全局 busy 判定。
- P11 不新增 format 排队、取消、重入拦截或“同一时间只允许一个请求”的策略；底层如何处理重入保持 P10 行为。发现底层重入缺陷时另立行为修复提交。
- `adjust_active_record_time()` 由 storage owner 操作 `uxfile_data_t`，record service 不再取得该裸指针。
- `rdx_record.c` 的实时 raw write/DAT 路径保留在 allowlist，不通过 service 增加热路径跳转。
- WiFi TX completion 中的 `ReqFileInfo *` 与 buffer cleanup 在 P11 保持现状并进入精确 allowlist，P12 再随 file-transfer ownership 一并迁移。
- 既有 `rdx_storage_service_cleanup_ble_buffers()` 同时清理 protocol 与 uxfile 状态，P11 仅把它视为 file-transfer compatibility facade，不宣称其最终 owner 是 Storage；旧符号保留，P12 随 file-transfer ownership 重新归属。

#### 6.4.1 BLE cleanup compatibility profiles

当前立即断连 subscriber 与 delayed disconnect 的清理集合不同，P11 必须在 `compat/rdx_file_transfer_cleanup_compat.h/.c` 中保留两个 profile：

```c
rdx_err_t rdx_file_transfer_compat_cleanup_record_disconnect(void);
rdx_err_t rdx_file_transfer_compat_cleanup_ble_delayed(void);
```

精确顺序：

| profile | 前置 gate | 清理顺序 |
|---|---|---|
| `cleanup_record_disconnect` | record BLE-disconnected event 已成立 | upload info clean -> record file buffer free -> file-sync busy timer stop -> send buffer reinit |
| `cleanup_ble_delayed` | caller 先检查 WiFi transfer inactive | upload info clean -> record file buffer free -> **DAT list buffer free** -> file-sync busy timer stop -> send buffer reinit |

规则：

- record service 只能调用 immediate profile，禁止复用 full/delayed profile，否则会新增 DAT list buffer free 副作用。
- `rdx_ble_server_disconnected_delay_handle()` 保留 WiFi-active skip gate，再调用 delayed profile。
- 既有 `rdx_storage_service_cleanup_ble_buffers()` 符号保持，内部只作为 delayed profile 的兼容 wrapper；不得改成 immediate profile，也不得删除。
- 两个 profile 暂存 compat 层，不宣称 Storage 是最终 owner；P12 建立 file-transfer ownership 后再迁移。
- Host golden trace 和 CC 断连测试必须分别覆盖两个 profile，不能只验证最终“未崩溃”。

#### 6.4.2 APP format ACK 决策表

APP format 的协议顺序必须显式冻结，不能因 clean API 返回 `rdx_err_t` 而改成“底层成功后再 ACK”：

| 条件/顺序 | P10 当前行为 | P11 规则 |
|---|---|---|
| indicate ops 为空 | 直接返回 | 保持，不发 ACK、不发起 format |
| OTA/record/file-send busy | `sd_format_ack_indicate(1)` 后返回 | gate 和失败 ACK 顺序保持 |
| 非 busy | **先** `sd_format_ack_indicate(0)` | 成功 ACK 必须仍发生在 format 请求之前 |
| ACK 后 | 调用 format handle | 旧 handler 可忽略新 clean API 的 initiation error，保持 P10 协议口径；不得补发第二次 ACK |
| format callback 成功 | publish `RDX_EVENT_STORAGE_FORMAT_DONE` | callback 线程、次数和 event 顺序保持 |
| format callback 失败 | 不 publish done event | 不借 P11 新增失败 ACK/event |

如果产品希望把底层 initiation/callback 失败反馈给 APP，必须另立协议行为变更，不得混入 ownership 迁移。

### 6.5 Device 编排接口

device service 的职责是固定顺序地调用领域 API，例如：

```text
检查 OTA
  -> 查询 record active
  -> 查询 WiFi/file transfer busy
  -> 请求 record stop（需要停止的流程）
  -> 请求 storage format/cleanup
  -> BLE disconnect / WiFi off
  -> RTC store
  -> reset / poweroff
```

P11 不合并 factory reset、unbound、soft poweroff、charge prepare 和 idle 流程。每条流程保留自己的历史顺序，只替换跨领域裸访问。

推荐顺序：

1. LED 的 `is_active()` 判断。
2. charge/OLED 只读判断。
3. storage/device 的 busy gate。
4. DUT 进入条件和状态打印。
5. app 按键映射、单击/三击等只读判断。
6. OTA 中确认无用途的死读取独立删除。

规则：

- 每类调用点独立提交。
- 不在本阶段迁移直接写字段或 stop/process。
- query 失败必须保持旧的保守/默认策略，并在契约表记录。
- 日志可改用 semantic 名称，但不得改变协议输出。

### 7.4 P11.3：外部 stop/start/switch 命令迁移

风险从低到高：

1. DUT start/stop。
2. charge prepare stop。
3. device soft poweroff 与 app idle stop。
4. APP_MSG_RECORD_OFF。
5. key-trigger 与 record switch。
6. BLE disconnect 和异常恢复。

每个路径必须逐项比对：

- 字段写入顺序。
- `rdx_record_process()` 当前执行或 `app_core` 投递方式。
- protocol trigger/state indicate 的先后。
- motor/LED、WiFi、storage cleanup 的先后。
- timer start/stop/re-run 的先后。
- 已 STOP 时的幂等行为。
- 投递失败时日志和状态是否与旧逻辑一致。

迁移表必须给每个 caller 固定 `_now`、`_post` 或“保留 APP message”之一。禁止在 command 内自动判断 task，禁止把所有 stop 原因合并为同一副作用序列。通用 command 可以复用状态转换，但 reason-specific orchestration 必须保留。

### 7.5 P11.4：Record service 内部所有权收口

实施：

1. 新增 `internal/rdx_record_domain.*` 与 `compat/rdx_record_protocol_adapter.*`，record service 只通过其 clean API 访问 owner 和协议 payload。
2. 将 `g_rp_pool` 与 busy 位图物理迁入 protocol adapter；其仅作为静态库 trigger payload 兼容池，不是状态真相源。

4. 将空壳 `rdx_record_service_start/stop/get_state/is_active` 删除或落地；若已被外部符号引用则保留兼容 wrapper，禁止继续返回固定假值。
5. 对新 service API 统一 `rdx_err_t`，旧 wrapper 显式映射旧口径。

验收：

- `service/rdx_record_service.c` 中零 `RecordStatus`、零 `rdx_record_get_status()`、零 `rdx_record_process()`；不允许文件内兼容区域。

### 7.6 P11.5：Storage 控制面收口

实施顺序：

4. P11 实际触及的 app runtime init/exit 薄封装；未触及调用点保留精确兼容例外并转 P12。

边界规则：

## 8. 静态边界门禁

在 `tools/check_rdx_boundaries.ps1` 增加 P11 规则：

7. event subscriber 不得取得 owner 裸指针后修改状态。
8. `rdx_record_get_status()` 和 `rdx_record_process()` 定义必须继续为外部可见且签名与 P8 一致。
9. `rdx_record_service.c` 必须对 `RecordStatus`、`rdx_record_get_status()` 和 `rdx_record_process()` 零命中；禁止用同文件注释区域做 allowlist。
10. WiFi TX completion 的 P12 转交例外必须精确到既有函数和 `rdx_uxfile_*` 符号，禁止允许整个 `rdx_wifi_service.c`。
11. 禁止新增 storage activity/system busy 位图；活跃路径只能使用 owner 窄查询。
12. `rdx_record_service_is_active()` 必须继续声明/定义为 `u8 ... (void)`；禁止同名 bool 替换。
13. `rdx_device_service_emmc_poweroff_check()` 的第一个可执行语句必须仍为 `return`，不可达 timer/activity 路径不得接入新 query。
14. 禁止新增保存任意 `cb + ctx` 的通用 format API；APP clean API 不接收 callback，DUT/unbound legacy callback 只允许出现在 compat header/实现。
15. `rdx_record_mode_active_check()`、`rdx_app_get_record_mode()`、`rdx_app_get_wifi_info()` 和三个 `rdx_app_emmc_*` 旧 wrapper 必须继续按固定签名导出；不得改成 service 新符号要求静态库重链接适配。
16. immediate cleanup profile 不得调用 `rdx_uxfile_datFileInfo_sendBuf_free()`；delayed profile 必须保留该调用及其相对顺序。
17. `rdx_storage_service_cleanup_ble_buffers()` 作为过渡兼容符号保留，且只能转发 delayed cleanup profile；不得以此扩大 storage 对其他 protocol 状态的访问。
18. `rdx_record_protocol_adapter.h` 与 `rdx_record_domain.h` 不得出现 `RecordStatus`；protocol adapter 必须按 payload kind 保持 DEVICE 清零、UPLOAD/SWITCH 不额外清零的差异。
19. 禁止通过注释、宏拼接、函数指针强转或扩大目录 allowlist 绕过门禁。

allowlist 必须按“文件 + 符号 + 用途”记录，禁止只允许整个目录。

### 9.2 Golden call trace 规范

P11.0 先在 `tests/host/rdx_p11_trace_schema.h`、`rdx_p11_trace_spy.*` 与 `test_rdx_p11_golden_trace.c` 固定 Host/诊断 trace schema、比较器和负向自测；这仅是 executable scaffold。只有 caller spy 接线后实际捕获 P10 trace、解析 execution context 并通过 `rdx_p11_trace_evidence.psd1` 门禁，才可称为可执行 golden trace。后续 Host spy 必须可编译关闭，生产候选默认关闭，且不引入动态分配或运行时字符串表。每条记录固定为：

```c
typedef struct {
    u32 sequence_id;
    u8  execution_context;
    u8  operation;
    s16 result;
    u32 arg0;
    u32 arg1;
} rdx_p11_trace_entry_t;
```

最小 operation 集合：

```text
FIELD_TRANSITION
APP_MESSAGE
TASK_POST
LOCAL_PROCESS
PROTOCOL_INDICATE
POOL_ALLOC / POOL_RELEASE
TIMER_START / TIMER_STOP / TIMER_RESTART
STORAGE_CLEANUP
FORMAT_CALLBACK
```

比较规则：

- 比较 operation 顺序、execution context、关键参数和 result；忽略时间戳、绝对地址、普通日志文本和无关计数器。
- Host spy 每次截获 task post、timer、protocol indicate、pool 和 cleanup 操作时，同步读取一次 owner domain state 并附着到 trace 辅助表；借此观察 P10 直接字段写入在外部可见边界前后的结果，无需修改 P10 字段赋值语句。
- P10 基线 trace 与 P11 candidate 使用同一 Host spy schema；P10 无法插桩的 CC 路径以现有串口日志、协议抓包和 callback 结果建立人工顺序表，不重编译已归档最终固件伪造基线。
- trace hook 只允许在 Host/诊断构建启用；最终 CC 固件用协议抓包、串口关键点和目标板行为复核，不能用不同 trace 固件代替最终固件。
- 每个 P11.3/P11.4 提交至少保存对应 caller 的迁移前后 trace diff；任何顺序变化都需独立行为授权。

| APP 录音 | APP start/pause/resume/stop | 命令响应、run 状态和文件完整性一致 |
| BLE 断连 | 在线录音中断开 | rerun/offline/stop；immediate cleanup 不释放 DAT list buffer |
| BLE 延迟清理 | WiFi inactive/active 两种条件等待 delayed handler | inactive 执行含 DAT list free 的 full profile；active 保持 skip |
| BLE 重连 | 断连后重连并同步状态 | state indicate 只发送预期次数 |
| charge prepare | 录音中插入充电 | stop、WiFi、RTC 顺序不变 |
| DUT | DUT 录音 start/stop；录音中请求进入 DUT | 允许/拒绝规则与 P10 一致 |
| soft poweroff | 录音中请求关机 | 文件收尾、task free、外设下电顺序不变 |
| idle | 录音中进入 idle | stop 与文件清理完整，无悬空 task |
| 异常恢复 | 设置 reboot flag 后启动 | 原 scene 恢复，flag 清零时机不变 |
| format | APP/DUT/unbound 三类 format | APP success ACK 先于请求；callback、event、reset 顺序不变 |
| time sync | 录音中校时 | active file start time 修正与 P10 一致 |
| eMMC 禁用策略 | 调用现有 poweroff check 入口 | 继续立即返回，不创建 activity timer、不改变电源状态 |

### 9.5 核心冒烟与 P10 防回归

- BLE 广播、配对、绑定、连接、断开和重连。
- BLE 录音上传不少于 30 秒。
- WiFi 在线录音不少于 30 秒。
- 文件列表、删除、同步和格式化。
- 恢复出厂、解绑和重新配对。
- 软关机和恢复、自动关机、RTC restore、DUT。
- 抽样复测绑定状态、MIC gain、BLE 名称/MAC 持久化，证明 P11 未破坏 P10 边界。

## 11. 风险与控制

| 风险 | 表现 | 控制 |
|---|---|---|
| 静态库持有旧 status 指针 | 换对象后读取悬空或状态不同步 | 保持原对象、地址和生命周期；只收口源码访问 |
| 静态库 getter 访问性质未知 | 源码 writer 表漏掉 archive 内写访问 | member 级反汇编/map 证据；未知项按可能访问处理 |
| 静态库 wrapper 清单遗漏 | mode/app getter/eMMC wrapper 被重命名或改签名 | 当前 nm 已知符号显式冻结 + P11.0 全量 undefined/map 检查 |
| 新 API 撞旧 service 符号 | `u8` 被同名 `bool` 替换，源码/调用约定漂移 | P11.0 冻结全部旧 service 签名；旧符号只做兼容 wrapper |
| snapshot 成为第二真相源 | 异步后按陈旧状态写回 | snapshot 只读、不可回写、不可作为 CAS 输入 |
| snapshot 并发撕裂 | `run/scene/mode` 来自不同状态瞬间 | P11.0 writer-context；优先 owner 串行，必要时最短 critical section |
| stop 时序被统一异步化 | 文件未收尾、重复 indicate、关机竞态 | 冻结调用上下文；now/post 显式分离 |
| start/switch 被过度通用化 | connected/offline、pool/timer/payload 分支丢失 | 场景化 command + 决策表 + golden trace |
| command source 被猜测 | 同一旧 wrapper 同时来自 APP/DUT，策略或日志错误 | `device_toggle()` 不接收 source；caller trace 单独记录 |
| event bus 被当 command bus | 发布成功却无人处理或处理过晚 | command/query 直达 owner；event 只通知已发生事实 |
| protocol payload 改型 | 静态库按旧布局解析错误 | legacy payload 与 pool 精确保留；ABI 测试 |
| pool 迁移时统一清零 | UPLOAD/SWITCH slot 历史残留字节行为变化 | protocol payload kind 决定 DEVICE 清零、其他路径只覆写原字段 |
| 同文件兼容区域扩大 | service 主体继续取得裸状态 | domain/protocol adapter 物理拆文件；service 文件零命中 |
| storage facade 吞并数据面 | 音频热路径增加延迟或栈深 | `rdx_record.c` raw write 精确 allowlist |
| storage 吞并全局 busy | WiFi/OTA 策略归属混乱 | P11 不建 activity 位图；device 使用各 owner 窄查询 |
| format callback 改线程/顺序 | ACK/reset 时机变化 | 调用上下文表 + CC 三类 format 专项 |
| 通用 format callback 生命周期 | 保存悬空 ctx、重入规则变化 | 场景化 thin wrapper；无 ctx、不排队、不新增重入策略 |
| 两类 BLE cleanup 被合并 | immediate 路径提前释放 DAT list buffer | immediate/delayed compat profile 分离并做顺序 trace |
| clean format 返回值改变 ACK | APP 成功 ACK 从请求前移动到请求后 | 显式 ACK-before-format 决策表；旧 handler 不补发 ACK |
| 误启用 eMMC 历史策略 | 新 activity query 让不可达 timer 开始下电 | 保持入口立即返回；P11 不迁移不可达 activity 代码 |
| device service 变成全局状态中心 | 新一轮中心化与反向依赖 | 只编排，各领域状态留在 owner |
| query 失败默认不一致 | reset/关机在未知状态下继续 | 每个 caller 冻结保守策略；失败记录诊断 |
| 门禁误删旧 ABI | 源码零调用后删除旧符号 | ABI allowlist 明确“必须存在但禁止新调用” |
| Flash/RAM 增长 | snapshot/pool/adapter 重复存储 | 无动态分配；不复制权威状态；最终 ≤ 2% |

## 12. P11 完成定义

P11 完成必须同时满足：

- [ ] P10 最终 CC 验证与归档已完成，P11 基线可追溯。
- [ ] `librdxApp.a` Git blob 和固定 SHA256 全程未变化。
- [ ] 固定 P8 ABI baseline 未更新为 P10/P11 浮动提交。
- [ ] `rdx_protocol.h`、`RecordStatus`、`rdx_tws_sync_record_t`、`ReqFileInfo`、协议回调布局保持不变。
- [ ] `rdx_record_get_status()` 继续导出并返回原稳定对象地址。
- [ ] `rdx_record_process()` 和 P11 触及的 uxfile/protocol 旧符号签名、可见性不变。
- [ ] 静态库 record trigger payload 的布局、生命周期、pool 行为不变。
- [ ] P11.0 已先扩展 ABI 门禁，覆盖 `rdx_tws_sync_record_t`、旧函数定义可见性、稳定 status 身份和触及符号清单。
- [ ] 调用 `rdx_record_get_status()` 的 archive member 已按 read/write/unknown 归档；unknown 没有被当作“已证明只读”。
- [ ] `rdx_record_mode_active_check()`、`rdx_app_get_record_mode()`、`rdx_app_get_wifi_info()` 和三个 eMMC wrapper 已按当前 nm 证据加入固定 ABI 检查。
- [ ] record service public header 不暴露 legacy/JL 私有类型。
- [ ] 既有 service public symbol 签名保持不变，尤其 `u8 rdx_record_service_is_active(void)` 未被同名 bool 接口替换。
- [ ] record 单一真相源仍为 `rdx_record.c::record_status`，没有可写镜像。
- [ ] writer-context 表覆盖 snapshot 所读字段，所选串行/critical 策略已通过并发契约测试。
- [ ] app、charge、DUT、LED、OTA、device/storage service 不取得可写 `RecordStatus *`。
- [ ] 普通业务代码不直接调用或投递 `rdx_record_process()`。
- [ ] 录音 start/stop/switch/mode 更新均通过语义 command；每个 caller 固定 now/post/message 路径，command 内不猜测当前 task。
- [ ] upload fallback 固定使用 `RDX_RECORD_STOP_UPLOAD_FALLBACK`：connected 为 `prepare_stop + protocol trigger`，disconnected 为 `stop_post`，不存在“实现时再决定”的 caller。
- [ ] `device_toggle()` 不接收或猜测 APP/KEY/DUT/RECOVERY source；来源只存在于 caller trace。
- [ ] `device_toggle()` 与 `switch_scene()` 的 connected/offline、pool、timer、payload、post 失败分支均与决策表和 golden trace 一致。
- [ ] 录音只读判断默认使用窄 query，只有记录了多字段一致性需求的 caller 使用 snapshot。
- [ ] event bus 只发布状态事实，不承载同步命令或 query。
- [ ] `internal/rdx_record_domain.*` 与 `compat/rdx_record_protocol_adapter.*` 已物理拆分；`rdx_record_service.c` 对 legacy record 类型/getter/process 零命中。
- [ ] domain/protocol private header 使用 clean types，零 `RecordStatus`；protocol adapter 按 payload kind 保持 DEVICE 清零和 UPLOAD/SWITCH 非清零写法。
- [ ] record service 不直接访问 `rdx_uxfile_*` 或 `uxfile_data_t *`。
- [ ] P11 范围内的 storage 控制面调用集中在 storage service/private adapter；WiFi TX completion 等 P12 转交项具有精确 allowlist。
- [ ] P11 未新增 storage activity/system busy 位图；活跃 caller 使用 `is_formatting()` 等窄查询。
- [ ] APP 使用无 callback 的 clean format 入口，DUT/unbound 使用 compat thin wrapper；没有通用 `cb + ctx`、排队或新重入策略。
- [ ] `rdx_storage_service_cleanup_ble_buffers()` 明确归档为过渡 file-transfer compatibility facade，没有被宣称为最终 Storage ownership。
- [ ] immediate 与 delayed BLE cleanup profile 已分离；只有 delayed profile 释放 DAT list buffer，旧 storage cleanup wrapper 只转发 delayed profile。
- [ ] APP format 保持 success ACK-before-request、失败 callback 不新增 ACK/event 的协议顺序。
- [ ] `rdx_device_service_emmc_poweroff_check()` 继续立即返回，没有启用不可达 activity timer 或新增硬件行为。
- [ ] `rdx_record.c` 数据面 uxfile allowlist 精确且没有扩大。
- [ ] device service 只编排，不直接写 record/storage/WiFi owner 状态。
- [ ] 旧 wrapper 返回值、线程上下文、timer、protocol indicate 和副作用顺序保持不变。
- [ ] P11 boundary、query/command/storage host tests、ABI、配置矩阵全部通过。
- [ ] P11.3/P11.4 各 caller 的 golden trace schema、spy 边界 owner state、P10 基线、P11 diff 和差异结论已归档。
- [ ] EP、shadow、最终 CC 按顺序 clean build 通过。
- [ ] 最终 CC firmware、map、SHA256、构建日志和 size 增量已归档。
- [ ] P11 CC 专项、核心冒烟和 P10 持久化抽样回归通过。
- [ ] P11 最终 RDX Flash/RAM 净增长不超过 P10 最终 CC 基线 `2%`。

以下情况不得关闭 P11：

- 把 `RecordStatus *` 改成 `const RecordStatus *` 并宣称 ABI 未破坏。
- 删除源码零调用但静态库可能依赖的旧 symbol。
- 将既有 `u8 rdx_record_service_is_active(void)` 改成同名 bool 函数。
- 将 `record_status` 搬到 service，或让 service 与 record.c 各维护一份状态。
- 用 event bus 替代需要同步结果的 stop/format/reset 命令。
- 通过统一异步投递改变原调用线程或副作用顺序。
- 在 command 内检测当前 task 后自动选择 now/post。
- 给 `device_toggle()` 新增无法从旧 wrapper 可靠推导的 source/trigger 策略参数。
- 让 upload fallback 保持“reason-specific 或 adapter 二选一”的未闭合状态。
- 在 writer-context 未完成前实现 snapshot，或用 mutex 包住状态机/日志/文件操作。
- 在无法确认 archive getter 调用性质时，直接宣称静态库只读 `RecordStatus`。
- 为消除 grep 命中把 `RecordStatus` 强转成 `void *`。
- 把整个 `service/` 或 `rdx_record.c` 加入模糊 allowlist。
- 只在 `rdx_record_service.c` 内划兼容代码区域，而不物理拆分 domain/protocol adapter。
- 把 start/switch 简化成对称字段 setter，丢失 connected/offline、pool、timer 或 payload 分支。
- 在迁移 pool 时统一清零所有 slot，改变 UPLOAD/SWITCH 只覆写部分字段的基线。
- 把录音 raw write 热路径迁入通用 service 后只凭编译通过验收。
- 新增 storage activity 位图，或将 WiFi transfer、protocol send、OTA 状态塞进全局 system busy。
- 迁移、接线或板测当前入口立即返回的 eMMC auto-poweroff activity 路径，并把它记作 P11 功能完成。
- 引入保存任意 callback context、排队或改变重入语义的通用 format API。
- 用 delayed/full BLE cleanup 替换 immediate record-disconnect cleanup，或反向删除 delayed profile 的 DAT list free。
- 因 clean format API 返回失败而移动 APP success ACK、补发第二次 ACK 或新增失败 event。
- 更新 ABI baseline 以接受已经改变的 header/结构/符号。
- 只跑 Host mock，没有最终 CC 目标板录音、断连、format 和关机回归。

## 13. 归档与回滚

P11 完成时新增：

```text
docs/verification/<YYYY-MM-DD>-rdx-p11-ownership-validation.md
```

归档至少包含：

1. P10 基线与 P11 起始/最终 commit、工作区状态。
2. 静态库 blob、SHA256、固定 ABI baseline、undefined symbols、getter archive member read/write/unknown 分类和触及符号表。
3. `RecordStatus` 稳定身份、`rdx_tws_sync_record_t` 嵌套布局、旧函数定义可见性和 protocol payload 兼容证明。
4. writer-context、command-context、start/switch decision、trigger factor、两个 cleanup profile、format-context 表与迁移前后映射。
5. P11 静态门禁、Host、配置矩阵日志。
6. EP、shadow、最终 CC clean build 与产物 hash。
7. Flash/RAM symbol/section 对比。
8. Host golden trace schema、各 caller 的 P10/P11 trace diff、CC 状态所有权专项、核心冒烟和 P10 抽样回归结果。
9. EP/shadow 未做硬件功能验证声明。
10. 已知限制、精确 allowlist 和后续 P12 入口。
11. eMMC auto-poweroff 入口保持禁用、未做功能验证的声明。

回滚按领域提交执行：

- query 映射错误：回滚对应只读迁移，不触碰旧 ABI。
- 某 stop 路径时序异常：只回滚该 reason/caller 的 command 提交。
- protocol payload 异常：整体回滚 record compat adapter 提交，保留已验证查询面。
- format callback 异常：回滚对应 storage format 提交，不回滚 record ownership。
- 最终目标板失败：回到 P10 最终 CC 固件对照；不得修改静态库、清空用户数据或改 ABI baseline 规避。

## 14. P11 后续方向

P11 完成后，P12 可在新的稳定边界上选择一个独立方向：

- 收口 `RdxWifiInfo *` 与 `ReqFileInfo *` 的剩余裸状态访问，建立 WiFi/file-transfer ownership。
- 迁移 P11 精确保留的 WiFi TX completion uxfile cleanup 和未触及 storage runtime 例外。
- 清理 app/device 生命周期中剩余的 task free、power 和 JL SDK 直连。
- 对 record/storage service 做可执行 host service init/exit 测试扩展。

P12 不得反向修改 P11 冻结的静态库兼容边界；任何旧 ABI 清理只能在有新版静态库及明确版本化迁移方案后另立项目。
