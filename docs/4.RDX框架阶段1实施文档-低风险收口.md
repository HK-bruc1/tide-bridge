# RDX 框架阶段 1 实施文档：低风险收口（边界集中化）

> 版本：v1.2
> 对应大纲：`docs/3.RDX框架JL平台复用性优化大纲.md` 阶段 1
> 前提约束：
> 1. **`librdxApp.a` 二进制不修改**，现有静态库头文件作为兼容边界处理。
> 2. SDK 版本不变，只做代码组织重构。
> 3. 阶段 1 只迁移低风险、高集中收益的变化点，不全量清理业务 `.c` 中的旧调用。

---

## 1. 阶段目标

在不改变 RDX 协议行为和产品功能的前提下，把当前散落在业务 `.c`、公共 `.h` 和第三方库头文件中的 **板级常量、JL OS 原语、存储访问** 集中收口到明确位置：

- 板级常量 → `board/t2616_cc/rdx_board_config.c`
- JL OS API → `port/jl/rdx_jl_osal.c`（阶段 1 主要落地接口定义和 mutex/timer/time 最小实现）
- syscfg/VM 访问 → `port/jl/rdx_jl_storage.c`（阶段 1 先提供 wrapper，不要求业务 `.c` 全量切换）
- 日志入口 → `rdx_log.h`
- 构建变量 → `RDX_BOARD` / `RDX_CHIP_FAMILY`
- 非法组合 → 编译期 `_Static_assert` 拦截

阶段 1 的边界：**新增代码必须走新抽象；旧代码不要求一次性全改**，避免把阶段 1 变成高风险全量重构。

---

## 2. 设计模式落地

| 设计模式 | 在阶段 1 中的落地形式 |
|---|---|
| ③ Wrapper 二次封装 | `rdx_jl_osal_*`、`rdx_jl_storage_*`、`rdx_jl_gpio_*`、`rdx_jl_spi_*` 等统一命名空间。 |
| ⑤ 轻量 OSAL | `rdx_mutex_t`、`rdx_sem_t` 基于 JL OS 类型包装；封装 JL OS 原语，业务公共头不暴露 `OS_MUTEX`/`OS_SEM`。 |
| ⑥ Board Config / HAL 分层子集 | `rdx_board_config_t` + `rdx_board_get_config()` 集中所有板级引脚和参数。 |
| ① 条件编译 + `_Static_assert` | 编译期校验 APP/DEVICE/BOARD/CHIP 组合合法性。 |

---

## 3. 目录结构变更

阶段 1 只新增文件，不删除旧文件。建议最终结构：

```text
SDK/apps/common/third_party_profile/rdx_protocol/
├── board/
│   └── t2616_cc/
│       ├── rdx_board_config.h      # board config 结构体、当前板型宏
│       └── rdx_board_config.c      # 当前板型的 rdx_board_get_config 实现
├── port/
│   └── jl/
│       ├── rdx_jl_osal.h           # JL OS 原语 wrapper 接口
│       ├── rdx_jl_osal.c           # JL OS 原语 wrapper 实现
│       ├── rdx_jl_storage.h        # syscfg/VM wrapper 接口
│       ├── rdx_jl_storage.c        # syscfg/VM wrapper 实现
│       ├── rdx_jl_gpio.h           # GPIO/power 引脚 wrapper（薄层）
│       ├── rdx_jl_spi.h            # SPI transport wrapper 接口
│       └── rdx_jl_rtc.h            # RTC wrapper 接口（阶段 1 只定义，最小实现）
├── rdx_log.h                       # 统一日志宏入口
├── rdx_err.h                       # 统一错误码枚举（阶段 1 先定义，逐步替换）
├── rdx_app_config.h                # 改为引入 board config 和 product config
├── rdx_app.c/h                     # 逐步用新 wrapper / board config 替换旧宏
├── rdx_spi.c/h                     # 参数化 SPI 引脚、芯片类型
└── ...（其他业务文件不变）
```

阶段 1 不要求把所有旧引用一次性迁完，但必须做到：

1. 新增代码全部使用新抽象。
2. 被迁移的旧宏/函数保留为 `deprecated` 形式，保证现有代码仍能编译；阶段 2 再彻底删除。具体机制见 4.6.4 节。
3. 阶段 1 优先迁移以下高风险集中点：`rdx_spi.c` 引脚/芯片类型、`rdx_app.c` 启动诊断中的板级引脚、`rdx_app_config.h` 的组合校验。业务 `.c` 中的 `syscfg_*`、`os_*` 全量清理放到阶段 2/4。
4. 每个被迁移的旧宏位置记录在《阶段 1 迁移映射表》中，用于阶段 2 彻底删除。

## 4. 详细实施步骤

### 4.1 建立 `rdx_err.h`（统一错误码）

阶段 1 先定义，不强制全量替换。目标是把后续新增接口从 `-1` 迁移到具体错误码。

```c
#ifndef __RDX_ERR_H__
#define __RDX_ERR_H__

typedef enum {
    RDX_OK          = 0,
    RDX_ERR_INVAL   = -22,   /* -EINVAL */
    RDX_ERR_TIMEOUT = -110,  /* -ETIMEDOUT */
    RDX_ERR_NOMEM   = -12,   /* -ENOMEM */
    RDX_ERR_NOTSUP  = -95,   /* -ENOTSUP */
    RDX_ERR_IO      = -5,    /* -EIO */
    RDX_ERR_NOENT   = -2,    /* -ENOENT */
    RDX_ERR_BUSY    = -16,   /* -EBUSY */
    RDX_ERR_AGAIN   = -11,   /* -EAGAIN */
} rdx_err_t;

/* 兼容旧代码的泛型失败判断，阶段 4 再逐步移除 */
#define RDX_IS_ERR(x)   ((x) < 0)

#endif
```

### 4.2 建立 `rdx_log.h`（统一日志入口）

阶段 1 不替换所有现有 `printf/y_printf/log_info`，但新增诊断代码必须使用 `RDX_LOG_*`。阶段 4 再批量替换旧调用。

```c
#ifndef __RDX_LOG_H__
#define __RDX_LOG_H__

#include "app_config.h"  /* 保留现有 JL 日志宏兼容 */

/*
 * 当前 SDK 的日志宏定义在 debug.h：
 *   log_error / log_warn / log_info / log_debug
 * 阶段 1 的 RDX_LOG_* 直接映射到这些宏。
 */

#define RDX_LOG_TAG "RDX"

#define RDX_LOG_LEVEL_NONE  0
#define RDX_LOG_LEVEL_ERR   1
#define RDX_LOG_LEVEL_WARN  2
#define RDX_LOG_LEVEL_INFO  3
#define RDX_LOG_LEVEL_DBG   4

#ifndef RDX_LOG_LEVEL
#define RDX_LOG_LEVEL RDX_LOG_LEVEL_INFO
#endif

#if (RDX_LOG_LEVEL >= RDX_LOG_LEVEL_ERR)
#define RDX_LOGE(fmt, ...)  log_error("[RDX_E] " fmt "\r", ##__VA_ARGS__)
#else
#define RDX_LOGE(fmt, ...)  ((void)0)
#endif

#if (RDX_LOG_LEVEL >= RDX_LOG_LEVEL_WARN)
#define RDX_LOGW(fmt, ...)  log_warn("[RDX_W] " fmt "\r", ##__VA_ARGS__)
#else
#define RDX_LOGW(fmt, ...)  ((void)0)
#endif

#if (RDX_LOG_LEVEL >= RDX_LOG_LEVEL_INFO)
#define RDX_LOGI(fmt, ...)  log_info("[RDX_I] " fmt "\r", ##__VA_ARGS__)
#else
#define RDX_LOGI(fmt, ...)  ((void)0)
#endif

#if (RDX_LOG_LEVEL >= RDX_LOG_LEVEL_DBG)
#define RDX_LOGD(fmt, ...)  log_debug("[RDX_D] " fmt "\r", ##__VA_ARGS__)
#else
#define RDX_LOGD(fmt, ...)  ((void)0)
#endif

#endif
```

### 4.3 建立 Board Config

#### 4.3.1 `board/t2616_cc/rdx_board_config.h`

```c
#ifndef __RDX_BOARD_CONFIG_H__
#define __RDX_BOARD_CONFIG_H__

#include "typedef.h"  /* JL SDK 基础类型，如 u32 */

/* 当前芯片族 */
#ifndef RDX_CHIP_FAMILY
#define RDX_CHIP_FAMILY     "jl7018"
#endif

/* 板型标识 */
#ifndef RDX_BOARD_NAME
#define RDX_BOARD_NAME      "t2616_cc"
#endif

/* 无效 IO 占位值：当前源码中未用引脚写 0xff */
#ifndef RDX_IO_INVALID
#define RDX_IO_INVALID      0xff
#endif

/* SPI 引脚与参数 */
typedef struct {
    u32 wifi_power_io;
    u32 vdd_power_io;
    u32 led_data_io;

    u32 spi_cs_io;
    u32 spi_clk_io;
    u32 spi_mosi_io;
    u32 spi_miso_io;        /* 若 ESP8684 不使用 miso，可填无效值 */
    u32 spi_handshake_io;

    u8  spi_port;
    u32 spi_clk_hz;

    const char *chip_family;
    const char *board_name;
} rdx_board_config_t;

const rdx_board_config_t *rdx_board_get_config(void);

#endif
```

#### 4.3.2 `board/t2616_cc/rdx_board_config.c`

```c
#include "board/t2616_cc/rdx_board_config.h"
#include "gpio_config.h"   /* 提供 IO_PORTA_* / IO_PORTC_* / IO_PORTE_* 等宏 */

/*
 * 阶段 1 先把当前板型的真实引脚值直接落到 board config。
 * 不要引用 rdx_spi.c 等 .c 文件内的私有宏。
 * 这些值来自对当前代码的梳理，阶段 1 结束后作为迁移映射表的来源。
 */
static const rdx_board_config_t g_rdx_board_t2616_cc = {
    .wifi_power_io      = IO_PORTA_04,     /* xxpUart.h:39 WIFI_POWER_PORT_IO */
    .vdd_power_io       = IO_PORTA_00,     /* rdx_app.h:42 VDD_POWER_PORT_IO */
    .led_data_io        = IO_PORTC_01,     /* rdx_app.h:46 LED_PT0807_DATA_PORT_IO */

    .spi_cs_io          = IO_PORTE_05,     /* rdx_spi.c:100 ESP8684_CS_PORT_IO */
    .spi_clk_io         = IO_PORTA_05,     /* rdx_spi.c:85 ESP8684_SCLK_PORT_IO */
    .spi_mosi_io        = IO_PORTA_06,     /* rdx_spi.c:77 ESP8684_MOSI_PORT_IO */
    .spi_miso_io        = RDX_IO_INVALID,  /* ESP8684 无 MISO */
    .spi_handshake_io   = IO_PORTA_03,     /* rdx_spi.c:68 ESP8684_HANDSHAKE_PORT_IO */

    .spi_port           = 0,               /* 或 JL_SPI_PORT_A，按实际 SDK 定义填写 */
    .spi_clk_hz         = 4000000,

    .chip_family        = RDX_CHIP_FAMILY,
    .board_name         = RDX_BOARD_NAME,
};

const rdx_board_config_t *rdx_board_get_config(void)
{
    return &g_rdx_board_t2616_cc;
}
```

注意：

- 上表中的引脚值来自当前源码梳理，实施时若硬件有变更需同步更新。
- `rdx_board_config.c` 必须包含能提供 `IO_PORT*` 宏的头（当前工程为 `gpio_config.h`），否则编译时找不到 `IO_PORTA_04` 等定义。
- 阶段 1 不允许 `rdx_board_config.c` 再 `#include "rdx_spi.c"` 或引用 `.c` 文件内的私有宏。
- 业务 `.c` 必须改为调用 `rdx_board_get_config()`，不能再直接使用这些旧宏。
- 阶段 2 再把旧宏彻底删除。

### 4.4 建立 JL OSAL

#### 4.4.1 `port/jl/rdx_jl_osal.h`

```c
#ifndef __RDX_JL_OSAL_H__
#define __RDX_JL_OSAL_H__

#include "typedef.h"
#include "os/os_type.h"   /* OS_MUTEX / OS_SEM 真实类型，工程通用写法 */
#include "rdx_err.h"

/*
 * 阶段 1 的 public handle 仍直接基于 JL OS 类型，
 * 但只在 port/jl 内部包含 os_type.h，业务 core/service public header 禁止 include `rdx_jl_osal.h`。
 * 阶段 2/3 再考虑是否需要不透明包装。
 */
typedef OS_MUTEX *rdx_mutex_t;
typedef OS_SEM   *rdx_sem_t;
typedef int       rdx_timer_t;     /* JL sys_timeout 返回 int id */
typedef int       rdx_task_t;

/* 任务入口签名 */
typedef void (*rdx_task_entry_t)(void *arg);

/* mutex */
rdx_err_t rdx_os_mutex_create(rdx_mutex_t m);  /* m 指向已分配的 OS_MUTEX */
rdx_err_t rdx_os_mutex_lock(rdx_mutex_t m, u32 timeout_ms);
rdx_err_t rdx_os_mutex_unlock(rdx_mutex_t m);
void      rdx_os_mutex_destroy(rdx_mutex_t m);

/* sem */
rdx_err_t rdx_os_sem_create(rdx_sem_t s, u32 initial);
rdx_err_t rdx_os_sem_wait(rdx_sem_t s, u32 timeout_ms);
rdx_err_t rdx_os_sem_post(rdx_sem_t s);
void      rdx_os_sem_destroy(rdx_sem_t s);

/* timer：timeout_ms = 0 表示立即触发 */
rdx_timer_t rdx_os_timer_add(void (*cb)(void *), void *priv, u32 timeout_ms);
void        rdx_os_timer_del(rdx_timer_t id);

/* task */
rdx_err_t rdx_os_task_create(const char *name, rdx_task_entry_t entry, void *arg,
                             u32 stack_depth, u32 prio, rdx_task_t *task);
rdx_err_t rdx_os_task_post_msg(const char *task_name, u32 msg, u32 arg);

/* time */
u32 rdx_os_time_ms(void);
u32 rdx_os_time_tick(void);

#endif
```

要点：

- 与 JL SDK 真实签名对齐：`os_mutex_create(OS_MUTEX *)`、`os_sem_create(OS_SEM *, int)`。
- `rdx_mutex_t` 为 `OS_MUTEX *`，`rdx_sem_t` 为 `OS_SEM *`，这样 wrapper 可以直接透传给 JL API。
- 业务头文件（新增 core/service public header）不暴露 `OS_MUTEX` / `OS_SEM`。

#### 4.4.2 `port/jl/rdx_jl_osal.c`

```c
#include "port/jl/rdx_jl_osal.h"
#include "system/includes.h"    /* JL SDK 头，仅在 port 层包含 */
#include "os/os_api.h"

rdx_err_t rdx_os_mutex_create(rdx_mutex_t m)
{
    if (!m) {
        return RDX_ERR_INVAL;
    }
    int ret = os_mutex_create(m);
    return (ret == 0) ? RDX_OK : RDX_ERR_NOMEM;
}

rdx_err_t rdx_os_mutex_lock(rdx_mutex_t m, u32 timeout_ms)
{
    if (!m) {
        return RDX_ERR_INVAL;
    }
    /*
     * timeout 单位统一为毫秒。
     * 若 JL os_mutex_pend 实际要求 tick，则需要除以 ms_per_tick；
     * 若 JL 已经按 ms 处理，则直接透传。
     */
    int ret = os_mutex_pend(m, timeout_ms);
    return (ret == 0) ? RDX_OK : RDX_ERR_TIMEOUT;
}

rdx_err_t rdx_os_mutex_unlock(rdx_mutex_t m)
{
    if (!m) {
        return RDX_ERR_INVAL;
    }
    int ret = os_mutex_post(m);
    return (ret == 0) ? RDX_OK : RDX_ERR_IO;
}

void rdx_os_mutex_destroy(rdx_mutex_t m)
{
    if (m) {
        os_mutex_del(m, OS_DEL_ALWAYS);
    }
}

rdx_timer_t rdx_os_timer_add(void (*cb)(void *), void *priv, u32 timeout_ms)
{
    return sys_timeout_add(priv, cb, timeout_ms);
}

void rdx_os_timer_del(rdx_timer_t id)
{
    sys_timeout_del(id);
}

u32 rdx_os_time_ms(void)
{
    /* 使用 SDK 提供的 jiffies_msec()，避免依赖 sys_jiffies() */
    return (u32)jiffies_msec();
}
```

要点：

- timeout 统一用 **毫秒**。
- 错误码统一转成 `rdx_err_t`。
- `os_mutex_pend` 的实际超时单位需要在 wrapper 里转换；若 JL API 要求 tick，则 `timeout_ms / ms_per_tick`。

### 4.4.3 关于 semaphore / task 接口的说明

`rdx_jl_osal.h` 中声明了 semaphore 和 task 相关接口，但阶段 1 的核心迁移场景主要使用 mutex、timer、time。为降低一次性改动风险，阶段 1 的最小实现集为：

- `rdx_os_mutex_*`
- `rdx_os_timer_*`
- `rdx_os_time_*`

semaphore 和 task wrapper 的**实现**可在阶段 2 补全，但头文件定义应先落地，使新增代码有统一命名可用。阶段 1 验收时，若业务代码未实际调用这些接口，不会触发链接失败。

如果阶段 1 就需要使用 semaphore/task wrapper，必须同时补齐实现。参考实现如下：

```c
rdx_err_t rdx_os_sem_create(rdx_sem_t s, u32 initial)
{
    if (!s) {
        return RDX_ERR_INVAL;
    }
    int ret = os_sem_create(s, (int)initial);
    return (ret == 0) ? RDX_OK : RDX_ERR_NOMEM;
}

rdx_err_t rdx_os_sem_wait(rdx_sem_t s, u32 timeout_ms)
{
    if (!s) {
        return RDX_ERR_INVAL;
    }
    int ret = os_sem_pend(s, timeout_ms);
    return (ret == 0) ? RDX_OK : RDX_ERR_TIMEOUT;
}

rdx_err_t rdx_os_sem_post(rdx_sem_t s)
{
    if (!s) {
        return RDX_ERR_INVAL;
    }
    int ret = os_sem_post(s);
    return (ret == 0) ? RDX_OK : RDX_ERR_IO;
}

void rdx_os_sem_destroy(rdx_sem_t s)
{
    if (s) {
        os_sem_del(s, OS_DEL_ALWAYS);
    }
}

rdx_err_t rdx_os_task_post_msg(const char *task_name, u32 msg, u32 arg)
{
    int ret = os_taskq_post_msg(task_name, 2, msg, arg);
    return (ret == 0) ? RDX_OK : RDX_ERR_IO;
}
```

> 注：上述函数名和参数以 JL SDK 常见 API 为例，实际实现必须与当前项目使用的 JL OS API 签名对齐。

### 4.5 建立 JL Storage Wrapper

#### 4.5.1 `port/jl/rdx_jl_storage.h`

`rdx_vm_id_t` 枚举值**不能直接写死 0x01/0x02**。它们必须映射到 JL SDK `syscfg_id.h` 中实际定义的 VM ID 宏。阶段 1 应先做一次全量扫描，列出当前所有 `syscfg_read/write` 调用中使用的 VM ID，再建立映射。

示例（选项 A：直接用现有 VM ID 宏）：

```c
#ifndef __RDX_JL_STORAGE_H__
#define __RDX_JL_STORAGE_H__

#include "typedef.h"
#include "rdx_err.h"
#include "syscfg_id.h"    /* 工程通用写法：RDX 现有代码直接使用 syscfg_id.h */

/* VM ID 在此集中管理，业务代码不再直接写 syscfg id
 * 以下宏来自 SDK/interface/utils/syscfg_id.h，实施时请核对当前 SDK 版本。
 */
typedef enum {
    RDX_VM_ID_AI_MODE           = VM_RDX_AI_MODE,
    RDX_VM_ID_RECORD_FILE_NUM   = VM_RDX_RECORD_FILE_NUM,
    RDX_VM_ID_CUSTOM_AUTH       = VM_RDX_CUSTOM_AUTH,
    RDX_VM_ID_BOUND_STATUS      = VM_RDX_NOTTA_BOUND_STATUS,
    RDX_VM_ID_BLE_NAME          = VM_RDX_BLE_NAME,
    RDX_VM_ID_RTC_INIT_VALUE    = VM_RDX_RTC_INIT_VALUE,
    RDX_VM_ID_WIFI_MAC          = VM_RDX_WIFI_MAC,
    RDX_VM_ID_BLE_MAC           = VM_RDX_BLE_MAC,
    RDX_VM_ID_AUTO_OFF_TIME     = VM_RDX_AUTO_OFF_TIME,
    RDX_VM_ID_MIC_GAIN          = VM_RDX_MIC_GAIN,
    RDX_VM_ID_REC_ERR_REBOOT    = VM_RDX_REC_ERR_REBOOT,
    RDX_VM_ID_CHARGE_TIME_INFO  = VM_RDX_CHARGE_TIME_INFO,
    RDX_VM_ID_DAT_VERSION       = VM_RDX_DAT_VERSION,
    RDX_VM_ID_KEY_DUT_DISABLED  = VM_RDX_KEY_DUT_DISABLED,
    /* 后续阶段逐步补齐 */
} rdx_vm_id_t;

rdx_err_t rdx_storage_read(rdx_vm_id_t id, u8 *buf, u16 len);
rdx_err_t rdx_storage_write(rdx_vm_id_t id, const u8 *buf, u16 len);

#endif
```

如果现有 VM ID 宏命名不规范，或同一个逻辑 ID 在不同设备宏下指向不同 syscfg ID，则使用**选项 B：映射表**。映射表中的返回值必须使用 `syscfg_id.h` 中真实存在的宏，例如：

```c
static int rdx_vm_to_syscfg_id(rdx_vm_id_t id)
{
    switch (id) {
    case RDX_VM_ID_CUSTOM_AUTH:    return VM_RDX_CUSTOM_AUTH;
    case RDX_VM_ID_BOUND_STATUS:   return VM_RDX_NOTTA_BOUND_STATUS;
    /* ... */
    default: return -1;
    }
}
```

阶段 1 验收时，必须验证 `rdx_storage_read/write` 传入的 ID 与重构前 `syscfg_read/write` 传入的 ID 完全一致。

#### 4.5.2 `port/jl/rdx_jl_storage.c`

```c
#include "port/jl/rdx_jl_storage.h"
#include "app_config.h"
#include "system/includes.h"
#include "syscfg_id.h"

rdx_err_t rdx_storage_read(rdx_vm_id_t id, u8 *buf, u16 len)
{
    int ret = syscfg_read((int)id, buf, len);
    if (ret < 0) {
        return RDX_ERR_IO;
    }
    if (ret == 0) {
        return RDX_ERR_NOENT;
    }
    return RDX_OK;
}

{
```

#### 4.6.4 `deprecated` 机制具体实现

`#warning` / `#pragma message` 是预处理指令，**不能嵌入到宏体内部**，因此不能做到“谁用谁警告”。阶段 1 推荐两种可工作的 deprecate 方案：

**方案 A：用 `__attribute__((deprecated))` 包装成函数（推荐用于函数/变量）**

```c
/* 旧接口包装，调用时产生 deprecated 警告 */
__attribute__((deprecated("use rdx_board_get_config()->vdd_power_io instead")))
static inline u32 rdx_deprecated_vdd_power_io(void)
{
    return rdx_board_get_config()->vdd_power_io;
}

/* 如果旧代码是宏，先改成调用上述函数 */
#define VDD_POWER_PORT_IO  rdx_deprecated_vdd_power_io()
```

**方案 B：在包含旧宏的头文件顶部输出一次性警告**

```c
/* rdx_app.h 顶部 */
#ifdef RDX_ENABLE_DEPRECATION_WARNINGS
#pragma message("rdx_app.h: VDD_POWER_PORT_IO / LED_PT0807_DATA_PORT_IO are deprecated, use rdx_board_get_config()")
#endif
```

这种方案只能提示“这个头里有旧宏”，不能定位到具体调用点。

**方案 C：迁移完成后直接删除宏，让编译器报错定位（适用于内部可控模块）**

阶段 2 使用。

阶段 1 推荐组合：

- 频繁使用的板级常量 → 方案 A，让调用者看到具体位置。
- 一次性提示整体进度 → 方案 B 作为补充。
- 内部模块且引用点已全部查清 → 直接删除（方案 C 的局部应用）。

## 6. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 旧宏被大量引用，迁移遗漏 | 编译失败或行为不一致 | 保留 `deprecated` 形式；验收时 `grep` 全量扫描；建立迁移映射表 |
| OSAL timeout 单位转换错误 | 任务/定时器超时异常 | 文档明确 `timeout_ms`；单元测试覆盖 0、1、0xFFFFFFFF 等边界值 |
| board config 引脚错误 | 硬件损坏或功能异常 | 启动日志打印全部引脚；保留硬件冒烟测试；阶段 1 不改动真实硬件初始化时序 |
| `librdxApp.a` 依赖被移动的旧符号 | 链接失败 | 阶段 0 先输出 ABI 保留清单；阶段 1 只迁移确认无静态库依赖的符号 |
| Makefile 新变量与旧构建脚本冲突 | CI 构建失败 | 新变量带默认值 `?=`；给出具体插入行号和变量名；验收时从 clean build 开始 |
| 新增文件导致 include 路径问题 | 头文件找不到 | `Makefile` 显式增加 include path；验收时从 clean build 开始 |
| 阶段 1 范围膨胀，要求全量清理 syscfg/os | 高风险重构 | 验收标准明确：阶段 1 只迁热点，业务 `.c` 旧调用保留并登记 |
