# 10-15. BLE 下载期间录音抢占 APP 对接说明

> 更新：2026-11-25。APP/SDK 按 §3～§6 对接、按 §8 联调验收。
> 设备端设计见 [10-1 §10 / §10.1](10-1.量产产线问题积累.md)。

## 联调摘要：固定无额外延时后，27 轮未见控制通知漏报

- **最终板测：** 移除实验延时后，关闭提示音的 F19 10/10 通过，开启提示音的 F19 11/11、F18 6/6 通过。每轮均收到主动停传、开录、结束并记录保存完成，APP 停传到开录最短 **2.4 ms**（§8.1）。
- **固定行为：** 保留「在途文件帧 → `*DEV#filecmd#0#` → 录音状态和音频流」的发送顺序，移除 1 秒实验开关，停传提交后不再人为等待。APP/SDK 不得假设两条通知之间有最小间隔。
- **待补测：** 关闭提示音的 F18 下载抢占尚未覆盖；请在存储余量充足的设备上补齐 `frame=0` / `frame=1`（§8.4）。此前的 APP/SDK 清理竞态仍是待验证假设；若再漏报，按 §8.2 分层定位。

## 1. 场景与结论

APP 通过 BLE 下载录音文件（`*APP#opusfile#…` 分块请求，设备回 `*DEV#filect#…` 帧）时，用户按
F18（会议）/F19（灵感）/通话录音键。**录音优先于下载**：设备停止本次下载，开始录音。

录音启动不等下载清理，停传通知交给 ATT 后不额外延迟录音状态。正常路径下，设备按以下顺序发送：

```text
正在发送的那一整帧 → *DEV#filecmd#0# → 录音状态（record / flashnote）→ 音频流（stream）
```

对齐的目标是防止 **已到达 APP 的报文被文件拼帧吞掉**，不是保证链路异常时每条状态都能送达。

APP 需要做四件事：

1. 拼帧时能识别被截断的帧并立即跳出（§3）——这是兜底，防止异常截断时吞掉后续报文。
2. 收到 `*DEV#filecmd#0#` 后，SDK 立即结束本次下载并拒收旧下载分片，不再请求、不再超时重试（§4）。
3. 被抢占的下载就此结束，录音结束后**不自动恢复**；用户再次发起时可按偏移续传（§5）。
4. 万一漏收录音开始状态、直接收到音频流，按“已开始录音”完整保存，不截断、不丢弃（§6）。

## 2. 设备端发送顺序（正常路径）

| 项 | 设备行为 |
| --- | --- |
| 帧内不插包 | 帧（`*DEV#filect#` 头 + 负载 + 校验尾）正常发完之前不插发其他业务报文 |
| 停止时机 | 有帧正在发则等待帧尾（最多约 2 s），再发 `*DEV#filecmd#0#`；没有帧在发则不等帧 |
| 停止之后 | 设备不应再发送旧下载的分片；`record`、`flashnote`、`stream` 排在 `filecmd#0` 之后 |
| 录音期间的下载请求 | `pack=1`：拒绝并再回一条 `*DEV#filecmd#0#`；`pack>=2`：静默拒绝，不回任何报文 |
| 录音结束后 | 设备不恢复下载；空闲时按正常流程受理用户新发起的 `pack=1` 请求 |

`*DEV#filecmd#0#` 是现有命令，与 5 s 超时、APP 取消时设备的回应是同一条，含义都是“本次传输已在设备侧停止”，
不代表失败、不代表文件损坏，也不是录音开始信号。

以下情况不能依赖完整帧或状态送达，APP 仍需按 §3、§4、§6 兜底：

- 链路拥塞，约 2 s 内该帧仍未发完：设备照常停止，该帧可能被截断；
- 断线、设备复位导致的帧截断；
- 旧固件（无帧边界屏障）：帧发到一半按键会直接截断；
- 停传后若 APP 仍收到旧下载数据，必须丢弃，不能重新进入文件拼帧模式（§3.1、§4）。

## 3. 拼帧：识别截断帧并跳出（必须）

### 3.1 问题

旧解析路径按 `*DEV#filect#` 帧头里的长度拼包：没收够长度之前，把之后**每一个** notify 都当作负载追加，且没有超时。
一旦帧被截断，紧随其后的 `*DEV#filecmd#0#`、录音开始状态、音频流都会被当成负载吞掉，直到长度凑够后校验失败。
2026-11-20 旧固件实测：

| 测试 | 抢占次数 | 被吞次数 | 每次被吞时长 | 后果 |
| --- | --- | --- | --- | --- |
| 13:51（旧 APP） | 6 | 3 | — | 停止和录音开始都没收到，只看到录音结束 |
| 14:31（新 APP） | 8 | 5 | 2.7～6.5 s | 停止、录音开始及这段时间的在线音频全部丢失 |

被吞时长 = 截断帧剩余字节 ÷ 在线流速率（约 3 KB/s），帧越靠前被截断，吞得越久。

2026-11-23 复测中，曾两次在停传后观察到文件拼帧重新开启且录音开始未解析；
不能据此确认丢失在哪一环节。SDK 在停传后必须拒绝迟到的旧下载分片，不能再次进入文件拼帧。

### 3.2 设备分包规律

- 一个 notify 携带一个文件分片。多片帧的首片以 `*DEV#filect#` 开头，首片和中间分片等长，末片是剩余长度；
- APP 以该帧实际首片长度为准，不从 ATT MTU 推算或写死。例：ATT MTU 为 517 时常规分片为 504 B，
  Android 紧凑分片可为 244 B；
- 帧外报文（`filecmd`、`record`、`flashnote`、`stream` 等）以 `*DEV#` 开头，通常比块长短，
  但可能和尾片等长（例：`*DEV#filecmd#0#` 15 B、实测 `flashnote` 31 B、`stream` 58 B）。

### 3.3 规则

SDK 只有在**当前下载仍有效且有匹配的待收块**（含预取）时，才允许 `filect` 开启文件拼帧。帧模式下，每条 notify 的
期望长度为 `min(块长, 本帧剩余字节数)`，块长取本帧第一片的长度。

1. **长度不符**：丢弃未完成的文件帧，退出文件模式，保留此前已校验的块。如果此 notify 是已知报文的开头，
   将**同一条 notify** 交给普通报文解析，不要连同文件帧一起丢掉。
2. **长度相符**：先作为候选文件分片，整帧校验通过才交付。若恰好凑齐但校验失败，不丢弃该尾片的原始字节；
   退出文件模式后，若该 notify 本身符合已知报文格式，按普通报文重新解析。例如还差 15 B 时收到
   `*DEV#filecmd#0#`，不能因为等长就把停传吞掉。
3. **静默超时**：帧模式下 **500 ms** 内没有任何 notify，丢弃未完成帧并退出。连续收到录音音频时不会触发
   静默超时，不能靠它代替报文识别或 §4 的停传处理。

识别报文要看 notify 起点的**已知命令头和对应格式**，不能只凭 `*DEV#`，也不要在文件负载中扫描命令。
`stream` 含二进制音频，按协议头和长度识别；短 MTU 下拆开的命令交给现有命令解析器继续拼接。
先处理拆出的报文，再决定坏块是否可重试；回调执行前还要检查下载仍有效，录音或停传时不得重试。

## 4. SDK 收到 `*DEV#filecmd#0#`（必须）

**SDK 解析到停传时，必须先终止该下载，再处理下一条 notify 或通知 UI。** 仅在 UI 设置 `stopped=true` 不够。
日志里的“文件下载已取消”或 `operation.finished` 也不能代替对拼帧状态、旧下载回调和后续普通报文路由的检查。

1. **结束该轮下载并解除等待。** 将当前下载标为“被设备停止”（非失败、不可重试），立即结束该轮所有等待
   文件数据的任务，取消超时及重试定时器，不能等 10 s 超时后才收尾。
2. **阻止旧请求继续发送。** 撤销尚未写入 GATT 的预取、重试和收尾请求。已经写入的请求不能撤回；
   用下载轮次或取消标记挡住该轮迟到的回调，不能再触发请求、重试或 APP 主动取消。
3. **只清理下载解析状态。** 丢弃未完成的文件帧和 SDK 文件接收队列，保留已校验并保存的连续文件数据和续传点。
   在用户重新发起下载（§5）前，不得让晚到的 `filect` 或续片开启拼帧、生成文件块或唤醒旧等待。
   不清空普通命令和音频的接收状态，`record`、`flashnote`、`stream` 照常解析。
4. **重复停传幂等。** 同一轮已停止时，再收到 `filecmd#0` 不重复收尾、不再补发取消。

**F18 会议录音：** `filecmd#0` 只负责结束下载，复用 F19 的清理流程。设备自行开始采集并主动上报
`record` state=1，APP 按原有会议录音流程处理状态、接收 `stream`，在 state=0 时正常收尾；
不需要 APP 回发录音开始命令。

**实测：** 2026-11-20 已发现停传后仍发预取、超时重试、从头重下。2026-11-23 的 6 次抢占中 UI
虽已标为停止，SDK 仍经历 2～3 次 10 s `transfer.timeout`，最后再次发取消。14:00:42 那次连停止和
`flashnote` 开始态都正常解析，仍超时 3 次，说明 SDK 收尾问题不是漏解析开始态造成的。

## 5. 录音结束后不恢复下载（必须）

被抢占的下载在收到 `filecmd#0` 时就已结束（状态为“被设备停止”，非失败）。录音结束后 APP/SDK
**不得自动重新发起下载**，也不得把“录音结束”当作续传触发条件。是否继续下载由用户之后重新发起。

### 5.1 录音结束信号

| 录音类型 | 开始 | 结束 |
| --- | --- | --- |
| F18 会议 / 通话 | `*DEV#record#…`（state 1） | `*DEV#record#…`（state 0） |
| F19 灵感 | `flashnote` state=1 | `flashnote` state=0 |

录音结束信号只用于结束录音会话、落盘（§6），与下载无关。

### 5.2 用户重新发起下载时的断点续传（可选）

用户之后重新下载同一文件时，APP 可以从头下载，也可以利用已保存的数据断点续传：

```text
*APP#opusfile#<ack>#<sn>#1#<auto_delete>#<offset>#
```

- `pack` 固定为 `1`（新传输），不要用中断前的块号；
- `offset` = 本轮起始偏移 + 本轮已校验并保存的连续负载字节数，即下一未下载字节的位置。标准块为 24480 B；
  按实际保存的负载长度累加，不计协议头、校验尾、未完成帧或重复块；
- `sn`、`auto_delete` 与中断前一致；之后按正常流程 `pack=2,3…` 请求，结束时发 `pack=0`。

录音期间不要发任何下载请求，包括用户手动发起的。若录音期间误发 `pack=1`，设备会再回一条 `filecmd#0`，APP 按 §4 处理即可。

## 6. 漏收录音开始状态时的音频处理（必须）

正常情况下 APP 先收到录音开始（`record` state=1 / `flashnote` state=1），再收到 `*DEV#stream#…` 音频流。
但遇到旧固件、链路异常截断或 APP 自身解析问题时，录音开始状态可能丢失，APP 会**直接收到音频流**。
此时设备**已经在录音**，APP 必须按“录音进行中”处理。兜底只能保存实际收到的音频，不能补回未到达 APP 的数据。

### 6.1 规则

1. 收到音频流但没有对应的录音开始状态：立即进入“录音中”，开始完整保存，**不设帧数/时长上限**，不丢弃已收到的帧。
   预缓冲只能用于决定“写到哪个文件”，不能限制长度；确定后把预缓冲内容连同后续音频完整写入。
2. 之后补收到录音开始状态：沿用当前录音会话，补全文件名、`fileSn` 等信息，不要另开新会话或丢弃已缓冲的音频。
3. 收到录音结束（`record` state=0 / `flashnote` state=0）：
   不论之前有没有收到开始状态，只要收到过音频，都要**落盘并完成保存**，不能只做本机收尾、把已缓冲的音频丢掉。
4. 录音类型按本次会话的状态判断。未知时先保存，收到结束报文再按类型（`record` 为会议/通话，`flashnote` 为灵感）归档。
5. 收到音频流时若下载流程仍在进行，按 §4 结束本次下载（等同于收到 `filecmd#0`），录音结束后不恢复（§5）。

### 6.2 14:31 测试中暴露的问题

| 现象 | 次数 | 实际音频 | APP 保存 | 原因 |
| --- | --- | --- | --- | --- |
| F19 灵感漏收 flashnote state=1 | 3 | 7.9～9.7 s | 恰好 250 帧（5.0 s） | “启动缓冲”模式上限 250 帧，超过部分丢弃 |
| F19 灵感漏收 flashnote state=1 | 1 | 4.2 s | 208 帧 | 未超上限，完整保存 |
| F18 会议漏收 record state=1 | 1 | 约 14 s | **未保存** | 收到 record#0 时停在 `starting-record`，只打印“只做本机收尾” |

上表的“实际音频”只是 APP 收到的那部分，截断帧吞掉的 2.7～6.5 s 已在 §3 统计，无法补回。
正常收到开始状态的 3 次（`本地采集` 模式）保存的帧数与音频时长一致。

## 7. 其他约定

- **APP 主动发起的录音**（APP 下发录音命令）不经过设备抢占：APP 应先取消当前下载（等到 `filecmd#0` 或取消完成），
  再下发录音命令。
- **一次抢占可能收到多条 `filecmd#0`**（如录音期间又发了 `pack=1`）。`filecmd#0` 幂等：已停止时再次收到直接忽略。
- **按键落在两个文件之间**（上一个文件已 `pack=0`、下一个文件 `pack=1` 尚未发出）：设备没有活动传输，不会发
  `filecmd#0`，录音状态直接上报。APP 收到录音开始（§5.1）时，若下载流程仍在进行，应自行结束下载流程（不再发下一个文件的 `pack=1`），录音结束后不恢复。

### 8.2 双端联合排查：收到停传但录音状态缺失

**历史异常结论：** 固件修正截帧后，旧 APP 曾在 `frame=0` 且下一块待收时解析到主动停传，却未解析开录和结束。
设备侧 ATT 接纳不代表报文已到 APP。1 秒对照实验未复现，但不能确认清理竞态；如再出现，优先排查旧下载回调是否
重开拼帧、异步清理是否误清共用接收缓冲，以及 SDK 已解析但未分发的情况。

1. **共同复测。** 固定同一设备、下载文件和 APP/SDK 版本，使用不额外延时的固件。BLE 下载中按 F19，优先覆盖
   “APP 已预取下一块、设备尚未发首片”（`frame=0`）；保留异常轮及一轮成功对照。
   双方在触发前开始记录，持续到录音结束后；一起记录轮次、设备编号、固件构建标识、APP/SDK 和主机系统版本。
   按轮次、同一块请求及停传事件对齐日志，毫秒间隔用各自日志内的时间计算，不直接相减两端时钟。
2. **固件侧：抓提交顺序。** 保留同轮串口日志，标出最后一块文件帧尾的提交结果、下一块请求和首片是否交给协议栈，
   以及 `DL_PREEMPT` 的 `frame`、`stop sent` 和 `RDX_TX_PROBE` 的开录/结束提交结果。提交成功不当作 APP 已收。
3. **APP/SDK 侧：抓入口和状态切换。** 在 BLE 回调入口、SDK 解析前记录每条通知的序号、时间、长度及控制报文和类型不明
   报文的原始字节；确认是文件或音频时可只记头和长度。用同一序号记录解析路由、丢弃原因和事件分发结果。
   在 `filecmd#0` 处理前后记录下载代次、待收块号、拼帧剩余字节、清理开始/结束及清理对象。记录迟到回调携带的代次，
   检查是否切回文件模式，或误清普通命令和 `stream` 缓冲。下载代次和拼帧状态须在处理下一条 notify 前切换，
   UI 收尾和链路参数查询可以异步执行；旧代次回调不得修改当前接收状态。
4. **一起判断丢在哪一层。** 原始 `flashnote` 已到回调、却被旧下载路径消费或清掉，才能确认清理竞态；
   若已有 `frame.text` 但没有业务事件，则追分发与录音业务状态；若回调入口没有该报文，再用同轮主机 HCI 和串口对照。
   没有逐条原始字节时，不用 `traffic.summary` 或 `att-ok` 定责。
   若已确认 `stream` 到达但未保存，按 §6 单独检查缺状态时的保存路径。

| 帧刚发完按 F19 / F18 | `filecmd#0` → 录音开始；音频正常保存 |
| 下载中双击 F18（会议录音） | SDK 收到 `filecmd#0` 后结束下载，不回发开录命令；APP 正常处理 `record` state=1 → `stream` → `record` state=0，保存录音且不自动续传 |
| 设备刚收到下一块请求、首片尚未发送时按 F19 | 停传后无旧文件首片；停传、开录、结束均被解析 |
| 回放下一块已预取的场景：上一块通过校验，`filecmd#0` 后紧接开录、音频、结束 | 下一块等待被取消，开录和结束均解析、录音保存；不依赖两条通知之间额外延时 |
| 回放停传后让旧下载的取消完成、超时或预取回调插在开录通知前后 | 旧回调不恢复拼帧、不清普通通知或音频；开录和结束均解析并保存 |
| SDK 有预取和等待时收到 `filecmd#0` | 等待立即结束；旧下载后续无 GATT 写入、无 `transfer.timeout`、无重试或补发取消 |
| 回放 `filecmd#0` → 迟到的 `filect` 首片／续片 → `flashnote` 或 `record` 开始 → `stream` → 录音结束 | 旧片不拼帧、不产生 `frame.transfer`；开始、结束均解析，音频完整保存；重复 `filecmd#0` 不影响录音 |
| 文件帧正好剩 15 B 时收到 `filecmd#0` | 文件校验失败后用同一条 notify 解析停传；对照的合法等长尾片能通过校验并正常保存 |
| `filecmd#0` 已解析，`flashnote#1` 和 `flashnote#0` 都缺失 | 收到 `stream` 仍开始保存，不因下载停止而清录音缓冲；断连时按中断保留实际已收音频，不标为完整录音 |
| 录音结束 | APP 不自动发任何下载请求；设备串口无新的 `opusfile` 请求 |
| 录音结束后用户重新下载该文件 | 断点续传（`pack=1` + 已保存偏移）或从头下载均可，文件无缺失、无重复 |
| 下载中断开 BLE | 重连后从续传点 `pack=1` 重新请求 |
| 两个文件之间按键 | 录音开始后 APP 结束下载流程，录音结束后不继续 |
| 漏收开始状态（旧固件帧中按键可复现） | 截断帧丢弃后，后续音频完整保存，保存时长 ≈ 录音结束 − 首帧音频，不止 5 s |
| F18 漏收 record#1 | 收到 record#0 时仍落盘，不只做本机收尾 |

### 8.4 固定时序后的回归（F18 / F19）

延时宏和定时器已移除。F18 双击（`record`）和 F19 按住（`flashnote`）仍共用停传屏障。
不额外延时不等于两条通知同时到达，实际间隔受在途帧、录音初始化、提示音和链路调度影响。

最终回归已覆盖 F19 提示音开／关、F18 提示音开的 `frame=0` 和 `frame=1`。待补项是在有足够存储余量的设备上
关闭提示音、在 BLE 下载中双击 F18；分别覆盖 `frame=0`（无在途帧，优先覆盖下一块刚预取）和 `frame=1`（在途帧）。
按 §8.2 记录 APP 接收间隔、主动停传、开录和结束的解析结果及保存情况；异常时留原始 notify。另试听保存音频的开头和结尾。
