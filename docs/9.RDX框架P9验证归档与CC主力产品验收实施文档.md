# RDX 框架 P9 验证归档与 CC 主力产品验收实施文档

> 日期：2026-07-21
> 当前状态：P8 产品配置拆分已完成；Zenchord CC 目标板行为已回归。2026-07-21 已确认 Zenchord EP 和 CC 均可通过生产构建入口 clean build，但不能据此表述为“所有产品固件均已通过”：`jl7018_shadow` 尚未执行 clean build，统一 Host 门禁也尚未通过。P9 尚未完成，仍需修复 Host 入口/判定问题并补齐可追溯归档；P9 本身不要求重新烧录。
> 上游依据：`docs/3.RDX框架JL平台复用性优化大纲.md`、`docs/4.RDX框架重构进度与完成度评估.md`、`docs/8.RDX框架P8产品配置拆分实施文档.md`
> P9 定位：以当前生产主力 Zenchord CC 为唯一硬件验收对象，补齐 P8 的可复查验证证据；不扩大产品承诺，不进行新的业务架构重构。

## 1. 结论

P9 不再沿用“所有已存在档位均须完成目标板回归”的口径。当前可获得并承担生产责任的实机为 Zenchord CC，因此 P9 的硬件功能验收范围固定为：

```text
RDX_PRODUCT=zenchord_cc
RDX_CHIP_FAMILY=jl7018
RDX_BOARD=t2616_cc
RDX_AI_SEL_APP=APP_ZENCHORD_EN
RDX_SEL_DEVICE=DEVICE_ZENCORD_CC_T2616
```

`zenchord_ep` 和 `jl7018_shadow` 保留为配置选择、预处理和编译隔离档位；因没有对应目标板，P9 不对其执行硬件功能回归，也不宣称其已经生产可用。

P9 只完成以下闭环：

1. 固化 CC 主力产品的构建、静态检查、配置矩阵、静态库和目标板回归证据。
2. 对 EP/shadow 保留最低限度的非硬件防退化检查。
3. 记录已知验证边界和未验证范围。
4. 更新 P8 完成状态和后续 P10 的进入条件。

P9 不修改 `librdxApp.a`、协议 ABI、产品参数、service 接口或目标板运行逻辑。若验证中发现问题，先按问题归属单独立项；禁止以 P9 名义混入 Storage、OSAL、BLE 或 `rdx_app.c` 重构。

## 2. 验收范围与口径

### 2.1 支持分级

| 档位 | 配置/静态检查 | Host/编译检查 | 目标板功能回归 | P9 结论 |
|---|---|---|---|---|
| `zenchord_cc + jl7018` | 必须 | 必须 | 必须 | 主力生产验收对象 |
| `zenchord_cc + jl7018_shadow` | 必须 | 尽力执行；工具链可用时必须通过 | 不执行 | 芯片隔离 skeleton，不宣称硬件可用 |
| `zenchord_ep + jl7018` | 必须 | 尽力执行；工具链可用时必须通过 | 不执行 | 产品/板型隔离档位，不宣称硬件可用 |

“尽力执行”不等于允许失败：当本地具备对应生产工具链和构建入口时，EP/shadow 必须从 clean 状态构建 PASS。只有缺少工具链、许可证或外部依赖时才允许记为 `NOT RUN`，并归档命令、环境限制和原因。由源码、配置或构建脚本缺陷引起的失败必须修复，不能通过“已记录原因”关闭 P9；不得将 `NOT RUN` 表述为通过。

### 2.2 P9 硬件验收边界

P9 只验证 CC 主力产品的现有行为，不新增功能、不改变产品语义。目标板回归至少覆盖：

- 启动日志中的 product、board、chip、版本信息。
- BLE 名称、广播厂商数据和产品码。
- 配对、绑定、BLE 连接、断开和重连。
- BLE 录音上传不少于 30 秒。
- WiFi 在线录音不少于 30 秒。
- BLE 强制停止、在线/离线录音与断连处理。
- WiFi AP 名称、密码策略和连接。
- OTA 版本比较。
- 软关机和恢复。
- 恢复出厂后重新配对。
- 自动关机、DUT、充电满电检查、LED 刷新和 RTC restore。
- 已持久化状态的重启保持，包括绑定状态、BLE 名称、RTC 和 MIC gain。

目标板已完成的回归可以作为 P9 证据归档；P9 不要求为同一固件无理由重复执行完整测试。若 P9 执行期间重新构建、重新烧录或发现影响上述路径的差异，则必须针对受影响项重新回归。

### 2.3 EP/shadow 的非硬件边界

EP 和 shadow 的检查仅用于防止公共配置、Makefile 或 port 选择静默退化：

- `RDX_PRODUCT` 只能选择受支持的原始字面量。
- APP、DEVICE、BOARD 必须由同一产品档位一致选择。
- C 配置 validator 必须拒绝未知 APP、未知 DEVICE、多 APP、非法 APP/DEVICE 组合。
- Makefile 必须拒绝 board 错配、内部变量覆盖、递归 Make 表达式和非法 chip family。
- 若生产工具链可用，EP/shadow 必须能从 clean 状态编译。

这些检查不验证实际射频、录音、WiFi、低功耗、GPIO、充电或协议互通行为。

## 4. P9 实施任务

P9 采用一次提交完成。执行顺序固定为“基线记录 -> 静态/Host 门禁 -> EP clean build -> shadow clean build -> 最终 CC clean build -> 固化产物/map/hash -> 关联既有 CC 回归记录 -> 完成度更新”。最终 CC 构建之后不得再执行会覆盖产物的 clean/build；P9 本身不要求重新烧录，验证期间发现的功能缺陷也不混入本提交。

记录以下信息，以便后续验证结果可追溯：

Windows 环境记录：

```bat

git status --short
powershell.exe -NoProfile -Command "Get-FileHash -Algorithm SHA256 'SDK/apps/common/third_party_profile/rdx_protocol/librdxApp.a'"
```

Unix-like 环境可使用：

```sh
git rev-parse HEAD
git status --short
shasum -a 256 SDK/apps/common/third_party_profile/rdx_protocol/librdxApp.a
```

同时保存：

- 当前提交 SHA。
- 工作区是否干净；若不干净，列出与 P9 无关的已有改动并避免覆盖。
- `librdxApp.a` SHA256。
- CC 目标板使用的产品档位、固件版本、烧录产物标识和回归日期。
- 生产工具链、make、编译器和 PowerShell 版本。

P9 不应依赖口头结论。已经完成的 CC 目标板回归必须整理为结构化记录，至少包含测试组合、步骤、预期、实际结果和日志/截图/视频索引。

### 4.2 步骤 2：执行静态边界和配置矩阵

Windows 环境优先使用仓库提供的 PowerShell 入口；Unix-like 环境使用 `pwsh`：

```bat
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/check_rdx_boundaries.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/host/test_rdx_config_matrix.ps1
```

```sh
pwsh -NoProfile -ExecutionPolicy Bypass -File tools/check_rdx_boundaries.ps1
pwsh -NoProfile -ExecutionPolicy Bypass -File tests/host/test_rdx_config_matrix.ps1
```

执行结果必须记录实际命令、PowerShell 版本、编译器版本、make 版本和完整日志路径。配置矩阵中预期失败的 C/Make 用例必须由测试脚本正确识别为 PASS；不得因 PowerShell 将原生编译器 stderr 提升为异常而中断矩阵。

验收：

- 静态边界脚本全部 PASS，包含 P7 和 P8 规则。
- 配置矩阵全部 PASS。
- `zenchord_cc`、`zenchord_ep` 和全部 17 个产品配置头在 C 配置检查中保持可选择。
- 非法 APP、未知 DEVICE、多 APP、非法 APP/DEVICE、board 错配、内部变量覆盖、递归 Make 表达式和非法 chip family 均按预期失败。
- 命令行整体传入 `DEFINES=...` 时，最终预构建参数仍含档位 APP/DEVICE 宏。

### 4.3 步骤 3：执行统一 Host 门禁

Windows 环境执行：

```bat
tests\host\run_tests.bat clean
tests\host\run_tests.bat all
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/check_rdx_boundaries.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/host/test_rdx_static_library_abi.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/host/test_rdx_record_recovery.ps1
```

Unix-like 环境执行等价的 GNU Make 与 `pwsh` 命令。`tests\host\run_tests.bat all` 已覆盖六个 C mock 和配置矩阵；其余三个 PowerShell 脚本补齐静态边界、静态库 ABI 和录音恢复契约。归档时将这组命令作为 P9 的统一 Host 门禁，不得只运行其中一个子集后声明 Host 全量通过。

验收：

- `test_dispatch`、`test_event_bus`、`test_time_ops`、`test_board_config`、`test_util`、`test_time_service` 均通过。
- `rdx_config_matrix`、静态边界、静态库 ABI 和 `test_rdx_record_recovery.ps1` 均通过。
- Host 全量 PASS 是 P9 完成的硬门禁。
- 只有具备 C11 `_Static_assert` 的 Host 编译器、PowerShell 或仓库构建工具确实不可获得时才可记为 `BLOCKED`；TinyCC 0.9.27 只能运行六个 C mock，不能解析配置 validator，不能用于宣称统一 Host 门禁通过。`BLOCKED` 必须归档准确输出、宿主 OS 和工具版本，并且不得将 P9 标记为完成。
- 验证脚本自身对 PowerShell 版本、换行格式或预期 stderr 处理错误造成的假失败属于 P9 验证基础设施缺陷，必须修复并重新运行，不能按环境限制豁免。

Host 测试只验证逻辑和配置边界，不替代 CC 目标板上的时序、低功耗、BLE、WiFi 或外设行为验证。

### 4.4 步骤 4：EP/shadow 隔离验证

EP/shadow 不进入硬件验收，但必须先于最终 CC 构建执行，避免后续 clean 或链接覆盖已归档的 CC 产物。Windows 生产构建通过环境变量选择档位后调用工程 wrapper：

```bat
cd SDK
call .vscode\winmk.bat clean
set RDX_PRODUCT=zenchord_ep
set RDX_CHIP_FAMILY=jl7018
call .vscode\winmk.bat
call .vscode\winmk.bat clean
set RDX_PRODUCT=zenchord_cc
set RDX_CHIP_FAMILY=jl7018_shadow
call .vscode\winmk.bat
```

在独立 `cmd.exe` 或构建脚本中执行上述命令，防止环境变量污染后续 CC 构建。若工程 wrapper 要求将变量作为 make 参数传入，应在归档中记录实际可复现命令；不得用 `make -n` 或仅执行 `rdx_config_check` 代替 clean build。

验收：

- 工具链可用时，两个组合均从 clean 状态构建 PASS。
- 只有缺少工具链、许可证或外部依赖时允许记为 `NOT RUN`，并记录命令、环境、完整错误和阻塞原因。
- 源码、配置或构建脚本缺陷引起的失败不能以“已记录原因”关闭 P9。
- 无论结果如何，归档必须写明：EP/shadow 未进行目标板功能验证，不声明其硬件可用性。

禁止因没有 EP/shadow 实机而跳过步骤 2 的配置矩阵和静态边界检查。

### 4.5 步骤 5：最终 CC clean build 与产物固化

EP/shadow 检查完成后，清除其构建环境和产物，再执行本轮最后一次生产构建。Windows 环境使用真实生产 wrapper：

```bat
cd SDK
set RDX_PRODUCT=zenchord_cc
set RDX_CHIP_FAMILY=jl7018
call .vscode\winmk.bat clean
call .vscode\winmk.bat
```

构建完成后、任何其他 clean/build 之前立即固化：

```powershell
Get-FileHash -Algorithm SHA256 <firmware-path>
Get-FileHash -Algorithm SHA256 apps/common/third_party_profile/rdx_protocol/librdxApp.a
```

`<firmware-path>` 必须在实际执行时替换为构建日志报告的真实产物路径，并将完整命令写入归档。Unix-like 环境可使用等价的 `make` 和 `shasum -a 256`。不得以 `make -n` 代替真实编译。

验收：

- CC 从 clean 状态构建成功，且是 EP/shadow 之后的最终构建。
- 产物对应 `zenchord_cc + jl7018`，不存在错误选择 EP board 或 shadow port 的情况。
- map 不引用当前源码树不存在的 RDX board、port、service 或产品配置对象。
- 启动诊断可识别为 CC 对应 product、board、chip、SDK、transport、storage 和 RTC path。
- 在后续构建覆盖前记录固件路径、固件 SHA256、map 路径、构建日志路径及 RDX 相关 Flash/RAM/section 数据。
- `librdxApp.a` SHA256 与步骤 1 的 P9 基线一致。

### 4.6 步骤 6：建立 CC 固件与既有板测记录的证据关联

P9 是验证归档阶段，本身不要求重新烧录或无理由重复目标板测试。归档应尽可能形成以下关联：

```text
commit SHA
  -> RDX_PRODUCT / RDX_CHIP_FAMILY / APP / DEVICE / BOARD
  -> 完整构建日志
  -> 固件路径与 SHA256 / map
  -> 既有 CC 回归使用的固件版本或唯一标识
  -> CC 板号与目标板回归记录
```

步骤 5 的最终 CC clean build 用于建立可复查的当前构建基线；当前已完成的 CC 目标板回归可以直接归档，不要求为了 P9 再烧录。若既有回归的固件标识能够与当前提交或生产版本对应，应记录该关联；无法证明二者完全一致时，必须如实标注“构建基线与既有板测固件未建立逐字节一致性”，但这本身不触发重新烧录。只有验证期间修改了运行逻辑、产品参数、构建选择，或发现影响第 2.2 节行为的差异时，才需要重新构建、烧录并回归受影响用例。

每个用例至少包含：

| 字段 | 要求 |
|---|---|
| 构建组合 | 固定为 `zenchord_cc + jl7018`，并记录 APP、DEVICE、BOARD。 |
| 固件标识 | 版本、构建时间、产物 SHA256 或其他唯一标识。 |
| 硬件信息 | 板号、硬件版本、必要外设或测试夹具信息。 |
| 测试步骤 | 可由其他开发者重复执行的操作步骤。 |
| 预期结果 | 明确可观察的正确行为。 |
| 实际结果 | PASS/FAIL，以及关键日志或现象。 |
| 证据索引 | 串口日志、APP 日志、截图、视频或测试记录路径。 |
| 异常说明 | 未覆盖项、环境限制或已知风险。 |

P9 的 CC 目标板结论只能写为“CC 主力产品目标板回归通过”。不得扩展为“全部 RDX 产品通过”或“EP/shadow 已通过”。

### 4.7 步骤 7：更新完成度与后续入口

更新 `docs/4.RDX框架重构进度与完成度评估.md`，使其不再保留 P8 已完成、CC 已目标板回归但未反映的历史状态。

更新原则：

- P8 标为静态重构、配置矩阵和 CC 主力产品目标板回归完成。
- P9 标为完成必须严格基于实际归档证据；Host 存在失败或 `BLOCKED`、EP/shadow 在工具链可用时未 PASS、ABI/record recovery 未 PASS，均不得勾选。
- 目标板验收范围明确限定为 CC；EP/shadow 的硬件验证状态明确为“无实机，未验证”。
- 后续正式架构任务更新为 P10 Storage 持久化边界收口。

### 5.2 本轮发现的问题及处理状态

| 问题 | 处理 | 状态 |
|---|---|---|
| EP 编译进入 `sk4558.c` 时默认要求 `RDX_BJ_VERSION` 及充电 GPIO 定义，但 EP 没有已确认的充电硬件契约。 | 将原有充电硬件实现限定在 `RDX_BJ_VERSION` 档位；EP 保留空操作初始化/开关和固定未满电查询，不猜测 GPIO。 | 已解决，EP/CC 生产构建均通过；EP 硬件行为仍未验证。 |
| `rdx_app.c` 无条件引用 WiFi AP SSID/密码，EP 产品配置没有这些参数。 | 增加 `RDX_HAS_WIFI_AP_CONFIG` 语义能力，仅在 SSID 与密码同时存在时创建并注册 WiFi 配置；同时拒绝只配置其中一个字段。 | 已解决，未为 EP 虚构 WiFi 参数。 |
| BLE 广播制造商数据无条件追加 `PRODUCT_TYPE`，而 EP 历史配置没有该字段。 | 增加 `RDX_HAS_PRODUCT_TYPE`，仅在产品实际定义该字段时追加。 | 已解决，保留 CC 既有行为。 |
| 充电仓 pair/unpair 实现对 EP 也参与编译，虽然调用与命令注册已是充电仓专属。 | 将实现体同样收口到 `RDX_PRODUCT_IS_CHARGE_CASE`。 | 已解决。 |
| Windows PowerShell 5 会把配置矩阵中“预期失败”的原生编译器 stderr 提升为异常，造成脚本假失败。 | 配置矩阵统一捕获输出和退出码，再按期望成功/失败判定。 | 脚本问题已修复；显式 JL clang 的 32/32 矩阵已通过。 |
| TinyCC 0.9.27 不支持 validator 使用的 C11 `_Static_assert`，原 Host Makefile 的 TinyCC fallback 会产生无效门禁。 | 移除 TinyCC fallback，并在 Host 文档中明确要求 C11 编译器。 | 策略已修正，但当前统一入口仍硬传不存在的 `gcc`，尚未闭环。 |
| ABI 检查受 CRLF/LF 和 `git show` 文本读取方式影响，可能把换行差异误判为 ABI 变化。 | 工作区与 HEAD 内容统一换行，并以明确 UTF-8 输出读取 `git show`。 | 实现已修复，本轮尚未纳入统一 Host 全量复跑。 |
| Host 配置矩阵没有先验证显式 `-Compiler` 是否真实可执行。编译器不存在时，合法用例失败，但负例会把“命令不存在”当作预期编译失败而显示 PASS。 | 本轮只记录，不继续修改测试框架；后续应在运行矩阵前做编译器 preflight，并区分“编译器启动失败”和“源码按预期拒绝”。 | 未解决，是当前不能声明统一 Host 门禁通过的直接原因。 |

因此，本轮可以声明的是“EP 与 CC 的生产固件 clean build 通过，EP 编译缺陷已修复”；不能声明“所有产品档位通过”或“P9 已收尾”。统一 Host 门禁和 shadow clean build 均保留为后续项。

## 7. P10 预告：Storage 持久化边界收口

P9 闭环后，下一项架构重构定义为：

> P10：RDX Storage 持久化边界收口。直接复用现有 JL persistence port `port/jl/include/rdx_jl_storage.h`，将 `syscfg_read/write` 从业务 `.c` 迁入该 port，保持 VM ID、持久化格式、默认值、写入时机和 CC 行为不变。现有 `rdx_storage_service` 继续负责 SD/文件操作，不承载 VM 持久化。

P10 的推荐范围：

1. P10.0 先建立持久化契约表：逐项记录 VM ID、数据长度、默认值、缺失/短读策略、写入时机、调用者和 CC 板测用例。
2. P10.1 处理 `rdx_vm.c`、`rdx_rtc.c` 和 `rdx_dut.c`，统一通过 `rdx_jl_storage.h` 的固定长度读写契约访问 VM。
3. P10.2 单独处理 `rdx_record.c`，保持录音恢复、MIC gain 默认值和现有写后读回校验语义。
4. P10.3 最后处理 `rdx_ble_server.c` 的 BLE 名称、MAC 等敏感状态，并以配对、绑定、恢复出厂和重连回归验证。
5. 只允许 JL storage port 直接调用 `syscfg_*`；业务层通过稳定接口访问持久化能力。
6. 增加静态边界规则和 Host storage mock，覆盖正常读写、缺失、短读、长度错误、写入失败和默认值恢复。
7. `rdx_battery.c` 当前 `syscfg_*` 命中位于 `#if 0` 死代码，不为其新增迁移接口；若未来启用，再按实际契约单独纳入。

P10 的明确非目标：

- 不修改 `librdxApp.a`。
- 不修改协议 ABI 或旧外部符号。
- 不改变 VM ID、二进制布局或已有持久化数据兼容性。
- 不在同一阶段处理全量 OSAL、BLE/Record/Storage 深度解耦或 `rdx_app.c` 行数优化。
- 不要求 EP/shadow 目标板回归；仍按 P9 的支持分级执行。

P10 仅在 P9 已形成可信 CC 构建、map 和目标板回归基线后启动。这样每一次持久化边界迁移都可以以 CC 的绑定、BLE 名称、RTC、MIC gain、恢复出厂、DUT 和录音异常恢复进行实际回归。

## 8. 风险与控制

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 验收范围被误扩大 | 没有 EP/shadow 实机却声明所有档位功能通过 | 将支持分级和未验证结论写入 P9 归档与完成度文档。 |
| 验收范围被误缩小 | 因无实机而取消 EP/shadow 配置门禁 | 保留配置矩阵和工具链可用时的 clean build 检查。 |
| 旧对象污染构建 | 未 clean 的 `.o` 或 map 掩盖构建选择问题 | CC 必须从 clean 状态构建；记录产物和 map 路径。 |
| 目标板结论不可复核 | 只保留口头“回归 OK” | 使用固定字段归档构建组合、步骤、预期、实际和证据索引。 |
| P9 范围膨胀 | 验证时混入 Storage、OSAL 或 BLE 重构 | 缺陷单独立项；P9 只修验证脚本、归档或构建门禁本身的问题。 |
| 静态库边界被意外改变 | 为解决构建问题修改 archive 或 ABI | 固定 SHA256、执行 ABI 检查，禁止修改 `librdxApp.a`。 |
| 后续无体积参照 | P10 改动后无法判断 Flash/RAM 变化 | 将 CC map/section 数据归档为后续增量基线。 |

## 9. 回滚

P9 是验证和文档归档提交，不应改变运行逻辑。若归档脚本或文档存在错误，可整体回滚 P9 提交；不得回滚已经独立完成并通过回归的 P8 产品配置重构。

若 P9 验证暴露 CC 功能回归，应停止 P10，基于 P8/P9 证据定位问题并以独立修复提交解决；修复后重新执行受影响的 CC clean build、静态库检查和目标板用例。
