## 1. 结论

P9 不再沿用“所有已存在档位均须完成目标板回归”的口径。当前可获得并承担生产责任的实机为 Zenchord CC，因此 P9 的硬件功能验收范围固定为：

```text
RDX_PRODUCT=zenchord_cc
RDX_CHIP_FAMILY=jl7018
RDX_BOARD=t2616_cc
RDX_AI_SEL_APP=APP_ZENCHORD_EN
RDX_SEL_DEVICE=DEVICE_ZENCORD_CC_T2616
```

`zenchord_ep` 和 `jl7018_shadow` 保留为配置选择、预处理和编译隔离档位；因没有对应目标板，P9 不对其执行硬件功能回归，也不宣称其已经生产可用。

P9 只完成以下闭环：

1. 固化 CC 主力产品的构建、静态检查、配置矩阵、静态库和目标板回归证据。
2. 对 EP/shadow 保留最低限度的非硬件防退化检查。
3. 记录已知验证边界和未验证范围。
4. 更新 P8 完成状态和后续 P10 的进入条件。

P9 不修改 `librdxApp.a`、协议 ABI、产品参数、service 接口或目标板运行逻辑。若验证中发现问题，先按问题归属单独立项；禁止以 P9 名义混入 Storage、OSAL、BLE 或 `rdx_app.c` 重构。

P9 不得为了验证新增生产环境之外的工具依赖。硬门禁只允许复用当前生产构建已经要求的 JL 工具链、仓库内 `make.exe`、Windows 自带 PowerShell 5 和 Git；不得要求开发者额外安装 `gcc`、桌面 LLVM、MSYS2、Unix `pwsh` 或其他 Host 测试环境。

## 2. 验收范围与口径

### 2.1 支持分级

| 档位 | 零新增依赖门禁 | 生产 clean build | 目标板功能回归 | P9 结论 |
|---|---|---|---|---|
| `zenchord_cc + jl7018` | 必须 | 必须 | 必须 | 主力生产验收对象 |
| `zenchord_cc + jl7018_shadow` | 必须 | 生产工具链可用时必须通过 | 不执行 | 芯片隔离 skeleton，不宣称硬件可用 |
| `zenchord_ep + jl7018` | 必须 | 生产工具链可用时必须通过 | 不执行 | 产品/板型隔离档位，不宣称硬件可用 |

当正常生产环境具备既有 JL 工具链和构建入口时，EP/shadow 必须从 clean 状态构建 PASS。缺少正常生产构建本身所需的工具链、许可证或受控输入时才允许记为 `NOT RUN`，并归档命令、环境限制和原因；不得通过安装 P9 专用 Host 工具绕过问题。由源码、配置或构建脚本缺陷引起的失败必须修复，不能通过“已记录原因”关闭 P9。

### 2.2 P9 硬件验收边界

P9 只验证 CC 主力产品的现有行为，不新增功能、不改变产品语义。目标板回归至少覆盖：

- 启动日志中的 product、board、chip、版本信息。
- BLE 名称、广播厂商数据和产品码。
- 配对、绑定、BLE 连接、断开和重连。
- BLE 录音上传不少于 30 秒。
- WiFi 在线录音不少于 30 秒。
- BLE 强制停止、在线/离线录音与断连处理。
- WiFi AP 名称、密码策略和连接。
- OTA 版本比较。
- 软关机和恢复。
- 恢复出厂后重新配对。
- 自动关机、DUT、充电满电检查、LED 刷新和 RTC restore。
- 已持久化状态的重启保持，包括绑定状态、BLE 名称、RTC 和 MIC gain。

目标板已完成的回归可以作为 P9 证据归档；P9 不要求为同一固件无理由重复执行完整测试。若 P9 执行期间重新构建、重新烧录或发现影响上述路径的差异，则必须针对受影响项重新回归。

### 2.3 EP/shadow 的非硬件边界

EP 和 shadow 的检查仅用于防止公共配置、Makefile 或 port 选择静默退化：

- `RDX_PRODUCT` 只能选择受支持的原始字面量。
- APP、DEVICE、BOARD 必须由同一产品档位一致选择。
- C 配置 validator 必须拒绝未知 APP、未知 DEVICE、多 APP、非法 APP/DEVICE 组合。
- Makefile 必须拒绝 board 错配、内部变量覆盖、递归 Make 表达式和非法 chip family。
- 若生产工具链可用，EP/shadow 必须能从 clean 状态编译。

上述配置检查必须在现有 Windows/JL 生产环境中使用 JL clang、仓库内 `make.exe` 和 Windows PowerShell 5；入口不得搜索 PATH 或回退到 Unix `pwsh`、系统 make、`cc/gcc`、桌面 LLVM。六个需要原生 Host C 编译器并在宿主机执行的 mock 仅作为可选开发检查；没有 `HOST_CC` 时记为 `OPTIONAL NOT RUN`，不阻塞 P9，也不得为运行它们新增软件依赖。`host_all` 与配置矩阵相互独立，执行可选 mock 不得改变必选门禁的结果。

这些检查不验证实际射频、录音、WiFi、低功耗、GPIO、充电或协议互通行为。

## 4. P9 实施任务

P9 可将验证基础设施修复和最终归档分成小提交，禁止通过改写已推送历史强行满足“单提交”。执行顺序固定为“基线记录 -> 零新增依赖门禁 -> EP clean build -> shadow clean build -> 最终 CC clean build -> 固化产物/map/hash -> 关联 CC 回归记录 -> 完成度更新”。最终 CC 构建之后不得再执行会覆盖产物的 clean/build；验证期间发现的功能缺陷单独提交并重新冻结后续验证基线。

### 4.1 步骤 1：记录 P9 基线

记录以下信息，以便后续验证结果可追溯：

Windows 环境记录：

```bat
git rev-parse HEAD
git status --short
powershell.exe -NoProfile -Command "Get-FileHash -Algorithm SHA256 'SDK/apps/common/third_party_profile/rdx_protocol/librdxApp.a'"
```

同时保存：

- 当前提交 SHA。
- 工作区是否干净；若不干净，列出与 P9 无关的已有改动并避免覆盖。
- `librdxApp.a` SHA256。
- CC 目标板使用的产品档位、固件版本、烧录产物标识和回归日期。
- 生产工具链、make、编译器和 PowerShell 版本。

P9 不应依赖口头结论。已经完成的 CC 目标板回归必须整理为结构化记录，至少包含测试组合、步骤、预期、实际结果和日志/截图/视频索引。

### 4.2 步骤 2：执行零新增依赖的静态边界和配置矩阵

Windows 生产环境使用系统自带 PowerShell 5、现有 JL clang 和仓库内 `make.exe`：

```bat
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/check_rdx_boundaries.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/host/test_rdx_config_matrix.ps1 -Compiler C:\JL\pi32\bin\clang.exe -MakeCommand SDK\tools\utils\make.exe
```

非 Windows 宿主机不建立平行的 P9 配置矩阵环境；默认入口必须直接拒绝，而不是要求安装 Unix `pwsh`、系统 `make` 或原生 C 编译器。跨宿主机形式一致不属于 P9 验收目标。

执行结果必须记录实际命令、PowerShell 版本、JL clang 解析路径/版本、仓库 make 解析路径/版本和完整日志路径。脚本必须先验证编译器和 make 可执行，并验证编译器支持所需 C11 语法；工具无法启动属于基础设施错误，不能被负例当作“预期编译失败”。负例只有在退出码非 0 且输出命中该用例绑定的预期诊断时才能判为 PASS，不得将无关语法、文件或工具错误当作预期拒绝。

验收：

- 静态边界脚本全部 PASS，包含 P7 和 P8 规则。
- 配置矩阵全部 PASS。
- `zenchord_cc`、`zenchord_ep` 和全部 17 个产品配置头在 C 配置检查中保持可选择。
- 非法 APP、未知 DEVICE、多 APP、非法 APP/DEVICE、board 错配、内部变量覆盖、递归 Make 表达式和非法 chip family 均按预期失败。
- 命令行整体传入 `DEFINES=...` 时，最终预构建参数仍含档位 APP/DEVICE 宏。
- 全部必选检查不要求安装生产环境之外的 Host 编译器或脚本运行时。

### 4.3 步骤 3：执行静态契约门禁

Windows 环境执行：

```bat
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/host/test_rdx_static_library_abi.ps1 -BaselineRef 5d0284f17006bd333de992ed22d5a1c7484c37a0
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/host/test_rdx_record_recovery.ps1
```

这两个脚本是静态契约检查，不编译或执行生产固件。它们与步骤 2 一起组成 P9 的零新增依赖门禁，但不替代生产 clean build 或 CC 目标板验收。ABI 检查必须与固定的 P8 基线提交和 `librdxApp.a` SHA256 指纹比对；不得仅与浮动的 `HEAD` 比较，否则 ABI 改动一旦被提交就会失去检测能力。

验收：

- 静态库 ABI 和 `test_rdx_record_recovery.ps1` 均通过。
- 验证脚本自身对 PowerShell 版本、换行格式、工具启动或预期 stderr 处理错误造成的假失败必须修复并重新运行。
- 不得为了使门禁通过而安装额外 Host 编译器、TinyCC、MSYS2 或 Unix PowerShell。

`test_dispatch`、`test_event_bus`、`test_time_ops`、`test_board_config`、`test_util`、`test_time_service` 六个可执行 mock 继续保留。开发环境已经具有兼容的原生编译器时，可显式执行 `tests\host\run_tests.bat host_all HOST_CC=<existing-native-compiler>`；该目标只运行六个可选 mock，不再连带运行或代表配置矩阵。结果单独归档为补充证据。未运行或失败不得被写成 PASS，但缺少该额外编译器不阻塞 P9。

### 4.4 步骤 4：EP/shadow 隔离验证

EP/shadow 不进入硬件验收，但必须先于最终 CC 构建执行，避免后续 clean 或链接覆盖已归档的 CC 产物。Windows 生产构建通过环境变量选择档位后调用工程 wrapper：

```bat
cd SDK
call .vscode\winmk.bat clean
set RDX_PRODUCT=zenchord_ep
set RDX_CHIP_FAMILY=jl7018
call .vscode\winmk.bat
call .vscode\winmk.bat clean
set RDX_PRODUCT=zenchord_cc
set RDX_CHIP_FAMILY=jl7018_shadow
call .vscode\winmk.bat
```

在独立 `cmd.exe` 或构建脚本中执行上述命令，防止环境变量污染后续 CC 构建。若工程 wrapper 要求将变量作为 make 参数传入，应在归档中记录实际可复现命令；不得用 `make -n` 或仅执行 `rdx_config_check` 代替 clean build。

验收：

- 工具链可用时，两个组合均从 clean 状态构建 PASS。
- 只有正常生产构建本身所需的 JL 工具链、许可证或受控输入不可用时允许记为 `NOT RUN`，并记录命令、环境、完整错误和阻塞原因；P9 不引入其他工具弥补生产环境缺失。
- 源码、配置或构建脚本缺陷引起的失败不能以“已记录原因”关闭 P9。
- 无论结果如何，归档必须写明：EP/shadow 未进行目标板功能验证，不声明其硬件可用性。

禁止因没有 EP/shadow 实机而跳过步骤 2 的配置矩阵和静态边界检查。

### 4.5 步骤 5：最终 CC clean build 与产物固化

EP/shadow 检查完成后，清除其构建环境和产物，再执行本轮最后一次生产构建。Windows 环境使用真实生产 wrapper：

```bat
cd SDK
set RDX_PRODUCT=zenchord_cc
set RDX_CHIP_FAMILY=jl7018
call .vscode\winmk.bat clean
call .vscode\winmk.bat
```

构建完成后、任何其他 clean/build 之前立即固化：

```powershell
Get-FileHash -Algorithm SHA256 <firmware-path>
Get-FileHash -Algorithm SHA256 apps/common/third_party_profile/rdx_protocol/librdxApp.a
```

`<firmware-path>` 必须在实际执行时替换为构建日志报告的真实产物路径，并将完整命令写入归档。固件哈希使用 Windows PowerShell 5 自带的 `Get-FileHash`，不得为此引入 Unix `shasum` 或其他工具。不得以 `make -n` 代替真实编译。

验收：

- CC 从 clean 状态构建成功，且是 EP/shadow 之后的最终构建。
- 产物对应 `zenchord_cc + jl7018`，不存在错误选择 EP board 或 shadow port 的情况。
- map 不引用当前源码树不存在的 RDX board、port、service 或产品配置对象。
- 启动诊断可识别为 CC 对应 product、board、chip、SDK、transport、storage 和 RTC path。
- 在后续构建覆盖前记录固件路径、固件 SHA256、map 路径、构建日志路径及 RDX 相关 Flash/RAM/section 数据。
- `librdxApp.a` SHA256 与步骤 1 的 P9 基线一致。

### 4.6 步骤 6：建立 CC 固件与既有板测记录的证据关联

P9 是验证归档阶段，不无理由重复目标板测试，但最终 CC 产物必须与板测固件建立可验证的唯一标识关联：

```text
commit SHA
  -> RDX_PRODUCT / RDX_CHIP_FAMILY / APP / DEVICE / BOARD
  -> 完整构建日志
  -> 固件路径与 SHA256 / map
  -> 既有 CC 回归使用的固件版本或唯一标识
  -> CC 板号与目标板回归记录
```

步骤 5 的最终 CC clean build 用于建立可复查的当前构建基线。既有 CC 回归只有在其记录的固件 SHA256 或等价唯一标识能够对应最终 CC 产物时才可直接归档；仅有版本号、口头说明或提交号不足以证明产物一致。无法建立唯一标识关联时，必须将步骤 5 的最终 CC 固件重新烧录，并执行第 2.2 节目标板回归后才能关闭 P9。若验证期间修改了运行逻辑、产品参数或构建选择，同样必须针对最终固件重新执行受影响用例。

每个用例至少包含：

| 字段 | 要求 |
|---|---|
| 构建组合 | 固定为 `zenchord_cc + jl7018`，并记录 APP、DEVICE、BOARD。 |
| 固件标识 | 版本、构建时间、产物 SHA256 或其他唯一标识。 |
| 硬件信息 | 板号、硬件版本、必要外设或测试夹具信息。 |
| 测试步骤 | 可由其他开发者重复执行的操作步骤。 |
| 预期结果 | 明确可观察的正确行为。 |
| 实际结果 | PASS/FAIL，以及关键日志或现象。 |
| 证据索引 | 串口日志、APP 日志、截图、视频或测试记录路径。 |
| 异常说明 | 未覆盖项、环境限制或已知风险。 |

P9 的 CC 目标板结论只能写为“CC 主力产品目标板回归通过”。不得扩展为“全部 RDX 产品通过”或“EP/shadow 已通过”。

### 4.7 步骤 7：更新完成度与后续入口

更新 `docs/4.RDX框架重构进度与完成度评估.md`，使其不再保留 P8 已完成、CC 已目标板回归但未反映的历史状态。

更新原则：

- P8 标为静态重构、配置矩阵和 CC 主力产品目标板回归完成。
- P9 标为完成必须严格基于实际归档证据；零新增依赖必选门禁失败、EP/shadow 在生产工具链可用时未 PASS、ABI/record recovery 未 PASS，均不得勾选。可选 Host mock 的 `OPTIONAL NOT RUN` 不阻塞 P9。
- 目标板验收范围明确限定为 CC；EP/shadow 的硬件验证状态明确为“无实机，未验证”。
- 后续正式架构任务更新为 P10 Storage 持久化边界收口。

## 7. P10 预告：Storage 持久化边界收口

P9 闭环后，下一项架构重构定义为：

> P10：RDX Storage 持久化边界收口。直接复用现有 JL persistence port `port/jl/include/rdx_jl_storage.h`，将 `syscfg_read/write` 从业务 `.c` 迁入该 port，保持 VM ID、持久化格式、默认值、写入时机和 CC 行为不变。现有 `rdx_storage_service` 继续负责 SD/文件操作，不承载 VM 持久化。

P10 的推荐范围：

1. P10.0 先建立持久化契约表：逐项记录 VM ID、数据长度、默认值、缺失/短读策略、写入时机、调用者和 CC 板测用例。
2. P10.1 处理 `rdx_vm.c`、`rdx_rtc.c` 和 `rdx_dut.c`，统一通过 `rdx_jl_storage.h` 的固定长度读写契约访问 VM。
3. P10.2 单独处理 `rdx_record.c`，保持录音恢复、MIC gain 默认值和现有写后读回校验语义。
4. P10.3 最后处理 `rdx_ble_server.c` 的 BLE 名称、MAC 等敏感状态，并以配对、绑定、恢复出厂和重连回归验证。
5. 只允许 JL storage port 直接调用 `syscfg_*`；业务层通过稳定接口访问持久化能力。
6. 增加静态边界规则和 Host storage mock，覆盖正常读写、缺失、短读、长度错误、写入失败和默认值恢复。
7. `rdx_battery.c` 当前 `syscfg_*` 命中位于 `#if 0` 死代码，不为其新增迁移接口；若未来启用，再按实际契约单独纳入。

P10 的明确非目标：

- 不修改 `librdxApp.a`。
- 不修改协议 ABI 或旧外部符号。
- 不改变 VM ID、二进制布局或已有持久化数据兼容性。
- 不在同一阶段处理全量 OSAL、BLE/Record/Storage 深度解耦或 `rdx_app.c` 行数优化。
- 不要求 EP/shadow 目标板回归；仍按 P9 的支持分级执行。

P10 仅在 P9 已形成可信 CC 构建、map 和目标板回归基线后启动。这样每一次持久化边界迁移都可以以 CC 的绑定、BLE 名称、RTC、MIC gain、恢复出厂、DUT 和录音异常恢复进行实际回归。

## 8. 风险与控制

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 验收范围被误扩大 | 没有 EP/shadow 实机却声明所有档位功能通过 | 将支持分级和未验证结论写入 P9 归档与完成度文档。 |
| 验收范围被误缩小 | 因无实机而取消 EP/shadow 配置门禁 | 保留配置矩阵和工具链可用时的 clean build 检查。 |

| 旧对象污染构建 | 未 clean 的 `.o` 或 map 掩盖构建选择问题 | CC 必须从 clean 状态构建；记录产物和 map 路径。 |

| P9 范围膨胀 | 验证时混入 Storage、OSAL 或 BLE 重构 | 缺陷单独立项；P9 只修验证脚本、归档或构建门禁本身的问题。 |
| 静态库边界被意外改变 | 为解决构建问题修改 archive 或 ABI | 固定 SHA256、执行 ABI 检查，禁止修改 `librdxApp.a`。 |
| 后续无体积参照 | P10 改动后无法判断 Flash/RAM 变化 | 将 CC map/section 数据归档为后续增量基线。 |
