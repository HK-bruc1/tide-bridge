# RDX 框架 JL 平台复用性评估

> 评估视角：RDX 框架的目标不是跨 STM32、ESP32、Zephyr、FreeRTOS 等异构生态，而是在 **JL 平台内的多型号芯片、多板型、多产品形态** 之间复用。本文借鉴《嵌入式跨平台设计模式》的思想，但不以通用跨 RTOS/跨 MCU 框架作为评价标准。

## 1. 评估结论

当前 RDX 更准确的定位是：

> **面向 JL SDK 的产品协议与业务集成框架，适合在 JL 同平台、多型号芯片、多产品形态之间复用；但尚未形成清晰的 JL 平台内 port/board/module 分层。**

如果目标是“只支持 JL 平台”，当前大量使用 JL SDK API 并不是根本问题。真正的问题是：**JL 相关依赖没有被集中收口，业务、板级、芯片差异、协议、存储、BLE、录音和电源管理交织在同一批模块里**。这会让同平台复用仍然变重，尤其在换芯片、换板型、换外设组合、换 SDK 版本时，改动会扩散。

### 1.1 评分标准（Rubric）

本报告评分按 1–10 分级，含义如下：

| 分数段 | 含义 |
|---:|---|
| 1–2 | 完全缺失或严重阻碍复用 |
| 3–4 | 有初步结构但不成体系，改动明显扩散 |
| 5–6 | 基本可用但维护成本高，边界时有模糊 |
| 7–8 | 结构良好、边界清晰，复用成本可控 |
| 9–10 | 理想状态，新增产品/芯片/板型几乎零侵入 |

### 1.2 综合评分

| 维度 | 评分 | 结论 |
|---|---:|---|
| JL 平台内产品复用 | 6/10 | 已有产品宏和模块拆分，能支撑多个客户/产品，但配置和业务差异集中在大宏表中，后续维护压力会增长。 |
| JL 多芯片复用 | 4/10 | 目前芯片、GPIO、SPI、RTC、低功耗差异没有独立 board/port 层，换芯片时容易修改业务模块。 |
| 模块化 | 4/10 | 文件按功能拆分，但模块之间大量直接互调，公共头暴露平台类型，边界不够硬。 |
| 协议层抽象 | 6/10 | `RdxProtocolCallbacks` / `RdxProtocolIndicateOps` 是正确方向，已经具备 vtable 思路。 |
| 板级抽象 | 3/10 | 引脚、电源、SPI、WiFi 模块控制多处硬编码，尚未形成统一 board config。 |
| 可测试性 | 3/10 | 强依赖 JL OS、任务队列、BLE 栈、syscfg 和静态库，难以做 PC 端或 host mock 测试。 |
| 生命周期管理 | 4/10 | 有部分 init/deinit，但任务、定时器、mutex、buffer 的归属和释放语义不完全统一。 |

## 2. 适用边界

本评估建议按以下边界理解 RDX：

- **支持范围**：JL 平台内的多个芯片型号、多个板型、耳机/充电仓/录音卡片/AI 录音设备等产品形态。
- **不作为目标**：把 RDX 直接移植到 STM32、ESP-IDF、Zephyr、Linux host 等非 JL 生态。
- **可借鉴目标**：用跨平台设计模式中的“隔离变化点”思想，把 JL 平台内的变化点收口到明确位置。

因此，评价重点不是“代码里有没有 JL API”，而是：

1. JL API 是否集中在 port/board 层。
2. 产品差异是否通过配置注入，而不是散落在业务逻辑中。
3. 上层协议和业务是否能在不同 JL 芯片/板型上少改或不改。
4. 外设差异是否通过小型 wrapper/vtable 屏蔽。

## 4. 从设计模式角度评估

### 4.1 条件编译

当前大量使用 `RDX_AI_SEL_APP`、`RDX_SEL_DEVICE`、`RDX_PRODUCT_IS_CHARGE_CASE`、`TCFG_*`、`RDX_MULTI_FUNC_INTERFACE` 等宏。

在 JL 平台内，这种方式是合理的第一阶段选择：

- 零运行时开销。
- 适合资源受限固件。
- 适合客户/产品线快速切换。

但当前风险是宏分散在 `rdx_app.c`、`rdx_record.c`、`rdx_charge.c`、`rdx_vm.c`、`rdx_ble_server.c` 等多个业务模块中。随着 JL 芯片型号和板型增加，容易变成“同平台内的 `#ifdef` 地狱”。

建议保留条件编译，但把它限制在：

- 产品配置头。
- board 配置头。
- port 实现文件。

业务模块中应尽量减少产品/芯片宏判断。

### 4.2 Wrapper 二次封装

RDX 已经有一些 wrapper 倾向，例如 `rdx_ble_server_*`、`rdx_spi_*`、`rdx_vm_*`、`rdx_rtc_*`。但 wrapper 的边界还不稳定。

主要问题：

- `rdx_spi.c` 既做 SPI 寄存器/驱动调用，也做协议传输、任务队列、WiFi 数据触发。
- `rdx_ble_server.c` 既做 BLE server，也反向调用录音、文件同步、协议状态清理。
- `rdx_vm.c` 既做 syscfg 读写，也执行解绑、恢复出厂、TWS 删除、BLE 断开、文件格式化。

建议在 JL 平台内采用更薄的 wrapper：

```c
rdx_jl_os_post_msg(...)
rdx_jl_timer_start(...)
rdx_jl_ble_send(...)
rdx_jl_syscfg_read(...)
rdx_jl_gpio_set(...)
rdx_jl_spi_transfer(...)
```

上层业务只调用 `rdx_*` 命名空间，不直接触碰 JL SDK API。这样即使仍然只支持 JL，换 SDK 版本或芯片外设 API 时也能集中修改。

### 4.3 vtable 合约

`rdx_protocol.h` 中已有 `RdxProtocolCallbacks` 和 `RdxProtocolIndicateOps`，这是当前框架里最接近跨平台思想的部分。

这类设计适合继续扩大，但要避免一个巨大 vtable 管全部能力。更适合拆成小合约：

```c
typedef struct {
    int (*send)(const u8 *data, u32 len);
    int (*is_ready)(void);
    u16 (*get_mtu)(void);
} rdx_ble_transport_ops_t;

typedef struct {
    int (*raw_write)(const u8 *data, u32 len, u8 scene);
    int (*raw_read)(u32 offset, u8 *data, u32 len);
    int (*format)(void *cb);
} rdx_storage_ops_t;

typedef struct {
    int (*set_time)(u32 timestamp);
    u32 (*get_time)(void);
} rdx_time_ops_t;
```

对 JL 多芯片复用来说，vtable 的价值不是运行时动态换平台，而是把“需要替换的东西”明确列出来。即使最终只有一个 JL 实现，也能形成清晰边界。

### 4.4 OSAL 适配

当前 RDX 公共头直接暴露了 `OS_SEM`、`OS_MUTEX`、`cbuffer_t` 等 JL/SDK 类型。对“只支持 JL”来说这可以编译通过，但会削弱模块边界。

建议做一个轻量 JL OSAL，不追求跨 RTOS，只追求隔离 JL OS API：

```c
typedef void *rdx_mutex_t;
typedef void *rdx_sem_t;

int rdx_os_mutex_create(rdx_mutex_t *m);
int rdx_os_mutex_lock(rdx_mutex_t *m, u32 timeout);
int rdx_os_mutex_unlock(rdx_mutex_t *m);
int rdx_os_task_create(...);
int rdx_os_task_post(...);
u32 rdx_os_time_ms(void);
```

这样做的好处：

- JL SDK API 变化时，上层不用动。
- mock 测试更容易。
- 模块头文件更干净。
- 任务、timer、mutex 生命周期可以统一约束。

### 4.5 HAL/Board 分层

当前最大短板是 board/chip 差异没有独立层。例如：

- SPI 引脚和 WiFi 电源脚硬编码。
- `CHIP_TYPE` 在 `rdx_spi.h` 中固定。
- `VDD_POWER_PORT_IO`、`LED_PT0807_DATA_PORT_IO` 放在 `rdx_app.h`。
- `WIFI_POWER_ON/OFF` 放在 `xxpUart.h`。

对 JL 平台内多芯片复用，最应该引入的是 **Board Abstraction Layer**，而不是完整跨平台 HAL。

建议形成：

```text
rdx/
  core/                 # 协议、状态机、纯业务
  service/              # record、ble service、storage service
  port/jl/              # JL OS/BLE/SPI/syscfg/timer wrapper
  board/t2616_cc/       # 当前板型引脚和外设配置
  board/xxx_ep/         # 其它 JL 板型
  config/product/       # 客户/产品配置
```

其中 board 层提供：

```c
typedef struct {
    u32 wifi_power_io;
    u32 spi_cs_io;
    u32 spi_clk_io;
    u32 spi_mosi_io;
    u32 spi_handshake_io;
    u32 led_data_io;
    u8  spi_port;
    u32 spi_clk_hz;
} rdx_board_config_t;

const rdx_board_config_t *rdx_board_get_config(void);
```

这样换 JL 芯片或换 PCB 时，主要改 board 文件，不改协议和业务。

### 4.6 推荐设计模式组合

结合“只支持 JL 平台”的前提，推荐组合如下：

| 位置 | 推荐模式 | 原因 |
|---|---|---|
| 产品/能力裁剪 | 条件编译 | JL 固件资源敏感，编译期裁剪合理。 |
| JL SDK API 调用 | Wrapper | 屏蔽 SDK 版本和芯片 API 差异。 |
| BLE/Storage/RTC/SPI | 小 vtable | 让依赖显式化，方便替换和 mock。 |
| OS/Timer/Task | 轻量 OSAL | 不追求跨 RTOS，只隔离 JL OS 原语。 |
| GPIO/电源/外设引脚 | Board config | 换板型时不改业务。 |
| 产品特化钩子 | 弱符号/弱默认实现 | 适合 LED、马达、DUT、调试等可选行为，不承载核心协议流程。 |
| 重型平台级代码生成 | 暂不建议 | 对当前 JL 内部复用来说过重，先做配置拆分和编译期校验。 |

## 5. 当前复用风险

### 5.1 `rdx_app.c` 过度中心化

`rdx_app.c` 承担了协议事件处理、WiFi 控制、录音调度、BLE 状态、电源、低功耗、SD 电源、DUT、LED 等职责。它现在更像“产品 main controller”，而不是可复用框架层。

风险：

- 新产品功能变化时容易继续往里面加分支。
- 业务规则和板级动作混在一起。
- 很难单独验证协议事件到业务动作的映射。

建议把 `rdx_app_protocol_handle()` 拆成面向 service 的 dispatch：

```text
protocol event
  -> rdx_command_dispatch
      -> rdx_record_service
      -> rdx_storage_service
      -> rdx_ble_service
      -> rdx_device_service
```

### 5.2 公共头暴露平台类型

公共头中出现 `OS_MUTEX`、`OS_SEM`、`cbuffer_t`、`IO_PORT*`、`APP_MSG_*`，说明模块消费者必须理解 JL SDK 内部类型。

如果目标是 JL 多芯片复用，这也会带来问题：不同 JL SDK 版本或芯片线可能对 OS、BLE、低功耗、GPIO 宏有差异。

建议规则：

- `rdx_core/*.h` 不包含 JL SDK 头。
- `rdx_service/*.h` 尽量只暴露 RDX 自己的类型。
- JL 类型只允许出现在 `port/jl` 和 `board/*`。

### 5.3 配置宏表过大

`rdx_app_config.h` 把客户、产品、型号、版本、WiFi、能力开关集中在一个文件中。短期很方便，但长期容易出现：

- 一个客户改动影响另一个客户。
- 产品能力和板级能力混在一起。
- 编译配置不可追踪。
- 新型号加入时需要理解整个宏矩阵。

建议拆为三层：

```text
product_config      # 客户/产品/协议能力/名称/版本
board_config        # 引脚/外设/电源/存储/LED/RTC
build_config        # 是否启用 BLE、TWS、UUX_FILE、调试日志等
```

### 5.4 静态库边界不透明

`librdxApp.a` 中承载了协议和文件相关核心实现。对商业交付来说这是可以接受的，但对框架演进要注意：

- 头文件已经暴露很多内部状态，说明库边界不是纯黑盒。
- 如果库和源码互相回调过多，问题定位会困难。
- 业务层很难 mock 静态库内部行为。

建议把静态库当作 third-party core，只通过窄接口访问：

- 输入：packet recv、product config、transport ops。
- 输出：protocol event、send request、storage request。
- 禁止静态库直接依赖产品宏和板级宏。

### 5.5 不改进的代价（场景推演）

若维持当前架构，以下两类变更的成本会快速上升：

**场景 A：新增一颗 JL 芯片（如从 JL7018 切换到下一代芯片）**

- 当前 `CHIP_TYPE` 硬编码在 `rdx_spi.h`，SPI cs/clk/mosi/hold 等引脚宏散落在 `rdx_spi.c` 中。
- 低功耗、RTC、GPIO 初始化逻辑在 `rdx_app.c`、`rdx_charge.c`、`rdx_rtc.c` 中直接调用 JL API。
- 预估影响面：至少 5 个业务模块需要同步修改，约 200+ 行代码需要逐行核对引脚和寄存器差异。
- 风险：改动容易遗漏，回归测试只能依赖真机，问题定位周期长。

**场景 B：新增一个客户产品（基于现有 T2616 芯片但板型不同）**

- 当前新增客户需要在 `rdx_app_config.h` 中复制一个完整的 `#elif` 块，重新定义 BT name、factory code、product code、WiFi SSID、版本号等。
- 如果该客户板型引脚不同，还需要修改 `rdx_app.c`、`rdx_app.h`、`rdx_charge.c`、`rdx_dut.c` 中的 `VDD_POWER_PORT_IO`、`LED_PT0807_DATA_PORT_IO` 等硬编码。
- 预估影响面：配置层 50+ 行新增，业务层 10–30 处引脚/电源相关改动。
- 风险：客户配置与板级代码耦合，容易因引脚错误导致硬件损坏或功能异常。

## 6. 建议目标架构

建议 RDX 在 JL 平台内演进为以下结构：

```text
RDX Application
    |
    v
RDX Service Layer
    |-- record service
    |-- ble service
    |-- storage service
    |-- device service
    |-- wifi service
    |
    v
RDX Core
    |-- protocol parse/encode
    |-- command dispatch
    |-- state machine
    |-- common util
    |
    v
RDX JL Port
    |-- os/timer/task wrapper
    |-- ble wrapper
    |-- syscfg/vm wrapper
    |-- spi wrapper
    |-- rtc wrapper
    |
    v
RDX Board Config
    |-- T2616_CC
    |-- other JL chip/board variants
```

核心原则：

1. **业务层不直接碰 JL SDK API**，统一经 `rdx_jl_*` wrapper。
2. **协议层不直接碰板级能力**，板级能力通过 config/ops 注入。
3. **板级差异不进入业务 ifdef**，放到 `board/*`。
4. **产品差异优先配置化**，确实需要编译裁剪时再用宏。
5. **vtable 拆小**，避免一个大 ops 塞几十个函数。

## 7. 分阶段改进建议

### 阶段 1：低风险收口

**目标**：不大改行为，只把变化点集中。

**任务**：

- 新增 `rdx_board_config.h/c`，先搬迁 WiFi 电源脚、SPI 引脚、LED 引脚、VDD 电源脚。
- 新增 `rdx_jl_osal.h/c`，封装 `os_task_create`、`os_taskq_post_msg`、`sys_timeout_add/del`、`os_mutex_*`。
- 新增 `rdx_jl_storage.h/c`，封装 `syscfg_read/write` 和关键 VM ID 访问。
- 对 `rdx_spi.c` 先做参数化，不再在 `.c/.h` 中写死 `CHIP_TYPE` 和固定 IO。
- 对 APP/DEVICE/BOARD 组合增加 `_Static_assert` 或等价编译期校验，避免非法组合静默编译通过。
- 对 `RdxProtocolIndicateOps` 增加启动校验和安全调用封装，关键函数为空时给出明确诊断。
- 不动 `librdxApp.a`，只保护它的调用边界。

**工作量估算**：约 1–2 人周。

**风险与缓解**：

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 封装 wrapper 增加代码体积 | JL 芯片资源敏感 | 使用 `static inline` 或宏封装，确保无额外运行时开销；阶段 1 结束后做一次 size diff。 |
| 搬迁引脚映射出错 | 硬件损坏或功能异常 | 保留旧宏作为别名过渡；在 board config 中增加引脚合法性自检；上电打印 board config。 |
| OSAL 抽象与现有 JL API 语义不完全对齐 | 任务优先级、timeout 单位不一致 | 先映射再抽象，明确 timeout 单位（ms），并补充单元测试。 |

### 阶段 2：服务层拆分

**目标**：降低 `rdx_app.c` 的中心化。

**任务**：

- 把 `rdx_app_protocol_handle()` 中的 record/storage/device/rtc/name/offtime 分发拆成独立 service。
- 把 WiFi 控制从 `rdx_app.c` 独立为 `rdx_wifi_service.c`，保留现有 `rdx_wifi_event` 思路。
- 把恢复出厂/解绑流程从 `rdx_vm.c` 中拆出 `rdx_device_service.c`，`rdx_vm` 只做持久化。
- BLE 只负责连接、广播、收发，不直接清理文件同步和录音状态。

**工作量估算**：约 2–3 人周。

**风险与缓解**：

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 拆分后行为不一致 | 回归测试困难 | 先提取接口，保持原实现不变；通过对比反汇编/符号表确认调用关系一致；再逐步迁移逻辑。 |
| 静态库 `librdxApp.a` 内部可能直接调用 `rdx_app.c` 符号 | 拆出 service 后链接失败 | 阶段 2 开始前先做符号依赖分析，确认静态库导出的未解析符号。 |
| 消息分发增加一次间接调用 | 录音/WiFi 热点路径延迟微增 | 对热点路径保留直接函数指针 dispatch，普通事件走统一 service dispatch。 |

### 阶段 3：JL 多芯片适配

**目标**：新增 JL 芯片/板型时不改 core/service。

**任务**：

- 每个板型一个 `board/<name>/rdx_board_config.c`。
- 每个芯片族一个 `port/jl/<chip_family>/`，处理 SPI、RTC、低功耗等差异。
- Makefile 按板型选择 board 源文件。
- 建立最小编译矩阵：当前 T2616_CC + 一个模拟新板型配置。

**工作量估算**：约 3–4 人周（含一个新板型的验证）。

**风险与缓解**：

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 新芯片 SDK API 差异大于预期 | port 层工作量膨胀 | 阶段 3 开始前做 API diff，列出必须抽象的调用点；不要一次性支持所有芯片族。 |
| 不同芯片的启动顺序/低功耗行为不同 | 同一业务代码在芯片 A 正常，芯片 B 异常 | 在 port 层提供统一的生命周期钩子（pre_sleep/post_wakeup），业务代码只调用钩子。 |
| Makefile 板型切换引入构建错误 | 多人协作时配置混乱 | 增加编译期 `RDX_BOARD_*` 宏和启动自检日志。 |

### 阶段 4：测试与诊断

**目标**：让复用修改可验证。

**任务**：

- 给 `rdx_util`、RTC 纯函数、协议事件 dispatch 做 host mock 测试。
- 给 product/board/build 配置做组合校验，至少覆盖当前主力 APP 和设备型号。
- 给 board config 增加启动日志，打印当前 product、board、chip、SDK 版本。
- 对 vtable/ops 增加启动校验，关键函数为空时直接报错。
- 给 BLE/SPI/storage 增加统一错误码，减少 `-1` 泛化错误。

**工作量估算**：约 2–3 人周。

**风险与缓解**：

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| host mock 无法覆盖 JL 特有行为 | 测试信心不足 | mock 聚焦纯函数和 dispatch；对依赖 JL 栈的部分保留真机冒烟测试。 |
| 配置组合爆炸 | 校验用例维护成本高 | 优先覆盖当前主力组合，后续新增产品时必须补充对应用例。 |
| 统一错误码改动面大 | 现有 `if (ret < 0)` 判断需要批量调整 | 先定义枚举，再逐模块替换；保留 `-1` 兼容层过渡。 |

## 8. 重点整改清单

优先级从高到低：

1. 建立 `rdx_board_config`，搬走所有硬编码引脚和板级常量。
2. 建立 `rdx_jl_osal`，公共头不再直接暴露 `OS_SEM`、`OS_MUTEX`。
3. 把 `rdx_app_config.h` 拆为 product/board/build 三层。
4. 增加 APP/DEVICE/BOARD 编译期校验，防止非法产品组合进入运行期。
5. 给 `RdxProtocolIndicateOps` 增加 validate/safe-call 机制，并逐步拆成小 ops。
6. 把 `rdx_app_protocol_handle()` 拆到 command/service dispatch。
7. 把 `rdx_vm` 从“持久化 + 恢复出厂动作”拆成“VM 仓储层 + device service”。
8. 把 `rdx_spi` 定位为 transport port，协议和文件状态清理不要放在 SPI 驱动里。
9. 给 `librdxApp.a` 外围接口写清楚 contract，避免静态库和业务源码双向深耦合。
10. 增加启动诊断日志：product、board、chip、transport、storage、RTC path。

## 9. 最终评价

RDX 当前不是一个“跨平台框架”，但在“JL 平台内复用”这个目标下，它有可继续演进的基础：

- 协议回调/vtable 思路已经出现。
- 产品配置集中，便于快速派生。
- 录音、BLE、RTC、SPI、VM 等模块已经按文件拆分。
- WiFi 事件总线已经开始做域内解耦。

真正需要提升的是 **边界纪律**：

- JL API 可以用，但要集中用。
- 宏可以用，但要限制位置。
- 静态库可以保留，但接口要窄。
- 模块可以互相协作，但不要随意 `extern` 互调。

如果按本文建议做 1 到 2 个阶段的收口，RDX 可以从“能复用的产品集成代码”提升为“JL 平台内可维护、可扩展、可验证的产品框架”。
