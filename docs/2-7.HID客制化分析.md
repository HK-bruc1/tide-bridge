# 2-7. HID 客制化分析

本文面向刚接触 HID 和键盘客制化的读者，从 HID 的用途讲起，再说明实体按键、键值、快捷键与业务功能的关系，最后结合我们的五键设备说明推荐方案。

## 1. HID 不只是键盘，而是一套设备与主机交互的规范

### 1.1 先纠正一个容易出现的误区

**HID 不等于键盘，HID 键盘只是 HID 设备中的一种。**

HID 是 Human Interface Device 的缩写，通常译为“人机接口设备”。从 PC 的角度，可以把 HID 规范理解为：**电脑与外部人机交互设备之间，用来描述设备能力、交换输入和控制数据的一套共同规则。**

它也不限于 PC。手机、平板和其他支持相应 HID 协议的主机，同样可以接收 HID 设备的数据。HID 的用途已扩展到部分传感器等设备，并不要求每一项数据都由用户按键直接产生。

| HID 可以描述的设备 | 典型交互内容 |
|---|---|
| 键盘 | 哪些键正在按下、修饰键状态、键盘指示灯状态 |
| 鼠标 | 移动量、鼠标按键、滚轮变化 |
| 游戏控制器 | 按钮、摇杆、扳机等状态 |
| 触摸屏、数位笔 | 触点位置、接触状态、笔压等 |
| 多媒体控制设备 | 音量、静音、播放／暂停等控制 |
| 部分传感器设备 | 按相应 HID 定义描述和上报传感器数据 |

因此，一个设备支持 HID，并不表示它必须是一把键盘。我们的产品虽然只有几个按键，也可以将这部分能力作为 HID 键盘提供给电脑。

### 1.2 为什么使用同一套规范

如果每个厂商都用自己的方式表示“按下 A”“鼠标向右移动”，电脑就需要逐一学习每个产品的协议。HID 通过统一的描述和数据规则，让主机知道收到的是什么数据。

对于受操作系统支持的标准 HID 键盘、鼠标等功能，通常可以使用系统自带驱动，无需安装厂商驱动才能完成基本输入。这里的“免驱”是指**不需要用户另装驱动，系统仍然有驱动在工作**。

私有功能则不同：系统能够接收厂商自定义 HID 数据，不代表它知道这些数据对应“启动翻译”还是“切换某种模式”，这仍需要配套软件解释。

### 1.3 HID 和 USB、蓝牙是什么关系

HID 描述“数据代表什么、如何组织”，USB 或蓝牙提供相应的连接和传输方式。**不同传输方式有各自的 HID 协议约定，但可以表达相同的标准键盘按键**。

| 常见方式 | 如何理解 |
|---|---|
| USB HID | 通过 USB 连接传输 HID 数据 |
| 经典蓝牙 HID | 通过经典蓝牙的 HID 协议传输 |
| BLE HOGP | 通过低功耗蓝牙的 GATT 服务传输 HID 数据 |

我们的键盘扩展采用 HOGP，即 HID over GATT Profile。它让电脑通过 BLE 接收键盘输入；对 APP 的普通快捷键逻辑来说，通常仍然表现为操作系统提供的键盘事件。

下文重点讨论 HID 中的键盘部分，不展开鼠标、传感器等设备的具体协议。

## 2. 先区分三个概念：实体键、键值、功能

理解键盘时，先把下面三件事分开：

| 概念 | 是什么 | 例子 |
|---|---|---|
| 实体键 | 手指按下的物理按键 | 键盘上的 C 键、设备上的 KEY1 |
| 键值 | 设备告诉电脑“哪个键按下或松开了”的标准编号 | C、F1、F13 等键对应的 HID Usage |
| 功能 | 电脑或设备收到按键后执行的操作 | 复制、截图、开始翻译 |

HID 定义了标准键值的含义，但键值不等于业务功能。例如，Ctrl+C 表示 Ctrl 与 C 的组合，具体是复制还是中断程序，**要由电脑根据当前环境解释**。

```text
按下实体键 → 设备上报 HID 按键报告 → 操作系统识别和分发 → 系统或 APP 执行功能
```

### 2.1 键值不是字符，也不是业务命令

例如，按下字母键后，**设备上报相应的键盘 Usage**，而不是直接发送一个 Unicode 字符。**最终输入小写、大写，或者参与中文输入，由键盘布局、Shift／Caps Lock 状态和输入法共同决定。**

同样，Ctrl+C 通常也不是一个叫“复制”的 HID 命令。设备表达的是 Ctrl 和 C 同时处于按下状态，电脑再决定这组按键的用途。

这也解释了为什么同一个物理按键可以被重新映射：键帽上印着什么、固件发送哪个键值、软件执行什么功能，是三个不同层面的事情。

### 2.2 主机怎样知道报告里的数字是什么意思

HID 设备会提供报告描述符，可以把它理解为“这台设备的数据格式说明书”。它告诉主机，后续报告中的哪些字段是键盘按键、鼠标移动量或其他数据。在 HOGP 中，这份描述通过 Report Map 提供。

两个术语只需先记住它们的关系：

| 术语 | 含义 | 键盘相关例子 |
|---|---|---|
| Usage Page（用途页） | 一组用途的分类 | Keyboard/Keypad 页为 `0x07`，Consumer 页为 `0x0C` |
| Usage（用途） | 该分类下某一项的编号 | Keyboard/Keypad 页中的 F13 为 `0x68` |

**编号需要结合用途页和报告格式解释。** 不能把多媒体功能的编号直接放进普通键盘报告，就期待电脑自动识别为音量或播放功能。

### 2.3 上报还包括按住和松开

键盘输入不仅需要告诉电脑“按了哪个键”，还需要正确表达按住和松开。以 F13 为例，按下时报告包含 F13，松开后报告不再包含 F13；电脑据此产生相应的按键事件。

如果设备只报告按下却不正确释放，主机可能认为按键一直被按住。长按是否重复触发，还与系统和 APP 的处理方式有关。因此，固件虽然不理解业务语义，仍需要管理正确的按键状态。

## 3. HID 键盘有哪些键，厂商必须全部提供吗

### 3.1 常见按键类别

| 类别 | 常见按键 | 说明 |
|---|---|---|
| 字母、数字和符号 | A～Z、0～9、标点符号 | 最终输入的字符受键盘布局和输入法影响 |
| 基本控制键 | Enter、Escape、Backspace、Tab、Space | 输入、取消、删除等常用操作 |
| 修饰键 | 左右 Ctrl、Shift、Alt、GUI | 常与其他键组合；GUI 通常对应 Windows 键或 Command 键 |
| 功能键 | F1～F24 | 都有标准键值，常见键盘通常只提供 F1～F12 |
| 编辑和导航键 | Insert、Delete、Home、End、Page Up、Page Down、方向键 | 编辑和光标移动 |
| 数字小键盘 | 小键盘数字、加减乘除、Enter、Num Lock | 小键盘数字与主键区数字有不同的标准编号 |
| 其他标准键 | Caps Lock、Print Screen、Scroll Lock、Pause、国际／语言键等 | 按产品用途选用 |

**键盘产品还常提供音量、静音、播放／暂停、亮度等功能。这些通常使用 HID 的 Consumer Control（消费类控制）定义，与普通键盘键值属于不同类别。**

电脑也可以向键盘发送状态，例如控制 Caps Lock、Num Lock 指示灯；产品是否提供这些灯，由厂商决定。

### 3.2 不要求实现全部键值

**厂商不必实现 HID 键盘规范中的全部键值，也不必提供一套完整实体按键。** 84 键、87 键、98 键、104 键键盘，以及我们的五键设备，都可以遵循同一套 HID 键盘标准。

这些键数表示产品的按键数量和布局，不是不同的 HID 键值标准。没有独立实体键的功能，可以通过 Fn 组合实现，也可以不提供。

| 可以由厂商决定 | 必须遵循标准的部分 |
|---|---|
| 实体键的数量、位置、外观 | 所使用的标准键值及报告格式 |
| 一个实体键发送 F13、Enter 还是组合键 | 发送 F13 时，主机将其识别为 F13 |
| APP 收到 F13 后执行什么功能 | 通用键盘驱动不会自动把 F13 理解为“开始翻译” |

### 3.3 F1～F12 上的音量、亮度图案是什么

这些图案通常表示同一个实体键的另一种功能。通过 Fn 或 Fn Lock，同一个键可以发送普通 F 键，也可以发送图案对应的功能，例如 F2 或音量降低。

音量、静音、播放等通常已有标准 HID 定义，厂商主要决定将它们放在哪个实体键上。专属功能可能由配套软件处理；键盘灯效也可能由键盘内部直接处理。**键帽上有厂商安排的图案，不代表它使用的是厂商私有键值。**

**Fn 通常由键盘内部处理，用来选择另一层映射，不一定像 Ctrl、Shift 那样作为普通修饰键上报。例如，按 Fn+F2 后，电脑可能只收到“音量降低”，并不知道用户在键盘上按了 Fn。具体行为由产品设计决定。**

## 4. 按键功能由 Windows 决定，还是 APP 决定

### 4.1 系统和 APP 都可以处理按键

**键盘负责上报，操作系统负责识别和分发，系统或 APP 根据当前环境决定功能。**

| 按键与使用环境 | 常见功能 | 处理方 |
|---|---|---|
| 编辑器中的 Ctrl+C | 复制选中文字 | 编辑器 |
| 文件管理器中的 Ctrl+C | 复制选中文件 | 文件管理器 |
| 终端中的 Ctrl+C | 中断当前程序 | 终端及相关程序 |
| Windows 中的 Win+Shift+S | 调用系统截图功能 | Windows 系统组件 |

Win+Shift+S 不需要另外运行第三方 APP，但背后仍然有系统软件负责处理。没有系统或软件处理的按键，可能没有任何可见效果。

### 4.2 APP 的快捷键是怎么实现的

编辑器通过 Ctrl+S 保存文件，录屏软件通过用户设置的快捷键开始录制，都是 APP 接收按键后执行功能的例子。

**PC APP 可以监听设备上报的按键。** **普通快捷键通常接收的是操作系统转换后的键盘事件或快捷键通知**，不需要直接解析底层 HID 报告。

- 窗口内快捷键：通常在该窗口获得焦点时生效。
- 全局快捷键：APP 可以通过系统机制注册，让快捷键在 APP 位于后台时也能生效，但需要注册成功并处理冲突。

假设 APP 将 Ctrl+C 绑定为“开始翻译”：负责处理的 APP 或后台服务运行、绑定生效时，才可以执行翻译。它退出、绑定失效后，Ctrl+C 按系统和当前窗口原有的规则处理。

**这不是自动回退到一个统一的“系统默认功能”。** 在编辑器里可能复制，在终端里可能中断，也可能没有效果。关闭 APP 窗口也不一定代表后台服务已经退出。

### 4.3 系统和 APP 使用同一个快捷键，会一起触发吗

不一定。**APP 在前台不代表优先于系统，也不保证两个功能同时触发。** 例如，APP 尝试使用 Win+Shift+S 时，结果取决于监听方式和系统规则：

| APP 的方式 | 可能结果 |
|---|---|
| 接收普通窗口键盘事件 | 系统处理快捷键，APP 可能收不到完整组合 |
| 注册全局快捷键 | 组合键被系统保留或已经占用，注册可能失败 |
| 使用键盘钩子观察并放行事件 | 若能收到相关事件，APP 和系统功能可能同时触发 |
| 使用键盘钩子尝试拦截事件 | 对允许拦截的按键，可能只触发 APP 功能 |

键盘钩子可以理解为在按键事件传递过程中观察或尝试拦截事件的机制。它不能保证覆盖所有系统快捷键，上表也不表示 Win+Shift+S 在所有环境下都能被拦截。

设计自己的快捷键时，应避开常用系统组合键，而不是依赖拦截来争夺它们。

## 5. 行业内常见的客制化方式

“客制化”表示按产品或用户需要改变按键行为。它可以在键盘端实现，也可以在电脑端实现，常见方式可以组合使用。

| 方式 | 例子 | 功能主要在哪里执行 |
|---|---|---|
| 修改实体键到标准键值的映射 | 将某个键设置为 Enter 或 Ctrl+C | 键盘上报映射后的键值，电脑按原有规则处理 |
| 标准键值绑定 APP 功能 | 上报 F13，APP 收到后开始翻译 | PC APP 或后台服务 |
| 厂商私有 HID 报告 | 专属功能键发送厂商约定的数据，由配套软件解释 | PC 配套软件 |
| 键盘内部功能或板载宏 | 切换灯效，或按一次键发送预设的按键序列 | 键盘固件；序列中的按键仍由电脑解释 |

### 5.1 用具体例子区分四种方式

**方式一：修改按键映射。** 用户把设备 KEY1 设置成 Ctrl+C，设备按下时就报告 Ctrl 与 C。复制动作仍由当前编辑器或文件管理器处理。如果映射已经保存在设备中，之后通常不需要配置软件持续运行，但当前软件仍需支持这个快捷键。

**方式二：用标准键值触发自己的 APP。** 用户把 KEY1 设置为 F13，翻译 APP 监听 F13 后开始翻译。这时 F13 是触发信号，“翻译”由 APP 实现。负责监听的软件没有运行，翻译就不会发生。这最符合我们当前的需求。

**方式三：发送厂商私有报告。** 设备与配套软件约定一个私有事件，例如“专属键 1 按下”。配套软件读取这个事件，再执行功能。这个事件不必成为普通键盘的 F13 或 Ctrl+C，因此通常不会进入普通快捷键处理流程，但需要设备与软件共同实现私有协议。

**方式四：设备内部执行。** 按键直接切换键盘灯效，或者让固件按顺序发送一组按键。后者称为板载宏；宏的执行在设备内，但它发送的按键产生什么效果，仍取决于电脑端当前环境。能否保存和执行这类配置，要看具体产品的板载能力。

### 5.2 厂商的“专属驱动应用”也算 APP 吗

算电脑端配套软件。例如，部分罗技、雷蛇键盘支持通过 Logitech G HUB、Razer Synapse 等软件配置可编程键，让它启动应用或执行宏。

这些程序常被统称为“驱动软件”，但实际处理功能的可能是普通应用、后台服务或驱动组件。需要电脑端处理时，可以理解为：

```text
按下厂商功能键 → 上报标准按键或私有报告 → 厂商配套软件接收 → 执行配置的功能
```

如果它监听标准键值并执行功能，本质上也是 APP 快捷键机制。但不能认为所有厂商功能都采用这一种方式：具体产品也可能使用私有报告，或将映射和宏保存到板载存储，由键盘直接执行，不要求配套软件持续运行。

### 5.3 HID 是否真的提供厂商私有空间

有。HID 提供 Vendor-defined Usage Page（厂商自定义用途页），范围为 `0xFF00～0xFFFF`，允许厂商约定自己的报告内容，并由配套软件解释。

这需要另外定义报告格式，不能向普通键盘键值里随便填一个“没用过的数字”。标准键盘页中标为 Reserved（保留）的值，也不等于厂商可自由使用的私有键值。

厂商自定义用途页也不是简单地“再增加几个标准键”。设备需要声明相应的数据格式，PC 软件需要按约定读取；普通编辑器不会自动理解这些私有数据。

一个产品可以同时提供标准键盘输入和厂商私有功能。前者负责通用输入，后者用于产品特有的交互，两者并不冲突。

## 6. 我们的五键设备推荐怎么做

### 6.1 使用标准 F13～F24，绑定 APP 功能

**对于我们的少量自定义功能，推荐使用标准键值作为两端的约定：固件保存配键，APP 定义收到键值后的功能；有需要时，固件也可以将指定配键作为设备端功能的触发条件。**

```text
用户按下 KEY1
    ↓
固件按保存的配置上报 F13
    ↓
操作系统识别为 F13 键盘事件
    ↓
PC APP 监听并执行“开始翻译”
```

例如，APP 给 KEY1 下发 F13 的配键配置，固件校验后保存，并在 HID 就绪时按该配置生成键盘报告。固件不需要保存或理解“开始翻译”这个业务含义。

用户以后在 APP 中把 F13 对应的功能改成“开始录音”，设备仍然可以上报 F13，无需为了修改业务功能而改变固件中的键值。

### 6.2 为什么选 F13～F24

**F13～F24 是标准功能键，不是专门留给厂商的私有键。** 常见键盘没有这些实体键，它们也没有跨所有软件统一的默认功能，因此比 Ctrl+C、Win+Shift+S 等常用快捷键更适合绑定少量业务操作。

它们仍可能被其他软件使用，所以 APP 要检查冲突；若使用全局快捷键注册，要检查是否成功。当我们的 APP 或后台服务没有运行，且没有其他软件绑定这些键时，按下通常不会产生可见效果。

### 6.3 配置与使用是两个过程

配置时，APP 需要分别管理“设备发送什么”和“收到后执行什么”：

| 配置放在哪里 | 保存的内容 | 示例 |
|---|---|---|
| 设备固件 | 实体键对应的标准键值及修饰键配置 | KEY1 对应 F13 |
| PC APP | 键值对应的业务动作及相关设置 | F13 对应开始翻译 |

使用时，设备按保存的配置上报，APP 根据自己的映射执行功能。因此可以只改 APP 中的业务映射，也可以通过配键协议修改设备发送的键值；如果修改了键值，APP 的监听配置也需要保持一致。

当前固件默认映射为 KEY1～KEY5 对应 F13～F17；下表的 APP 动作仅为示例，由 APP 自行定义。已有 APP 保存的有效配键优先于固件默认值：

| 实体键 | 设备上报 | APP 中可配置的动作 |
|---|---|---|
| KEY1 | F13 | 开始翻译 |
| KEY2 | F14 | 停止翻译 |
| KEY3 | F15 | 在 PC 端开始／停止录音 |
| KEY4 | F16 | 切换翻译方向 |
| KEY5 | F17 | 显示／隐藏 APP 窗口 |

这里的录音、翻译等动作由 PC APP 实现，不表示设备收到这些按键后会自动执行本地业务。

KEY5 另有固件端的在线长按录音约定，是同一标准键值关联两端自定义功能的实际案例，详见下一节。

### 6.4 实际案例：用 KEY5／F17 关联 PC 与设备端功能

选择 F13～F24，不只是为了让 APP 监听几个不常用的功能键。我们的 KEY5／F17 案例还说明：**标准键值可以作为产品内部的共同约定，一方面参与 PC 应用层的功能映射，另一方面参与设备固件的功能判断。** 自定义的是两端赋予它的业务含义，不是 F17 的 HID 标准定义。

#### 6.4.1 上行：标准按键触发 PC 应用层功能

KEY5 默认配键为 F17。在 HID 就绪时，设备上报标准 F17 的按下／松开状态。PC APP 可以监听这些事件，再执行自己定义的动作，例如显示录音界面、响应按住说话交互等。

```text
KEY5 物理按下／松开
    → 固件按当前配键生成 F17 报告
    → HID 上报，操作系统分发键盘事件
    → PC APP 监听 F17，执行应用层自定义功能
```

这里的 APP 动作是可设计的应用层行为，不代表固件已经替 APP 实现。设备上报的是按键状态，若 APP 要区分点击和长按，还需自行处理事件时序。

#### 6.4.2 设备端：指定配键使能固件功能

当前固件把“KEY5 配键为单独 F17”作为在线长按录音的准入条件：

```text
KEY5 产生长按事件
    → RDX 会话是否就绪？
    → KEY5 当前生效的配键是否为单独 F17？
    → 满足条件后，进入现有在线录音流程
```

“单独 F17”表示无修饰键、无其他键值。这个判断使用当前生效的运行时配键，不等待 PC 收到 F17，也不要求 HID 上报成功。录音仍受原有录音流程的准入和状态管理约束，配成 F17 不等于任何情况下都保证录音成功。

因此，同一次 KEY5 操作有两条处理路径：**HID 路径向 PC 报告按键状态，固件业务路径在长按时决定是否允许在线录音。** 两条路径通过 KEY5 的配键约定关联，但不是“PC 收到 F17 后回传命令，固件才开始录音”的串行关系。

#### 6.4.3 下行：通过配键配置改变两端行为

APP 可以通过现有配键协议下发 KEY5 的键值。配置成功生效后，既改变设备上报什么，也影响 KEY5 是否满足在线录音条件：

| KEY5 当前生效的配键 | HID 就绪时上报 | RDX 就绪时在线长按录音 |
|---|---|---|
| 单独 F17 | F17 | 允许进入原有录音流程 |
| F18 等其他键值 | 对应的标准键值 | 不触发 |
| Ctrl+F17 等组合键 | 对应的组合键 | 不触发 |
| 禁用配键 | 不产生该键的有效按键输入 | 不触发 |

```text
PC APP 下发 KEY5 配键
    → 固件校验、保存并使配置生效
    → HID 上报使用新的键值
    → 后续 KEY5 长按按新的配键判断是否允许在线录音
```

**这里可以理解为“上行按键上报＋下行配键配置”的双向客制化，但不能理解成“F17 键盘事件本身可以双向传输”。** 当前上行走 HID 键盘输入，下行走 APP 配键协议；不是 PC 通过 HID Output Report 发送 F17 来命令设备录音。在电脑的另一把键盘上按 F17，也不会因此启动本设备录音。

同样，当前下行能配置的是键值，不是任意固件功能。KEY5／F17 对应在线长按录音这一规则由固件实现；如果未来希望 APP 任意指定“F18 对应另一项设备功能”，仍需扩展相应的固件能力和配置协议。

#### 6.4.4 本案例的行为边界

- 只绑定 KEY5：其他实体键即使配成 F17，也不会获得在线长按录音能力。
- 在长按事件到来时检查配键：未获准后保持按住再改回 F17，不会追补触发，需重新按下并长按。
- 开始受限，结束必须配对：已触发在线录音后，即使按住期间修改配键，松开仍走原有停止流程。
- 离线录音和工厂测试按键行为不受这项配键限制；正常 HID 上报仍遵循其自身的就绪条件。
- 已实现的收尾例外（实机待验收）：已有离线属性录音接入 APP 后，KEY5 双击仅停止该录音，不受 F17 配键限制；它不是在线双击启动能力，也不改变 HID 上报。停止执行校验目标录音代次，避免旧重试误停新录音。详见 `10-2.离线在线模式转换时的体验优化.md` 第 17 节。
- PC 与固件功能需要协同设计：若 APP 也监听 F17 控制同一录音业务，应明确开始／停止的责任，避免重复发起操作。

这个案例体现了我们选择 F13～F24 的用法：**保留标准键盘输入的通用性，同时由 APP 和固件各自赋予受控的业务含义。** 不需要为在线录音发明一个私有 HID 键值，也不意味着这些标准键被我们独占。

### 6.5 实际案例：KEY1／F13、KEY2／F14 的业务按键灯效

客户可以在 PC 应用中监听 KEY1 默认的 F13、KEY2 默认的 F14 并执行自定义业务，同时要求设备单击 KEY1 亮一次蓝灯、单击 KEY2 亮一次白灯。固件不必实现 PC 端的业务，也可以根据约定的实体键和配键提供本地提示。

**这里定义的是“业务按键反馈”，不是“PC 业务执行成功反馈”。** HID 就绪仅说明键盘输入路径具备发送条件，不保证 PC 应用正在监听，也不保证应用执行成功。灯效不等待 PC 回传确认，不改变 HID 按下／松开上报。

#### 6.5.1 准入与配键关系

| 单击事件的处理条件 | 请求的本地反馈 | 同次单击查电量 |
|---|---|---|
| HID 就绪，KEY1 当前配键为单独 F13（`0x68`） | 蓝灯亮一次 | 不触发 |
| HID 就绪，KEY2 当前配键为单独 F14（`0x69`） | 白灯亮一次 | 不触发 |
| KEY1／KEY2 改为其他键值、组合键或禁用配键 | 原有电量查询 | 保留 |
| HID 未就绪，包括离线、未订阅、未加密或挂起 | 原有电量查询 | 保留 |
| KEY3～KEY5 单击 | 原有电量查询 | 保留 |

“单独”表示恰好一个目标键值，无修饰键、无其他键值。只绑定指定实体键与指定配键，其他实体键配成 F13／F14 不会获得对应灯效；也不依赖 RDX 会话就绪。

按键适配层只投递单击键号，实际在 `app_core` 回调执行时检查当前 HID 就绪状态和生效配键。长按、保持、松开及多击事件不请求这个单击提示；PC 的按键自动重复也不会反向触发设备灯效。业务未启动、工厂按键测试、关机、PC 模式及格式化期间继续遵循原有按键反馈保护。

#### 6.5.2 与电量查询和其他灯效的关系

同一次单击在入口二选一，而不是先亮电量颜色再用业务颜色覆盖：

```text
单击事件进入 app_core
    → 检查按键反馈保护条件
    → HID 就绪且命中指定实体键＋纯键值？
        → 是：请求蓝灯／白灯提示，本次不再查询电量
        → 否：请求原有电量提示
    → 统一由灯效模块仲裁是否显示
```

- 业务按键提示优先于手动电量查询：可以替换正在显示的手动电量提示，显示期间新的电量查询不能抢占。
- 录音、Wi-Fi 传输、OTA、DUT、充电、存储切换、包装完成及关机等保护状态保持既有规则，不因按键提示重启持续灯效的相位。
- 提示被拒绝直接丢弃，不排队，也不回退显示电量；按键 HID 上报仍按原有路径处理。
- 周期性低电提醒不是手动电量查询，保留原来的仲裁策略；它显示期间不被本提示抢占。
- 蓝灯、白灯使用独立场景及颜色，单次亮 **2 秒**，与录音标记、电量查询共用 `RDX_LED_SINGLE_INDICATION_MS` 时长配置，结束后恢复实时业务场景。白色沿用设备现有校准值；不改变连接成功的五秒提示时长。
- 提示结束按实时业务状态恢复灯效，不保存并恢复过时颜色；显示期间新出现的高优先级业务也由现有更新流程接管。
- 已绑定设备采用静默广播：上述单次提示结束后，空闲时灭灯，不恢复广播蓝闪；未绑定设备保持原有广播提示。此规则仅限制广播场景，不屏蔽 KEY1 的蓝色业务按键反馈，详见《10-2.离线在线模式转换时的体验优化》第 18 节。

颜色、亮度、时长集中在 `rdx_led_cfg.h` 中配置；单击分流位于 `rdx_app_key_click_cb()`，仲裁及恢复由 `rdx_led_ctrl.c` 负责。新增代码不定义 PC 业务命令，也不增加灯效下行协议。

#### 6.5.3 与 F17 案例的区别及验收

F17 案例通过配键使能设备端在线长按录音；F13／F14 案例通过配键关联 PC 端业务与设备端按键提示。两者都是**保留标准 HID 键值，在产品层赋予额外约定**，并非修改 HID 标准或独占这些键值。

若未来需要“PC 完成业务后才亮灯”，应另外设计 PC 下行反馈命令及会话、过期约束，不能将本地按键提示当作应用成功回执。

本轮已实现并补充主机行为测试，实机待验收。重点检查：

1. HID 就绪、默认配键时，KEY1 蓝灯及 KEY2 白灯各亮一次，无绿色电量闪烁；PC 仍收到正常按下／松开。
2. 改为普通键、组合键或禁用后，单击恢复原有查电量；恢复默认配键后恢复业务提示。
3. 离线或 HID 未就绪时保留查电量；仅 HID 就绪、不建立 RDX 会话时也能提示。
4. 录音、传输、OTA、DUT、充电及存储切换期间不抢占原有灯效，拒绝业务提示后也不补查电量。
5. 长按、多击不误触发单击提示；KEY3～KEY5 原有手势、F17 在线录音及联网后的离线录音双击停止不变。
6. 电量提示中单击业务键可切换到业务提示；提示结束或期间业务状态改变后，恢复正确的实时灯态。

### 6.6 APP 运行状态和输入来源也要考虑

如果希望用户在其他软件中工作时仍能触发功能，APP 需要实现后台监听，例如成功注册全局快捷键，不能只处理自己窗口内的按键。

普通快捷键通常按“哪个键”识别，不自动区分“来自哪一把键盘”。如果另一把键盘也发送 F13，同一个快捷键也可能被触发。若将来要求只响应我们的设备，PC APP 就需要额外识别输入设备来源，或评估私有报告方式；仅选择 F13 本身不能实现设备隔离。

### 6.7 当前方案的边界

当前配键协议表达的是普通 HID 键盘键值及修饰键组合，F13～F24 已在支持范围内。固件会按协议校验键值，并非任意数字都可以保存和上报；上报时还需要符合键盘报告格式及连接就绪条件。

多媒体控制和厂商私有报告属于不同类别，不能直接当成普通键盘键值填入当前配置。如果未来需要这些能力，再扩展对应协议和报告格式。

我们的方案无需为“翻译”“录音”等业务新增 HID 私有键值：**标准键值负责传递按键，APP 映射负责 PC 端功能，固件规则负责设备端功能，配键协议负责下发配置。**

## 7. 常见理解误区对照

| 容易产生的理解 | 更准确的理解 |
|---|---|
| HID 就是键盘协议 | HID 可以描述多类设备，键盘只是其中一种 |
| HID 只给 PC 使用 | 其他支持相应协议的主机也可以使用 |
| 标准里有的键，厂商都必须做出来 | 厂商可按产品需要选用，不必提供全部实体键或键值 |
| 键盘发送的是“复制”“翻译”命令 | 普通键盘发送按键状态，业务含义由系统或 APP 解释 |
| F13～F24 是厂商私有保留键 | 它们是标准功能键，可以被不同软件使用 |
| 没有独立实体键，就不能上报该键值 | 固件可以将现有实体键或组合映射为该标准键值 |
| 免驱表示完全没有驱动 | 通常表示使用系统自带驱动，不必另装厂商驱动 |
| 专属功能一定需要专属底层驱动 | 也可以由普通 APP 或后台服务监听标准按键实现 |
| APP 在前台就能抢过系统快捷键 | 是否能接收或拦截，取决于系统规则和监听方式 |
| 所有客制化本质上都是 APP 快捷键 | APP 快捷键只是其中一种；KEY5／F17 还结合了固件端功能判断 |
| 下行客制化就是 PC 把 F17 作为 HID 命令发回设备 | 当前下行是配键协议配置；F17 的 HID 输入上报与固件录音判断是不同路径 |
