# PC App共享HID连接时的RDX释放：问题复盘与处理方案

> 更新时间：2026-09-09。固件已实现单条 `*APP#custom#rdxclose#1#` 指令，复用已有 RDX 断开清理流程，保留共享 ACL 上的 HID。构建及 5 组主机检查通过；已用 PC BLE 调试工具完成共享连接下的 RDX 释放与手机接管验证，方案有效。PC APP 正式接入及其余验收项待完成。
> PC APP 开发对接见 [PC APP 断开指令对接说明](3-6.PC_APP断开指令对接说明.md)；本次真机验证见第 4.1 节。
> 以下第 1、2 节保留问题发生时的架构、现象与验证结果。

## 1. 我们发现的问题

### 1.1 PC App断开不等于系统HID连接断开

PC HID由Windows系统蓝牙/HID栈建立并维护。当前PC App的断开操作释放自身的GATT使用关系，不能依赖它去断开系统持有的HID连接。PC App与HID共享物理ACL时，App显示断开后，Windows仍可为键盘保留这条ACL。

修改前，固件将RDX会话释放绑定在物理ACL断开回调上。PC App已经退出业务，但固件没有收到会话结束事件，RDX owner继续留在PC链路上，手机无法接管RDX。

解决目标是PC App显式通知固件“结束我的RDX会话”，固件只清理RDX、保留HID及其物理连接。无需PC App获得断开系统蓝牙的权限，也不要求手机与PC统一断开指令。

### 1.2 与已解决问题的边界

本问题必须与此前的跨peer重绑问题分开：

| 路径 | 问题复盘时的状态 | 结论 |
|---|---|---|
| PC App单独占用ACL并主动断开 | 已连续两轮真机验证 | Windows终止唯一ACL，固件收到`Disconnection Complete`，RDX runtime正常回到`READY` |
| 手机RDX与PC/HID各占一条ACL并分别主动断开 | 已通过真机验证 | 每条物理ACL独立触发对应wrapper的断开回调 |
| 手机RDX物理ACL断开，PC/HID ACL保持，PC App接管RDX | 已通过真机验证 | 同peer地址锁问题已经解决 |
| PC物理ACL断开，手机重新连接并接管RDX | 现有物理断开生命周期支持，仍需纳入完整矩阵 | 固件可以收到Disconnection Complete |
| PC App关闭GATT对象，但Windows为HOGP保留复用ACL，手机接管RDX | 阻塞 | App级GATT detach不是物理ACL断开，固件收不到可用于释放RDX owner的事件 |

因此，当前现象不是旧的FIFO边界未清理、runtime卡在`RESETTING`，也不是跨peer claim仍被地址锁拒绝。旧问题已经完成以下闭环：

```text
旧RDX物理断开
  -> ACTIVE -> QUIESCING
  -> receive FIFO nonce barrier
  -> workers idle + final buffer reset
  -> READY
  -> 不同peer合法claim
  -> ACTIVE
```

当前阻塞只发生在复用ACL拓扑的第一步之前：PC App单独使用时可以触发“旧RDX物理断开”；PC App与HOGP复用时不会触发物理断开，也没有发送等价的“RDX逻辑会话关闭”协议消息。

### 1.3 修改前代码的根因

修改前，固件用于释放RDX的断开入口是`rdx_ble_server_phase0a_packet_handler()`中的`HCI_EVENT_DISCONNECTION_COMPLETE`。它是物理连接事件，不是“某个Windows应用停止使用某组GATT特征”的事件。事件到达后，`rdx_ble_server_phase0a_link_disconnected()`才会按该链路持有的能力执行RDX detach、HOGP本地清理和整条link release。新增指令只增加RDX清理的触发入口，不代替物理断开回调。

修改前的registry把RDX capability设计为物理链路生命周期内粘性持有：

```text
RDX claim -> link.capability增加RDX bit
           -> rdx_link_index指向该slot
           -> runtime ACTIVE

Disconnection Complete
           -> RDX detach和runtime收敛
           -> link release
           -> RDX/HID owner按该物理链路释放
```

RDX CCC写`0`目前只清除`rdx_ccc_configured`和`rdx_stream_tx_ready`，不释放RDX bit或`rdx_link_index`。这是此前为防止普通CCC变化造成owner漂移而冻结的安全边界。

Same-link PC拓扑使“应用会话”和“物理连接”不再等价：

```text
Windows物理ACL
  + HOGP会话：由Windows HID栈长期持有
  + RDX会话：由PC App临时使用
```

PC App关闭RDX时，Windows可以只销毁应用侧GATT对象而继续保留ACL。PC App单独使用时，GATT detach之后没有其他消费者，Windows进一步终止ACL，所以固件恰好能够通过物理断开释放RDX；这只是独占拓扑下应用生命周期与ACL生命周期重合，不能作为RDX会话关闭协议。

复用拓扑中两者不再重合。固件既不能从不存在的HCI事件判断PC App是否退出，也不能把普通ATT空闲可靠地解释为退出。因此旧RDX owner继续占用是当前设计的确定行为，不是callback注册、wrapper路由或断开清理代码的遗漏。

### 1.4 不能采用的修补方式

#### 1.4.1 不能强制断开整条ACL

`rdx_ble_server_force_disconnect_timer_cb()`对应的是整条BLE连接断开，并且当前函数被硬编码立即返回。重新启用它会同时破坏：

- HOGP键盘在线状态；
- HID Input CCC与report发送；
- Windows设备连续性；
- same-link复合owner的产品目标。

因此不能用“PC App退出后踢掉BLE连接”代替RDX逻辑释放。

#### 1.4.2 不能仅按ATT空闲超时释放

PC App正常停留在页面、没有操作时也可能长时间没有ATT写入。仅按最后一次业务包计时会把正常空闲误判为退出，并可能在文件、OTA或后台任务期间错误切换owner。

#### 1.4.3 不能直接调用整条link release

现有`rdx_ble_session_link_release()`会清理整个slot及其RDX/HID owner索引。Same-link场景直接调用会把仍然有效的HOGP一起释放，并使registry与真实ACL状态不一致。

#### 1.4.4 不能只清RDX owner字段

`librdxApp.a`是不可修改的异步单例。若只清`rdx_link_index`或capability bit而跳过`QUIESCING -> FIFO barrier -> RESETTING -> READY`，旧receive、record、file、bulk、OTA或send工作可能污染下一位手机owner。

## 2. 实际现象与验证结果

### 2.1 修改前的操作过程与故障表现

1. 手机 APP 与 PC HID 分别建立独立的物理连接，功能正常。
2. 手机 APP 断开，固件完成手机链路的 RDX 清理。
3. PC APP 使用已有 PC HID 连接取得 RDX，形成同链路 HID+RDX。
4. PC APP 点击断开，Windows 为 HID 保留物理连接，固件无法通过物理断开事件释放 RDX。
5. 手机再次接入时，即使已建立第二条物理连接，仍无法取得 RDX 会话，APP 表现为连接失败。

### 2.2 已完成的对照验证

| 验证场景 | 实测结果 | 说明 |
|---|---|---|
| 手机 RDX 断开，PC HID 保持，随后 PC APP 接入 | PC APP 成功接管 RDX，并完成录音启动、停止和文件保存 | 跨设备交接与原有 RDX 清理流程有效 |
| PC APP 单独使用，连续两轮主动连接和断开 | 两轮均触发物理断开并完成 RDX 清理 | 原有物理断开处理有效 |
| 手机 APP 与 PC HID 分别连接、分别断开 | 手机断开只释放手机链路，PC HID 保持；PC HID 断开也能独立处理 | 两条物理连接的清理范围正确 |
| PC APP 与 PC HID 共用连接，PC APP 执行原来的断开操作 | PC 物理连接保留，RDX 会话仍被占用，手机无法接管 | APP 关闭自身 GATT 资源不能代替显式 RDX 释放 |

以上验证将问题定位到共享连接下缺少 RDX 会话结束通知。新增指令后的验证步骤与结果见第 4.1 节。

## 3. 处理方案

### 3.1 按物理连接与业务分别确定清理范围

PC 与手机是不同的 BLE 对端，各自建立独立的物理 ACL；PC APP 与 Windows HID 则可以共用同一条 PC ACL。两条 ACL 可以同时存在，但全局仍只允许一个 RDX owner。

| 触发场景 | 清理范围 | 保留内容 |
|---|---|---|
| 手机或 PC 的物理 ACL 断开 | 清理该 ACL 上的全部 RDX/HID 状态（按实际持有的能力），释放该连接 slot | 另一条 ACL 及其业务状态 |
| PC APP 与 PC HID 共用 ACL，PC APP 发送 `rdxclose` | 只清理当前 PC owner 的 RDX 业务与占用状态 | PC 物理 ACL、HID owner、HID 订阅和键盘可用状态 |

“全部清理”只针对已经断开的那条物理连接，不是清空设备上两条 ACL 的全部状态。新指令始终表示“释放 RDX”，不要求断开物理 BLE 连接；即使 PC 当前未使用 HID，也按同一语义处理。

### 3.2 PC APP 只增加一条释放指令

PC APP 主动断开时停止业务写入，通过现有 RDX 通道向 `0x0006` 发送完整 ASCII 文本：

```text
*APP#custom#rdxclose#1#
```

待 BLE 写操作完成后释放 APP 自身的通信资源。正常连接流程不变，无需 OPEN、会话 ID、请求 ID、CRC、关闭握手、租约或心跳。手机 APP 保持现有物理断开方式。

指令共 21 字节；默认 MTU 23 下，按顺序先发 `*APP#custom#rdxclose#1`，再发最后一个 `#`。不加换行或 NUL，无需订阅 Notify，无专用回包。写操作完成不等于固件已完成清理，验证以手机实际接管结果为准。

### 3.3 固件复用已有 RDX 清理部分

新指令通过现有 custom 解析入口，在 btstack 校验内部连接代次后，调用已有断开处理中的 RDX 清理部分。内部代次用于防止旧连接排队的指令影响新 owner，不需要 PC APP 传入。

复用关系如下：

```text
物理 ACL 断开 -> 该链路的 RDX 清理（如持有 RDX）
             -> 该链路的 HID 清理（如持有 HID）
             -> 释放该物理连接 slot

rdxclose 指令 -> 当前 owner 的 RDX 清理
             -> 保留物理连接 slot 和 HID 状态
```

RDX 清理包括停止新业务、取消传输和定时器、清除 RDX capability 与 owner 索引，并复用 `QUIESCING -> FIFO barrier -> RESETTING -> READY` 流程，等待任务停止和缓冲区复位。完成后才允许手机取得 RDX。

新指令路径不调用整条 `rdx_ble_session_link_release()`，不调用 HID 断开处理，不主动断开 ACL；保留 HID CCC、加密状态、MTU 和物理连接身份。PC 从 `RDX_HID` 变为 `HID`，键盘继续可用。

## 4. 验收

### 4.1 已完成的验证方法与结果

1. 先连接 PC HID，再连接 PC APP，两者共用同一条 PC BLE 物理连接。
2. 在 PC APP 中执行原来的断开操作，保留 PC HID 连接。
3. 使用手机 APP 连接，仍然无法接入 RDX，复现原问题。
4. 使用 PC BLE 调试工具向 RDX 写特征 `06068D1C-6B97-11EF-B864-0241AC120002`，以 **Write Without Response（无响应写入）** 发送完整 ASCII 指令 `*APP#custom#rdxclose#1#`，不附加换行或 NUL。
5. 再次使用手机 APP 连接，成功接入 RDX。PC BLE 调试工具仍显示连接，符合保留物理连接的预期。

| 验证阶段 | 结果 |
|---|---|
| PC HID 与 PC APP 连接后 | PC 同时持有 HID 和 RDX |
| PC APP 执行原来的断开操作后 | 手机连续三次申请 RDX 均失败 |
| BLE 调试工具发送新指令后 | PC 释放 RDX，保留 HID 状态与物理连接，并执行已有 RDX 清理流程 |
| 手机再次接入 | 成功取得 RDX，并正常发送电量、版本等业务指令 |

结论：实测确认新指令能够释放 PC 占用的 RDX 会话，保留 HID 状态和物理连接，使手机重新接入。BLE 工具代发直接验证了固件方案，也间接验证了 PC APP 替换断开指令的可行性。正式 PC APP 尚需接入同一指令；本次验证确认了 HID 能力保留，键盘实际连续输入仍需单独确认。

### 4.2 后续验收

PC APP 替换断开指令后，按第 4.1 节相同步骤复测，由 APP 自身发送指令。其余真机验收项如下：

1. 共享 ACL：新指令使 PC capability 从 3（RDX+HID）变为 2（HID），runtime 回到 READY；PC ACL 保持，键盘继续输入，手机可接管 RDX。
2. 独立 ACL：手机物理断开时，手机链路完整释放，PC HID 继续工作；PC 物理断开时，只清理 PC 链路，另一条手机 ACL 不受影响。
3. 共享 ACL 物理断开：如果 PC 的整条 ACL 确实断开，该链路上的 RDX 和 HID 都必须清理，不能套用“仅释放 RDX”的范围。

覆盖默认 MTU 分包、PC/手机至少 20 轮交替接入、传输中释放、重复排队指令及物理断开竞争。APP 异常退出而未发送指令的情况作为独立后续需求。
