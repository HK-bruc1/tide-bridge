## 2. 当前方案与配置

### 2.1 数据链路

```text
MIC0 / MIC3 → 各自 DNS、AGC → 双路 FIFO
→ Source_Dev1：每路 320 点，共 1280 字节 planar PCM
→ EffectDev2：动态择优，输出一路 320 点 / 640 字节 PCM
→ Opus：16 kHz / 1 ch / 16 kbit/s / 20 ms / format_mode=0
→ Sink_Dev1 → RDX/BLE 发送 → APP
            → 有界编码帧队列 → 独立存储任务 → MTA / RAW → 本地回放
```

保持双路采集，在编码前生成一路 PCM。择优通常输出选中一路，切换时交叉淡化；它不负责说话人识别、分离，也不保证完整保留多人同时发言，需通过实际会议样音验收。

| 项目 | 当前约定 |
| --- | --- |
| 采集输入 | 每路 16 kHz、16 bit、320 点 / 20 ms；前 MIC0、后 MIC3 |
| 单声道编码 | 一路 320 点，第二 PCM 指针传 NULL；实测每帧 40 字节 |
| 历史双声道 | 每帧 80 字节；用于旧文件兼容及回退 |
| 长度边界 | 编码/发送使用实际 `encLen`；保存校验锁定的 40/80 字节配置，不能推广到任意 Opus 参数 |
| 外层协议 | 沿用原 RDX/BLE、RAW 及 DAT JSON schema，不修改 APP 文件协议 |
| 声道上报 | CHAT 单声道为 `format=1 mode=0 channels=1`；双声道及 CALL 为 `mode=1` |

`format_mode=0` 为 JL 接口的“百度无头”模式，不能当作任意标准 Opus 文件解析。播放的 48 kHz / 双路 source 协商也不等于文件编码变回双声道。

## 3. 实现边界与维护要点

### 3.1 录音、算法与故障隔离

- recorder 在协商和启动前通过 `NODE_IOC_SET_PRIV_FMT` 固定本次实例策略；采集保持 `global_ch_mode=AUDIO_CH_LR`，EffectDev2 区分两路输入和一路编码输出。不能提前将全局采集模式改为单声道。
- `STREAM_SCENE_AI_VOICE` 不等于 RDX CHAT；历史名称 `PIPELINE_UUID_TRANSLATION_MONO`（0x9463）的流程实际包含双 MIC 与 EffectDev2，本轮保留该图及 `stream.bin`。
- 工作区按 `need_buf()` 分配，PCM 与编码缓冲由实例持有；只有成功 create 的实例能销毁算法单例，重复申请失败不能影响已有持有者。停止、挂起及失败按归属清理，恢复重新创建。
- 分配/open 失败阻止启动；输入不匹配、process 不返回 320 或编码失败后停止提交。音频回调只记录故障，由原 100 ms 定时检查投递 `app_core` 收尾，队列满重试；epoch/binding 防止迟到故障停止新会话。
- 动态模式任一路 FIFO 丢数锁存 `-20`；源已启动且 500 ms 无完整配对帧锁存 `-21`。恢复来数也不继续编码，不隐式降级或猜测重同步。500 ms 是工程阈值，仍需负载实测定版。
- 每路 FIFO 5120 字节，约 160 ms。等到两路各 320 点仅保证数量，不证明共同采样时刻；共同采集时钟、分支延迟及启动对齐仍需同步信号/PCM 实测。

CALL 保持原 PCM 路由与双声道编码，不接入择优或配对 watchdog；但它仍经过共用的保存聚合、格式记录与存储故障 STOP。因此 recorder 的故障定时器也覆盖 CALL 和双声道回退，不能仅按 `policy.mic != 0` 创建，否则共享格式写入失败可能无法收尾。“CALL 保持原链路”不表示共享基础设施没有变化，实机回归仍必须覆盖通话录音及保存失败。

### 3.2 保存与格式恢复

主要模块为 `rdx_record.c/h`、`rdx_record_format.c/h`、`rdx_storage_lifecycle.c`。

| 环节 | 实现与约束 |
| --- | --- |
| 聚合保存 | 两条本地写入分支共用 append/flush，循环处理跨 8000 字节缓存的余量和停止尾部；写失败停止处理余量，防止重复提交 |
| stream-only | 只发送，不新增本地录音文件 |
| 文件身份 | 新会话推进 generation 并清空旧标记；暂停续录保留文件身份与格式 |
| 格式持久化 | 首帧落 RAW 前写同名 `.mta`，记录 SN、名称、场景、开始时间、格式及首帧指纹，flush 后读回核验 |
| DAT / APP | 复用 `opus`、`frame_size`；单声道 `opus=1084752896`、`frame_size=40` |
| 启动恢复 | 在 RDX 文件任务、缓存和定时器启动前执行一次；验证 `.mta`、RAW 首帧和帧对齐，先只读核对 DAT，仅在格式不符或缺少条目时纠正或补建，不触碰活动缓存 |
| 索引提交 | 先写 `rfmt.tmp` 和校验提交记录 `rfmt.cmt`，再替换 DAT；重启可重放已提交临时索引，验证并 flush 后清理提交记录 |
| 不确定状态 | 身份冲突、指纹不符、未对齐尾部、损坏索引/提交记录拒绝自动猜测，恢复校验失败关闭业务准入 |

恢复保留现有 DAT 旧条目和 marks，沿用最多 300 条容量，逐对象处理 JSON。DAT 丢失时可用 `.mta` 恢复格式、大小和 CRC，结束时间按帧数估算；丢失的 marks 和暂停墙钟时长无法重建。已删除 RAW 不因残留 `.mta` 复活；`.mta` 与 DAT 同时丢失时，无头 RAW 无可靠格式恢复依据。

不要将混合单双声道文件的介质交回不识别这些格式记录的旧固件扫描。首次元数据写入、启动扫描耗时和真实掉电恢复仍待实机验收。

格式模块是 RDX 文件库的兼容适配层：运行时通过既有 `uxfile_data_t` 设置格式，直接编辑 DAT 仅限库初始化前。升级 RDX 静态库时必须复核 DAT 字段、文件命名、40/80 字节配置及 300 条容量约定。健康 DAT 的启动核对不创建临时文件、不写 DAT，并保留原始字节；需要修复时才执行第二遍解析与事务提交。若存在上次未完成的有效提交记录，仍优先重放。损坏、身份冲突等错误继续关闭准入，不为减少耦合而放宽数据保护；扫描耗时仍需测量。

### 3.3 本地回放与自然结束

主要模块为 `rdx_playback.c`、`source_dev0_file.c`、`dev_flow_player.c`、`lib_media_config.c`。

- 按 DAT 选择 40 字节单声道或 80 字节双声道，旧字段 0 沿用历史双声道；不根据文件总大小猜格式。时长、seek/resume 随格式计算，切换候选成功后才替换活动配置。
- 统一采用与编码器匹配的 STENC 解码路径，启用 raw 包头模式、CBR 长度 0。每帧仅在内存增加 8 字节头：前 4 字节为大端有效载荷长度，后 4 字节当前库未校验；RAW 和 BLE 不增加包头。
- `lib_media_config.c` 的 raw/CBR 参数是解码库全局配置，并非播放器实例配置。当前源码中的 STENC source 为 SourceDev0；以后接入其他 STENC/OGG Opus 音源，必须复核其分包契约，不能假定此配置只影响本地录音回放。
- 消费位置只计算原始音频字节，临时头不进入暂停和 seek 位置。沿用原播放流程，STENC source 为 48 kHz LR，decoder/DAC 按实际格式协商。
- 自然 EOF 通过临时 `pb_close` 任务执行 `jlstream_stop(..., 50)`；`app_core` 每 10 ms 查询完成，保持 DRAINING 和播放器占用，停止完成后才释放、发布空闲。
- 清理任务创建失败重试；定时器分配失败回退同步关闭。收尾期间显式停止、暂停或切换仍同步等待同一任务，再统一释放，避免重复 stop 和释放后访问。此次优化针对自然 EOF，未承诺显式关闭无等待。

## 5. 排障经验

### 5.1 编码成功但 APP 仍显示双声道

根因是 `rdx_record_auto_run()` 在 CHAT 启动/恢复时固定设置双声道 record_mode。应根据实际格式，在投递录音任务前设置模式，停止/暂停保留本次模式。通过源码即可修复，不需要给 RDX 静态库新增补丁。

`sample` 是采样率枚举，16 kHz 单/双声道均为 1；后面的 record_mode 才是声道模式。单声道状态示例：

```text
[RDX_RECORD_REPORT] format=1 mode=0 channels=1
开始：*DEV#record#1#0#1#0#1#0#
停止：*DEV#record#0#0#1#0#1#0#
```

### 5.2 stream-only 正常，保存一触发就停止

`除了在线录音其他都不行.log` 中，编码正常但首次格式保存报 `-22`，两次都在 16 帧后 STOP。原因是 `f_flush_wbuf()` 误传设备名 `sd0`，SDK 要求文件系统路径 `storage/sd0/C/`。修正元数据、索引提交与恢复的全部调用，并让主机模拟检查路径约定。

经验：按编码、格式持久化、实际落盘逐段排查；mock 不能宽松到掩盖 SDK 参数错误。增加 write/flush/close/读回失败和代码行日志，比笼统报告“存储错误”更有效。

### 5.3 文件格式正确，但本地播放立即 dec_err

单声道分支曾选择普通 Opus，与录音的 `get_opus_stenc_ops()` 不匹配；改回 STENC 后还要处理底层固定 80 字节 CBR 的假设。只读核查 JL 库后，采用内存 raw 包头传递 40/80 字节帧长，源码适配即可，不修改静态库。

经验：编解码匹配包含具体实现、分包方式和 PCM 协商。必须同时核对暂停/seek 字节计数，不能将临时头算入文件位置。`nch=1`、APP 显示正确、文件能打开，分别只证明各自环节。

### 5.4 EOF 完成但 app_core 超时

同步 `dev_flow_player_close()` 等待淡出及 DAC 停止约 170 ms，占用定时回调所在的 `app_core`。改为临时任务停止、主任务查询完成；不能靠屏蔽告警或取消淡出来认定解决。

- 缓冲排空不等于硬件停止，必须保持占用到流停止完成，才能开放存储、电源和新播放准入。
- 使用 SDK 实际可链接的 `os_task_create/os_sem_query/os_sem_pend/os_task_del`；`thread_fork/thread_kill/os_sem_accept` 虽有声明，本工程不可链接。
- 异步化消除主任务同步等待，不消除音频清理耗时；验证要同时看到任务启动、停止完成、释放以及该区间无超时。

### 5.5 日志与听音的证据边界

- 按设备时间、音源及回调归属区分录音回放和提示音。其他时段的 `dec_err` 不能直接判本次录音失败，也不能忽略为全日志正常。
- 按帧数计算时长，对照播放耗时和 `read/written`。数据完整送入链路不等于尾音、音调和听感已经验收。
- active=1/2 表示算法输入 MIC0/MIC3，物理位置需实测；淡化期可能混合两路，active 表示目标通道。
- 约每秒 RMS/active 日志不能判断每次切换质量。`max_ms` 仅是毫秒级算法调用最大耗时，不含编码和调度，不代替 P99、CPU 或资源余量。
- 测试保存建议至少 15 秒，避免既有少于 4000 字节丢弃策略影响结论；不能按总文件大小猜编码格式。

### 5.6 重大 Bug：离线动态单声道录音因 FIFO 丢数自动结束（2026-09-22，修复已实现、待实机验收）

#### 5.6.1 影响、证据与结论边界

日志：[录音自动结束.txt](../录音自动结束.txt)。该日志未包含完整启动过程，固件构建标识和测试条件需随复测补齐并归档；以下代码归因依据当前源码及 Git 提交差异。

**影响：用户未请求停止，离线录音被固件提前终止，停止后的会议内容不再采集。这是核心录音功能的重大可靠性缺陷，阻断生产验收。** 已实机确认离线动态单声道；普通在线 CHAT 保存及 stream-only 同样启用动态模式的配对健康检查，也必须回归，不能将未复现场景写为已受影响或已通过。CALL、双声道回退不启用该配对检查，但共享保存路径仍需回归。

关键实现位于 `source_dev1_file.c` 的 `source_input_write/source_dev1_pair_health`、`effect_dev2_node.c` 的 `audio_effect_dev2_run/effect_dev2_fail`、`translation_ear_recoder.c` 的故障投递，以及 `rdx_record.c` 的 STOP 和本地保存路径。

- **高优先级根因假设：**音频处理路径仍直接同步调用 `rdx_uxfile_raw_write()`；每路 FIFO 仅约 160 ms，而最后一轮写文件相关日志跨度约 201 ms，紧接着出现故障，符合消费阻塞导致 FIFO 溢出的模式。但该跨度包含日志、调度等因素，尚不是精确的存储调用耗时；不能把存储阻塞确诊为唯一根因。
- **不是本次时长限制触发：**当前 `RDX_RECORD_LIMIT_TIME=((5*60*60-2)*1000)` 仍有效，录音初始化启动定时器，到期调用 STOP，即 4 小时 59 分 58 秒。它与本次约 17 分钟的 `-20` 故障无关。若产品要求无固定时长上限，须另行移除该定时停止逻辑并覆盖跨原阈值长测，不能把修复 `-20` 等同于已取消限时。

本轮设计缺口是：新增严格双麦同步保护，却未验证同步存储、实时任务调度及缓冲容量能否共同满足长录音；也未提供经过验证的配对恢复机制。保护避免错位音频继续处理的目的成立，但不能靠用户整段录音提前结束来满足正常介质延迟下的稳定性要求。

#### 5.6.2 推荐修复方案：实时音频与存储解耦，保持明确的数据所有权

以下为修复设计与最终验收要求。首轮已实现范围见 5.6.4；完整耗时分布、实机延迟注入、长测和异常提示体验尚未全部验收。

1. **先补低开销观测，建立可复现基线。**记录两路 FIFO 当前/最高水位、首次丢数时刻及写入长度、采集/配对/编码帧数、任务调度间隔、择优加编码耗时，以及 RAW/元数据/flush 调用耗时的平均值、P99、最大值。故障打印包含明确 stage/reason、session generation 和水位；常态使用内存计数及低频汇总，避免每帧或大量十六进制串口输出干扰实时性。分别对照日志开关、stream-only/本地保存、固定选路/动态模式，区分算法开销、存储和调度因素。
2. **将存储移出实时音频回调。**推荐使用预分配、有界的编码数据队列，由专用存储 worker 负责聚合和写入。音频回调只完成帧处理及有限时间的数据复制/入队，不等待文件系统、不动态申请内存、不执行同步元数据持久化。队列必须复制或转移明确归属的缓冲，不能保存随后会被音频框架释放/复用的帧指针。目标是音频不受正常范围内的存储长尾延迟阻塞，而不是仅将写操作搬到仍会阻塞音频的另一个回调。
3. **元数据与文件库调用由同一存储顺序约束保护。**首帧可先入内存队列，worker 必须在第一笔 RAW 写入前完成本会话 `.mta` 持久化及校验。复用现有格式记录与 RAW/DAT 协议；先审计 RDX 文件库线程归属、并发和已有文件任务约束，保证同一文件只有一个写入者，不能直接新增任务并发调用静态库。格式写入失败通过现有故障收尾路径结束，不能留下误标为成功的录音。
4. **按实测阻塞预算配置两级缓冲。**PCM FIFO 覆盖采集/处理调度抖动，编码队列覆盖存储长尾延迟，两者不能互相替代。编码队列容量至少按“最大编码字节率 × 设计可承受的存储停顿时间 + 聚合块/在途块余量”计算，并满足持续写入吞吐高于持续产出。当前单声道 2000 B/s、历史双声道 4000 B/s，应按实际支持的最大速率设计并核对 RAM；不能直接把 201 ms 当作介质最大延迟。定义高水位、容量上限及超预算处理；扩大 PCM FIFO 可作为验证或临时缓解，不能作为唯一根治。
5. **保持严格 STOP/PAUSE 与存储生命周期栅栏。**队列项目携带不可变的会话身份与帧顺序。正常 STOP 先截止本会话生产，再按序排空已接收数据、写尾部、完成现有格式/索引提交，最后发布保存完成并释放文件所有权。PAUSE/RESUME 保留文件身份和顺序；新会话不得复用仍被旧 worker 持有的缓冲。USB/PC、关机、恢复出厂设置及存储卸载必须等待或按现有生命周期规则拒绝，不能仅因音频流已停止便宣告存储空闲。stream-only 不创建保存队列文件。
6. **明确不可恢复故障，不静默丢帧。**队列满、持续介质故障或超预算不能回退为阻塞音频回调，也不能覆盖旧数据继续假装正常。锁存一次原因，由 `app_core` 收尾，明确上报录音异常及可保存范围；保留已成功写入数据和可恢复信息，避免重复提交。保存尚未完成时不得报告成功。具体错误反馈需覆盖离线用户可感知的提示和在线状态，避免只有串口日志说明异常。

优先落地“消除正常负载下丢数”的方案，保留现有双麦故障保护。**不得通过删除 `-20`、清零丢数计数、只延长 500 ms watchdog 或回退后不再自动停录来宣称修复。**本次触发的是溢出 `-20`，不是无配对超时 `-21`。

若产品后续要求短暂采集丢数后继续录音，需单独设计并验证同步恢复：在共同采样源产生共享帧序号/采样时间，两路保留身份，只向择优算法提交同一采样时刻的完整帧对；失配按明确规则丢弃完整配对范围并重建一致的算法状态，记录缺口及时间语义。当前仅凭两路缓存长度或 `drop=2/2` 无法证明同步，不能盲目清 FIFO 后继续，也不能未经评估插零或改变 RAW/DAT 的时长含义。此能力不作为首轮修复的捷径。

#### 5.6.4 首轮修复实现（2026-09-22）

新增 `rdx_record_storage.c/h`，两条产品分支的本地保存均通过 `rdx_record_storage_push()` 复制完整编码帧。音频数据回调不再调用 `rdx_record_format_frame()` 或 `rdx_uxfile_raw_write()`；按住 stream-only 仍不入保存队列。保持现有 40/80 字节固定帧格式、8000 字节 RAW 聚合、首 10 帧过滤及录音时限策略。

- **容量和所有权：**128 个 80 字节槽，两种格式均可容纳 128 个 20 ms 帧，即 2.56 秒（包含正在处理的帧）。原 8000 字节聚合空间迁到存储模块，额外编码帧空间为 10240 字节，另加状态、信号量和任务栈；任务栈配置为 768 个 32 位项。该容量是待真机定版的工程预算，不等同于已测介质最大延迟。
- **单写入者：**`rdx_rec_store` 优先级 2，低于 `jlstream`/音频处理任务；先完成首帧 `.mta` 写入、flush 和回读，再聚合 RAW。通过原库 LLVM IR 核对 RAW 写入为同步文件操作、无音频任务身份依赖；文件生成/保存仍在原控制路径，借助 begin/end 与 worker 串行。没有修改 RDX 二进制库或 RAW/DAT 协议。
- **会话与停止边界：**generation、scene、format 在 begin 固定；active 时拒绝再次 begin。生产者复制最多 80 字节后归还原帧，在途槽直到 worker 使用完才释放。依赖 sink 生命周期保证旧数据回调全部返回后才进入 exit；exit 先关闭入队并等待已接收帧及聚合尾部排空，再执行原暂停保留/停止保存、状态通知和断电检查。下一次 begin 只能在前次排空后重用内存；暂停恢复沿用原文件身份。队列中不投递跨会话的外部帧指针。
- **故障收尾：**队列满/帧长异常锁存 `REC_STORE error=-23`，RAW 写失败为 `-24`，元数据/帧校验失败为 `-25`，通过现有录音故障轮询请求 STOP（外层 storage fault 为 `-22`）。溢出仍按序保存此前已接收的前缀；I/O 失败不重试可能已部分写入的块，也不继续拼接后续字节。排空结束后锁存存储错误，USB/DUT/解绑保存结果也检查此错误。既有异常灯态与 STOP 路径沿用，未新增 APP 协议错误码；离线提示及 APP 异常体验仍需产品实测。
- **统计：**每次排空打印 `[REC_STORE] epoch=… accepted=… persisted=… peak=…/128 raw_max_ms=… meta_max_ms=… error=…`。accepted/persisted 是本次 sink 开启区间的字节数，暂停前后需要求和。成功收尾应相等；故障时结合差值检查未持久化范围。最长耗时包含该调用内的调度停顿；本轮未实现 P99、两路 PCM FIFO 峰值等完整遥测。
- **保护保持：**未清零丢数计数、未删除 `-20`，未更改 `-21` 的 500 ms 阈值，也未扩大 PCM FIFO。若仍出现 `-20`，必须继续定位采集/算法/日志/系统调度停顿，不能关闭保护掩盖问题。

### 6.2 稳定性、异常与资源

| 待测项 | 验收记录要求 |
| --- | --- |
| 长录音 | 普通录音、stream-only 各至少 2 小时，记录输入/算法/编码/接收帧数、FIFO 水位及丢数；无新增处理导致的丢帧，差异可解释 |
| 生命周期 | 启停至少 100 次、暂停恢复至少 100 次，清理后资源回到可重复基线，无持续内存增长或单例残留 |
| 实时性 | BLE 与存储负载下统计算法加编码耗时平均值、P99、最大值；按 20 ms 周期定版余量，不仅看平均值 |
| 双路同步 | 用同步信号或实际 PCM 验证共同采样时刻、分支延迟、启动帧对应关系，补齐双路基线样音 |
| FIFO 故障 | 注入单路溢出、停产及恢复，验证故障锁存和收尾，无无限等待或错位继续编码；实测定版 500 ms 等待阈值 |
| 失败注入 | 分配、create/process、编码失败、投递忙、停止与故障同时发生、旧错误迟到；记录停止次数、资源释放及下次启动 |
| 存储恢复 | 在有备份的专用测试介质上验证 DAT 缺失、录音/索引替换时掉电，核对格式、CRC、实际解码和异常准入；主机模拟通过不代替实测 |
| CPU/RAM/功耗 | 同条件对比双声道基线，记录峰值、稳态和最低余量，产品负责人定版允许增量 |
