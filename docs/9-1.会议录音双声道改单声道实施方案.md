# 会议录音双声道改单声道实施方案

本文统一维护会议录音单声道实施方案、接口核查与联调结论，更新日期：2026-09-17。目标为“双 MIC 采集、择优生成一路 PCM、单声道 Opus 编码”。当前已验证按住录音 stream-only 的固定 MIC0 单声道编码及 App 声道显示；动态择优、本地单声道保存/回放和完整音质验收尚未完成。当前实现与剩余工作见第 9 节。

现有链路详见 [9-0.会议录音双声道流程](9-0.会议录音双声道流程.md)。

## 1. 目标与范围

客户要求会议录音输出单声道。此次方案保留 MIC0、MIC3 两路采集，在编码前接入 MIC 择优算法，最终只编码一路声音。

```text
现状：MIC0 / MIC3 → 分别 DNS、AGC → 两路缓存与组帧 → 双声道 Opus → RDX / BLE、存储
目标：MIC0 / MIC3 → 分别 DNS、AGC → 两路缓存与组帧 → MIC 择优 → 单声道 Opus → RDX / BLE、存储
```

择优算法通常输出当前选中的一路；切换时通过交叉淡化混合旧、新通道，最终仍然输出一路 PCM。它不等于始终平均混音，也不负责说话人识别、分离或多人同时发言的完整保留。

本次范围是会议录音场景 `RECORD_SCENE_CHAT`。录音启停、会话绑定、RDX owner、BLE 连接和存储生命周期继续沿用现有机制。其他使用同一编码节点的场景需要排查并保持原有行为，不能无条件将所有场景改为单声道。

## 2. 参考资料及已确认事实

以下算法资料已在本机核查，计划在动态择优阶段单独引入，不包含在本次固定选路里程碑提交中。

| 资料 | 已确认内容 | 使用方式 |
| --- | --- | --- |
| `sl_mic_select.h` | 支持 2 或 4 路 int16 PCM 输入，输出一路；16 kHz 下按每路 320 点处理；静态单例 | 当前会议场景采用两路配置 |
| `一些参数1.txt` | 能量、削波、切换确认、驻留和淡化参数 | 作为初始调试参数，不直接视为产品最优值 |
| `一些参数2.txt` | 初始化配置示例，其中 MIC 数量按四路填写 | 改为两路，并核对所有配置字段 |
| 参考 `effect_dev2_node.c` | 气导/骨导处理后，以 `nch=1` 编码 | 仅参考单声道编码接法，不能直接覆盖工程文件 |
| `libsl_V2_0722.a` | 已用工具确认导出 `sl_mic_select_*` 和 `sl_audio_*` 符号 | 独立目标链接已通过，完整固件运行资源仍需验证 |

参考 C 文件调用的是 `sl_audio_process_bone_air()`，并不是 `sl_mic_select_process()`。当前 MIC0/MIC3 的采集关系不能直接解释成“气导麦 + 骨导麦”，本方案采用头文件描述的 MIC 择优接口。

## 3. 哪些部分复用，哪些部分修改

| 环节 | 计划 |
| --- | --- |
| MIC0/MIC3、ADC、两路 DNS/AGC | 首轮保留，实测 AGC 是否削弱择优依据 |
| EffectDev3 / EffectDev1 写两路缓存 | 复用 |
| Source_Dev1 等齐两路、每路取 320 点 | 复用，保持双路输入 |
| EffectDev2 编码前处理 | 新增择优算法，输出单路 320 点 PCM |
| Opus 编码库 | 复用，会议场景改为 `nch=1`，调整输入及码率 |
| 节点声道协商 | 明确区分双路采集输入与单声道编码输出 |
| RDX/BLE、录音存储 | 尽量复用，核对声道、帧长、封装假设 |
| App 解码、本地回放 | 核对单声道及码率兼容性，必要时同步修改 |

不能简单把 `global_ch_mode` 改成单声道。当前它参与 Source_Dev1 取数和格式传递，提前改成单路可能使择优算法拿不到第二路输入。也不能仅将 Opus 的 `nch` 改成 1，而不处理算法输入、节点协商及输出说明。

### 3.1 数据量与协议边界

| 项目 | 当前双声道 | 目标单声道 |
| --- | --- | --- |
| 采集和择优输入 | 每路 16 kHz、16 bit、20 ms | 保持两路，各 320 点 |
| 编码入口 PCM | 1280 字节：L 640 + R 640 | 择优输出 640 字节 |
| Opus 声道数 | 2 | 1 |
| 按现有公式计算的目标码率 | 32 kbit/s | 16 kbit/s |
| 按目标码率估算的每帧输出 | 约 80 字节 | 约 40 字节 |

编码后长度必须使用 `encLen`，不能将估算值写成固定包长。单声道也可以选择其他码率；首轮以现有公式得到的 16 kbit/s 为候选，音质验收后确定。

“仍是 Opus”不等于“所有包格式不变”。PCM 输入布局、编码声道和码率会变化；外层 RDX 包头、分片及帧边界能否保持不变，需核对库协议和接收端。当前可见 C 源码不足以证明这一点。

## 4. 阶段一：建立基线并核对接口

**目标：确认接入位置和端到端格式约定，形成可对照的双声道基线。**

工作内容：

1. 保存当前会议录音的构建结果、关键日志和样音，记录固件版本及音频资源版本。
2. 沿 `translation_ear_recoder.c → Source_Dev1 → EffectDev2 → Sink_Dev1` 核对场景、格式协商和实际帧长，列出其他复用场景。
3. 验证算法库适配 AC701N/BR28 的工具链、ABI 和依赖；核对头文件与库版本匹配。
4. 确认算法处理返回值的成功/失败语义、两路模式未用输入指针的传法、初始化与销毁约束。头文件未明确的部分以供应方说明或可验证结果补齐，不猜测。
5. 核对 RDX 音频封装、App 解码和本地回放是否写死双声道、80 字节帧长或固定码率，明确是否需要格式标识或版本区分。
6. 明确客户验收的是单声道编码输出，以及择优对多人同时发言的取舍是否符合会议场景需求。
7. 提前采集同一时段的两路实际 PCM，在能够运行该库的目标环境中验证择优，覆盖靠近不同 MIC、轮流发言、噪声和同时发言。对比 DNS/AGC 后的 RMS 与选路结果；若能量差被拉平或噪声持续占优，先确定参数或接入位置调整方向，再进行完整接入。
8. 核查双路采集的时间对应关系、FIFO 丢数方式和单路停产检测能力，明确场景策略传入节点的接口及异常上报路径。

当前编码配置为 `format_mode=0`，JL 接口注释称其为“百度无头”，不能直接假定为接收端可独立解析的标准 Opus 包。接口核对表须记录封装模式、帧边界来源、声道信息来源、实际帧长范围、RDX 分片重组规则和新旧录音识别方式；每项结论注明源码、协议资料或抓包/解码依据。

交付物：基线样音与日志、接口核对表、接收端兼容性结论、待确认问题清单。

通过条件：算法调用约定和场景边界明确；协议及接收端已确定兼容方式；实际双路 PCM 的择优试验已形成接入位置结论。可以先独立验证算法链接，但未确认的协议假设不得作为产品完成依据。

## 5. 阶段二：接入双 MIC 择优与单声道编码

**目标：在会议录音中建立完整的两路输入、一路编码链。**

主要文件：

- `SDK/Makefile`：加入经验证的算法库与头文件路径。
- `SDK/audio/framework/nodes/effect_dev2_node.c`：算法生命周期、两路输入检查、单路输出与单声道编码。
- `SDK/audio/interface/recoder/translation_ear_recoder.c`、`source_dev1_file.c`、`sink_dev1_node.c`：按实际协商需要调整，保证采集输入与编码输出的含义清晰。
- 项目配置头：按职责集中管理功能开关和调试参数，不修改工具生成配置来保存产品策略。

### 5.1 分两步建立链路

**阶段 2A：固定一路，验证单声道链路。** 保留双路采集与 1280 字节组帧，调试配置分别固定取 MIC0、MIC3 的 320 点进行单声道编码，暂不运行动态择优。验证实际单声道编码、App 解码及短录音保存/回放，提前执行阶段三的最小兼容性检查。固定选路仅用于调试，不作为最终交付功能。

**阶段 2B：接入动态择优。** 在 2A 通过后，将固定选路替换为算法输出，沿用已验证的编码和封装参数，再执行完整的阶段三和阶段四。保留固定选路调试能力，便于区分编码/协议问题与算法/音质问题。

### 5.2 实现要求

1. 首轮保留现有双路采集、DNS/AGC 和 FIFO 组帧，输入仍为前 320 点 MIC0、后 320 点 MIC3 的 planar 数据。
2. `sl_mic_select_create()` 配置 `sample_rate=16000`、`num_mics=2`、`analysis_samples=320`。
3. 每次处理严格检查两路输入共 1280 字节、16 bit 和采样率；输出缓冲区至少容纳 320 个 int16 样本。
4. 调用择优算法生成一路 PCM，再用 `nch=1` 的 Opus 编码；第二个 PCM 指针的传法按编码接口验证结果确定，参考示例使用 `NULL`。
5. 避免单声道输出协商反向导致 Source_Dev1 只提供一路数据。编码参数与节点对外格式说明保持一致，并验证框架的帧长计算。
6. 正确管理算法静态单例，录音停止后释放；暂停/恢复、新会话和异常退出均验证状态是否重置，不能重复 create 后继续使用失败状态。
7. 检查内存分配、算法初始化、处理和编码返回值。首版失败策略为停止该次录音并走现有清理路径，不发送未初始化 PCM 或错误格式数据。
8. 使用 `need_buf()` 核对编码工作区容量；保留当前工程的输入长度保护，不能用参考文件覆盖后退回无边界拷贝。
9. 将改动限定到会议场景，其他复用场景继续使用各自既有的输入和编码规则。

### 5.3 场景策略与资源归属

当前 EffectDev2 的 `NODE_IOC_SET_SCENE` 分支为空。阶段一需确认框架场景参数是否与 RDX 场景含义一致、是否在协商和启动前可靠到达；若不满足，通过明确的节点配置接口传递本次录音策略，记录具体接口和调用顺序。

由录音创建入口固定本次场景、采集格式、编码声道、码率和调试选路方式，保存到实例上下文并在协商前生效。运行中不依赖可变全局场景切换编码格式；会议启动缺少有效策略应报错，其他场景保留原有规则。

算法单例须记录持有者和本实例创建成功标志。重复申请失败不得影响已有持有者，只有成功持有的实例才能 reset/destroy，清理须可重复调用。当前 `run_buf`、`tst_buf_LR` 也是全局变量，应核实多实例可能性，采用实例独立存储或明确强制独占，不能只保护新增算法单例。

### 5.4 异常上报与停止流程

当前初始化函数返回 `void`，编码失败主要打印日志，需补齐失败传播机制。初始化失败应阻止节点进入工作状态；处理或编码失败后停止提交该实例音频，将错误原因和会话 token 上报现有录音管理任务。

管理任务核验 token 仍属于当前会话后，触发既有停止和收尾路径；旧会话迟到错误不得停止新会话。同一故障只触发一次停止，任务投递失败也须有明确处置和记录，不能打印后继续发送。避免在音频回调内直接销毁正在执行的链路，释放前必须确保回调已停止访问算法及缓冲区。

验证分配失败、create/process/编码失败、停止与错误同时发生、新会话收到旧错误等情况，记录错误码、停止次数、资源释放和下次启动结果。

### 5.5 双路同步和缺帧处理

两路 FIFO 都达到 320 点只保证数据量，不能独立证明时间对应。核对共同采集时钟、分支处理延迟、启动清空顺序及溢出策略，通过采集序号、累计样本计数或受控同步信号验证对齐关系。

区分“一路有数据但静音/削波”和“一路停止产出”：前者可交给算法，后者可能使组帧一直等待，算法无法自行接管。首版不隐式降级为单路采集；单路停产超过规定超时，或发现无法确认对齐的丢帧时，走异常停止流程。若后续要求不中断恢复，需另行定义成对丢弃、重新对齐和算法状态重置规则。

阶段一依据正常调度抖动和缓存容量确定等待超时的具体毫秒值，并验证正常负载不会误触发。主动制造单路 FIFO 溢出、停产和恢复，验证不会无限等待或持续处理时间错位的数据。

初始参数取参考值：能量优势 3 dB、连续确认 8 帧、最小驻留 1500 ms、交叉淡化 600 ms、冷启动 16 帧。20 ms 一帧下，8 帧为 160 ms，16 帧为 320 ms；实际切换还受驻留和其他条件约束，不能把 160 ms 当成固定响应时间。

交付物：可构建的会议单声道固件、配置说明、算法与编码运行日志。

通过条件：2A 固定选路端到端验证通过；2B 每次处理时间对应的两路 320 点并输出一路 320 点；Opus 实际以单声道初始化并正常编码；场景隔离、缺帧检测和异常清理通过，反复启停无单例残留、内存泄漏或异常输出。

## 6. 阶段三：验证发送、存储和接收端兼容

**目标：App 和本地回放能正确接收、解码单声道录音。**

工作内容：

1. 检查 `rdx_record_run_data_handle()` 到 RDX 库的长度传递，确认全链使用实际编码长度。
2. 根据协议资料或抓包确认音频帧边界、分片、格式标识；如外层格式无需变化，记录依据。
3. 验证 App 单声道解码、持续播放和保存，核对总时长、采样率及声道配置。仅凭左右耳都能听到声音不能证明编码是单声道。
4. 验证普通录音的在线发送与本地保存，以及 stream-only 的发送路径。
5. 验证本地存储聚合缓冲区跨界与停止尾部刷新。跨界丢弃剩余输入的问题已修复并通过主机行为测试（见第 9 节），物理介质落盘仍待实机验收；不能依赖约 40 字节恰好整除缓存。
6. 验证旧双声道录音与新单声道录音的回放兼容方式，避免接收端依赖不明确的格式假设。

交付物：App 解码记录、协议/抓包核对结果、在线与本地样音、完整性检查结果。

通过条件：接收端正确处理单声道，音频无因声道、码率、帧边界或存储跨界造成的截断、错速和破音；外层协议是否改变有明确结论。

## 7. 阶段四：实机调音与资源评估

**目标：验证择优对会议拾音有实际价值，并满足设备资源约束。**

| 场景 | 重点观察 |
| --- | --- |
| 同一说话人分别靠近 MIC0、MIC3 | 选中通道是否合理，弱侧切换是否及时 |
| 说话人移动、轮流发言 | 切换是否自然，是否频繁来回跳转、漏掉句首 |
| 两人同时发言 | 是否过度压低另一方，是否满足客户期望 |
| 静音、背景噪声、风噪、敲击 | 是否把噪声能量当成优质人声 |
| 一路遮挡、过弱或削波 | 通道状态及保护性切换是否符合预期 |
| 两路经过独立 AGC | 能量差是否被拉平，择优依据是否失效 |
| 长时间录音及重复启停 | CPU、RAM、功耗、缓存丢数和算法状态 |

以低频统计方式记录选中通道、各路 RMS、通道状态、处理耗时和缓存 drop，避免逐样本日志干扰实时性。调参时对比同一条件下的旧双声道样音、单路原始分支和新择优输出。

阶段一完成接入位置初步验证，本阶段扩大场景并调优。如现有 AGC 影响择优，单独评估 AGC 参数或算法接入位置；不要未经对比就删除现有降噪链。

### 7.1 验收记录与量化门限

以下是首轮工程验证要求，不代表客户已确认的产品指标。阶段一明确各项负责人；阶段四正式测试前填齐待定门限，不能用“听起来正常”替代未定版指标。

| 项目 | 首轮要求与记录方式 |
| --- | --- |
| 长时间录音 | 普通录音和 stream-only 各至少连续 2 小时；记录输入、算法、编码和接收帧数，正常条件下无新增处理导致的丢帧，帧数差异均可解释 |
| 生命周期 | 启停至少 100 次、暂停恢复至少 100 次；清理后资源回到可重复基线，无持续内存增长或单例残留 |
| 实时性 | BLE 发送及存储负载下记录算法加编码耗时的平均值、P99、最大值和 FIFO 水位；按 20 ms 输入周期核算预算，阶段一定版具体余量，不仅凭平均值判定 |
| 同步与异常 | 覆盖单路溢出、停产、恢复和各类失败注入；在已定超时内检测并收尾，无无限等待、重复销毁或旧错误终止新会话 |
| 切换质量 | 固定声源、距离和噪声条件，记录触发条件、实际切换时间、句首损失及伪音；分别评估冷启动、驻留、淡化影响，时延和漏字容忍门限定版后判定 |
| 数据完整性 | 按实际编码帧及长度核对接收/保存数据，覆盖跨界和停止时尾部刷新；无无法解释的字节丢失，解码时长按帧数及已确认的编解码延迟核算 |

### 9.2 已实现的 2A 范围与配置

仅 **CHAT 按住录音 stream-only 会话**启用固定一路单声道。普通 App 录音、本地保存、离线录音及 CALL 保持双声道，避免产生旧回放无法识别的单声道文件。尚未调用动态择优算法。

在 `SDK/apps/earphone/include/t2620_project_config.h` 配置 `TCFG_T2620_MEETING_MONO_DEBUG_MIC`：

| 值 | 行为 |
| --- | --- |
| 0 | 回退原双声道 |
| 1（默认） | 固定 MIC0 |
| 2 | 固定 MIC3 |

修改后重新构建、烧录，无运行中切换命令。数据路径如下：

```text
MIC0/MIC3 → 各自 DNS/AGC → 双路 FIFO
→ Source_Dev1：每路 320 点，合计 1280 字节 planar PCM
→ EffectDev2：固定取一路 320 点（640 字节）
→ Opus：16 kHz / 1 ch / 16 kbit/s / 20 ms / format_mode=0
→ Sink_Dev1：按实际 encLen 提交 → 原 RDX/BLE → App
```

- recorder 在协商/start 前通过 `NODE_IOC_SET_PRIV_FMT` 传入实例策略；保持采集 `global_ch_mode=AUDIO_CH_LR`，EffectDev2 明确两路输入、一路输出，拒绝不匹配流程及 eSCO 组合。
- 编码工作区按 `need_buf()` 分配，工作区及 PCM 缓冲由实例持有；单声道编码第二 PCM 指针为 NULL，本轮真实编码已运行成功。压缩帧独立提交，长度使用 `encLen`，不写死 40 字节。
- 分配/open 失败阻止启动；坏帧、输出分配或编码失败后停止提交。音频回调记录故障，由 100 ms 定时检查投递 app_core 收尾，队列满重试；epoch 和绑定 token 防止旧会话错误停止新会话。
- `rdx_record.c` 两条本地写入分支共用 append/flush，循环处理跨 8000 字节缓存的余量和结束尾部；写失败停止处理余量，防止重复提交。该修复不改变 stream-only 和原有过滤规则。

### 9.3 App 声道显示修复

根因是 `rdx_record_auto_run()` 在 CHAT 启动/恢复时将 record_mode 固定设为双声道。现根据实际格式，在投递录音任务前设置模式：`format=1` 对应 `mode=0`（单声道），双声道及 CALL 为 `mode=1`；停止/暂停保留本次模式。

单声道状态报文为：

```text
[RDX_RECORD_REPORT] format=1 mode=0 channels=1
开始：*DEV#record#1#0#1#0#1#0#
停止：*DEV#record#0#0#1#0#1#0#
```

sample 是采样率枚举，16 kHz 单/双声道均为 1；其后的 record_mode 才是此次修正的声道模式。外层 RDX 包头和发送入口沿用现有实现。此次显示问题通过 C 源码修复，新增的 devrec 静态库补丁已撤回；原有 uxfile 存储补丁保留。
