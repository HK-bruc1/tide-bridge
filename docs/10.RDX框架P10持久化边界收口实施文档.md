# RDX 框架 P10 持久化边界收口实施文档

> 日期：2026-07-24
> 当前状态：P9 已完成；P10 的代码迁移、静态边界和 Mac 静态审核已完成，Windows/JL 配置矩阵、生产 clean build、map/产物归档和 CC 目标板回归待生产环境执行。
> 上游依据：P9 最终验收归档、`docs/3.RDX框架JL平台复用性优化大纲.md`、当前源码持久化调用盘点。
> P10 定位：保持持久化数据和产品行为不变，将 RDX 业务代码对 JL `syscfg_*` 的直接依赖收口到既有 JL storage port。

## 1. 结论

P10 的核心目标不是新增一套 Storage service，也不是重写 VM 数据模型，而是建立一条单向且可防退化的持久化依赖链：

```text
RDX 业务 / domain module
        |
        | 语义 key、固定长度契约或明确的 legacy blob 契约
        v
port/jl/include/rdx_jl_storage.h
        |
        | JL key -> syscfg id 映射、返回值归一化
        v
port/jl/<chip>/rdx_jl_storage.c
        |
        v
JL syscfg_read / syscfg_write / syscfg_read_string
```

P10 完成后：

1. 活跃业务路径不再直接调用 `syscfg_read`、`syscfg_write` 或 `syscfg_read_string`。
2. 业务代码不再传递 `VM_RDX_*`、`CFG_BT_NAME`、`CFG_BT_MAC_ADDR` 等 JL 原始 ID。
3. 固定长度 VM 数据继续采用“仅精确长度传输才成功”的契约。
4. BLE 名称保留历史变长记录兼容，不能被机械改成固定长度读取。
5. `rdx_storage_service` 继续负责 SD、文件、格式化和文件同步，不承载 VM 持久化。
6. `librdxApp.a`、旧 ABI、VM ID、数据布局、默认值、写入时机和 CC 产品行为保持不变。

P10 必须按“契约冻结 -> port 完善 -> 低风险状态 -> 录音状态 -> BLE 敏感状态 -> 最终闭环”的顺序执行。禁止一次性替换全部调用后统一调试。

> **P10 第一硬约束：不得破坏 `librdxApp.a` 的 ABI。** P10 只允许在旧入口内部增加 storage port 转发；不允许修改静态库二进制，不允许删除、改名、隐藏或改变静态库依赖的函数、全局变量、回调和数据布局。任何 ABI 门禁失败都必须立即停止当前阶段，不能用 clean build 或目标板“看起来正常”替代 ABI 证明。

## 2. 范围与约束

### 2.1 P10 范围

P10 处理以下持久化边界：

- `rdx_vm.c`：绑定状态和充电仓配对信息。
- `rdx_rtc.c`：软件 RTC 恢复时间戳。
- `rdx_dut.c`：按键进入 DUT 的持久化禁用标志。
- `rdx_record.c`：MIC gain 和录音异常重启标志。
- `rdx_ble_server.c`：BLE 名称、BLE MAC 和 JL 工厂 BT MAC 读取。
- `rdx_device_service.c`：恢复出厂路径中的 JL BT 名称配置访问。
- `port/jl/include/rdx_jl_storage.h`：逻辑 key、传输语义和平台配置语义接口。
- `port/jl/jl7018/rdx_jl_storage.c` 与 `port/jl/jl7018_shadow/rdx_jl_storage.c`：JL ID 映射和实际 `syscfg_*` 调用。
- `tools/check_rdx_boundaries.ps1`：P10 静态边界门禁。
- `tests/host/`：必选静态契约检查和可选 storage port 可执行 mock。

### 2.2 第一硬约束：`librdxApp.a` ABI 完整保护

P10 不授权任何静态库 ABI 变化。保护范围不是“静态库文件没有改”这一项，而是同时覆盖二进制、符号、数据结构、回调和行为五层契约。

| 保护层 | P10 必须保持不变 | 禁止操作 |
|---|---|---|
| 静态库二进制 | `librdxApp.a` Git blob 与 SHA256 | 反编译后修改、重编译、替换 archive 成员、重新打包 |
| 外部符号 ABI | 静态库引用的函数名、全局变量名、可见性、调用约定、参数和返回类型 | 删除、改名、改签名、改成 `static`、条件编译掉、改变链接可见性 |
| 数据布局 ABI | `RdxProtocolCallbacks`、`RdxProtocolIndicateOps`、`RecordStatus`、`MicGainPara` 以及静态库可见结构体的字段顺序、类型、大小、对齐 | 增删字段、调序、改类型、改变 packing/alignment |
| 回调契约 | 回调字段位置、函数指针类型、NULL 允许性和注册时机 | 重排回调表、用不兼容强转绕过编译、改变初始化生命周期 |
| 行为兼容 | 旧入口成功/失败返回口径、默认值、同步/异步时序和必要副作用 | 将 `rdx_err_t` 直接穿透旧 ABI、改变成功长度、吞掉旧副作用 |

执行原则：

1. **旧入口默认受保护**：P10 触及的 `rdx_vm_*`、`rdx_record_*`、`rdx_ble_server_*` 旧函数，在证明不属于静态库依赖前，一律按 ABI 入口保护。
2. **只允许 thin wrapper**：旧函数签名和外部符号保留，内部可改为调用新的 storage port，再将 `rdx_err_t` 映射回旧返回语义。
3. **新增接口只做加法**：新的 logical key、blob 和 factory config 接口只能作为 RDX 内部增量接口，不能要求修改或重新编译 `librdxApp.a`。
4. **ABI 基线固定不漂移**：ABI 比对继续使用首次冻结静态库边界的固定 P8 基线 `5d0284f17006bd333de992ed22d5a1c7484c37a0` 和 SHA256 `c540d70540dc4d61e15d1ca13579cd2342d4ea972ff0a74a1afccc04b1ef4aca`；P9 最终提交只作为 CC 构建和行为基线，不能替代固定 ABI 基线。
5. **触及符号清单必须前置**：P10.0 使用 JL 工具链的 `llvm-nm`/等价工具读取 archive undefined symbols；工具不可用时从最终 CC `.map` 的交叉引用反推。将本次触及的 VM、Record、BLE 外部入口加入 ABI 保留清单。
6. **门禁必须逐提交执行**：任何 P10 代码提交在进入生产 clean build 前，必须先通过固定基线 ABI 脚本；失败时停止该阶段，不得继续板测或更新基线掩盖差异。

除 ABI 外，P10 还必须保持：

- 不修改 `VM_RDX_*` 与 `CFG_BT_*` 的数值。
- 不修改 `EarphoneInfo`、`MicGainPara`、`time_t` 或其他已持久化结构的字段、顺序、对齐和长度。
- 不改变绑定、配对、恢复出厂、RTC restore、DUT、MIC gain、录音恢复、BLE 名称和 BLE MAC 的现有产品语义。
- 不改变 APP 与设备之间的协议命令、响应、事件和字节流。
- 不升级 JL SDK、编译器或生产工具链；P10 只做当前 SDK 内的代码组织和依赖收口。
- 新增 core/service public header 不得暴露 `OS_MUTEX`、`OS_SEM`、`cbuffer_t`、`IO_PORT*`、`APP_MSG_*` 或其他 JL 私有类型。
- 新增抽象保持轻量；最终 CC map 中 P10 引入的 RDX Flash/RAM 净增长必须不超过 P9 基线的 `2%`，任何增长都要按 symbol/section 说明来源。
- 不将 VM 持久化并入 `rdx_storage_service`。
- 不在 P10 同时实施 BLE/Record 深度 service 化、全量 OSAL、SPI 重构或 `rdx_app.c` 行数优化。
- 不为 EP 或 shadow 填写未经目标板确认的默认值和硬件行为。
- 不以 Host mock 替代 CC clean build 和目标板回归。

### 2.3 明确非目标

以下内容不属于 P10：

- 设计数据库、KV 框架、版本迁移框架或通用序列化层。
- 引入动态分配、反射、注册表或大型 storage vtable。
- 将所有状态包装成独立 getter/setter 文件。
- 修改恢复出厂流程的业务顺序。
- 修正与本次边界迁移无关的历史数据内容。
- 宣称 EP 或 `jl7018_shadow` 已完成硬件持久化验证。

## 3. 启动基线与当前实施状态

### 3.1 P10 启动时已有基础

当前已经存在：

- `rdx_storage_read()`：固定长度 VM 读取，`ret == len` 才返回 `RDX_OK`。
- `rdx_storage_write()`：固定长度 VM 写入，`ret == len` 才返回 `RDX_OK`。
- `rdx_storage_cfg_read_string()` / `rdx_storage_cfg_write()`：JL 配置区薄 wrapper。
- `jl7018` 和 `jl7018_shadow` 两份 storage port 实现。
- MIC gain 已通过 storage port 读写，并执行写后读回与逐字节校验。

P10 应复用并收紧这些基础，不新建平行 persistence service。

### 3.2 P10 启动时的直接依赖

当前活跃业务路径仍直接访问：

| 文件 | 持久化内容 | 当前直接调用 |
|---|---|---|
| `rdx_vm.c` | 绑定状态、`EarphoneInfo` | `syscfg_read/write` |
| `rdx_rtc.c` | RTC 初始化时间戳 | `syscfg_read/write` |
| `rdx_dut.c` | DUT key disabled 标志 | `syscfg_read/write` |
| `rdx_record.c` | 录音异常重启标志 | `syscfg_read/write` |
| `rdx_ble_server.c` | BLE 名称、BLE MAC、工厂 BT MAC | `syscfg_read/write` |

`rdx_device_service.c` 虽然已经通过 wrapper 访问 `CFG_BT_NAME`，但仍在业务层传递 JL 原始 ID，P10 也需要收口。

### 3.3 `rdx_battery.c` 死代码边界

P10 启动基线中，`rdx_battery.c` 的两个 `syscfg_*` 命中位于完整的 `#if 0` 区块，不参与当前产品编译，其中写入代码还使用了与 charge time 不匹配的历史 ID。

P10 不为该死代码新增 storage key 或迁移接口。执行时采用以下二选一策略，并在提交说明中记录实际选择：

1. 确认无保留价值后删除完整 `#if 0` 区块；这是推荐方案。
2. 暂时保留时，在静态门禁中只允许该文件该禁用区块的精确命中，并额外校验命中仍处于 `#if 0` 内。

禁止把这段死代码恢复为活跃逻辑，或借 P10 猜测 charge time 的真实持久化契约。

本次实施采用推荐方案，已删除该完整 `#if 0` 区块，没有新增 charge time storage key。

## 4. 持久化契约表

### 4.1 RDX 自有 VM

| 逻辑 key | JL ID | 数据长度 | 当前默认/失败策略 | 写入时机 | P10 传输契约 |
|---|---|---:|---|---|---|
| `BOUND_STATUS` | `VM_RDX_NOTTA_BOUND_STATUS` | `1` | RAM 初始为 `0`；读失败保持未绑定语义 | 绑定、解绑流程 | 固定长度 exact |
| `CUSTOM_AUTH` | `VM_RDX_CUSTOM_AUTH` | `sizeof(EarphoneInfo)` | 读失败清零 `epInfo` | 充电仓配对信息更新 | 固定长度 exact |
| `RTC_INIT_VALUE` | `VM_RDX_RTC_INIT_VALUE` | `sizeof(time_t)` | 读失败、`0` 或年份越界均视为无有效时间 | RTC store、恢复出厂时间保存 | 固定长度 exact |
| `KEY_DUT_DISABLED` | `VM_RDX_KEY_DUT_DISABLED` | `1` | 默认 `0xFF`，仅 `0xAA` 表示禁用 | finalpack end、重新启用 DUT | 固定长度 exact |
| `MIC_GAIN` | `VM_RDX_MIC_GAIN` | `sizeof(MicGainPara)` | 缺失、短读或非法值使用安全默认；必要时修复写回 | MIC gain 设置、恢复出厂、录音启动修复 | 固定长度 exact + 写后读回 |
| `REC_ERR_REBOOT` | `VM_RDX_REC_ERR_REBOOT` | `1` | 读失败保持局部默认 `0xFF` | 录音异常恢复、恢复出厂清零 | 固定长度 exact |
| `BLE_NAME` | `VM_RDX_BLE_NAME` | 历史为 `1..24`，部分路径写 `24` | 缺失时按 `BLE_LOCAL_NAME + auth suffix` 生成默认名 | 默认生成、用户改名、恢复出厂 | legacy blob，允许正长度短记录 |
| `BLE_MAC` | `VM_RDX_BLE_MAC` | `6` | 缺失、短读、全 `00` 或全 `FF` 时读取 controller MAC 并写回 | 首次缺失或非法时修复 | 固定长度 exact |

说明：

- `RDX_VM_ID_CHARGE_TIME_INFO` 在启动基线中只服务于禁用死代码；该死代码已删除，不进入 P10 活跃 key 集合。
- 固定长度 exact 的含义是：读到 `0` 返回 `RDX_ERR_NOENT`；负值、短读和超预期返回 `RDX_ERR_IO`；只有恰好传输请求长度返回 `RDX_OK`。
- 业务层继续决定默认值、有效范围和修复策略；port 只负责传输事实，不替业务层猜测默认值。

### 4.2 JL 工厂/系统配置

| 语义接口 | JL ID | 长度 | 所有权 | P10 规则 |
|---|---|---:|---|---|
| BT 工厂名称读取/重写 | `CFG_BT_NAME` | `LOCAL_NAME_LEN` | JL 系统配置 | 业务层不得传原始 ID；保持现有恢复出厂调用顺序和数据内容 |
| BT 工厂 MAC 读取 | `CFG_BT_MAC_ADDR` | `6` | JL 系统配置 | 只提供语义读取；RDX 当前路径不写该 ID |

这两项不是 RDX 自有 VM，不得加入名为 `RDX_VM_ID_*` 的枚举，也不得与 BLE 自有名称/MAC 混为同一数据源。

## 5. 目标接口设计

### 5.1 逻辑 key 与 JL ID 解耦

`rdx_jl_storage.h` 不再通过枚举值直接暴露 `VM_RDX_*`，也不再要求业务代码 include `syscfg_id.h`。推荐接口形态：

```c
typedef enum {
    RDX_STORAGE_KEY_BOUND_STATUS = 0,
    RDX_STORAGE_KEY_CUSTOM_AUTH,
    RDX_STORAGE_KEY_RTC_INIT_VALUE,
    RDX_STORAGE_KEY_DUT_DISABLED,
    RDX_STORAGE_KEY_MIC_GAIN,
    RDX_STORAGE_KEY_REC_ERR_REBOOT,
    RDX_STORAGE_KEY_BLE_NAME,
    RDX_STORAGE_KEY_BLE_MAC,
} rdx_storage_key_t;

rdx_err_t rdx_storage_read(rdx_storage_key_t key, u8 *buf, u16 len);
rdx_err_t rdx_storage_write(rdx_storage_key_t key, const u8 *buf, u16 len);
```

`jl7018` 与 `jl7018_shadow` 各自在私有 `.c` 中通过 `switch` 将逻辑 key 映射到真实 JL ID。未知 key 返回 `RDX_ERR_NOTSUP`，空指针或零长度返回 `RDX_ERR_INVAL`。

现有 `RDX_VM_ID_*` 名称如果已被其他内部源码使用，可在 P10 迁移窗口内保留兼容别名；P10 完成时业务源码应统一使用逻辑 key，不保留对 JL ID 数值的依赖。

### 5.2 固定长度接口

`rdx_storage_read/write` 继续承载固定长度数据：

- port 不填默认值。
- port 不校验业务字段是否合法。
- port 不自动重试和写回。
- port 不吞掉短读、短写或底层负错误。
- caller 根据 `RDX_OK`、`RDX_ERR_NOENT`、`RDX_ERR_IO` 决定保持默认、修复或返回旧 ABI 结果。

### 5.3 BLE 名称 legacy blob 接口

BLE 名称必须使用独立接口，推荐形态：

```c
rdx_err_t rdx_storage_read_blob(rdx_storage_key_t key,
                                u8 *buf,
                                u16 capacity,
                                u16 *actual_len);

rdx_err_t rdx_storage_write_blob(rdx_storage_key_t key,
                                 const u8 *buf,
                                 u16 len);
```

约束：

- 仅 `RDX_STORAGE_KEY_BLE_NAME` 允许使用 blob 接口。
- `1..capacity` 的正长度读取均返回 `RDX_OK` 并输出 `actual_len`。
- caller 在读取前清零 `capacity + 1` 缓冲区，读取后保证字符串终止。
- `0` 返回 `RDX_ERR_NOENT`；负值或大于 capacity 返回 `RDX_ERR_IO`。
- 写入成功要求底层返回值与本次 `len` 一致。
- P10 不在读取旧短记录后自动扩写为 24 字节，避免改变写入时机和增加 Flash 写次数。
- 默认名生成路径继续按当前实际长度写入；用户改名和 reset 路径继续保持当前写入长度。

### 5.4 JL 配置语义接口

业务代码不再调用接受任意 `u16 id` 的通用配置接口。推荐替换为：

```c
rdx_err_t rdx_storage_read_factory_bt_name(void *buf, u16 len);
rdx_err_t rdx_storage_write_factory_bt_name(const void *buf, u16 len);
rdx_err_t rdx_storage_read_factory_bt_mac(u8 mac[6]);
```

原 `rdx_storage_cfg_read_string()` 和 `rdx_storage_cfg_write()` 在所有调用点迁移后删除；若经 ABI 扫描确认存在外部依赖，则保留为内部兼容 wrapper，但不得继续新增调用点。

### 5.5 错误码与旧 ABI 映射

port 新接口统一返回 `rdx_err_t`。旧业务函数保持原签名，并在内部映射：

| 旧函数类型 | 成功映射 | 失败映射 |
|---|---|---|
| `void` setter | 保持 `void`，记录明确错误日志 | 不改变调用者控制流 |
| `int` 且历史返回传输长度 | 返回原成功长度 | 返回 `-1` 或原有失败口径 |
| 指针 getter | 返回现有 RAM cache | 按原逻辑返回默认值、清零对象或 `NULL` |
| `u8` getter | 返回读取值 | 返回原局部默认值 |

禁止将 `rdx_err_t` 直接穿透到旧协议 ABI，导致上层看到新的负值语义。

## 6. 分阶段实施

### 6.1 P10.0：基线与契约冻结

实施：

1. 记录 P10 起始 commit、工作区状态、P9 最终 CC 固件 SHA256、map 和 `librdxApp.a` SHA256。
2. 使用固定 P8 ABI 基线执行 `test_rdx_static_library_abi.ps1`，确认 P10 起点没有既有 ABI 漂移。
3. 扫描 `librdxApp.a` undefined symbols 或 P9 最终 CC map 交叉引用，建立 P10 触及符号保留清单，至少核对 `rdx_vm_*`、`rdx_record_*`、`rdx_ble_server_*` 相关入口和全局依赖。
4. 将现有 ABI 脚本未覆盖、但在 P10 中会触及的旧函数签名、全局变量或结构体加入固定基线检查；禁止只依赖编译器报错发现 ABI 问题。
5. 用当前源码刷新全部 `syscfg_*` 命中，区分活跃路径、port 和 `#if 0` 死代码。
6. 确认第 4 节契约表与生产行为一致，尤其确认：
   - `sizeof(EarphoneInfo)`、`sizeof(MicGainPara)`、`sizeof(time_t)` 的 JL 编译结果。
   - BLE 名称历史记录的实际返回长度。
   - DUT `0xAA/0xFF` 语义。
   - RTC 有效年份范围。
7. 保存一块已绑定且设置过 BLE 名称、MIC gain、RTC 的 CC 板作为升级兼容样本。

验收：

- 契约表每一项都有 ID、长度、默认值、短读策略、写入时机和回归用例。
- P10 基线能关联到 P9 最终 CC 产物与板测记录。
- `librdxApp.a` blob、SHA256、协议兼容头和 P10 触及符号保留清单已冻结。
- 固定 P8 ABI 基线检查在任何 P10 代码修改前通过。
- 未确认的历史行为不得在后续阶段凭推测修改。

### 6.2 P10.1：完善 storage port 契约

修改：

- `port/jl/include/rdx_jl_storage.h`
- `port/jl/jl7018/rdx_jl_storage.c`
- `port/jl/jl7018_shadow/rdx_jl_storage.c`
- `tests/host/test_rdx_storage_contract.ps1`（新增）
- `tests/host/test_storage_port.c` 与必要 mock（新增，可执行检查）

实施：

1. 将 public key 改为与 JL 数值无关的逻辑枚举。
2. 在两个 port 私有实现中建立同构 key -> JL ID 映射。
3. 保持固定长度 exact 语义。
4. 增加 BLE 名称 blob 接口。
5. 增加 BT 工厂名称和 MAC 语义接口。
6. 对空指针、零长度和未知 key 返回明确错误。
7. 不修改任何业务调用点，先单独验证 port。

必选静态契约覆盖：

- public header 不 include `syscfg_id.h`。
- public enum 不引用 `VM_RDX_*` 或 `CFG_BT_*`。
- 两个芯片 port 的 key 集合一致。
- exact read/write 保持精确长度判断。
- blob read 保留实际正长度。
- 工厂配置 ID 只出现在 port 私有 `.c`。

可选可执行 Host mock 覆盖：

- 精确长度读写成功。
- 缺失返回 `RDX_ERR_NOENT`。
- 负错误、短读和短写返回 `RDX_ERR_IO`。
- 空指针、零长度返回 `RDX_ERR_INVAL`。
- 未知 key 返回 `RDX_ERR_NOTSUP`。
- BLE 名称短记录读取成功并返回实际长度。
- jl7018 与 shadow 的外部契约一致。

验收：

- storage port 可独立编译。
- `librdxApp.a` blob/SHA256、静态库兼容头、回调布局和 P10 触及的旧符号签名均与固定 ABI 基线一致。
- 尚未迁移业务调用时，生产行为不发生变化。

### 6.3 P10.2：低风险 VM、RTC、DUT 迁移

修改顺序固定为：

1. `rdx_vm.c`：`BOUND_STATUS`。
2. `rdx_vm.c`：`CUSTOM_AUTH`。
3. `rdx_rtc.c`：`RTC_INIT_VALUE`。
4. `rdx_dut.c`：`DUT_DISABLED`。

迁移规则：

- 每迁移一个 key，先保持原局部变量初始化，再调用 port。
- 读失败时执行当前默认/清零逻辑，不引入新默认值。
- 写失败只增加准确日志，不改变原调用链和重启时序。
- `EarphoneInfo` 仅在 `RDX_PRODUCT_IS_CHARGE_CASE` 下参与。
- 不趁机改变 `rdx_vm_*` 的旧命名和返回类型。

每个 key 的验收：

| key | 静态/构建验收 | CC 目标板验收 |
|---|---|---|
| `BOUND_STATUS` | 原文件无对应 `syscfg_*` | 绑定后重启保持；解绑后重启保持未绑定 |
| `CUSTOM_AUTH` | charge-case 条件编译保持 | 充电仓配对信息重启后保持；无数据时安全清零 |
| `RTC_INIT_VALUE` | software/hardware RTC 配置均可编译 | 软 RTC 重启恢复；无效时间不恢复 |
| `DUT_DISABLED` | `0xAA/0xFF` 常量语义不变 | finalpack 后按键 DUT 禁用；重新启用后重启保持 |

阶段验收：

- `zenchord_cc + jl7018` clean build 通过。
- EP/shadow 配置与编译隔离不退化。
- P9 对应绑定、RTC restore、DUT 用例无回归。

### 6.4 P10.3：录音持久化迁移

范围：

- 保持 MIC gain 现有 port 读写和写后读回逻辑。
- 将 `VM_RDX_REC_ERR_REBOOT` 迁移到 exact storage 接口。
- 更新 `test_rdx_record_recovery.ps1`，覆盖两个录音持久化 key 均不直接访问 `syscfg_*`。

迁移规则：

- `rdx_record_err_reboot_flag_read_from_vm()` 读失败仍返回局部默认 `0xFF`。
- `rdx_record_err_reboot_flag_write_into_vm()` 保持旧 `int` ABI；成功返回原成功长度，失败返回非成功值。
- MIC gain 的结构长度、合法值、legacy normalize、安全默认和写后读回均不得简化。
- VM 失败不得阻塞录音启动；仍允许使用 runtime safe defaults。

验收：

- `rdx_record.c` 不再出现 `syscfg_*`。
- MIC gain 设置后查询一致，重启后保持。
- 缺失/非法 MIC gain 使用安全默认，录音仍能启动。
- 写入失败和读回不一致仍被判为失败。
- 异常重启标志可读写，恢复出厂后清零。
- BLE 录音和 WiFi 在线录音各不少于 30 秒。

### 6.5 P10.4：BLE 名称、MAC 与工厂配置迁移

这是 P10 风险最高的阶段，必须最后执行。

实施顺序：

1. 将 `rdx_device_service.c` 的 `CFG_BT_NAME` 访问迁移到 BT 工厂名称语义接口。
2. 将 `rdx_ble_server.c` 的 `CFG_BT_MAC_ADDR` 访问迁移到 BT 工厂 MAC 语义接口。
3. 将 `VM_RDX_BLE_MAC` 迁移到 exact storage 接口。
4. 最后将 `VM_RDX_BLE_NAME` 迁移到 legacy blob 接口。

BLE 名称兼容要求：

- P10.0 保存的升级样本在刷入 P10 固件后必须保留原 BLE 名称。
- 历史短记录、24 字节记录均可读取。
- 读取缓冲区必须预清零并保证终止，禁止使用未终止字符串。
- 缺失时继续按当前 `BLE_LOCAL_NAME` 和 auth suffix 规则生成默认名。
- 用户改名、恢复出厂和重新配对后的名称行为保持一致。

BLE MAC 要求：

- 6 字节有效记录直接复用。
- 缺失、短读、全 `00`、全 `FF` 时继续获取 controller MAC 并写回。
- 工厂 BT MAC 与 RDX BLE MAC 保持两个独立数据源。
- P10 不改变 `bt_make_ble_address()`、`bt_update_mac_addr()`、controller MAC 设置顺序。

验收：

- `rdx_ble_server.c` 和 `rdx_device_service.c` 不出现 `syscfg_*`、`VM_RDX_*`、`CFG_BT_*`。
- 已保存 BLE 名称升级后保持。
- 改名后广播名正确，重启后保持。
- 恢复出厂后名称恢复当前产品默认规则。
- BLE MAC 重启前后一致，非法 VM MAC 可自动修复。
- 配对、绑定、断开、重连和恢复出厂重新配对通过。
- 广播厂商数据、产品码和连接参数行为无变化。

### 6.6 P10.5：边界门禁与最终闭环

在 `tools/check_rdx_boundaries.ps1` 增加 P10 规则：

1. 活跃业务 `.c` 不得调用 `syscfg_read/write/read_string`。
2. `VM_RDX_*` 只允许出现在 JL storage port 私有实现、JL SDK ID 定义和明确的历史测试基线中。
3. `CFG_BT_NAME`、`CFG_BT_MAC_ADDR` 不得出现在 RDX 业务和 service 源码。
4. `rdx_jl_storage.h` 不得 include `syscfg_id.h` 或暴露 JL 原始 ID。
5. `rdx_storage_service.*` 不得 include `rdx_jl_storage.h`，防止 SD/file service 吞并 VM 职责。
6. jl7018 与 shadow storage port 必须实现相同 public 接口。
7. 若保留 `rdx_battery.c` 的 `#if 0` 区块，必须执行精确例外校验，禁止扩大 allowlist。

最终执行顺序：

```text
记录 P10 最终候选 commit 与工作区
  -> 静态边界与 storage 契约检查
  -> 配置矩阵与 ABI/record recovery 检查
  -> EP clean build
  -> shadow clean build
  -> 最终 CC clean build
  -> 固化 firmware/map/hash/Flash/RAM
  -> 烧录最终 CC 固件
  -> P10 持久化专项回归
  -> CC 核心链路冒烟
  -> P10 归档
```

最终 CC 构建后不得再执行会覆盖产物的 EP/shadow clean/build。

## 9. 风险与控制

| 风险 | 表现 | 控制 |
|---|---|---|
| BLE 名称短记录不兼容 | 升级后名称回退默认 | 独立 blob 接口；保存真实升级样本；短记录专项测试 |
| exact 契约改变旧失败语义 | 短读从“部分成功”变为失败 | 固定长度项逐项确认；BLE 名称作为明确例外 |
| JL ID 仍泄漏到业务层 | 只替换函数名，耦合仍存在 | 逻辑 key 私有映射；public header 禁止 `syscfg_id.h` |
| VM 与文件 storage 混层 | `rdx_storage_service` 变成万能模块 | 静态禁止其 include persistence port |
| 默认值下沉到 port | 新平台默认行为与产品语义混合 | 默认/修复策略留在业务 owner，port 只报告传输结果 |
| 旧 ABI 返回值变化 | 静态库或上层误判 | wrapper 内显式映射；固定 P9 ABI 基线检查 |
| shadow 实现漂移 | CC 编译通过但 shadow 缺接口 | 两 port 接口集合静态对比，shadow clean build |
| Flash 写次数增加 | 读取短记录时自动归一化写回 | P10 禁止读时自动扩写 BLE 名称 |
| 死代码污染边界规则 | 为 `#if 0` 添加错误 key 或扩大 allowlist | 删除死代码优先；否则只允许精确禁用区块 |
| 最终固件与回归不一致 | 测试的是中间构建 | EP/shadow 在前，CC 最后构建并立即固化 hash/map |

## 10. P10 完成定义

P10 完成必须同时满足：

- [ ] P10 起始基线与 P9 最终 CC 固件、map、目标板记录可追溯关联。
- [ ] `librdxApp.a` Git blob 与固定 SHA256 `c540d70540dc4d61e15d1ca13579cd2342d4ea972ff0a74a1afccc04b1ef4aca` 全程未变化。
- [ ] 固定 P8 ABI 基线 `5d0284f17006bd333de992ed22d5a1c7484c37a0` 未被改写或替换为浮动 baseline。
- [ ] `librdxApp.a` undefined symbols/map 交叉引用形成 P10 触及符号保留清单。
- [ ] 静态库依赖的旧函数、全局变量、回调结构和数据布局均未删除、改名、隐藏、改签名或改变布局。
- [ ] P10 新增 storage 接口为纯增量内部接口，旧入口只在函数体内转发并保持原返回与副作用语义。
- [ ] JL SDK、编译器和生产工具链版本与 P9 基线一致。
- [ ] 新增 public header 未向 core/service 暴露 JL 私有类型。
- [ ] APP 与设备之间的协议命令、响应、事件和字节流保持不变。
- [ ] 最终 CC map 中 P10 引入的 RDX Flash/RAM 净增长不超过 P9 基线 `2%`，增量已有 symbol/section 说明。
- [ ] 第 4 节全部持久化契约已按实际生产行为确认。
- [ ] `rdx_jl_storage.h` 不暴露 `syscfg_id.h`、`VM_RDX_*` 或 `CFG_BT_*`。
- [ ] jl7018 与 shadow port 使用逻辑 key 映射并实现相同接口。
- [ ] 固定长度数据保持 exact read/write 契约。
- [ ] BLE 名称通过 legacy blob 接口兼容历史短记录和 24 字节记录。
- [ ] BT 工厂名称和 MAC 通过语义接口访问，业务层不传 JL 原始 ID。
- [ ] 活跃 RDX 业务路径不直接调用 `syscfg_*`。
- [ ] `rdx_storage_service` 未承载 VM 持久化。
- [ ] `rdx_vm.c`、`rdx_rtc.c`、`rdx_dut.c`、`rdx_record.c`、`rdx_ble_server.c` 和 `rdx_device_service.c` 完成边界迁移。
- [ ] MIC gain 默认、legacy normalize、写后读回和录音不中断语义保持不变。
- [ ] 每个 P10 代码提交和最终候选版本的固定基线 ABI 门禁均通过。
- [ ] P10 静态边界、storage 契约、record recovery 和配置矩阵全部通过。
- [ ] EP、shadow、最终 CC 按顺序 clean build 通过。
- [ ] 最终 CC firmware、map、SHA256、Flash/RAM 增量和构建日志已归档。
- [ ] CC 持久化专项回归和核心冒烟全部通过。
- [ ] EP/shadow 明确记录为未执行硬件功能验证。
- [ ] 可选 Host storage mock 的状态准确记录为 PASS、FAIL 或 `OPTIONAL NOT RUN`。

以下情况不得关闭 P10：

- 只把 `syscfg_*` 替换成接受原始 JL ID 的另一个通用 wrapper。
- 修改、重编译、替换或重新打包 `librdxApp.a`，即使最终链接和板测通过。
- 删除、改名、改成 `static`、条件编译掉或修改静态库依赖的旧外部符号。
- 修改回调结构体字段顺序/类型、静态库可见结构体布局或旧函数返回语义。
- 将 ABI baseline 更新到当前提交，以“新基线通过”掩盖已经发生的 ABI 漂移。
- BLE 名称改用 exact read，导致历史短记录失效。
- 将默认值、产品参数或恢复策略放入 JL port。
- 为消除扫描命中而迁移或启用 `rdx_battery.c` 的未知死代码契约。
- 修改 VM ID、结构布局或旧 ABI 后仅凭 clean build 判定通过。
- 只执行 Host mock，没有最终 CC 固件和目标板持久化回归。
- 最终 CC 构建后又执行 EP/shadow build，覆盖归档产物。
- P10 同时混入 BLE/Record service 深度重构，无法隔离行为变化。

## 11. 归档要求

P10 完成时新增一份实际执行归档，建议路径：

```text
docs/verification/<YYYY-MM-DD>-rdx-p10-storage-validation.md
```

归档至少包含：

1. P10 起始和最终 commit、工作区状态。
2. P9 基线固件与 P10 最终固件的 SHA256、map 和 Flash/RAM 对比。
3. `librdxApp.a` Git blob、SHA256、固定 ABI baseline、触及符号保留清单与逐提交 ABI 检查结果。
4. 持久化契约确认结果和实际 JL 类型长度。
5. 静态边界、storage 契约、record recovery、配置矩阵日志。
6. EP、shadow、最终 CC clean build 命令和结果。
7. BLE 名称历史短记录升级样本的固件前后证据。
8. CC 持久化专项用例、实际结果和日志/截图/视频索引。
9. CC 核心冒烟结果。
10. 可选 Host storage mock 状态。
11. EP/shadow 未做硬件验证声明。
12. 未覆盖范围、已知限制和后续 P11 入口条件。

大型固件、map、串口全量日志和视频继续放在受控存储中；源码仓库只记录路径、文件名、SHA256 和访问方式。

## 12. 回滚

P10 每个阶段必须可独立回滚：

- port 接口错误：回滚 P10.1，不保留半套 key 映射。
- 某个 VM key 行为异常：只回滚对应迁移提交，其他已验收 key 可保留。
- BLE 名称升级异常：优先回滚 BLE name 提交，不回滚已通过的 BLE MAC 或低风险 VM 迁移。
- 发现 VM 数据兼容性问题：停止后续阶段，保留问题设备原始 VM，禁止通过恢复出厂掩盖问题。
- 最终回归失败：以 P9 最终 CC 固件作为行为参照，定位后独立修复并重新执行受影响阶段。

不得修改已发布历史、清空用户 VM 或改变 ID 来规避迁移问题。

## 13. P10 完成后的下一方向

P10 完成后，RDX 的平台持久化依赖将形成稳定边界。下一阶段建议进入 P11 领域状态与 service ownership 收口：

- 用 record/storage/device service 的命令和查询接口替代跨模块裸状态指针。
- 减少 service 对 `RecordStatus *`、`rdx_record_process()` 和 `rdx_uxfile_*` 的直接访问。
- event bus 只承担状态通知，不替代同步命令和查询。
- `rdx_app.c` 保留 ABI wrapper、平台消息入口和生命周期协调职责，不以行数作为唯一目标。

P11 不得提前混入 P10。只有 P10 最终 CC 固件完成持久化专项回归并归档后，才允许迁移状态所有权。
