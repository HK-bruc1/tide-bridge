Date: 2026-11-02

## Checkpoint status

This checkpoint retains the BLE download-then-delete repair only. On

`COM3_2026-11-02_16-37-16.log` also records, at firmware time

The approximately 3 mA idle current after BLE download is **not fixed or

without automatic deletion, so deletion is not required to trigger that
symptom. Its root cause remains unconfirmed; this repair must not be described

public entry point and host-test stubs have been removed. Existing connection

reverse-engineering artifacts and local firmware build outputs are not part of

## Scope and evidence

The reported sequence is: list files, enable download-then-delete, download over
BLE, refresh the list, then attempt another recording. The supplied reproducible
22 mA trace shows the deletion/index failure; the user also reports persistent
22 mA spikes and approximately 3 mA after PA4 is off. Neither current value is
accepted as proof of the intended low-power state.

The legacy completion path calls `rdx_uxfile_del_read_file_dat`. It can remove
the RAW and the last DAT without removing the paired MTA; later dirty-cache
invalidation can write the pre-delete index back. It also uses a truncated SN
in the legacy deletion path.

The observed `f5062.mta` orphan receives the existing management identity
`0x12000000 + 0xf5062 = 302993506` when reconciled. This explains the large SN
without assuming random memory corruption. Separately, an absent DAT makes
`rdx_record_format_space()` fail, preventing recording admission. The host
storage regression reproduces both consequences. The fail-closed recording
space check is retained.

The clock log prints the current/destination values before applying the new
clock; it does not by itself prove that the CPU remains at 160 MHz. Repeated
commands refresh the native observation window. The supplied trace does not
include the actual PA4-OFF interval corresponding to the reported 3 mA
measurement. Later user testing confirms the post-download current symptom
persists; see the checkpoint status above.

## Implementation

- `rdx_file_download.c` validates the bounded command before the legacy parser
  mutates its shared request. It captures the full SN, filename, RDX owner token,
  transfer generation and initial auto-delete intent.
- Successful read/enqueue results establish contiguous coverage from the
  requested resume offset to EOF. Only a matching explicit `pack=0` with the
  original auto-delete intent can submit deletion. This relies on the APP's
  completion acknowledgement; enqueue success is not itself RF delivery proof.
- A duplicate completion is harmless. A completion for a different SN cannot
  clear an active newer download. Generic finish, STOP, timeout and upload
  cleanup invalidate deletion authority and never delete.
- Duplicate data requests no longer queue callbacks borrowing mutable
  `r_file_info`. Chunk lengths/offsets derive from the current request. Short
  reads fail closed, and allocation-failure cleanup no longer frees a buffer
  twice.
- Before finishing the transfer, the code reserves storage admission and a
  PA4/business lease and copies an immutable deletion request. All queue,
  allocation and admission failures retain the file and release reservations.
- The UXFILE worker reuses the checked transactional deletion/cache handoff.
  It flushes dirty DAT, checks full SN plus filename, deletes RAW and MTA,
  retains a valid empty DAT when removing the last entry, invalidates list
  snapshots and reloads the cache. The persistent SN counter is not reset.
- Owner authorization is checked before execution and immediately before
  writing durable deletion intent. Once intent is committed, transaction replay
  completes even if the owner disconnects. Real storage errors keep file
  service closed instead of reporting false success.
- Transfer cleanup releases the timer, file handle, buffers, queues, busy state
  and download clock request. Delete completion frees its context even if the
  app_core callback cannot be queued. No unsolicited `delfile` ACK is added.

There are no new periodic probes or changes to BLE connection parameters,
slave latency, LRC sleep clock, PA4 timeout or native low-power policy.

## Required device regression

1. Back up valuable recordings first. Start with one valid recording, enable
   download-then-delete, download it, refresh the list and reboot. It must stay
   absent with a valid empty list and no resurrected management entry.
2. Repeat with multiple files, including an SN above 255. Delete only the
   downloaded target; other files and their identities must remain unchanged.
3. Test download without deletion, resume, duplicate completion, cancellation,
   timeout and disconnect/reconnect. Incomplete or unauthorized transfers must
   retain their files; a new transfer must work afterward.
4. After deletion, start/stop/save another recording via APP and physical
   recording keys. Refresh and download it. SN must advance, not reset.

## Separate unresolved power follow-up

Do not count the deletion result as a power acceptance result. When power
investigation resumes, stop APP polling and business activity, keep the
connection and USB/charging conditions unchanged, and wait past the existing
120-second idle window. Compare download-only, download-then-delete and
connected standby, then repeat after physical disconnection. Capture measured
current with PA4 state and timestamped logs. PA4 OFF or an idle `lp_target`
snapshot alone does not prove that the chip entered the intended sleep state.
The abnormal 3 mA floor remains open; the earlier 22 mA report is not separately
signed off by this checkpoint.

## Operational notes

Deletion-result logs are `[AUTO_DELETE] ... result=0`, `retained ...`,
`queue rejected; file retained`, and `[REC_FORMAT] file service=0`. A successful
delete log is not a current measurement.

This change prevents new orphans; it does not silently erase old management
entries or auto-format the volume. If the old trace has already left orphan
entries, preserve evidence and use explicit reviewed management deletion after
backup. Do not mistake preexisting retained entries for a new failed transfer.
