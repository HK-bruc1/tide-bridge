# BLE 一拖二双连接多服务共存设计理念——RDX 私有服务与 HOGP

> 架构名称：Dual-Link, Dual-Wrapper, Single Composite GATT Profile。
>
> 核心起点：由单链接复合 Profile 共享 GATT 数据库演进到双 Peripheral 链路；扩展的是连接承载能力，不是 GATT 数据库、Profile 或产品身份。
>
> 文档定位：本文只冻结设计缘由、核心理念、产品边界和关键架构决策，仅讨论 BLE，不包含 Classic Bluetooth HFP、SCO 或其他经典蓝牙音频链路。
>
> 配套实施：具体落地步骤与验收要求见[五号实施方案](./5.BLE一拖二双连接多服务共存实施方案_RDX私有服务与HOGP.md)。

## 1. 从单链路复合 Profile 到 BLE 一拖二

### 1.1 三号方案解决了什么

三号方案首先解决的是 RDX 与 HOGP 的 GATT 架构问题：

- RDX 私有 Service 与标准 HID Service 合并到同一个 `rdx_profile_data[]`；
- 两类 Service 共用同一份字节级 GATT/ATT 数据库定义；
- `config_le_gatt_server_num` 保持为 `1`；
- RDX 与 HOGP 复用同一个 BLE 设备地址、名称和统一广播入口；
- 主 ADV 保留 `Flags + Name`，Scan Response 保留 RDX Manufacturer Data，并追加 HID UUID `0x1812`；
- 删除 CONFIG/HOGP 分时广播、KEY5 三击切换和 connection owner；
- 同一条连接可按实际 ATT 行为独立激活 RDX/HID；Phase 3真机验证后正式允许同一PC链路组成`RDX_HID`复合owner，同时仍保持每类capability全局唯一；
- HID 继续以 `Input CCC enabled && encrypted && !suspended` 作为 ready 边界；
- bonded HID CCC 已按 peer identity 持久化，避免跨 peer 泄漏订阅状态。

该方案证明了“复合 Profile + 共享 GATT 数据库 + 统一广播”在当前 App 与 Windows 环境中可行，也完成了大量必须保留的 Profile、安全、keymap 和断连收敛工作。

### 1.2 单链路不能满足什么

单链路复合 Profile 只表示：

```text
同一个 BLE Central 建立连接后
可以发现同一 GATT 数据库中的 RDX Service 与 HID Service
```

它不表示：

```text
Windows PC 与手机 App
可以共享同一个 connection_handle
```

BLE ATT/GATT 会话依附于具体 ACL connection。PC 与手机都是独立 BLE Central，要同时在线，设备端就必须同时维持两条 BLE Peripheral 链路。

原单连接模型下，Windows 一旦自动回连 HOGP，唯一连接槽就被占用；手机 App 无法再连接 RDX。用户若要修改 HID 自定义按键，只能经历：

```text
断开 PC HID
→ 手机 App 连接并修改配置
→ 断开 App
→ 恢复广播
→ 等待 PC HID 自动回连
```

该流程破坏键盘连续使用体验，也无法满足客户“保持 HID 在线并通过 App 热修改按键”的明确需求。因此，单连接不再是正式产品边界。

### 1.3 最新演进方向

最新方案保留三号方案已经稳定的复合 Profile 与统一广播，只扩展连接承载模型：

```text
三号方案：
一份复合 Profile
+ 一个 app_ble_hdl wrapper
+ 最多一条 BLE 连接

四号方案：
同一份复合 Profile
+ 两个 app_ble_hdl wrapper
+ 最多两条 BLE 连接
+ 一个 HOGP capability 会话
+ 一个 RDX capability 会话
```

这里增加的是连接 wrapper 和 per-link runtime，不是第二套 GATT Profile、第二套 RDX 协议栈或第二个产品身份。

四号方案的产品容量策略不是“任意两条链路共享任意能力”，而是：两条链路都可以发现完整复合 Profile；全局最多一个 RDX owner和一个HID owner。两个owner既可以分别位于手机App与PC的两条ACL，也可以同时位于同一台PC的一条ACL。后一种same-link复合owner是PC专属RDX应用与Windows HOGP共存的正式产品拓扑。

## 2. 最终目标运行模型

```text
                 统一 connectable legacy advertising
          主 ADV：Flags + 统一名称
          Scan Response：RDX Manufacturer Data + HID UUID
                               │
                     一个空闲 wrapper 负责广播
                               │
              ┌────────────────┴────────────────┐
              │                                 │
       Wrapper / Link 0                  Wrapper / Link 1
              │                                 │
       Windows / PC Central              手机 BLE App Central
       HOGP Input CCC + 加密              RDX CCC + 私有命令
              │                                 │
       HID report 定向发送                RDX response 定向发送
              └────────────────┬────────────────┘
                               │
                    同一份 rdx_profile_data[]
               同一组 RDX + HID ATT handle 布局
                      同一设备地址和名称
```

典型运行状态为：

```text
Link 0:
    connected = 1
    capability = HID
    hid_ready = 1

Link 1:
    connected = 1
    capability = RDX
    rdx_ccc = 1
```

产品允许两条链路的连接顺序互换：

- PC 先连接后，设备继续广播，手机 App 再连接；
- 手机 App 先连接后，设备继续广播，PC 再连接；
- 两条连接建立后停止广播；
- 任意一条断开后，只释放该链路，并使用空闲 wrapper 恢复统一广播；
- 另一条连接及其业务能力不受影响。

## 3. 设计缘由与核心理念

### 3.1 基于当前代码现状，而不是重新设计整套协议

当前工程不是一份空白 BLE Demo，而是已经包含以下成熟资产：

- 预编译 `librdxApp.a` 及其单会话命令、文件、录音、OTA 和发送队列；
- 已合并的 `rdx_profile_data[]`；
- 已完成 Windows 回归的 HOGP Report Map、Report 长度和 ATT handle；
- 已完成的 HID CCC、加密、suspend 和 peer-scoped subscription 恢复；
- 已完成的 keymap revision、CRC、双 VM slot、prepare/commit 和 rollback；
- 依赖 `app_ble_hdl` 的广告、连接、发送长度、发送队列和断连 API。

因此，本方案不追求一次性实现“任意两个 Central、任意两个 RDX 会话、任意两个 HID host”的通用多连接框架，而采用满足产品需求的固定 `1 + 1` 模型：

```text
最多一个 HID report sink
+
最多一个 RDX App control session
```

这可以保留现有 RDX 业务单例，避免改造预编译库，同时消除用户反复断开和重连的交互问题。

### 3.2 遵循 JL SDK 已有的一拖二实践

当前 SDK 已存在两套直接相关的 BLE 一拖二实现参考。

#### Find My 示例

`SDK/apps/common/third_party_profile/bt_fmy/ble_fmy.c` 中：

- `FMY_MAX_CONNECTIONS` 定义为 `2`；
- 同时维护 `fmy_ble_hdl` 与 `fmy_second_ble_hdl`；
- 两个 wrapper 均通过 `app_ble_hdl_alloc()` 分配；
- 两个 wrapper 注册同一份 `findmy_profile_data`；
- 两个 wrapper 注册同一套 read/write/HCI/L2CAP/SM callbacks；
- 发送和断连根据 `app_ble_get_hdl_con_handle()` 选择目标 wrapper；
- 第一 wrapper 已连接时，第二 wrapper 可以承担后续广播和连接。

#### RCSP 一拖二示例

`SDK/apps/common/third_party_profile/jieli/rcsp/rcsp_interface.c` 中：

- 双设备模式维护 `rcsp_server_ble_hdl` 与 `rcsp_server_ble_hdl1`；
- 两个 wrapper 注册同一份 `rcsp_profile_data`；
- 收发、MAC 查询、断连和状态统计均按 wrapper/connection handle 区分；
- RDX 当前使用的 `app_ble_*` 封装与该实现属于同一套 SDK 接口体系。

这两套实现说明，在当前 JL SDK 中，`app_ble_hdl` 不只是协议注册标识，也承载一条连接的 wrapper runtime。实现 BLE 一拖二时，使用两个 wrapper 比强行让一个 wrapper 管理两个 connection handle 更符合 SDK 既有模式。

### 3.3 两个 wrapper，不是两套产品身份

两个 wrapper 必须保持以下一致：

- BLE 地址；
- GAP Device Name；
- Advertising Data；
- Scan Response Data；
- `rdx_profile_data[]`；
- ATT handle 布局；
- read/write callback；
- HCI/L2CAP/SM callback；
- 安全策略。

任意时刻只由一个空闲 wrapper 发送统一广播。用户在 Windows 和手机中看到的仍是同一个产品，不出现 `Keyboard`、`Config` 两个广播名称，也不恢复模式切换。

### 3.4 连接槽不等于 connection owner

本方案禁止根据 wrapper 序号预设：

```text
Wrapper 0 永远属于 PC
Wrapper 1 永远属于 App
```

连接建立时，slot 只表示一条物理 BLE 链路。能力根据对端真实 ATT 行为激活：

- 开启 HID Input CCC 的链路成为 HID capability 链路；
- 订阅 RDX CCC 或下发合法 RDX 命令的链路成为 RDX capability 链路。

这是按真实 ATT 行为进行 capability routing，不是按 wrapper序号固定身份，也不是恢复旧的全局 connection owner。同一link可以按访问顺序从`NONE`变为`RDX`、`HID`或`RDX_HID`；RDX-first与HID-first必须得到相同的复合结果。只有第二个同类owner抢占才会被拒绝。

### 3.5 传输状态与业务状态分离

连接、MTU、加密和 CCC 属于 per-link 传输状态；keymap、录音状态、文件状态和产品设置属于全局业务状态。

本方案要求：

- 传输层始终携带明确 `connection_handle` 或 `app_ble_hdl`；
- RDX 业务仍只绑定一个 active RDX link；
- HOGP executor 仍只绑定一个 ready HID link；
- 业务模块不得继续读取含义模糊的全局 `ble_conn` 或 `ble_con_handle`；
- 任意一条链路断开，只清理其实际激活的 capability。

## 4. 目标与非目标

### 4.1 目标

1. PC HOGP 与手机 RDX App 可以同时保持 BLE 连接。
2. HID 在线期间，App 可以读取、修改和保存自定义 keymap。
3. keymap 保存期间 PC HID 不断开，下一次物理按键使用新配置。
4. PC-first、App-first 和双方同时回连均可工作。
5. 保留三号方案统一广播字节布局与正式 App 发现兼容性。
6. 保留同一份复合 `rdx_profile_data[]` 和既有 ATT handle。
7. 保持一个 GATT Server role，不创建第二套 RDX/HID 数据库定义。
8. 使用两个 `app_ble_hdl` wrapper 承载两条连接。
9. RDX 与 HID 的 CCC、加密、MTU、peer 和断连清理按链路隔离。
10. 保持最多一个 RDX session 与最多一个 HID report sink。
11. 任意一条链路断开时，另一条链路继续工作。
12. 所有新增路径具有 host contract，并完成真实 PC/App 双连接回归。
13. 同一物理链路可以复合认领RDX与HID，但一个RDX owner和一个HID owner的全局容量边界不变。

### 4.2 非目标

- 不讨论或兼容 Classic Bluetooth HFP、SCO、eSCO；
- 不实现两个 PC 同时接收 HID report；
- 不实现两个手机 App 同时控制 RDX；
- 不将 key report 广播发送给所有已连接 Central；
- 不创建 CONFIG/HOGP 两种广播模式；
- 不恢复 KEY5 三击模式切换；
- 不恢复 connection owner；
- 不根据 MAC、操作系统名称或连接顺序猜测对端身份；
- 不改变 HID Report Map、8-byte Input Report 或现有 handle 布局；
- 不新增第二份 RDX 协议栈或改造预编译 `librdxApp.a`；
- 不使用 Extended Advertising；
- 不在本阶段解决 RDX 远端身份认证问题。

## 5. 已冻结的架构决策

### 5.1 单链接复合 Profile 共享 GATT 数据库是演进基础

本方案从已经落地的单链接复合 Profile 出发，不拆分 RDX 与 HOGP 的 GATT 数据库：

- 只保留一份 `rdx_profile_data[]` 和一套 ATT handle 布局；
- `config_le_gatt_server_num` 保持为 `1`；
- 通过两个 `app_ble_hdl` wrapper 承载最多两条 BLE Peripheral 连接；
- 两个 wrapper 注册相同 Profile、相同 ATT callbacks 和相同安全策略；
- 不创建第二套 RDX 协议栈、第二个 HID 实例或第二个产品身份。

这里的“一拖二”是连接承载能力扩展，不是 Profile、GATT Server role 或业务协议栈数量翻倍。

### 5.2 统一广播身份与单一 advertiser

两个 wrapper 使用相同 BLE 地址、名称、Advertising Data 和 Scan Response Data。任意时刻只允许一个空闲 wrapper 广播：

- 零连接：一个 wrapper 广播；
- 一连接：另一个空闲 wrapper 继续相同广播；
- 两连接：停止广播；
- 任一链路释放：空闲 wrapper 恢复相同广播。

Windows 和手机 App 始终看到同一设备，不恢复 CONFIG/HOGP 模式切换，也不按 wrapper 构造两个逻辑产品。

### 5.3 唯一 link registry

全系统只允许一个 per-link 状态中心。该 registry 唯一拥有：

- 两个 link slot；
- wrapper 与 connection handle 映射；
- RDX/HID capability owner；
- per-link MTU、CCC、加密、peer 和连接参数状态；
- `slot_generation` 与 `transport_epoch`。

`rdx_ble_server.c` 负责 wrapper 生命周期、广播策略和 SDK callback，不再维护影子连接状态。业务模块通过窄接口查询当前 RDX owner 或 HID sink，不直接读取含义模糊的全局连接字段。

### 5.4 固定 1 + 1 capability 模型

```text
physical BLE links <= 2
active RDX owner   <= 1
active HID sink    <= 1
capability/link    <= 1
```

连接建立时不根据 MAC、OS、wrapper 序号或连接顺序预判身份。能力由真实 ATT 行为认领：

- 加密后的 HID Input CCC enable 或 bonded subscription 恢复认领 HID；
- RDX CCC enable 或合法 RDX value write 认领 RDX；
- 静态服务发现与静态读取不认领 capability。

同一物理链路不能同时认领 RDX 与 HID。Capability 一旦认领便粘性保持到该链路断开；CCC 写 `0` 只改变 ready/tx 状态，不释放 ownership。

### 5.5 同步事件与异步工作的隔离原则

所有同步 HCI、ATT、L2CAP 和 SM 事件必须同时校验 wrapper 与 connection handle。任何携带 link 语义、未来会读取 owner、handle、MTU、CCC、安全状态或尝试 BLE 发送的异步工作，必须携带并校验：

```text
slot_index + slot_generation + transport_epoch
```

纯本地、完全不访问 BLE link 状态的业务 timer 不适用该 token 规则。这个边界用于阻止旧 ADV timer、CAN_SEND_NOW、app_core 消息、录音、OTA 或文件任务污染复用后的 slot 或新的 RDX owner。

### 5.6 安全与 capability claim 顺序

未加密链路首次写 HID Input CCC enable 时，只请求配对并返回 `INSUFFICIENT_ENCRYPTION (0x0f)`，不得提前 claim HID、写 CCC、持久化 subscription 或修改 HOGP 单例。只有加密后的 CCC 重试或 bonded subscription 恢复才能 claim HID。

Capability claim 的内部结果与 ATT wire error 分离。Phase 0B 先以标准 `UNLIKELY_ERROR (0x0e)` 验证拒绝路径；vendor-specific `0x80/0x81` 只有在 Windows 与正式 App 实测兼容后才允许冻结。

### 5.7 单 RDX 会话与单 HID sink 是正式边界

现阶段不要求预编译 `librdxApp.a` 支持两个 App 会话，也不把 HOGP 单例复制为两个实例。正式接入前必须确认：

- 只有 RDX owner 的输入进入协议库；
- 协议库输出动态解析当前 RDX wrapper；
- 只有 RDX owner 的 CAN_SEND_NOW 唤醒 RDX 发送；
- 只有 RDX owner 断开才清理 OTA、文件、录音和 bulk 会话；
- HID report 永远只发送到当前 HID sink；
- Disconnection Complete 之后只做本地清理，不再尝试 ATT release report。

### 5.8 架构冻结与实施准入

当前结论：Phase 0A至Phase 2已关闭；Phase 3已完成same-link复合owner、在线Keymap与同peer重连实现，完整重连真机矩阵仍待关闭；Phase 4已进入清理、回归与正式启用阶段。双连接是唯一正式运行模型，禁止恢复单连接fallback或隐藏兼容开关。

Host contract 只能冻结源码结构和禁止项，不能替代 wrapper 绑定、callback 分发、controller 双连接调度、SM peer 隔离及广播恢复时序的实机验证。

## 7. 最终结论

三号方案建立的“单链接复合 Profile、共享 GATT 数据库、统一广播”仍是必要基础，但它只能解决 RDX 与 HOGP 服务共存，不能让 Windows PC 与手机 App 两个 Central 同时在线。

结合客户在 HID 在线期间通过 App 热修改按键的需求、当前 RDX/HOGP 单业务会话代码现状，以及 JL SDK 中 Find My 和 RCSP 已有的一拖二实践，正式架构冻结为：

```text
同一份 RDX + HOGP 复合 Profile
+ 一个 GATT Server role / 同一字节级 ATT 数据库定义
+ 两个 app_ble_hdl wrapper
+ 最多两条 BLE Peripheral 连接
+ 一个 HID capability 会话
+ 一个 RDX capability 会话
+ 同一物理 link 可组成 RDX_HID 复合owner，每类owner仍全局唯一
+ 唯一 link registry 与 generation/epoch 异步防护
+ 按 wrapper 与 connection handle 定向收发
```

该模型在不引入经典蓝牙 HFP/SCO 范围、不重写预编译 RDX 协议库的前提下，解决 HID 与 App 反复断开重连的交互问题，是当前代码基础上的 BLE 正式演进方向。
