# JL 平台文件系统与 USB PC 模式通用指南

## 1. 文档目标与适用范围

本文总结 JieLi（JL）SDK 中存储设备、VFS 文件系统、设备管理器以及 USB Device Mass Storage（MSC/MSD）之间的通用关系，目标是帮助不同 JL 项目完成以下工作：

- 接入 SD 卡、SD NAND、NOR Flash、NAND Flash、外部 U 盘或虚拟磁盘；
- 在固件内挂载文件系统并读写文件；
- 将某个块设备通过 USB 暴露给 Windows、macOS 或 Linux；
- 在设备侧文件访问与 PC 侧块访问之间安全切换；
- 按层定位“设备不在线、挂载失败、PC 不出盘、读写失败、拔线后不能恢复”等问题。

本文以当前仓库所使用的 AC701N/BR28 耳机 SDK 为可验证样本，但正文描述的是同类 JL SDK 的通用架构。不同芯片、SDK 分支和应用模板的宏名、文件路径、USB 控制器数量及设备表可能不同，移植时应以目标 SDK 源码为准。

本文不规定某个产品的开关、充电、蓝牙、按键或业务协议策略。这些属于项目层，应建立在本文描述的平台机制之上。

## 2. 先记住六个结论

1. **块设备、文件系统和 USB MSC 是三个不同层次。** 块设备能读写扇区，不等于 FAT 已挂载；PC 能看到磁盘，也不等于固件能打开文件。
2. **MSC 暴露的是逻辑块地址（LBA），不是文件。** PC 通过 SCSI `READ(10)`、`WRITE(10)` 等命令直接访问介质扇区，并由 PC 操作系统解析分区和文件系统。
3. **同一个 FAT 卷不能同时由 PC 和固件挂载读写。** 两端各自缓存 FAT、目录项和空闲簇信息，并发访问很容易损坏文件系统。
4. **USB Host 与 USB Device/Slave 不要混淆。** `udisk0` 通常表示 JL 作为 Host 读取外接 U 盘；把 `sd0` 暴露给 Windows，则是 JL 作为 Device/Slave 提供 MSC。Windows 仍会把它显示成“U 盘”。
5. **`msd_register_disk()` 只登记 LUN 对应的设备名。** 介质仍必须有可用的设备节点、正确的容量/块大小、在线状态和扇区读写实现。
6. **格式化不是通用的挂载失败修复手段。** 挂载失败也可能来自供电、引脚、时序、设备未在线、分区表不兼容或瞬时 I/O 故障；自动格式化可能直接擦除用户数据。

## 3. JL 存储栈的分层模型

### 3.1 设备侧文件访问路径

```text
业务模块
  -> fopen / fread / fwrite / fclose
  -> JL VFS（fat、sdfile、rec_fs 等）
  -> mount() 创建的挂载实例
  -> 设备节点 dev_open / dev_ioctl / dev_bulk_read / dev_bulk_write
  -> SD、NOR、NAND、USB Host 等底层驱动
  -> 物理介质
```

### 3.2 PC 侧 MSC 访问路径

```text
PC 文件系统驱动
  -> SCSI READ(10) / WRITE(10) / READ CAPACITY ...
  -> USB Bulk-Only Transport
  -> JL USB MSD 实现
  -> dev_open / dev_ioctl / dev_bulk_read / dev_bulk_write
  -> 底层块设备驱动
  -> 物理介质
```

两条路径最终访问同一块设备，但 PC 的 MSC 路径不会经过设备侧 `fopen()`。这也是为什么 PC 模式可以在设备侧 VFS 已卸载时工作，以及为什么两条路径必须做所有权仲裁。

### 3.3 各层的职责

| 层次 | 典型对象/API | 主要职责 | 成功能证明什么 |
|---|---|---|---|
| 物理与驱动层 | SD、NOR、NAND、USB Host 驱动 | 上电、引脚、协议初始化、扇区读写 | 介质可以进行原始块访问 |
| 设备节点层 | `REGISTER_DEVICE(S)`、`dev_open()` | 用名字绑定驱动操作和平台数据 | 固件可以通过设备名打开驱动 |
| 设备管理层 | `dev_reg[]`、`dev_manager_add()` | 维护逻辑设备、挂载状态、活动设备 | 逻辑盘已加入管理链表，可能已挂载 |
| VFS 层 | `mount()`、`fopen()`、`f_format()` | 解析分区和文件系统、提供文件 API | 固件可以按路径访问文件 |
| USB MSC 层 | `usb_device_mode()`、`msd_register_disk()` | 把块设备映射成 USB LUN | PC 可以查询容量并读写 LBA |
| 应用模式层 | `APP_MODE_PC` 或项目状态机 | 决定何时进入/退出 PC、如何交接资源 | 产品行为符合业务策略 |

## 4. 最容易混淆的术语

### 4.1 `name`、`logo`、路径和 LUN

当前 SDK 的 `struct __dev_reg` 包含以下字段：

| 字段 | 示例 | 含义 |
|---|---|---|
| `logo` | `sd0` | 设备管理器使用的逻辑标识 |
| `name` | `sd0` | 传给底层 `dev_open()` 的设备节点名 |
| `storage_path` | `storage/sd0` | VFS 挂载点 |
| `root_path` | `storage/sd0/C/` | 业务常用的分区根目录 |
| `fs_type` | `fat` | VFS 驱动类型 |

这些字段在简单设备上可能同名，但概念并不相同。增加新介质时，应同时检查：

1. 是否注册了底层设备节点；
2. `dev_reg[]` 是否存在对应逻辑设备；
3. 挂载路径与业务文件路径是否一致；
4. USB MSC 登记的设备名是否能被 `dev_open()` 打开。

USB LUN 是 Host 看到的逻辑单元编号。`msd_register_disk("sd0", NULL)` 的含义是把设备节点 `sd0` 放入一个 LUN 槽位，不是挂载 `storage/sd0/C/`，也不是创建一个名为 `sd0` 的文件系统。

### 4.2 “U 盘”有两种相反方向

| 需求 | JL 的 USB 角色 | 常见设备名/配置 | 数据方向 |
|---|---|---|---|
| JL 读取插在自己 USB 口上的实体 U 盘 | Host | `TCFG_USB_HOST_ENABLE`、`TCFG_UDISK_ENABLE`、`udisk0` | 外部 U 盘提供介质，JL 访问 |
| JL 把自己的 SD/NOR/NAND 暴露给 PC | Device/Slave | PC/Slave + MSC，LUN 为 `sd0`、`fat_nor` 等 | JL 提供介质，PC 访问 |
| JL 提供 RAM/Flash 构造的虚拟磁盘 | Device/Slave | `vir_udisk0` 等 | JL 提供虚拟介质，PC 访问 |

因此，“Windows 已经显示 U 盘”只描述了 PC 的用户界面，不能据此推断固件侧设备名是 `udisk0`。

### 4.3 在线、已注册、已加入、已挂载不是一回事

- **已注册（registered）**：设备节点存在于链接段或设备表中。
- **在线（online）**：底层驱动认为介质存在并可访问。
- **已加入（managed/listed）**：`dev_manager` 链表中存在该逻辑设备。
- **已挂载（mounted）**：`mount()` 成功并获得 `struct imount *`。
- **业务有效（valid）**：设备管理器允许业务使用；具体语义随 SDK 分支而异。
- **已登记为 LUN**：USB MSD 保存了设备名，Host 可以开始查询介质。

排查时必须说明失败发生在哪个状态，不能只说“SD 不工作”或“文件系统不工作”。

## 5. 存储设备接入的通用流程

### 5.1 第一步：启用并配置底层介质

以 SD 为例，通常需要：

- 打开 `TCFG_SD0_ENABLE` 或 `TCFG_SD1_ENABLE`；
- 配置 CMD、CLK、DATA 引脚、数据宽度、时钟、检测方式和供电回调；
- 确认相关引脚没有与 USB、UART、触摸、按键或其他外设复用冲突；
- 对可插拔卡实现可靠的在线检测，对焊接介质定义符合硬件的常在线策略；
- 使用目标板实测信号完整性和启动时序。

典型设备节点注册形态如下：

```c
REGISTER_DEVICES(device_table) = {
    { "sd0", &sd_dev_ops, (void *)&sd0_data },
};
```

设备表把字符串 `sd0`、驱动操作集和板级平台数据关联起来。只有宏打开但设备表没有节点，或者节点存在但平台数据错误，后续 VFS 和 MSC 都不能正常工作。

### 5.2 第二步：先验证原始块设备

在引入文件系统和 USB 之前，先确认：

```text
dev_online("sd0")
dev_open("sd0", NULL)
dev_ioctl(..., IOCTL_GET_STATUS, ...)
dev_ioctl(..., IOCTL_GET_CAPACITY, ...)
dev_ioctl(..., IOCTL_GET_BLOCK_SIZE, ...)
dev_bulk_read(..., lba, count)
```

关键检查项：

- `dev_open()` 是否成功；
- 容量和块大小是否合理；
- LBA0 是否能稳定重复读取；
- 多次上电、插拔和温度变化后结果是否一致；
- 写保护状态是否符合预期。

原始写测试会破坏介质内容，只能在明确保留的测试区域或可擦除样品上进行，不能对包含用户数据的 LBA 随意写入。

### 5.3 第三步：配置逻辑盘和 VFS

设备管理器通过 `dev_reg[]` 把底层节点映射到文件系统。例如：

```c
{
    .logo         = "sd0",
    .name         = "sd0",
    .storage_path = "storage/sd0",
    .root_path    = "storage/sd0/C/",
    .fs_type      = "fat",
},
```

随后典型调用链是：

```text
设备上线事件或固定介质初始化
  -> dev_manager_add("sd0")
  -> mount("sd0", "storage/sd0", "fat", ...)
  -> 获得挂载句柄
  -> fopen("storage/sd0/C/xxx.dat", ...)
```

文件系统编译开关也必须打开。当前耳机 SDK 会根据 SD、外部 U 盘、NOR FAT 或第三方业务配置推导 `CONFIG_FATFS_ENABLE`，但其他 SDK 分支可能需要显式配置。

### 5.4 第四步：做最小文件闭环

在接入 USB PC 模式前，至少完成一次设备侧闭环：

1. mount 成功；
2. 获取容量或剩余空间；
3. 创建临时文件；
4. 写入固定数据并关闭；
5. 重新打开并校验；
6. unmount 后重新 mount；
7. 再次读取并校验。

如果这一阶段失败，不应先调 USB。USB 只会把现有块设备问题带到 Host 侧，使问题更难分层。

## 6. 常见介质及其平台边界

| 设备 | 常见名称 | 是否天然是块设备 | 常见 VFS | 能否作为 MSC LUN |
|---|---|---:|---|---|
| SD 卡 / SD NAND | `sd0`、`sd1` | 是 | FAT | 可以 |
| JL 作为 Host 读取的外接 U 盘 | `udisk0` | 是 | FAT | 通常用于设备侧访问，不是同一 USB 口的 Device LUN |
| 外挂 NOR 的 FAT 分区 | `fat_nor` | 取决于适配层 | FAT | SDK 支持时可以 |
| 外挂 NAND | `nandflash_ftl` 等 | 必须先经过坏块管理/FTL | FAT 等 | FTL 和设备节点完整时可以 |
| 虚拟 U 盘 | `vir_udisk0` | 由虚拟块驱动提供 | FAT 或预制镜像 | 可以 |
| 资源文件系统 | `sdfile`、`nor_sdfile` | 通常面向只读资源 | `sdfile` 系列 | 不应默认当作通用可写 MSC |
| 录音专用文件系统 | `rec_fs` 等 | 实现相关 | 专用 FS | 不应默认直接给 PC |

`task_pc.c` 中出现某个 `msd_register_disk()` 分支，只表示 USB 层预留了映射入口，不代表目标板已经具备完整驱动。例如 NAND Flash 通常还需要：

- 板级 SPI/并口配置；
- 芯片识别和坏块管理；
- FTL 或等价逻辑块映射；
- 可用的 `device_operations`；
- 容量、块大小、状态和 flush 等 ioctl；
- 与 `dev_manager` 配套的注册及所有权策略。

只打开一个 NAND 宏，无法替代上述接入工作。

## 7. USB Device MSC 的启动链路

### 7.1 配置职责

以下名称来自当前 SDK，其他版本可能不同：

| 配置 | 通用职责 | 不负责什么 |
|---|---|---|
| `TCFG_APP_PC_EN` | 启用 PC 应用模式 | 不配置具体存储驱动 |
| `TCFG_PC_ENABLE` | PC/USB Device 功能总开关，常由应用宏推导 | 不等于已启用 MSC |
| `TCFG_USB_SLAVE_ENABLE` | 编译 USB Device/Slave Stack | 不决定 LUN 介质 |
| `TCFG_USB_SLAVE_MSD_ENABLE` | 把 Mass Storage 加入 USB Class | 不负责挂载 FAT，也不负责 SD 引脚 |
| `TCFG_SD0_ENABLE` / `TCFG_SD1_ENABLE` | 启用对应 SD 块设备 | 不自动取得 PC 所有权 |
| `TCFG_DEV_MANAGER_ENABLE` | 启用逻辑设备管理 | 不替代底层在线检测 |
| `CONFIG_FATFS_ENABLE` | 编译 FAT VFS 支持 | MSC 原始块传输并不依赖 VFS 保持挂载 |
| `TCFG_USB_HOST_ENABLE` / `TCFG_UDISK_ENABLE` | JL 作为 Host 读取外部 U 盘 | 不是把 JL 介质暴露给 PC 的开关 |
| `TCFG_SD_ALWAY_ONLINE_ENABLE` | 固定介质的在线策略 | 不表示 FAT 必须永远挂载 |
| `TCFG_USB_DM_MULTIPLEX_WITH_SD_DAT0` | 描述 USB DM 与 SD DATA0 复用 | 不能绕过真实的硬件冲突 |
| `TCFG_CHARGE_POWERON_ENABLE` | 产品的充电开机策略 | 不是 MSC 枚举的技术依赖 |

在当前 SDK 中，`TCFG_APP_PC_EN` 通常推导 `TCFG_PC_ENABLE`；`usb_common_def.h` 再由 PC 功能推导 OTG Slave 和 `TCFG_USB_SLAVE_ENABLE`。移植时应检查预处理后的有效值，不要仅看配置工具页面或某个头文件中的原始定义。

### 7.2 两种常见的应用入口

JL SDK 常见两类启动方式：

1. OTG 检测到 Slave 后切换到 `APP_MODE_PC`，再由 PC 模式启动 USB Stack；
2. `USB_PC_NO_APP_MODE` 等配置使 USB 在当前应用模式中直接启动。

二者的 USB 传输层相同，差异在于产品是否切换前台应用、是否退出蓝牙/音频，以及由谁管理存储所有权。不要把某个项目的模式切换策略当成所有 JL 产品的限制。

### 7.3 USB Class 和 LUN 注册

当前 `task_pc.c` 的核心行为可以概括为：

```c
class |= MASSSTORAGE_CLASS;
usb_device_mode(usb_id, class);
msd_register_disk("sd0", NULL);
```

实际代码会根据配置选择 `sd0`、`sd1`、`fat_nor`、`nandflash_ftl`、`vir_udisk0` 等 LUN，也可能同时组合 HID、UAC、CDC、MIDI 或其他 USB Class。

复合设备会增加端点、描述符、SRAM、时钟和 Host 兼容性约束。若产品只需要磁盘，先用纯 MSC 完成闭环，再按需求增加其他 Class。

### 7.4 Host 第一次访问介质时发生什么

`msd_register_disk()` 通常只保存设备名。Windows 开始发 SCSI 命令后，MSD 才会按 LUN：

1. 检查设备管理器中是否存在该逻辑设备；
2. 调用 `dev_open(dev_name, NULL)`；
3. 查询在线状态、容量、块大小和写保护；
4. 使用 `dev_bulk_read()` / `dev_bulk_write()` 处理 LBA；
5. 在停止、离线或释放时 flush/close 句柄。

这解释了两种常见现象：

- USB 描述符已经枚举，但 Windows 不出盘：可能是 LUN 对应设备打不开或容量查询失败；
- Windows 出现“需要格式化”：USB 和块设备可能已经工作，只是 Host 不识别当前分区或文件系统。

## 8. MSC 与 VFS 的排他所有权

### 8.1 为什么不能双挂载

FAT 驱动会缓存 FAT 表、目录项、空闲簇和写缓冲。Windows 也会做相同的缓存。若两端同时修改一个卷，可能出现：

- 文件长度或目录项回退；
- 簇链交叉、丢簇或循环；
- 刚写入的文件消失；
- 下次挂载要求修复或直接失败；
- 极端情况下整卷不可读。

互斥锁只能保护固件内部线程，无法锁住 PC 的文件系统驱动，因此必须做介质所有权切换。

### 8.2 推荐状态机

```text
DEVICE_OWNED_MOUNTED
  -> QUIESCING
  -> HOST_OWNED_MSD
  -> STOPPING_MSD
  -> RESTORING
  -> DEVICE_OWNED_MOUNTED

任一步骤失败 -> FAULT / BLOCKED（禁止两端继续访问）
```

状态不能只由“当前是否处于 PC 模式”推断。USB Stop 超时、介质离线或 remount 失败时，应用模式和真实存储所有权可能暂时不一致。

### 8.3 进入 PC 前的正确顺序

1. 设置 `QUIESCING`，阻止新的录音、播放、升级、文件传输、扫盘和格式化请求；
2. 等待已有操作结束，关闭所有 `FILE *`、目录扫描器和业务缓存；
3. 刷新需要落盘的数据；
4. 禁止设备管理器或插拔事件自动重新 mount；
5. unmount VFS，并检查返回值；
6. 保留底层设备节点和必要的设备管理器条目；
7. 标记 `HOST_OWNED_MSD`；
8. 启动 USB Device Stack 并登记 LUN。

在启用 `TCFG_DEV_MANAGER_ENABLE` 的当前 MSD 实现中，`check_disk_status()` 会先检查逻辑设备是否仍在管理链表中。因此交接时通常应“卸载文件系统但保留设备条目”，而不是直接 `dev_manager_del()`。

### 8.4 PC 模式期间的约束

- 所有设备侧文件入口都必须检查所有权，而不只检查某个 UI 或应用模式；
- 后台任务不得自动 remount；
- 不得启动录音、日志落盘、OTA 写文件或数据库更新；
- 介质插拔/掉电必须同时通知 USB MSD，使 Host 收到正确的 Not Ready 状态；
- 焊接式介质可以保持“物理在线”，但 VFS 仍必须保持卸载。

### 8.5 退出 PC 后的正确顺序

1. 停止接收新的 USB 块请求；
2. flush 并关闭 MSD 持有的块设备句柄；
3. 注销或释放 USB Class/LUN，关闭 USB Device 数据通路；
4. 确认 USB Stop 已完成；
5. 重新 mount 文件系统；
6. mount 成功后再解除设备侧访问阻塞；
7. 标记 `DEVICE_OWNED_MOUNTED`，恢复业务。

若 USB Stop 或 remount 失败，应保持 fail-closed：禁止设备侧继续访问，也不能假装切换成功。记录错误并由产品定义重试、提示、重启或维护流程。

### 8.6 `dev_manager_takeover()` / `restore()` 的定位

当前仓库在 `dev_manager` 中增加了 `mount_blocked`、`dev_manager_takeover()` 和 `dev_manager_restore()`，用于实现“阻止重挂载 + 卸载 + 恢复”的原子化边界。这是一个可复用的设计模式，但不是所有 JL SDK 都自带的标准 API。

移植到其他 SDK 时，如果没有这些接口，应实现等价能力，而不是直接复制函数名：

- 一个可查询的所有权状态；
- 一个覆盖所有文件入口的访问门；
- 一个阻止后台重挂载的标志；
- 有返回值和超时处理的 USB Stop；
- remount 失败时保持阻塞。

### 8.7 安全弹出与拔线不是同一事件

PC 的“安全弹出”可能发送 SCSI `START STOP UNIT`，但 USB 线和 Device 枚举仍然存在。产品可以选择：

- 弹出后保持 PC 模式，等物理拔线再恢复 VFS；
- 收到可靠的 eject 后主动停止 MSC 并恢复设备侧；
- 只把介质报告为不可用，等待下一次显式装载。

无论采用哪种策略，都必须定义重复弹出、弹出后重新访问、系统休眠/唤醒、拔线和 USB Reset 的状态转移，不能只处理一个“USB OUT”事件。

## 9. 分区、文件系统与格式化

### 9.1 PC 出盘不代表固件能挂载

PC 能查询容量并读写 LBA 后，仍可能因为以下原因不显示卷：

- 没有分区表或引导扇区；
- 分区起始 LBA、类型或大小错误；
- 使用 GPT、扩展分区或目标 JL VFS 不支持的布局；
- 使用 exFAT、NTFS 或目标固件未链接的文件系统；
- FAT BPB 参数或簇链损坏；
- 介质容量/块大小上报错误。

反过来，Windows 能挂载 exFAT 或 NTFS，也不能证明设备侧 JL VFS 支持它。产品必须明确规定双方共同支持的文件系统和分区布局，并在量产工具、PC 使用说明和固件校验中保持一致。

### 9.2 FAT32 是常见交集，但仍需实测

对需要 Windows 与嵌入式固件轮流访问的可移动卷，MBR + 单主分区 + FAT32 通常是兼容性较好的基线。但以下内容仍与 SDK 版本、介质容量和所链接的文件系统库有关：

- 是否支持无 MBR 的 super-floppy 布局；
- FAT12/16/32 的容量边界；
- exFAT 是否编译、授权并经过验证；
- 最大扇区大小、簇大小和最大分区容量；
- 长文件名、Unicode、时间戳和隐藏属性行为。

不要仅依据 PC 格式化工具的成功结果制定产品约束。

### 9.3 `f_format()` 的路径语义

当前 SDK 头文件对以下两类调用给出了不同语义：

```c
/* 整个设备格式化；当前 SDK 注释说明会生成 FAT32。 */
f_format("sd0", "fat", 0);

/* 格式化已识别的 C 分区；行为与原文件系统及实现有关。 */
f_format("storage/sd0/C/", "fat", 0);
```

这是破坏性操作。不同 SDK 分支可能实现不同，使用前必须阅读目标版本的 `fs.h` 和格式化实现，并在无用户数据的样品上验证。

### 9.4 自动格式化策略

量产产品不应把“任意 mount 失败”直接等价为“空白新介质”。推荐至少区分：

- 从未初始化的全新介质；
- 已初始化但文件系统损坏；
- 不支持的文件系统；
- 介质暂时离线或通信失败；
- 容量/块大小异常；
- 所有权切换尚未完成；
- 用户主动请求恢复出厂。

更安全的策略是：

1. 只在制造流程或明确的用户确认后格式化；
2. 首次初始化标志只作为辅助证据，不能覆盖原始介质检查；
3. 已使用介质 mount 失败时保留现场，不自动擦除；
4. 格式化后必须 remount、写入、断电重启并校验；
5. 任何格式化入口都应与 MSC 所有权互斥。

## 10. 推荐的分阶段 Bring-up 方法

### 阶段 A：底层设备

目标：稳定打开介质并读取正确容量、块大小和 LBA。

不要启用 PC MSC，也不要依赖业务文件扫描。此阶段失败通常定位在供电、引脚、检测、时钟、协议初始化、设备表或 FTL。

### 阶段 B：VFS

目标：设备侧 mount、文件读写、unmount/remount 闭环通过。

此阶段失败通常定位在分区表、文件系统格式、VFS 编译配置、路径映射或介质数据损坏。

### 阶段 C：纯 MSC

目标：只启用必要的 USB Device + MSC，PC 能稳定枚举磁盘并完成大文件读写校验。

暂时关闭与目标无关的 UAC、HID、CDC 等复合 Class，可减少端点和内存变量。此阶段失败通常定位在 USB 角色、描述符、端点、LUN 登记、设备在线状态或块 I/O。

### 阶段 D：所有权交接

目标：设备侧文件访问与 PC 访问能够反复切换，不并发、不丢数据、失败时保持阻塞。

需要覆盖录音、播放、数据库、OTA、文件传输、后台扫盘、异常拔线和 remount 失败。

### 阶段 E：产品策略

目标：再叠加充电开机、蓝牙是否后台运行、按键/拨码开关、提示音、自动关机及产品 UI。

这些策略不应改变底层存储与 MSC 的互斥原则。

## 11. 故障定位表

| 现象 | 优先检查层 | 常见原因 |
|---|---|---|
| 没有 OTG Slave/Device 上线事件 | USB 物理与角色 | 线缆仅充电、DP/DM 冲突、OTG 配置、供电或检测时序 |
| 有 OTG 事件，但没有 USB 描述符日志 | USB Stack/应用入口 | PC 模式未启动、Device Stack 未编译、状态机拒绝进入 |
| 有 MSC 描述符，但 PC 没有磁盘 | LUN/设备节点 | 未登记 LUN、`dev_open()` 失败、设备管理器无条目、介质离线 |
| PC 出现磁盘但容量为 0 或异常 | 块设备 ioctl | 容量、块大小、FTL 或设备句柄错误 |
| PC 提示“请插入磁盘” | 介质状态 | `check_disk_status()` 失败、被标记 eject、在线检测抖动 |
| PC 提示格式化 | 分区/VFS | 空白介质、不支持的布局或文件系统、BPB/FAT 损坏 |
| PC 复制时 I/O 错误 | 块读写 | `dev_bulk_*` 返回值、供电、信号完整性、写保护、flush/异步缓存 |
| PC 正常，拔线后固件打不开文件 | 所有权恢复 | USB/LUN 句柄未释放、没有 remount、设备仍 blocked、介质被 Host 改成不兼容格式 |
| 偶发文件损坏 | 并发与掉电 | 双挂载、写入中拔线、未 flush、错误的格式化恢复策略 |
| 周期性出现磁盘又消失 | 在线检测/复用 | 可插拔检测抖动、固定介质未采用合适策略、DP/DM 与 SD 复用 |
| USB Reset 日志出现数次 | 先看最终枚举结果 | 枚举阶段 Reset 可以正常出现；若持续循环且不出盘，再查信号、描述符和端点 |

日志排查应按以下顺序寻找证据：

```text
设备节点/介质在线
  -> dev_manager add
  -> VFS mount 结果
  -> OTG Slave 上线
  -> PC 模式或 USB Stack 启动
  -> MSC Class 描述符
  -> LUN 对应 dev_open
  -> 容量/块大小
  -> READ(10)/WRITE(10)
  -> USB Stop 和句柄释放
  -> VFS remount
```

不要让无关设备的警告干扰判断。例如某个可选 `sdfile` 逻辑盘未注册，并不必然表示 `sd0` 失败；应分别看每个 logo 的结果。

## 12. 通用验证矩阵

### 12.1 基础功能

| 场景 | 预期结果 |
|---|---|
| 冷启动，无 USB | 介质按产品策略上线，设备侧可挂载和读写 |
| 已开机后插 PC | 进入 USB Device/MSC，PC 出现正确容量的磁盘 |
| PC 写文件后安全弹出并拔线 | 固件恢复挂载，能读取新文件 |
| PC 空闲时直接拔线 | 固件不崩溃，能恢复挂载 |
| 固件写文件时请求进入 PC | 等待完成或明确拒绝，不强制双占用 |
| PC 占用期间触发固件文件业务 | 请求被拒绝或排队，不访问 VFS |

### 12.2 数据一致性

- 复制不同大小文件并做 Hash 校验；
- 测试跨簇、跨 FAT 表更新和大目录；
- PC 写入后由固件读取并校验，固件写入后由 PC 读取并校验；
- 连续执行 enter/exit、mount/unmount 和 100 次以上插拔；
- 检查每轮是否有句柄、任务、信号量、内存或端点资源泄漏。

### 12.3 异常与故障注入

- PC 写入中拔线；
- USB Reset、Suspend/Resume 和系统睡眠唤醒；
- 安全弹出但不拔线，再尝试重新访问；
- 介质瞬时离线或底层读写返回短块；
- USB Stop 投递失败或超时；
- remount 失败；
- 不支持的文件系统或损坏的 MBR/BPB；
- 低电压、慢启动介质和重复上电。

异常测试的合格标准不是“总能自动恢复”，而是“不并发访问、不静默擦除数据、不把失败状态伪装成成功”。

## 13. 当前串口日志的成功链路示例

日志 `COM3_2026-08-25_13-57-22.log` 可以作为一次 AC701N/BR28 项目的实例，但不应作为平台文档主线。最后一次完整进入过程包含以下证据：

```text
usb_stack_init()
create_task usb_stack
create_task dev_mg
sd0 add start
[SD-FMT] sd0 mount ok, skip format on boot
__dev_manager_add, sd0 add ok
...
OTG state 3 -> 5
USB slave detected ...
app = APP_MODE_PC
...
[PC-STORAGE] DEVICE_OWNED -> HOST_OWNED
App Start - PC
USB_DEVICE_CLASS_CONFIG:1
msd_desc_config() 0
usb reset / msd_reset
...
sd io init !
```

结合 Windows 已出现磁盘，可得出：

1. `sd0` 底层和 FAT 在进入 PC 前可用；
2. OTG 最终识别为 USB Slave；
3. 应用进入 PC 模式并完成设备侧到 Host 的所有权交接；
4. USB Class 位图为纯 MSC，描述符已被 Host 请求；
5. Host 后续访问触发了 SD 设备打开/初始化；
6. Windows 已能把该 LUN 识别为磁盘。

日志中的多次 `usb reset` / `msd_reset` 位于描述符枚举阶段，且最终 Windows 已出盘，不能仅因日志使用了 `<error>` 级别就判定枚举失败。

这份日志没有覆盖 USB 退出和 VFS 恢复，也没有单独证明长时间读写、写缓存落盘和异常拔线可靠性。还需要补充安全弹出/拔线后的 `USB Stop -> 句柄释放 -> remount` 日志，以及大文件 Hash 和重复插拔测试。

日志中的 DIP、RDX、BT 退出和充电处理属于该产品的应用策略，不是 JL 文件系统或 MSC 的平台前提。

## 16. 总结

JL 平台上实现“PC 看到一个磁盘”的关键不是单独打开某个宏，而是打通并正确仲裁两条链路：

```text
设备侧：设备节点 -> dev_manager -> VFS -> 文件业务
PC 侧：USB Device MSC -> LUN -> 块设备 -> 物理介质
```

先分别证明块设备、VFS 和 MSC，再用显式所有权状态机把它们串起来。这样形成的方案才能从一个具体项目迁移到其他 JL 芯片、介质和产品形态中。
