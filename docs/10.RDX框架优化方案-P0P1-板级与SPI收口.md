# RDX 框架优化方案 — P0/P1：板级 config 接管与 SPI 参数化

> 依据：`docs/9.RDX框架重构真实达成度评估.md` 第 7 节建议的 P0、P1 优先级。
> 定位：面向开发者的技术执行方案，包含差距清单 + 具体改造步骤 + 验证方式。
> 涵盖范围：P0（board config 替代旧宏）和 P1（rdx_spi.c 参数化），不含 P2+。

---

## 术语表

| 术语 | 含义 |
|---|---|
| **旧宏** | `WIFI_POWER_PORT_IO`、`VDD_POWER_PORT_IO`、`LED_PT0807_DATA_PORT_IO`、`ESP8684_*_PORT_IO`、`IO_PORTC_*` 等直接在业务 `.c` 中硬编码引用的板级/芯片宏 |
| **board config** | `rdx_board_config_t` 结构体 + `rdx_board_get_config()` 访问器，当前已有两套 board 实例（t2616_cc / t2616_ep） |
| **board helper** | 新增的薄封装函数，例如 `rdx_board_wifi_power_off()`，内部从 board config 取值并操作 GPIO，对外提供语义化 API |
| **CHIP_TYPE 下沉** | 移除 `rdx_spi.c` 中的 `#if (CHIP_TYPE == CHIP_JL7018)` 条件编译；当前 CS 控制共用 `port/jl/common/`，后续确有芯片差异再下沉到 chip-family 目录 |
| **IO 宏** | `IO_PORTA_04`、`IO_PORT_SPILT()` 这类 JL SDK 提供的底层 GPIO 宏，仅在 board config `.c` 和 port 层中使用 |

### 1.1.3 PC2/PC3/PC4/PC5 硬件语义

PC2/PC3/PC4/PC5 属于明确的板级硬件资源：

| IO | 硬件功能 | 说明 |
|---|---|---|
| `IO_PORTC_01` | LED 数据脚 | = led_data_io，当前 board config 已覆盖 |
| `IO_PORTC_02` | `MIC_BIAS_CE` | 麦克风偏置使能 |
| `IO_PORTC_03` | SD NAND Flash `DATA0` | **当前 RDX 高阻序列中未明显出现** — 需确认 SD NAND 驱动是否已统一管理，历史代码是否漏管。不要贸然新增高阻操作。 |
| `IO_PORTC_04` | SD NAND Flash `CLK` | 当前在关机/低功耗路径中高阻 |
| `IO_PORTC_05` | SD NAND Flash `CMD` | 当前在关机/低功耗路径中高阻 |

### 1.1.4 Board config 字段补充

P0 改造不应把这些引脚抽象成无语义的 gpio map，而应在 board config 中保留真实硬件字段：

```c
typedef struct {
    // ... 现有字段保持不变 ...

    /* P0 新增：有板级硬件语义的引脚 */
    u32 mic_bias_ce_io;      /* IO_PORTC_02: MIC_BIAS_CE */
    u32 sd_nand_data0_io;    /* IO_PORTC_03: SD NAND DATA0（注意：仅定义字段，不贸然加入高阻序列） */
    u32 sd_nand_clk_io;      /* IO_PORTC_04: SD NAND CLK */
    u32 sd_nand_cmd_io;      /* IO_PORTC_05: SD NAND CMD */

    u8  led_spi_instance;    /* LED SPI 实例号（替代 LED_PT0807_SPI1） */
} rdx_board_config_t;
```

## 1.2 改造方案

### 1.2.1 新增 board HAL 函数

在 `board/` 层新增语义化 HAL，内部读取 `rdx_board_get_config()` 并执行 GPIO 操作。业务代码只调用动作接口，不直接操作 `IO_PORTC_*`。

```
新增文件：board/common/rdx_board_hal.h
         board/common/rdx_board_hal.c
```

API 列表：

```c
/* WiFi 电源控制 */
void rdx_board_wifi_power_on(void);
void rdx_board_wifi_power_off(void);

/* VDD 电源控制 */
void rdx_board_vdd_power_on(void);
void rdx_board_vdd_power_off(void);

/* LED 数据 IO */
u32  rdx_board_led_data_io(void);           // 返回 io 编号，供 led_pt0807_init 使用
u8   rdx_board_led_spi_instance(void);       // 返回 SPI 实例号（替代 LED_PT0807_SPI1）

/* 分场景 IO 状态切换（替代分散的 IO_PORTC_* 裸操作） */
void rdx_board_shutdown_io_state(void);          // 关机序列：LED + MIC_BIAS_CE + SD NAND CLK/CMD
void rdx_board_charge_poweroff_io_state(void);   // 充电满电关断：LED + MIC_BIAS_CE
void rdx_board_sd_nand_poweroff_io_state(void);  // SD NAND/eMMC 关断：SD NAND CLK/CMD
```

**实现原则**：

- 每个 HAL 内部调用 `rdx_board_get_config()` 取当前 board 的引脚值。
- 使用 `IO_PORT_SPILT()` 和 `gpio_set_mode()` / `rdx_gpio_set_*()` 执行实际操作。
- board config 中值为 `RDX_IO_INVALID` 的引脚，HAL 内部跳过操作（如 EP board 的 vdd_power_io）。
- 不同业务场景的高阻集合不同，不使用单一 `rdx_board_enter_low_power_io_state()` 覆盖所有路径，避免把 `rdx_charge.c` / `rdx_device_service.c` 的行为范围扩大。
- **不将 PC3（SD NAND DATA0）纳入上述高阻序列**，除非先确认 SD NAND 驱动已统一管理该引脚。当前代码中 PC3 未出现在高阻序列中，贸然新增可能破坏 SD NAND 通信。
- 不引入新的编译条件，通过 board config 的运行时/编译期多态实现板型差异。

#### 步骤 5：删除旧宏定义

改造完成后，从定义源删除宏：

- `xxpUart.h`：删除第 39/42/43 行的 `WIFI_POWER_PORT_IO`、`WIFI_POWER_ON`、`WIFI_POWER_OFF`。`WIFI_POWER_ON` / `WIFI_POWER_OFF` 仅有宏定义、无实际调用，安全删除。

删除宏会让任何残留引用立即触发编译错误，自然地定位遗漏点。

### 1.2.3 Board config 字段补充

Board config 结构体补充见 1.1.4 节。两个 board config `.c`（t2616_cc / t2616_ep）需同步更新新增字段的初始化值。t2616_ep 中 `sd_nand_data0_io` / `sd_nand_clk_io` / `sd_nand_cmd_io` 的引脚编号需根据 EP 板原理图确定（与 CC 板 PORT 映射可能不同）。

## 1.3 验证方式

### 编译验证

1. **三组合配置编译通过**（例如 `RDX_BOARD=t2616_cc RDX_CHIP_FAMILY=jl7018`、`RDX_BOARD=t2616_cc RDX_CHIP_FAMILY=jl7018_shadow`、`RDX_BOARD=t2616_ep RDX_CHIP_FAMILY=jl7018`，均需通过语法编译）。
2. **旧宏定义删除后零编译错误**。如果删除宏后仍有文件引用，说明迁移不完整。

### 静态检查补充

在 `tools/check_rdx_boundaries.bat` 中增加检查规则：

```
# 规则：业务 .c 不得直接引用旧板级宏
pattern: WIFI_POWER_PORT_IO|VDD_POWER_PORT_IO|LED_PT0807_DATA_PORT_IO
files:  rdx_app.c, rdx_charge.c, rdx_dut.c, rdx_device_service.c
expect: 0 hits

# 规则：业务 .c 不得直接操作 IO_PORTC_*（仅 board HAL 内部允许）
pattern: IO_PORTC_01|IO_PORTC_02|IO_PORTC_03|IO_PORTC_04|IO_PORTC_05
files:  rdx_app.c, rdx_charge.c, rdx_dut.c, service/*.c
expect: 0 hits

# 注意：PC3（IO_PORTC_03 / SD NAND DATA0）当前未出现在高阻序列中。
# 此处加入检查是为了主动发现未来是否有代码试图直接操作它，
# 而不是建议把它加入高阻序列。所有 PC3 操作应通过 SD NAND 驱动统一管理。
```

### 目标板冒烟

1. **WiFi 电源路径**：软关机 → WiFi 模块断电（测量 PA4 电平）→ 开机 → WiFi 模块上电。
2. **VDD 电源路径**：CC board 关机后 VDD 拉低，开机后 VDD 拉高；EP board 的 VDD 操作应因 `RDX_IO_INVALID` 被跳过（检查日志无异常）。
3. **LED 初始化**：开机 LED 灯效正常。
4. **充电场景**：插入充电器后 WiFi 正确断电。

## 2.2 改造方案

### 2.2.1 总体思路

`rdx_spi.c` 改为通过 `rdx_board_get_config()` 获取所有板级参数。`CHIP_TYPE` 分支从业务文件中移除；当前 JL7018 / jl7018_shadow 的 CS 控制逻辑一致，统一放到 `port/jl/common/`。

改造顺序：
1. 补齐 `rdx_board_config_t` 中的 SPI 组合 IO 字段。
2. 在 `rdx_spi.c` 中加入 board config include 并替换所有硬编码。
3. 将 `CHIP_TYPE` 分支转为 port 层提供的参数或 vtable。
4. 清除 `rdx_spi.c` 顶部的所有旧引脚宏。

### 2.2.2 Board config 字段补齐

`rdx_board_config_t` 保持"每个引脚一个组合 IO 值"的模型，不新增 `spi_cs_pin` / `spi_cs_port` 这类派生字段。`rdx_spi.c` 和 port 层在实际操作 GPIO 时直接使用 `IO_PORT_SPILT(cfg->spi_cs_io)` 等 JL SDK 宏完成拆分。

板级类型定义统一抽到 `board/common/rdx_board_config_types.h`，`t2616_cc` / `t2616_ep` 的 `rdx_board_config.h` 只保留 `RDX_CHIP_FAMILY`、`RDX_BOARD_NAME` 和 `rdx_board_get_config()` 声明，避免两个 board header 复制结构体字段。

### 2.2.3 `rdx_spi.c` 逐项替换

#### 替换 1：CS 引脚操作

```c
// 当前 (行 207)
gpio_set_mode(IO_PORT_SPILT(ESP8684_CS_PORT_IO), PORT_OUTPUT_HIGH);

// 替换为
const rdx_board_config_t *cfg = rdx_board_get_config();
gpio_set_mode(IO_PORT_SPILT(cfg->spi_cs_io), PORT_OUTPUT_HIGH);
```

`spi_cs_h()` / `spi_cs_l()` 宏同样改为使用 `cfg->spi_cs_io`。

#### 替换 2：Handshake 引脚操作

```c
// 当前 (行 655)
while (gpio_read(ESP8684_HANDSHAKE_PORT_IO) && wait < 500)

// 替换为
while (gpio_read(cfg->spi_handshake_io) && wait < 500)
```

`gpio_irq_config_esp` 的 `.gpio` 字段同样从 `cfg->spi_handshake_io` 取值。

#### 替换 3：SPI 平台数据

```c
// 当前 (行 1067-1085)
struct spi_platform_data spix_p_data_rdx = {
    .port = { IO_PORTA_05, IO_PORTA_06, 0xff, ... },
    .clk  = 16000000L,
    ...
};

// 替换为
struct spi_platform_data spix_p_data_rdx = {
    .port = {
        cfg->spi_clk_io,   // SCLK
        cfg->spi_mosi_io,  // MOSI
        cfg->spi_miso_io,  // MISO
        0xff, 0xff, 0xff,
    },
    .clk  = cfg->spi_clk_hz,
    ...
};
```

#### 替换 4：删除 `spi_cs_pin` 冗余字段

`esp8684_param.spi_cs_pin` 在 CS 操作改为 `cfg->spi_cs_io` 后已无有效调用路径，结构体字段直接删除，不再保留无赋值的兼容字段。

### 2.2.4 CHIP_TYPE 分支下沉

当前 `rdx_spi.c` 中有 2 处活跃 `#if (CHIP_TYPE == CHIP_JL7018)`：

1. **行 204** — `spi_cs_init()` / `spi_cs_uninit()` 差异：JL7018 走 `jl_spi_set_cs_pin()`，非 JL7018 走 `gpio_set_mode()`。
2. **行 1055** — `HW_SPI2` vs `HW_SPI1` 选择。

处理方式：

- **行 1055（HW_SPI2 vs HW_SPI1）**：直接在 `spi_platform_data` 初始化后通过 `board_get_config()->spi_port` 选择。`spi_port` 字段为 `u8`，board config `.c` 中填写 `HW_SPIx` 枚举值。

- **行 204（spi_cs_init/uninit 策略）**：将这个差异封装为 port 层函数：

```c
// port/jl/include/rdx_port_spi.h
void rdx_port_spi_cs_init(u32 cs_io);
void rdx_port_spi_cs_uninit(u32 cs_io);
```

当前 JL7018 与 jl7018_shadow 的 CS init/uninit 行为一致，具体实现放在 `port/jl/common/rdx_port_spi.c`。`rdx_spi.c` 调用 `rdx_port_spi_cs_init(cfg->spi_cs_io)`，不再需要条件编译。未来新增芯片族如确有差异，再按实际差异拆出 chip-family 实现。

### 2.2.5 清除旧宏

改造完成后删除 `rdx_spi.c` 中行 69-101 的所有 `ESP8684_*_PORT_IO` 及其 `_PORT` / `_PIN` 变体宏定义。同时删除 `rdx_spi.h` 中的 `CHIP_TYPE` / `CHIP_JL7018` / `CHIP_JL7016` 定义。

## 2.3 验证方式

### 编译验证

1. **t2616_cc + t2616_ep 两个 board 配置均编译通过**。
2. **`ESP8684_*` 宏删除后零引用**。
3. **`CHIP_TYPE` 引用仅出现在 `port/jl/` 和 board config 中**，不出现在 `rdx_spi.c` 中。

### 静态检查补充

```
# 规则：rdx_spi.c 不得引用 ESP8684 旧宏
pattern: ESP8684_
files:  rdx_spi.c
expect: 0 hits

# 规则：rdx_spi.c 不得有 CHIP_TYPE 条件编译
pattern: CHIP_TYPE
files:  rdx_spi.c
expect: 0 hits
```

### 目标板冒烟

1. **SPI 通信正常**：录制一段音频 → ESP8684 成功接收数据 → 无 SPI 超时或 CRC 错误。
2. **SPI 握手正常**：`notify_slave_to_recv()` 和 `spi_wait_handshake_low()` 时序正确。
3. **CS 拉高拉低正常**：chip select 时序符合 ESP8684 规格要求。
4. **多板型验证**：t2616_cc（`spi_port=HW_SPI2`, 16MHz）和 t2616_ep（`spi_port=HW_SPI2`, 8MHz）均在目标板上通过 30 秒录音测试。
5. **⚠ EP SPI 时钟需实测**：t2616_cc 保持原 16MHz 行为；t2616_ep 使用新板型配置的 8MHz，必须实测 SPI 传输稳定性与端到端录音转发延迟是否满足要求。
