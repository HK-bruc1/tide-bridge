## 1. 需求与结论

APP 新增的音量控件**只查询和设置设备本地录音回放的音量**。设置后应在播放、暂停和停止状态下保持一致，并沿用设备现有的音量记忆能力。

不属于本需求：

- 不调节麦克风录音增益、录音文件内容、提示音、通话音量或手机系统音量，也不改变其他可用音源的音量。
- 不改变现有实体按键的配键、两档步进、准入或非回放场景下的行为。APP 界面按两档为一步操作；协议仍传递原始档位，并兼容已有奇数音量。
- 不新建一套音量 VM、dirty 状态、周期定时器或复位补写机制。若严格隔离使既有记忆链无法安全复用，必须先另行设计兼容方案，而不是忽略隔离要求。

当前设备已经可以识别 `0x07 + F15/F16` 的本地音量功能，但 KEY1～KEY5 的默认映射是 F13、F14、F17、F18、F19，并非默认包含 F15/F16；需要先通过配键把它们映射到实体键。现有音量按键路径按当前音频状态调节：IDLE/MUSIC 改 `music_volume`，CALL 等状态可能改其他音量，不能把它一概称为回放专属。

**实施路线：**复用既有回放音量运行值和 SDK 记忆，增加 RDX `custom#vol` 查询、设置和按键变化通知。当前源码未显示必须另建回放音量状态或 VM 的正常产品路径；实施与测试围绕第 2 节列出的具体边界展开，发布前完成验收。以下协议已按设备端源码实施，但仍不等于实机或 APP 联调已通过。

当前预期的原始最大档位是 16，尚需实板确认。若确认为 16，APP 展示 8 个调整间隔，每个间隔对应设备原始音量 2 档；0 到 8 包含 9 个刻度位置，0 为最低档，不预先承诺绝对静音。

## 2. 现有能力与产品边界

### 2.1 已有记忆，不需要重复实现

用户已实测确认：通过现有本地音量调节改变回放音量后，重启可以记忆。该结果确认的是**已有本地入口的能力**，不包含 APP SET 的实机验证，也不扩展为立即异常断电的持久化保证。

源码中的既有记忆链与该结果一致：

1. IDLE/MUSIC 音量的运行值是 `app_var.music_volume`；SDK 音量变化路径会延迟写入 `CFG_MUSIC_VOL`（`SDK/audio/common/audio_volume_mixer.c:661`）。
2. 开机从 `CFG_MUSIC_VOL` 读取；读不到时使用已有默认值逻辑（`SDK/apps/earphone/user_cfg.c:260`）。
3. 正常关机路径已有写入（`SDK/apps/earphone/mode/idle/idle.c:117`、`:142`）；整机恢复出厂调用 `rdx_vm_playback_volume_set_default()` 写入并设置最大值（`SDK/apps/common/third_party_profile/rdx_protocol/rdx_vm.c:798`）。

APP 通过正确的 SDK 设置路径修改同一个运行值，即复用这条记忆链，不增加 APP 专用 VM、dirty 状态、保存定时器或关机/复位补写。当前仓内源码及 Makefile 未发现 `AUDIO_VOLUME_SAVE_DISABLE` 的定义；最终构建仍须保持音量保存启用。异步保存的时序和限制见第 6 节。

### 2.2 已核查的当前产品边界

以下是源码核查结果，不替代最终构建和实机时序验证：

| 范围 | 已确认的源码事实 | 对本方案的约束 |
| --- | --- | --- |
| 音量运行值与节点 | IDLE/MUSIC 共用 `app_var.music_volume`；dev-flow 运行时 MUSIC 音量指向 `74E325`，其余场景可能指向 `Vol_BtmMusic` 等节点，节点更新有延迟回调（`audio_volume_mixer.c:710`、`:825`、`:867`） | 复用共享值和保存链，但须核对播放/停止时的节点、最大档位与切换行为 |
| 经典蓝牙 | 生成配置保留 A2DP/音量同步，`vol_sync.c:75` 的同步路径也存在；但 `BT_STATUS_INIT_OK` 后安排 1000 ms 定时关闭经典 BT，包含清回连列表、关闭双连接和 `USER_CTRL_POWER_OFF`（`rdx_app.c:1716`、`:1849`）。仓内可见 `rdx_app_bt_open()` 的唯一调用在进入 DUT，退出 DUT 再关闭（`rdx_dut.c:2120`、`:2147`） | 不能仅凭生成配置认定正常模式持续开放 A2DP；验证启动窗口、历史配对重连和 DUT 退出，不预设要重构音量隔离 |
| 其他音乐源 | 仓内正常业务的 dev-flow 播放入口是本地录音播放器（`rdx_playback.c:574`）；`app_default_msg_handler.c:538`、`:549` 的测试入口未注册。当前普通音乐、LINEIN、LE Audio 应用关闭；项目默认关闭 PC 模式，启用可选 PC 存储时也关闭 USB 音频 | 当前未发现另一个正常可用的共享音乐源；未来开启其他音源时须重新核查，不能沿用本次结论 |
| 提示音与通话 | 通话使用 `call_volume`；提示音、按键音、铃声有独立运行值。固定提示音配置会拒绝普通 WTONE SET，但其独立值为 0 时 `app_audio_get_volume()` 会回退到 `music_volume`（`audio_volume_mixer.c:890`、`:895`、`:1025`） | 固定音量宏本身不能证明响度隔离；核对实际加载的 `Vol_SysTone/Vol_SysKTone/Vol_SysRing` 配置及实际输出 |
| DUT 喇叭测试 | 暂时设置共享音乐音量，再恢复测试前的值（`rdx_dut_speaker.c:138`、`:169`） | 产测期间 GET/SET 均 busy，不能展示临时值或让测试恢复覆盖 APP SET；不额外承诺 DUT 中异常掉电的记忆 |

因此，当前有依据采用最小复用，而不是先新增独立音量状态或 VM。但不能把“正常模式关闭经典 BT”扩大为所有时序均已隔离；只检查 IDLE/MUSIC 或增加 busy，也不能代替下述验收。

### 2.3 最小复用决策与交付验收

本版按**最小复用方案**进入实现：APP 使用现有运行值和 `CFG_MUSIC_VOL`，不改变其保存策略。发布前基于最终构建完成以下针对性验收，并记录配置、覆盖场景和结果：

1. 经典 BT 的启动关闭窗口、已有配对设备的重连及 DUT 退出符合预期；这些路径和迟到的蓝牙同步回调不会意外改变用户回放音量。产测期间按第 5 节屏蔽读写，结束并恢复后再查询。
2. 核对实际加载的提示音、按键音、铃声独立值，确认不会因零值回退而跟随 `music_volume`；将回放音量从最低调到最高，验证提示音不变，并覆盖 SET 后紧邻提示音/录音启动的异步回调。
3. 播放中、暂停、停止及重新开流时，APP 查询值、回放响度和既有重启记忆一致；覆盖无历史 VM、`volume_def_state=1`、同值 SET，以及 `Vol_BtmMusic` 与 `74E325` 的最大档位和缩放关系。
4. DUT/工厂音频、恢复出厂及其他切换期间准入正确，结束后不暴露临时值。对最终产品可达的通话或其他音源，验证 APP SET 不改变其音量或手机系统音量；不可达场景记录依据，不为 SDK 中仅存在的通用路径额外扩建音量系统。

若上述验证发现实际共享冲突，或产品配置新增其他音乐源，先定位具体路径并评审必要的场景隔离和记忆兼容，再决定改动范围；不能靠 busy 掩盖冲突，也不能未经论证就新增 VM。未解决的实际隔离问题仍是发布阻塞项，不把当前源码核查等同于已完成板测。

## 3. 通道与协议

复用现有 RDX `custom` 通道，新增 `vol`，不修改 HID 报告描述符和配键协议。HOGP Output Report 是键盘 LED 报告，不是录音回放音量的 APP 控制通道；当前 Output Report 的 value handle 见 `rdx_hogp_profile.h:103`。

现有 `rdx_app_volume_indicate()` 会按当时音频状态将音量换算成百分比，由 AVRCP 音量变化事件触发（`rdx_app.c:844`、`:1733`）。这是旧音量主动上报，不是本地回放 GET/SET 接口。**本控件只采纳 `custom#vol` 的原始 `cur/max`，不得用旧百分比音量通知更新它，也不以支持旧上报推断支持本协议。**

```text
查询：*APP#custom#vol#get,<id>#
设置：*APP#custom#vol#set,<id>,<level>#
应答：*DEV#custom#vol#<id>,<result>,<cur>,<max>#
主动：*DEV#custom#vol#0,ntf,<cur>,<max>#
```

| 字段 | 约定 |
| --- | --- |
| `id` | 1～65535，1～5 位 ASCII 十进制；允许前导零，应答原样带回。`0` 只用于主动通知 |
| `level` | 1～2 位 ASCII 十进制，范围 `0..max`，允许前导零；是设备**原始绝对档位**，不是 APP 的 0～8 格数，也不是百分比 |
| `cur` | 当前可信的回放**原始档位**，`0..max`；可以是奇数，busy 时固定为 0 |
| `max` | 回放**原始最大档位**，必须为 1～99；busy 时固定为 0。16 是当前配置的待验证值，APP 不写死 |
| `result` | 请求应答为 `ok`、`busy`、`arg`；主动通知为 `ntf` |

| 结果 | 设备语义 | APP 处理 |
| --- | --- | --- |
| `ok` | GET 获得可信值；或 SET 被运行时接受。SET 不保证音频节点已完成异步更新，也不保证写入 Flash | 用应答中的 `cur/max` 更新显示 |
| `busy` | 当前不能安全执行或不能取得可信值；不执行 SET，统一返回 `0,0` 哨兵 | 不显示成 0，不计算 `cur/max`；提示暂不可用，忙状态结束后重新 GET |
| `arg` | 可识别请求 ID，但操作或参数不合法；不修改音量 | 排查 APP 请求；`cur/max` 是当前可信值 |
| `ntf` | 设备侧确认回放音量发生变化后的尽力通知 | 按有效的 `cur/max` 刷新；不需要应答 |

对于有效 ID，若当前取不到可信的 `cur/max` 或处于要求屏蔽查询的状态，优先返回 `busy,0,0`，不构造带不可信值的 `arg`。请求缺少合法 ID 时不回复。

`get`、`set` 和命令名使用小写；不允许空格、多余逗号字段或换行。严格解析适用于预编译协议库已经交给 `rdx_app_custom_command_parse()` 的 `value`：先恢复合法 ID，再检查其余语法。库可能先截取 wire 字段，不能仅凭新增模块保证所有额外 `#` 等原始帧错误都能被检测；实施时须用实际库接收路径测试并记录边界。

SET 使用绝对原始档位，连续重复设置同一个值不会累加音量；但若中间有实体键等其他操作，再次发送旧 SET 可能覆盖新的音量。合法 SET 先校验 `0..max`，再改运行值：SDK 的 `audio_app_volume_set()` 会先保存传入值，不能依赖后续输出限幅来拦截越界。协议接收范围内的整数，包括奇数；不能因界面步进为 2 就拒绝奇数或自动改为偶数。

### 3.1 APP 显示与两档步进

协议保留原始 `cur/max`，不将两个字段改成 0～8。以实机最终确认 `max=16` 为例：

| 设备原始 `cur` | APP 显示位置 | 说明 |
| ---: | ---: | --- |
| 0 | 0/8 格 | 最低档 |
| 2 | 1/8 格 | 一个完整间隔 |
| 6 | 3/8 格 | 常规偶数值 |
| 7 | 3.5/8 格 | 保留并如实表示奇数值 |
| 8 | 4/8 格 | 常规偶数值 |
| 16 | 8/8 格 | 最大档 |

显示位置按 `cur / 2` 换算，显示范围随真实 `max / 2` 变化；16 是目标产品的待验证配置，不是让 APP 把协议 `max` 写死为 16 或 8。若以后原始 `max` 不是 16，APP 须根据实际值展示，不能仍声称恰好有 8 个完整间隔；若上限为奇数，末端可能只有半个间隔。

- APP 的“加一格/减一格”以最近一次可信的**原始** `cur` 为基准，计算 `min(cur + 2, max)` / `max(cur - 2, 0)`，再通过绝对 SET 提交。达到上下限时限幅，不重复提交同值；例如原始值 15 加一格只能到 16。
- 滑条可显示 0～8 的刻度，建议在奇数音量时如实表示两个刻度之间的位置。一次拖动可跨多格：在无并发变化时，以手势开始时最近的可信原始值为基准，将位移换算成整数个两档增量，再限幅并发送绝对 SET；不能先把奇数基准四舍五入成偶数。若设备状态在手势期间发生变化，按第 7 节处理并发。
- APP 启动、GET、收到通知或刷新界面时，**不得因为显示换算而自动发送 SET**，也不得把已有的奇数音量或 VM 记忆悄悄归一化。界面若只能近似显示，必须保留原始 `cur` 用于下一次运算，且不能把近似位置当成设备的真实值。
- 原始值 7 按一次加键目标为 9，减键目标为 5；APP 可以向设备发送这些奇数。默认只新增绝对 GET/SET 和通知，不新增相对加减指令。

上述步进与实体键一致，是指基于相同原始值且没有并发修改时的行为；绝对 SET 与按键并发时不能保证每次操作都被累加，详见第 7 节。

## 4. BLE 长度与收发

### 4.1 上行：请求必须一次完整写入

协议使用 ASCII，一个字符占 1 字节：

| 请求 | 字节数 |
| --- | ---: |
| `*APP#custom#vol#get,1#` | 22 |
| `*APP#custom#vol#set,1,0#` | 24 |
| `*APP#custom#vol#set,65535,99#` | 29 |

默认 ATT MTU 23 的普通写入载荷只有 20 字节，连最短 GET 都装不下。现有接收链不能假定自动把多次 GATT 写拼成一条 custom 命令；`rdx_ble_server.c:3184` 也拒绝非零 offset，不能假定 ATT long write 可用。

现有 `rectone`/`recsave` 走同一 `custom` 写入和解析通道，其最长合法请求均为 32 字节；`vol` 最长只有 29 字节，没有引入更高的传输要求。因此，若目标 APP/设备组合已经能够按既有方式发送 `rectone`/`recsave` 的 32 字节请求，`vol` 可直接沿用该基线开始联调，不需要再增加一道前置门槛。对普通 ATT Write Request/Command，32 字节请求要求协商后的 ATT MTU 至少为 35；实际能力以既有业务在目标平台的表现和首轮抓包为准。

首轮 `vol` 联调仍建议用抓包或固件接收日志确认 29 字节确实作为一次完整写入到达，但这属于测试确认，不是启动阻塞条件。若目标平台连既有 32 字节 `rectone`/`recsave` 路径也不能满足，则音量功能同样标记为暂不可用，不发送半条命令。若以后需要支持更小 MTU，须另行设计有界收包、超时、owner/token 和断连清理并测试；**不能由 APP 直接分两次写入来冒充一条命令**。

### 4.2 下行：应答可能分片

按本协议的字段上限，最长合法应答 `*DEV#custom#vol#65535,arg,99,99#` 为 32 字节；设备应答缓冲区建议至少 48 字节，包含结尾 `\0`。即使上行 MTU 满足 32，下行仍可能分为多个 notification。

设备侧使用 `rdx_ble_server_send_text_for_token()` 按当前 MTU 分片。APP 复用 RDX 文本流接收器，从完整帧中识别 `vol`，按结尾 `#` 拼帧；遇到新帧起始而旧帧不完整时丢弃旧半帧。断连清空拼帧缓存。其他业务共用通道时，还须验证帧间并发和恢复行为。

该发送接口可能在发送部分分片后失败，也不能把入队成功当成端到端送达；有竞争或拥塞时 APP 可能收到不完整帧，以超时和重新 GET 恢复，不保证通知必达。

## 5. 设备端执行与准入

### 5.1 线程、会话和回包

新增 `rdx_volume.c/.h` 并从 `rdx_app_custom_command_parse()` 的 runtime-active 检查之后分发，参照 `rdx_record_tone.c`：

1. 在协议任务捕获当前 RDX owner 的 token，确认 RDX CCC 已订阅；恢复 ID、解析请求，并将请求投递到 `app_core`。
2. 在 `app_core` 上执行准入、取值和设置。执行前复核原 token 和 CCC，不能将旧请求转交给新 owner。
3. 回包前再次复核同一个 token 和 CCC，使用 `rdx_ble_server_send_text_for_token()`。分配失败、队列满、连接失效或发送失败时可无应答。
4. 执行前检查时会话已失效则丢弃请求；如果断连与检查后的设置竞争，可能仍会执行。已执行的设置不回滚，但不得向新会话发送旧应答。APP 重连后 GET。

音量 API 会安排调用任务上的延迟回调，不能直接从协议任务或硬件定时器调用。GET 也在 `app_core` 中读取一致的运行状态，不在协议任务直接访问共享音量。协议任务捕获当前 token 本身不等于入站包已绑定原始会话：实施时还须验证现有 RDX FIFO 生命周期屏障覆盖旧包排队、释放和新 owner 接管，避免旧包被误绑定到新会话。

### 5.2 最大档位、默认态与 SET

最小复用方案中，回放最大档位以已验证的本地回放节点配置为准。`app_audio_get_max_volume()` 随当前音频状态变化，不适合直接作为协议上限。

`app_audio_volume_max_query(AppVol_BT_MUSIC)` 间接调用的 `volume_ioc_get_max_level()` 不检查读取结果：`volume_ioc_get_cfg()` 读失败时会返回错误并填入最大档位 16 的回退值（`SDK/audio/framework/nodes/volume_node.c:248`）。因此 `max <= 0` **无法检测配置读取失败**。

实施时应明确选择可验证的读取方式：例如在适用的 scene 下调用 `volume_ioc_get_cfg()` 并检查返回值；只有确认 scene、配置来源和生命周期后，才可使用经过验证的缓存。读取失败、值不在 `1..99`、当前值不在 `0..max`，或本地播放节点上限无法确认时，返回 `busy,0,0`，不要把回退的 16 当成读取成功。实板核对 `Vol_BtmMusic` 与 `74E325` 的上限及缩放关系；如无法从当前 scene 正确读取，先解决配置来源，不得擅自写死。

SET 在 `app_core` 串行执行：

1. 校验 session、准入、可信 `cur/max`，以及原始目标范围；失败时不修改音量。奇数只要处于 `0..max` 也是合法目标。
2. 选择已证明只影响回放的设置路径。最小复用方案下，还要确认当前没有其他 MUSIC 音源，且延迟回调不会误作用于切换后的其他音源；不能只检查 IDLE/MUSIC。
3. 合法 SET 即使与当前值相同，也先调用 `app_audio_set_volume_def_state(0)` 或通过经验证的等价操作取消默认态。否则开机无 VM 时下一次音频初始化可能重新选择默认值。
4. 数值未变化时可直接回复 `ok`，不人为重启 SDK 保存定时器；这不承诺同值 SET 会新写 VM。数值变化时，通过已验证的 SDK 音量设置路径应用，让现有记忆链负责延迟保存。

开机无 `CFG_MUSIC_VOL` 时，SDK 保留 `volume_def_state`，之后的音频初始化可能根据节点配置重置运行值（`audio_volume_mixer.c:801`）。因此 GET 不能简单假设开机时的 RAM 值必然是下一次回放值：须验证默认态下两者一致；若不一致，应在不扰动其他音源的前提下正确解析回放默认值，否则返回 busy 并先完善设计。

### 5.3 GET / SET 状态约定

以下 busy 仅表示命令**到达模块、ID 可识别且会话和回包仍有效时**应返回的结果，不保证每种场景一定能收到应答。准入以 `app_core` 实际执行时的状态为准；请求在队列中等待时，设备状态可能已经发生变化。

| 场景 | GET | SET |
| --- | --- | --- |
| 正常待机、本地回放中、暂停或停止，且已通过隔离核验 | 值可信时 `ok` | 符合准入时 `ok`；播放与切换竞态无法安全处理时 `busy` |
| 普通录音、录音开始/停止处理、录音按键会话或普通提示音期间 | 可信时 `ok`；不能确认则 `busy` | 默认 `busy`，不修改音量 |
| DUT、工厂音频、恢复出厂过程中 | `busy`，不展示临时或中间值 | `busy` |
| 存储切换、格式化、PC 模式、关机及其他不安全切换 | `busy` | `busy` |
| 通话或其他音源 | 值可信时可 `ok`，否则 `busy` | 默认 `busy`；发现共享音乐源可用时，仍须完成第 2.3 节隔离设计 |
| OTA、断连、CCC 关闭、上游丢包或队列满 | 可能无应答 | 可能无应答；不能保证返回 `busy` |

SET 可参考现有 `rdx_record_config_busy()` 覆盖关机、OTA、DUT/工厂音频、存储/格式化、录音相关忙状态和 `tone_resetting` 等，再补足 PC、音源和播放切换判断；不能把其中的恢复出厂锁排除。`tone_resetting` 在恢复流程中晚于音量恢复步骤才置位，不能仅靠它证明覆盖整个恢复窗口：还须核验所有恢复入口与 `app_core` 的串行关系；若存在并发窗口，应先设计完整的恢复准入和失败清理。GET 需要独立判断，不能直接复用会把普通录音也判忙的整套 SET 门禁。

OTA 期间，预编译库的接收路径可能在 custom 分发前就丢弃请求，因此即使设备端的 SET 门禁包含 OTA，也不能承诺 GET 或 SET 必有 busy 应答。产测忙结束后 APP 应重新 GET，不能沿用产测临时值。

### 5.4 按键通知

- 保持 `rdx_app_local_volume_change()` 现有的按键路径和行为；不为接入 APP 强制改写为统一 apply。
- 在已证明隔离的实现中，只有确认按键使**目标回放音量**实际改变时才安排 `ntf`；同值、被拦截或只改变通话音量时不通知。不要直接监听全局 `APP_MSG_VOL_CHANGED` 并把所有来源都当成回放变化。
- 在 `app_core` 使用约 150 ms 定时合并连按；发送时读取最新的可信原始 `cur/max`，包括奇数，而不是缓存第一次按键的值或换算为 APP 格数。SET 成功时取消该会话尚未开始提交发送的旧按键通知，使用 SET 应答表示当前值；之后的新按键可重新安排通知。
- 定时器绑定触发时的 RDX owner token；发送前复核该 token、待发批次有效性和 CCC。断连、owner 更换、CCC 关闭或值不可信时丢弃，不得改捕获新会话后发送旧通知。无 owner、定时器创建失败或发送失败均可丢弃。
- **CCC 关闭要显式作废关闭前的待发批次。**当前关闭分支会清订阅状态，但不会推进会话 token（`rdx_ble_server.c:3224`）；token 不包含 CCC 订阅代次（`rdx_ble_session.c:335`）。因此仅检查发送时的 token 和 CCC，无法识别同一 ACL 的快速 `0→1`。在 CCC 关闭入口调用 token 范围内的通知取消接口，立即使旧批次失效；定时器清理仍在 `app_core` 执行。若清理延后，须携带旧批次标识，不能误删重新订阅后产生的新通知，不能仅排队清理而让旧批次在重订阅后继续发送。不为此改造全局会话 token 或新增持久化状态。
- 恢复出厂会改变默认值，但可能随后复位或中途失败；不承诺恢复期间的 `ntf` 可达。APP 在恢复结束或重新连接后重新 GET。

取消针对模块内尚未开始提交发送的待发通知；批次领取进入发送阶段与作废操作须同步，之后不承诺撤回已开始提交或正在 BLE 发送链中的通知/分片。APP 关闭订阅时清理在途请求和拼帧缓存、禁用控件；重新订阅后用新 ID GET 确认，取得有效应答前不因 `ntf` 恢复可调状态。150 ms 是合并策略，不是端到端送达时限；若业务并发导致文本分片交错或丢失，按第 4.2 节恢复。

## 6. 音量记忆与恢复出厂

| 场景 | 本方案沿用的现状与边界 |
| --- | --- |
| 音量连续变化 | SDK 的 1 秒周期定时器在变化时清零计数，第 5 次计数后写 `CFG_MUSIC_VOL`；不重设周期，因此末次变化后约数秒写入，实际受调度影响，并非严格的 5 秒承诺 |
| SET 的 `ok` | 表示运行时接受，不表示 Flash 已写入或音频节点更新已经完成；SDK 延迟写没有检查 `syscfg_write()` 的结果 |
| 正常关机 | 现有 `idle.c` 路径会尝试写音量，但不能据此保证底层 Flash 写入成功 |
| 设置后立即重启、异常复位或断电 | 末次变化可能尚未保存；不新增复位补写，也不承诺异常掉电持久化 |
| 录音期间 | 虽然本方案默认拒绝新的 SET，但录音开始前已启动的 SDK 延迟写仍可能在录音期间发生；需要实机验证录音质量 |
| 整机恢复出厂 | 沿用 `rdx_vm_playback_volume_set_default()`：该步骤检查写入返回长度并同步运行值到最大；后续其他恢复步骤仍可能失败，不把整次恢复视为原子操作 |
| 仅重置配键 | 不修改音量 |

拨码 3 秒保护回调是硬件定时器上下文（`rdx_dip_switch.c:72`），不得在其中写 Flash、输出日志或投递队列；其他 `cpu_reset()` 路径也不因为本功能增加无条件的 app_core 专属调用。

如果产品另有“SET 应答后立即断电也必须保留”的强持久化要求，需要单独评估可执行上下文、断电保障、写入确认和磨损；不能将现有的延迟保存描述成已经满足该要求。

## 7. APP 对接流程

1. 建立 RDX 会话、订阅 CCC，并确认第 4.1 节的单次完整写入能力后，用新 ID 发送 GET。每次重连、重新建立 RDX 会话或恢复 CCC 订阅后重新 GET；CCC 关开后仍不得复用可能收到迟到应答的 ID。
2. 保留设备上报的原始 `cur/max`，仅在界面显示时换算成第 3.1 节的格数。加减以原始值为基准增减 2 并限幅；拖动按原始基准计算整数个两档增量，松手时发送绝对 SET。
3. 一次只保留一个 `vol` 请求在途。连按可等待上一次应答后基于最新可信原始值计算，或合并为一个绝对目标；拖动中若需要连续发送，也必须串行处理并基于新反馈重新计算。应答按 ID 匹配，避免复用仍可能收到迟到应答的 ID。
4. `ok` 和合法 `ntf` 更新原始值及显示；`busy,0,0` 表示不可用，不用该哨兵刷新滑条，也不做除法。`arg` 不重试错误参数。界面刷新或收到新值不应自行触发 SET。
5. 例如 2 秒内未收到完整应答时显示“暂不可用/未确认”，而不是认定旧固件不支持：小 MTU、OTA、断连、拥塞或回包丢失都可能超时。只有结合可靠的固件版本/能力信息才能区分不支持与暂时失败。
6. SET 超时后不要假定成功或失败；会话和写入能力恢复后，用新的 ID GET 核实。无需盲目重复 SET 或持续轮询。
7. 收到 busy 后等相关操作结束或用户重试时 GET；恢复出厂及产测结束后、重新连接后也要 GET。通知是尽力同步，不是持久状态来源。

**并发边界：**本方案的 SET 是绝对值，没有版本号或原子加减语义。APP 读取到 6 后计算“加一格”目标 8，若实体键先把音量从 6 加到 8，随后 APP 的 SET 8 仍得到 8，而不是 10；如果 APP 基于过期值计算减档，也可能覆盖实体键的更新。通知可能延迟或丢失，APP 串行发送及在发现冲突后 GET 只能获取查询执行时的状态，不能保证并发操作都被累加，也不能保证查询之后音量不会再变化。若产品要求并发下每次按下都严格相对设备最新值增减 2，须另行设计在 `app_core` 原子执行的相对加减指令及请求去重/重试语义，不能把它当成本版绝对 SET 已具备的能力。

示例假设相关状态可达模块、最大档位已验证为 16：

```text
连接后查询，原始 6 对应 APP 的 3/8 格：
APP -> *APP#custom#vol#get,1#
DEV -> *DEV#custom#vol#1,ok,6,16#

APP 增加一格，设置原始值 8，显示为 4/8 格：
APP -> *APP#custom#vol#set,2,8#
DEV -> *DEV#custom#vol#2,ok,8,16#

已配置的 0x07+F16 再增加两档，尽力通知原始值 10，显示为 5/8 格：
DEV -> *DEV#custom#vol#0,ntf,10,16#

独立场景：设备历史原始值为 7，显示为 3.5/8 格：
APP -> *APP#custom#vol#get,3#
DEV -> *DEV#custom#vol#3,ok,7,16#
APP 增加一格，基于 7 设置为 9，显示为 4.5/8 格：
APP -> *APP#custom#vol#set,4,9#
DEV -> *DEV#custom#vol#4,ok,9,16#

录音中设置，被拒绝：
APP -> *APP#custom#vol#set,5,11#
DEV -> *DEV#custom#vol#5,busy,0,0#

录音结束后越界：
APP -> *APP#custom#vol#set,6,20#
DEV -> *DEV#custom#vol#6,arg,9,16#
```

- 验证播放、暂停、停止、重新开流时的 GET/SET、最低档及最大档，确认最低档是否绝对静音；无历史 VM 的首次开机和同值 SET 后重新播放也要一致。
- 确认目标 scene 的配置读取返回值、`Vol_BtmMusic` 与 `74E325` 的最大档位和实际响度映射；确认是否确为 16，不要只看 SDK 的 16 档回退。若上限不同，按实际 `max` 展示，不把 8 格当作已验证结论。
- 至少在目标 APP 平台验证 MTU 不足时禁用、单次 29 字节完整上行、下行分片、拥塞、重连、CCC 快速关开和与其他 RDX 业务并发；恢复订阅后重新 GET，旧百分比音量上报不影响本控件，超时不直接判为旧固件。
- 先把 F15/F16 配到实体键，验证播放时两档步进及连按通知；CALL、busy、断连/重连和会话切换时行为符合第 5.4 节。
- 验证 APP 与实体键从相同偶数、奇数原始值各自单步调整时都按 2 档变化，端点按实际限幅；例如 7 对应 3.5/8 格，增加后为 9、显示 4.5/8 格。验证并发时以设备最终回复及后续 GET 为准，不承诺操作累加。
- 使用已有或测试注入的奇数记忆值验证开机、查询和界面刷新不会因显示换算而自行取整或触发新的音量写入；正常关机仍可能按既有路径写回，重新启动后奇数值应保持。
- 验证 SET 后等待 SDK 保存并正常关机重启的记忆表现；分别测试立即复位/断电并记录可能丢失。验证恢复出厂最大值和单独配键重置不影响音量。
- 验证录音、提示音及 DUT/工厂音频期间的准入；覆盖“调音后立即开始录音”时原有延迟 VM 写入对录音的影响。产测结束后 GET 不应返回其临时音量。

## 10. 待确认

1. 第 2.3 节的针对性验收由谁负责、覆盖哪些 APP 平台？需记录最终构建下的经典 BT 启动/DUT 边界、实际提示音配置和播放切换结果，不再把已有本地重启记忆列为未知能力。
2. 录音期间 APP 是否需要预调回放音量？本文默认 SET busy；若放开，需要评估 SDK 延迟写与录音并发，并补充实机验证。
3. 目标 APP 平台是否已经实测确认既有 `rectone`/`recsave` 32 字节单次写入？若已确认，`vol` 29 字节沿用该基线；若未确认，则在首轮联调中一并抓包确认，不重复增加启动门槛。
4. 是否要求立即断电也必须记忆最后一次 SET？若要求，应另立持久化设计，不沿用本文的 `ok` 语义。
5. 客户 APP 是否消费现有 AVRCP 百分比音量上报，是否另有音量控制入口或可靠的固件能力标识？对接时必须区分旧上报和 `custom#vol`，避免单位混用、重复入口和错误兼容判断。
6. APP 是否要求并发按键操作严格逐次累加？如要求，需另议设备端相对加减及去重，而不是依赖现有绝对 SET。
