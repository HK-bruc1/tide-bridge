# RDX 框架 JL 平台复用性优化大纲

> 版本：v1.1
>
> **前提约束：**
>
> 1. 优化范围限定在 **JL 平台内** 的多芯片/多板型/多产品形态复用，不把跨 RTOS/MCU 厂商作为目标。
> 2. **`librdxApp.a` 二进制在本次优化中不修改**——把它当作不可变的 third-party core，所有优化只能调整其外围调用边界。
>    - 与静态库强相关的现有头文件视为兼容边界，阶段 1-2 不做破坏性改动。
>    - 新增 core/service 对外头文件不得继续扩散 JL 类型；如必须引用现有静态库头文件，应通过 adapter/facade 层隔离。
> 3. 优先使用《嵌入式跨平台设计模式》中的 **条件编译、Wrapper、小 vtable、轻量 OSAL、Board Config、弱符号** 等轻量模式，不引入 devicetree/Kconfig 等重型代码生成。

---

## 1. 背景与问题摘要

参考 `docs/2.RDX框架JL平台复用性评估.md` 的量化结论，当前 RDX 的核心问题不是“用了 JL SDK API”，而是 **JL 依赖、产品差异、板级差异没有集中收口**。典型症状：

- `rdx_app.c` 3403 行 / 178 函数 / 70 个条件编译分支，直接命中 JL SDK 205 次，是事实上的“产品 main controller”。
- `rdx_spi.c` 命中 JL SDK 380 次，同时承担 SPI 驱动、协议传输、WiFi 数据触发。
- 板级常量（`VDD_POWER_PORT_IO`、`LED_PT0807_DATA_PORT_IO`、`CHIP_TYPE`、`WIFI_POWER_ON/OFF`）分散在业务 `.c`、公共 `.h` 和第三方库头文件中。
- `rdx_app_config.h` 以 APP 产品块和 DEVICE 子配置组合管理客户差异，新增客户需要复制整块配置；阶段 0 需要用当前源码重新刷新 APP/DEVICE 数量口径，避免历史统计与代码漂移。
- 公共头暴露 `OS_MUTEX`、`OS_SEM`、`cbuffer_t`、`IO_PORT*`、`APP_MSG_*` 等 JL 类型。
- `librdxApp.a` 不只是协议 parse/encode：当前 archive 成员还包含 `rdx_uxfile`、`xxpUart`、`rdx_queue`、`rdx_encryption` 等对象，外部符号依赖覆盖 OS、BLE、文件、录音、APP 控制等模块。它应被视为“第三方核心包”，而不是单纯协议库。

## 2. 优化目标

### 2.1 总体目标

在不修改 `librdxApp.a` 的前提下，把 RDX 从“能复用的产品集成代码”演进为 **JL 平台内可维护、可扩展、可验证的产品框架**。

### 2.2 设计模式选型

依据 `docs/1.嵌入式跨平台设计模式.md` 的“按平台数量选”和“按代码类型选”指南：

| 位置 | 模式 | 理由 |
|---|---|---|
| 客户/能力裁剪 | ① 条件编译 | 平台数（JL 单生态）和产品数可控，零运行时开销。 |
| JL SDK API 调用 | ③ Wrapper 二次封装 | 薄封装统一命名，不改 SDK API 签名，改动最小。 |
| BLE/Storage/RTC/SPI | ④ 小 vtable 合约 | 依赖显式化，便于替换和 mock；避免单表膨胀。 |
| OS/Timer/Task/Mutex | ⑤ 轻量 OSAL | 不跨 RTOS，只隔离 JL OS 原语，便于 mock 和 SDK 升级。 |
| GPIO/电源/外设/引脚 | ⑥ Board Config（HAL 分层的子集） | 单厂商（JL）多芯片/板型场景，用 board config 而非完整跨厂商 HAL。 |
| LED/马达/DUT/调试钩子 | ② 弱符号默认实现 | 可选行为默认退化，不承载核心协议。 |
| 配置校验 | ① 条件编译的 `_Static_assert` | 编译期发现非法组合，低成本高回报。 |

### 2.3 不变约束

- **`librdxApp.a` 二进制不变**：不反编译、不重编译；现有静态库头文件作为兼容边界处理，不在阶段 1-2 做破坏性签名调整。
- **静态库 ABI 不破坏**：凡是 `librdxApp.a` 已引用的外部符号都必须保留，包括函数名、参数/返回值契约、全局变量、回调结构体字段顺序与类型、静态库会访问的结构体布局。重构时允许把旧函数实现改成 thin wrapper，但不能删除旧符号、改名、改签名，或把旧外部符号改成 `static`。
- **新增公共头去 JL 化**：新增 core/service public header 不暴露 `OS_MUTEX`、`OS_SEM`、`cbuffer_t`、`IO_PORT*` 等 JL 类型；历史兼容头通过 adapter/facade 收口。
- **协议行为不变**：优化前后，APP 与设备之间的协议字节流保持一致。
- **SDK 版本不变（阶段 1-2）**：阶段 1-2 只做代码组织重构，不升级 JL SDK；阶段 3 可按需引入新芯片 SDK。
- **Flash/RAM 预算不变**：新增抽象层必须通过 `static inline`、链接器 gc-sections 等手段控制体积增长 ≤ 2%。

## 4. 分阶段优化计划

### 阶段 0：信息补齐与风险识别（强制门禁）

**目标**：在动手改代码前，补齐对 `librdxApp.a`、构建系统、当前配置矩阵和现有产物的了解，避免阶段 1-2 中意外破坏静态库边界。

**任务**：

1. **静态库指纹与成员扫描**
   - 记录 `librdxApp.a` SHA256。
   - 使用 JL 工具链的 `llvm-ar`/`llvm-nm` 等工具列出 archive 成员、defined symbols、undefined symbols。
   - 如果符号工具不可用或输出不完整，则通过 clean build 生成的 `.map` 中 undefined/交叉引用信息反推依赖。

2. **符号依赖扫描**：列出 `librdxApp.a` 未解析的外部符号（undefined references），确认它依赖了哪些 RDX 源码中的函数/变量，并按 `os_*`、`rdx_app_*`、`rdx_ble_*`、`rdx_uxfile_*`、`rdx_record_*`、libc/third-party 等分组。

3. **回调边界梳理**：列出 `librdxApp.a` 通过哪些函数指针/全局变量回调到 RDX 源码（如 `RdxProtocolCallbacks`、`RdxProtocolIndicateOps`），明确每个回调是否允许为 NULL。

4. **头文件边界梳理**：列出现有 public header 中暴露的 JL 类型（`OS_SEM`、`OS_MUTEX`、`cbuffer_t`、`IO_PORT*`、`APP_MSG_*` 等），区分：
   - 静态库兼容头：阶段 1-2 不破坏签名，只能通过 adapter 隔离。
   - 新增 core/service 头：禁止继续扩散 JL 类型。

5. **ABI 保留清单**：基于 undefined symbol、回调结构体和 public header，列出阶段 1-3 必须保留的旧入口。后续 service 拆分时，这些旧入口只能改成 wrapper 转发到新实现，不能删除或改签名。

6. **构建系统基线**
   - 记录当前 Makefile 中 RDX 源文件列表、`librdxApp.a` 链接位置、include path、map 输出路径。
   - 执行 clean build，避免引用陈旧 `.o` 或旧 `.map` 产物。

7. **产品组合清单**：整理当前主力编译组合（APP × DEVICE × BOARD × CHIP），作为后续回归测试基线。

8. **基线 size 记录**：记录当前目标组合的 `.map` 中 RDX 相关 section 的 Flash/RAM 占用。

9. **固定冒烟测试清单**：定义所有阶段共用的端到端冒烟测试，至少覆盖设备配对/绑定、BLE 录音上传（≥ 30 秒）、WiFi 在线录音（≥ 30 秒）、软关机与恢复、恢复出厂与重新配对。

**验收标准**：

- [ ] 输出《librdxApp.a 指纹与成员表》，包含 SHA256、archive 成员、每个成员的 defined symbol 数量。
- [ ] 输出《librdxApp.a 外部符号依赖表》，覆盖全部未解析符号；若工具链限制无法完整导出，必须记录限制和 map 反推方法。
- [ ] 输出《librdxApp.a 回调接口表》，明确每个回调的调用时机、参数、是否允许为 NULL。
- [ ] 输出《RDX 头文件边界表》，标记哪些头属于静态库兼容边界，哪些头是新增 clean public API。
- [ ] 输出《静态库 ABI 保留清单》，列出不能删除、改名、改签名或改为 `static` 的函数/全局变量/结构体字段。
- [ ] 刷新当前源码指标：`rdx_app.c` 行数/函数数/条件分支、`rdx_app_config.h` APP/DEVICE 统计、JL SDK 命中次数。
- [ ] 建立最小编译矩阵：当前 T2616_CC（Zenchord CC）+ 当前主力 APP，能成功编译并生成 map。
- [ ] 建立阶段共用的冒烟测试清单，并记录阶段 0 的通过结果。
- [ ] 阶段 0 不改动任何业务代码，只产出文档和脚本。

**参考模式**：文档化、分析工具（不属于 7 种设计模式，但是重构前提）。

### 阶段 1：低风险收口（边界集中化）

**目标**：不大改行为，只把“变化点”集中。让后续阶段有清晰的修改边界。

**任务**：

1. **建立 `rdx_board_config.h/c`**
   - 迁移 `VDD_POWER_PORT_IO`、`LED_PT0807_DATA_PORT_IO`、`WIFI_POWER_PORT_IO`、SPI 引脚（cs/clk/mosi/hold/handshake）、`CHIP_TYPE` 等到 board config。
   - 提供 `const rdx_board_config_t *rdx_board_get_config(void)`。
   - 当前板型命名为 `t2616_cc`，新增板型时复制目录即可。

2. **建立 `rdx_jl_osal.h/c`**
   - 封装 `os_task_create`、`os_taskq_post_msg`、`sys_timeout_add/del`、`os_mutex_*`、`os_sem_*`。
   - 引入 `rdx_mutex_t`、`rdx_sem_t`、`rdx_timer_t` 等不透明类型，公共头不再直接暴露 `OS_MUTEX`、`OS_SEM`。
   - 优先使用 `static inline` 或宏封装，确保无运行时开销。

3. **建立 `rdx_jl_storage.h/c`**
   - 封装 `syscfg_read/write` 和关键 VM ID 访问。
   - 所有 VM ID 在此文件内集中管理，业务模块不再直接写 `syscfg_*`。

4. **参数化 `rdx_spi.c`**
   - 从 board config 读取 SPI 引脚、SPI 端口、时钟频率。
   - 移除 `.c/.h` 中写死的 `CHIP_TYPE` 和固定 IO；`CHIP_TYPE` 退化为 board config 的一个字段或编译期宏。

5. **建立最小日志入口**
   - 增加 `rdx_log.h`，先以 `RDX_LOG_INFO/WARN/ERR` 宏封装现有打印能力。
   - 阶段 1 的启动诊断全部通过 `rdx_log` 调用，避免阶段 4 再替换调用点。

6. **构建系统显式化**
   - 增加 `RDX_BOARD`、`RDX_CHIP_FAMILY` 等显式构建变量。
   - Makefile 按变量选择 `board/<name>/` 和 `port/jl/<chip_family>/` 源文件及 include path。
   - 非法或缺失配置必须在编译早期报错，禁止隐式目录扫描。

7. **增加编译期组合校验**
   - 在 `rdx_app_config.h` 或 board config 中增加 `_Static_assert`：
     - `RDX_AI_SEL_APP` 必须是已定义的 `APP_*_EN` 之一。
     - `RDX_SEL_DEVICE` 必须是已定义的 `DEVICE_*` 之一。
     - `RDX_AI_SEL_APP` 与 `RDX_SEL_DEVICE` 的兼容组合（至少覆盖当前已知合法组合）。

8. **保护 `librdxApp.a` 调用边界**
   - 不动静态库；检查所有调用静态库的入口，确保它们不直接依赖新迁移的板级宏。
   - 给 `RdxProtocolIndicateOps` 增加启动校验和安全调用封装，关键函数为 NULL 时打印诊断并返回错误，不崩溃。

**验收标准**：

- [ ] `grep -R "VDD_POWER_PORT_IO\|LED_PT0807_DATA_PORT_IO" rdx_protocol/*.c` 在业务 `.c` 中返回 0 命中（board config 和 port 层除外）。
- [ ] `grep -R "OS_MUTEX\|OS_SEM\|cbuffer_t" rdx_core/*.h rdx_service/*.h` 返回 0 命中（允许 port 层包含）。
- [ ] `rdx_spi.c` 中不再出现硬编码 `IO_PORTC_0x` 等裸 GPIO；全部来自 `rdx_board_get_config()`。
- [ ] 新增一个“模拟板型”（不接入真实硬件，仅配置不同），能通过编译，验证 board config 的隔离性。
- [ ] Makefile 支持通过 `RDX_BOARD` 和 `RDX_CHIP_FAMILY` 选择 board/port 源文件，非法组合能在编译早期失败。
- [ ] 启动日志通过 `rdx_log` 打印 product、board、chip、SDK 版本、transport、storage、RTC path 7 个字段。
- [ ] 编译期校验能拦截至少 3 种非法 APP/DEVICE 组合（测试用例需保留在 CI 或本地脚本中）。
- [ ] 阶段 1 结束后，`librdxApp.a` 的调用点数量不增加、调用签名不改变。
- [ ] Flash 增长 ≤ 2%（通过 `.map` 对比阶段 0 基线）。

**参考模式**：③ Wrapper、⑤ 轻量 OSAL、⑥ Board Config、① `_Static_assert`。

**风险与缓解**：

| 风险 | 缓解 |
|---|---|
| 旧宏被大量引用，一次性迁移容易遗漏 | 保留旧宏作为 `deprecated` 别名，编译期输出 `#warning`，阶段 2 彻底删除。 |
| OSAL 语义与 JL API 不完全对齐 | 文档明确 timeout 单位（ms）、锁递归行为；补充 host mock 单元测试。 |
| board config 引脚映射错误 | 启动时通过 `rdx_log` 打印 board config 关键字段；保留硬件冒烟测试。 |
| Makefile 源文件选择错误或引用陈旧对象 | 阶段 1 验收必须从 clean build 开始；map 中不得出现当前源码树不存在的 board/port/service 对象。 |

### 阶段 2：服务层拆分（降低中心化）

**目标**：把 `rdx_app.c` 中的产品主控逻辑拆分为独立 service，使 `rdx_app.c` 退化为“service 协调器”。

**任务**：

1. **定义 service 间通信契约**
   - 建立 `rdx_event_bus`，提供最小接口：
     - `rdx_event_subscribe(event_id, callback, user_ctx)`
     - `rdx_event_unsubscribe(event_id, callback, user_ctx)`
     - `rdx_event_publish(event_id, payload, payload_len)`
   - service 之间的横向通知统一走 event bus；禁止直接 `extern` 互调。
   - 热点同步路径可通过小 vtable/dispatch 直连，但必须在接口表中登记，不允许临时跨层调用。

2. **建立 `rdx_command_dispatch`**
   - 把 `rdx_app_protocol_handle()` 中的协议事件分发逻辑独立出来。
   - 每个命令号映射到一个 service 处理函数；dispatch 表可用静态数组 + vtable 实现。
   - dispatch 层不直接调用 JL SDK，只调用 service 接口。

3. **拆分独立 service**
   - `rdx_record_service.c`：录音状态机、在线/离线录音调度、mic gain 控制。
   - `rdx_storage_service.c`：文件同步、格式化、离线文件管理。
   - `rdx_device_service.c`：恢复出厂、解绑、TWS 删除、BLE 断开、重启/关机。
   - `rdx_wifi_service.c`：从 `rdx_app.c` 抽取 WiFi 控制逻辑，保留 `rdx_wifi_event` 事件总线。
   - `rdx_ble_service.c`：BLE 只负责连接、广播、收发；不直接清理文件同步和录音状态。

4. **拆分 `rdx_vm.c`**
   - `rdx_vm` 只做持久化读写（syscfg/VM 仓储层）。
   - 恢复出厂/解绑动作迁移到 `rdx_device_service.c`。

5. **清理反向调用**
   - `rdx_ble_server.c` 不再反向调用录音、文件同步、协议状态清理。
   - `rdx_spi.c` 不再处理协议和文件状态清理，定位为纯 transport port。

6. **弱符号化可选钩子**
   - 对 LED、马达、DUT、调试等可选行为提供 `__attribute__((weak))` 默认空实现。
   - 产品特化时只需覆盖对应函数，不需要新增 `#ifdef`。

**验收标准**：

- [ ] `rdx_app.c` 行数从 3403 降到 ≤ 2000；函数数从 178 降到 ≤ 100。
- [ ] `rdx_app.c` 中不再包含录音状态机、文件同步、恢复出厂、WiFi 控制的具体实现。
- [ ] 每个 service 有独立的 `.c/.h` 文件，且 service 之间不直接 `extern` 互调，统一通过 dispatch 或事件总线通信。
- [ ] `rdx_event_bus` API 和事件 ID 清单落地；service 间横向通知不得绕过事件总线。
- [ ] `rdx_ble_server.c` 中不再调用 `rdx_record_*` 或 `rdx_uxfile_*` 函数。
- [ ] `rdx_spi.c` 中不再调用协议/文件状态清理函数。
- [ ] 模拟新增一个客户产品配置，主要修改 `config/product/*.h`，业务 `.c` 文件零改动并通过编译。
- [ ] `librdxApp.a` 的输入接口不变：仍然通过 `RdxProtocolCallbacks` / `RdxProtocolIndicateOps` 与 RDX 源码交互。
- [ ] 编译当前主力组合，生成的 `.map` 中 RDX 代码段总大小变化 ≤ 3%。

**参考模式**：④ 小 vtable（command dispatch）、② 弱符号（可选钩子）。

**风险与缓解**：

| 风险 | 缓解 |
|---|---|
| 拆分时行为不一致 | 先提取接口保持原实现，用符号对比/反汇编确认调用关系一致后再迁移逻辑。 |
| `librdxApp.a` 内部直接调用 `rdx_app.c` 符号 | 阶段 0 的符号依赖表前置识别；阶段 2 只迁移确认无静态库依赖的函数。 |
| 消息分发增加延迟 | 热点路径保留直接函数指针 dispatch；普通事件走统一 service dispatch。 |

### 阶段 3：JL 多芯片/多板型适配

**目标**：新增 JL 芯片或板型时，core/service 层代码不改动。

**任务**：

1. **建立芯片族 port 目录**
   - `port/jl/jl7018/`：当前芯片实现。
   - `port/jl/jl70xx_next/`（占位名）：下一代芯片实现；如暂时没有真实新芯片，则用 `port/jl/jl7018_shadow/` 模拟 API 差异验证隔离效果。
   - 每个芯片族处理 SPI、RTC、低功耗、GPIO 初始化等差异。

2. **建立多板型 board 目录**
   - `board/t2616_cc/rdx_board_config.c`
   - `board/xxx_ep/rdx_board_config.c`
   - `board/xxx_cc/rdx_board_config.c`
   - Makefile 按 `RDX_BOARD` 选择 board 源文件。

3. **统一生命周期钩子**
   - 在 port 层提供 `rdx_jl_pre_sleep()`、`rdx_jl_post_wakeup()`、`rdx_jl_early_init()` 等钩子。
   - 业务代码只调用钩子，不直接调用芯片特定的低功耗 API。

4. **小 vtable 落地**
   - 完成 `rdx_ble_transport_ops_t`、`rdx_storage_ops_t`、`rdx_time_ops_t` 等结构体定义和注册。
   - 不同芯片/板型通过填充不同 vtable 实例实现差异隔离。

5. **构建矩阵扩展**
   - 最小编译矩阵：T2616_CC + 一个模拟新板型配置 + 一个模拟新芯片配置（芯片配置可不接入真实硬件，仅验证编译隔离）。
   - 若没有真实新芯片，shadow port 必须故意改动若干 SPI/RTC/GPIO 适配入口名称或参数形态，验证 service/core 不需要随之修改。

**验收标准**：

- [ ] 新增一个 board 目录后，只需在 Makefile 中切换 `RDX_BOARD` 即可编译，core/service 代码零改动。
- [ ] 新增一个 chip family 目录后，只需在 Makefile 中切换 `RDX_CHIP_FAMILY` 即可编译，service 代码零改动。
- [ ] 所有板型相关宏只出现在 `board/*` 和 `rdx_board_config.h` 中；所有芯片相关宏只出现在 `port/jl/<chip_family>/` 中。
- [ ] vtable 关键函数 NULL 检查覆盖率 100%，启动时非法 vtable 直接报错。
- [ ] 阶段 3 不修改 `librdxApp.a`；静态库的调用入口保持稳定。

**参考模式**：④ 小 vtable、⑥ Board Config/HAL 分层。

**风险与缓解**：

| 风险 | 缓解 |
|---|---|
| 新芯片 SDK API 差异超出预期 | 阶段 3 前做 API diff；有真实新芯片时以真实 SDK 验证，无真实芯片时用 shadow port 模拟 API 漂移。 |
| 不同芯片启动/低功耗行为不同 | 业务代码统一走 port 钩子；新芯片 port 负责适配。 |
| Makefile 变复杂 | 增加 `RDX_BOARD`、`RDX_CHIP_FAMILY` 等显式变量；禁止隐式目录选择。 |

### 阶段 4：迁移收口与可验证性基线

**目标**：完成阶段 3 转交的应用层迁移收口，并建立可本地执行的验证基线。阶段 4 的产出是“可验证的 checkpoint”，不强行清偿所有高风险边界债务。

**任务**：

1. **应用层迁移收口**
   - 将 `rdx_app.c` 中剩余协议 handler 迁入对应 service，`rdx_app.c` 不再注册命令。
   - 将 RTC 命令迁入 `rdx_time_service`，通过 `RDX_EVENT_TIME_SYNCED` 通知 record service 修正录音时间。
   - 将 WiFi transport 调用收口到 `rdx_wifi_transport_ops_t`。

2. **BLE connect/disconnect cutover**
   - BLE 连接/断开路径通过 event bus 通知 `rdx_record_service`。
   - 不在阶段 4 强行处理 `stop_recording()` / `cleanup_protocol_state()` 的深度解耦，转阶段 5。

3. **弱符号与启动诊断**
   - LED 场景控制通过 `rdx_hook_led_*`。
   - 启动日志打印 product、board、chip、SDK 版本、transport、storage、RTC path 7 个字段。
   - 启动时校验 lifecycle/time/wifi transport vtable，并打印成功/失败诊断。

4. **本地验证基线**
   - 落地 host mock 骨架：command dispatch、event bus、time ops、board config。
   - 落地静态边界检查脚本：`tools/check_rdx_boundaries.ps1` / `.bat`。
   - 三组合 clean build：`t2616_cc+jl7018`、`t2616_cc+jl7018_shadow`、`t2616_ep+jl7018`。

5. **剩余项归档**
   - 对 `rdx_app.c` 剩余函数做分类清单。
   - 将 BLE 深度解耦、错误码统一、host mock 扩展、目标板冒烟、`.map` 基线策略转阶段 5。

**验收标准**：

- [ ] `rdx_app.c` 中无 `rdx_cmd_register()`；27 个命令由 service 注册。
- [ ] `rdx_time_service` 存在，`RDX_EVENT_TIME_SYNCED` publish/subscribe 链路完整。
- [ ] BLE connect/disconnect 通过 event bus 执行业务逻辑；剩余 stop/cleanup 债务已记录到阶段 5。
- [ ] LED 场景控制业务调用点全部替换为 `rdx_hook_led_*`。
- [ ] WiFi transport vtable 落地，`rdx_wifi_service.c` 不直接调用 `xxp_esp32_*`。
- [ ] host mock 基线测试和静态边界检查脚本可本地运行并通过。
- [ ] 三组合 clean build 通过。
- [ ] `rdx_app.c` 未达成行数/函数数目标时，必须给出剩余函数分类和阶段 5 计划。

**参考模式**：④ vtable（mock 实现）、⑤ OSAL（mock OS 原语）、② event bus。

### 阶段 5：框架精化与边界债务清偿

**目标**：清偿阶段 4 归档时明确转交的高风险边界债务，让重构结果从“可验证 checkpoint”推进到“可长期维护的中间件边界”。

**任务**：

1. **BLE 剩余边界 cutover**
   - `rdx_ble_service_stop_recording()` 不再直接操作 `RecordStatus` 或调用 `rdx_record_process()`。
   - `rdx_ble_service_cleanup_protocol_state()` 不再直接调用 `rdx_uxfile_*`。
   - 优先使用明确 service API（如 record/storage service API），必要时再内部 event 化。

2. **`rdx_app.c` D 类候选迁移**
   - 将 clock 管理候选抽取到 `rdx_clock_service.c`。
   - 评估 `sdmmc_set_power()` 归属：storage service 或 board power helper。
   - 评估 `rdx_led_hardware_init()` 归属：board/port 初始化或保留为 product hook wrapper。
   - ABI wrapper、协调器、产品入口函数默认保留，不为行数强迁移。

3. **host mock 扩展**
   - 新增 `rdx_util` host 单元测试。
   - 至少让一个 service 在 host mock 环境跑通 init/exit。
   - 扩展 event bus async pool、unsubscribe 等边界测试。

4. **统一错误码收口**
   - 新增或改造的 storage/ble/wifi service API 返回 `rdx_err_t`。
   - 旧 ABI wrapper 保持旧返回值兼容，内部做映射。
   - 记录仍保留 `-1` 的历史接口和原因。

5. **验证闭环补齐**
   - 以阶段 4 收尾提交建立新的 `.map` 基线，后续做增量对比。
   - 执行目标板冒烟：配对/绑定、BLE 录音 30 秒、WiFi 在线录音 30 秒、BLE 强制停止、软关机恢复、恢复出厂重配对。
   - 归档三组合 clean build、host mock、静态边界检查和目标板冒烟结果。

**验收标准**：

- [ ] `rdx_ble_service.c` 不再直接操作 `RecordStatus` / `rdx_record_*` / `rdx_uxfile_*`。
- [ ] `rdx_app.c` 阶段 4 附录 C 的 D 类候选全部处理并更新清单。
- [ ] host mock 覆盖 `rdx_util` 和至少一个 service init/exit。
- [ ] storage/ble/wifi 新 service API 使用 `rdx_err_t`。
- [ ] 三组合 clean build、host mock、静态边界检查全部通过。
- [ ] 目标板端到端冒烟结果已记录。
- [ ] `librdxApp.a` 未修改。

**参考模式**：② event bus、③ board/port 分层、④ 小 vtable、⑤ OSAL、⑥ service API。

## 8. 成功标准（整体）

优化完成后的 RDX 应满足：

1. **JL API 集中化**：业务 `.c` 文件不再直接调用 `os_`、`gpio_`、`spi_`、`syscfg_` 等 JL SDK API，统一通过 `rdx_jl_*` wrapper。
2. **产品差异配置化**：新增客户产品时，主要修改 `config/product/*.h`，不需要在业务 `.c` 中增加 `#ifdef`；验收时必须模拟新增一个产品配置并通过编译。
3. **板级差异隔离化**：换板型时主要修改 `board/<name>/`，不改 service/core 代码。
4. **静态库边界稳定**：`librdxApp.a` 在整个优化过程中未被修改；其依赖的旧符号和 ABI 保持兼容，旧入口可转发到新 service，但不可删除、改名或改签名。
5. **高风险边界可控**：BLE stop/cleanup、clock、SD power、LED init 等跨层路径有明确 service/port 归属，不再依赖临时 extern 直连。
6. **可验证**：新增编译矩阵、host mock 测试、启动诊断日志、目标板冒烟记录，复用修改可追踪、可回归。

## 附录 B：设计模式使用反例

| 模式 | 错误用法 | 正确用法 |
|---|---|---|
| 条件编译 | 在业务 `.c` 中到处写 `#ifdef BOARD_XXX` | 差异集中在 board config / product config，业务层只读取配置 |
| 弱符号 | 用 weak 覆盖核心协议行为 | 只用于 LED、马达、DUT、调试钩子等可选行为 |
| Wrapper | 封装后仍把 JL 类型暴露给 service/core public header | `rdx_jl_*` 类型和 JL 类型只停留在 port 层或兼容 adapter 层 |
| vtable | 一个全局 vtable 塞入几十个函数指针 | 按领域拆成 transport/storage/time/device 等小表，并做启动校验 |
| OSAL | 试图抽象完整 RTOS 语义 | 只封装当前 RDX 需要的 task/timer/mutex/sem/queue 子集 |
| Board Config | 把运行时业务策略也塞进 board config | 只描述硬件和板级差异：GPIO、电源、外设、频率、能力开关 |
