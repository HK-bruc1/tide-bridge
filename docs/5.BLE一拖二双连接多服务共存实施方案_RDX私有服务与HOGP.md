## 1. BLE 栈与编译配置

### 1.1 正式配置

目标配置为：

```c
config_le_hci_connection_num = 2;
config_le_gatt_server_num = 1;
config_le_gatt_client_num = 0;
config_le_sm_support_enable = 1;
```

含义如下：

| 配置 | 目标值 | 含义 |
|---|---:|---|
| `config_le_hci_connection_num` | 2 | 最多两条 BLE ACL connection |
| `config_le_gatt_server_num` | 1 | 设备只承担一套 GATT Server role/Profile 定义 |
| `config_le_gatt_client_num` | 0 | 设备不作为 BLE GATT Client/Central |
| `config_le_sm_support_enable` | 1 | 支持 HOGP 配对、加密与 bonding |

两个远端设备都是 Central，但本设备仍只承担 Peripheral/GATT Server 角色；本地不需要启用 GATT Client。

### 1.2 正式产品模型

Phase 4已删除`TCFG_RDX_HOGP_DUAL_LINK_ENABLE`。`lib_btstack_config.c`在选择RDX协议时固定`config_le_hci_connection_num = 2`，RDX/HOGP源码只保留双wrapper实现，不再编译或维护单连接fallback。

后续不得重新引入隐藏开关来长期并存两套连接模型。若产品需要改变连接容量，必须作为新的架构变更重新评审连接路由、广播调度、ATT隔离和异步生命周期。

下一阶段如需复用到一拖一产品，应引入连接容量配置并继续复用当前唯一的per-link registry、owner token和定向发送架构：wrapper改为按容量管理的数组，初始化接口接收wrapper集合与实际数量，所有生命周期路径按同一数量循环。不得恢复以条件编译切换全局单连接状态与per-link双连接状态的旧实现。

### 1.3 ATT RAM 与发送缓存

`multi_protocol_main.c` 已调用：

```c
ble_op_multi_att_send_init(att_ram_buffer,
                           ATT_RAM_BUFSIZE,
                           ATT_LOCAL_PAYLOAD_SIZE);
```

说明工程已经启用 multi ATT 发送基础设施。双连接实施时必须：

- 继续保留唯一的正式 ATT RAM 初始化入口；
- 删除或禁止使用 `rdx_ble_server.c` 中未接入初始化的重复 `att_ram_buffer`；
- 评估现有 `ATT_SEND_CBUF_SIZE` 对 RDX 业务发送与 HID report 的容量；
- 通过真实 App 文件/状态发送和连续 HID 输入测量峰值，而不是盲目扩大 RAM；
- 若扩容，统一修改 `multi_protocol_main.c` 的正式共享 buffer。

## 2. 双 wrapper 设计

### 2.1 数据结构

wrapper 和 link runtime 必须收敛到唯一固定数组。`rdx_ble_session.c`（也可命名为 `rdx_ble_link_registry.c`）是该数组、capability owner index 和 slot generation 的唯一所有者；`rdx_ble_server.c` 只负责 wrapper 初始化、广播策略和 SDK callback，不得再维护第二份连接状态影子。

```c
#define RDX_BLE_LINK_MAX 2
#define RDX_BLE_LINK_INVALID_INDEX 0xff

typedef enum {
    RDX_BLE_CAPABILITY_NONE = 0,
    RDX_BLE_CAPABILITY_RDX = 1 << 0,
    RDX_BLE_CAPABILITY_HID = 1 << 1,
    RDX_BLE_CAPABILITY_RDX_HID =
        RDX_BLE_CAPABILITY_RDX | RDX_BLE_CAPABILITY_HID,
} rdx_ble_capability_t;

typedef struct {
    void *ble_hdl;
    u16 con_handle;
    u16 mtu_size;
    u32 slot_generation;

    u8 connected;
    u8 encrypted;
    u8 peer_addr_type;
    u8 peer_addr[6];
    u8 capability;

    u8 rdx_ccc_configured;
    u8 rdx_stream_tx_ready;

    u8 hid_notify_enabled;
    u8 hid_suspended;
    u8 hid_protocol_mode;

    u8 conn_param_index;
} rdx_ble_link_ctx_t;

typedef struct {
    rdx_ble_link_ctx_t links[RDX_BLE_LINK_MAX];
    u8 rdx_link_index;
    u8 hid_link_index;
    u8 advertising_link_index;
    u32 transport_epoch;
} rdx_ble_transport_t;

typedef struct {
    u8 slot_index;
    u32 slot_generation;
    u32 transport_epoch;
} rdx_ble_async_token_t;
```

`slot_generation` 在 slot 每次建立新连接或释放时推进，用于拒绝旧 timer、跨 task 消息和异步完成事件；`transport_epoch` 在 BLE transport init/deinit、poweroff 和整体重建时推进，使上一生命周期的所有异步 token 一次性失效。同步 HCI/ATT 事件仍以 `hdl + connection_handle` 校验为主，不能假设原始 SDK 事件自带 slot generation。本文的 BLE `slot_generation` 与 keymap事务自身的 generation 是两个独立概念。

`link.capability` 是 slot业务归属的唯一权威字段，不再额外维护等价的 `rdx_active` 或 `hid_attached` 布尔值。`rdx_link_index` 与 `hid_link_index` 只是 registry 内部的派生快速索引，必须在同一次 claim/release 状态转换中与 `link.capability` 一起更新，并保持以下不变量：

```text
link.connected == 0
    → link.capability == NONE

link.capability & RDX
    → rdx_link_index指向该slot

link.capability & HID
    → hid_link_index指向该slot

link.capability == RDX_HID
    → rdx_link_index与hid_link_index同时指向该slot
```

设备级名称、MAC、广播参数、发送 mutex 等全局配置可以继续保存在 server/global context；以下字段必须从全局 `rdx_ble_server_info_t` 移出：

- `ble_con_handle`；
- `ble_mtu_size`；
- `ccc_configured`；
- `stream_tx_ready`；
- 单一连接意义下的 `ble_conn`；
- 连接参数更新计数。

### 2.2 wrapper 初始化

两个 wrapper 均执行：

```c
app_ble_hdl_alloc();
app_ble_set_mac_addr(...same address...);
app_ble_profile_set(..., rdx_profile_data);
app_ble_att_read_callback_register(...);
app_ble_att_write_callback_register(...);
app_ble_att_server_packet_handler_register(...);
app_ble_hci_event_callback_register(...);
app_ble_l2cap_packet_handler_register(...);
app_ble_sm_event_callback_register(...);
```

任一分配或注册失败都必须回收已创建的 wrapper，并禁止进入半初始化运行状态。

### 2.3 wrapper 与 connection handle 映射

Connection Complete、Disconnection Complete、Encryption Change、MTU、连接参数、L2CAP 和 SM 等链路事件必须把 callback 的 `hdl` 一直传入最终处理函数，并同时校验 wrapper 与事件中的 connection handle：

```c
u16 event_handle = ...;

if (app_ble_get_hdl_con_handle(hdl) != event_handle) {
    return;
}
```

Connection与断连处理函数本身也必须保留wrapper参数，禁止在入口校验后调用一个丢失 `hdl` 的全局处理函数：

```c
static u8 rdx_ble_link_connected(void *hdl,
                                 const u8 *packet,
                                 u16 size,
                                 u8 enhanced);
static void rdx_ble_link_disconnected(void *hdl,
                                      const u8 *packet,
                                      u16 size);
```

随后通过 `hdl` 或 `event_handle` 定位唯一 link slot。不得再把每个 HCI 事件无条件写入同一个全局 session。

同步事件采用以下路由规则：

1. callback 的 `hdl` 必须属于 registry 中的一个 wrapper；
2. `app_ble_get_hdl_con_handle(hdl)` 必须与事件中的 connection handle 一致；
3. ATT read/write callback 中的 `hdl` 与 `connection_handle` 必须映射到同一 slot；
4. 同一 SDK 事件若被另一个 wrapper 的 callback 收到，必须无副作用地过滤；
5. slot 已释放或 connection handle 不匹配时，不得修改 capability、CCC、MTU、发送信号量或业务单例。

建议提供统一查询 API：

```c
rdx_ble_link_ctx_t *rdx_ble_link_find_by_hdl(void *hdl);
rdx_ble_link_ctx_t *rdx_ble_link_find_by_con_handle(u16 con_handle);
rdx_ble_link_ctx_t *rdx_ble_link_get_rdx(void);
rdx_ble_link_ctx_t *rdx_ble_link_get_hid(void);
u8 rdx_ble_link_active_count(void);
```

这些 API 读取的是同一个 registry，不允许 `rdx_ble_server_info_t`、HOGP 模块或录音模块另外缓存“最近一次 connection handle”作为路由依据。

## 3. 统一广播与连接槽管理

### 3.1 广播内容保持不变

继续使用三号方案已通过正式 App 与 Windows 实机验证的候选 C：

```text
Advertising Data:
    Flags
    Complete/Shortened Local Name

Scan Response:
    RDX Manufacturer Data（保持第一个 AD Structure）
    HID Service UUID 0x1812
```

不修改 Manufacturer Data 字节、AD Structure 顺序和 HID UUID。

### 3.2 单一活动 advertiser

虽然存在两个 wrapper，但任意时刻只启用一个空闲 wrapper 的 legacy connectable advertising：

```text
两个 wrapper 都空闲：
    选择 Link 0 广播

Link 0 已连接、Link 1 空闲：
    Link 1 广播

Link 1 已连接、Link 0 空闲：
    Link 0 广播

两个 wrapper 都已连接：
    停止广播
```

禁止两个 wrapper 使用同一设备地址同时开启重复 legacy advertising。

### 3.3 连接后的广播恢复

legacy advertising 通常在连接建立后由栈停止。Connection Complete callback 返回后，应通过短延迟 one-shot timer 在另一个空闲 wrapper 上恢复统一广播，避免与 wrapper 内部 connection handle 更新竞争。

该逻辑与三号方案“断连后延迟恢复广播”的经验一致，但触发条件改为：

```text
只要 active_link_count < RDX_BLE_LINK_MAX
且广播没有被 poweroff / DUT / Wi-Fi 等现有策略禁止
就选择一个空闲 wrapper 恢复广播
```

不再是“只有全部断开后才恢复广播”。

所有延迟广播、断连恢复和广播刷新必须复用同一个调度器，并遵守 stale-token 规则：

1. 调度前取消同类型旧 timer；
2. timer 参数携带 `slot_index + slot_generation + transport_epoch`；
3. callback 执行时重新校验 token，不相信调度时的连接计数；
4. 重新确认 `active_link_count < RDX_BLE_LINK_MAX`；
5. 重新确认目标 wrapper 仍空闲，且 `app_ble_get_hdl_con_handle(link->ble_hdl) == 0`；
6. 重新执行 poweroff、DUT、Wi-Fi 和现有广播禁止策略；
7. 任一条件不满足时直接退出，不开启广播；
8. deinit/poweroff 先取消所有广播 timer，再推进 `transport_epoch`。

示意逻辑：

```c
if (!rdx_ble_async_token_is_current(token)) {
    return;
}
if (rdx_ble_link_active_count() >= RDX_BLE_LINK_MAX) {
    return;
}
link = rdx_ble_link_get_by_index(token->slot_index);
if (!link || link->connected ||
    app_ble_get_hdl_con_handle(link->ble_hdl) != 0 ||
    !rdx_ble_adv_policy_allowed()) {
    return;
}
rdx_ble_adv_start(link);
```

### 3.4 名称或广播数据更新

名称、Manufacturer Data 等广播内容改变时：

- 更新设备级缓存；
- 若存在空闲 advertising wrapper，在该 wrapper 上安全重建；
- 已连接 wrapper 不需要为更新广播而断开；
- 两个 wrapper 下一次承担广播时必须使用相同最新内容。

## 4. Capability 激活与容量策略

### 4.1 连接建立时不分配身份

Connection Complete 只执行：

1. 找到对应 wrapper slot；
2. 推进该 slot 的 `slot_generation` 并保存 `con_handle`；
3. 初始化 link-level MTU、加密、peer 和连接参数状态；
4. 增加 active link count；
5. 停止自动关机；
6. 若仍有空闲 slot，安排另一个 wrapper 恢复广告；
7. 不激活 RDX；
8. 不激活 HOGP；
9. 不请求配对；
10. 不设置 owner。

### 4.2 HOGP capability 激活边界

以下行为可以激活 HOGP：

- 已加密链路对 `HID_INPUT_REPORT_CLIENT_CONFIGURATION_HANDLE` 写入 `0x0001`；
- 已绑定 peer 加密成功，并按该 peer identity 找到持久化 HID subscription；
- 目标 Windows 重连后，per-peer CCC 被安全恢复。

以下行为不能激活 HOGP：

- 读取 HID Service declaration；
- 读取 Report Map；
- 读取 HID Information；
- 读取 Device Information；
- 普通 GATT 全服务发现；
- 仅建立 BLE 连接。

原因是手机 App 或通用 GATT 工具可能枚举整个复合 Profile。若静态 HID read 就认领 HID slot或触发配对，会造成 App 链路误占 HOGP capability。

HOGP attach 的顺序必须固定为：

```text
按 hdl + connection_handle 定位 link
→ 校验CCC值、长度和link加密状态
→ 原子 claim HID capability
→ 将 HOGP 单例绑定到该 link 的 wrapper/handle/slot_generation
→ 更新或恢复该连接的 HID CCC
→ 满足加密、CCC 和非 suspend 条件后进入 ready
```

禁止先修改 `s_hid_notify_enabled`、peer、HOGP wrapper 或其他 HOGP 单例，再判断 claim 是否成功。

首次未加密的 HID Input CCC enable必须走独立的配对前置路径：

```text
收到CCC = 0x0001
→ link.encrypted == 0
→ 只调用sm_api_request_pairing(connection_handle)
→ 返回ATT错误INSUFFICIENT_ENCRYPTION（0x0f）
→ 不claim HID
→ 不写multi-ATT CCC
→ 不持久化subscription
→ 不绑定或修改HOGP单例
```

只有 Windows 在加密完成后重试 CCC enable，或已bonded peer加密完成并命中持久化subscription时，才允许claim HID。这样未完成配对或中途放弃的Central不会占用HID sink直到断连。Protocol Mode、Control Point和Output Report等其他HID动态写只能由现有HID owner处理，不得作为首次claim入口。

只有满足以下条件时才进入 ready：

```text
link.connected
&& link.capability == RDX_BLE_CAPABILITY_HID
&& link.hid_notify_enabled
&& link.encrypted
&& !link.hid_suspended
```

### 4.3 RDX capability 激活边界

以下行为可以激活 RDX：

- RDX notify CCC 开启；
- 收到合法 RDX value write；
- 收到合法 OTA/私有命令 characteristic write。

普通 GAP、Battery、HID 静态读取以及对 RDX value/CCC 的普通读取都不激活 RDX。只有成功校验的 RDX CCC enable 或合法私有写入才允许进入 RDX 协议库；claim 失败的输入不得继续传给 `librdxApp.a`。

RDX激活后，现有单例`librdxApp.a`、RDX发送队列、文件和录音状态绑定该link，直到该RDX link断开。断开后先关闭ATT/runtime门并进入`QUIESCING`，只有认证receive FIFO屏障到达且所有可观测worker均空闲，才经`RESETTING`回到`READY`。后续仅允许断开前记录的同一peer重绑；屏障入队或身份捕获失败才进入`FAILED`并保持到重启。`QUIESCING/RESETTING/FAILED`期间的RDX输入返回`NOT_READY`且不得进入`librdxApp.a`。

### 4.4 每条链路可组合 capability、每种 capability 最多一个 sink

MVP容量策略为：

```text
active HID link <= 1
active RDX link <= 1
physical BLE links <= 2
capability per physical link ∈ {NONE, RDX, HID, RDX_HID}
```

正式实现采用RDX/HID独立bit claim，同一物理link可以成为复合owner：

```text
link.capability == RDX_BLE_CAPABILITY_RDX
    → HID尚无owner时允许追加HID bit

link.capability == RDX_BLE_CAPABILITY_HID
    → RDX runtime READY且peer规则通过时允许追加RDX bit

link.capability == RDX_BLE_CAPABILITY_RDX_HID
    → rdx_link_index == hid_link_index == 当前slot
```

若第二条链路尝试开启已被另一条链路占用的 HID CCC：

- 拒绝新链路的 capability 激活；
- 返回明确 ATT error；
- 不清除旧 HID CCC；
- 不切换 report 发送目标；
- 不断开正在工作的 HID link。

若第二条链路尝试激活已被占用的 RDX session，同样拒绝新激活，不允许覆盖当前 RDX link。

这种策略避免第二个 PC 或第二个 App 抢占，同时不把 wrapper 序号固化为远端身份。

所有认领必须经过 registry 的唯一入口：

```c
rdx_ble_claim_result_t rdx_ble_session_claim_hid(
    rdx_ble_link_state_t *link, u32 expected_slot_generation);
rdx_ble_claim_result_t rdx_ble_session_claim_rdx(
    rdx_ble_link_state_t *link, u32 expected_slot_generation);
```

claim 必须在一次不可拆分的状态转换中完成：检查 link 仍连接、校验 slot generation、检查全局同类 owner、按位追加 capability 并更新对应 owner index，然后才允许修改 HOGP/RDX 业务单例。另一类capability已在同一link上不是冲突；两个owner index指向同一slot是合法复合状态。claim 固定在 BTStack task 串行执行；其他 task 必须投递回 BTStack task，不得直接修改 registry。若未来允许跨 task 直接 claim，则必须增加临界区或等价同步。

claim 失败不能返回成功后静默丢弃，也不能抢占、切换或断开当前 owner。registry先冻结内部结果语义，ATT层再按实机验证结果映射错误码：

```c
typedef enum {
    RDX_BLE_CLAIM_OK = 0,
    RDX_BLE_CLAIM_BUSY,
    RDX_BLE_CLAIM_CONFLICT,
    RDX_BLE_CLAIM_STALE,
    RDX_BLE_CLAIM_NOT_READY,
} rdx_ble_claim_result_t;
```

- 同一 link 重复 claim 已拥有的同类 capability：幂等成功；
- 同一 link claim 尚未拥有的另一类 capability：若该类无其他owner则成功并形成`RDX_HID`；
- capability 已被另一 link占用：内部返回 `RDX_BLE_CLAIM_BUSY`；
- RDX重绑peer与记录身份不匹配：内部返回 `RDX_BLE_CLAIM_CONFLICT`；
- link/slot generation失效：内部返回 `RDX_BLE_CLAIM_STALE`；
- RDX runtime不在`READY`或加密peer identity尚未解析：内部返回 `RDX_BLE_CLAIM_NOT_READY`；
- HID/RDX CCC写 `0`：不触发claim，即使该link不是owner也只清除该connection的对应CCC；
- bonded HID subscription恢复前先claim HID；claim失败时不得恢复CCC、不得修改HOGP单例，也不得发起配对。

ATT错误码采用分阶段策略：

1. Phase 0B拒绝路径先将 `BUSY/CONFLICT/STALE` 映射为现有标准 `UNLIKELY_ERROR (0x0e)`；
2. 实测 Windows 对 HID Input CCC失败后的重试、配对、缓存和重连行为，确认不会出现无限重试、错误配对或异常缓存；
3. 只有验证 Windows与正式App均兼容后，才允许把 `BUSY/CONFLICT` 分别映射为application error `0x80/0x81`；
4. 若自定义码没有明确产品收益或存在兼容风险，正式实现继续统一使用 `0x0e`。

因此 `0x80/0x81` 不是当前冻结的外部ABI；冻结的是“忙、同链路冲突、stale”三种内部结果及其无副作用拒绝行为。

### 4.5 Capability ownership 为粘性生命周期

capability 一旦成功 claim，就绑定到该物理链路直到该链路断开：

- HID CCC 写 `0` 只令 `hid_notify_enabled/ready` 失效，不释放 `hid_link_index`；
- RDX CCC 写 `0` 只令 `rdx_ccc_configured/stream_tx_ready` 失效，不释放 `rdx_link_index`；
- HID suspend 只影响 ready，不释放 HID ownership；
- 不通过超时、静态读取、临时发送失败或后台状态自动迁移 capability；
- 只有匹配 owner link 的 Disconnect Complete 才释放 capability index；
- 若未来增加显式 App logout capability release，必须作为新协议行为单独设计，不能隐式复用 CCC disable。

## 5. ATT、CCC 与定向发送

### 5.1 ATT callback

read/write callback 已接收：

```c
void *hdl;
hci_con_handle_t connection_handle;
uint16_t att_handle;
```

所有动态处理都必须首先验证 `hdl` 与 `connection_handle` 映射到同一个 link context，并拒绝未知、已断开或映射不一致的 stale handle。禁止继续使用全局 `rdx_ble_session_is_current()` 的单链接语义。

静态读取与 capability 激活必须解耦：完整服务发现、Report Map/HID Information 读取、RDX value读取和 CCC读取均不得产生 claim、配对、业务连接回调或发送状态变化。

### 5.2 CCC 必须 per connection

所有 RDX/HID CCC 都使用：

```c
multi_att_set_ccc_config(connection_handle, att_handle, cfg);
multi_att_get_ccc_config(connection_handle, att_handle);
multi_att_clear_ccc_config(connection_handle);
```

当前 RDX callback 中的：

```c
att_set_ccc_config(handle, value);
```

必须删除或替换，否则两个连接会共享、覆盖或错误读取 CCC。

### 5.3 HID report 定向发送

HID 发送只使用当前 HID link 对应 wrapper：

```c
app_ble_att_send_data(hid_link->ble_hdl,
                      HID_INPUT_REPORT_VALUE_HANDLE,
                      payload,
                      sizeof(payload),
                      ATT_OP_NOTIFY);
```

不得无连接目标地广播给两个 wrapper，也不得根据最近一次连接选择目标。

### 5.4 RDX 数据定向发送

RDX response、notify、OTA 与 bulk data 只使用当前 RDX link：

```c
app_ble_att_send_data(rdx_link->ble_hdl,
                      rdx_att_handle,
                      data,
                      len,
                      op_type);
```

`app_ble_att_vaild_len_get()`、disconnect、remote MAC 查询和 send fail 统计也必须传入 RDX link wrapper。

### 5.5 ATT_EVENT_CAN_SEND_NOW

两个 wrapper 都可能收到发送事件。callback 必须：

- 先确认事件属于哪个 wrapper/connection；
- 只有 RDX link 的事件才能唤醒 RDX bulk-send semaphore；
- HID link 的 CAN_SEND_NOW 不得误清 RDX bulk flag；
- 断开后的迟到事件不得操作已复用 slot。

处理顺序必须至少满足：

```c
link = rdx_ble_link_find_by_hdl(hdl);
if (!link || !link->connected ||
    app_ble_get_hdl_con_handle(hdl) != link->con_handle ||
    link != rdx_ble_link_get_rdx()) {
    break;
}

/* 只有此后才能清 bulk/send-confirm 并 post RDX send semaphore。 */
```

若 CAN_SEND_NOW 事件格式中包含 connection handle，还必须同时比较事件 handle；若该 SDK 事件不携带 handle，则 RDX发送路径在请求/等待 CAN_SEND_NOW 时必须保存 `slot_index + slot_generation + transport_epoch` pending token，callback同时校验 `hdl` 当前映射和 pending token，且只能清除匹配 token。没有有效 RDX pending token 的事件不得唤醒发送信号量。

### 5.6 MTU 与连接参数

MTU、connection update index、interval 和 timeout 均改为 per-link。

MTU发送上限使用：

```c
ble_op_multi_att_set_send_mtu(connection_handle, mtu);
```

不得继续使用无 connection handle 的 `ble_op_att_set_send_mtu(mtu)`。

建议策略：

- HID link 以低延迟和稳定按键为优先；
- RDX link 以配置可靠性和合理吞吐为优先；
- 不使用一个全局 `connection_update_cnt` 同时驱动两条链路；
- 一条链路拒绝参数更新不影响另一条链路的更新状态。

### 5.7 业务模块只使用窄接口

`rdx_ble_server_info_t` 只保留名称、MAC、广播缓存、设备级 timer/mutex 和 wrapper资源，不再向录音、文件或 LED 模块暴露 per-link 字段。业务模块统一使用：

```c
u8  rdx_ble_rdx_is_connected(void);
u8  rdx_ble_rdx_stream_tx_ready(void);
u16 rdx_ble_rdx_mtu_get(void);
int rdx_ble_rdx_send(u16 att_handle,
                     const u8 *data,
                     u16 len,
                     u8 op_type);
```

必须清理 `rdx_ble_server_get_info()` 调用方对 `ble_con_handle`、`ble_mtu_size`、`ccc_configured`、`stream_tx_ready` 和单 wrapper 的直接访问，避免 registry 与公开结构形成两个真相来源。

### 5.8 携带 link 语义的异步操作必须使用 token

async token只约束会跨越当前调用栈并在未来再次访问BLE link语义的工作，不要求所有纯本地timer机械携带token。

凡异步回调、app_core消息、task queue、timer或完成通知会执行以下任一行为，投递时都必须复制 `slot_index + slot_generation + transport_epoch`，执行时重新解析并验证当前RDX/HID owner：

- 读取或修改RDX/HID owner；
- 读取connection handle、MTU、CCC、加密或peer状态；
- 调用BLE notify/indicate、查询发送长度或等待CAN_SEND_NOW；
- 操作与当前RDX link绑定的录音上传、OTA、文件同步、bulk buffer或keymap响应；
- 在断连后可能把旧业务结果发送给新owner或已复用slot。

```c
rdx_ble_async_token_t token = rdx_ble_link_token_capture(rdx_link);
post_to_app_core(..., token);

/* app_core/timer callback */
rdx_ble_link_ctx_t *link = rdx_ble_link_token_resolve_rdx(&token);
if (!link) {
    return;
}
/* 只有此后才能读取link状态或尝试BLE发送。 */
```

取消timer、清空队列或设置业务stop flag只能作为源码可控异步路径的辅助收敛，不能替代callback入口的token校验。RDX owner断开、slot复用或transport deinit后，旧token必须失效；新的RDX owner不得继承旧录音、OTA、文件或发送任务。

不可修改的`librdxApp.a`内部异步工作是唯一例外：其队列节点无法补充token，因此不能用“执行时读取当前owner”代替归属校验。第6.5节使用接收FIFO nonce屏障、屏障后的二次取消、发送worker主动唤醒和可观测idle条件证明旧工作已经收敛，再把同一单例runtime重绑给原peer；源码token与legacy runtime屏障是叠加关系，不互相替代。

纯本地且与BLE link无关的timer不适用，例如只更新本地LED动画、文件系统维护或不读取/发送任何连接状态的离线任务。是否需要token以callback实际访问的数据和副作用为准，而不是以源文件位于 `rdx_record.c`、`rdx_ota.c` 或 `rdx_app.c` 为准。

## 6. 连接生命周期与清理边界

### 6.1 RDX link 断开

仅当断开链路实际激活了RDX时执行。第一步必须把RDX runtime从`ACTIVE`原子切换到`QUIESCING`并关闭ATT输入门，同时推进runtime epoch使旧owner token立即失效，随后才允许执行其他清理：

- 停止 RDX force-disconnect timer；
- 停止同步与文件 busy timer；
- 清理 RDX发送状态和 bulk buffer；
- 中断或收敛与 App 连接相关的在线录音/传输；
- 清理 OTA 会话；
- 调用 `rdx_hogp_keymap_config_on_disconnect()` 取消尚未完成的 App keymap事务；
- 清除该 link 的 RDX CCC 和 tx-ready；
- 释放 `rdx_link_index`；
- 清除legacy连接handle后主动唤醒发送worker，使其排空旧队列而不是等待已经失效的`CAN_SEND_NOW`；
- 向legacy receive FIFO追加仅本地已知的随机nonce屏障包；屏障到达前保持`QUIESCING`，到达后进入`RESETTING`并重复取消可能由旧接收包启动的业务；
- 只有receive、录音、文件、OTA、send与bulk可观测状态全部空闲，才执行最终buffer清理并进入`READY`；屏障入队或peer身份捕获失败则进入`FAILED`。

不得执行：

- 清除另一个 HID link 的 CCC；
- 清除 HID peer identity；
- 把按键路径切回离线；
- 主动断开 PC；
- 重置整个 BLE transport。

`HCI_EVENT_DISCONNECTION_COMPLETE`所在BTStack callback负责关闭输入、失效owner/token、发起local-only清理并排入FIFO屏障。不得在callback内同步删除/重建静态库协议任务，也不得用固定延时重新开放RDX。若屏障已到达但worker仍busy，保持`RESETTING`；后续合法ATT访问可以再次检查可观测idle状态，但经过多少时间本身永远不构成屏障。

### 6.2 HID link 断开

仅当断开链路实际激活了 HOGP 时执行：

- 清理 HID report runtime；
- 清理该 link 的 CCC、加密、suspend和peer缓存；
- 释放 `hid_link_index`；
- 使 `rdx_hogp_keyboard_is_ready()` 收敛为 0；
- 后续物理按键恢复离线产品功能。

不得执行：

- 取消 App keymap事务；
- 停止 RDX notify；
- 清理 RDX文件/OTA状态；
- 把 App连接标记为断开。

release report 的发送边界必须与 Disconnect Complete 分开：

- 本地主动断连前、keymap apply/切换前、HID suspend前和 CCC disable前：链路仍 ready 时可以尽力发送 release；
- 远端主动断开、supervision timeout 或异常掉线：不能保证发送，只清理本地 pressed/report state；
- 收到 `HCI_EVENT_DISCONNECTION_COMPLETE` 后：ACL 已不存在，禁止再调用任何 ATT send API；
- `rdx_hogp_on_disconnected()` 必须提供 local-only cleanup 路径，不能间接调用 `rdx_hogp_keyboard_release_all()`。

### 6.3 公共链路清理

任一连接断开都执行：

- 按 callback `hdl + disconnected_handle` 定位且只接纳对应 slot 一次；
- 在 slot 清零前记录其 capability 与 slot generation，并执行对应 local-only cleanup；
- 清理该 connection handle 的 runtime CCC；
- 仅当该 slot 是 capability owner 时释放对应 owner index；
- 清空连接态并推进 slot generation，使旧异步 token失效；后续SM/MTU/Encryption事件由 `hdl + connection_handle` 映射拒绝，CAN_SEND_NOW还必须校验RDX pending token；
- 减少 active link count；
- 若存在空闲 wrapper，延迟恢复统一广播；
- 只有 active link count 变为 `0` 才恢复自动关机策略；
- deinit/poweroff 时显式断开两个 wrapper 并逐个释放。

### 6.4 `ble_conn` 语义拆分

当前代码中的 `g_rdx_ble_server_info.ble_conn` 同时被用于：

- 任意 BLE 是否连接；
- RDX App 是否连接；
- LED 显示；
- 录音在线模式；
- 广告禁止；
- 自动关机。

双连接后必须拆成明确接口：

```c
u8 rdx_ble_link_active_count(void);
u8 rdx_ble_any_link_connected(void);
u8 rdx_ble_rdx_is_connected(void);
u8 rdx_hogp_keyboard_is_connected(void);
u8 rdx_hogp_keyboard_is_ready(void);
```

调用方必须按业务含义选择接口，禁止继续使用一个模糊布尔值。

### 6.5 不可修改静态库的RDX保活重绑屏障

`librdxApp.a`是不可修改、不可重入的单例legacy runtime。LLVM IR审计确认，现有free/create接口不足以形成可证明的运行时重建屏障：`rdx_protocol_task_free()`先删除queue/semaphore/mutex再删除task且忽略返回值，`rdx_uxfile_task_free()`只删除task，UXFILE timer、mutex和buffer没有完整清理，create/init路径也没有完整失败回滚。因此Phase 3不销毁或重建task、queue、timer、mutex和runtime，而是让原runtime保活，在证明旧工作收敛后仅重绑transport。

现行状态转换如下：

```text
boot/init: OFF -> STARTING -> READY
valid RDX access: READY -> ACTIVE
RDX disconnect: ACTIVE -> QUIESCING
authenticated FIFO barrier: QUIESCING -> RESETTING
all observable workers idle: RESETTING -> READY
same-peer valid RDX access: READY -> ACTIVE
enqueue/identity failure: QUIESCING/RESETTING -> FAILED
reboot: FAILED -> OFF -> STARTING -> READY
```

- `OFF`：BLE transport未初始化；
- `STARTING`：初次启动RDX runtime；
- `READY`：runtime可以接受RDX claim；首次连接允许任意合法peer，重连只允许已记录的原peer；
- `ACTIVE`：唯一RDX owner已绑定runtime epoch，合法命令和OTA输入可以进入静态库；
- `QUIESCING`：输入已关闭且旧token已失效，等待带随机nonce的receive FIFO屏障回调；屏障没有到达时不得因超时进入`READY`；
- `RESETTING`：FIFO屏障已经证明更早的receive节点均已执行或丢弃，正在等待录音、文件、OTA、send和bulk worker的可观测idle条件；
- `FAILED`：屏障无法入队或缺少可信原peer身份，后续RDX claim、CCC enable和private value write保持拒绝，直到整机重启。

`s_rdx_runtime_consumed_this_boot`仍是只增不减的boot-lifetime标志，但它的Phase 3语义改为“后续claim必须匹配首次会话peer”，不再表示“本次上电永久禁止第二次会话”。BLE server或transport局部reinit不得清除此标志；局部reinit也不会伪造一次完整的FIFO/worker收敛证明。首次合法RDX CCC enable、普通命令或OTA写入必须先从`READY`成功claim并进入`ACTIVE`，然后才调用静态库入口；普通服务发现和静态读取不会消费runtime。

RDX owner断开时必须按以下顺序执行：

1. `ACTIVE -> QUIESCING`，立即关闭RDX输入门；
2. 推进runtime epoch并失效owner token、pending send、CAN_SEND_NOW及sync-data/stream-ready timer token；
3. 记录断开peer。加密链路使用SM解析后的identity；identity尚不可用时只允许raw address type和address完全相等；
4. 执行现有RDX业务取消，清除legacy连接handle并主动post发送semaphore，让发送worker看到无连接状态后排空；
5. 通过`rdx_protocol_packet_recv()`在旧receive FIFO尾部追加由两次`rand32()`组成的64-bit nonce私有包；入队长度不完整立即进入`FAILED`；
6. nonce武装且runtime仍为`QUIESCING`时，legacy兼容视图只向预编译receive parser临时暴露`ble_conn = TRUE`，但`ble_con_handle`保持`0`，因此接收队列可以排到屏障而所有发送路径仍关闭；
7. nonce必须在源码custom入口、普通`ACTIVE` callback门之前精确匹配。只有该本地认证屏障可以在`QUIESCING`时继续执行；其他旧custom callback和`RdxProtocolCallbacks`事件全部丢弃；
8. 屏障回调执行`QUIESCING -> RESETTING`，关闭上述parser临时准入并再次取消file/bulk/record/OTA等业务，覆盖屏障之前旧命令可能新启动的工作；
9. 检查storage/file/record/OTA以及`BLE_SendData.send_pending`、`BLE_SendData.bulk_sending`、`BleBulkSendData.busy`、`BleBulkSendData.bulk_flag`。任一busy则保持`RESETTING`；
10. 全部idle后才执行prepared/upload/record/dat/send buffer最终清理并进入`READY`；后续ATT访问也可以重试本步骤，但不得把延时当成idle证明；
11. 新claim只接受第3步记录的同一peer，再次推进runtime epoch并进入`ACTIVE`。不同peer返回`CONFLICT`，identity尚未解析完成返回`NOT_READY`；
12. 全程不调用`rdx_protocol_task_free/create()`、`rdx_uxfile_task_free/init()`，不改变`librdxApp.a`、`RdxProtocolCallbacks`、custom callback或`rdx_ble_server_info_t` ABI；
13. 保持另一条HID链路、加密状态、CCC和report发送独立可用。

该方案支持同一开机周期内原peer多次物理断开和重连，不支持把单例runtime改绑给不同peer。重连没有“等待固定毫秒数后自动放行”的时间窗口：只有屏障与idle事实成立才进入`READY`；条件未成立时继续拒绝RDX输入，失败条件进入`FAILED`。若未来要求不同peer接管或真正重建runtime，仍必须取得新的、可审计的静态库生命周期契约。

## 7. HID 在线热修改 Keymap

### 7.1 现有能力可直接复用

当前 `rdx_hogp_keymap_config.c` 已实现：

- request decode和参数校验；
- request id冲突处理；
- revision并发控制；
- 幂等重试；
- keymap CRC；
- 双 VM slot；
- prepare/apply/commit；
- VM失败回滚；
- executor publish；
- App断开时的 generation失效。

四号方案不修改该协议与持久化 ABI，只修正它所依赖的 BLE发送目标和断连边界。

### 7.2 热更新流程

```text
PC HOGP link 已 ready
        │
手机 App 通过 RDX link 发送 SET_KEYMAP
        │
RDX link 完成协议、revision、CRC和busy校验
        │
准备 inactive VM slot
        │
通过 HID link 发送/收敛旧 report release
        │
更新 RAM active keymap
        │
提交并校验 VM slot
        │
失败则恢复旧 keymap
        │
通过 RDX link 返回成功/失败响应
        │
下一次物理按键使用最新 committed keymap
```

整个过程中：

- PC HID connection handle 不改变；
- HID CCC 不关闭；
- Windows 不需要重新枚举设备；
- App 不需要主动断开；
- 不切换广播模式；
- 不触发 PC自动回连。

### 7.3 并发边界

keymap commit 在 `app_core` 串行执行，继续保留单 pending request。提交期间若物理按键事件可能并发进入 executor，应保证：

- 先取消旧 release timer；
- 先释放当前按键状态；
- 完整复制 keymap后再发布 active generation；
- 回滚时同样先 release再恢复旧 map；
- 任何错误都不能让半份 keymap 可见。

## 8. 安全、配对与 Peer 状态

### 8.1 HOGP安全策略

继续使用三号方案已经验证的：

```text
IO_CAPABILITY_NO_INPUT_NO_OUTPUT
+ Just Works
+ Bonding
+ Secure Connections
```

HID动态写继续要求加密。只有 Input CCC 写入或 bonded subscription恢复才触发 HOGP attach，不恢复“连接即配对”。

### 8.2 Peer identity 必须 per link

当前 `rdx_hogp_keyboard.c` 只缓存一个 `s_peer_identity_con_handle`。双连接后必须把 peer address/type 保存到对应 link slot，禁止通过全局“最近 peer”推断。

bonded HID subscription store 已支持多个 peer entry，可以继续复用；查询和更新必须传入当前 HID link 对应 peer identity。

以下情况必须拒绝：

- 全零 peer；
- 全 `0xFF` peer；
- stale connection handle；
- RDX手机 peer 继承 Windows的 HID CCC；
- 第二条链路覆盖第一条链路尚未完成的 subscription更新。

### 8.3 RDX访问策略

四号方案不把 wrapper、slot、HID bond或加密状态当作 RDX远端身份认证。沿用当前产品已批准的“连接并按协议访问即有权调用 RDX”语义。

若未来需要真正的 App身份认证，应增加独立挑战/响应或密钥协议；不得重新引入伪 owner作为替代。

## 10. 分阶段实施方案

### Phase 0A-T：纯 wrapper transport POC（已通过）

目标：只验证当前芯片、SDK二进制版本和 `config_le_gatt_server_num = 1` 下的双 Peripheral wrapper transport，不接入 RDX命令、capability ownership、HID report发送、订阅持久化或完整业务。此阶段验证的不是两个 wrapper 同时广播，而是任意时刻仅由一个空闲 wrapper广播，并依次建立两条同时存在的 Peripheral ACL。由于生产复合 Profile始终公开HOGP，Windows枚举必须使用最小HOGP控制面兼容层，不能再把所有动态写统一拒绝。

实施内容：

1. 设置 `config_le_hci_connection_num = 2`；
2. 分配两个 RDX wrapper；
3. 两者注册同一 Profile与callbacks；
4. 上电由第一个 wrapper广播；
5. 第一条连接的完整callback fan-out返回后，使用短延迟one-shot timer由第二个wrapper恢复相同广播；严禁在Connection Complete callback内同步开启第二wrapper广播；
6. callback日志记录 `hdl`、wrapper index、事件 connection handle和`app_ble_get_hdl_con_handle(hdl)`；
7. Connection Complete只允许事件发生时的active advertising wrapper接纳；其他wrapper即使暂时读到同一connection handle也必须拒绝并清理stale绑定；
8. 两个Central只做服务发现、静态读取以及Windows完成驱动枚举所需的HOGP控制面写入；
9. HOGP最小控制面只处理per-connection Input CCC、Protocol Mode、Control Point和Output Report的合法性与加密门控，不claim、不持久化、不进入HOGP单例、不发送report；
10. RDX和其他动态写继续返回标准 `0x0e`；
11. 任意一条断开后，另一条保持连接。

Go条件（transport范围）：

- 两个 Central 可以先后成功建立 ACL，并至少在日志观测窗口内同时保持连接；正式 App 因 Phase 0A-T 主动拒绝 RDX 业务写而主动断开，不计为 transport失败；
- 两个 wrapper映射正确；
- 无第二连接覆盖第一 wrapper handle；
- 同一次Connection Complete只有active advertising wrapper接纳一次；
- Windows HID Input CCC写成功且不会出现驱动错误；
- 无 ATT数据库异常或服务缺失；
- 单边断开不导致另一边HCI断开。

2026-07-22 实机验收证据：

```text
PC      → wrapper 0 / connection handle 0x0050
空闲槽  → wrapper 1延迟恢复统一广播
App     → wrapper 1 / connection handle 0x0051
双连接  → active count = 2，停止广播
App写入 → RDX 0x0009被POC返回0x0e
App断开 → reason 0x13（Remote User Terminated Connection）
PC链路  → 未被连带断开
```

该时序证明双wrapper能够依次承担单一活动广播并同时承载两条Peripheral ACL，wrapper/connection handle映射正确，Phase 0A-T判定为Go。它不证明HID report或RDX业务可用：PC链路仅完成HOGP枚举控制面，未claim HID、未进入ready；App链路的RDX runtime被主动隔离。

Phase 0A-T期间不得为了快速演示而把完整 RDX/HOGP 单例直接接入两个 wrapper。最小HOGP控制面只是公开复合Profile面向Windows时的枚举契约，不代表HID capability已经接入；本阶段只回答“双wrapper能否同时承载两条Peripheral connection”这一不可由预编译库静态证明的问题。

### Phase 0B：双连接 ATT 隔离 POC（已通过）

在 Phase 0A通过后验证：

- 两条连接分别读取同一份 Profile中的相同 handle；
- 两条连接的 MTU、CCC 和 notify目标相互独立；
- wrapper/connection映射在两条连接同时存在时保持稳定；
- 一个 wrapper 的 Disconnect Complete不会被另一个 wrapper重复处理；
- HID wrapper的CAN_SEND_NOW不会唤醒RDX发送信号量；
- 第二slot连接完成、slot快速复用或deinit后，旧ADV timer不会重新开启广播。

使用不接入HOGP业务单例的最小CCC test harness补充验证：

- 未加密 HID Input CCC enable只触发pairing request并返回 `0x0f`，不claim、不写CCC、不持久化；
- capability拒绝路径先返回标准 `0x0e`，观察Windows是否出现异常重试、错误配对、缓存污染或重连循环；
- 自定义 `0x80/0x81` 仅作为对照实验，不在Phase 0B前冻结为外部ABI。

实机验收证据：

```text
Link 0  → wrapper 0 / connection handle 0x0050 / MTU payload 514
Link 1  → wrapper 1 / connection handle 0x0051 / MTU payload 514
共享读取 → 两条link均可读取0x0003与0x000e
CCC隔离 → 0x0050与0x0051分别配置Battery CCC
定向发送 → Battery notify分别以0x0050、0x0051调用multi ATT发送
CCC关闭 → 0x0051写0只清除自身Battery CCC
事件隔离 → 两个wrapper的CAN_SEND_NOW均被观测并丢弃
```

#### Phase 3解决方案：same-link RDX + HID复合owner

修正限于当前工程源码，不修改`librdxApp.a`、导出函数签名、`RdxProtocolCallbacks`布局、`rdx_ble_server_info_t`布局或任何静态库ABI。目标owner模型从单值互斥改为独立capability/位集：

```text
NONE -> RDX
NONE -> HID
RDX  -> RDX + HID
HID  -> HID + RDX
```

实施要求：

- 仍然只允许一个RDX owner和一个HID owner，但`rdx_owner_index == hid_owner_index`必须成为合法状态；
- claim顺序无关：RDX先claim后可以在同link attach HID，HID先claim后也可以在同link activate RDX；

日志确认Windows/HID先连接后进入`ready=1`，第二条App链路使`connected_count=2`，随后RDX runtime进入`ACTIVE`。双连接在线期间HID press/release和RDX录音启停、响应及文件保存同时成功。RDX owner以`reason=0x13`断开后runtime按设计进入`FAILED`并恢复空闲wrapper广播；App可重新建立ACL，但RDX claim以`RDX_BLE_CLAIM_NOT_READY`稳定拒绝。补充实测确认此时HID继续上报，整机重启后RDX重新进入`READY -> ACTIVE`并恢复录音业务。

通过1至11可以判定“静态库不修改条件下，一个RDX owner与一个HID owner双连接共存”的Phase 2B-4安全降级方案可行；第12项关闭已有的反向连接顺序追溯项。此前把“App断开后同一开机周期无法再次使用RDX”作为已接受限制，仅适用于Phase 2B-4阶段验收。产品现已要求正常断开重连，因此该限制从Phase 3起重新定义为必须收敛的问题，不能继续作为最终方案的通过条件。

同一开机周期RDX恢复业务现在是Phase 3要求，但这不等于批准直接销毁并重建静态库。Phase 3已经采用第6.5节不重建runtime的安全transport重绑方案替换本节历史行为；第7、9项“断开后进入FAILED并拒绝重连”只用于说明Phase 2B-4旧镜像，不是现行固件预期。

### 11.8 Phase 3 RDX重连生命周期真机验收

本节是Phase 3剩余的On-device Reconnect Gate。连续性验证以separate-link拓扑为主：Windows/PC独占HID ACL，手机或正式App独占RDX ACL，因此RDX物理断开期间HID必须保持连接、`ready=1`并可持续发送report。Same-link拓扑的物理ACL断开按设计同时释放RDX与HID capability，不应误判为HID隔离失败。

正常断连日志应依次观察到：

```text
[RDX_BLE_SESSION] runtime QUIESCING ... drain barrier queued
[RDX_BLE_SESSION] receive FIFO drain barrier reached
[RDX_BLE_SESSION] runtime RESETTING: old workers still busy   （仅存在未收敛worker时）
[RDX_BLE_SESSION] runtime READY: FIFO drained and workers idle
[RDX_BLE_SESSION] runtime ACTIVE ...                          （同peer重连并重新claim后）
```

2026-07-24首次真机日志`COM3_2026-07-24_10-25-33.log`没有通过本节：日志在`drain barrier queued`后立即出现`rdx_protocol_recieve_data_handle --> BLE not connected, ignore request`，没有出现`RDX receive FIFO drain barrier reached`或`RDX runtime READY`；约5.4秒后的新ACL写入以`RDX claim rejected result=4`（`NOT_READY`）被拒绝。根因是预编译receive parser在解析nonce前先读取legacy `ble_conn`，而旧实现已将其清零。现行修复仅在nonce武装且`QUIESCING`时向receive parser开放该位，并保持handle为`0`；该日志属于失败与根因证据，不能勾选下列任何验收项。

修复版真机日志`COM3_2026-07-24_10-44-43.log`已完成基础同peer重连复验：首次连接在`ACTIVE`状态下完成真实RDX命令和发送；两次物理断开均依次出现`QUIESCING`、`RDX receive FIFO drain barrier reached`和`READY`，没有出现`FAILED`、claim reject、assert、watchdog或异常复位；首轮`READY`后重新执行ATT写入和RDX发送成功，第二轮也再次完成屏障收敛。该日志证明receive屏障准入修复和空闲态同peer保活重绑可工作，但只覆盖两轮单RDX链路，未覆盖separate-link下HID连续性、活动中的文件/bulk/OTA隔离、不同peer冲突、SM identity/RPA及至少十轮压力矩阵；因此不能据此关闭下列完整验收清单。日志中的`add_sys_timer_in_irq`重复告警保留为后续专项追踪项，不作为本次生命周期屏障失败判据。

不得仅按日志状态判定成功。每轮必须由正式App发送带可区分request id或业务内容的真实命令，并确认响应属于当前轮；旧轮响应、旧录音完成、旧文件/bulk数据或旧timer输出均不得到达新连接。

```text
[ ] 1. separate-link下建立PC/HID ready与App/RDX ACTIVE，验证真实RDX命令/响应和HID press/release均正常
[ ] 2. 物理断开RDX ACL，确认按QUIESCING -> RESETTING -> READY收敛，不出现assert、watchdog或异常复位
[ ] 3. 同一App peer在同一开机周期重连，重新开启CCC并执行真实RDX命令/响应，无需整机重启
[ ] 4. 从RDX断开到重新ACTIVE的全过程，PC/HID保持连接、ready且持续发送report
[ ] 5. 录音活动中断开并重连：旧录音/完成事件不进入新session，新session可重新启停录音
[ ] 6. 文件传输或文件同步活动中断开并重连：旧文件状态/数据不进入新session，新传输可重新开始
[ ] 7. bulk/send pending活动中断开并重连：发送worker完成排空，不依赖旧CAN_SEND_NOW，旧payload不进入新session
[ ] 8. OTA会话中断开并重连：旧OTA状态不污染新session；是否允许重新开始OTA按产品协议验证
[ ] 9. 在一次上电内连续执行至少10轮“ACTIVE -> 断开 -> READY -> 同peer ACTIVE”，每轮真实命令与HID报告均成功
[ ] 10. 原peer断开且runtime READY后，改用不同RDX peer尝试claim，必须返回CONFLICT且不占owner；原peer随后仍可重连
[ ] 11. 加密peer使用SM identity跨RPA重连成功；无法取得identity的测试链路仅在raw address type/address完全相同时成功
[ ] 12. 在可控故障注入条件下验证屏障入队/peer identity失败保持fail closed；若量产环境无法安全注入，保留自动化contract证据并记录未执行原因
[ ] 13. 屏障到达但worker仍busy时，ATT访问只能触发idle复查，不能因等待固定时长直接进入READY
[ ] 14. 全程无stale custom callback、RdxProtocolCallbacks事件、pending response、cross-send或different-peer claim被接受
```

第1至11、13和14项全部通过后，才能关闭Phase 3 On-device Reconnect Gate；第12项允许以已通过的fail-closed自动化合同加明确的真机不可注入说明替代。一次普通空闲重连成功不足以证明生命周期关闭。

## 12. 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 只改连接数、不改单例状态 | 第二连接覆盖第一连接，任意断开导致全局清理 | 双 wrapper + per-link session必须原子实施 |
| server/session各维护一份links | 两个状态中心不一致，释放与发送目标漂移 | link registry唯一拥有links、owner和slot generation |
| 一个 wrapper承载两个handle | `app_ble_get_hdl_con_handle()`、发送、广告和断连语义不匹配 | 遵循Find My/RCSP双wrapper实践 |
| App枚举HID触发attach | 手机误占HID、弹配对提示 | HID只在Input CCC或bonded恢复时attach |
| 未加密CCC写失败前已claim HID | 放弃配对的Central占住HID sink直到断连 | 未加密路径只请求配对并返回0x0f，加密重试后才claim |
| 静态RDX read触发attach | 通用枚举误占RDX session或唤醒预编译库 | RDX只在CCC enable或合法私有write时claim |
| 同一PC的RDX/HOGP复用一条ACL，但同link capability互斥 | RDX先claim时HID失效，HID先claim时PC专属应用无法使用 | Phase 3改为RDX + HID复合owner，仅限同一link共享，仍保持每类owner全局唯一 |
| RDX CCC仍为全局 | 两条链路相互覆盖订阅 | 全面迁移到`multi_att_*ccc_config` |
| RDX响应发错Central | PC收到私有notify或App收不到响应 | 发送始终选择`rdx_link->ble_hdl` |
| HID report发错Central | App收到键盘report、PC无输入 | 发送始终选择`hid_link->ble_hdl` |
| 一条断开清理另一条 | HID/App相互掉功能 | link cleanup、RDX cleanup、HID cleanup三层拆分 |
| ATT buffer不足 | RDX吞吐下降、HID send busy | 测量峰值后统一调整multi ATT buffer |
| 两条链路连接参数互相污染 | HID延迟或App不稳定 | 参数索引、MTU和更新状态per-link |
| 双连接同时回连竞态 | wrapper映射错误、stale event误清理 | hdl + con_handle双重校验和slot generation |
| Connection Complete回调内同步开启空闲wrapper广播 | 同一HCI事件继续fan-out时第二wrapper绑定第一条connection handle | 仅active advertiser接纳连接，callback返回后再延迟恢复广播 |
| 复合Profile公开HOGP但POC拒绝全部动态写 | Windows Input CCC写失败、HID驱动错误并主动断开 | Phase 0A保留无claim、无持久化、无report发送的最小HOGP控制面 |
| 旧ADV timer跨slot复用或poweroff执行 | 满连接后错误广播或deinit后访问wrapper | slot generation + transport epoch + callback重检策略 |
| HID CAN_SEND_NOW唤醒RDX | bulk/send-confirm状态错乱 | 只有当前RDX wrapper事件可操作RDX信号量 |
| 旧app_core/录音/OTA/文件任务访问新owner | 旧业务结果跨会话发送或污染新RDX session | 所有携带link语义的异步工作捕获并校验async token |
| 用固定延时冒充静态库quiescence | 延时到期后旧task仍可能处理新owner状态 | 使用nonce receive FIFO屏障和可观测worker idle事实；缺少屏障绝不按超时进入READY |
| 静态库timer、queue或worker清理不完整 | 旧会话污染同一开机周期的新owner | 屏障前后两次取消，显式唤醒发送worker，并等待record/file/OTA/send/bulk全部idle后才rearm |
| BLE局部reinit重新开放RDX | 未完成收敛证明却开始下一RDX会话 | boot-lifetime consumed标志不得由server/transport reinit清零；只允许完成屏障的同peer重绑 |
| RDX断开后接纳新RDX owner | 新旧会话共享无token静态库队列 | `QUIESCING/RESETTING/FAILED`拒绝且不占owner；仅屏障与idle成立后的`READY`允许原peerclaim，不同peer返回`CONFLICT` |
| 自定义ATT错误码触发Windows异常行为 | CCC无限重试、错误配对或缓存异常 | Phase 0B先用标准0x0e并实测，0x80/0x81不预先冻结 |
| Disconnect Complete后发送release | 已断ACL上调用ATT send，状态或队列异常 | release只在主动断连前；Complete仅做local cleanup |
| 预编译RDX库不支持双App | 两个App命令状态混乱 | 正式范围限制为单RDX session |
