# BLE 一拖二双连接多服务共存实施方案——RDX 私有服务与 HOGP

> 架构基线：单链接复合 Profile 共享同一 GATT 数据库，在此基础上使用两个 `app_ble_hdl` wrapper 承载最多两条 BLE Peripheral 连接。
>
> 文档定位：本文只描述如何实施、验证和验收，不重新展开架构选型论证。设计缘由、产品边界和冻结决策见[四号设计理念](./4.BLE一拖二双连接多服务共存方案_RDX私有服务与HOGP.md)。
>
> 当前准入：Phase 0A 可执行；Phase 0B 必须在 0A 通过后执行；完整业务双连接改造必须等待 Phase 0B 与 `librdxApp.a` transport 边界审计通过。
>
> 范围：仅 BLE，不包含 Classic Bluetooth HFP、SCO 或其他经典蓝牙音频链路。

## 1. BLE 栈与编译配置

### 1.1 正式配置

目标配置为：

```c
config_le_hci_connection_num = 2;
config_le_gatt_server_num = 1;
config_le_gatt_client_num = 0;
config_le_sm_support_enable = 1;
```

含义如下：

| 配置 | 目标值 | 含义 |
|---|---:|---|
| `config_le_hci_connection_num` | 2 | 最多两条 BLE ACL connection |
| `config_le_gatt_server_num` | 1 | 设备只承担一套 GATT Server role/Profile 定义 |
| `config_le_gatt_client_num` | 0 | 设备不作为 BLE GATT Client/Central |
| `config_le_sm_support_enable` | 1 | 支持 HOGP 配对、加密与 bonding |

两个远端设备都是 Central，但本设备仍只承担 Peripheral/GATT Server 角色；本地不需要启用 GATT Client。

### 1.2 项目开关

建议在 `t2620_project_config.h` 中增加产品级正式开关：

```c
#define TCFG_RDX_HOGP_DUAL_LINK_ENABLE    1
```

`lib_btstack_config.c` 根据该开关选择 `config_le_hci_connection_num = 2`。不要把该值散落在 RDX 或 HOGP 模块中。

该开关只用于产品能力配置和受控实施，不得重新发展为单连接/双连接长期并存的复杂运行时模式。方案完成验收后，双连接应成为本产品唯一正式模型。

### 1.3 ATT RAM 与发送缓存

`multi_protocol_main.c` 已调用：

```c
ble_op_multi_att_send_init(att_ram_buffer,
                           ATT_RAM_BUFSIZE,
                           ATT_LOCAL_PAYLOAD_SIZE);
```

说明工程已经启用 multi ATT 发送基础设施。双连接实施时必须：

- 继续保留唯一的正式 ATT RAM 初始化入口；
- 删除或禁止使用 `rdx_ble_server.c` 中未接入初始化的重复 `att_ram_buffer`；
- 评估现有 `ATT_SEND_CBUF_SIZE` 对 RDX 业务发送与 HID report 的容量；
- 通过真实 App 文件/状态发送和连续 HID 输入测量峰值，而不是盲目扩大 RAM；
- 若扩容，统一修改 `multi_protocol_main.c` 的正式共享 buffer。

## 2. 双 wrapper 设计

### 2.1 数据结构

wrapper 和 link runtime 必须收敛到唯一固定数组。`rdx_ble_session.c`（也可命名为 `rdx_ble_link_registry.c`）是该数组、capability owner index 和 slot generation 的唯一所有者；`rdx_ble_server.c` 只负责 wrapper 初始化、广播策略和 SDK callback，不得再维护第二份连接状态影子。

```c
#define RDX_BLE_LINK_MAX 2
#define RDX_BLE_LINK_INVALID_INDEX 0xff

typedef enum {
    RDX_BLE_CAPABILITY_NONE = 0,
    RDX_BLE_CAPABILITY_RDX,
    RDX_BLE_CAPABILITY_HID,
} rdx_ble_capability_t;

typedef struct {
    void *ble_hdl;
    u16 con_handle;
    u16 mtu_size;
    u32 slot_generation;

    u8 connected;
    u8 encrypted;
    u8 peer_addr_type;
    u8 peer_addr[6];
    u8 capability;

    u8 rdx_ccc_configured;
    u8 rdx_stream_tx_ready;

    u8 hid_notify_enabled;
    u8 hid_suspended;
    u8 hid_protocol_mode;

    u8 conn_param_index;
} rdx_ble_link_ctx_t;

typedef struct {
    rdx_ble_link_ctx_t links[RDX_BLE_LINK_MAX];
    u8 rdx_link_index;
    u8 hid_link_index;
    u8 advertising_link_index;
    u32 transport_epoch;
} rdx_ble_transport_t;

typedef struct {
    u8 slot_index;
    u32 slot_generation;
    u32 transport_epoch;
} rdx_ble_async_token_t;
```

`slot_generation` 在 slot 每次建立新连接或释放时推进，用于拒绝旧 timer、跨 task 消息和异步完成事件；`transport_epoch` 在 BLE transport init/deinit、poweroff 和整体重建时推进，使上一生命周期的所有异步 token 一次性失效。同步 HCI/ATT 事件仍以 `hdl + connection_handle` 校验为主，不能假设原始 SDK 事件自带 slot generation。本文的 BLE `slot_generation` 与 keymap事务自身的 generation 是两个独立概念。

`link.capability` 是 slot业务归属的唯一权威字段，不再额外维护等价的 `rdx_active` 或 `hid_attached` 布尔值。`rdx_link_index` 与 `hid_link_index` 只是 registry 内部的派生快速索引，必须在同一次 claim/release 状态转换中与 `link.capability` 一起更新，并保持以下不变量：

```text
link.connected == 0
    → link.capability == NONE

link.capability == RDX
    → rdx_link_index指向该slot && hid_link_index不指向该slot

link.capability == HID
    → hid_link_index指向该slot && rdx_link_index不指向该slot
```

设备级名称、MAC、广播参数、发送 mutex 等全局配置可以继续保存在 server/global context；以下字段必须从全局 `rdx_ble_server_info_t` 移出：

- `ble_con_handle`；
- `ble_mtu_size`；
- `ccc_configured`；
- `stream_tx_ready`；
- 单一连接意义下的 `ble_conn`；
- 连接参数更新计数。

### 2.2 wrapper 初始化

两个 wrapper 均执行：

```c
app_ble_hdl_alloc();
app_ble_set_mac_addr(...same address...);
app_ble_profile_set(..., rdx_profile_data);
app_ble_att_read_callback_register(...);
app_ble_att_write_callback_register(...);
app_ble_att_server_packet_handler_register(...);
app_ble_hci_event_callback_register(...);
app_ble_l2cap_packet_handler_register(...);
app_ble_sm_event_callback_register(...);
```

任一分配或注册失败都必须回收已创建的 wrapper，并禁止进入半初始化运行状态。

### 2.3 wrapper 与 connection handle 映射

Connection Complete、Disconnection Complete、Encryption Change、MTU、连接参数、L2CAP 和 SM 等链路事件必须把 callback 的 `hdl` 一直传入最终处理函数，并同时校验 wrapper 与事件中的 connection handle：

```c
u16 event_handle = ...;

if (app_ble_get_hdl_con_handle(hdl) != event_handle) {
    return;
}
```

Connection与断连处理函数本身也必须保留wrapper参数，禁止在入口校验后调用一个丢失 `hdl` 的全局处理函数：

```c
static u8 rdx_ble_link_connected(void *hdl,
                                 const u8 *packet,
                                 u16 size,
                                 u8 enhanced);
static void rdx_ble_link_disconnected(void *hdl,
                                      const u8 *packet,
                                      u16 size);
```

随后通过 `hdl` 或 `event_handle` 定位唯一 link slot。不得再把每个 HCI 事件无条件写入同一个全局 session。

同步事件采用以下路由规则：

1. callback 的 `hdl` 必须属于 registry 中的一个 wrapper；
2. `app_ble_get_hdl_con_handle(hdl)` 必须与事件中的 connection handle 一致；
3. ATT read/write callback 中的 `hdl` 与 `connection_handle` 必须映射到同一 slot；
4. 同一 SDK 事件若被另一个 wrapper 的 callback 收到，必须无副作用地过滤；
5. slot 已释放或 connection handle 不匹配时，不得修改 capability、CCC、MTU、发送信号量或业务单例。

建议提供统一查询 API：

```c
rdx_ble_link_ctx_t *rdx_ble_link_find_by_hdl(void *hdl);
rdx_ble_link_ctx_t *rdx_ble_link_find_by_con_handle(u16 con_handle);
rdx_ble_link_ctx_t *rdx_ble_link_get_rdx(void);
rdx_ble_link_ctx_t *rdx_ble_link_get_hid(void);
u8 rdx_ble_link_active_count(void);
```

这些 API 读取的是同一个 registry，不允许 `rdx_ble_server_info_t`、HOGP 模块或录音模块另外缓存“最近一次 connection handle”作为路由依据。

## 3. 统一广播与连接槽管理

### 3.1 广播内容保持不变

继续使用三号方案已通过正式 App 与 Windows 实机验证的候选 C：

```text
Advertising Data:
    Flags
    Complete/Shortened Local Name

Scan Response:
    RDX Manufacturer Data（保持第一个 AD Structure）
    HID Service UUID 0x1812
```

不修改 Manufacturer Data 字节、AD Structure 顺序和 HID UUID。

### 3.2 单一活动 advertiser

虽然存在两个 wrapper，但任意时刻只启用一个空闲 wrapper 的 legacy connectable advertising：

```text
两个 wrapper 都空闲：
    选择 Link 0 广播

Link 0 已连接、Link 1 空闲：
    Link 1 广播

Link 1 已连接、Link 0 空闲：
    Link 0 广播

两个 wrapper 都已连接：
    停止广播
```

禁止两个 wrapper 使用同一设备地址同时开启重复 legacy advertising。

### 3.3 连接后的广播恢复

legacy advertising 通常在连接建立后由栈停止。Connection Complete callback 返回后，应通过短延迟 one-shot timer 在另一个空闲 wrapper 上恢复统一广播，避免与 wrapper 内部 connection handle 更新竞争。

该逻辑与三号方案“断连后延迟恢复广播”的经验一致，但触发条件改为：

```text
只要 active_link_count < RDX_BLE_LINK_MAX
且广播没有被 poweroff / DUT / Wi-Fi 等现有策略禁止
就选择一个空闲 wrapper 恢复广播
```

不再是“只有全部断开后才恢复广播”。

所有延迟广播、断连恢复和广播刷新必须复用同一个调度器，并遵守 stale-token 规则：

1. 调度前取消同类型旧 timer；
2. timer 参数携带 `slot_index + slot_generation + transport_epoch`；
3. callback 执行时重新校验 token，不相信调度时的连接计数；
4. 重新确认 `active_link_count < RDX_BLE_LINK_MAX`；
5. 重新确认目标 wrapper 仍空闲，且 `app_ble_get_hdl_con_handle(link->ble_hdl) == 0`；
6. 重新执行 poweroff、DUT、Wi-Fi 和现有广播禁止策略；
7. 任一条件不满足时直接退出，不开启广播；
8. deinit/poweroff 先取消所有广播 timer，再推进 `transport_epoch`。

示意逻辑：

```c
if (!rdx_ble_async_token_is_current(token)) {
    return;
}
if (rdx_ble_link_active_count() >= RDX_BLE_LINK_MAX) {
    return;
}
link = rdx_ble_link_get_by_index(token->slot_index);
if (!link || link->connected ||
    app_ble_get_hdl_con_handle(link->ble_hdl) != 0 ||
    !rdx_ble_adv_policy_allowed()) {
    return;
}
rdx_ble_adv_start(link);
```

### 3.4 名称或广播数据更新

名称、Manufacturer Data 等广播内容改变时：

- 更新设备级缓存；
- 若存在空闲 advertising wrapper，在该 wrapper 上安全重建；
- 已连接 wrapper 不需要为更新广播而断开；
- 两个 wrapper 下一次承担广播时必须使用相同最新内容。

## 4. Capability 激活与容量策略

### 4.1 连接建立时不分配身份

Connection Complete 只执行：

1. 找到对应 wrapper slot；
2. 推进该 slot 的 `slot_generation` 并保存 `con_handle`；
3. 初始化 link-level MTU、加密、peer 和连接参数状态；
4. 增加 active link count；
5. 停止自动关机；
6. 若仍有空闲 slot，安排另一个 wrapper 恢复广告；
7. 不激活 RDX；
8. 不激活 HOGP；
9. 不请求配对；
10. 不设置 owner。

### 4.2 HOGP capability 激活边界

以下行为可以激活 HOGP：

- 已加密链路对 `HID_INPUT_REPORT_CLIENT_CONFIGURATION_HANDLE` 写入 `0x0001`；
- 已绑定 peer 加密成功，并按该 peer identity 找到持久化 HID subscription；
- 目标 Windows 重连后，per-peer CCC 被安全恢复。

以下行为不能激活 HOGP：

- 读取 HID Service declaration；
- 读取 Report Map；
- 读取 HID Information；
- 读取 Device Information；
- 普通 GATT 全服务发现；
- 仅建立 BLE 连接。

原因是手机 App 或通用 GATT 工具可能枚举整个复合 Profile。若静态 HID read 就认领 HID slot或触发配对，会造成 App 链路误占 HOGP capability。

HOGP attach 的顺序必须固定为：

```text
按 hdl + connection_handle 定位 link
→ 校验CCC值、长度和link加密状态
→ 原子 claim HID capability
→ 将 HOGP 单例绑定到该 link 的 wrapper/handle/slot_generation
→ 更新或恢复该连接的 HID CCC
→ 满足加密、CCC 和非 suspend 条件后进入 ready
```

禁止先修改 `s_hid_notify_enabled`、peer、HOGP wrapper 或其他 HOGP 单例，再判断 claim 是否成功。

首次未加密的 HID Input CCC enable必须走独立的配对前置路径：

```text
收到CCC = 0x0001
→ link.encrypted == 0
→ 只调用sm_api_request_pairing(connection_handle)
→ 返回ATT错误INSUFFICIENT_ENCRYPTION（0x0f）
→ 不claim HID
→ 不写multi-ATT CCC
→ 不持久化subscription
→ 不绑定或修改HOGP单例
```

只有 Windows 在加密完成后重试 CCC enable，或已bonded peer加密完成并命中持久化subscription时，才允许claim HID。这样未完成配对或中途放弃的Central不会占用HID sink直到断连。Protocol Mode、Control Point和Output Report等其他HID动态写只能由现有HID owner处理，不得作为首次claim入口。

只有满足以下条件时才进入 ready：

```text
link.connected
&& link.capability == RDX_BLE_CAPABILITY_HID
&& link.hid_notify_enabled
&& link.encrypted
&& !link.hid_suspended
```

### 4.3 RDX capability 激活边界

以下行为可以激活 RDX：

- RDX notify CCC 开启；
- 收到合法 RDX value write；
- 收到合法 OTA/私有命令 characteristic write。

普通 GAP、Battery、HID 静态读取以及对 RDX value/CCC 的普通读取都不激活 RDX。只有成功校验的 RDX CCC enable 或合法私有写入才允许进入 RDX 协议库；claim 失败的输入不得继续传给 `librdxApp.a`。

RDX 激活后，现有单例 `librdxApp.a`、RDX 发送队列、文件和录音状态绑定该 link，直到该 RDX link 断开。

### 4.4 每条链路最多一种 capability、每种 capability 最多一个 sink

MVP容量策略为：

```text
active HID link <= 1
active RDX link <= 1
physical BLE links <= 2
capability per physical link <= 1
```

正式 MVP 采用同链路 capability 互斥：

```text
link.capability == RDX_BLE_CAPABILITY_RDX
    → 拒绝 HID claim

link.capability == RDX_BLE_CAPABILITY_HID
    → 拒绝 RDX claim
```

若第二条链路尝试开启已被另一条链路占用的 HID CCC：

- 拒绝新链路的 capability 激活；
- 返回明确 ATT error；
- 不清除旧 HID CCC；
- 不切换 report 发送目标；
- 不断开正在工作的 HID link。

若第二条链路尝试激活已被占用的 RDX session，同样拒绝新激活，不允许覆盖当前 RDX link。

这种策略避免第二个 PC 或第二个 App 抢占，同时不把 wrapper 序号固化为远端身份。

所有认领必须经过 registry 的唯一入口：

```c
int rdx_ble_link_claim_hid(rdx_ble_link_ctx_t *link,
                           u32 expected_slot_generation);
int rdx_ble_link_claim_rdx(rdx_ble_link_ctx_t *link,
                           u32 expected_slot_generation);
```

claim 必须在一次不可拆分的状态转换中完成：检查 link 仍连接、校验 slot generation、检查同链路 capability、检查全局同类 owner、设置 capability 与 owner index，然后才允许修改 HOGP/RDX 业务单例。claim 固定在 BTStack task 串行执行；其他 task 必须投递回 BTStack task，不得直接修改 registry。若未来允许跨 task 直接 claim，则必须增加临界区或等价同步。

claim 失败不能返回成功后静默丢弃，也不能抢占、切换或断开当前 owner。registry先冻结内部结果语义，ATT层再按实机验证结果映射错误码：

```c
typedef enum {
    RDX_BLE_CLAIM_OK = 0,
    RDX_BLE_CLAIM_BUSY,
    RDX_BLE_CLAIM_CONFLICT,
    RDX_BLE_CLAIM_STALE,
} rdx_ble_claim_result_t;
```

- 同一 link 重复 claim 已拥有的同类 capability：幂等成功；
- capability 已被另一 link占用：内部返回 `RDX_BLE_CLAIM_BUSY`；
- 当前 link 已拥有另一类 capability：内部返回 `RDX_BLE_CLAIM_CONFLICT`；
- link/slot generation失效：内部返回 `RDX_BLE_CLAIM_STALE`；
- HID/RDX CCC写 `0`：不触发claim，即使该link不是owner也只清除该connection的对应CCC；
- bonded HID subscription恢复前先claim HID；claim失败时不得恢复CCC、不得修改HOGP单例，也不得发起配对。

ATT错误码采用分阶段策略：

1. Phase 0B拒绝路径先将 `BUSY/CONFLICT/STALE` 映射为现有标准 `UNLIKELY_ERROR (0x0e)`；
2. 实测 Windows 对 HID Input CCC失败后的重试、配对、缓存和重连行为，确认不会出现无限重试、错误配对或异常缓存；
3. 只有验证 Windows与正式App均兼容后，才允许把 `BUSY/CONFLICT` 分别映射为application error `0x80/0x81`；
4. 若自定义码没有明确产品收益或存在兼容风险，正式实现继续统一使用 `0x0e`。

因此 `0x80/0x81` 不是当前冻结的外部ABI；冻结的是“忙、同链路冲突、stale”三种内部结果及其无副作用拒绝行为。

### 4.5 Capability ownership 为粘性生命周期

capability 一旦成功 claim，就绑定到该物理链路直到该链路断开：

- HID CCC 写 `0` 只令 `hid_notify_enabled/ready` 失效，不释放 `hid_link_index`；
- RDX CCC 写 `0` 只令 `rdx_ccc_configured/stream_tx_ready` 失效，不释放 `rdx_link_index`；
- HID suspend 只影响 ready，不释放 HID ownership；
- 不通过超时、静态读取、临时发送失败或后台状态自动迁移 capability；
- 只有匹配 owner link 的 Disconnect Complete 才释放 capability index；
- 若未来增加显式 App logout capability release，必须作为新协议行为单独设计，不能隐式复用 CCC disable。

## 5. ATT、CCC 与定向发送

### 5.1 ATT callback

read/write callback 已接收：

```c
void *hdl;
hci_con_handle_t connection_handle;
uint16_t att_handle;
```

所有动态处理都必须首先验证 `hdl` 与 `connection_handle` 映射到同一个 link context，并拒绝未知、已断开或映射不一致的 stale handle。禁止继续使用全局 `rdx_ble_session_is_current()` 的单链接语义。

静态读取与 capability 激活必须解耦：完整服务发现、Report Map/HID Information 读取、RDX value读取和 CCC读取均不得产生 claim、配对、业务连接回调或发送状态变化。

### 5.2 CCC 必须 per connection

所有 RDX/HID CCC 都使用：

```c
multi_att_set_ccc_config(connection_handle, att_handle, cfg);
multi_att_get_ccc_config(connection_handle, att_handle);
multi_att_clear_ccc_config(connection_handle);
```

当前 RDX callback 中的：

```c
att_set_ccc_config(handle, value);
```

必须删除或替换，否则两个连接会共享、覆盖或错误读取 CCC。

### 5.3 HID report 定向发送

HID 发送只使用当前 HID link 对应 wrapper：

```c
app_ble_att_send_data(hid_link->ble_hdl,
                      HID_INPUT_REPORT_VALUE_HANDLE,
                      payload,
                      sizeof(payload),
                      ATT_OP_NOTIFY);
```

不得无连接目标地广播给两个 wrapper，也不得根据最近一次连接选择目标。

### 5.4 RDX 数据定向发送

RDX response、notify、OTA 与 bulk data 只使用当前 RDX link：

```c
app_ble_att_send_data(rdx_link->ble_hdl,
                      rdx_att_handle,
                      data,
                      len,
                      op_type);
```

`app_ble_att_vaild_len_get()`、disconnect、remote MAC 查询和 send fail 统计也必须传入 RDX link wrapper。

### 5.5 ATT_EVENT_CAN_SEND_NOW

两个 wrapper 都可能收到发送事件。callback 必须：

- 先确认事件属于哪个 wrapper/connection；
- 只有 RDX link 的事件才能唤醒 RDX bulk-send semaphore；
- HID link 的 CAN_SEND_NOW 不得误清 RDX bulk flag；
- 断开后的迟到事件不得操作已复用 slot。

处理顺序必须至少满足：

```c
link = rdx_ble_link_find_by_hdl(hdl);
if (!link || !link->connected ||
    app_ble_get_hdl_con_handle(hdl) != link->con_handle ||
    link != rdx_ble_link_get_rdx()) {
    break;
}

/* 只有此后才能清 bulk/send-confirm 并 post RDX send semaphore。 */
```

若 CAN_SEND_NOW 事件格式中包含 connection handle，还必须同时比较事件 handle；若该 SDK 事件不携带 handle，则 RDX发送路径在请求/等待 CAN_SEND_NOW 时必须保存 `slot_index + slot_generation + transport_epoch` pending token，callback同时校验 `hdl` 当前映射和 pending token，且只能清除匹配 token。没有有效 RDX pending token 的事件不得唤醒发送信号量。

### 5.6 MTU 与连接参数

MTU、connection update index、interval 和 timeout 均改为 per-link。

MTU发送上限使用：

```c
ble_op_multi_att_set_send_mtu(connection_handle, mtu);
```

不得继续使用无 connection handle 的 `ble_op_att_set_send_mtu(mtu)`。

建议策略：

- HID link 以低延迟和稳定按键为优先；
- RDX link 以配置可靠性和合理吞吐为优先；
- 不使用一个全局 `connection_update_cnt` 同时驱动两条链路；
- 一条链路拒绝参数更新不影响另一条链路的更新状态。

### 5.7 业务模块只使用窄接口

`rdx_ble_server_info_t` 只保留名称、MAC、广播缓存、设备级 timer/mutex 和 wrapper资源，不再向录音、文件或 LED 模块暴露 per-link 字段。业务模块统一使用：

```c
u8  rdx_ble_rdx_is_connected(void);
u8  rdx_ble_rdx_stream_tx_ready(void);
u16 rdx_ble_rdx_mtu_get(void);
int rdx_ble_rdx_send(u16 att_handle,
                     const u8 *data,
                     u16 len,
                     u8 op_type);
```

必须清理 `rdx_ble_server_get_info()` 调用方对 `ble_con_handle`、`ble_mtu_size`、`ccc_configured`、`stream_tx_ready` 和单 wrapper 的直接访问，避免 registry 与公开结构形成两个真相来源。

### 5.8 携带 link 语义的异步操作必须使用 token

async token只约束会跨越当前调用栈并在未来再次访问BLE link语义的工作，不要求所有纯本地timer机械携带token。

凡异步回调、app_core消息、task queue、timer或完成通知会执行以下任一行为，投递时都必须复制 `slot_index + slot_generation + transport_epoch`，执行时重新解析并验证当前RDX/HID owner：

- 读取或修改RDX/HID owner；
- 读取connection handle、MTU、CCC、加密或peer状态；
- 调用BLE notify/indicate、查询发送长度或等待CAN_SEND_NOW；
- 操作与当前RDX link绑定的录音上传、OTA、文件同步、bulk buffer或keymap响应；
- 在断连后可能把旧业务结果发送给新owner或已复用slot。

```c
rdx_ble_async_token_t token = rdx_ble_link_token_capture(rdx_link);
post_to_app_core(..., token);

/* app_core/timer callback */
rdx_ble_link_ctx_t *link = rdx_ble_link_token_resolve_rdx(&token);
if (!link) {
    return;
}
/* 只有此后才能读取link状态或尝试BLE发送。 */
```

取消timer、清空队列或设置业务stop flag只能作为辅助收敛，不能替代callback入口的token校验。RDX owner断开、slot复用或transport deinit后，旧token必须失效；新的RDX owner不得继承旧录音、OTA、文件或发送任务。

纯本地且与BLE link无关的timer不适用，例如只更新本地LED动画、文件系统维护或不读取/发送任何连接状态的离线任务。是否需要token以callback实际访问的数据和副作用为准，而不是以源文件位于 `rdx_record.c`、`rdx_ota.c` 或 `rdx_app.c` 为准。

## 6. 连接生命周期与清理边界

### 6.1 RDX link 断开

仅当断开链路实际激活了 RDX 时执行：

- 停止 RDX force-disconnect timer；
- 停止同步与文件 busy timer；
- 清理 RDX发送状态和 bulk buffer；
- 中断或收敛与 App 连接相关的在线录音/传输；
- 清理 OTA 会话；
- 调用 `rdx_hogp_keymap_config_on_disconnect()` 取消尚未完成的 App keymap事务；
- 清除该 link 的 RDX CCC 和 tx-ready；
- 释放 `rdx_link_index`。

不得执行：

- 清除另一个 HID link 的 CCC；
- 清除 HID peer identity；
- 把按键路径切回离线；
- 主动断开 PC；
- 重置整个 BLE transport。

### 6.2 HID link 断开

仅当断开链路实际激活了 HOGP 时执行：

- 清理 HID report runtime；
- 清理该 link 的 CCC、加密、suspend和peer缓存；
- 释放 `hid_link_index`；
- 使 `rdx_hogp_keyboard_is_ready()` 收敛为 0；
- 后续物理按键恢复离线产品功能。

不得执行：

- 取消 App keymap事务；
- 停止 RDX notify；
- 清理 RDX文件/OTA状态；
- 把 App连接标记为断开。

release report 的发送边界必须与 Disconnect Complete 分开：

- 本地主动断连前、keymap apply/切换前、HID suspend前和 CCC disable前：链路仍 ready 时可以尽力发送 release；
- 远端主动断开、supervision timeout 或异常掉线：不能保证发送，只清理本地 pressed/report state；
- 收到 `HCI_EVENT_DISCONNECTION_COMPLETE` 后：ACL 已不存在，禁止再调用任何 ATT send API；
- `rdx_hogp_on_disconnected()` 必须提供 local-only cleanup 路径，不能间接调用 `rdx_hogp_keyboard_release_all()`。

### 6.3 公共链路清理

任一连接断开都执行：

- 按 callback `hdl + disconnected_handle` 定位且只接纳对应 slot 一次；
- 在 slot 清零前记录其 capability 与 slot generation，并执行对应 local-only cleanup；
- 清理该 connection handle 的 runtime CCC；
- 仅当该 slot 是 capability owner 时释放对应 owner index；
- 清空连接态并推进 slot generation，使旧异步 token失效；后续SM/MTU/Encryption事件由 `hdl + connection_handle` 映射拒绝，CAN_SEND_NOW还必须校验RDX pending token；
- 减少 active link count；
- 若存在空闲 wrapper，延迟恢复统一广播；
- 只有 active link count 变为 `0` 才恢复自动关机策略；
- deinit/poweroff 时显式断开两个 wrapper 并逐个释放。

### 6.4 `ble_conn` 语义拆分

当前代码中的 `g_rdx_ble_server_info.ble_conn` 同时被用于：

- 任意 BLE 是否连接；
- RDX App 是否连接；
- LED 显示；
- 录音在线模式；
- 广告禁止；
- 自动关机。

双连接后必须拆成明确接口：

```c
u8 rdx_ble_link_active_count(void);
u8 rdx_ble_any_link_connected(void);
u8 rdx_ble_rdx_is_connected(void);
u8 rdx_hogp_keyboard_is_connected(void);
u8 rdx_hogp_keyboard_is_ready(void);
```

调用方必须按业务含义选择接口，禁止继续使用一个模糊布尔值。

## 7. HID 在线热修改 Keymap

### 7.1 现有能力可直接复用

当前 `rdx_hogp_keymap_config.c` 已实现：

- request decode和参数校验；
- request id冲突处理；
- revision并发控制；
- 幂等重试；
- keymap CRC；
- 双 VM slot；
- prepare/apply/commit；
- VM失败回滚；
- executor publish；
- App断开时的 generation失效。

四号方案不修改该协议与持久化 ABI，只修正它所依赖的 BLE发送目标和断连边界。

### 7.2 热更新流程

```text
PC HOGP link 已 ready
        │
手机 App 通过 RDX link 发送 SET_KEYMAP
        │
RDX link 完成协议、revision、CRC和busy校验
        │
准备 inactive VM slot
        │
通过 HID link 发送/收敛旧 report release
        │
更新 RAM active keymap
        │
提交并校验 VM slot
        │
失败则恢复旧 keymap
        │
通过 RDX link 返回成功/失败响应
        │
下一次物理按键使用最新 committed keymap
```

整个过程中：

- PC HID connection handle 不改变；
- HID CCC 不关闭；
- Windows 不需要重新枚举设备；
- App 不需要主动断开；
- 不切换广播模式；
- 不触发 PC自动回连。

### 7.3 并发边界

keymap commit 在 `app_core` 串行执行，继续保留单 pending request。提交期间若物理按键事件可能并发进入 executor，应保证：

- 先取消旧 release timer；
- 先释放当前按键状态；
- 完整复制 keymap后再发布 active generation；
- 回滚时同样先 release再恢复旧 map；
- 任何错误都不能让半份 keymap 可见。

## 8. 安全、配对与 Peer 状态

### 8.1 HOGP安全策略

继续使用三号方案已经验证的：

```text
IO_CAPABILITY_NO_INPUT_NO_OUTPUT
+ Just Works
+ Bonding
+ Secure Connections
```

HID动态写继续要求加密。只有 Input CCC 写入或 bonded subscription恢复才触发 HOGP attach，不恢复“连接即配对”。

### 8.2 Peer identity 必须 per link

当前 `rdx_hogp_keyboard.c` 只缓存一个 `s_peer_identity_con_handle`。双连接后必须把 peer address/type 保存到对应 link slot，禁止通过全局“最近 peer”推断。

bonded HID subscription store 已支持多个 peer entry，可以继续复用；查询和更新必须传入当前 HID link 对应 peer identity。

以下情况必须拒绝：

- 全零 peer；
- 全 `0xFF` peer；
- stale connection handle；
- RDX手机 peer 继承 Windows的 HID CCC；
- 第二条链路覆盖第一条链路尚未完成的 subscription更新。

### 8.3 RDX访问策略

四号方案不把 wrapper、slot、HID bond或加密状态当作 RDX远端身份认证。沿用当前产品已批准的“连接并按协议访问即有权调用 RDX”语义。

若未来需要真正的 App身份认证，应增加独立挑战/响应或密钥协议；不得重新引入伪 owner作为替代。

## 10. 分阶段实施方案

### Phase 0A：纯 wrapper POC

目标：只验证当前芯片、SDK二进制版本和 `config_le_gatt_server_num = 1` 下的双 Peripheral wrapper模式，不接入 RDX命令、HID CCC或完整业务。

实施内容：

1. 设置 `config_le_hci_connection_num = 2`；
2. 分配两个 RDX wrapper；
3. 两者注册同一 Profile与callbacks；
4. 上电由第一个 wrapper广播；
5. 第一条连接后由第二个 wrapper恢复相同广播；
6. callback日志记录 `hdl`、wrapper index、事件 connection handle和`app_ble_get_hdl_con_handle(hdl)`；
7. 两个 Central只做服务发现与静态读取；
8. 任意一条断开后，另一条保持连接。

Go条件：

- Windows与正式 App可以同时保持连接；
- 两个 wrapper映射正确；
- 无第二连接覆盖第一 wrapper handle；
- 无 ATT数据库异常或服务缺失；
- 单边断开不导致另一边HCI断开。

Phase 0A期间不得为了快速演示而把完整 RDX/HOGP 单例直接接入两个 wrapper；它只回答“双 wrapper能否同时承载两条 Peripheral connection”这一不可由预编译库静态证明的问题。

### Phase 0B：双连接 ATT 隔离 POC

在 Phase 0A通过后验证：

- 两条连接分别读取同一份 Profile中的相同 handle；
- 两条连接的 MTU、CCC 和 notify目标相互独立；
- wrapper/connection映射在两条连接同时存在时保持稳定；
- 一个 wrapper 的 Disconnect Complete不会被另一个 wrapper重复处理；
- HID wrapper的CAN_SEND_NOW不会唤醒RDX发送信号量；
- 第二slot连接完成、slot快速复用或deinit后，旧ADV timer不会重新开启广播。

使用不接入HOGP业务单例的最小CCC test harness补充验证：

- 未加密 HID Input CCC enable只触发pairing request并返回 `0x0f`，不claim、不写CCC、不持久化；
- capability拒绝路径先返回标准 `0x0e`，观察Windows是否出现异常重试、错误配对、缓存污染或重连循环；
- 自定义 `0x80/0x81` 仅作为对照实验，不在Phase 0B前冻结为外部ABI。

Phase 0B通过前，不进入完整 capability和预编译RDX会话接入。Phase 0B的临时test harness不得演变成第二套生产registry或业务状态中心。

- 延迟ADV callback重新校验slot generation与transport epoch；
- 任意单边断开只清理对应 capability；
- HID断开不调用 `rdx_hogp_keymap_config_on_disconnect()`；
- RDX断开不清理 HID ready runtime；
- HOGP static read不attach或请求配对；
- RDX static read不attach或进入预编译协议库；
- capability claim通过唯一API完成，同一link不能同时claim RDX/HID；
- 未加密HID CCC enable在claim前返回 `0x0f`，且不写CCC、不持久化；
- claim内部结果与ATT错误码映射分离，`0x80/0x81`不是预先冻结的ABI；
- CCC写0只改变ready/tx状态，不释放owner index；
- Disconnection Complete路径不调用HID ATT send；
- 携带link语义的异步BLE工作在入口校验async token；
- keymap handle、Report Map和8-byte report契约保持不变。

Host contract只能冻结源码结构和禁止项，不能证明wrapper实际绑定、callback分发、controller双连接调度、SM peer隔离或广播恢复时序；这些项目必须由Phase 0A/0B和后续实机矩阵验证，不能以PowerShell静态检查替代。

### 11.2 真实设备连接顺序

```text

[ ] App先连RDX，PC后连HOGP

```

## 12. 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 只改连接数、不改单例状态 | 第二连接覆盖第一连接，任意断开导致全局清理 | 双 wrapper + per-link session必须原子实施 |
| server/session各维护一份links | 两个状态中心不一致，释放与发送目标漂移 | link registry唯一拥有links、owner和slot generation |
| 一个 wrapper承载两个handle | `app_ble_get_hdl_con_handle()`、发送、广告和断连语义不匹配 | 遵循Find My/RCSP双wrapper实践 |
| App枚举HID触发attach | 手机误占HID、弹配对提示 | HID只在Input CCC或bonded恢复时attach |
| 未加密CCC写失败前已claim HID | 放弃配对的Central占住HID sink直到断连 | 未加密路径只请求配对并返回0x0f，加密重试后才claim |
| 静态RDX read触发attach | 通用枚举误占RDX session或唤醒预编译库 | RDX只在CCC enable或合法私有write时claim |
| 同一link同时claim RDX/HID | 手机同时占用两个capability，PC无法成为HID sink | MVP同链路capability互斥且ownership粘到断连 |
| RDX CCC仍为全局 | 两条链路相互覆盖订阅 | 全面迁移到`multi_att_*ccc_config` |
| RDX响应发错Central | PC收到私有notify或App收不到响应 | 发送始终选择`rdx_link->ble_hdl` |
| HID report发错Central | App收到键盘report、PC无输入 | 发送始终选择`hid_link->ble_hdl` |
| 一条断开清理另一条 | HID/App相互掉功能 | link cleanup、RDX cleanup、HID cleanup三层拆分 |
| ATT buffer不足 | RDX吞吐下降、HID send busy | 测量峰值后统一调整multi ATT buffer |
| 两条链路连接参数互相污染 | HID延迟或App不稳定 | 参数索引、MTU和更新状态per-link |
| 双连接同时回连竞态 | wrapper映射错误、stale event误清理 | hdl + con_handle双重校验和slot generation |
| 旧ADV timer跨slot复用或poweroff执行 | 满连接后错误广播或deinit后访问wrapper | slot generation + transport epoch + callback重检策略 |
| HID CAN_SEND_NOW唤醒RDX | bulk/send-confirm状态错乱 | 只有当前RDX wrapper事件可操作RDX信号量 |
| 旧app_core/录音/OTA/文件任务访问新owner | 旧业务结果跨会话发送或污染新RDX session | 所有携带link语义的异步工作捕获并校验async token |
| 自定义ATT错误码触发Windows异常行为 | CCC无限重试、错误配对或缓存异常 | Phase 0B先用标准0x0e并实测，0x80/0x81不预先冻结 |
| Disconnect Complete后发送release | 已断ACL上调用ATT send，状态或队列异常 | release只在主动断连前；Complete仅做local cleanup |
| 预编译RDX库不支持双App | 两个App命令状态混乱 | 正式范围限制为单RDX session |

## 13. 最终验收标准

本方案完成必须同时满足：

- PC与正式手机App可同时保持BLE连接；
- 无需断开PC即可修改HID自定义按键；
- 保存配置后下一次按键立即使用新map；
- Windows不重新枚举、不自动重连；
- 两个连接使用相同复合Profile和统一广播身份；
- 第一条连接后仍能被另一端扫描并连接；
- 两条连接满载后停止广播，释放一个slot后恢复广播；
- 双 wrapper能力已由Phase 0A实机验证，per-connection ATT隔离已由Phase 0B验证；
- 未加密HID CCC写不会claim，最终ATT拒绝码映射已由Windows与正式App实测冻结；
- RDX notify只发送到App link；
- HID report只发送到PC link；
- 同一物理link不能同时占用RDX与HID，CCC关闭不迁移ownership；
- 所有同步事件按wrapper + connection handle路由，所有携带link语义的异步操作受slot generation/epoch保护；
- 所有携带link语义的app_core、录音、OTA和文件异步工作均受async token保护；
- App断开不影响HID，HID断开不影响App；
- bonded HID CCC继续按peer隔离和跨上电恢复；
- App全服务发现不触发HID配对；
- 现有HID Profile contract、keymap事务和RDX基础业务回归通过；
- `librdxApp.a` transport输入、输出、发送唤醒、断连与重绑定边界审计通过；
- host software tests与Windows固件构建通过。
