## 2. 已采用的正式基线

### 2.1 适用场景与安全边界

- 目标是正常开机、电池供电、USB/VBUS 拔出且无业务/收尾；充满不等于拔线。
- 不断开 ACL，不释放 RDX/HID owner，不改变订阅、加密或绑定。上一阶段 `632ddc0b` 保留第二连接入口常开；本轮采用第 4.2 节的有限窗口，历史组合实验见第 3 节。
- 按键、录音、播放和文件访问正常唤醒；关机、低电保护、USB 所有权与 OTA 安全不因省电放宽。
- 不新增常驻连接态轮询。空闲窗口与灯效在 `app_core` 按事件调度；存储入口仍可在调用任务同步恢复共享域。

### 2.2 PE5 跟随实际输出

**PE5 = DAC 模拟就绪且数字输出运行。** 输出停止后关闭功放，不等待 DAC 模拟关闭，不绕过 JL 框架强关模拟资源。此策略与 BLE 状态和 PA4 无关，未连接时同样适用。

### 2.3 PA4 复用共享域管理器

连接态和未连接态分别判断关电资格，共用安全停用/恢复执行器。不能简单删除“有连接则忙”的判断，更不能用第二入口慢广播冒充整机未连接。

| 环节 | 策略 |
|---|---|
| 开始计时 | 至少一条 ACL；无 USB/充电/OTG 占用，无录音、播放、文件、RGB、DUT、OTA 等业务及持久存储占用 |
| 空闲期限 | 条件全部就绪后计满 120 秒，不从建链瞬间计时；业务/拓扑变化或恢复后重新评估完整窗口 |
| 不延长窗口的活动 | 纯版本/电量查询、协议空检查、重复状态通知；列表/容量/文件读取属于真实存储业务 |
| 安全关断 | 确认无排队请求、脏缓存、读句柄、删除/保存及在途 IO，完成 SD 卸载和 RGB/SPI 停用后关闭 PA4 |
| 按需恢复 | 真实访问先登记占用再同步恢复；可用后才放行访问，纯 HOGP 报告不需要 PA4 |
| 竞争与失败 | 新业务、USB 或拓扑变化撤销旧关断；停用失败保留供电，恢复失败拒绝访问，不自动格式化 |
| 调度 | 仅空闲期限保留单次超时；忙时等待业务结束事件，不用 1 秒轮询等待空闲 |

共享域恢复与灯效调度分开：恢复 RGB 硬件默认 OFF，不无条件创建灯效定时器；OFF/永久常亮停表，短提示等截止时间，动态效果才短周期续约。

### 2.4 连接参数以交互为先

- 每条已连接的物理 ACL 建链后即常驻请求单一目标 `{6,12,L,600}`，不区分 RDX、HID、复合会话或尚未认领的链路，`L = TCFG_T2620_CONN_SLAVE_LATENCY`（默认 49，范围 0–49，在 `t2620_project_config.h` 配置）。实际 interval=6–12（7.5–15 ms）且 latency 等于 L 才算达标，不强求手机精确采用 7.5 ms。
- latency 必须相等：手机会自行改回 latency 0（录音结束时观察到 30 ms / lat 0，推测为 APP 切换连接优先级），协调器随即按有限预算重新请求，实测约 280 ms 回到 lat=49。只改 latency 时手机接受很快（实测 340–360 ms），不会重现旧慢档改 interval 时约 18.8 s 的慢回快。
- 不切换快慢档，也不带本地 latency 门控：从机有待发数据时可在任一连接事件发送，下载、录音流、HID 报告不受 latency 拖慢；只有手机下行的首包最坏多等 (L+1)×interval（L=49、12.5 ms 时约 625 ms），实测 APP 操作可接受。门控实验见第 3.3 节，未采用。
- 下载结束和历史参数入口统一归入同一目标检查。第 3 节旧慢档（改 interval）仅用于实验，不代表重新采用。
- 当前只确认 Android 连接态低功耗达标；其余场景的已知风险见第 2.6 节，出现问题再优化。
- 保留 `app_core` 统一请求、实际参数确认、每条物理 ACL 的节流、有限重试和旧回调隔离。每轮最多 3 次、间隔至少 2 秒；重复业务通知和逻辑会话切换不刷新预算，确认快档后再次退化才开启新的恢复轮次。
- 不阻塞业务等待协商；已达快档或重试耗尽后停表，不为参数维护新增常驻轮询。
- 参数目标属于物理 ACL，而不是 RDX/HID 逻辑会话：建链、断链、参数更新完成事件由 `rdx_ble_server.c` 直接通知协调器，不依赖共享 VDD 模块；RDX 认领、释放和 HID 接入只触发重新检查，不刷新同一 ACL 的重试预算。双 ACL 时两条链路各自独立收敛。断连/关机撤销待办，双 ACL 休眠保护不变。
- 2026-11-10 前的旧边界只管理 RDX 链路（及其逻辑退出后保留 HID 的同一 ACL），纯 HID 回连的 PC 链路停在 15 ms / latency 0，约 3 mA 无法降下来，因此取消该边界。
- PA4 的 120 秒窗口、PE5 策略和未连接快慢广播独立保留。连接参数与广播参数不是同一机制。

### 2.5 上一阶段正式增量：接收任务事件化，单 RDX 主路径已测

- 空闲使用信号量无限等待，不再每秒空超时；保留入队通知、连续消费、自通知和退出 FIFO 屏障，空通知消耗完毕后重新阻塞。
- 成功取出数据包后、解析前才刷新原生算力；保留下载、音频等既有时钟申请。空队列、出队失败不提频，不强制固定低频。
- 通知计数饱和意味着已有唤醒令牌；其他通知错误返回失败，退出屏障沿用既有 fail-closed，不靠定时轮询修补无效 OS 对象。
- 调频观察回调明确归属 `app_core`，不依赖发起提频的任务分发定时消息。保留原生 10 秒观察间隔、7 轮计算和算力约束；真实业务刷新观察期限，旧期限到达不提前降频，观察结束后停表，下一轮业务可重新启动。
- 该阶段不调整第二入口/睡眠门禁、BLE 参数、HOGP、USB 或 PA4/PE5 策略；单 RDX 阶段电流约 5/4 mA，不能套用组合实验的 2.5/1.5 mA。该次连接期间仍为 `system_sleep_block=1`，验证的是原生降频和外设关电；连接态睡眠的本轮证据见第 1.1 节。

### 2.6 latency 49 的已知风险与后续优化方向

当前结论覆盖 **Android 手机 + 单 RDX 连接**（关窗待机 0.6–1.3 mA，列表、录音等 APP 操作响应可接受）和 **Windows PC 纯 HID 单连接**（2026-11-10 按 ACL 请求参数后，用户实测 1 mA 以下）。以下场景未验证，按“出现问题再优化”处理，不预先增加机制。

| 风险 | 原因 | 预期表现 | 出现问题时的优化方向 |
|---|---|---|---|
| iOS 不省电 | 苹果要求 latency ≤30、interval ≥15 ms、interval_min + 15 ms ≤ interval_max；`{6,12,49}` 不合规 | 手机拒绝或忽略请求，协调器重试 3 次后停止（日志 `[RDX_CONN_POLICY] unconfirmed`），沿用手机参数；功能正常，电流约回到 1.0–1.5 mA | 收到 `ostype` 后改用 iOS 合规目标（如 `{12,24,30,600}`），并为新目标重开一轮有限重试 |
| 手机→设备大量写入变慢（OTA 上传等） | 从机空闲时每 (49+1)×interval（约 625 ms）才监听一次；手机下行数据只能在从机监听的连接事件送达，是否因收包自动放弃 latency 取决于 JL controller，未验证 | OTA 耗时显著变长，甚至触发 APP 超时 | 传输期间本地 `ble_op_latency_skip(con, 0xffff)`，结束后恢复（冻结分支门控已验证接口可用）；或传输期间临时请求 latency 0（只改 latency，手机约 300 ms 接受） |
| 手机下行首包延迟 | 同上，首条指令最坏多等约 625 ms | 单条操作体感偏慢；连续操作时首包后同样受限 | 当前 Android 实测可接受；若某些交互不可接受，同上按需本地临时取消 latency |
| 手机反复改回 latency 0 | APP 切换连接优先级（实测录音结束时出现 30 ms / lat 0） | 协调器按 2 s 节流、每轮最多 3 次重新请求；若手机持续覆盖，空闲电流回升 | 抓日志确认触发方，必要时与 APP 约定不在空闲时请求高优先级 |
| PC HID 场景 | 2026-11-06 Windows PC 已接受并保持 `if=12 lat=49`（含已绑定重连）；原 HOGP 键盘就绪后 10 ms 周期服务已改为事件驱动（第 2.7 节）。2026-11-10 发现纯 HID 回连时旧策略不请求参数（`COM3_2026-11-10_19-12-47.log`：15 ms / lat 0，约 3 mA），已改为按 ACL 请求 | 已验证：复合会话关窗后持续睡眠，静置降至 1 mA 以下；纯 HID 单连接修正后（`COM3_2026-11-10_20-00-53.log`、`COM3_2026-11-10_20-45-37.log`）参数为 `if=12 lat=49`、持续 `S<>w[]`，用户实测 1 mA 以下。绑定回连时 PC 直接沿用 `12/49`，无需再请求；手机作为第二 ACL 接入给出 `6/0` 时，设备请求 1 次即在约 110 ms 内收敛到 `12/49` | 精确电流、长稳和更多 PC/系统版本待测；若再出现无睡眠，先核对参数是否为 lat=49，再按第 2.7 节核对 `S<>w[]` 与唤醒源 |
| 下载吞吐 | 设备→手机通知有待发数据即可在任一连接事件发送，理论不受 latency 影响 | 预期无变化，未专项实测 | 若变慢，传输期间本地取消 latency |
| 监督超时余量 | 最长空闲间隔 15 ms × 50 = 750 ms，监督超时 6 s | 余量 8 倍；弱信号下仍需长稳观察 | 必要时减小 `TCFG_T2620_CONN_SLAVE_LATENCY` |

回退手段：`TCFG_T2620_CONN_SLAVE_LATENCY` 设为 4 即回到原快档请求（判定由 latency ≤4 改为等于 4，手机给 latency 0 时会重新请求，属可接受差异）。

### 2.7 PC HID + PC RDX 复合会话：HOGP 输入服务事件化（2026-11-06）

最常用的 PC 待机场景是 PC HID 与 PC APP（RDX）复用同一条 ACL。[3-6](3-6.BLE复合会话满占时第二入口广播控制方案.md) 已在复合 owner 形成后关闭第二入口，但用户实测 PA4 关闭后仍约 3 mA，没有保持单 RDX 的成果。

**根因：HID 业务此前未做低功耗优化。** `rdx_hogp_input.c` 在键盘就绪（CCC 打开、已加密、未 suspend）后常驻 10 ms 周期 `sys_timer`。`sys_timer` 会把系统从低功耗唤醒，并向 `app_core` 投递回调，因此约 100 次/s 的周期让系统始终无法进入睡眠。纯 RDX 场景 HOGP 未就绪、本就停表，所以第 3.3 节探针没有覆盖到它。

| 依据 | 事实 |
|---|---|
| `COM3_2026-11-06_17-18-19.log` | 复合会话参数为 `if=12 lat=49`，关窗确认后 `system_sleep_block=0`，PA4 已关，但之后始终没有 `<>` 睡眠回调。参数和门禁都不是原因 |
| `COM3_2026-11-06_17-49-48.log`（临时 A/B，仅把 10 ms 改为 1000 ms，未提交） | `00:00:48.602` 关窗确认，`00:00:50.191` 起持续出现 `S<>w[]`，约 9–10 次/s；用户实测 PA4 关后 0.5–3 mA 跳动。确认主因就是该周期定时器 |

**正式实现**（`rdx_hogp_input.c`，没有新增配置开关）：

- 在线空闲时不保留周期定时器。按键扫描、手势、失效与就绪变化本来就会投递 `app_core`，不再依赖定时器兜底。
- 只有 HID 报告在途（等待 btstack 回执）或欠发松开报告时，才运行 10 ms 重试定时器；条件解除后立即删除。长按保持期间不计时。
- 记录已处理的 HID 就绪状态。就绪变化、或需要重试却没有定时器（创建失败）时，`rdx_hogp_input_needs_poll()` 交给已有的 DIP 优先级 0 恢复桥接，不新增常驻轮询。
- 本轮执行期间新产生的待办（含本轮内部失效）补投一次；连续两轮仍有待办就不再自投递，避免忙循环。
- 首键、松键、按住、新会话松开屏障、ATT 背压及失效清理的语义不变。`periodic_running` 现在表示“重试定时器正在运行”，空闲时为 0 属正常。

主机测试 `test_hogp_hold.py` 新增“在线空闲无定时器、按下/松开只在在途期间计时、长按无定时器、欠发松开重试后停表”，并按新语义调整定时器失败恢复用例。统一入口 24 个套件全部通过。

**板测**（`COM3_2026-11-06_18-15-15.log`，SHA-256 `ce829923c332697c6943d43acf655528f211955c98d14fd80892e3e42107b155`，原始日志本地保留，含授权信息不入库；下表为设备运行时间，中途有一次复位，分两段）：

## 3. 单连接探底结果与归因边界

### 3.1 已测条件与实验措施

场景为电池供电、无 USB/VBUS、仅一台手机 RDX 连接、无 HID ready、无录音/文件/OTA 业务。实验保留 PA4 的 120 秒安全关断、电池保护、DIP 关机、看门狗和缓存持久化，不以断连换电流。

| 已归档实验措施 | 作用与限制 |
|---|---|
| 关闭第二连接入口 | 第一条 ACL 建立后停止另一入口；两个 wrapper 及原有休眠保护不删除，停广播失败继续阻止睡眠；实验版不能接入第二台设备 |
| 接收任务事件化 | 用信号量阻塞替代每秒空超时，取消空闲 `clock_refurbish()`；保留入队通知、队列消费、自通知及会话退出屏障 |
| PA4 关闭后申请慢档 | 请求 `{80,80,9,600}`，实测采用 100 ms、latency 9；尚未验收首包和业务响应 |
| PA4 关闭后强制低频 | 临时固定 24 MHz，覆盖业务频率需求；启动/配对不强压低频，唤醒恢复为异步协调，不能保证新业务执行前已恢复算力 |
| 暂停 HOGP、放宽 USB 检测 | 停用 HOGP 10 ms 周期服务，原生 OTG 检测由 250 ms 改为 2 秒；两者均未按正式业务验收 |
| 低扰动诊断 | 关闭应用睡眠回调的逐次字符，保留两次快照；日志仍有底层 `Sw[]` 等输出，不等于已关闭所有底层打印 |

实验配置的构建、主机测试和补丁库可重复生成检查已通过，用户已完成该次功耗板测；这些历史结果不替代当前正式配置的功能与长稳验收。

### 3.2 日志确认的关键机制

- 单连接关闭第二入口后，`system_sleep_block` 从 1 变为 0；随后快档仍为 11.25 ms、latency 4。**进入实验慢档前，系统已经获准睡眠。**
- 原生调频在约 24 秒开始从 160 MHz 降频，约 34 秒已处于 24 MHz；强制低频直到约 133 秒 PA4 关闭后才启用。**低频并不必然依赖实验强锁，优先消除虚假算力需求。**
- PA4 安全关闭后慢档实际生效；两次相隔约 30 秒的睡眠进入/退出计数均从 2877 增至 3139，期间 `links=1`、`block=0`。这证明连接态发生睡眠，不直接表示睡眠时长或占比。
- 约六分钟日志未见断连、断言或异常复位；只证明本次短时静置，没有证明低功耗后的业务恢复或所有手机行为。

**大幅下降已出现在慢参数和强制低频之前，但仍属于多项改动的组合结果。** 不能从该次组合反推出门禁、接收任务与 USB 检测的独立贡献；正式分阶段收益另见第 1 节。实验中 2.5 到 1.5 mA 同时涉及 PA4、参数和时钟策略，不能全部归给慢参数。纯 RDX 未就绪的 HOGP 原本应停表，不能把实验收益归给停用 HOGP。PA4/PE5 关闭也不能证明片内模拟与板级损耗为零。

### 3.3 连接态触底探针（2026-10-29，实验包）

冻结分支：`freeze/conn-probe-20261029`（触底包 `KEEP=0x00`、`PARAM=2` 及两份对照日志）；业务分支 `不加HFP` 不混入探针代码，逐项回退只在冻结分支上进行。

目的：在当前正式业务代码上，单 ACL、第二入口已关窗、PA4/PE5 已关的稳定待机中，暂停全部项目业务周期源及可停的软件唤醒源，量出连接态电流下限，再逐项回退做归因。JL 原生定时器不在本轮范围，留作下一阶段。

**实现与开关**（只在 `t2620_project_config.h` 配置，正常业务构建必须 `TCFG_T2620_CONN_PROBE_ENABLE=0`）：

| 配置 | 含义 |
|---|---|
| `TCFG_T2620_CONN_PROBE_KEEP` | 置位项保持原样，其余暂停；`0` 为完整触底。`0x01` 串口、`0x02` USB 检测、`0x04` 电池采样、`0x08` 按键扫描、`0x10` 动态调频（否则锁 24 MHz）、`0x20` 项目业务周期源（RTC 3 min 落盘、拨码 100 ms 守护、HOGP 键盘就绪后 10 ms 服务） |

- 准入：无关机流程、`links=1`、睡眠门禁已放行、PA4 已 OFF、PE5 关、无业务占用、无充电、USB 为 IDLE/DISCONN、可读到链路参数；不满足时打印 `[CONN_PROBE] waiting: <原因>`，原因变化才打印。

每档测量：`floor ready` 后拔串口读关窗待机电流，日志核对 `if/lat` 是否被手机接受；随后在 APP 操作列表、录音开始/停止，记录首条与连续指令体感。未加本地门控时连续指令也按该档变慢，属预期；iOS 需另限 latency ≤30、interval ≥15 ms。

**LAT49 实测（2026-10-29，`COM3_2026-10-29_19-45-02.log`）**：手机给出 if=10（12.5 ms）、lat=49，请求后约 340 ms 生效，有效监听间隔约 625 ms；关窗待机 0.6–1.3 mA，与触底档 2 持平；无本地门控时 APP 操作延迟仍可接受。原因是 latency 只限制从机监听，参数协商本身不涉及 interval，手机接受很快，不会重现 18.8 s 的慢回快。该档设为空闲参数候选。此包 KEEP=0x3e 在 `floor ready` 后关闭了 UART，日志看不到之后的活动时序。

**本地 latency 门控（实验包，2026-10-29）**：新增 `rdx_conn_gate.c`，开关 `TCFG_T2620_CONN_LATENCY_GATE_ENABLE`（默认 1），保持时长 `TCFG_T2620_CONN_ACTIVE_HOLD_MS`（默认 2000）。手机 ATT 写入、RDX/OTA 通知、HID 报告成功后，在空闲到活跃的边沿投递 app_core 执行 `ble_op_latency_skip(con, 0xffff)`；最后一次活动后静默满 HOLD 再 `ble_op_latency_skip(con, 0)` 恢复 latency，活跃期间每次续期都重发 skip，防止计数耗尽；断链时释放槽位。门控只改本端监听，不发起协商。**结论：不采用**——无门控的 LAT49 包响应已可接受，门控只缩短手机下行首包等待，不改变待机电流，徒增状态与竞态面；代码只保留在冻结分支。日志：`[RDX_CONN_GATE] active con= src= t=` / `idle con= t= held= events=`，`[RDX_CONN_POLICY] request` 与 `[RDX_BLE_PARAM] initial/update` 同步带 `t=`（ms）。测试包 KEEP=0x3f，保留 UART，便于核对切换时序；读电流时串口板的影响需单独评估。

**LAT49 + 本地门控实测（2026-10-29，`COM3_2026-10-29_20-06-51.log`，Android）**：关窗待机仍为 0.6–1.3 mA，APP 指令延迟可接受；KEEP=0x3f 保留 UART 后电流无可见变化，sample1 唤醒 72 次/10 s，与关 UART 的 LAT49 包一致。时序：
- 探针请求 `{6,12,49}` 后 360 ms 生效（if=10、lat=49）。
- 首条指令到达即 `active`（`src=rx`），录音 11 s 期间保持全监听（events=491），最后一次活动后 2 s `idle`，`ret` 均为 0。
- 录音结束时手机自行改为 30 ms/lat 0（无本端请求，推测为 APP 切换连接优先级），协调器随即重请求，280 ms 后回到 lat=49。
- 录音开始时 APP 在 1 s 内重发两次 `record#1`：设备先播提示音约 0.8 s 才回复，重发早于门控生效后的应答，属业务应答时序，与连接参数无关。

结论：快档 interval + latency 49 在 0.6–1.3 mA 下响应可接受，作为正式常驻参数（第 2.4 节），不带门控；待补测文件下载吞吐、OTA 上传、iOS 参数和 PC HID 场景。

测量统一在 `floor ready` 后拔掉串口板读数，并记录 `sample2` 的 `delta`。回退结果已决定正式方案：连接参数占主导，但不需要“空闲进慢档、业务前回快档”的参数状态机——保持快档 interval、只加大 latency 即可同时满足电流与响应，见第 2.4 节。

## 4. 从正式基线重新实施

### 4.1 按收益优先级实施

当前采用 **快连接参数 + JL 原生动态调频 + 接收任务事件化 + 安全允许系统睡眠**，单 RDX 核心路径已实测关窗后约 2 mA。第 4.2 节的有限窗口与列表唤醒重开已验证，但完整功能组合仍待回归，不承诺复现实验版的 1.5 mA。

当前分支不再采用“保留整包实验、逐个关闭开关”的方式。从 `de557688` 独立实施第 2.5 节并提交为 `632ddc0b`，再单独实施第二入口窗口；既有 PE5、PA4、DUT、DIP/CDC、快档协调和双 ACL 保护全部保留，HOGP 正常服务、USB 原生检测不变。

**先处理阻止原生降频和睡眠的机制，再处理残余唤醒；按目标场景的预期收益、证据强度及功能代价确定起始顺序，每轮用实测重新排序。** 接收事件化与第二入口窗口均已取得阶段收益，但缓存和 USB 检测尚无独立 mA 排名，不能虚构数值，也不能仅凭定时器周期短就认定收益大。

| 优先级与场景 | 动作 | 收益依据与实施边界 |
|---|---|---|
| 1，共用路径，单 RDX 主路径已测，完整回归待完成 | 接收任务事件驱动，取消空超时及空闲拉频 | 消除每秒空等待重置原生 10 秒调频观察窗口的问题；首次及业务后均降至 24 MHz，连接 PA4 开/关约 5/4 mA。保留真实业务算力、入队通知、连续消费及退出/重连收尾，观察器归属 `app_core`；不同时修改参数、入口、HOGP 或 USB |
| 2，单 ACL，已提交 `471dd462` | 第二入口开放 120 秒，到期关闭；真实业务退出待机时再开放 120 秒 | 本次入口开放/关窗待机约 4/2 mA；两次关窗、睡眠、列表重开及不续期已验证。保留正常拓扑门禁及断言，异常状态更保守；HID、持续业务、边缘竞态及完整回归待完成 |
| 3，纯 RDX 残余唤醒，缓存作为基础设施保留 | 单独实施 RDX 缓存按需保存，USB 保持原生 | RDX 库原有 5 秒空检查；现改为干净停表、脏缓存限期保存，板测仍约 4/2 mA，新增收益未量化，写入持久化待验收，见第 4.6 节。USB 默认 250 ms 检测未改；不能把周期或回调减少直接换算成电流收益 |
| 独立场景，HID ready，2026-11-06 已实施 | 输入服务事件化 | 原 HID ready 即常驻 10 ms 周期服务，是复合会话关窗后无法睡眠、约 3 mA 的主因；现只在报告在途或欠发松开时运行重试定时器，复合会话静置降至 1 mA 以下，见第 2.7 节。保留首键、松键、按住与背压恢复 |
| 不列入正式实施 | 强制 24 MHz、重新采用实验慢参数、停用 HID | 原生已能自行降至 24 MHz；旧慢参数收益小且损害交互，新实验慢档未验收响应。保留快参数和业务算力，不靠取消功能追求电流数字 |

第 1 步先实施是因为机制明确且无需改变产品能力，不代表已证明其收益大于第 2 步。上一阶段 CPU 已降至 24 MHz，但第二入口仍阻止系统睡眠；本轮经关闭确认后恢复了睡眠流程。两项分别解决“无意义高频需求”和“睡眠资格”，不能互相替代，也不能把与实验版的电流差值全部归给门禁。接收改动影响共用路径，不能只优化无连接状态或把空轮询转移到连接后。

第 2 项接入体验取舍及核心路径收益已确认并提交。用户随后明确要求开启下一项，故只推进业务侧缓存，不同时推进 USB 或 HOGP；此选择不表示第 2 项录音/下载、HID/双 ACL、重复循环与长稳缺口已经通过。若快参数和原生调频下已达到电流、响应目标，或缓存增量无可重复收益，应停止扩大修改范围，不为清空定时器列表继续冒险。

需要拆分实验贡献时，备份版只用于隔离对照，任一 A/B 配对只改变一个机制并固定其余条件；接收旧等待策略的对照必须使用原生调频，避免强制 24 MHz 掩盖空超时拉频。连续阶段的收益只相对于各自上一版成立，受调频与睡眠耦合影响，不能直接相加或倒推出单项固定收益。对照改动不整包带回当前分支，也不以实验功能牺牲作为正式默认值。

CDC 无有效 USB/DTR 时已停表，有效会话内服务不计入本轮基线。业务与 JL 原生定时器盘点继续引用 [6-0](6-0.T2620外设低功耗与共享VDD电源管理设计.md)，不再重复建设。

### 4.2 历史策略：120 秒窗口，业务退出待机时重开（已由 4.2.1 取代）

> 本节保留 `471dd462` 阶段“到期关闭入口”的已板测证据与关闭保护设计，**不再是当前策略**。当前行为见第 4.2.1 节：单 ACL 入口常开，120 秒后只降速不关闭。下表中“到期关闭”“窗口已关闭”等状态只用于解释历史测量与仍保留的关闭确认机制。

**该阶段已实现且单 RDX 核心路径板测通过：一条物理连接、一个广播时，第二入口只开放 120 秒；到期关闭，直到连接态因真实业务退出待机时，再开放一轮 120 秒。** 不增加专用配对按键或新 APP 指令，不改变现有按键、录音和 HID 操作含义。窗口关闭后，第二台设备不能仅靠自身连接尝试唤醒本机；需要本机或已连接端先触发真实业务。各场景验收状态见第 4.4 节。

| 实际拓扑（当前策略） | 休眠门禁 |
|---|---|
| 零 ACL | 允许睡眠 |
| 一条 ACL，第二入口未开放（复合会话满占等抑制状态） | 允许睡眠 |
| 一条 ACL，第二入口准备开启，或广播关闭/重开在途 | 阻止睡眠（仅覆盖在途事务） |
| 一条 ACL，第二入口 100 ms 快广播稳定开启 | 允许睡眠（2026-11-09 起） |
| 一条 ACL，第二入口 500 ms 慢广播稳定开启 | 允许睡眠；单连接低功耗时万用表实测整机 0.5–2.2 mA 跳动，未按广播档位分别记录或积分 |
| 两条 ACL | 阻止睡眠 |
| 广播控制结果无法确认，故障锁定 | 保留保护至重启，包括退回零 ACL |

“允许”只表示本门禁不阻止，实际睡眠仍须满足其他框架条件。

门禁用于规避闭源 controller 的双 ACL 低功耗断言。当前只在双 ACL、广播关闭/重开在途和故障锁定时阻止睡眠；**单 ACL 的快档与慢档都不再是常驻门禁**。因此 3 mA 的旧读数来自“入口开放即不睡”，不是 500 ms 广播本身；放开后仍可能在第二台设备接入的瞬间触碰 controller 低功耗计数。2026-11-09 两轮共 3 次“睡眠中接入”均未触发断言或异常复位（业务唤醒切快档另有 1 次 `timer_no_response`）；第二轮已覆盖快档睡眠轨迹、慢档重复接入和 2→1 回升，绑定重连与长稳仍未覆盖。详情见 [双 ACL 低功耗断言复盘](3-5.BLE双ACL低功耗断言问题复盘与量产最佳实践.md)。常开入口**不是 controller 修复，也不是双连接功耗达标**；不得删除双 ACL/在途/故障保护、屏蔽断言、强制断开已有连接或周期性重开广播。

| 场景（历史窗口策略） | 已实现的策略，完整硬件矩阵待完成 |
|---|---|
| 零 ACL | 保持原有快/慢广播和自动接入，不套用第二入口期限 |
| 首条 ACL 建立 | 正常产品状态允许广播时，给第二台设备一次 120 秒接入机会；到期仍为单连接就关闭空闲入口，保持已有连接和业务 |
| 单 ACL，窗口已关闭 | 不接纳新的物理连接；确认安全关闭后才释放本门禁，其他框架条件仍决定能否实际睡眠 |
| 真实业务使连接态退出待机 | 若仍为单连接且允许广播，先建立休眠保护，再开放第二入口并开始新一轮 120 秒窗口；不阻塞原业务等待广播完成 |
| 窗口内持续操作 | 不续期；重复通知、持续录音/下载、按住及重复键报告不能让入口永久开放 |
| 两条 ACL / 退回单 ACL | 双连接不广播并保留保护；其中一条断开后给一次 120 秒重连窗口，全部断开回到零连接策略 |

**“退出低功耗”是业务待机到业务活跃的转换，不是 CPU 每次睡醒。** 结合真实业务占用与收尾状态判断，不以广播已关闭、PA4 电平或某次睡眠回调代替。窗口到期时若业务仍在进行，照常关闭入口；同一业务的后续数据不会立即将其重开，须待业务收尾、重新待机后，由下一次真实业务唤醒。

| 事件 | 是否触发待机后的重开 |
|---|---|
| 用户录音、播放、列表/文件访问等真实业务；去抖后的有效物理按键 | 是，每次待机退出只受理一次；按键原有功能继续执行，不吞首键或松键 |
| 只有 PC/HID 在线时的真实按键 | 是，不要求手机先连接或发送 RDX 命令；不因纯 HID 操作而要求 PA4 上电 |
| BLE 连接事件、CPU 睡眠退出、系统定时器、空队列/缓存空检查、电池检查 | 否，维持连接或框架运行不等于用户业务 |
| 后台心跳、版本/电量查询、重复状态通知 | 否，不能靠 APP 轮询持续开放入口 |
| 广播开启、为广播恢复外设、相应的电源/灯效状态通知 | 否，不能形成“开广播 -> 恢复外设 -> 再判活动 -> 重计时”的自激循环 |

120 秒是**接入期限**，不是 PA4 的连续空闲期限；两者独立判定和计时，复用已有事件基础设施而不互相重置。同一 ACL 上的 RDX/HID 复合服务不占第二条物理连接；关闭广播不释放 owner、订阅、加密或绑定。现有零连接快广播恢复入口不直接改作单连接业务唤醒入口，五击恢复出厂等手势含义不变。关机、DUT、USB 所有权等已有广播抑制条件优先，唤醒不得绕过。

**广播关闭不能相信软件缓存：** 实施前存在关闭失败后清空跟踪句柄、开启后才建立保护的边界；SDK 状态查询可能先清状态、后返回关闭失败。本次把所有入口重开/刷新收敛到 `rdx_ble_entry.c` 的 `app_core` 协调器，开放前先保护，关闭保留 wrapper/广播句柄，等待明确完成后才放行。正常单次窗口只保留必要超时，队列失败复用已有优先级 0 恢复桥接，不新增常驻系统轮询。

控制器关闭分两阶段：先通过公开 `ll_hci_cmd_to_task` 提交 `0x2039` 停指定广播集、`0x203c` 移除，收到后者 Command Complete 的 `0` 或 `0x42`（集合已不存在）才清理 SDK 软件状态；随后再等一次 `0x203c` 完成，确保 SDK 清理时提交的复用缓冲命令已经消费，才允许重开或释放保护。每阶段超时为 1 秒；仅主 wrapper 消费完成事件，命令使用稳定缓冲。当前 SDK 公共广播句柄为零基编号，`0xff` 表示无句柄；测试固定两份库哈希，升级必须重新审阅该 ABI。本次不修改 controller 库或断言。

异常、超时或无法确认的开启失败进入保守锁定：不接受迟到完成作为恢复，不再开放广播，并阻止系统睡眠（即使已退回零 ACL），直到整机重启。尚未提交开启时的准入取消不属于该故障。关闭期间刚好建链时按真实已接纳连接处理，不以消失的广播句柄误判失败。

退出先停协调器并作废旧任务/超时，再在 `app_core` 有界等待上述关闭过程，最后释放 wrapper；等待期间不建立新会话或重连任务。正常退出可以重新初始化；未确认退出保留命令缓冲及故障，不能靠重新初始化抹掉。SDK 调用本身的耗时仍需板测，既有独立关机复位保护保留。

本阶段从 `632ddc0b` 独立实施，只改变第二入口策略与必要安全边界，不夹带慢参数、强制低频或 USB/HOGP 周期调整。本轮入口开放约 4 mA、关窗待机约 2 mA 的阶段收益已锁定，列表恢复与 120 秒重开已验证；严格固定 PA4 等状态的单机制 A/B 仍未完成，不承诺复现实验版的 1.5 mA。如果未来又要求第二设备始终自动接入，仍须推进 JL controller 修复，不能删除保护。

### 4.2.1 当前策略：单连接第二入口快广播常开（2026-11-11）

单 ACL 且入口未被复合会话占满时，空闲 wrapper 的第二入口**固定 100 ms 快广播（interval 160）常开**，不再做快慢切换：

- 取消 120 秒到期转 500 ms 慢广播，取消慢档业务唤醒回升快档，不再挂 120 秒 deadline 定时器。`rdx_ble_entry_adv_slow()` 保留接口，恒返回 0。
- 原因：第二入口转 500 ms 慢广播后，第二台设备可能搜索不到或发现很慢；而快广播稳定期不占睡眠门禁，用户实测常开快广播入睡后电流影响不大，没有必要为此维护快慢状态机。
- 不变：睡眠门禁（单 ACL 稳定广播放行；双 ACL、广播关闭/重开在途、故障锁定仍阻止睡眠）；同一 ACL 已同时持有 HID 和 RDX 时关闭入口，`rdxclose` 释放后重开；2→1 重开入口；零 ACL 的未连接慢广播策略（`rdx_adv_policy.c`）；连接参数 `{6,12,49,600}`；PA4 连接态空闲关断。
- 附带效果：不再有按键触发的慢转快重开广播，原先 `input_service` 的 `timer_no_response` 告警来源随之消失。
- 预期日志：单 ACL 期间 `[BLE_ENTRY] open` / `[RDX_BLE_LP]` 一直是 `adv_interval=160`，不再出现 `second entry slow adv`、`business wake fast adv`；睡眠标记持续出现。
- 验证状态：`COM3_2026-11-11_11-27-02.log`（单 PC HID → 复合 HID+RDX → `rdxclose` → 再复合）：单 HID 期间入口以 `adv_interval=160` 开放并持续睡眠；复合会话关入口（`close confirmed status=0x42`）后睡眠；`rdxclose` 后入口以 160 重开，持续 128 秒以上仍为 160、无转慢日志且持续睡眠；PA4 正常关断/恢复；无断言、watchdog、复位或 `timer_no_response`。用户实测电流影响不大（未积分）。用户随后板测确认：单 PC HID 进入低功耗后，手机 RDX 可通过常开快广播接入第二 ACL（未提供日志文件名）。绑定重连与长稳尚未专门复测。

#### 历史：快慢档切换（2026-11-09 至 2026-11-11，已由上述策略取代）

以下为快慢档策略的设计与板测记录，保留作证据，不再代表当前行为。


按客户接受“入口常开带来的慢广播增量”的要求，第二入口改为**固定策略**，不再提供 `TCFG_T2620_BLE_SECOND_ENTRY_ALWAYS` / `TCFG_T2620_BLE_SECOND_ENTRY_SLEEP` 编译开关。

| 状态 | 单 ACL 第二入口行为 |
|---|---|
| 首条 ACL 建立（或 2→1、或 `rdxclose` 释放后） | 重新从 100 ms 快广播开始，计 120 秒 |
| 快档期间 | 保持 100 ms 快广播；快档内的业务活动**不续期** |
| 满 120 秒 | 经“关闭确认后重开”切到 500 ms 慢广播；除切换瞬间及既有抑制、故障条件外，入口继续开放 |
| 慢档期间出现真实业务唤醒 | 回升一轮 100 ms 快广播并重新计 120 秒；同一业务突发只触发一次，到期后回慢档 |
| 慢档静置 | 无期限、无周期定时器；系统可正常睡眠 |

120 秒是**快广播期限**，不等同于 PA4 连续空闲或 CPU 真正进入睡眠的时刻。快档内活动不续期，即使持续业务跨过期限也会转慢；同一业务仍在进行时，其后续数据不再触发回升，需业务收尾后再次唤醒。系统也可能在快档就睡眠，不会因某一次 CPU 睡醒或入睡而切换广播。

**睡眠门禁只按真实拓扑和事务状态判定，不再看广播速率：**

| 条件 | `system_sleep_block` |
|---|---|
| 单 ACL，入口快档稳定开启 | 0（允许睡眠） |
| 单 ACL，入口慢档稳定开启 | 0（允许睡眠；已板测） |
| 单 ACL，入口未开放（复合会话满占等抑制） | 0 |
| 单 ACL，广播准备/关闭/重开在途（`g_rdx_ble_adv_setup` 或关闭等待） | 1 |
| 双 ACL | 1 |
| 广播控制故障锁定 | 1，直到重启 |

保留边界（不因取消单 ACL 门禁而放宽）：

- 两条 ACL、HID+RDX 复合会话满占同一 ACL、DUT/关机/USB 所有权等既有抑制条件仍优先，入口照常关闭后再按各自规则恢复。复合会话仍遵循 [3-6](3-6.BLE复合会话满占时第二入口广播控制方案.md)：此时第二台设备拿不到已占用的 HID/RDX owner，继续广播只会误导对端。
- 睡眠门禁只保留双 ACL、广播关闭/重开在途和故障锁定三项；单 ACL 的快档与慢档都不再阻止睡眠。关闭广播仍须 controller 明确确认，无法确认的故障继续锁定到重启。
- 业务唤醒不再影响入口开关（单 ACL 时入口本就常开），但慢档期间的一次真实业务唤醒会把广播拉回 100 ms 快档并重新计满 120 秒：业务消息（录音/播放控制等 `APP_MSG_*` 路径）和 5 个产品键按下会调用 `rdx_ble_entry_activity()`，普通 PC 键盘敲击不经过该入口。快档内的后续活动不续期，到期后重新回 500 ms 慢档，避免持续 100 ms 功耗；每次活动突发最多换一轮窗口。`rdxclose` 的 FIFO/worker 释放、READY 交接和失败退避路径不变。
- 快→慢沿用现有“关闭确认后重开”的刷新路径：先按两阶段确认停广播，再以 500 ms 重开；期间若有第二台设备接入，按广播已被连接消耗处理，不误判故障。关闭失败、超时等异常仍进入原有保守锁定，不以慢广播绕过保护。门禁只在关闭、清理和重开提交期间保持阻止，重开成功即恢复为单 ACL 允许睡眠。
- DUT、PC/USB 所有权、关机等状态仍可关闭入口；恢复时按真实拓扑重新判定，不因取消单 ACL 门禁绕过保护。
- 快档期限定时器创建失败时尝试提前切到慢档并有限重试；切换仍依赖关闭确认。广播事务超时或结果不确定则锁定保护，不能保证异常状态下入口持续可见。若关闭在途且超时定时器也创建失败，保护保持阻止睡眠，须靠完成事件、后续服务或退出路径继续处理，不能声称此时仍有定时超时保证。

**主场景是 PC HID + PC RDX，二者共用同一条 ACL（复合会话）**：只有一条连接，可以正常睡眠，静置降至 1 mA 以下（第 2.7 节）；复合会话期间第二入口按 3-6 关闭。PC HID + 手机 RDX 是两条 ACL 的次要拓扑：PC 自动回连后只有 HID owner，入口保持开放，手机可通过第二条 ACL 认领 RDX；手机断开或退出后按 2→1 重开。

**双 ACL 不睡眠是有意的保护，不是缺陷，暂不处理。** 两条 ACL 同时在线时，`rdx_ble_dual_acl_lp_target` 门禁保持 `system_sleep_block=1`。原因是杰理预编译 controller 在双 ACL 睡眠时会触发 `bb_le_power.c:352` 断言，随后看门狗复位（[3-5](3-5.BLE双ACL低功耗断言问题复盘与量产最佳实践.md)）。因此 PC HID + 手机 RDX 期间即使 PA4 已关，电流也降不下来：2026-11-11 日志中两段双 ACL（`00:11:53`–`00:16:14`、`00:22:54`–`00:25:21`）没有任何 `S<>w` 睡眠标记，PA4 照常关断。当年只验证过“第二条连接建立后很快断言”，双 ACL 稳定后能否睡眠从未测试；这需要杰理修正版 controller 或专项长稳实验，按产品优先级暂不投入。入口常开的增量功耗只发生在单 ACL 阶段，不会叠加到双 ACL 上。0.5–2.2 mA 是新策略单连接低功耗时的整机跳动范围（尖峰 2.2 mA，目测粗估约 1 mA），不是广播增量，快慢档未分别记录；快档睡眠已见 `S<>w[]`，绑定重连与长稳仍待板测。

### 4.3 BLE 与系统低功耗的职责

BLE 不使用 EDR `sniff.c` 的模式。BLE 连接事件之间由 controller 和系统低功耗框架协同睡眠，连接参数决定射频活动机会，系统忙票和软件活动决定能否充分利用空隙。

`ble_op_conn_param_request()` 是参数协商；`ble_op_latency_skip()`（`ll_vendor_latency_hold_cnt`）等是本地 latency 控制接口，不是绕过忙票的强制睡眠 API。冻结分支门控实验已验证 `ble_op_latency_skip(con, 0xffff/0)` 在 `app_core` 调用返回 0 且行为符合预期，但正式方案不使用。正式策略优先恢复框架正常工作，不额外寻找“强睡眠”捷径。

### 4.5 每阶段按实际收益决定去留

- 对照必须使用同一硬件、供电、手机、ACL/HID 状态、实际连接参数、业务和日志配置。分别记录 PA4 开、关且状态稳定后的平均电流；源码基线应重新构建烧录，不能拿仍在设备上的实验固件当基线。

### 4.6 RDX 缓存按需保存：作为基础设施保留

用户在 `471dd462` 提交后明确要求直接开启下一项。本阶段只处理业务侧缓存，保留上一阶段全部待测项。2026-10-19 用户复测入口开放约 4 mA、关窗待机约 2 mA，未观察到可区分的新增电流收益；作为按需调度基础设施保留，不称为新增降耗成果，写入持久化及完整回归仍待验收。

| 对象 | 来源及原有行为 | 本阶段选择 |
|---|---|---|
| DAT 文件缓存检查 | 第三方 RDX `librdxApp.a` 的 `rdx_uxfile_flush_cache_timer_cb`，不是 JL 原生业务；初始化 10 秒后首次执行，随后每 5 秒自续约，即使无脏数据 | 改为脏位变化通知驱动，不修改 JL 定时器实现 |
| USB 热插拔检测 | JL 原生 OTG，`usb_common_def.h` 的 `TCFG_OTG_DET_INTERVAL=250` 经 `usb_task.c` 传入 OTG 驱动；转换期还可能采用 50 ms | 保持不变，不混同于项目 CDC 会话服务 |
| 定时器 API | 两者都使用 JL 提供的调度设施；调用 JL API 不代表调用者的业务逻辑属于 JL 原生 | 按职责区分来源，不按 `SDK/` 目录或 API 名称归类 |

实施边界：

- `rdx_cache_flush.c` 只在 `app_core` 管理一次性超时；干净态不创建缓存定时器，状态通知本身不恢复 PA4、不登记业务、不重开第二入口。
- 补丁覆盖实际链接库全部 14 处 dirty 写入，包括置脏、同步保存、加载及显式格式化后的清除；处理到首次脏通知后安排 5 秒期限，重复修改不延后，先被同步保存则取消待办。未修改原有同步保存、下载快照、文件格式或存储屏障。
- 到期保存仍检查文件服务、PC 归还、重建、缓存加载、quiet 及 IO 故障；先登记被动准入，再获取 DAT 互斥锁，锁内复检。获取锁最多等待 1 个 OS tick（当前为 10 ms），超时不保存，不无限阻塞主任务；实际文件 IO 的耗时仍由原有存储实现决定。
- 仅有真实脏缓存且准入/互斥暂忙时按 500 ms 重试；保存成功即停表。真实 IO 失败保持原有错误锁存及脏位，停止自动重试，不以清脏掩盖错误，也不绕过 PA4 卸载保护。
- 消息/定时器分配失败保留待办并复用既有 DIP 优先级 0 桥接，不新建常驻兜底轮询。退出停止调度并作废旧任务/超时，重新初始化重新检查库的真实状态；不会因为停调度而清除脏数据。
- 从已校验原库执行 `patch_librdxApp.ps1`，新增 `patch_librdxApp_cache.ps1` 和 `rdx_cache_patch.ll`；原有存储/恢复/协议补丁继续应用。提交时补丁脚本、实际链接的 `librdxApp_patched.a`、源码和测试必须一起更新，不能只改脚本而链接旧库。

验证分为调度器和实际库两层：`test_cache_flush.py` 覆盖空闲停表、固定期限、同步清除、暂忙/故障、队列及定时器失败、退出重入、旧回调和回绕；`test_record_format.py` 内执行实际库准入、脏位通知、有界锁及失败保留测试。主机框架增至 20 项；真实 SDK 并发、SD 耐久性、插拔与电流仍须板测。

## 5. 必须保留的踩坑经验

| 问题 | 处理原则 |
|---|---|
| 外设已关，连接态仍约 6 mA | 先检查睡眠门禁、真实频率和唤醒源；PA4/PE5 OFF 不等于整机已睡眠，单连接也不等于没有第二 ACL 风险窗口 |
| 广播状态为 0 就认为可以睡眠 | SDK 查询的是软件缓存，关闭失败后不能清掉保护，也不能只靠重复查询认定恢复；开放前先保护，广播句柄仍须保留正确的在途连接事件归属 |
| 把 CPU 睡醒或 PA4 恢复当作业务唤醒 | 入口单 ACL 常开，业务唤醒只负责把慢档回升快档；连接事件、后台查询、广播自身恢复通知、CPU 睡醒与 PA4 恢复都不回升、不续期，纯 HID 按键不依赖 PA4 |
| 每秒空等待持续拉高频率 | `clock_refurbish()` 会拉高 CPU 并重置原生 10 秒调频观察窗口，不是无副作用的空查询；任务超时也算周期活动，不能只搜索定时器 |
| 首次降频成功，业务后却不再降频 | 原生观察器停止后，工作任务再次提频可能把新定时器建到自己名下；阻塞式工作任务不会分发定时消息。观察回调固定归属 `app_core`，测试必须包含“停表后业务唤醒，再次降频”，不能只测开机后的第一次静置 |
| 空闲期限反复重置 | 缓存空检查、版本/电量查询及重复通知不等于存储业务；通知幂等，恢复完成后重新评估，不把恢复中的旧状态当作最终状态 |
| 队列尚有业务却断电 | 占用覆盖准入、队列、持久句柄、在途 IO 和收尾；失败也成对释放。USB/VBUS、充电及 OTG 一起判断，充满不能当作拔线 |
| PA4 恢复后大量 `timer_no_response` | RGB 初始化在协议任务创建了不被该任务分发的 20 ms 定时器；不是大量任务都卡死。硬件默认 OFF，灯效交给 `app_core` 按需调度，不能把同步存储恢复搬到主任务后持锁等待 |
| 去掉 tick 后丢事件或停不下来 | 补齐真实业务通知、期限和旧回调隔离；队列失败复用已有恢复桥接，不新增常驻高频兜底；优先级 0 定时器只有系统能睡眠时才有延后机会 |
| 关闭慢档开关却仍刷新协商预算 | 实验待机切换曾无条件重置重试次数；仅关慢档宏仍会残留此行为。整包实验已撤回，后续保持参数目标与 PA4 状态解耦，不为相同目标反复开启新预算 |
| 组合实验通过就认为分项也通过 | 全开/全关覆盖不了混合配置；强制低频还可能掩盖空超时拉频。独立对照并补测试，正式代码不保留整包实验开关等待将来清理 |
| 异步日志触发 MMU 异常 | `Q_CALLBACK` 必须完整投递函数、参数描述和实参，不能依赖消息缓冲清零；回归覆盖残留消息标志，不只直接调用回调。此问题不同于 controller 低功耗断言 |
| 慢参数下首个业务卡顿 | 旧慢档允许的空闲监听间隔达 1.8 秒，命令收到后快档实际恢复又曾约需 19 秒；不能只靠“收到命令再切快”，也不能误拒手机采用的可用快档 |
| 照搬参考分支或强关模拟 | 复用现有共享域管理和完成事件，不带回忙时每秒复检；强关 DAC 模拟曾影响 MIC，保留 JL 音频资源管理。库补丁通过当前脚本可重复生成，不替换成来源不明的旧二进制 |
| 只看 latency 上限判定“已达标” | 原快档判定 latency≤4；改为常驻高 latency 后必须判等，否则现有 lat 4 链路被视为达标、不再请求，手机自行改回 lat 0 后也不会恢复 |
| 用快慢档切换换功耗 | 改 interval 需手机重新调度，曾约 18.8 s 才生效；只改 latency 由从机提出，手机数百毫秒接受，且空闲唤醒同样下降 |
| 诊断自身影响测量 | 使用少量状态快照，不新增高频打印；用匹配 ELF 定位问题，比较睡眠计数增量而非累计非零值，记录实际参数而非只看请求返回成功 |
| 门禁已放行、PA4 已关，仍完全没有 `<>` | 先找常驻 `sys_timer`：它会唤醒系统，周期短于睡眠门槛就等于禁睡。HOGP 就绪即 10 ms 周期正是复合会话约 3 mA 的原因；先用临时加长周期做 A/B 确认，再改为事件驱动，只在真正需要重试时计时 |
| 探针结论外推到未覆盖的场景 | 第 3.3 节探针在手机场景测得 HOGP 周期源“约为 0”，因为 HID 未就绪时本就停表；换到 PC HID 场景必须重新确认唤醒源 |

旧慢参数卡顿依据为 `COM3_2026-10-17_15-18-34.log`。其中 PA4 恢复约 150 ms，快档协商明显滞后；没有 APP 点击时间，不能精确归因首包延迟，也不能区分手机调度与 controller 内部原因。本次 100 ms、latency 9 的实验档仍允许较长空闲间隔，静置功耗通过不能代替交互验证。
