# T2620 BLE 连接待机低功耗设计

> 整理日期：2026-11-16。本文以当前业务代码为准：第 1 节概述方案演进与阶段收益，第 2–4 节说明现行方案，第 4.4 节列出板测状态和缺口，第 6 节给出 Windows 构建与测试方法。
>
> 适用平台为杰理 AC701N / BR28 和本项目的 Windows JL 工具链。本文中的电流均来自对应阶段的用户板测，不是主机测试推算值，也不是统一条件下的量产指标。未连接低功耗及 LRC 见 [6-0](6-0.T2620外设低功耗与共享VDD电源管理设计.md)，功放设计见 [6-1](6-1.通用功放低功耗设计.md)。

## 1. 方案演进与阶段收益

目标是在保持连接及正常业务能力的前提下，让单 ACL 空闲时能够降频、关闭不需要的外设并进入系统睡眠。方案经历了以下阶段；各行的供电、连接、广播和外设状态并不完全相同，**不能相加或直接视为同条件 A/B**。

| 阶段 | 措施与结论 | 当时的用户实测及边界 |
|---|---|---|
| 初始与外围电源 | PE5 跟随实际音频输出；PA4 在连接空闲满足安全条件后关闭 | 初始约 16 mA；PE5 优化后约 7 mA；随后 PA4 开/关约 7/6 mA |
| 接收与调频事件化 | RDX 接收空闲阻塞，避免空等待反复提频；原生时钟观察回调固定由 `app_core` 调度 | 单 RDX 时 PA4 开/关约 5/4 mA；是该阶段的组合结果 |
| 第二入口有限窗口 | 单 ACL 入口开放 120 秒后关闭，真实业务唤醒后重开；关闭确认后允许睡眠 | 入口开放约 4 mA、关窗待机约 2 mA；阶段性单 RDX 核心路径通过，见第 1.1 节。**该入口策略已废弃** |
| RDX 缓存按需保存 | 干净态停表，脏缓存按固定期限保存 | 复测仍约 4/2 mA，新增电流收益未量化；作为基础设施保留，持久化闭环待验收 |
| 快 interval + 高 latency | 触底实验表明连接参数是该工况下的可见主因；正式采用快 interval 和 latency 49，不采用本地 latency 门控 | Android 单 RDX、历史关窗待机约 1.0–1.5 → 0.6–1.3 mA；列表和录音交互当时可接受。探针及归因边界见第 3 节 |
| HOGP 输入事件化 | HID ready 空闲不再常驻 10 ms 系统定时器，只在报告在途或欠发松开时重试 | Windows PC HID + PC RDX 复合会话静置约 3 mA → 1 mA 以下；单 RDX 复测也低于 1 mA，两者精确差值未测，见第 2.7 节 |
| 第二入口常开并放行单 ACL 睡眠 | 先试 100 ms 快广播 120 秒后转 500 ms 慢广播；因慢广播可能导致第二设备搜索不到，2026-11-11 改为固定 100 ms 常开 | 历史快慢档方案用户实测整机 0.5–2.2 mA 波动、目测粗估约 1 mA，未分档或积分；当前常快方案用户观察电流影响不大，未积分。两者都不是射频增量的精确测量 |
| 文件传输睡眠保护 | 2026-11-16 为 BLE 长文件传输和同步增加系统睡眠门禁 | 单 ACL 复合会话的 411 个 `opusfile` 包、约 121.46 秒内无 `S<>`；F19 抢占后约 3 ms 门禁释放。正常下载完成与后续链路长稳仍待验证，见第 4.3.1、4.4 节 |

独立 LRC 业务版的**零 ACL** 慢广播电流曾实测 0.6–1.6 mA 波动，属于 [6-0 第 5 节](6-0.T2620外设低功耗与共享VDD电源管理设计.md) 的独立成果，不直接外推到连接态。

### 1.1 历史有限窗口的板测依据

`COM3_2026-10-19_10-46-46.log` 对应历史提交 `471dd462`：单 RDX 下两次入口到期关闭并确认，之后出现睡眠轨迹；列表业务唤醒后入口重开，窗口内重复查询不续期。第二台手机曾建立物理 ACL，但因首条链路已占用 RDX runtime 而被拒绝接管，随后退回单 ACL。用户确认入口开放约 4 mA、关窗待机约 2 mA。

这是**有限窗口阶段的组合收益和单 RDX 核心路径证据**：PA4 与 DAC 状态也有变化，不能把全部差值归为广播；它不代表 HID、持续录音/下载、双 ACL 或长稳已通过。当前入口行为已改为第 4.2.1 节的常开策略，不能沿用这次“到期关窗”的验收步骤。

## 2. 当前方案：连接与外围电源

### 2.1 场景和基本约束

- BLE 配置支持两条物理 Peripheral ACL、一个共享 GATT 数据库和两个 wrapper；RDX 与 HOGP 可以由不同 ACL 持有，也可以共用同一 ACL 形成复合会话。
- 主要待机场景是 **PC 的 HID 与 PC APP 的 RDX 共用一条 ACL**，已有相关板测的 PC 端为 Windows。单 PC HID、单手机 RDX 是其他单 ACL 场景；PC HID + 手机 RDX 则是两条 ACL。
- 空闲省电不以断开既有 ACL、释放 RDX/HID owner 或改变订阅、加密、绑定为代价。按键、录音、播放和文件访问仍须能正常恢复。
- 本文待机电流的典型条件是电池供电、USB/VBUS 拔出、无录音、播放、文件或其他收尾业务。充满不等于拔线；USB 所有权、充电、OTA、低电保护和关机规则仍须独立满足。
- 单 ACL 允许睡眠不意味着任何时刻都一定睡眠；广播事务、文件业务和其他框架忙票仍可能阻止。两条 ACL 按保护策略禁止系统睡眠，见第 4.1 节。

### 2.2 PE5：功放跟随实际输出

PE5 仅在 **DAC 模拟就绪且数字输出运行**时使能。输出停止后关闭功放，不等待 DAC 模拟资源完全关闭，也不绕过 JL 音频框架强制关闭模拟资源。PE5 与 BLE 连接及 PA4 的关断相互独立；MIC、功放时序和声音质量仍需板测。

### 2.3 PA4：共享 VDD 按业务安全关断

PA4 为 SD NAND 和 RGB 等共享域供电，由 `rdx_peripheral_power.c` 协调。连接态与未连接态分别判断资格，共用安全停用与恢复执行器。

- 至少一条 ACL 在线且 USB/充电/OTG、录音、播放、文件、RGB、DUT、OTA 等占用及存储收尾均满足条件后，才开始连续空闲计时；默认期限为 `TCFG_T2620_CONNECTED_VDD_IDLE_MS=120000`（120 秒）。真实业务或拓扑变化会重新评估，纯版本/电量查询、空检查和重复通知不应伪装成存储业务。
- 关断前确认队列、脏缓存、读句柄、保存/删除及在途 IO 安全，完成 SD 卸载和 RGB/SPI 停用。新业务先登记占用再同步恢复，恢复成功后才访问；停用失败保留供电，恢复失败拒绝访问，不自动格式化。
- PA4 的 120 秒是**外设空闲计时**，与第二入口广播无关。纯 HID 报告不需要为了广播或键盘上报恢复 PA4；真实本地功能或存储业务按需恢复。
- 空闲期限使用单次超时，忙时依赖业务结束事件，不增加每秒轮询。RGB 恢复默认 OFF；OFF/永久常亮不保留灯效周期，动态效果才按需调度。

`[PWR_CONN] reason=FILE_OP` 表示共享 VDD 不能关断，**不代表 CPU 已被禁止睡眠**；BLE 文件传输的系统睡眠保护另见第 4.3.1 节。

### 2.4 每条物理 ACL 使用统一连接参数

每条已连接 ACL 都纳入统一目标 `{6,12,L,600}`，不匹配时发起有限请求，无论其承载 RDX、HID、复合会话，还是尚未认领业务。`L=TCFG_T2620_CONN_SLAVE_LATENCY`，项目默认 49、允许范围 0–49，由 `t2620_project_config.h` 配置。

| 项目 | 当前规则 |
|---|---|
| 请求目标 | interval 6–12，即 7.5–15 ms；latency 默认为 49；监督超时 600，即 6 秒 |
| 达标判断 | 实际 interval 在 6–12 且 latency **等于**目标值；对端可在区间内选择，不要求一定为 7.5 ms |
| 协调方式 | 建链、断链和参数更新事件直接通知 `app_core` 协调器；每条 ACL 独立节流、确认和管理重试，RDX/HID 逻辑切换不刷新同一条链路的预算 |
| 重试边界 | 每轮最多 3 次，至少间隔 2 秒；已达标或耗尽预算后停表，实际达标后再次退化才获得新一轮恢复机会。业务不等待协商完成 |
| 时延取舍 | 例如对端采用 12.5 ms / latency 49，空闲时相邻监听机会可间隔约 625 ms，手机下行首条命令可能受影响；有待发数据时从机可在连接事件发送，实际吞吐仍需实测 |

不做连接 interval 快慢切换，也不启用本地 latency 门控。旧慢 interval 在手机接受后曾约需 18.8 秒才实际回到快档；单独改 latency 的历史 Android 板测约数百毫秒生效。APP 录音结束后曾把参数改为 30 ms / latency 0，协调器重新请求后约 280–300 ms 恢复 latency 49。

2026-11-10 修正了旧版只管理 RDX 的边界：纯 HID 自动回连若停在 15 ms / latency 0，即使 PA4 已关也可能约 3 mA。之后单 PC HID 和单 RDX 均按物理 ACL 协调，板测出现持续睡眠，用户实测均低于 1 mA。对端可拒绝或覆盖请求；iOS、更多 Windows 主机/版本、OTA 上传、下载吞吐及弱信号长稳仍需验证，不能把历史 Android 结果外推。

### 2.5 CPU 时钟与接收任务

- 睡眠时钟与 CPU 系统时钟是两回事：LRC 降低睡眠底噪，动态调频降低每次唤醒时的处理功耗。`TCFG_T2620_LOWPOWER_LRC_ENABLE` 默认开启，启动配置后不随广播档位切钟。
- 库启动时直接把系统时钟设为约 120 MHz，绕开时钟管理器；`rdx_app_tasks_init()` 启动完成时无条件调用一次 `clock_refurbish()`，让原生观察器在空闲时回落到约 24 MHz。后续真实业务通过 `clock_alloc` / `clock_lock` 申请算力，不直接 `clk_set("sys", ...)` 强锁频率。
- RDX 接收任务空闲使用信号量等待，真实取出数据后才刷新算力；保留入队唤醒、连续消费、自通知和退出 FIFO 屏障。空唤醒不能反复重置调频观察窗口；观察回调归属 `app_core`，业务后也须能再次降频。
- USB 检测、电池采样、按键扫描和调试串口保持 JL 原生策略；正常业务版不启用历史连接态探针或本地 latency 门控开关。

### 2.6 RDX 缓存按需保存

`rdx_cache_flush.c` 在缓存干净时不保留定时器；首次发现脏缓存后安排固定 5 秒保存期限，重复修改不向后推迟。同步保存可取消待办，暂忙时按需重试，真实 IO 故障保留错误与脏数据，不绕过共享 VDD 和存储安全边界。

这项修改减少无意义的空检查，但历史板测没有分辨出新增电流收益；写入、下载、删除和重启持久化仍需按第 4.4 节闭环，不把调度优化当作持久化已验收。

### 2.7 HOGP 输入服务：在线空闲也停表

HID 可用要求 Input CCC 已打开、链路已加密且未 suspend。`rdx_hogp_input.c` 在在线空闲和长按稳定保持期间不保留周期 `sys_timer`；只有 HID 报告在途或欠发松开报告时运行 10 ms 重试，条件消失后立即停表。输入、就绪/失效变化及既有优先级 0 恢复桥接负责重新调度，保留首键、松键、背压和失效清理。

历史故障是：复合会话的入口已关闭、PA4 已关、连接参数正常，但 HID ready 后的常驻 10 ms 系统定时器持续唤醒，使设备约 3 mA 且没有睡眠轨迹。`COM3_2026-11-06_18-15-15.log` 对应事件化后的板测，单 RDX 和 PC HID + PC RDX 复合会话均出现持续 `S<>w[]`，用户实测静置均低于 1 mA；按键后可再次出现睡眠。睡眠标记证明发生了睡眠流程，**不代表睡眠占比或积分平均电流**。

该日志另有一次 F17 本地回放启动约 2 秒后 `P33_VDDIO_LVD_RST`。测试时万用表串在供电回路，表内压降是可能因素，但日志不足以定因；仍需电池直连复测 F17 回放及 F18/F19 录音。HID suspend/resume、快速连击、长按、不同主机及长稳也需继续回归。

## 3. 连接态睡眠机制与探底归因

BLE 不使用 EDR 的 `sniff` 模式：controller 在连接事件之间与系统低功耗框架协同工作。连接参数决定射频活动机会，系统忙票和软件定时器决定这些间隙能否用于睡眠；降到 24 MHz、PA4/PE5 关闭或参数请求成功，都不能单独证明系统已睡眠。

历史实验保留两点归因，详细过程可查 Git 历史：

- 2026-10-17 的单连接组合探底同时改变第二入口、接收任务、时钟等措施，测得 PA4 开约 2.5 mA、关后约 1.5 mA；它不是当前配置，也不能拆算某一项的独立收益。实验备份为 `实验性组合探针打底` / `2893e900`。
- 2026-10-29 的单 RDX 触底实验中，恢复快参数后电流回到约 1.0–1.5 mA；恢复其他业务周期而保留慢参数时约 0.7–1.3 mA。结论是连接参数为该工况下**仪表可见的主因**，不代表其他唤醒源在所有场景都无影响。正式版选择快 interval + latency 49，探针及本地门控只保存在 `freeze/conn-probe-20261029`，不并入正常业务构建。

例如手机纯 RDX 探针期间 HID 尚未 ready，不能用它推断 PC HID 定时器没有功耗影响。后续 PC 复合会话实测恰好发现了第 2.7 节的常驻定时器问题。

## 4. 当前方案：第二入口与系统睡眠保护

### 4.1 按物理拓扑和业务状态判定

下表仅描述 `rdx_ble_dual_acl_lp_target` 这一门禁。多种状态同时成立时，任一“阻止”条件优先；该门禁放行后，仍需其他系统低功耗条件满足才会真正睡眠。

| 状态 | 本门禁 | 说明 |
|---|---|---|
| 零 ACL、无广播控制故障 | 放行 | 未连接广播策略由 [6-0](6-0.T2620外设低功耗与共享VDD电源管理设计.md) 管理，稳定慢广播为 500 ms |
| 单 ACL、第二入口稳定 100 ms 广播 | 放行 | 广播常开本身不构成睡眠忙票 |
| 单 ACL、复合 owner 满占且入口已关闭 | 放行 | PC HID + PC RDX 共用一条 ACL，满足其他条件时可睡眠 |
| 单 ACL、广播准备/关闭/重开在途 | 阻止 | 确认事务结束后才重新判定 |
| 至少一条 ACL 且长文件传输或同步忙 | 阻止 | 与拓扑条件叠加，业务结束后重新放行，见第 4.3.1 节 |
| 双 ACL | 阻止 | 有意保留 controller 保护，不以此拓扑承诺单 ACL 的待机电流 |
| 广播控制故障锁定 | 阻止 | 即使后来退回零 ACL 也保留保护，直到重启 |

双 ACL 睡眠曾触发杰理闭源 controller 的 `bb_le_power.c:352` 断言及后续复位，因此双 ACL 不睡眠是当前产品的保护策略；入口常开和单 ACL 放行不等于 controller 根因已修复。不得删除该保护或屏蔽断言，详见 [3-5](3-5.BLE双ACL低功耗断言问题复盘与量产最佳实践.md)。

### 4.2 历史策略：有限窗口

历史方案在单 ACL 时只开放第二入口 120 秒，到期确认关闭后允许睡眠，下一次真实业务唤醒再重开。它改善了当时的功耗，但待机期间第二台设备无法自主发现；之后又试过 120 秒快广播转慢广播。两者均已被第 4.2.1 节取代，历史电流和板测证据见第 1 节。

### 4.2.1 当前策略：单 ACL 第二入口固定 100 ms 常开

在产品允许广播且复合 owner 未满占时，单 ACL 由空闲 wrapper 持续提供第二入口，`adv_interval=160`，即 **100 ms**。稳定广播期间允许睡眠；不再在 120 秒后切到 500 ms，也不再由按键或业务唤醒触发慢转快。`rdx_ble_entry_adv_slow()` 保留接口，当前策略下恒为 0。

- 复合 HID+RDX 占用同一 ACL 时关闭第二入口；`rdxclose` 完成 RDX FIFO/worker 清理并重新可接管后，保留 HID 和原 ACL，再恢复第二入口。
- 双 ACL 不广播；其中一条断开、变回单 ACL 后按准入条件重开。DUT、关机、PC/USB 所有权及其他广播抑制条件优先。
- 零 ACL 仍使用未连接广播策略；不能把单 ACL 的 100 ms 第二入口和零 ACL 的 500 ms 慢广播混为一谈。
- `COM3_2026-11-11_11-27-02.log` 覆盖单 PC HID 的 100 ms 入口及睡眠、复合会话关入口、`rdxclose` 后重开并超过 120 秒保持 100 ms；无断言、复位或 `timer_no_response`。用户随后确认 PC HID 入睡后手机 RDX 能作为第二 ACL 接入，但未提供该次日志文件名。绑定重连及长稳仍需在常快版本专项复测。

### 4.3 广播关闭确认与故障保护

广播软件状态不能单独证明 controller 已停发。关闭过程先提交 HCI `0x2039` 停广播及 `0x203c` 移除广播集，等待成功或 `0x42`（集合已不存在）；SDK 清理后再等待一次移除完成，隔离 SDK 复用的命令缓冲。关闭在途保留 wrapper/句柄和睡眠保护，确认完成后才能重开或放行。

关闭失败、超时、已提交的开启结果不确定等故障保守锁定，禁止重开并持续阻止睡眠直到整机重启；开启提交前的准入取消不视为故障。广播集已被连接消耗，即使该连接在 `app_core` 评估前已断开，也不能仅凭句柄消失误判为广播故障。

广播完成事件、句柄及命令缓冲依赖当前 `btstack.a` / `btctrler.a` 的已审阅 ABI；升级库必须重新审阅，不能只更新测试中的哈希。退出/重初始化也不能抹掉未确认故障或让旧回调越权。

### 4.3.1 BLE 长文件传输期间阻止系统睡眠

至少一条 ACL 在线，且 `rdx_is_file_transfer_active()` 或 `rdx_is_file_sync_busy()` 为真时，本门禁阻止系统睡眠。普通 HID 报告、短通知或单个 ATT 事件不因此变成持续忙票。该规则是固定产品策略，不新增配置开关。

连接/广播事件缓存拓扑及是否有链路；低功耗查询每次动态读取文件传输/同步状态，与拓扑缓存相或，**不在低功耗线程遍历 BLE 句柄**。传输完成、失败、STOP、录音抢占或断链后，即使没有新的广播事件，也能在文件忙状态清除后重新判定；`rdx_ble_server_file_transfer_changed()` 同时用于刷新状态日志。`[RDX_BLE_LP]` 的 `reason=` 是触发刷新事件的标签，须结合 `connected`、`adv_in_flight`、`file_busy` 与实际睡眠标记判读。

2026-11-16 的 `COM3_2026-11-16_21-57-12.log` 记录：复合会话首个 `opusfile` 请求后 `system_sleep_block=1 file_busy=1`；411 包、约 121.46 秒传输区间内 `S<>` 为 0。F19 抢占后约 3 ms 日志变为 `system_sleep_block=0 file_busy=0`，之后再次出现睡眠标记。

本次文件传输被抢占，**不是正常完成**。门禁释放约 47 秒后出现 `Ping_Timeout`、`Auth_Timeout`，随后进入软关机并重启；未见 assert、watchdog 或 radio fault，但尚需确认是否为 PC 主动断开或用户关机，不能据此判为链路长稳通过。

### 4.4 当前板测状态与验收缺口

| 场景 | 已有证据 | 仍需验证 |
|---|---|---|
| 单 PC HID、单 RDX 待机 | 参数按 ACL 协调后均有睡眠轨迹，用户实测低于 1 mA；当前常快入口版本已覆盖单 PC HID | 常快版本的更多对端、绑定重连、重复循环及长稳；同条件记录连接参数、PA4/PE5 与电流 |
| PC HID + PC RDX 复合单 ACL | HOGP 事件化后静置低于 1 mA；复合时关入口，`rdxclose` 后保留 HID、重开入口 | 精确积分电流、首键/松键、长按、suspend/resume、录音/下载后再次待机，以及更多 Windows 主机 |
| 单 ACL 睡眠后接入第二设备 | 用户确认单 PC HID 低功耗后手机 RDX 可接入第二 ACL；常快版本无对应日志文件名 | 归档日志与固件标识，验证 PC-first/手机-first、绑定回连、异常断开及长时间重复；接入瞬间仍存在 controller 时序风险 |
| 双 ACL（如 PC HID + 手机 RDX） | 门禁按设计阻止睡眠 | 功能并发、断链和 2→1 恢复需回归；双 ACL 低功耗不是当前验收目标 |
| BLE 长文件传输 | 411 包传输期间无睡眠标记，F19 抢占后门禁释放并恢复睡眠 | 正常下载完整结束后的释放、失败/STOP/断链恢复、吞吐和电流；查明后续 `Ping_Timeout` / `Auth_Timeout` 与软关机原因 |
| 存储与共享 VDD | 历史板测覆盖空闲关电、列表恢复、短录音及部分下载；缓存增量电流收益未量化 | 录音停止 → 列表/大小更新 → 下载核对内容 → 重启保留 → 删除 → 再次重启确认删除；PA4 恢复失败及真实 IO 时序 |
| 模式与系统回归 | 软件测试覆盖相应边界，部分历史主路径已板测 | USB/CDC、DUT、DIP、OTA、充电/低电、广播故障与退出重入；F17/F18/F19 直连电池复测及温压/RF 长稳 |

每次板测应保存烧录镜像标识或哈希、匹配 ELF、日志、对端及实际连接参数，并记录供电、USB、ACL/owner、PA4/PE5、业务状态和测量方式。`S<>w[]` 不是睡眠占比；万用表跳动范围不是积分平均值。软件模拟通过不替代真实 controller、RF、存储和电流验收，局部场景通过也不等于量产验收。

## 5. 诊断时先区分的几件事

| 现象 | 先检查什么 |
|---|---|
| PA4/PE5 已关但电流仍高 | 核对 `system_sleep_block`、实际 `if/lat`、系统时钟和周期唤醒源；外设关断不等于 CPU 已睡眠 |
| 单 PC HID 约 3 mA | 确认纯 HID ACL 也请求到目标 latency；门禁放行后若没有 `<>`，检查 HID ready 是否仍有常驻 10 ms `sys_timer` |
| 第二入口看似关闭但仍不能睡 | 检查广播准备/两阶段关闭是否完成、是否发生 fault；不要只看 SDK 软件缓存，也不要绕过双 ACL 保护 |
| PA4 因 `FILE_OP` 保持供电 | 这是外设供电占用；再看 `file_busy` 与系统睡眠门禁，不能由 PA4 状态推断 CPU 睡眠状态 |
| 文件停止后仍不睡 | 同时检查文件传输/同步状态、拓扑缓存、广播事务及其他系统忙票；仅有一条旧日志不能证明当前门禁状态 |
| 开机能降频、业务后不能降频 | 检查是否存在空等待反复提频，以及原生观察回调是否由 `app_core` 分发；覆盖业务后再次空闲的过程 |
| 对端下行操作慢 | 记录实际 interval/latency、首包和业务处理时间；高 latency 可能增加首包等待，旧慢 interval 的重新协商又有较长延迟，不能只看请求返回值 |
| 单 ACL 变双 ACL 后无睡眠标记 | 当前双 ACL 按设计阻止睡眠；先验证连接及业务功能，不把它当成单 ACL 门禁失效 |

## 6. Windows 构建、软件测试与板测

JL 编译、链接和打包使用 Windows 工具链；以 `SDK/.vscode/tasks.json` 的 **Windows** 命令为准。VS Code 打开 `SDK/` 后可使用默认构建任务 `all` 和默认测试任务 `test: host software`。命令行从仓库根目录执行：

```powershell
cd SDK
.\.vscode\winmk.bat all
cd ..
powershell -NoProfile -ExecutionPolicy Bypass -File .\tests\host\run_host_tests.ps1
```

需要清理时，在 `SDK/` 下运行 `.\.vscode\winmk.bat clean`；若增量构建因已删除文件报 `No rule to make target`，先 clean 再 all。主机测试也可加 `-Suite contracts` 或 `-Suite behavior` 做定向检查；完整入口包含 4 个源码契约和 20 个行为套件，覆盖范围见 [tests/host/README.md](../tests/host/README.md)。其中连接入口、连接参数、共享 VDD、HOGP、缓存及 LRC 分别由对应套件检查。

上述构建与主机测试应在具备 JL 工具链、PowerShell 5.1 和 Python/llvmlite 的 Windows 环境执行。固件通过 JL Studio 或 `ISD_download.exe` 烧录，再执行第 4.4 节的实板检查。文档检查和历史日志不能代替上述验证；本次整理不改变固件策略，过往测试结果只适用于各自记录的版本。
