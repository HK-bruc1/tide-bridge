# PC APP逻辑断开无法释放RDX会话问题复盘与处理方案

> 更新时间：2026-08-05
> 当前状态：Root Cause Confirmed / Phone-to-PC Physical Handoff Passed / Explicit Logical Release Design Pending
> 阻塞结论：PC App、固件和协议目前没有共同定义“只关闭RDX、保留同一ACL上的HOGP”这一会话结束边界。仅修改固件的HCI断开回调无法解决；正式关闭需要PC App与固件协同实现显式逻辑释放，并为异常退出增加可证明的租约兜底。

## 1. 问题与已解决问题的边界

本问题必须与此前的跨peer重绑问题分开：

| 路径 | 当前状态 | 结论 |
|---|---|---|
| 手机RDX物理ACL断开，PC/HID ACL保持，PC App接管RDX | 已通过真机验证 | 同peer地址锁问题已经解决 |
| PC物理ACL断开，手机重新连接并接管RDX | 现有物理断开生命周期支持，仍需纳入完整矩阵 | 固件可以收到Disconnection Complete |
| PC App关闭GATT对象，但Windows为HOGP保留物理ACL，手机接管RDX | 阻塞 | 固件收不到可用于释放RDX owner的事件 |

因此，当前现象不是旧的FIFO边界未清理、runtime卡在`RESETTING`，也不是跨peer claim仍被地址锁拒绝。旧问题已经完成以下闭环：

```text
旧RDX物理断开
  -> ACTIVE -> QUIESCING
  -> receive FIFO nonce barrier
  -> workers idle + final buffer reset
  -> READY
  -> 不同peer合法claim
  -> ACTIVE
```

当前阻塞发生在第一步之前：PC App关闭时没有触发“旧RDX物理断开”，也没有发送等价的“逻辑会话关闭”协议消息。

## 2. 真机证据

### 2.1 手机到PC的跨peer交接已通过

日志：`COM3_2026-08-05_20-55-12.log`

关键顺序：

```text
20:55:26  PC/HID建立ACL con=0x0050，HOGP ready=1
20:55:39  手机建立第二条ACL con=0x0051
20:55:40  手机取得RDX owner，runtime ACTIVE con=0x0051
20:56:04  手机ACL断开，reason=0x13
20:56:04  runtime QUIESCING
20:56:04  receive FIFO drain barrier reached
20:56:04  runtime READY: FIFO drained and workers idle
20:56:11  PC App在既有con=0x0050上发起RDX写入
20:56:11  composite owner ... order=HID+RDX
20:56:11  runtime ACTIVE con=0x0050
```

随后PC App成功执行真实录音启动、停止和文件保存。日志不再出现：

```text
rebind peer rejected
RDX claim rejected result=2
```

这证明删除boot-lifetime同peer地址锁的修改有效，手机RDX物理断开后的buffer清理和PC接管均已完成。

### 2.2 PC App逻辑断开没有到达固件

PC App在`20:56:27`报告：

```text
{
  "connected": false
}
> disconnect
```

但固件日志从`20:56:19`最后一次PC业务ATT写入到日志结束，没有出现以下任一事件：

```text
att disconn
[RDX_BLE_LINK] disconnect ...
RDX CCC cfg=0x0000
显式RDX session close命令
runtime QUIESCING
runtime READY
```

PC App重复调用`disconnect`仍返回`connected:false`，只能证明应用侧GATT对象已经处于断开状态，不能证明Windows controller已经释放物理ACL。Windows仍需维持HOGP键盘，因此`con=0x0050`可以继续存在，HID owner和bonded Input CCC也仍然有效。

## 3. 根因

当前registry把RDX capability设计为物理链路生命周期内粘性持有：

```text
RDX claim -> link.capability增加RDX bit
           -> rdx_link_index指向该slot
           -> runtime ACTIVE

Disconnection Complete
           -> RDX detach和runtime收敛
           -> link release
           -> RDX/HID owner按该物理链路释放
```

RDX CCC写`0`目前只清除`rdx_ccc_configured`和`rdx_stream_tx_ready`，不释放RDX bit或`rdx_link_index`。这是此前为防止普通CCC变化造成owner漂移而冻结的安全边界。

Same-link PC拓扑使“应用会话”和“物理连接”不再等价：

```text
Windows物理ACL con=0x0050
  + HOGP会话：由Windows HID栈长期持有
  + RDX会话：由PC App临时使用
```

PC App关闭RDX时，Windows可以只销毁应用侧GATT对象而继续保留ACL。固件既不能从HCI事件判断PC App是否退出，也不能把普通ATT空闲可靠地解释为退出。因此旧RDX owner继续占用是当前设计的确定行为，不是回调遗漏。

## 4. 为什么现有兜底不能直接使用

### 4.1 不能强制断开整条ACL

`rdx_ble_server_force_disconnect_timer_cb()`对应的是整条BLE连接断开，并且当前函数被硬编码立即返回。重新启用它会同时破坏：

- HOGP键盘在线状态；
- HID Input CCC与report发送；
- Windows设备连续性；
- same-link复合owner的产品目标。

因此不能用“PC App退出后踢掉BLE连接”代替RDX逻辑释放。

### 4.2 不能仅按ATT空闲超时释放

PC App正常停留在页面、没有操作时也可能长时间没有ATT写入。仅按最后一次业务包计时会把正常空闲误判为退出，并可能在文件、OTA或后台任务期间错误切换owner。

### 4.3 不能直接调用整条link release

现有`rdx_ble_session_link_release()`会清理整个slot及其RDX/HID owner索引。Same-link场景直接调用会把仍然有效的HOGP一起释放，并使registry与真实ACL状态不一致。

### 4.4 不能只清RDX owner字段

`librdxApp.a`是不可修改的异步单例。若只清`rdx_link_index`或capability bit而跳过`QUIESCING -> FIFO barrier -> RESETTING -> READY`，旧receive、record、file、bulk、OTA或send工作可能污染下一位手机owner。

## 5. 正式解决方案

### 5.1 增加显式RDX逻辑关闭协议

PC App必须在销毁GATT对象之前发送可确认的RDX session close请求。正式wire格式应与PC App共同冻结，不能只在固件侧临时猜测`disconnect`语义。

请求至少应携带：

- 命令版本；
- 当前session id或等价generation；
- request id，用于幂等与响应匹配；
- 关闭原因，例如用户退出、应用切换或正常关机。

推荐时序：

```text
PC App停止创建新业务请求
  -> 等待录音/文件/OTA等前台事务结束或明确取消
  -> 写入RDX_SESSION_CLOSE（write with response或等价可靠控制点）
  -> 固件校验当前RDX owner与session id
  -> 固件进入CLOSING并拒绝后续普通业务输入
  -> 可靠确认close请求已经受理
  -> 在BTStack所属上下文调度RDX logical detach
  -> QUIESCING -> FIFO barrier -> RESETTING -> READY
  -> 仅释放RDX capability，HID capability和物理ACL保持
  -> PC App停止notifications并销毁GATT对象
```

ACK必须在关闭RDX发送门之前完成，或者直接使用ATT Write Response作为“请求已受理”的可靠确认。不能先清transport再尝试通过已关闭的RDX notify发送ACK。

### 5.2 增加per-capability release

registry需要新增只释放RDX capability的转换，满足：

```text
before: link.connected=1, capability=RDX_HID
after:  link.connected=1, capability=HID
        rdx_link_index=INVALID
        hid_link_index保持原slot
```

必须保留：

- wrapper与connection handle映射；
- slot generation；
- HID owner index；
- peer identity与加密状态；
- bonded HID CCC与HOGP ready状态；
- HID按键release/press链路。

只有RDX runtime完成FIFO屏障、worker idle和最终buffer reset后，才允许进入`READY`并接受手机claim。若收敛失败，保持fail closed，不得为了释放owner直接跳过屏障。

### 5.3 任务上下文

ATT写回调、owner registry和连接状态转换当前由BTStack路径串行维护。若close命令最终在`librdxApp.a` receive task或`app_core`被解析，不能直接跨task修改registry；必须投递携带`slot_index + slot_generation + transport_epoch`的消息回到规定的BLE/BTStack上下文，并在执行前重新校验token。

重复close、旧session close和非owner close必须幂等拒绝，不能关闭当前新owner。

### 5.4 异常退出使用心跳租约兜底

PC App崩溃、被强杀或系统异常时无法发送正常close。正式协议应增加RDX session lease：

- 仅在RDX逻辑会话建立后启用；
- PC App周期性发送带session id的heartbeat；
- 固件只接受当前owner、当前epoch的heartbeat续租；
- 超时先确认没有不可中断的OTA/格式化等操作，再走同一logical detach屏障；
- 超时释放只影响RDX，不影响HID ACL；
- 心跳周期和超时值必须经过功耗、后台调度和Windows挂起测试后冻结。

建议从`5 s`心跳、`15 s`租约作为验证参数开始，但不能在没有PC App持续心跳能力时直接启用固件超时，否则所有正常空闲PC会话都会被误释放。

现有协议中的`*APP#active#`及`RECORD_HEARTBEAT_SUPPORT`属于录音保活语义，且当前录音heartbeat支持未启用，不能直接视为通用RDX session lease。若选择复用wire命令，必须先重新冻结session id、续租时机、超时动作和向后兼容语义。

## 6. 实施拆分

### 6.1 PC App

- 定义并发送session close请求；
- close前停止新任务并处理在途事务；
- 等待可靠受理后再调用`stopNotifications()`和`gatt.disconnect()`；
- 维护session id、request id和heartbeat；
- 处理close超时、重复close与设备已提前断开的幂等结果；
- 日志同时区分`app_gatt_connected`、`rdx_session_active`和`physical_link_observed`，不再用单个`connected`布尔值代表三层状态。

### 6.2 固件

- 增加RDX logical close控制入口；
- 增加`ACTIVE -> CLOSING/QUIESCING`的原子门控；
- 把现有物理断开RDX cleanup抽取为可由逻辑关闭复用的内部路径；
- 增加只清RDX bit/index的registry API，禁止清HID和整个slot；
- 对close调度和heartbeat timeout使用owner token；
- 在`READY`前继续执行nonce FIFO屏障、二次取消、worker idle与最终buffer reset；
- 增加明确日志，区分`physical detach`与`logical detach`。

### 6.3 Host contracts

至少增加以下静态契约：

- logical release不调用整条link release；
- `RDX_HID -> HID`时HID owner与连接字段保持；
- logical release必须经过runtime quiesce/barrier/rearm；
- close与heartbeat timer携带owner token；
- stale/non-owner close不能释放当前owner；
- physical disconnect仍能同时清理该link上的RDX和HID；
- force-disconnect timer不得作为PC逻辑关闭实现。

## 7. 真机验收矩阵

```text
[ ] 1. PC/HID保持ready，PC App取得RDX并形成RDX_HID复合owner
[ ] 2. PC App正常close后出现logical QUIESCING -> barrier -> READY，不出现HCI disconnect
[ ] 3. logical close全过程Windows键盘持续输入，不重新枚举、不重新配对
[ ] 4. PC App close完成后手机在第二条ACL成功claim RDX并执行真实命令
[ ] 5. 手机释放后PC App可在原HID ACL再次claim，连续往返至少10轮
[ ] 6. PC App录音活动中close：按产品定义先停止或拒绝close，不遗留旧录音事件
[ ] 7. 文件/bulk活动中close：旧数据不发送给手机新owner
[ ] 8. OTA/格式化期间close：按不可中断策略明确拒绝或延迟，不破坏存储
[ ] 9. 重复close幂等，旧session id和非owner close不能释放新owner
[ ] 10. PC App崩溃后heartbeat租约超时，只释放RDX并保留HID
[ ] 11. Windows睡眠/唤醒及App后台节流不会误触发租约释放
[ ] 12. logical close收敛失败保持FAILED/fail closed，不允许手机提前claim
[ ] 13. PC物理ACL断开仍走原路径，同时清理该link上的RDX与HID
[ ] 14. 全程无cross-send、stale callback、assert、watchdog或异常复位
```

## 8. 当前可接受的临时边界

在显式逻辑释放完成前，产品与测试必须按以下事实解释结果：

- 手机RDX物理断开后由PC App接管：已支持并已验证；
- PC App只调用应用侧`disconnect`且Windows HID仍在线：RDX owner不会释放；
- 此时手机无法接管是已知阻塞，不是跨peerreset修复失效；
- 若必须立即让手机接管，只能让PC物理ACL真正断开或重启设备，但这不是最终用户流程；
- 不允许通过恢复同peer锁、清空全局registry、强制踢掉HID ACL或固定空闲超时掩盖问题。

完成第5节协议与固件设计、对应Host contract和第7节真机矩阵之前，本问题保持开放。
