# PC APP逻辑断开无法释放RDX会话问题复盘与处理方案

> 更新时间：2026-08-06
> 当前状态：Root Cause Confirmed / Standalone Physical Disconnect Callback Passed / Logical Release v1 Two-Phase Design Drafted / Implementation Pending
> 阻塞结论：PC App单独占用BLE链路时，主动断开会终止唯一物理ACL，固件能够收到HCI断开回调；PC App与HOGP复用同一ACL时，Windows只关闭PC App的GATT使用关系并为HID保留ACL，因此不会产生固件可见的物理断开回调。PC App、固件和协议目前仍未共同定义“只关闭RDX、保留同一ACL上的HOGP”这一会话结束边界；正式关闭需要显式RDX逻辑释放，并为异常退出增加可证明的租约兜底。

## 1. 问题与已解决问题的边界

本问题必须与此前的跨peer重绑问题分开：

| 路径 | 当前状态 | 结论 |
|---|---|---|
| PC App单独占用ACL并主动断开 | 已连续两轮真机验证 | Windows终止唯一ACL，固件收到`Disconnection Complete`，RDX runtime正常回到`READY` |
| 手机RDX与PC/HID各占一条ACL并分别主动断开 | 已通过真机验证 | 每条物理ACL独立触发对应wrapper的断开回调 |
| 手机RDX物理ACL断开，PC/HID ACL保持，PC App接管RDX | 已通过真机验证 | 同peer地址锁问题已经解决 |
| PC物理ACL断开，手机重新连接并接管RDX | 现有物理断开生命周期支持，仍需纳入完整矩阵 | 固件可以收到Disconnection Complete |
| PC App关闭GATT对象，但Windows为HOGP保留复用ACL，手机接管RDX | 阻塞 | App级GATT detach不是物理ACL断开，固件收不到可用于释放RDX owner的事件 |

因此，当前现象不是旧的FIFO边界未清理、runtime卡在`RESETTING`，也不是跨peer claim仍被地址锁拒绝。旧问题已经完成以下闭环：

```text
旧RDX物理断开
  -> ACTIVE -> QUIESCING
  -> receive FIFO nonce barrier
  -> workers idle + final buffer reset
  -> READY
  -> 不同peer合法claim
  -> ACTIVE
```

当前阻塞只发生在复用ACL拓扑的第一步之前：PC App单独使用时可以触发“旧RDX物理断开”；PC App与HOGP复用时不会触发物理断开，也没有发送等价的“RDX逻辑会话关闭”协议消息。

## 2. 真机证据

### 2.1 手机到PC的跨peer交接已通过

日志：`COM3_2026-08-05_20-55-12.log`

关键顺序：

```text
20:55:26  PC/HID建立ACL con=0x0050，HOGP ready=1
20:55:39  手机建立第二条ACL con=0x0051
20:55:40  手机取得RDX owner，runtime ACTIVE con=0x0051
20:56:04  手机ACL断开，reason=0x13
20:56:04  runtime QUIESCING
20:56:04  receive FIFO drain barrier reached
20:56:04  runtime READY: FIFO drained and workers idle
20:56:11  PC App在既有con=0x0050上发起RDX写入
20:56:11  composite owner ... order=HID+RDX
20:56:11  runtime ACTIVE con=0x0050
```

随后PC App成功执行真实录音启动、停止和文件保存。日志不再出现：

```text
rebind peer rejected
RDX claim rejected result=2
```

这证明删除boot-lifetime同peer地址锁的修改有效，手机RDX物理断开后的buffer清理和PC接管均已完成。

### 2.2 PC App单独使用时主动断开可以触发回调

日志：`PC-APP单独主动连接与断开日志.log`

同一次开机内连续完成两轮连接和主动断开：

```text
09:52:52  PC App取得RDX owner，runtime ACTIVE con=0x0050 epoch=2
09:53:08  att disconn
09:53:08  disconnect accepted status=0x00 reason=0x13
09:53:08  runtime QUIESCING -> FIFO drain barrier -> READY

09:53:21  PC App重新取得RDX owner，runtime ACTIVE con=0x0050 epoch=4
09:53:33  att disconn
09:53:33  disconnect accepted status=0x00 reason=0x13
09:53:33  runtime QUIESCING -> FIFO drain barrier -> READY
```

`reason=0x13`表示远端用户终止连接。这里PC App是该Windows设备上唯一使用该BLE链路的消费者；其主动断开最终使Windows controller终止物理ACL，因此固件现有`HCI_EVENT_DISCONNECTION_COMPLETE`路径能够正常工作。这排除了“PC App主动断开普遍无法进入固件回调”以及“固件物理断开清理路径失效”两种判断。

### 2.3 两条独立ACL按物理链路分别回调

日志：`PC-HID与手机APP拓扑结构反复主动断开与连接日志.log`

```text
09:48:55  手机APP取得RDX owner，con=0x0050，runtime ACTIVE
09:49:08  PC-HID在con=0x0051恢复Input CCC并进入ready
09:49:19  con=0x0050断开，reason=0x13，RDX runtime回到READY
09:49:28  手机APP在con=0x0050重新连接并取得RDX owner
09:49:37  con=0x0051断开，reason=0x13，触发HOGP disconnect
```

这组日志说明wrapper和回调分发没有把两条ACL混淆：手机APP的物理断开只释放RDX链路，PC-HID继续存在；PC-HID的物理断开也能命中自己的wrapper。是否触发回调取决于对应物理ACL是否终止，而不是RDX或HID服务本身是否关闭。

### 2.4 PC App与PC-HID复用ACL时只有App级detach

日志：`PC-APP与PC-HID拓扑结构PC-APP主动断开无回调.log`

```text
09:54:52  Windows建立con=0x0050
09:54:52  HOGP ready=1，HID owner attached con=0x0050
09:55:01  PC App在同一con=0x0050取得RDX，形成HID+RDX复合owner
09:55:11  最后一次PC App业务ATT写入
09:55:21  日志继续运行，但只有已禁用的force-disconnect timer返回
```

PC App主动断开后到日志结束，没有出现以下任一事件：

```text
att disconn
[RDX_BLE_LINK] disconnect ...
RDX CCC cfg=0x0000
显式RDX session close命令
runtime QUIESCING
runtime READY
```

这不是“复用后固件漏调了一个已经到达的断开事件”。HOGP仍然需要`con=0x0050`，Windows没有终止该物理ACL，自然不会产生`HCI_EVENT_DISCONNECTION_COMPLETE`。PC App侧的`connected:false`最多只能表示应用GATT对象已detach，不能表示controller已经释放ACL；固件也看不到Windows内部的GATT对象引用计数变化。

## 3. 根因

固件当前注册的断开入口是`rdx_ble_server_phase0a_packet_handler()`中的`HCI_EVENT_DISCONNECTION_COMPLETE`。它是物理连接事件，不是“某个Windows应用停止使用某组GATT特征”的事件。事件到达后，`rdx_ble_server_phase0a_link_disconnected()`才会依次执行RDX detach、HOGP本地清理和整条link release。

当前registry把RDX capability设计为物理链路生命周期内粘性持有：

```text
RDX claim -> link.capability增加RDX bit
           -> rdx_link_index指向该slot
           -> runtime ACTIVE

Disconnection Complete
           -> RDX detach和runtime收敛
           -> link release
           -> RDX/HID owner按该物理链路释放
```

RDX CCC写`0`目前只清除`rdx_ccc_configured`和`rdx_stream_tx_ready`，不释放RDX bit或`rdx_link_index`。这是此前为防止普通CCC变化造成owner漂移而冻结的安全边界。

Same-link PC拓扑使“应用会话”和“物理连接”不再等价：

```text
Windows物理ACL con=0x0050
  + HOGP会话：由Windows HID栈长期持有
  + RDX会话：由PC App临时使用
```

PC App关闭RDX时，Windows可以只销毁应用侧GATT对象而继续保留ACL。PC App单独使用时，GATT detach之后没有其他消费者，Windows进一步终止ACL，所以固件恰好能够通过物理断开释放RDX；这只是独占拓扑下应用生命周期与ACL生命周期重合，不能作为RDX会话关闭协议。

复用拓扑中两者不再重合。固件既不能从不存在的HCI事件判断PC App是否退出，也不能把普通ATT空闲可靠地解释为退出。因此旧RDX owner继续占用是当前设计的确定行为，不是callback注册、wrapper路由或断开清理代码的遗漏。

## 4. 为什么现有兜底不能直接使用

### 4.1 不能强制断开整条ACL

`rdx_ble_server_force_disconnect_timer_cb()`对应的是整条BLE连接断开，并且当前函数被硬编码立即返回。重新启用它会同时破坏：

- HOGP键盘在线状态；
- HID Input CCC与report发送；
- Windows设备连续性；
- same-link复合owner的产品目标。

因此不能用“PC App退出后踢掉BLE连接”代替RDX逻辑释放。

### 4.2 不能仅按ATT空闲超时释放

PC App正常停留在页面、没有操作时也可能长时间没有ATT写入。仅按最后一次业务包计时会把正常空闲误判为退出，并可能在文件、OTA或后台任务期间错误切换owner。

### 4.3 不能直接调用整条link release

现有`rdx_ble_session_link_release()`会清理整个slot及其RDX/HID owner索引。Same-link场景直接调用会把仍然有效的HOGP一起释放，并使registry与真实ACL状态不一致。

### 4.4 不能只清RDX owner字段

`librdxApp.a`是不可修改的异步单例。若只清`rdx_link_index`或capability bit而跳过`QUIESCING -> FIFO barrier -> RESETTING -> READY`，旧receive、record、file、bulk、OTA或send工作可能污染下一位手机owner。

## 5. 正式解决方案

### 5.1 最终原则与改动边界

最佳实践不是根据“当前是否复用ACL”在PC App里选择两套关闭方式，而是把RDX定义为独立于ACL的应用会话：

- 新版PC App无论单独使用还是与HOGP复用，都统一执行`OPEN -> 业务 -> CLOSE_PREPARE -> CLOSE_COMMIT`；
- 固件保留现有`HCI_EVENT_DISCONNECTION_COMPLETE`物理断开路径，继续兼容手机APP、旧版PC App、PC蓝牙关闭、超距和掉电；
- 新增的逻辑关闭只释放RDX，不断开ACL、不清HID；
- 逻辑关闭和物理断开最终汇入同一个RDX runtime cleanup，不维护两份清理代码；
- 两条路径必须幂等。逻辑关闭后若独占ACL又产生物理断开，只允许清理剩余link/HID状态，不得重复启动RDX barrier；
- 第一期必须完成显式`CLOSE_PREPARE/CLOSE_COMMIT`；心跳租约用于异常退出，作为第二期增强，不能替代正常关闭。

因此需要固件端和PC App端同时修改。手机APP当前以物理ACL断开结束RDX的方式可以保持不变；本次新增协议的直接对接方是PC App。

### 5.2 复用现有GATT与custom通道

不新增Service、Characteristic或handle，避免Windows GATT缓存、历史bond和量产兼容风险。控制命令复用现有RDX通道：

```text
PC App -> firmware: *APP#custom#rdxsession#<HEX>#
firmware -> PC App: *DEV#custom#rdxsession#<HEX>#
```

对应现有属性：

| 方向 | ATT handle | 当前属性 | 用途 |
|---|---:|---|---|
| PC App下行 | `0x0006` | `WRITE_WITHOUT_RESPONSE | DYNAMIC` | `OPEN`、`CLOSE_PREPARE`、`CLOSE_COMMIT`、`HEARTBEAT`请求 |
| 固件上行 | `0x0008` | Notify | `OPEN`响应、`CLOSE_PREPARED`及其他应用层响应 |

这里不能把ATT Write Response写进实现要求：`0x0006`当前只有`Write Without Response`，若改属性就会改变profile并引入Windows缓存兼容问题。v1必须使用`0x0008` Notification返回应用层响应。

外部命令固定为`rdxsession`。现有`__rdxlc`是固件内部向不可修改receive FIFO插入的nonce barrier，只能由固件生成和匹配，禁止PC App发送或复用。

### 5.3 建议冻结的`rdxsession v1`帧

为复用现有HOGP keymap codec模式，`<HEX>`采用大写或小写均可接受的十六进制字符串；多字节整数统一Little Endian；CRC使用当前工程的CRC32实现。控制帧必须受现有RDX分包/组包承载，不能假定一条ATT Write能容纳完整ASCII命令。

请求与响应共用以下头部：

| Offset | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| `0` | 1 | `version` | v1固定`0x01` |
| `1` | 1 | `opcode` | 请求见下表；有响应的操作使用`request_opcode | 0x80` |
| `2` | 2 | `request_id` | PC App递增生成，`0`保留；用于匹配和幂等 |
| `4` | 4 | `session_id` | PC App随机生成的非0值；一次逻辑会话内不变 |
| `8` | 2 | `payload_len` | payload字节数 |
| `10` | N | `payload` | 请求或响应数据 |
| `10 + N` | 4 | `crc32` | 对前面`10 + N`字节计算，Little Endian存放 |

v1 opcode建议冻结为：

| Opcode | 名称 | 请求payload | 响应payload |
|---:|---|---|---|
| `0x01` | `OPEN` | `client_flags:u16 + requested_lease_s:u16` | `status:u8 + firmware_flags:u16 + accepted_lease_s:u16` |
| `0x02` | `CLOSE_PREPARE` | `reason:u8` | `status:u8`；`OK`即`CLOSE_PREPARED` |
| `0x03` | `CLOSE_COMMIT` | 空；沿用对应PREPARE的`session_id + request_id` | 无响应；固件收到即开始logical detach |
| `0x04` | `HEARTBEAT` | 空 | `status:u8` |
| `0x05` | `QUERY` | 空 | `status:u8 + session_state:u8 + runtime_state:u8` |

`client_flags`与`firmware_flags`至少定义：

```text
bit0: EXPLICIT_CLOSE_SUPPORTED
bit1: SESSION_LEASE_SUPPORTED
bit2..15: reserved, sender写0、receiver忽略
```

第一期PC App发送`requested_lease_s=0`，固件返回`accepted_lease_s=0`，表示只启用显式关闭。第二期双方都声明`SESSION_LEASE_SUPPORTED`后，固件才允许返回非0租约。不能由固件单方面启用租约。

`CLOSE_PREPARE reason`建议定义为：

| 值 | 含义 |
|---:|---|
| `0x00` | 用户主动断开/退出设备 |
| `0x01` | App退出 |
| `0x02` | App切换设备 |
| `0x03` | 系统正常关机或注销 |
| `0x04` | 业务错误后主动收敛 |

v1 status建议冻结为：

| 值 | 名称 | PC App处理 |
|---:|---|---|
| `0x00` | `OK` | 请求成功；对`CLOSE_PREPARE`表示固件已经进入不可撤销的等待COMMIT阶段 |
| `0x01` | `ALREADY_CLOSING` | 已在等待同一session关闭；按`CLOSE_PREPARED`处理并发送COMMIT |
| `0x02` | `STALE_SESSION` | 清除本地旧session，不得用旧ID重试影响新owner |
| `0x03` | `NOT_OWNER` | 清除本地会话并重新发现/连接，不得视为当前owner |
| `0x04` | `BUSY_RETRY` | 保持会话，先结束在途业务，再使用同一session和新request重试 |
| `0x05` | `UNSUPPORTED_VERSION` | 降级到兼容策略并记录固件版本 |
| `0x06` | `UNSUPPORTED_OPCODE` | 视为双方协议不匹配 |
| `0x07` | `MALFORMED_FRAME` | 修复App编码，不自动无限重试 |
| `0x08` | `CRC_ERROR` | 同一request最多重发限定次数 |
| `0x09` | `REQUEST_ID_CONFLICT` | 同一request ID对应了不同内容，创建新request ID |
| `0x0A` | `INTERNAL_ERROR` | 保持fail closed并上报错误 |

固件按`opcode + session_id + request_id + request_frame_crc32`缓存最近一次有响应的控制请求。同一四元组重复到达时返回相同结果；同一`opcode + session_id + request_id`但CRC不同则返回`REQUEST_ID_CONFLICT`。`CLOSE_COMMIT`复用对应PREPARE的`session_id + request_id`，但opcode不同，因此不与PREPARE缓存冲突。关闭缓存至少保留到logical detach开始；detach之后不再尝试从无owner状态发送关闭响应。

正常首次接受PREPARE返回`OK`，完全相同的重复PREPARE返回缓存的`OK`。`ALREADY_CLOSING`只用于close上下文仍匹配同一`session_id + request_id + request CRC`、但响应缓存需要重建的防御性恢复分支；不同request ID不得返回`ALREADY_CLOSING`，否则PC App无法确定COMMIT应匹配哪个PREPARE。

### 5.4 `OPEN`是自动claim后的session绑定

现有`rdx_ble_server_phase2_rdx_write()`在把`0x0006`数据送入`rdx_protocol_packet_recv()`之前，已经调用`rdx_ble_server_phase2_rdx_attach()`。因此v1不能把`OPEN`定义成“parser解析后再claim”，也不能要求在无owner状态下通过不可修改的异步FIFO识别来源link。

PC App完成GATT发现并订阅`0x0008`后生成随机非0 `session_id`，并把`OPEN`作为第一条RDX命令发送。实际顺序固定为：

```text
OPEN的首个ATT写入
  -> 沿用现有phase2_rdx_attach()自动claim当前link
  -> runtime ACTIVE，后续分片进入现有RDX组包/FIFO
  -> rdx_app_custom_command_parse()解析完整OPEN
  -> 将session_id绑定到当前RDX owner token
  -> 按该token返回OPEN响应
```

固件处理规则如下：

1. `OPEN`只允许在当前RDX owner仍为`ACTIVE`时绑定；parser执行时若物理断开已经使owner失效，则静默丢弃，不得绑定后来的新owner；
2. 当前owner未绑定managed session时，绑定`session_id -> slot_index + slot_generation + transport_epoch`；
3. 当前owner已绑定同一个session时，幂等返回原`OPEN`响应；
4. 当前owner已绑定另一个session时返回`NOT_OWNER`或`REQUEST_ID_CONFLICT`，不得覆盖；
5. 新版PC App收到`OPEN OK`前不得发送录音、文件、配置等普通业务；
6. 另一个link已经持有RDX时，当前`Write Without Response`可能在进入parser前被claim gate拒绝，PC App应把`OPEN`无响应视为RDX busy并退避，不能期待跨owner响应；
7. 新版PC App收到`OPEN OK`后才把本地`rdx_session_active`置为true。

固件继续保留“第一条旧式RDX写入自动claim”的legacy模式；按当前实现，订阅RDX Notify产生的CCC写也可能先于`OPEN`完成claim。逻辑关闭后，同一HID ACL再次使用PC App时，新的CCC写或`OPEN`下行仍通过现有自动attach取得owner，随后`OPEN`只负责绑定新session。MVP不增加无owner状态的独立控制接收器；`QUERY`也只允许查询已经由当前owner绑定的session，不能用作无owner探测或抢占。

### 5.5 `CLOSE_PREPARE/CLOSE_COMMIT`两阶段关闭

RDX下行只有`Write Without Response`，上行`0x0008`只有Notify。`ATT_EVENT_CAN_SEND_NOW`表示ATT当前允许继续发送，不是上一条Notification的逐帧完成事件；事件也不携带request ID。因此不能用它证明`CLOSE_PREPARED`已经发送或被PC App收到。

v1改为由PC App回传`CLOSE_COMMIT`证明它已经收到`CLOSE_PREPARED`：

```text
ACTIVE
  | CLOSE_PREPARE通过owner/session/token校验，且业务允许关闭
  v
CLOSING_WAIT_COMMIT
  | 关闭新业务入口；按owner token发送CLOSE_PREPARED
  | PC App收到PREPARED后发送CLOSE_COMMIT
  | 或显式关闭宽限timer到期
  v
QUIESCING
  | 取消timer与业务，关闭旧transport，插入__rdxlc nonce barrier
  v
RESETTING
  | barrier到达；二次cancel；等待record/file/bulk/send worker idle
  v
READY
```

具体约束：

- `CLOSE_PREPARE`解析后取得该runtime epoch预先绑定的ingress `rdx_ble_async_token_t`，把事件投递到`btstack`任务；执行回调时重新resolve token；
- PREPARE一旦被当前owner接受即不可撤销，进入`CLOSING_WAIT_COMMIT`并启动显式关闭宽限timer；
- `CLOSE_PREPARED`按捕获token路由到原owner。Notification提交失败时仍保持等待状态；同一PREPARE重试应再次尝试发送缓存响应；
- PC App只有实际收到`CLOSE_PREPARED`后才发送完全匹配的`CLOSE_COMMIT`；COMMIT沿用PREPARE的`session_id + request_id`；
- 固件收到合法COMMIT后立即在`btstack`上下文进入logical detach，不发送PC App还必须等待的最终响应；
- `ATT_EVENT_CAN_SEND_NOW`只保留现有发送流控用途，严禁用它推进RDX关闭状态；
- 建议固件显式关闭宽限timer先取`5 s`，PC App的全部PREPARE重试窗口必须小于该值，例如在`3 s`内结束；
- 若PC App收到PREPARED后崩溃、COMMIT丢失或Notification回调后未能继续执行，宽限timer到期仍执行logical detach。该超时以已收到的显式关闭请求为前提，不是ATT空闲超时；
- 物理断开在任何阶段到达都取消等待timer并走原物理cleanup；已经开始的RDX barrier不能重复插入；
- 收敛失败进入`FAILED`并拒绝新claim，不得为了让手机连上而跳过FIFO barrier。

`CLOSE_PREPARED`的语义是“固件已接受不可撤销的关闭意图，等待COMMIT并最迟在宽限timer到期时收敛”，不是“物理ACL已断开”。PC App提交COMMIT并确认平台已将该Write Without Response加入发送队列后，才可清理自己的GATT对象；手机仍要等firmware runtime进入`READY`才能成功claim。

### 5.6 忙状态策略

PC App正常关闭前必须主动结束录音、文件传输和其他前台事务。固件在接受`CLOSE_PREPARE`前复用并补强`rdx_app_rdx_rebind_is_idle()`检查：

- 普通录音、播放、file/bulk/sync仍在收尾：返回`BUSY_RETRY`，PC App等待业务完成后重试；
- OTA、格式化等不可中断操作：明确返回`BUSY_RETRY`，禁止直接逻辑释放；
- PC App已取消业务且worker能够安全收敛：进入`CLOSING_WAIT_COMMIT`；
- 物理ACL突然断开不受上述拒绝策略限制，仍走现有强制abort、barrier和fail-closed清理。

第一期不建议“收到CLOSE_PREPARE就无条件杀掉所有任务”，否则容易把正常业务结束错误隐藏成关闭成功。PC App关闭流程应有明确的业务drain超时和错误提示。

### 5.7 只释放RDX capability

`rdx_ble_session`需要新增per-capability release API，不调用`rdx_ble_session_link_release()`：

```text
before: connected=1, capability=RDX_HID, rdx_owner=slot0, hid_owner=slot0
after:  connected=1, capability=HID,     rdx_owner=INVALID, hid_owner=slot0
```

逻辑释放必须保留：

- `ble_hdl`、`con_handle`和wrapper映射；
- `slot_generation`；
- link的`connected`、MTU和连接参数；
- peer address、peer identity及加密状态；
- HID owner index、bonded HID CCC、suspend/ready状态；
- HOGP report发送和键盘输入能力。

逻辑释放只清除：

- link上的`RDX` capability bit；
- `rdx_link_index`和RDX compatibility index；
- `rdx_runtime_active`、RDX CCC mirror和stream ready mirror；
- 当前RDX session binding、请求缓存和lease timer；
- 旧RDX transport token可见性。

`slot_generation`代表物理slot的连接代次，逻辑关闭时不能递增；RDX runtime/transport epoch在`begin_quiesce`时递增，用于使旧异步token失效。只有物理ACL释放时才递增slot generation并清空整个link。

### 5.8 物理断开与逻辑断开的汇合

建议把当前`rdx_ble_server_phase2_rdx_detach()`重构为带原因的共同入口：

```c
enum rdx_detach_cause {
    RDX_DETACH_PHYSICAL,
    RDX_DETACH_LOGICAL_COMMIT,
    RDX_DETACH_CLOSE_GRACE_TIMEOUT,
    RDX_DETACH_LEASE_TIMEOUT,
};
```

共同入口始终负责：timer cancel、同步业务cleanup、session abort、send worker quiesce、`__rdxlc` barrier、worker idle和最终buffer reset。原因只决定registry的link处理方式：

| 原因 | RDX cleanup | Registry动作 | HID/ACL |
|---|---|---|---|
| `PHYSICAL` | 执行一次 | 随后调用现有整条`link_release` | HID本地清理，ACL已断开 |
| `LOGICAL_COMMIT` | 执行一次 | 只调用`release_rdx` | 完全保留 |
| `CLOSE_GRACE_TIMEOUT` | 与COMMIT相同 | 只调用`release_rdx` | 完全保留 |
| `LEASE_TIMEOUT` | 与逻辑关闭相同 | 只调用`release_rdx` | 完全保留 |

如果物理断开到达时RDX已经处于`CLOSING_WAIT_COMMIT/QUIESCING/RESETTING`，物理路径先取消close-grace timer并将关闭上下文置为不可再次执行。若runtime尚未进入`QUIESCING`，由物理原因启动一次共同detach；若barrier已经在途，物理路径只清link/HID并继续等待现有barrier，不得再次插入第二个barrier。

### 5.9 异常退出的心跳租约

PC App在发送`CLOSE_PREPARE`之前就崩溃、被强杀或遇到Windows异常时，5秒close-grace timer尚未建立，第二期使用session lease兜底：

- 仅在`OPEN`双方协商出非0 `accepted_lease_s`后启用；
- PC App每`5 s`发送当前`session_id`的`HEARTBEAT`，固件建议从`15 s`租约开始验证；
- 固件收到合法heartbeat后，在`btstack`上下文按当前owner token重置timer；
- stale session、非owner link或旧epoch heartbeat不得续租当前owner；
- 租约超时先检查OTA/格式化等不可中断操作；可释放时走`RDX_DETACH_LEASE_TIMEOUT`共同路径；
- 不可中断时进入明确的`LEASE_EXPIRED_BUSY`内部状态，停止接受新普通业务，待安全点再收敛；
- Windows睡眠、现代待机、App后台节流和系统时间跳变必须完成测试后才能默认启用。

现有`*APP#active#`和`RECORD_HEARTBEAT_SUPPORT`只属于录音保活语义，不能直接作为RDX session lease。

## 6. 固件端实施方案

### 6.1 文件与职责拆分

建议按以下边界实施，避免把协议codec、registry和业务清理继续堆在一个函数中：

| 文件 | 具体修改 |
|---|---|
| `rdx_session_control.h/.c`（新增） | `rdxsession v1`编解码、CRC、session binding、request幂等缓存、PREPARED响应缓存、COMMIT匹配和close-grace timer上下文 |
| `rdx_app.c/.h` | 在`rdx_app_custom_command_parse()`中先分发内部`__rdxlc`和外部`rdxsession`，再执行普通custom命令的`runtime == ACTIVE`检查 |
| `rdx_ble_session.h/.c` | 新增`CLOSING_WAIT_COMMIT`状态和`rdx_ble_session_release_rdx()`，保持原`link_release()`语义不变 |
| `rdx_ble_server.c/.h` | ingress owner-token绑定、PREPARED定向发送、COMMIT/timer投递、普通业务门控、logical/physical共同detach及日志 |
| `SDK/Makefile` | 将新增codec/control源文件加入RDX源码列表 |
| `tests/host/test_rdx_lifecycle_contract.ps1` | 增加两阶段逻辑释放、owner token、幂等、超时和物理兼容契约 |

`librdxApp.a`不可修改；新增逻辑必须继续利用现有nonce FIFO barrier证明旧receive队列已排空。

### 6.2 Registry API建议

新增API应要求调用方提供link及期望generation，示意签名：

```c
u8 rdx_ble_session_rdx_runtime_begin_wait_commit(
    rdx_ble_link_state_t *link,
    const rdx_ble_async_token_t *token);

u8 rdx_ble_session_release_rdx(
    rdx_ble_link_state_t *link,
    u32 expected_slot_generation);
```

`release_rdx()`必须逐项校验：link仍connected、generation一致、link仍是RDX owner、runtime处于合法关闭状态。成功后只清RDX字段和owner index。Host contract必须断言函数体不调用`rdx_ble_session_link_clear()`，也不写HID owner index。

`begin_wait_commit()`只允许`ACTIVE -> CLOSING_WAIT_COMMIT`，立即清`link->rdx_runtime_active`以关闭现有普通发送门，但保持RDX owner、link capability、slot generation和transport epoch不变，使同一owner后续COMMIT仍可通过原token校验。只有共同detach调用`begin_quiesce()`时才递增transport epoch并使旧异步结果失效；`begin_quiesce()`需要同时接受从`ACTIVE`和`CLOSING_WAIT_COMMIT`进入。

`rdx_ble_server_phase2_rdx_write()`必须在调用`phase2_rdx_attach()`之前识别等待COMMIT状态：只有来源link与close上下文保存的owner token完全匹配、ATT handle为`0x0006`时，才绕过attach并继续送入组包器；其他handle或link全部拒绝。这个特例只保持控制帧可达，不得把runtime改回`ACTIVE`。

现有`rdx_ble_session_rdx_token_resolve(token, 1)`硬性要求runtime为`ACTIVE`，不能直接用于等待COMMIT阶段。PREPARED发送、COMMIT和close-grace专用路径应先用link-level token resolve，再显式校验link仍为RDX owner、状态为`CLOSING_WAIT_COMMIT`、session和close上下文完全匹配。普通业务发送继续使用`require_runtime_active=1`，禁止为了支持关闭而全局放宽token发送规则。

`rdx_ble_session_link_release()`保持原样服务于物理断开；不要把它改成默认只清RDX，否则手机APP和真实ACL掉线会留下伪连接slot。

### 6.3 自动claim、来源绑定与入站门

现有调用顺序必须作为实现前提保留：`rdx_ble_server_phase2_rdx_write()`先调用`rdx_ble_server_phase2_rdx_attach(link)`，完整数据随后才经`rdx_protocol_packet_recv()`到达异步parser。`OPEN`不是ownerless claim命令，而是对已经自动claim成功的当前owner做managed-session绑定。`QUERY`同样不能在无owner状态下解析或抢占。

`rdx_app_custom_command_parse(cmd, value)`当前没有link参数，而`rdx_protocol_packet_recv(buf, len)`也不能携带元数据，因此不能在parser里把“当前全局owner”直接当作来源。固件必须增加受runtime epoch保护的control ingress上下文：

1. runtime `ACTIVE`下第一笔`0x0006`写入通过自动claim后，在送入RDX FIFO前捕获并绑定`slot_index + slot_generation + transport_epoch`；
2. 同一个runtime epoch只允许绑定一个ingress owner token；后续分片只校验来源link与已保存token一致，不在`CLOSING_WAIT_COMMIT`中重新捕获active token；
3. parser识别出`rdxsession`后取出该epoch绑定的token，并把token连同已解码帧投递到`btstack`；
4. `btstack`回调重新resolve token，并确认它仍是当前RDX owner和对应session后才能改状态或发送响应；
5. 物理断开或`begin_quiesce()`使transport epoch变化后，旧parser结果只能被丢弃，不能回落到新的当前owner。

由于当前RDX只有一个全局owner，且新owner必须等待旧FIFO barrier和runtime `READY`，这里采用“每个runtime epoch一个ingress token”，不需要给不可修改的库API增加逐包元数据。但这一关联必须有Host contract；如果实现无法证明parser结果和ingress token属于同一epoch，v1应fail closed，不能靠`con_handle`或当前owner猜测来源。

`rdx_app_custom_command_parse()`的分发顺序固定为：

```text
1. 内部__rdxlc barrier匹配
2. 外部rdxsession控制命令解析并携带ingress token投递
3. runtime必须为ACTIVE且managed session不在closing
4. hogpkm、ft_*及其他普通custom命令
```

同时在`rdx_ble_server_phase2_rdx_write()`和所有可修改的RDX业务入口增加状态门：

- `ACTIVE + managed session ACTIVE`：普通RDX data/OTA/CCC按现有路径处理；
- `CLOSING_WAIT_COMMIT`：同一owner的`0x0006`数据可以继续进入组包器，以便解析COMMIT或重复PREPARE，但App必须停止普通写；固件所有普通业务入口必须检查session/runtime状态并拒绝执行，OTA写在BLE入口直接拒绝；
- `QUIESCING/RESETTING/FAILED`：拒绝data/OTA/CCC，不能再次调用`phase2_rdx_attach()`；
- runtime回到`READY`且物理HID link仍在：新的CCC写、`OPEN`或legacy首包仍沿用现有自动claim；MVP不承诺“只有OPEN才能claim”，以保留旧版PC App兼容。

控制帧可能跨多个ATT Write，不能在单个write回调里用`memcmp()`猜完整命令。`CLOSING_WAIT_COMMIT`期间的安全性依赖两项共同约束：PC App停止普通写；固件在所有可达业务入口做状态门控。若审计发现不可修改库在这些入口之前已经执行不可逆业务，则必须改用BLE层独立的增量control deframer，不能带着该缺口发布。

### 6.4 跨task执行

`rdxsession`最终由RDX receive task解析，而link registry和ATT发送事件在BTStack路径。建议新增固定投递函数：

```text
receive task解析控制帧
  -> 读取并携带该runtime epoch的ingress owner token
  -> os_taskq_post_type("btstack", Q_CALLBACK, ...)
  -> btstack callback重新resolve token
  -> 改状态、发PREPARED或处理COMMIT
```

消息参数不能只带`con_handle`，因为handle和slot都可能复用。投递失败时返回`INTERNAL_ERROR`或保持当前owner，不允许在receive task直接清registry作为补救。

物理断开会使slot generation或transport epoch变化，因此晚到的PREPARE、COMMIT、heartbeat和timer callback都会在resolve时自然失效。每一类stale事件都应有节流日志，不能执行清理当前新owner的副作用。

### 6.5 PREPARE/COMMIT实施

在`rdx_session_control`中增加专用close上下文，至少包含：

```text
active / detach_started
session_id
prepare_request_id
prepare_request_crc32
owner token
cached PREPARED response bytes/CRC
close_grace_timer_id
monotonic deadline
```

处理`CLOSE_PREPARE`时，`btstack`回调按以下顺序执行：

1. resolve owner token并校验当前session仍为`ACTIVE`；
2. 检查RDX Notify CCC和token定向发送路径可用，并确认record/file/bulk/OTA等业务已经可关闭；业务忙时返回`BUSY_RETRY`，发送路径未就绪时保持`ACTIVE`并记录错误，不创建close上下文；
3. 原子进入`CLOSING_WAIT_COMMIT`，保存完整PREPARE身份和owner token；
4. 先启动建议为`5 s`的close-grace timer，再生成并缓存`CLOSE_PREPARED`响应；
5. 通过token定向Notify提交缓存响应；提交失败不回滚关闭意图，重复的同一PREPARE再次尝试发送同一缓存响应；
6. 相同`session_id + request_id + request CRC`的重复PREPARE保持幂等；同session但不同request在等待期返回冲突，不得替换已接受的COMMIT匹配键。

处理`CLOSE_COMMIT`时必须同时匹配owner token、`session_id`和原PREPARE的`request_id`。匹配成功后原子设置`detach_started`、取消close-grace timer并以`RDX_DETACH_LOGICAL_COMMIT`进入共同detach。COMMIT没有最终响应；重复COMMIT、晚到COMMIT和非owner COMMIT只能被幂等忽略或记stale日志。

close-grace timer回调不能直接使用旧指针。它携带完整owner token投递到`btstack`，重新resolve并再次匹配close上下文；只有`detach_started == false`时才能原子置位并以`RDX_DETACH_CLOSE_GRACE_TIMEOUT`进入同一detach。COMMIT与timer竞争时必须保证共同detach恰好执行一次。

`ATT_EVENT_CAN_SEND_NOW`只代表ATT流控许可，不是某条Notification的完成回调，也没有request ID。它可以继续服务现有普通发送队列，但不得修改close上下文、不得取消close-grace timer、不得触发`CLOSING_WAIT_COMMIT -> QUIESCING`。

### 6.6 Cleanup重构顺序

共同detach内部顺序建议固定为：

1. 校验cause、runtime和owner token，保证只执行一次；
2. `rdx_ble_session_rdx_runtime_begin_quiesce()`使旧RDX token失效；
3. 对逻辑原因调用`rdx_ble_session_release_rdx()`；物理原因保留后续`link_release()`；
4. 取消sync/stream/lease/close-grace timer并冻结session control上下文；
5. 清pending send、send fail count和RDX全局connection mirror；
6. 执行`rdx_ble_server_rdx_disconnected_cleanup_internal()`；
7. 执行`rdx_ble_server_rdx_session_abort()`和send worker quiesce；
8. 生成随机nonce并向FIFO插入`*APP#custom#__rdxlc#<nonce>#`；
9. barrier到达后再次abort，等待`rdx_app_rdx_rebind_is_idle()`；
10. 执行最终buffer reset并`runtime_rearm()`到`READY`。

若barrier入队失败、worker无法idle或rearm失败，进入`FAILED`。逻辑关闭不能因为HID仍在线就绕过该安全边界。

### 6.7 固件日志

建议至少固定以下可自动解析的日志字段：

```text
[RDX_SESSION_CTL] open sid=%08x rid=%u slot=%u gen=%u epoch=%u result=%u
[RDX_SESSION_CTL] close prepare sid=%08x rid=%u reason=%u result=%u
[RDX_SESSION_CTL] close prepared queued sid=%08x rid=%u deadline_ms=%u
[RDX_SESSION_CTL] close commit sid=%08x rid=%u result=%u
[RDX_SESSION_CTL] close grace timeout sid=%08x rid=%u slot=%u gen=%u epoch=%u
[RDX_BLE_SESSION] logical detach cause=%u con=0x%04x capability=%u->%u
[RDX_BLE_SESSION] physical detach con=0x%04x reason=0x%02x
[RDX_SESSION_CTL] stale event dropped type=%u slot=%u gen=%u epoch=%u
[RDX_SESSION_CTL] lease renewed/expired sid=%08x ...
```

日志禁止打印密钥、完整业务payload或可长期追踪的peer identity；`session_id`只在本次App进程内随机使用。

## 7. PC App端对接实施方案

### 7.1 App状态拆分

PC App不能再用一个`connected`布尔值同时表示GATT对象、RDX会话和物理ACL。至少维护：

```text
gatt_state: DISCONNECTED / CONNECTING / CONNECTED
rdx_session_state: NONE / OPENING / ACTIVE /
                   CLOSING_PREPARE / CLOSING_COMMIT /
                   CLOSED / ERROR
session_id: uint32
next_request_id: uint16
lease_seconds: uint16
last_heartbeat_ack: monotonic timestamp
```

Windows是否仍为HID保留物理ACL不由PC App直接控制，UI和日志中不要把`gatt_state=DISCONNECTED`描述成设备物理断开。

### 7.2 建立会话

PC App每次取得新的GATT对象后执行：

1. 发现现有RDX service和`0x0006/0x0008`特征；
2. 先调用`startNotifications()`并确认监听器已安装；该CCC写可能已经触发现有固件自动claim；
3. 使用系统CSPRNG生成非0 `session_id`，进程内不得复用旧关闭session；
4. 分配非0 `request_id`并编码`OPEN`；
5. 通过现有分包器写入`*APP#custom#rdxsession#<HEX>#`；
6. 等待匹配`session_id + request_id + opcode`的响应；
7. 收到`OK`后才开放录音、文件、配置等业务入口；
8. 记录固件flags和lease协商值。

建议`OPEN`响应超时先取`1500 ms`，使用同一request最多重试3次；具体值再根据Windows BLE实测分布冻结。重复发送必须保持frame完全一致，不能只复用request ID却改变payload。

### 7.3 正常关闭

所有正常入口，包括用户点击断开、切换设备、退出App、注销和受控关机，共用一个可重入的`closeRdxSession(reason)`：

```text
设置rdx_session_state=CLOSING_PREPARE，原子禁止新业务
  -> 停止heartbeat
  -> 停止/取消录音、播放、文件、bulk、OTA入口
  -> 等待业务future与发送队列收敛
  -> 发送CLOSE_PREPARE(session_id, request_id, reason)
  -> 等待CLOSE_PREPARED: OK或ALREADY_CLOSING
  -> 设置rdx_session_state=CLOSING_COMMIT
  -> 发送匹配的CLOSE_COMMIT(session_id, 同一request_id)
  -> 等待平台确认Write Without Response已加入本地发送队列
  -> 清本地session
  -> stopNotifications()
  -> 释放GATT service/device对象
  -> 调用平台gatt.disconnect()作为本地资源清理
```

这套顺序在两种PC拓扑下完全一致：

- PC App单独使用：逻辑关闭完成后，Windows可能继续终止唯一ACL，固件随后再收到`reason=0x13`物理回调；
- PC App与HOGP复用：Windows只销毁App GATT对象，ACL和HID继续保持，固件不会也不需要收到HCI断开回调。

不要先`stopNotifications()`或`gatt.disconnect()`再完成PREPARE/COMMIT，否则App会主动销毁唯一可接收`CLOSE_PREPARED`的通道。平台的Write Without Response完成回调通常只证明COMMIT已进入本地系统发送队列，不证明固件收到；固件5秒close-grace timer负责覆盖COMMIT丢失，但App仍应记录本地提交结果。

### 7.4 重试与结果处理

建议PC App按下表处理：

| 结果 | 动作 |
|---|---|
| PREPARE返回`OK` / `ALREADY_CLOSING` | 不得立即清session；转入`CLOSING_COMMIT`并发送匹配COMMIT |
| 平台先报告GATT/ACL物理断开 | 视为终态成功，取消PREPARE/COMMIT等待；固件物理路径负责cleanup |
| PREPARE返回`BUSY_RETRY` | 保持GATT和session，等待在途业务结束；业务条件变化后使用新request ID重新发起PREPARE |
| `STALE_SESSION` / `NOT_OWNER` | 清本地session，禁止继续发送旧业务；按需重新连接并`OPEN` |
| PREPARE CRC/超时 | 在首次发送后的`3 s`内，用同一session、request ID和完整frame有限重发；不得越过固件5秒宽限窗口继续重试 |
| PREPARE全部超时 | 保持Notify和GATT对象至少覆盖最后一次PREPARE后的固件宽限窗口，然后标记`close_unconfirmed`并释放本地对象；UI不得宣称固件RDX已释放 |
| COMMIT本地入队失败 | 在固件5秒宽限到期前重发完全相同的COMMIT；不得更换session/request ID；最终仍由固件宽限超时收敛 |

同一PREPARE的超时重试必须保持frame逐字节一致，才能命中固件幂等缓存；收到`BUSY_RETRY`后因关闭尚未被接受，才允许在业务收敛后创建新request。建议把PREPARE重试调度限制在首次发送后的`3 s`内，为固件`5 s`宽限留出COMMIT时间。

App进程退出钩子只能做best effort，不能依赖异步关闭必然在进程被强杀前完成。用户主动退出应走完整有限等待；若操作系统强制结束进程，可以释放本地资源，但必须记录`close_unconfirmed`。若固件从未收到PREPARE，close-grace不会启动，只有第二期lease或后续物理断开能够兜底。

### 7.5 Heartbeat第二期

只有`accepted_lease_s > 0`时启动heartbeat：

- 周期使用单调时钟，不使用系统墙上时间；
- 每次带当前session ID，响应必须匹配session和request；
- 连续heartbeat失败时先把业务入口置为只读/暂停，再尝试重连；
- App进入Windows suspend前尽力发送最后一次heartbeat；resume后立即heartbeat或重新`OPEN`；
- 退出正常路径仍必须完成`CLOSE_PREPARE/CLOSE_COMMIT`，不能等lease自然超时。

### 7.6 PC App日志与测试桩

日志至少包含：固件版本、协议版本、session ID、request ID、opcode、status、重试次数、单调时间耗时、`gatt_state`与`rdx_session_state`。不要只记录`connected:false`。

PC App应增加可重复自动化场景：

- 正常`OPEN -> CLOSE_PREPARE -> CLOSE_COMMIT`；
- PREPARED延迟、丢失、重复和乱序；
- PREPARE或COMMIT发送后GATT先物理断开；
- `BUSY_RETRY`后重试；
- COMMIT缺失后固件close-grace timeout；
- PREPARE全部超时后的`close_unconfirmed`界面与日志；
- 旧session response晚到；
- App崩溃模拟及heartbeat停止；
- 单独ACL与共享ACL使用同一个关闭函数的断言。

## 8. 兼容与发布策略

### 8.1 版本组合

| PC App | 固件 | 结果 |
|---|---|---|
| 旧版 | 旧版 | 保持现状；共享ACL时无法逻辑释放 |
| 旧版 | 新版 | legacy自动claim仍可用；共享ACL时仍无法主动逻辑释放 |
| 新版 | 旧版 | `OPEN`无响应后进入明确legacy兼容模式；共享ACL限制仍存在并记录告警 |
| 新版 | 新版 | 使用`rdxsession v1`，单独和共享ACL统一逻辑关闭 |
| 手机APP | 新版 | 手机不需要改；物理ACL断开继续触发原cleanup |

新版PC App只有收到`OPEN OK`才能宣称设备支持logical close。不能因为固件能识别其他custom命令就推断支持`rdxsession`。

### 8.2 分期落地

建议按以下顺序发布：

1. 协议冻结：PC App与固件共同确认v1字段、status、超时和日志；保存golden frame及CRC测试向量；
2. 固件一期：实现`OPEN`、`CLOSE_PREPARE`、`CLOSE_COMMIT`、`CLOSING_WAIT_COMMIT`、close-grace timer、per-capability release、共同cleanup和Host contract，lease保持关闭；
3. PC App一期：所有正常关闭入口统一调用session close；在单独ACL和共享ACL上完成联调；
4. 灰度验证：至少10轮PC/手机RDX往返，验证HID不重枚举；
5. 固件与PC App二期：共同启用heartbeat/lease，再验证Windows睡眠和后台节流；
6. 量产启用：只有新固件与新版PC App组合完成矩阵后，才能关闭“shared-ACL logical release pending”问题。

## 9. Host contracts

在`test_rdx_lifecycle_contract.ps1`至少新增以下静态/结构契约：

- logical release不调用整条`rdx_ble_session_link_release()`；
- `RDX_HID -> HID`后`connected/con_handle/slot_generation/hid owner`保持；
- 现有自动claim发生在`OPEN`绑定之前，`OPEN`只绑定当前active owner及其ingress token；不存在ownerless `OPEN/QUERY`解析路径；
- parser结果必须携带并重新校验该runtime epoch的ingress owner token，不能按当前owner或单独`con_handle`猜来源；
- PREPARE接受后先进入`CLOSING_WAIT_COMMIT`并建立close-grace timer，再按owner token提交缓存的PREPARED响应；
- `ATT_EVENT_CAN_SEND_NOW`不能推进close状态、取消close-grace timer或触发detach；
- `CLOSING_WAIT_COMMIT`期间不能再次attach，普通RDX业务入口和OTA必须拒绝执行，但同owner控制流仍可解析COMMIT/重复PREPARE；
- 匹配的COMMIT或携带同一owner token的close-grace timer只能有一个成功进入共同detach；
- logical release必须经过runtime quiesce、nonce barrier、worker idle和rearm；
- PREPARE、COMMIT、close-grace和heartbeat timer都携带并重新校验owner token；
- stale/non-owner PREPARE或COMMIT不能释放当前owner；
- 重复PREPARE返回缓存响应；同request ID但不同CRC返回冲突；COMMIT必须匹配PREPARE的session/request；
- physical disconnect仍能清理该link上的RDX和HID；
- logical close后到达physical disconnect不会插入第二个barrier；
- `__rdxlc`仍是internal-only，外部命令只能使用`rdxsession`；
- force-disconnect timer不得作为PC逻辑关闭实现；
- legacy手机/PC首包claim路径仍存在。

协议codec应增加golden tests：合法`OPEN`、`CLOSE_PREPARE`、`CLOSE_COMMIT`、大小端、奇数HEX、超长payload、CRC错误、未知版本/opcode、PREPARE与COMMIT不匹配、request ID冲突和重复请求。

## 10. 真机验收矩阵

```text
[ ] 1. 新PC App在独占ACL上OPEN成功，PREPARE -> PREPARED -> COMMIT后逻辑cleanup完成
[ ] 2. 独占ACL随后出现reason=0x13物理回调，不重复barrier、不进入FAILED
[ ] 3. PC/HID保持ready，PC App取得RDX并形成RDX_HID复合owner
[ ] 4. 共享ACL上出现CLOSING_WAIT_COMMIT -> COMMIT -> QUIESCING -> barrier -> READY，无HCI disconnect
[ ] 5. 逻辑关闭全过程Windows键盘持续输入，不重新枚举、不重新配对
[ ] 6. PC App logical close完成后手机在第二条ACL成功claim RDX并执行真实命令
[ ] 7. 手机释放后PC App可在原HID ACL重新OPEN，往返至少10轮
[ ] 8. PC App录音活动中PREPARE：App先停止；固件busy时返回BUSY_RETRY，不遗留旧录音事件
[ ] 9. 文件/bulk活动中PREPARE：旧数据不发送给手机新owner
[ ] 10. OTA/格式化期间PREPARE：明确BUSY_RETRY，不破坏存储
[ ] 11. 重复PREPARE返回缓存响应；旧session、错误request和非owner COMMIT不能释放新owner
[ ] 12. PREPARED Notify首次提交失败或丢失时，同一PREPARE可重试且仍只建立一个timer
[ ] 13. PREPARED已收到但COMMIT缺失，5秒close-grace timeout只释放RDX并保留HID
[ ] 14. COMMIT与close-grace timer并发、或COMMIT后立即物理断开，cleanup仍只执行一次
[ ] 15. 任意link的ATT_EVENT_CAN_SEND_NOW都不会推进RDX关闭状态
[ ] 16. PC App崩溃且从未发送PREPARE后，lease超时只释放RDX并保留HID（二期）
[ ] 17. Windows睡眠/唤醒及App后台节流不会误触发lease（二期）
[ ] 18. logical close收敛失败保持FAILED/fail closed，不允许手机提前claim
[ ] 19. 手机APP物理断开仍走原路径，无需发送rdxsession命令
[ ] 20. 旧版PC App与新固件仍可完成原有独占ACL连接/断开
[ ] 21. 全程无cross-send、stale callback、assert、watchdog或异常复位
[x] 22. PC App单独占用ACL时，主动断开连续两轮收到reason=0x13并完成runtime收敛
[x] 23. 手机RDX与PC-HID分占两条ACL时，两条链路的物理断开分别命中正确wrapper
```

共享ACL正常关闭的预期关键日志顺序应固定为：

```text
RDX_SESSION_CTL close prepare ... result=OK
RDX_SESSION_CTL close prepared queued ... deadline_ms=5000
RDX_SESSION_CTL close commit ... result=OK
RDX_BLE_SESSION logical detach cause=LOGICAL_COMMIT ... RDX_HID->HID
RDX_BLE_SESSION runtime QUIESCING ... drain barrier queued
RDX_BLE_SESSION receive FIFO drain barrier reached
RDX_BLE_SESSION runtime READY: FIFO drained and workers idle
```

COMMIT缺失的超时路径只把第三、四行替换为`close grace timeout`和`cause=CLOSE_GRACE_TIMEOUT`，后续cleanup完全相同。两种序列中都不得出现`HCI_EVENT_DISCONNECTION_COMPLETE`、`HOGP disconnect`或HID重新配对；随后手机claim才算闭环。

## 11. 当前可接受的临时边界

在固件和PC App共同完成显式逻辑释放前，产品与测试必须按以下事实解释结果：

- 手机RDX物理断开后由PC App接管：已支持并已验证；
- PC App单独占用ACL并主动断开：Windows会终止物理ACL，固件回调及RDX cleanup已验证正常；
- PC App只调用应用侧`disconnect`且Windows HID仍在线：RDX owner不会释放；
- 此时手机无法接管是已知阻塞，不是跨peer reset修复失效；
- 若必须立即让手机接管，只能让PC物理ACL真正断开或重启设备，但这不是最终用户流程；
- 不允许通过恢复同peer锁、清空全局registry、强制踢掉HID ACL或固定空闲超时掩盖问题。

本问题的关闭条件是：固件一期、PC App一期、Host contract及第10节非lease真机项全部通过。心跳租约可作为异常退出增强单独跟踪，但在没有完成显式`CLOSE_PREPARE/CLOSE_COMMIT`前不能宣称正常关闭链路已经解决。
