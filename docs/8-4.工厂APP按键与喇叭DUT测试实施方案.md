# 工厂 APP 按键与喇叭 DUT 测试实施方案

> 更新日期：2026-09-18
>
> 状态：固件已实施，主机检查与构建通过，APP/实机验收待执行。接口依据为 [8-3.工厂APP按键与喇叭测试对接说明](8-3.工厂APP按键与喇叭测试对接说明.md)。第 11 节记录实际落地方式与验证边界。

## 1. 目标与范围

在 `SDK/apps/common/third_party_profile/rdx_protocol/rdx_dut.c` 中新增按键检测和喇叭播放两项 DUT 测试，沿用现有 BLE RDX 自定义命令、通知订阅、DUT 进入流程和单项互斥机制。

本次编码以 `rdx_dut.c/h` 为主，补充原始按键入口、会话清理、正弦波供数任务和 host 验证。进入 DUT 不主动查询或上报布局，喇叭测试不依赖按键查询。测试结果由 APP 保存：按键按标识集合计分，喇叭由工人听音判断。

## 2. 现有实现与缺口

| 位置 | 当前实现 | 本次需要补齐 |
|---|---|---|
| `rdx_app.c::rdx_app_custom_command_parse()` | 将 `ft_` 命令交给 DUT 模块 | 沿用入口，核实新增命令完整到达 |
| `rdx_dut_ble_cmd_handle()` | 多数命令用 `strstr`、`atoi` 匹配，投递 `app_core`，部分立即回包 | 新命令精确匹配、严格校验值，区分按键停止无回包与喇叭开始/停止有回包 |
| `rdx_dut_cmd_async_handle()` | 在 `app_core` 执行；包装完成处理中阻止命令 | 增加按键布局/停止、喇叭开始/停止，执行时复核 DUT 和会话有效性 |
| `current_func` / `rdx_dut_close_current_func()` | 单项互斥及统一关闭 | 增加 KEY、SPEAKER，并覆盖停止中的资源占用 |
| `rdx_dut_key_handle(int key_msg)` | 根据单击、多击切换 LED、马达、录音等 | 此入口已是业务消息，不能作为五键物理身份来源 |
| `rdx_app_earphone_key_remap()` | `KEY_IO_NUM0～4` 先分流至 HID、KEY5 录音或本地键表 | 新测试期间在这些分支前消费物理键事件 |
| `rdx_app_online_key_down()` | 目前仅为 NUM0～3 投递电量灯效；由 `apps/earphone/mode/key_tone.c` 调用 | 核实消抖后的按下入口，覆盖全部待测键，避免测试附带灯效/提示音 |
| `rdx_ble_server_send_for_token()` | 提供 token 绑定的异步发送 | 用于布局、按键事件与喇叭回包，防止会话更换后发送给新 owner |

当前工具生成的 `sdk_config.c::g_iokey_info[]` 配置如下。本次沟通确认 A～E 依次对应 NUM0～4，排列为三行两列 `A,B&C,D&E`，第三行只有 E；实机验收仍需逐键核对。

| 原始键值 | GPIO |
|---|---|
| `KEY_IO_NUM0` | PG7 |
| `KEY_IO_NUM1` | PB2 |
| `KEY_IO_NUM2` | PG8 |
| `KEY_IO_NUM3` | PB4 |
| `KEY_IO_NUM4` | PC2 |

PB1 为拨码电源开关，不列入待测按钮，不拦截其关机路径。保持生成配置文件的所有权，不直接修改 `sdk_config.c/h` 或 `iokey_config.c` 来添加厂测布局。

## 3. 命令契约

按 8-3 第 3 节具体报文落实：喇叭开始、停止均有回包，按键停止无回包。8-3 第 1 节已同步修正。

固件按“动作完成确认”实现：首次成功向 DAC 供数后回 `1`，本项资源释放且音量/静音恢复后回 `0`。该行为已写入 8-3；APP 超时与重试策略仍需联调验证。

| APP 请求 | 设备行为 | 回包 |
|---|---|---|
| `*APP#custom#ft_key_layout#`（兼容参数 `1`） | 校验条件，取得完整布局并启动检测 | `*DEV#custom#ft_key_layout#<布局>#` |
| `*APP#custom#ft_key#0#` | 停止按键检测，清除本轮待发事件 | 无 |
| `*APP#custom#ft_speaker#1#` | 启动固定音频 | `*DEV#custom#ft_speaker#1#` |
| `*APP#custom#ft_speaker#0#` | 停止本项音频并释放资源 | `*DEV#custom#ft_speaker#0#` |
| 设备主动事件 | 每次有效物理按下对应一个标识 | `*DEV#custom#ft_key_event#E#`，其中 E 仅为示例 |

新增命令使用 `strcmp` 精确匹配。`ft_key_layout` 接受空参数或字符串 `1`，`ft_key` 仅接受 `0`，`ft_speaker` 仅接受 `0` 或 `1`。不得通过子串命中旧的 `ft_key_dut_enable/disabled`，不得新增 `ft_key#1#` 启动命令。按键停止不回包；喇叭开始、停止分别返回上表中的 `1`、`0`。

旧 DUT 命令入队后校验原 RDX owner 和会话代次，不要求数据流已就绪：现有 APP 会先发 `ft_dut#1#`，再完成 appkey/write-ready。新增按键和喇叭测试仍需通知及数据流就绪。

布局语法严格沿用 8-3：`,` 分隔列，`&` 分隔行，标识按实物从上到下、从左到右分配。`NONE` 只表示产品无待测按键，不能用于忙、发送失败或配置错误。

8-3 尚未定义错误回包格式。本阶段不自行添加 `ERROR`、错误码或新命令；非法值、非 DUT、互斥冲突等失败不得返回非空成功布局，也不得启动检测，记录诊断日志。布局无响应由 APP 超时处理，超时时间和是否补充错误格式列入联调确认项。

## 4. 状态、顺序与互斥

### 4.1 单一执行上下文

沿用 `app_core` 作为 DUT 状态和音频操作的执行上下文。新增 BLE 请求在接收时复制命令参数和会话 token，不保留解析缓冲区指针；回调执行时再次校验 DUT 模式、包装流程、关机/存储生命周期门禁及原会话有效性。

按键扫描回调只投递小型事件，不在扫描任务中直接发 BLE、控制音频或修改共享业务状态。事件携带捕获时的测试代次；停止后旧事件即使迟到，也不能进入下一轮。

新增 `DUT_FUNC_KEY`、`DUT_FUNC_SPEAKER`；内部另外记录按键准备状态和喇叭停止状态。所有旧、新测试仍共用 `current_func` 互斥。上一项未停止就请求另一项时拒绝启动，不隐式替 APP 停掉上一项。

### 4.2 停止完成后再启动

APP 可以连续发送“停止上一项、启动下一项”，固件不能依赖 APP 等回包来保证互斥。按键停止没有 ACK；喇叭停止已有回包，APP 是否等待及超时策略需与更新后的接口说明统一。审查现有各项 stop 是否同步释放资源；若只是发出异步停止请求，应保持该项占用，等待完成后按接收顺序执行下一条命令。

实现一个有界的 DUT 顺序处理机制，资源释放完成前不越过停止操作。队列容量、失败日志和取消路径需明确；投递失败不能记录为执行成功。若停止命令无法排队，应设置可由 `app_core` 可靠观察的取消请求，阻止后续启动，避免喇叭持续播放。不得在蓝牙任务中阻塞等待音频关闭。

| 状态/输入 | 处理 |
|---|---|
| 空闲 + 有效布局查询 | 占用 KEY，完成布局发送排序后开放事件 |
| KEY + 同会话重复查询 | 暂停事件发送，重发布局；保持本项占用，不切换其他测试 |
| KEY + 按键停止 | 关闭事件入口，失效旧代次，清空待发数据，回到空闲 |
| 空闲 + 喇叭开始 | 占用 SPEAKER，启动成功后回 `ft_speaker#1`；失败则释放占用 |
| SPEAKER + 重复开始 | 确认已在播放后回 `ft_speaker#1`，不叠加播放器、不重复修改音量 |
| SPEAKER + 喇叭停止 | 禁止续播，等待本项播放器停止，恢复临时设置后回到空闲，回 `ft_speaker#0` |
| 已停止 + 同项停止 | 幂等，不影响其他测试；按键停止无回包，喇叭停止回 `ft_speaker#0` |
| 另一项运行 + 开始请求 | 拒绝启动，保留当前项 |
| DUT 退出或会话撤销 | 撤销本轮，停止资源，丢弃迟到回调 |

## 5. 按键测试实现

### 5.1 布局与身份使用同一份配置

在 DUT 产品配置中维护小型只读表，每项包含原始键值、标识、行列位置。建议先放在 `rdx_dut.c` 的产品配置区；如需多型号复用，再拆为专用头文件。

布局字符串和原始键值到标识的查找均从该表产生，避免维护两份映射。校验键值和标识唯一、行列有效、序列化无空行/空项、缓冲区容量充足，并与实际启用的 IO 键表一致。无键产品返回 `NONE`；配置错误应拒绝启动。

T2620 表已按本次确认填入：A/PG7、B/PB2 在第一行，C/PG8、D/PB4 在第二行，E/PC2 在第三行，序列化得到 `A,B&C,D&E`。8-3 中其他布局仍为通用解析示例。

### 5.2 保证布局先于事件

1. 校验 DUT、互斥、订阅和请求 token，预留 KEY 状态及有界事件缓冲。
2. 生成完整布局；非空时进入准备阶段，暂存此后发生的有效按下。
3. 将布局交给同一 token 绑定的有序发送路径。只有确认整条响应已按序接纳，才开放事件发送。
4. 排在布局后的事件逐个发送；发送失败则取消本轮并清理占用，不留下“APP 未得到布局但固件一直检测”的状态。

`rdx_protocol_custom_msg_indicate()` 的公开声明返回 `void`，不能直接据此确认发送成功。实施时复用现有文本封装规则，补充能返回接纳结果的 token 绑定发送封装，底层使用 `rdx_ble_server_send_for_token()`；核实返回值语义、发送队列顺序及分片路径。布局超过单包能力时必须确保完整重组后才能被 APP 解析，不能默认 MTU 足够。

### 5.3 原始按下与业务隔离

优先复用消抖后的 key-down 入口，编码前验证 `key_tone.c` 调用是否对五键均有效、是否受提示音开关影响。若无法保证，则在公共消抖按下路径增加独立 DUT 投递钩子，不依赖音效是否开启。

一次物理按下上报一次；持续长按、HOLD 重复、释放和多击合成消息不追加事件。松开后再次按同一键仍上报，由 APP 去重计分。进入测试时已经按住的键，释放后重新按下才计入。

在 `rdx_app_earphone_key_remap()` 的产品安全门禁之后、NUM 键的 HID/KEY5 分流之前，消费测试期间的按键业务事件。按键和喇叭测试期间均不允许物理键触发 HID、录音、旧 DUT 多击切项或普通提示音；只有 KEY 项生成厂测按下事件。停止时清理按住状态，并防止本轮迟到的释放/多击消息在普通模式触发业务。拨码 OFF 仍走原关机流程。

## 6. 喇叭测试实现

使用固件内置的 1 kHz 正弦波，以最大播放音量连续循环输出至产品喇叭，直到收到停止请求或触发退出清理。音源、循环策略和最大音量按本次沟通确定；播放不依赖 SD NAND 文件、用户录音或 `rdx_playback` 播放列表，也不默认启用可选本地播放功能。

复用 `SDK/audio/common/pcm_data/sine_pcm.c` 的 `sin1k_48k_16bit[48]`：1 kHz、48 kHz 采样率、16 bit 单声道、满幅 PCM 波表，连续循环读取，不额外衰减。该源文件已列入 Makefile，不需要新增音频文件打包。输出声道映射按产品硬件确认。

最大播放音量指所选播放场景在当前 SDK/产品配置下允许的最高音量档位，接入时通过对应场景的音量上限接口获取并设置，不硬编码音量值，也不沿用用户当前音量。开始前保存临时修改的音量状态，停止或启动失败后恢复；重复开始不得覆盖保存值。

`SDK/audio/cpu/br28/audio_demo/audio_dac_demo.c` 可参考 DAC 启动和循环供数方式，但不能直接调用其阻塞式 `while (1)` 示例，也不能复制其中的 PB2/PB3 按键控制。编码时验证音频流或独立供数任务的启动、可取消循环及本项实例停止接口，保证 `app_core` 能及时处理停止命令，循环接缝保持连续。

- 开始：检查音频资源可用，保存需临时调整的音量，设置为播放场景最大音量，创建本项正弦波播放实例；确认启动成功后回 `*DEV#custom#ft_speaker#1#`。启动失败立即清理并恢复音量，记录原因，不回成功报文；错误格式尚待约定。
- 续播：循环读取正弦波表供数；异步供数或续播请求携带代次，只有当前仍为同轮 SPEAKER 且未取消时才能继续。
- 停止：先撤销续播许可，再关闭本项实例，确认资源释放，恢复临时音量后回 `*DEV#custom#ft_speaker#0#`；不能无条件停止共享播放器而误伤其他业务。
- 异常：资源缺失、解码失败、断连、DUT 退出和关机都走同一幂等清理路径。

喇叭回包使用请求会话的 token 发送，不在 BLE 收包或任务投递成功时提前回包。异步完成回调必须校验会话与代次；每条有效请求只回一次，循环续播不重复回 `1`，内部异常清理不主动伪造停止请求的回包。回包发送失败记录日志，不发往新 owner；开始回包无法发送时取消本轮播放并清理，停止回包失败也不能恢复播放。非法值、非 DUT 或互斥拒绝不回成功报文，错误格式未定义时由 APP 超时处理。

APP 的“通过”仍是人工听音结论；开始回包仅确认软件播放状态，不能证明喇叭实际出声或音质合格，需实机验收。

## 7. 会话与退出清理

新增测试绑定启动它的 RDX 会话 token 和本轮代次。响应、事件、排队命令、音频回调不能在断连重连或 owner 更换后作用于新会话。

在现有 RDX 生命周期撤销路径接入新增测试取消，覆盖物理断连、通知发送资格丢失、`rdxclose` 逻辑释放和 owner 清理。逻辑释放不要求断开共享 HID/物理 ACL；仅取消该会话的厂测业务。取消应先使 token/代次失效，再异步收尾资源。

`rdx_dut_close_current_func()` 增加两项关闭分支，覆盖正常退出、产品关机清理和统一关闭调用。包装完成必须仍要求测试已经结束，不绕过现有格式化、VM 校验和最终红灯流程。`rdx_dut_show_refresh()` 补齐新枚举，避免运行中误恢复默认显示。

BLE 进入 DUT 仍不开放物理键专属的 USB CDC admission；本次命令不改变 `factory_key_dut_ready` 的来源。

## 8. 文件变更计划与实施顺序

以下路径以仓库根目录为基准，协议目录简称 `SDK/apps/common/third_party_profile/rdx_protocol/`。

| 文件 | 拟修改内容 |
|---|---|
| 协议目录 `rdx_dut.h` | 命令常量、功能枚举、必要的按下投递/消费与取消接口 |
| 协议目录 `rdx_dut.c` | 布局表、严格解析、顺序执行、会话/代次、按键发送、喇叭生命周期与回包、统一清理 |
| 协议目录 `rdx_app.c` | 测试期间按键路由拦截与原始按下投递配合 |
| `SDK/apps/earphone/mode/key_tone.c` 或公共消抖入口 | 经核实后选择按下钩子，防止提示音影响厂测 |
| 协议目录现有 RDX 会话撤销实现 | 调用厂测取消；发送复用 token API，必要时补充文本封装 |
| SDK 音频播放接入 | 复用已有正弦波表，接入可取消循环、场景最大音量设置与恢复 |
| `tests/host/test_t2620_product_contract.ps1` 及其行为 harness | 纳入新增 DUT 验证，保持统一五合同入口 |
| `tests/host/README.md`、8-3 | 实现后更新覆盖与接口状态 |

实施顺序：确认布局和输出声道 → 补命令、状态与取消机制 → 接入按键与有序发送 → 接入正弦波循环播放和最大音量 → 完成异步停止和跨项切换 → host 验证、固件构建 → BLE APP 与实物验收。

## 9. 验证用例

### 9.1 Host 行为验证

优先在现有产品合同下增加 mock BLE、任务队列、物理按键与播放器的行为 harness。源码检查只辅助确认路由和配置边界，不能替代时序测试。

| 编号 | 场景 | 预期 |
|---|---|---|
| DUT-K01 | 空闲 DUT 查询有效布局 | 一条完整布局先于全部事件；自动开启，无单独 start |
| DUT-K02 | 五键乱序、重复按、长按、释放 | 标识匹配配置；重复按可再次上报，HOLD/释放不增报 |
| DUT-K03 | 响应准备时发生按下 | 暂存事件在布局后发送，不串序 |
| DUT-K04 | NONE、坏配置、非法值、非 DUT、其他项忙 | 不开启；NONE 仅用于无待测键；不伪造成功布局 |
| DUT-K05 | 停止、重复停止、停止后旧事件迟到 | 无 ACK，无新事件，不影响其他测试 |
| DUT-K06 | HID 就绪、KEY5 录音路由、旧多击消息并存 | 测试输入不触发 HID/录音/旧 DUT 切项；拨码 OFF 有效 |
| DUT-K07 | 停止后重启、同会话重复查询 | 无旧代次事件混入；新响应仍先于事件 |

## 11. 本次实施记录

- **命令与顺序**：新增命令精确匹配；新旧 BLE DUT 命令共同进入 16 项有界 FIFO。`rdx_dut_init()` 在应用任务创建服务定时器：普通空闲时 1 秒兜底，请求通过任务消息即时唤醒，DUT 活动期间为 10 ms。喇叭启动/停止期间保持占用；队列满触发取消并清空积压。启动等待超过 2 秒时取消，不回成功 `1`。
- **按键入口**：在公共 `key_driver_scan()` 消抖完成后、业务事件聚合前增加弱钩子，由 `key_tone.c` 的产品实现接入 DUT。入口不依赖提示音开关。测试期间清除点击聚合，拦截灯效/提示音及 HID/录音路由；长按跨停止持续消费到释放，已排队消息按测试代次及按键时间戳过滤。

- **喇叭实例**：新增 `rdx_dut_speaker.c/h`，复用 `sin1k_48k_16bit[48]`，独立 `dut_sine` 任务及专用 DAC 通道循环供数；处理短写并保留相位。按 DAC 位宽输出 16 bit PCM 或等幅转换为 24 bit 容器，多声道时复制同一个正弦音。DAC 忙或非空闲音频场景拒绝启动。
- **音量与清理**：在 `app_core` 查询 `AppVol_BT_MUSIC` 上限，临时切换音乐场景、解除 DAC 静音并设最大档。DAC 创建、启动、关闭及采样率恢复也在 `app_core` 执行；供数任务只写 PCM，并在停止后报告 DONE。SDK 的 `audio_dac_channel_close()` 会经 `audio_dac_delay_off()` 注册 300 ms 的 `sys_timeout`；该回调属于调用线程，不能挂在随后被删除的供数任务上。停止后先回收供数任务，再关闭通道、恢复原采样率/音量/静音和音频状态，随后回 `0`。不调用全局 `audio_dac_close()` 或停止共享提示音播放器。

“单独录音正常”是定位入口差异的关键证据：普通入口已按当前会议配置选择单声道，工厂入口仍沿用旧双声道设置。普通录音正常不能证明工厂录音入口也正确。漏增会话代次是同时发现的代码缺陷，会使连续新录音误用上一会话初始化；不应把它写成此次日志已单独证明的故障原因。

### 12.2 为什么排查花了多轮

1. **修复一个阻塞点后过早判断整体根因。** 前期只追到 KEY 占用或提示音等待，没有继续检查旧录音入口的格式、会话初始化及保存路径。对用户的结论强于实机证据，导致反复烧录后又发现下一层问题。
2. **初始测试替代了需要验证的业务代码。** DUT harness 最初用设置 `current_func` 的替身模拟旧录音开始，只能证明切项成功，无法发现真实入口写死格式和漏增会话代次。测试通过反映的是当时覆盖范围，而不是录音全链路正确。
3. **低估 SDK API 的任务归属。** 调用关闭函数返回，不等于底层延迟清理完成。使用预编译 SDK 时也必须核查定时器回调投递目标、任务队列和任务生命周期，不能仅按函数名推断同步语义。
4. **没有优先比较正常入口与异常入口。** 相同录音业务有普通 APP、物理键、工厂命令等入口，公共配置演进后，复制的旧初始化很容易遗漏。应复用业务初始化，并检查各入口是否仍保持一致。
