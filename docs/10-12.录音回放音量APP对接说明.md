# 10-12. 录音回放音量 APP 对接说明

> 更新：2026-11-06。**现有本地回放音量调节后的重启记忆，已由用户实测确认。**当前设备端已实现 `vol`，固件构建及主机测试通过；基础 APP 实机 GET/SET、延时保存和软件重启记忆已在 COM3 日志中确认，恢复出厂日志也确认播放音量回到最大档 16 并在复位后保持。忙状态、通知、CCC 快速重订阅、29 字节最长 SET 和真实 sleep/RF 仍待专项验证。29 字节写入沿用既有 `rectone`/`recsave` 的 32 字节传输基线，作为首轮联调确认项，不作为额外启动门槛。
>
> 本版按“新增 APP 控制入口，复用既有音量与 SDK 记忆”实施。源码已核查正常模式关闭经典 BT 等产品边界，发布前仍需完成启动/DUT、提示音和播放切换的针对性验收，见 [10-11](10-11.录音回放音量APP控制方案.md) 第 2 节；已有重启记忆不代表这些场景或 APP 新入口均已验证。

## 1. 功能

APP 新增「录音回放音量」控件，查询和调整设备播放本地录音时的音量；不控制麦克风增益、录音文件、提示音、通话或手机系统音量。

- APP 和已配置的本地音量按键都以原始音量 **2 档为一个调整步进**，上下限处限幅。
- 协议传输设备的原始档位；APP 负责换算显示。原始最大档位预期为 16，但仍需实机确认，APP 不写死。
- 沿用设备已有的音量记忆，不增加 APP 专用音量 VM，也不靠 APP 重连后写回缓存来实现记忆；发布前完成 [10-11](10-11.录音回放音量APP控制方案.md) 的针对性验收。
- `SET ok` 表示设备运行时接受，不等于已完成异步音频更新或写入 Flash。正常保存后重启可恢复；立即断电或异常复位时，末次调整可能丢失。
- 整机恢复出厂时，现有音量步骤会尝试恢复为最大值；恢复结束后以 GET 为准。单独重置配键不改变音量。

## 2. 指令

复用与录音提示音 `rectone`、会议录音落盘 `recsave` 相同的 RDX `custom` 通道，不使用手机系统音量或 HID 键盘报告。

**与旧音量消息分开处理：**现有固件还有 AVRCP 触发的百分比音量主动上报（`rdx_app_volume_indicate()`），不是本控件的查询/设置接口。本控件只使用 `custom#vol` 返回的原始 `cur/max`；旧百分比音量上报不得更新本控件，也不表示固件支持 `vol`。

```text
查询：*APP#custom#vol#get,<id>#
设置：*APP#custom#vol#set,<id>,<level>#
应答：*DEV#custom#vol#<id>,<result>,<cur>,<max>#
主动：*DEV#custom#vol#0,ntf,<cur>,<max>#
```

| 字段 | 约定 |
| --- | --- |
| `id` | 请求编号，1～65535，1～5 位 ASCII 十进制；允许前导零，应答原样带回。`0` 专用于主动通知 |
| `level` | SET 的**原始绝对档位**，1～2 位十进制，范围 `0..max`；可以为奇数，不是 APP 显示的格数或百分比 |
| `cur` | 设备当前可信的**原始档位**，范围 `0..max`，可以为奇数；`busy` 时固定为 `0` |
| `max` | 设备回放的**原始最大档位**，正常值为 `1..99`；`busy` 时固定为 `0` |
| `result` | 请求应答为 `ok`、`busy`、`arg`；主动通知为 `ntf`，不需要 APP 应答 |

指令名、操作和结果均为小写；字段之间不加空格，不加多余字段、换行或额外结束符。`id` 缺失或不合法时不回复。原始帧的异常格式还受现有预编译协议库解析边界影响，须按 [10-11](10-11.录音回放音量APP控制方案.md) 实际接收链验证，APP 不应依赖错误格式一定得到应答。

### 2.1 应答处理

| `result` | 设备语义 | APP 处理 |
| --- | --- | --- |
| `ok` | GET 得到可信值；或 SET 在运行时被接受 | 用返回的原始 `cur/max` 更新状态和显示；不提示“已持久保存” |
| `busy` | 当前无法安全执行或取得可信值；SET 未修改音量，固定返回 `0,0` | 不把 `0,0` 当作音量或最大值，不做除法；提示设备暂不可用，稍后重新 GET |
| `arg` | 可识别 ID，但操作或参数不合法；未修改音量，返回可信 `cur/max` | 开发阶段排查请求，不自动重试错误参数 |
| `ntf` | 设备确认本地回放音量变化后的尽力通知，ID 固定为 `0` | 无须请求匹配或应答；有效时更新原始值和显示 |

录音、提示音、工厂测试及其他设备忙状态可能使 SET 返回 `busy`；GET 是否可用取决于设备能否取得可信值。OTA、断连、CCC 未订阅、拥塞或上游丢包时也可能完全无应答，不能假定所有忙状态都有 `busy`。本协议没有 `vmerr`。

处理 `ok`、`arg` 或 `ntf` 前，应校验字段数、整数和范围：`1 <= max <= 99`、`0 <= cur <= max`；格式或范围错误的帧不能更新音量。`busy,0,0` 是唯一的忙状态哨兵，不套用上述正常值校验。

## 3. 显示与调节

设备原始最大值尚待确认。以最终验证为 `max=16` 为例，APP 可显示 **8 个调整间隔**；`0～8` 共有 9 个刻度位置，0 表示最低档，不预先认定绝对静音。

| 原始 `cur/max` | APP 显示位置 | 加一格的 SET 目标 |
| --- | --- | --- |
| `0/16` | `0/8` | `2` |
| `6/16` | `3/8` | `8` |
| `7/16` | `3.5/8` | `9` |
| `15/16` | `7.5/8` | `16`，到达上限 |
| `16/16` | `8/8` | 已达上限，不发送同值 SET |

显示位置按 `cur / 2` 换算，显示范围按实际 `max / 2` 计算。如果最终 `max` 不是 16，应按设备返回值展示，不固定声称有 8 个完整间隔；奇数上限的末端可能只有半个间隔。

1. APP 保留最近一次可信的原始 `cur/max`。加一格发送 `min(cur + 2, max)`，减一格发送 `max(cur - 2, 0)`；目标与当前值相同时不重复发送。
2. 原始值可能为奇数：例如 `7` 减一格为 `5`，加一格为 `9`。建议滑条如实显示半格；若控件只能近似显示，也必须保留原始值计算，不能先取整。
3. 滑条一次拖动可以跨多格。在无并发变化时，以手势开始时最近的可信原始值为基准，将位移换算为整数个两档增量并限幅；建议松手后发送一个绝对 SET。不能将奇数基准先归一化为偶数。
4. 查询、接收通知、刷新界面或重连时，不因显示换算自动发送 SET，也不把 APP 缓存的旧值写回设备。初次查询前及状态不可信时，控件不可调。

## 4. APP 对接流程

### 4.1 连接和查询

1. 建立 RDX 会话并订阅通知，确认第 5 节要求的单次完整写入能力后，发送一次 GET。
2. 收到匹配 ID 的有效 `ok` 后，保存原始 `cur/max` 并显示控件；每次断开重连、重新建立 RDX 会话或恢复 CCC 订阅后重新 GET。
3. 不需要轮询，也不需要在每次录音前重复设置。APP 可显示带“未确认”标记的旧缓存，但不能把旧缓存当作当前设备值或据此调节。

### 4.2 用户调节与请求管理

- 同一时间只保留一个 `vol` 请求在途。建议 SET 等待应答期间禁用继续操作；若实现连按合并或拖动中连续发送，也须串行处理并基于最新可信反馈计算。
- 请求 ID 建议在当前 RDX 会话内递增，不复用仍可能收到迟到应答的 ID。仅匹配当前请求 ID 的应答可结束该请求；有前导零时按原字符串匹配。ID 为 `0` 的合法 `ntf` 独立处理。
- 建议超时 2 秒。GET 超时显示「暂不可用」；SET 超时显示「未确认」，不能认定成功或失败。会话及写入能力恢复后，用新 ID GET 核实，不盲目重发旧 SET。
- 收到 `busy` 时本次 SET 未生效；可保留但标记旧显示为未确认，不用 `0,0` 覆盖。等待相关操作结束或用户重试时再 GET，不持续自动重试。
- 断连或关闭 CCC 订阅时，清空在途请求和拼帧缓存，禁用控件；重连或恢复订阅后，用新 ID GET，取得匹配的有效 `ok` 前不因 `ntf` 恢复可调状态。CCC 关开后仍不得复用可能收到迟到应答的 ID。清空在途请求只是停止等待，不代表设备端 SET 未执行，不能据此重发旧 SET。
- 设备会作废 CCC 关闭时尚未开始提交发送的待发音量通知，但不保证撤回已开始提交或正在 BLE 发送链中的通知/分片。恢复出厂或产测结束后也应重新 GET。通知尽力发送，可能延迟或丢失，不能替代查询。

### 4.3 与实体键并发

本版 SET 是**绝对值**，不是设备端原子加减。APP 看到 `6` 后计算加一格为 `8`；若实体键先将音量从 `6` 加到 `8`，APP 随后的 SET 仍得到 `8`，不会自动变成 `10`。旧 SET 也可能覆盖实体键的更新。

拖动期间若收到设备音量变化通知，建议取消当前拖动目标，按收到的值更新界面，由用户重新操作；但通知可能延迟或丢失，这不能消除全部竞争。冲突或 SET 超时后可 GET 核实，GET 只代表查询执行时的值，不能保证每次并发操作均已累加。若要求严格逐次累加，需另议设备端相对加减及去重协议，本版不提供。

### 4.4 旧固件与能力判断

`vol` 与 `rectone`、`recsave` 是独立功能，支持后两者不代表支持音量控制。GET 超时也可能由 MTU、OTA、断连、拥塞或丢包造成，**不能仅凭超时断定旧固件不支持**。

若产品另有可靠的固件版本或能力标识，可据此隐藏不支持的入口；否则超时时显示「暂不可用」或「未确认」，由用户重试，不把音量显示为 0。

## 5. BLE 收发与分包

### 5.1 上行：必须单次完整写入

协议为 ASCII，1 个字符占 1 字节。GET 最短为 22 字节，SET 最短为 24 字节，合法 SET 最长为 29 字节：

```text
*APP#custom#vol#get,1#          22 字节
*APP#custom#vol#set,1,0#        24 字节
*APP#custom#vol#set,65535,99#   29 字节
```

默认 ATT MTU 23 的普通写入载荷仅 20 字节，连最短 GET 都放不下。现有 `rectone`/`recsave` 走同一 `custom` 写入和解析通道，最长合法请求均为 32 字节；`vol` 最长只有 29 字节，没有引入更高的传输要求。

如果目标 APP/设备组合已经能按既有方式发送 `rectone`/`recsave` 的 32 字节请求，`vol` 可以直接沿用该基线开始联调，不需要再增加启动门槛。首轮联调用抓包或设备接收日志确认一条 29 字节指令确实以一次完整写入到达即可；这是测试确认，不是新的前置条件。如果既有 32 字节路径本身不满足，则同样不发送半条 `vol` 命令，也不假设 long write 自动可用。

### 5.2 下行：使用 RDX 文本流拼帧

最长合法应答为 32 字节，即使满足上述上行条件，下行通知仍可能分片。APP 复用现有 RDX 文本流接收器，识别完整的 `*DEV#custom#vol#...#` 后再解析：

- 一帧可能跨多个通知，一个通知也可能包含多帧或帧的一部分；不要把单个通知直接当成完整应答。
- `vol` 前缀本身含多个 `#`：从完整前缀之后寻找结束 `#`，再按逗号解析 4 个字段。跨分片时不能假定前缀一次收齐。
- 半帧未完成又遇到新的 `*DEV#` 帧起始时丢弃旧半帧；断连清空缓存，并为缓存设置长度上限。解析失败、部分发送失败或其他业务竞争时，通过超时和 GET 恢复，不保证通知必达。

## 6. 示例

以下均为目标协议示例，假设设备状态允许操作且实机已确认 `max=16`：

```text
连接后查询：原始 6，APP 显示 3/8 格
APP -> *APP#custom#vol#get,1#
DEV -> *DEV#custom#vol#1,ok,6,16#

APP 增加一格：原始 8，APP 显示 4/8 格
APP -> *APP#custom#vol#set,2,8#
DEV -> *DEV#custom#vol#2,ok,8,16#

已配置的实体音量键再增加两档：原始 10，APP 显示 5/8 格
DEV -> *DEV#custom#vol#0,ntf,10,16#

独立场景：历史原始值为 7，APP 显示 3.5/8 格
APP -> *APP#custom#vol#get,3#
DEV -> *DEV#custom#vol#3,ok,7,16#
APP -> *APP#custom#vol#set,4,9#
DEV -> *DEV#custom#vol#4,ok,9,16#

录音中设置被拒绝，0,0 不是当前音量
APP -> *APP#custom#vol#set,5,11#
DEV -> *DEV#custom#vol#5,busy,0,0#

录音结束后设置越界，本次未修改，当前仍为 9
APP -> *APP#custom#vol#set,6,20#
DEV -> *DEV#custom#vol#6,arg,9,16#
```

## 7. 联调检查

- APP 可先用 mock 覆盖 GET、SET、`ok/busy/arg/ntf`、非法值、缺失应答和迟到应答；设备端源码和主机测试已完成，但 mock 成功仍不代表实机或 APP 联调完成。
- 使用包含本功能的测试固件，按 [10-11](10-11.录音回放音量APP控制方案.md) 第 2 节验证经典 BT 启动/DUT 边界、提示音配置及播放切换；对其他产品可达音源验证双向隔离，未解决的实际冲突仍阻止发布。
- 实机核对原始 `max`、最低档实际效果和响度映射；验证播放、暂停、停止、重新开流时显示与回放一致。
- 覆盖 `cur=6/7` 的加减、0 和上限限幅、奇数滑条起点及重连后奇数值；查询和刷新不能自行修改音量。
- 先将 `0x07 + F15`（降低）和 `0x07 + F16`（提高）配置到实体键，默认配键不含这两项；再检查两档步进、通知合并与断连，以及 APP SET 与实体键并发、通知延迟或丢失、超时后 GET。
- 在目标 APP 平台确认单次 29 字节上行、下行分片/拼帧、拥塞及断连；既有 `rectone`/`recsave` 32 字节路径作为传输基线。覆盖同 ACL 快速关闭/恢复 CCC 订阅，检查旧待发批次作废、新通知不被误取消，以及 APP 新 ID GET 和控件恢复流程。
- 注入旧 AVRCP 百分比音量上报，确认本控件的原始值、显示及可用状态不受影响，不与 `custom#vol` 混用。
- 在已有本地重启记忆的基础上，补验 APP SET 后正常保存/关机重启、录音等忙状态、设置后立即断电可能丢失，以及恢复出厂后重新查询；不要把已有本地实测当作 APP SET 已验证，也不要把 SET `ok` 当成 Flash 写入成功。

**当前实机结果（2026-11-06）：**`COM3_2026-11-06_13-53-52.log` 显示 APP GET/SET 均正常到达并执行，连续设置 14/12/10/8/6/8 后 SDK 输出 `VOL_SAVE`；软件关机重启后再次 GET，恢复播放值为 8，与重启前一致。补充日志 `回复出厂设置后.log` 中，出厂前 SET 4 后执行 `*APP#default#`，日志出现 `set_vol[idle]:music=16`；复位后启动显示 `music 16`，重新播放为 `set_vol[music]:music=16` 并输出 `VOL_SAVE 16`，确认恢复出厂最大值和持久化链路正常，音量相关未出现回包或队列失败。基础联调可判定通过，其余专项项仍按上述清单继续。
