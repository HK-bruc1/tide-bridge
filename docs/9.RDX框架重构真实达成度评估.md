# RDX 框架重构真实达成度评估

> 评估对象：当前 `SDK/apps/common/third_party_profile/rdx_protocol` 源码、`docs/3.RDX框架JL平台复用性优化大纲.md` 的整体成功标准，以及两份补充评估意见。  
> 评估结论：**骨架已搭好，但旧代码迁移不足；当前更接近阶段 4 checkpoint + 阶段 5 局部清债，而不是大纲最终完成态。**

## 1. 总体判断

当前重构已经建立了新架构的主要容器：

- `board/`：存在 `t2616_cc`、`t2616_ep` 两个 board config。
- `port/jl/`：存在 `include/`、`jl7018/`、`jl7018_shadow/`。
- `service/`：存在 command dispatch、event bus、device、record、storage、time、clock、wifi、ble 等 service。
- `config/`：存在 `product/`、`board/`、`build/` 目录。
- `tools/` 与 `tests/host/`：已有静态边界检查和 host mock 测试。

但大量旧路径仍然没有改为使用这些容器。最典型的问题是：`rdx_board_get_config()` 在生产代码中只有一次实际调用，而且用途是启动诊断日志；电源、LED、SPI、低功耗、OS taskq、timer 等仍有大量旧宏和 JL API 直连。

因此，本次重构的真实达成度更接近 **55% 左右**。若按“是否形成可长期维护的中间件边界”来判定，当前不能视为完成；若按“是否建立可继续迁移的骨架和验证基线”来判定，当前已经有实质进展。

## 2. 对用户补充评估的核查结论

用户评估的核心判断“容器已建好，血肉未迁移”总体属实。下面逐项给出核查结论和必要修正。

| 项目 | 结论 | 说明 |
|---|---|---|
| Board config 形同虚设 | 基本属实 | `rdx_board_get_config()` 在生产代码中只有 `rdx_app.c` 启动日志调用；board config 尚未驱动电源、LED、SPI 行为。 |
| 旧板级宏仍活跃 | 属实 | `WIFI_POWER_PORT_IO`、`VDD_POWER_PORT_IO`、`LED_PT0807_DATA_PORT_IO` 仍在 `rdx_app.c`、`rdx_charge.c`、`rdx_dut.c`、`rdx_device_service.c`、`xxpUart.h` 中出现。 |
| 旧宏 deprecated 机制未做 | 属实 | 未发现 `#warning`、`#pragma message` 或统一的 deprecated 别名机制。 |
| `rdx_spi.c` 未参数化 | 属实 | `rdx_spi.c` 不使用 `rdx_board_config_t`，仍硬编码 `ESP8684_*_PORT_IO`，并保留 `#if (CHIP_TYPE == CHIP_JL7018)`。 |
| service 层仍依赖 JL/board 细节 | 基本属实 | service 公共头较干净，但 service `.c` 实现仍直接包含 `rdx_jl_*`、`gpio_config.h`，并调用 `os_taskq_post_type()`、`sys_timeout_*()` 或使用 `IO_PORT*` / 电源宏。 |
| `rdx_ble_server.c` 仍跨层直连 record/protocol | 属实 | 仍存在 `rdx_record_get_status()`、`rdx_protocol_record_state_indicate()` 等调用；注意这不同于 `rdx_ble_service.c`，后者的 stop/cleanup 已经完成阶段 5 cutover。 |
| lifecycle hooks 全空 | 部分属实 | `early_init`、`pre_sleep`、`post_wakeup` 基本是 no-op；但 `pre_poweroff` 会调用 `rdx_rtc_store_timestamp()`，不能说全空。shadow 与真实 port 的行为差异仍很弱。 |
| 旧业务 `.c` 基本未迁移 | 属实 | `rdx_record.c`、`rdx_charge.c`、`rdx_dut.c`、`rdx_ota.c`、`rdx_vm.c` 中按 `os_/gpio_/syscfg_/spi_` 口径仍有 77 处命中。 |
| config 三层拆分未做 | 属实 | `config/product`、`config/board`、`config/build` 目录存在但为空；产品配置仍集中在 `rdx_app_config.h`。 |

需要修正的一点是：当前不是“完全只建空壳”。命令分发、event bus、WiFi vtable、BLE service stop/cleanup、错误码收口、host mock 与静态检查脚本已经有实际行为，不只是目录存在。

## 4. 已经真实达成的内容

### 4.1 命令分发去中心化

`rdx_app.c` 中已经没有 `rdx_cmd_register()` 调用。当前命令注册分布在：

- `rdx_device_service.c`：10 个
- `rdx_record_service.c`：7 个
- `rdx_storage_service.c`：3 个
- `rdx_info_service.c`：6 个
- `rdx_time_service.c`：1 个

这满足大纲阶段 4 “`rdx_app.c` 不再注册命令”的目标。

### 4.2 BLE service 的阶段 5 cutover

`rdx_ble_service_stop_recording()` 已转发到 `rdx_record_service_stop_from_ble()`。  
`rdx_ble_service_cleanup_protocol_state()` 已转发到 `rdx_storage_service_cleanup_ble_buffers()`。

这说明 `rdx_ble_service.c` 自身不再直接操作 `RecordStatus`、uxfile buffer 或 protocol buffer。剩余问题在旧的 `rdx_ble_server.c`，不是这个新 service。

### 4.3 WiFi transport vtable 已接入

`rdx_wifi_service.c` 通过 `g_wifi_transport->open()` / `close()` / `control()` 调用 WiFi port。真实 `xxp_esp32_*` 调用集中在 `port/jl/jl7018/rdx_ops.c`。

这项满足“WiFi 控制从业务层移到 port vtable”的核心方向。

### 4.4 错误码有实质收口

`service/*.c` 当前没有裸 `return -1;` 命中。多个新 service API 已经使用 `rdx_err_t`，例如 BLE、storage、wifi、device、event bus。

### 4.5 host mock 与静态边界检查已形成

已有 `tests/host/run_tests.bat` 和 `tools/check_rdx_boundaries.bat`。这给后续迁移提供了最小回归基础。

需要注意：当前静态边界检查脚本的检查口径偏窄。它能证明 public header、private include、`xxp_esp32_*`、LED hook 等边界没有明显违规，但不能证明 service `.c` 内部已经摆脱 JL API 或 board 宏。

### 4.6 启动诊断与 vtable 校验已接入

`rdx_app.c` 中启动日志已覆盖 product、board、chip、sdk、transport、storage、rtc_path、pins；启动阶段也会校验 `rdx_lifecycle_ops_t`、`rdx_time_ops_t`、`rdx_wifi_transport_ops_t` 并打印成功或失败日志。

### 4.7 弱符号 hooks 与 clock service 已接入

`rdx_default_hooks.c` 提供 LED、Motor、DUT、Diag 的 weak hook 默认实现；`rdx_clock_service.c` 已纳入 Makefile，`rdx_app.c` 中 clock 相关旧入口已变为 thin wrapper。

## 5. 未达到大纲目标的关键缺口

### 5.1 `rdx_app.c` 行数与函数数仍未达标

当前 `rdx_app.c` 为 2174 行，函数 regex 匹配 78 个。相比原始 3403 行 / 178 函数已经显著下降，但仍未达到大纲阶段 2/4 曾提出的行数 ≤ 2000、函数数 ≤ 50 的目标。

阶段 4/5 文档允许 ABI wrapper、协调器、产品特定函数保留，因此这个指标不应作为唯一硬门禁；但它仍能说明 `rdx_app.c` 尚未完全退化为薄协调器。

### 5.2 Board config 没有替代旧宏

当前 `rdx_board_config_t` 里已经有：

- `wifi_power_io`
- `vdd_power_io`
- `led_data_io`
- `spi_cs_io`
- `spi_clk_io`
- `spi_mosi_io`
- `spi_miso_io`
- `spi_handshake_io`
- `spi_port`
- `spi_clk_hz`

但实际业务路径仍然使用旧宏：

- `WIFI_POWER_PORT_IO`
- `VDD_POWER_PORT_IO`
- `LED_PT0807_DATA_PORT_IO`
- `ESP8684_*_PORT_IO`
- `IO_PORTC_01/02/04/05`

这意味着“换板型主要改 `board/<name>/`，不改 service/core 代码”的目标尚未达成。`t2616_ep` board config 可以参与构建选择，但不能保证真实运行行为按该 board config 生效。

### 5.3 SPI 仍是多板型/多芯片复用的硬阻塞

`rdx_spi.c` 仍硬编码 SPI 引脚和 `CHIP_TYPE`：

- `ESP8684_HANDSHAKE_PORT_IO`
- `ESP8684_MOSI_PORT_IO`
- `ESP8684_SCLK_PORT_IO`
- `ESP8684_CS_PORT_IO`
- `#if (CHIP_TYPE == CHIP_JL7018)`
- `HW_SPI2` / `HW_SPI1` 选择

这和阶段 3 “所有芯片相关宏只出现在 `port/jl/<chip_family>/` 中，所有板型相关宏只出现在 board 层”的目标冲突。

### 5.4 Service 层边界仍不够硬

当前 service 公共头没有明显暴露 `OS_SEM`、`OS_MUTEX`、`IO_PORT*` 等类型，这是进步。但 service 实现里仍有不少 JL 直连：

- `rdx_device_service.c` 包含 `gpio_config.h`、`rdx_jl_gpio.h`、`rdx_jl_osal.h`、`rdx_jl_storage.h`，并直接使用 `IO_PORTC_*` 和电源宏。
- `rdx_record_service.c` 多处直接调用 `os_taskq_post_type("app_core", ...)`。
- `rdx_event_bus.c` 的 async publish 直接调用 `os_taskq_post_type("app_core", ...)`。
- `rdx_clock_service.c` 直接调用 `sys_timeout_add()`、`sys_timeout_del()`、`sys_timer_re_run()`。

如果目标是“JL-only 但边界清晰”，这些实现可以暂时接受；如果目标是大纲中的“可长期维护的中间件边界”，这些应继续下沉到 port/OSAL 或明确的 platform adapter。

此外，service 实现层仍大量直接调用 legacy 模块，例如 `rdx_protocol_*`、`rdx_uxfile_*`、`rdx_record_*`。这说明 service 拆分已经完成了“命令注册归属”的第一步，但协议、文件、录音状态等底层边界仍未完全抽象。

### 5.5 旧 BLE server 仍绕过新 service

虽然 `rdx_ble_service.c` 已经收口，但 `rdx_ble_server.c` 仍直接访问 record/protocol 状态：

- `rdx_record_get_status()`
- `rdx_protocol_record_state_indicate()`
- `RecordStatus`

这说明 BLE 边界并未全局完成，只是新 service 的局部路径完成了。

### 5.6 产品配置仍是单一大头文件

`config/product/`、`config/board/`、`config/build/` 目前为空。`RDX_AI_SEL_APP`、`RDX_SEL_DEVICE`、`PRODUCT_TYPE`、`BT_NAME`、`BLE_LOCAL_NAME`、版本号、WiFi AP 配置等仍集中在 `rdx_app_config.h` 的条件编译分支中。

大纲要求“新增客户产品时主要修改 `config/product/*.h`，不需要在业务 `.c` 中增加 `#ifdef`”。当前没有达到这个目标。

### 5.7 验证闭环仍缺硬件和 clean build 证据

已有 host mock 和静态检查，但仍缺：

- 当前环境下可复现的三组合 clean build 记录。
- `.map` 体积增长对比。
- 目标板冒烟记录：配对/绑定、BLE 录音 30 秒、WiFi 在线录音 30 秒、BLE 强制停止、软关机恢复、恢复出厂重配对。

此前构建尝试显示当前工作环境存在构建清理/链接问题：`make clean` 删除 `SDK/objs` 时遇到 `Permission denied`，非 clean 构建链接阶段缺少 `objs/apps/earphone/sdk_version.z.S.o`。因此不能把文档中的历史 clean build 记录直接当作当前验证证据。

| 2. 产品差异配置化 | `config/product` 为空，产品配置仍在 `rdx_app_config.h`。 | 未达成 |

## 7. 建议的下一轮收口顺序

### P0：让 board config 真正接管板级差异

1. 在 `rdx_board_config_t` 中补齐所有仍裸写的板级 IO：`IO_PORTC_01/02/04/05` 等。
2. 新增 board 层或 port 层 helper，例如 `rdx_board_wifi_power_highz()`、`rdx_board_vdd_power_on()`、`rdx_board_led_data_io()`。
3. 替换 `rdx_app.c`、`rdx_charge.c`、`rdx_dut.c`、`rdx_device_service.c` 中的 `WIFI_POWER_PORT_IO` / `VDD_POWER_PORT_IO` / `LED_PT0807_DATA_PORT_IO`。
4. 保留旧宏时必须加 deprecated 标记，或者在内部模块中直接删除旧宏让编译器定位残留。

### P1：迁移 `rdx_spi.c` 到 board/port 参数

1. 让 `rdx_spi.c` 从 `rdx_board_get_config()` 获取 SPI 引脚和频率。
2. 把 `CHIP_TYPE`、`HW_SPI1/HW_SPI2` 选择下沉到 `port/jl/<chip_family>/`。
3. 清除 `rdx_spi.c` 中的 `ESP8684_*_PORT_IO` 硬编码。

### P2：继续清理 service 实现层 JL 直连

1. `os_taskq_post_type()` 统一封装到 OSAL task/callback API。
2. `sys_timeout_*()` 统一封装到 OSAL timer API。
3. `rdx_device_service.c` 中板级 IO 操作转向 board helper。
4. 静态边界检查脚本增加 service implementation 扫描，不只扫 public header。

### P3：处理旧 BLE server 跨层调用

1. 为 `rdx_ble_server.c` 中的 record/protocol 状态访问建立 service API。
2. 保留 ABI wrapper，但内部转发到 service。
3. 对 BLE 录音、断开重连、强制停止做目标板冒烟验证。

### P4：落地产品配置拆分

1. 建立 `config/product/<product>.h`。
2. `rdx_app_config.h` 退化为选择器和兼容层。
3. 至少模拟新增一个 product config 并通过编译。

### P5：补齐验证闭环

1. 修复当前构建环境的 clean 权限和 `sdk_version.z.S.o` 链接问题。
2. 重跑三组合 clean build。
3. 若已有其它机器的三组合 clean build 成功记录，应归档完整命令、exit code、日志、`sdk.map` 路径和产物时间戳。
4. 保存 `.map` 基线和阶段对比。
5. 补目标板冒烟记录。

## 8. 最终结论

当前 RDX 重构不能按“大纲最终完成”验收。它已经完成了架构容器和一部分关键路径迁移，但旧代码仍是实际运行路径的主体。

更准确的状态描述是：

> 新架构的骨架已经搭好，部分关键器官已经接入；但板级、SPI、产品配置、旧 BLE server、旧业务模块的大量血肉仍留在旧位置。下一阶段不应继续扩容新抽象，而应集中做“替旧”和“收口”，让现有业务路径真正经过 board/port/service 边界。
