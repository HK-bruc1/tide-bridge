# RDX 框架阶段 2 实施文档：服务层拆分（降低中心化）

> 版本：v1.1
> 对应大纲：`docs/3.RDX框架JL平台复用性优化大纲.md` 阶段 2
> 前置条件：阶段 1 的目录与基础抽象层已就绪（`board/`、`port/jl/` 已入编译），但业务调用点仍需在阶段 2 迁移到 wrapper 边界。
> 前提约束：
> 1. **`librdxApp.a` 二进制不修改**，现有静态库头文件作为兼容边界处理。
> 2. SDK 版本不变，只做代码组织重构。
> 3. 阶段 2 依赖阶段 1 的 `rdx_board_config`、`rdx_jl_osal`、`rdx_jl_storage` 边界；新增 service 不得新增裸 `os_*`、`syscfg_*`、`gpio_*` 调用，若 wrapper 不足，先补 wrapper 再迁移业务代码。

---

## 1. 阶段目标

把 `rdx_app.c`（当前 3428 行 / 历史统计约 80 函数，其中 `rdx_*` 定义约 55 个）中的产品主控逻辑拆分为独立 service，使 `rdx_app.c` 退化为 **service 协调器**——只负责系统初始化、全局状态、service 间编排，不再承载具体业务实现。

当前代码基线（2026-06-26 仓库扫描）：
- `service/` 目录已存在但为空，`SDK/Makefile` 尚未包含任何 `rdx_protocol/service/*.c`。
- `rdx_ble_server.c` 仍有多处 `rdx_record_*`、`rdx_uxfile_*`、`rdx_protocol_*clean/reinit` 反向调用。
- `rdx_spi.c` 仍直接推进协议/文件传输闭环，不能简单删除调用，必须先建立 WiFi transport 回调契约。
- `rdx_vm.c` 仍混有 VM 读写、解绑/恢复出厂、TWS 删除、BLE 断开、格式化异步回调。

| 指标 | 阶段 1 现状 | 阶段 2 目标 |
|---|---|---|
| `rdx_app.c` 行数 | 3428 | 首轮 ≤ 2500；收尾目标 ≤ 2000 |
| `rdx_app.c` 函数数 | ~80（`rdx_*` 定义约 55） | 首轮 ≤ 60；收尾目标 ≤ 50 |
| 独立 service 文件 | 0（目录已存在但为空） | ≥ 5 |
| service 间直接 extern 互调 | 大量 | 0（统一走 event bus 或 dispatch） |
| `rdx_ble_server.c` 反向调用 `rdx_record_*` / `rdx_uxfile_*` | 存在 | 0 |
| `rdx_spi.c` 中协议/文件状态清理 | 存在 | 0 |

## 2. 设计模式落地

| 设计模式 | 在阶段 2 中的落地形式 |
|---|---|
| ④ 小 vtable 合约 | `rdx_command_dispatch` 用静态数组 + vtable 做命令→service 映射；`rdx_event_bus` 用订阅表管理 service 间通知。 |
| ② 弱符号默认实现 | LED、马达、DUT、调试钩子提供 `__attribute__((weak))` 空实现，产品特化时只需覆盖对应函数。 |
| ① 条件编译 | 新增 service 的编译开关集中在 Makefile/board config 中，不在 service 内部散落产品宏。 |
| ③ Wrapper | 所有新增 service 代码统一经 `rdx_jl_*` wrapper 访问 JL SDK，不直接调用 `os_*`、`syscfg_*`、`gpio_*`。 |

**阶段 2 不引入**：event bus 不使用动态内存分配（受限于 JL 平台），全部用静态数组 + 编译期常量。

## 3. 目标架构（service 视图）

```text
┌──────────────────────────────────────────────────────┐
│  rdx_app.c  (协调器)                                 │
│  - 系统初始化 / service 注册 / 全局状态              │
│  - 按键事件转发到对应 service                        │
│  - 生命周期管理 (init / idle / exit)                  │
└──────────┬───────────────────────────────┬───────────┘
           │                               │
    ┌──────▼──────┐                 ┌──────▼──────┐
    │ event bus   │                 │ cmd dispatch│
    │ 发布/订阅   │                 │ 协议→服务   │
    └──────┬──────┘                 └──────┬──────┘
           │                               │
    ┌──────▼───────────────────────────────▼───────────┐
    │                  Service Layer                    │
    ├─────────────┬──────────┬──────────┬──────────────┤
    │ record      │ storage  │ device   │ wifi         │
    │ service     │ service  │ service  │ service      │
    │ 录音状态机  │ 文件同步 │ 出厂复位 │ WiFi 控制    │
    │ 在线/离线   │ 格式化   │ 解绑/关机│ 事件处理     │
    └─────────────┴──────────┴──────────┴──────────────┘
```

service 之间不直接 `extern` 互调，统一通过以下两条路径：
- **协议事件** → `rdx_command_dispatch` → service 处理函数
- **横向通知** → `rdx_event_bus` publish/subscribe

对热点同步路径（如录音数据推送），保留直接函数指针 dispatch，但必须在接口表中登记，不允许临时跨层调用。

## 5. 详细实施步骤

### 5.1 建立 `rdx_event_bus`（service 间通信契约）

**当前问题**：`rdx_app.c` 中的 WiFi 事件处理、录音状态变化、设备状态通知等直接通过函数调用或全局变量传递，service 之间没有明确通信边界。

**设计**：

```c
// service/rdx_event_bus.h

/* 事件 ID 枚举——阶段 2 先列出当前已知事件，后续按需扩展 */
typedef enum {
    RDX_EVENT_RECORD_START        = 0x01,
    RDX_EVENT_RECORD_STOP         = 0x02,
    RDX_EVENT_RECORD_DATA_READY   = 0x03,
    RDX_EVENT_WIFI_CONNECTED      = 0x10,
    RDX_EVENT_WIFI_DISCONNECTED   = 0x11,
    RDX_EVENT_WIFI_DATA_SENT      = 0x12,
    RDX_EVENT_STORAGE_FORMAT_DONE = 0x20,
    RDX_EVENT_STORAGE_SYNC_DONE   = 0x21,
    RDX_EVENT_DEVICE_PAIRED       = 0x30,
    RDX_EVENT_DEVICE_UNPAIRED     = 0x31,
    RDX_EVENT_DEVICE_POWEROFF     = 0x32,
    RDX_EVENT_BLE_CONNECTED       = 0x40,
    RDX_EVENT_BLE_DISCONNECTED    = 0x41,
    RDX_EVENT_IDLE_ENTER          = 0x50,
    RDX_EVENT_IDLE_EXIT           = 0x51,
    RDX_EVENT_MAX                 = 0x60,
} rdx_event_id_t;

typedef void (*rdx_event_callback_t)(rdx_event_id_t event, void *payload, u32 len, void *user_ctx);

/* 订阅者上限——编译期常量，按需调整 */
#define RDX_EVENT_MAX_SUBSCRIBERS  8

/*
 * 初始化事件总线。
 * 阶段 2 使用静态数组实现，不分配动态内存。
 */
void rdx_event_bus_init(void);

/*
 * 订阅事件。
 * 同一个 (event_id, callback) 组合不可重复注册（内部去重）。
 * 返回 0 成功，<0 失败（如订阅表满）。
 */
int rdx_event_subscribe(rdx_event_id_t event, rdx_event_callback_t callback, void *user_ctx);

/*
 * 取消订阅。
 * 如果 callback 为 NULL，取消该事件下全部订阅。
 */
int rdx_event_unsubscribe(rdx_event_id_t event, rdx_event_callback_t callback, void *user_ctx);

/*
 * 发布事件。
 * 同步遍历所有订阅者并调用回调。payload 可为 NULL。
 * 回调必须非阻塞、不可做耗时 I/O；不确定当前上下文时使用 async 版本。
 */
void rdx_event_publish(rdx_event_id_t event, void *payload, u32 len);

/*
 * 异步发布事件。
 * 内部只把 event/payload 指针封装后 post 到 app_core，再由 app_core 调用同步 publish。
 * payload 生命周期必须覆盖到 app_core 消费完成；阶段 2 不做动态拷贝。
 */
int rdx_event_publish_async(rdx_event_id_t event, void *payload, u32 len);
```

**实现要点**：

- 订阅表用静态数组 `static rdx_event_subscriber_t g_subscribers[RDX_EVENT_MAX][RDX_EVENT_MAX_SUBSCRIBERS]`。
- `rdx_event_publish()` 同步调用，只允许在已知安全上下文中使用；订阅者回调必须非阻塞，不直接执行格式化、重启、BLE 断开等耗时动作。
- BLE HCI/GATT 回调、SPI 中断/握手回调、protocol recv/send 任务中不确定上下文的事件，统一使用 `rdx_event_publish_async()` 转投 `app_core`。
- 回调中禁止再调用 `unsubscribe`/`subscribe`（文档约定，不加运行时检测）。

**验收方式**：

- 新增一个 host mock 测试：注册 3 个订阅者 → publish → 验证全部被调用，unsubscribe → 验证不再被调用。
- host mock 需要提供最小 `typedef.h` stub 和 `app_core` post stub；验证同步 publish 与 async 投递各 1 个用例。
- 所有 service 间横向通知走 event bus，`grep -n "extern.*rdx_.*_service" service/*.c` 返回 0 命中。

### 5.2 建立 `rdx_command_dispatch`（协议事件分发）

**当前问题**：`rdx_app_protocol_handle()`（位于 `rdx_app.c:2795`）是一个大 switch/if-else，直接处理来自 `librdxApp.a` 的所有协议事件。当前函数 ~300 行，承载了录音、存储、设备、WiFi、TWS 等多种事件的分类和分发。

**设计**：

```c
// service/rdx_command_dispatch.h

#include "rdx_protocol.h"  /* ProtocolEvents, RdxProtocolIndicateOps */

/* 命令处理函数签名 */
typedef void (*rdx_cmd_handler_t)(ProtocolEvents event, void *data, u32 len);

/*
 * 注册命令处理函数。
 * 每个 event 只能注册一个 handler（覆盖式注册）。
 * 热点命令可用直接函数指针。
 */
void rdx_cmd_register(ProtocolEvents event, rdx_cmd_handler_t handler);

/*
 * 协议事件入口——替代当前 rdx_app_protocol_handle() 中的 switch。
 * 查找已注册 handler 并调用；未注册的事件打印 RDX_LOG_WARN 并忽略。
 */
void rdx_cmd_dispatch(ProtocolEvents event, void *data, u32 len);

/*
 * 初始化命令分发器。
 * 阶段 2 在 rdx_app_all_init() 之后，由各 service 的 init 函数注册 handler。
 */
void rdx_cmd_dispatch_init(void);
```

**实现要点**：

- dispatch 表用静态数组 `static rdx_cmd_handler_t g_cmd_table[PROTOCOL_EVENT_CMD_TYPE_MAX]`（当前 `rdx_protocol.h` 的枚举尾项为 `PROTOCOL_EVENT_CMD_TYPE_MAX`，不是 `PROTOCOL_EVENT_MAX`）。
- 各 service 在自己的 `init()` 中调用 `rdx_cmd_register()` 注册。
- `rdx_app_protocol_handle()` 改为一行转发：`rdx_cmd_dispatch(event, data, len)`。
- 热点路径（如录音数据推送）保留直接函数指针 dispatch，但必须在 dispatch 表中登记（注册 handler），不允许临时硬编码跨层调用。

**验收方式**：

- 所有 `ProtocolEvents` 的 handler 都在 dispatch 表中有注册点，启动时 `rdx_log` 打印已注册事件数量。
- 未注册事件被触发时打印 WARN 日志但不崩溃。

### 5.3 拆分独立 service

以下 5 个 service 各自从 `rdx_app.c` 和周边强耦合文件抽取对应职能。**抽取策略**：先建立边界接口，再移动函数体；保持旧函数签名不变，原位置保留 thin wrapper（转发到新 service），确保 `librdxApp.a` 和其他模块的链接不中断。

阶段 2 不追求一次性“大搬家”。优先把 `rdx_spi.c`、`rdx_ble_server.c`、`rdx_vm.c` 中的跨层调用改成明确接口，再抽 record/storage/device 的业务实现，避免只是把耦合从一个文件搬到另一个文件。

#### 5.3.1 `rdx_record_service`（录音服务）

**抽取来源**：`rdx_app.c` + `rdx_record.c`

**职责**：
- 录音状态机（IDLE → RECORDING → ONLINE_SEND / OFFLINE_SAVE → STOP）
- 在线/离线录音调度
- mic gain 控制
- `rdx_app_record_state_upload_timer_*` 系列
- `rdx_app_device_record_handle()`
- `rdx_app_record_switch()`

**对外接口**：

```c
// service/rdx_record_service.h
void rdx_record_service_init(void);
void rdx_record_service_exit(void);
void rdx_record_start(u8 mode);
void rdx_record_stop(void);
u8   rdx_record_get_state(void);
bool rdx_record_is_active(void);
```

**关键决策**：
- `rdx_record_service.c` 是 `rdx_record.c` 的 "service wrapper"——不替代 `rdx_record.c`（后者是历史遗留，可能被静态库依赖），而是在其上层加一层 service 语义：状态管理、事件发布、与 storage/wifi service 的协调。
- `rdx_record.c` 当前约 2326 行，阶段 2 不把底层录音 task、opus 编码、mic gain VM 读写全部迁入 service；否则会形成新的中心化文件。
- BLE 连接/断开导致的 `rdx_record_stream_interrupt()`、`rdx_record_stream_resume_delayed()`、`rdx_record_on_ble_conn_changed()` 先由 `rdx_ble_service` 适配到 record service API，再逐步改成事件订阅。
- 录音数据推送属于热点路径，不强制走 event bus；可以保留直接函数指针 dispatch，但必须在 service 接口表中登记。

#### 5.3.2 `rdx_storage_service`（存储服务）

**抽取来源**：`rdx_app.c` + `rdx_uxfile`（静态库接口）

**职责**：
- 文件同步调度
- 格式化请求处理（`rdx_app_format_handle` → `rdx_app_format_cb`）
- 离线文件管理
- 与 `rdx_jl_storage` port 层对接

**对外接口**：

```c
// service/rdx_storage_service.h
void rdx_storage_service_init(void);
int  rdx_storage_format_request(void);
int  rdx_storage_sync_start(void);
int  rdx_storage_sync_stop(void);
bool rdx_storage_is_syncing(void);
```

#### 5.3.3 `rdx_device_service`（设备管理服务）

**抽取来源**：`rdx_app.c` + `rdx_vm.c`（部分）

**职责**：
- 恢复出厂设置
- 解绑/取消配对（`rdx_app_device_pair_handle` / `rdx_app_device_unpair_handle`）
- TWS 删除
- BLE 断开
- 重启/软关机（`rdx_app_normal_poweroff` / `rdx_app_time_to_reset`）
- 充电满电自动关机（`rdx_app_charge_full_timer_to_poweroff`）

**对外接口**：

```c
// service/rdx_device_service.h
void rdx_device_service_init(void);
int  rdx_device_factory_reset(void);
int  rdx_device_unpair(void);
int  rdx_device_soft_poweroff(void);
int  rdx_device_reboot(void);
```

**与 `rdx_vm.c` 的关系**：

- 阶段 2 的硬目标是：业务动作函数迁出，VM 读写函数保留。`rdx_vm.c` 允许继续保留必要的 `syscfg_*` 读写，后续再按 `rdx_jl_storage` 覆盖范围逐步替换。
- `rdx_device_service.c` 负责恢复出厂、解绑、TWS 删除、BLE 断开、格式化完成后的重启等编排；`rdx_vm.c` 只保留数据读写和旧符号 thin wrapper。
- `rdx_uxfile_sd_format(cb)` 是异步编排点，迁移时必须把 format done 回调建模为 `RDX_EVENT_STORAGE_FORMAT_DONE` 或 device service 私有完成回调，不能只移动代码块。
- 旧 `rdx_vm.c` 中的 `rdx_vm_unbound_handle()` / `rdx_vm_choose_to_unbound_handle()` / `rdx_vm_sys_reset_to_defaults()` / `rdx_vm_user_para_set_defaults()` 等业务动作函数改为 thin wrapper 转发到 `rdx_device_service`，保持链接兼容。

#### 5.3.4 `rdx_wifi_service`（WiFi 控制服务）

**抽取来源**：`rdx_app.c`（WiFi 相关函数）

**职责**：
- WiFi 模块开关控制（`rdx_app_wifi_handle`）
- WiFi 事件总线（`rdx_app_wifi_event_handle`）
- TCP 文件传输协调
- 与 `rdx_spi.c` transport 层对接

**对外接口**：

```c
// service/rdx_wifi_service.h
typedef void (*rdx_wifi_rx_cb_t)(const u8 *data, u32 len, void *ctx);
typedef void (*rdx_wifi_tx_done_cb_t)(void *ctx);

void rdx_wifi_service_init(void);
void rdx_wifi_power_on(void);
void rdx_wifi_power_off(void);
void rdx_wifi_data_send(const u8 *data, u32 len);
bool rdx_wifi_is_connected(void);

/*
 * SPI transport 回调边界。
 * rdx_spi.c 只负责收发原始数据和通知 tx done；
 * rdx_wifi_service.c 负责推进协议解析、文件同步、下一包发送。
 */
void rdx_wifi_service_on_rx(const u8 *data, u32 len);
void rdx_wifi_service_on_tx_done(void);
```

**关键决策**：
- `rdx_spi.c` 当前承担“WiFi 文件数据发送完成后通知协议层发送下一块”的闭环；阶段 2 不能直接删掉 `rdx_protocol_*` / `rdx_uxfile_*` 调用，必须先用 `rdx_wifi_service_on_tx_done()` 承接。
- 若出现头文件循环，回调 typedef 可下沉到 `rdx_wifi_transport.h`，由 `rdx_spi.h` 与 `rdx_wifi_service.c` 同时包含。

#### 5.3.5 `rdx_ble_service`（BLE 服务）

**当前状态**：`rdx_ble_server.c`（2130 行）既做 BLE GATT server，也反向调用录音停止、录音流中断/恢复、文件同步清理、协议发送 buffer 重建、format 状态检查。

**阶段 2 目标**：BLE service 只负责连接、广播、MTU/CCC 管理、数据收发。不直接清理文件同步和录音状态——这些通过 event bus 通知给 storage/record service。

**重构策略**：

1. `rdx_ble_server.c` 保持为 BLE GATT/ATT port 层，旧符号不删除。
2. 新增 `service/rdx_ble_service.c` 作为适配层，先提供 `rdx_ble_service_on_connected()` / `rdx_ble_service_on_disconnected()`，由 `rdx_ble_server.c` 在连接状态变化时调用。
3. `rdx_ble_service` 负责发布 `RDX_EVENT_BLE_CONNECTED` / `RDX_EVENT_BLE_DISCONNECTED`，并在过渡期调用 record/storage/protocol 的兼容接口。
4. 第二步再把 record/storage 对 BLE 事件的响应迁到各自 service，逐步删除兼容调用。不要在第一轮把所有 `rdx_ble_server.c` 反调同时改成 event publish。

**对外接口**：

```c
// service/rdx_ble_service.h
void rdx_ble_service_init(void);
void rdx_ble_service_on_connected(void);
void rdx_ble_service_on_disconnected(void);
int  rdx_ble_send_data(const u8 *data, u32 len);
bool rdx_ble_is_connected(void);
u16  rdx_ble_get_mtu(void);
```

**5 个 service 的验收方式**：

- 每个 service 有独立的 `.c/.h` 文件。
- service `.c` 之间不直接 `extern` 互调——验证：`grep -rn "extern.*rdx_.*_service" service/` 返回 0 命中（允许 `rdx_app.c` 调用 service 接口）。
- 同时检查业务前缀耦合：`grep -rn "rdx_record_\\|rdx_uxfile_\\|rdx_protocol_\\|rdx_ble_server_" service/` 只能命中经批准的兼容适配层，不能散落在多个 service 中。
- 每个 service 的 init 返回 void（失败内部处理并打日志）；
- 每个 service 在 init 中向 `rdx_command_dispatch` 注册自己处理的 `ProtocolEvents`。

### 5.4 拆分 `rdx_vm.c`

**当前问题**：`rdx_vm.c`（821 行）既做 syscfg 读写，也执行解绑、恢复出厂、TWS 删除、BLE 断开、文件格式化。当前扫描可见 `bt_tws_*`、`rdx_ble_server_*`、`rdx_uxfile_*`、`rdx_app_*`、`syscfg_*` 混在同一文件中。

**拆分方案**：

```text
rdx_vm.c (保持为 VM 仓储层)
  ├── syscfg_read / syscfg_write       # 阶段 2 允许保留；wrapper 覆盖后逐步替换
  ├── VM ID 集中管理                    # 所有 VM ID 在此文件内定义
  ├── 绑定状态读写
  └── 认证信息读写

rdx_device_service.c (新增)
  ├── 恢复出厂编排                      # 调用 rdx_vm_* + BLE 断开 + 文件清理 + 重启
  ├── 解绑编排                          # 调用 rdx_vm_* + BLE 断开 + 文件清理
  └── TWS 删除 / 重启 / 关机
```

**向后兼容**：`rdx_vm.c` 中现有的 `rdx_vm_factory_reset()` 等业务动作函数改为 thin wrapper，内部调用 `rdx_device_service_*`。这保证静态库和其他模块的链接不受影响。

**验收方式**：

- `rdx_vm_unbound_handle()`、`rdx_vm_choose_to_unbound_handle()`、`rdx_vm_sys_reset_to_defaults()`、`rdx_vm_user_para_set_defaults()` 等业务动作入口保留为 thin wrapper，主体编排迁入 `rdx_device_service.c`。
- `rdx_vm.c` 中不再直接执行 `bt_tws_remove_pairs()`、`rdx_ble_server_app_disconnect()`、`rdx_ble_server_reset_local_name()`、`rdx_uxfile_sd_format()` 等业务动作；`syscfg_*` 读写允许阶段 2 保留。
- `rdx_vm.c` 函数数先降到 ≤ 25；阶段 3/4 再收敛到 ≤ 20。

### 5.5 清理反向调用

**5.5.1 `rdx_ble_server.c` 反调清理**

当前 `rdx_ble_server.c` 在以下场景反向调用了录音/文件同步/协议清理函数：

| 场景 | 当前反调 | 阶段 2 改为 |
|---|---|---|
| BLE 断开延迟处理 | `rdx_protocol_uploadFileInfo_clean()`、`rdx_uxfile_*_sendBuf_free()`、`rdx_protocol_file_sync_busy_timer_stop()`、`rdx_protocol_send_buffer_reinit()` | `rdx_ble_service_on_disconnected()` → storage/protocol 兼容清理 → 后续迁入 storage service 事件订阅 |
| BLE 断开即时处理 | `rdx_record_stream_interrupt()`、`rdx_record_on_ble_conn_changed(false)`、`rdx_record_process()` | `rdx_ble_service_on_disconnected()` → record service 兼容接口；稳定后发布 `RDX_EVENT_BLE_DISCONNECTED` |
| BLE 连接 | `rdx_record_on_ble_conn_changed(true)`、`rdx_record_stream_resume_delayed()`、TWS 同步 | `rdx_ble_service_on_connected()` → 发布 `RDX_EVENT_BLE_CONNECTED`，必要时 async 到 `app_core` |
| 广播/format 状态判断 | `rdx_uxfile_sd_format_status_check()`、`rdx_vm_is_unbouding()`、`rdx_app_get_wifi_info()` | 第一轮保留在 BLE server 或由 ble service 查询只读状态；不和清理动作同批迁移 |

record service 和 storage service 最终各自订阅 BLE 事件并处理；第一轮允许 `rdx_ble_service` 作为兼容适配层集中承接旧调用，避免同步语义一次性变化过大。

**5.5.2 `rdx_spi.c` 反调清理**

当前 `rdx_spi.c` 中承载了协议状态清理和文件传输结束通知。阶段 2 把 `rdx_spi.c` 定位为 **纯 transport port**：

- SPI 驱动：cs/clk/mosi/hold 引脚控制（来自 board config）
- DMA/中断管理
- 数据收发原始接口
- **不再处理**：协议字节解析、文件状态清理、WiFi 事件触发

WiFi 数据触发改为：`rdx_spi.c` → transport callback → `rdx_wifi_service.c` 处理。必须显式保留当前“发送完成后推进下一包/清理 buffer”的闭环：

```c
/* rdx_spi.h 或独立 rdx_wifi_transport.h */
typedef void (*rdx_spi_rx_cb_t)(const u8 *data, u32 len, void *ctx);
typedef void (*rdx_spi_tx_done_cb_t)(void *ctx);

void rdx_spi_register_wifi_callbacks(rdx_spi_rx_cb_t rx_cb,
                                     rdx_spi_tx_done_cb_t tx_done_cb,
                                     void *ctx);
```

`rdx_wifi_service.c` 注册回调后，负责调用协议/文件同步模块推进：
- `rdx_protocol_recordFileData_indicateByRequestNum()` 或后续 command dispatch 等价接口。
- `rdx_protocol_file_sync_busy_timer_stop()` / `rdx_protocol_prepared_data_clean()` 的替代清理路径。
- `rdx_uxfile_recordFileData_sendBuf_free()` 的替代释放路径。

**验收方式**：

- `grep -n "rdx_record_\|rdx_uxfile_\|rdx_protocol_.*clean\|rdx_protocol_.*reinit\|rdx_app_record" rdx_ble_server.c` 返回 0 命中，或仅命中迁移期明确标注的 `rdx_ble_service` 适配入口。
- `grep -n "rdx_protocol_\|rdx_uxfile_\|rdx_wifi_event\|RDX_PROTOCOL_SEND_TASK_NAME" rdx_spi.c` 返回 0 命中（允许 callback typedef / callback 注册命中）。
- compile 通过（验证旧符号的 thin wrapper 仍然存在，链接不中断）。
- 使用现有 APP 设备做端到端冒烟测试：配对/绑定、BLE 录音上传（≥ 30 秒）、WiFi 在线录音（≥ 30 秒）、软关机与恢复、恢复出厂与重新配对。

### 5.6 弱符号化可选钩子

**目标**：对 LED、马达、DUT、调试等可选行为提供 `__attribute__((weak))` 默认空实现。产品特化时只需覆盖对应函数，不需要在业务 `.c` 中新增 `#ifdef`。

**设计**：

```c
// service/rdx_default_hooks.h

/* LED 控制钩子 */
void rdx_hook_led_on(u8 led_id)     __attribute__((weak));
void rdx_hook_led_off(u8 led_id)    __attribute__((weak));
void rdx_hook_led_blink(u8 led_id, u32 period_ms) __attribute__((weak));

/* 马达控制钩子 */
void rdx_hook_motor_start(u32 duration_ms) __attribute__((weak));
void rdx_hook_motor_stop(void)             __attribute__((weak));

/* DUT 模式钩子 */
void rdx_hook_dut_enter(void) __attribute__((weak));
void rdx_hook_dut_exit(void)  __attribute__((weak));
bool rdx_hook_dut_is_active(void) __attribute__((weak));

/* 调试诊断钩子 */
void rdx_hook_diag_dump_state(void) __attribute__((weak));
```

```c
// service/rdx_default_hooks.c

#include "rdx_default_hooks.h"

/* 所有钩子默认空实现 */
void rdx_hook_led_on(u8 led_id)          { (void)led_id; }
void rdx_hook_led_off(u8 led_id)         { (void)led_id; }
void rdx_hook_led_blink(u8 led_id, u32 period_ms) { (void)led_id; (void)period_ms; }
void rdx_hook_motor_start(u32 duration_ms) { (void)duration_ms; }
void rdx_hook_motor_stop(void)           {}
void rdx_hook_dut_enter(void)            {}
void rdx_hook_dut_exit(void)             {}
bool rdx_hook_dut_is_active(void)        { return false; }
void rdx_hook_diag_dump_state(void)      {}
```

如当前产品需要 LED 控制，只需在项目源文件中提供同名强符号：

```c
/* 产品特化覆盖 */
void rdx_hook_led_on(u8 led_id)
{
    gpio_set_mode(IO_PORT_SPILT(LED_PT0807_DATA_PORT_IO), PORT_OUTPUT_HIGH);
}
```

链接器优先选择强符号，覆盖默认空实现。

**验收方式**：

- 默认编译（不提供任何覆盖）时，所有钩子链接到 `rdx_default_hooks.c` 的空实现，不产生链接错误。
- 产品特化覆盖任一钩子后，链接到新实现，默认空实现被忽略。

## 6. 实施顺序

推荐按以下顺序推进，每步完成后编译验证 + 冒烟测试（至少配对/绑定 + BLE 录音 30 秒）。阶段 2 先清边界，再大规模搬函数：

| 步骤 | 内容 | 预估工作量 | 依赖 |
|---|---|---|---|
| 0 | 导出 `librdxApp.a` 未解析符号；确认 `llvm-nm` 或等价工具路径 | 0.5 天 | 无 |
| 1 | 建立 `rdx_event_bus.c/h` + host mock 测试（含 async 语义） | 1 天 | 步骤 0 |
| 2 | 建立 `rdx_command_dispatch.c/h`（使用 `PROTOCOL_EVENT_CMD_TYPE_MAX`） | 0.5 天 | 步骤 1 |
| 3 | 建立 `rdx_default_hooks.c/h`（弱符号） | 0.5 天 | 无 |
| 4 | 建立 `rdx_wifi_service` 与 `rdx_spi.c` transport 回调契约，先消除 SPI 直接协议/uxfile 推进 | 2 天 | 步骤 1 |
| 5 | 建立 `rdx_ble_service` 连接/断开适配层，BLE server 先调用 service 入口 | 2 天 | 步骤 1 |
| 6 | `rdx_device_service` 抽取 + `rdx_vm.c` 业务动作 wrapper 化 | 2.5 天 | 步骤 1-2 |
| 7 | `rdx_storage_service` 抽取格式化/同步编排 | 2 天 | 步骤 4、6 |
| 8 | `rdx_record_service` 抽取录音状态编排，承接 BLE 事件/适配调用 | 3 天 | 步骤 5、7 |
| 9 | `rdx_ble_server.c` 反调清理收尾 | 2 天 | 步骤 5、8 |
| 10 | `rdx_app.c` 瘦身收尾（移除已迁出实现，保留 ABI wrapper） | 1.5 天 | 步骤 4-9 |
| 11 | 弱符号替换产品 `#ifdef` | 1 天 | 步骤 3 |
| 12 | clean build + `.map` 对比 + 端到端冒烟回归 | 2 天 | 全部 |

总计：**约 20 人天（~4 人周）**。13 人天可作为理想路径估算，但当前 BLE/SPI/VM 耦合密度下不建议作为承诺工期。

## 7. 风险与缓解

| 风险 | 严重度 | 缓解措施 |
|---|---|---|
| `librdxApp.a` 内部直接调用 `rdx_app_*` 函数 | 高 | 步骤 4 开始前，用 `llvm-nm -u librdxApp.a` 列出未解析符号，确认哪些 `rdx_app_*` 符号被静态库依赖。被依赖的函数保留在 `rdx_app.c` 作为 thin wrapper，只转发不删除。 |
| 拆分后行为不一致 | 高 | 每步完成后执行冒烟测试；对比拆分前后的 `.map` 中函数调用关系（通过交叉引用反推）。 |
| BLE 回调同步语义变化 | 高 | 第一轮用 `rdx_ble_service_on_connected/disconnected` 适配旧调用，不直接把所有反调改成事件；确认行为稳定后再迁到订阅者。 |
| SPI 文件传输闭环断链 | 高 | 先定义 transport rx/tx_done 回调，保证“发送完成 → 推进下一包/清理 buffer”的路径由 `rdx_wifi_service` 承接。 |
| event bus 在错误上下文执行耗时回调 | 高 | 同步 publish 仅用于安全上下文；BLE/SPI/protocol 不确定上下文使用 `rdx_event_publish_async()` 转投 `app_core`；订阅者回调必须非阻塞。 |
| 阶段 1 wrapper 覆盖不足 | 中 | 新增 service 不新增裸 JL API；若迁移点需要 OS/task/timer/storage/gpio 能力，先补 `rdx_jl_*` wrapper。 |
| 消息分发增加延迟 | 低 | 热点路径（录音数据推送、文件分包推进）保留登记过的函数指针 dispatch；普通事件走统一 event bus。 |
| 静态数组订阅表容量不足 | 中 | `RDX_EVENT_MAX_SUBSCRIBERS` 初始设为 8；启动时打印订阅表占用情况，发现接近上限时增大编译期常量。 |
| `rdx_vm.c` 拆分打断静态库链路 | 中 | `rdx_vm.c` 中的旧函数保留为 thin wrapper；阶段 2 不删除任何静态库依赖的函数签名。 |
| 本机缺少 `llvm-nm` | 中 | 先从 JL 工具链或 LLVM 安装目录定位 `llvm-nm`；若不可用，使用工具链等价 `nm`，并把命令路径记录在迁移日志。 |
