## 2. 代码事实与复用审计

> 本篇沿用原方案第 2～14 章编号，以保持既有评审记录和交叉引用稳定。产品原理与选型结论见配套原理篇。

### 2.1 已有能力及唯一所有者

| 能力 | 现有所有者 | 本项目策略 |
|---|---|---|
| Classic 初始化与应用生命周期 | `earphone.c` | 直接复用，不在 RDX 重建 |
| 开机扫描、配对、回连、连接超时 | `dual_conn.c`、`bt_event_func.c` | 直接复用，不新建配对状态机 |
| Link Key/bond | BT Stack/VM | 直接复用，不建第二份数据库 |
| Inquiry/Page Scan 联动 | `dual_conn.c::write_scan_conn_enable()` | 复用现有入口，不直接操作 LMP |
| HFP SDP 注册 | `bt_profile_config.c` | 由 `TCFG_BT_SUPPORT_HFP` 控制 |
| HFP SLC | JL BT Stack、`phone_call.c` 事件 | 只观察，不接管 |
| SCO/eSCO 生命周期 | `phone_call.c` | 唯一音频 owner |
| 麦克风编码和上行 | `esco_recoder` | 直接复用 |
| 下行播放 | `esco_player` | 直接复用，产品层决定是否静音 |
| mSBC/CVSD、AEC/CVP | JL 音频模块 | 直接复用 |
| BLE HOGP transport | `rdx_hogp_keyboard.c` | 保持唯一 HID transport owner |
| HOGP key action/report 转换 | `rdx_hogp_key_action.c` | 一期提取通用 click-action 入口并复用既有 release timer；二期再扩展 press/release |

### 2.3 当前阻断点

JL SDK 在 `BT_STATUS_INIT_OK` 后已经初始化 BLE、加载回连记录，并在非 TWS 路径打开 Classic 扫描。随后 RDX handler 又在约 1 秒后调用 `rdx_app_bt_shutdown()`：

```text
dual_conn_close()
USER_CTRL_POWER_OFF
sd_set_power(0)
dac_power_off()
```

因此当前问题不是“缺少 Classic 配对和回连实现”，而是 RDX 产品主动关闭了 SDK 已经启动的 Classic 能力，并把它与板级省电动作绑在了一起。

### 2.4 当前按键事实

IO key 默认参数为：

```text
scan_time = 10 ms
long_time = 75
hold_time = 90
```

对应行为：

- 按住约 750 ms：产生一次 `KEY_ACTION_LONG`；
- 继续按住：周期产生 `KEY_ACTION_HOLD`，adapter 还可能转换为 1/3/5 秒事件；
- 达到 long 后松开：产生一次 `KEY_ACTION_UP`；
- 未达到 long 松开：产生 `KEY_ACTION_CLICK`，不会产生 `UP`。

这套语义适合一期“长按触发一次”：LONG 发送 `Win+H` click，HOLD 不重复发送，UP 只用于结束已接管手势。二期也可在同一事件流上扩展为 LONG 开始、UP 结束的真 PTT。无需新增物理 down/up observer。

## 3. 目标与非目标

### 3.1 目标

1. 最大化复用 JL SDK 的 Classic/HFP/音频/连接管理。
2. 新增模块只补状态观测、RDX 产品绑定和 KEY5 语音意图。
3. 支持同一台 PC 同时连接 BLE HOGP 与 Classic HFP。
4. HFP active 时保持 HOGP 输入，任一链路断开不主动关闭另一条链路。
5. 一期 KEY5 达到 long 阈值后发送一次 `Win+H` click，HOLD/UP 不产生第二次系统快捷键。
6. 所有产品覆盖位于 `t2620_project_config.h`，不修改工具生成配置。
7. 保留现有产测、DUT 和 Classic 无线升级所需 Profile；本方案只关闭会与 BLE HOGP 重复枚举的 Classic HID，不顺带精简 A2DP、AVCTP、SPP、MAP 或升级能力。
8. 每个阶段有自动验收、设备验收、回归范围和退出条件。

### 3.2 非目标

- 不实现第二套 Classic 配对、扫描、回连或 bond 数据库。
- 不复制 `dual_conn.c`、`bt_event_func.c` 或 `phone_call.c`。
- 不在新模块中调用 `esco_player_open/close()` 或 `esco_recoder_open/close()`。
- 不直接调用 `lmp_hci_write_scan_enable()`。
- 不伪造 HFP SLC、SCO 或通话状态。
- 不把麦克风音频放到 HID、RDX GATT 或自定义 BLE characteristic。
- 不定义 Mic-only 私有 SDP。
- 不让 HFP 模块处理 KEY5；语音触发是独立产品模块。
- 不在一期实现 F24、真 PTT、PC Agent 或自动麦克风绑定。
- 不在一期支持 PC HOGP、手机 RDX Config、Classic HFP 三方并发。
- 不在 HFP 麦克风改造中精简既有 Classic Profile；任何后续 Profile 裁剪必须先证明不影响产测、DUT、SPP 和 Classic 无线升级，并作为独立项目评审。

## 4. 推荐模块架构

### 4.1 架构图

```text
JL SDK（既有、唯一控制者）
├─ earphone.c / dual_conn.c / bt_event_func.c
│  └─ Classic 生命周期、扫描、配对、bond、回连
├─ BT Stack / bt_profile_config.c
│  └─ HFP SDP、ACL、SLC、SCO/eSCO
└─ phone_call.c / esco_player / esco_recoder
   └─ HFP 音频生命周期和麦克风数据

新增公共观测层
└─ bt_hfp_mic_status.c/.h
   └─ 从既有 BT_STATUS_* 派生 T2620 单 Classic 链路的只读快照和统计，不发送控制命令

RDX 产品层
├─ rdx_hfp_mic.c/.h
│  └─ 编译开关、HFP 事件转发和诊断；不 include/call HOGP
└─ rdx_voice_trigger.c/.h
   ├─ 一期：KEY5 LONG/HOLD/UP + HOGP ready -> 在线单次 Win+H 或完整离线分发
   └─ 二期：可演进或并列增加 rdx_voice_ptt，实现 F24 press/release

RDX 组合入口
└─ rdx_app.c
   └─ 组合 HFP Mic、HOGP 和 voice trigger；模块之间不形成双向依赖

既有 HOGP
├─ rdx_hogp_key_action.c/.h
│  └─ Action -> Keyboard Report；一期增加通用 click-action 入口并复用现有 click 生命周期
└─ rdx_hogp_keyboard.c/.h
   └─ ATT notify transport
```

### 4.2 推荐文件

```text
SDK/apps/common/bt_common/
├─ bt_hfp_mic_status.h
└─ bt_hfp_mic_status.c

SDK/apps/common/third_party_profile/rdx_protocol/
├─ rdx_hfp_mic.h
├─ rdx_hfp_mic.c
├─ rdx_voice_trigger.h
└─ rdx_voice_trigger.c
```

不新增 `hfp_mic_core`、`hfp_mic_platform_ops` 或自建 pairing state machine。当前项目本身就是 JL SDK 固件，额外抽象一套平台控制接口只会形成双重所有权。

### 4.3 依赖规则

| 模块 | 允许依赖 | 禁止依赖 |
|---|---|---|
| `bt_hfp_mic_status` | JL 基础类型、BT event 常量 | RDX、HOGP、scan/reconnect、音频 open/close |
| `rdx_hfp_mic` | status public API、既有 RDX BT event 转发点 | HOGP、LMP、dual_conn 内部状态、audio owner、KEY5 |
| `rdx_voice_trigger` | HOGP ready/key action API、RDX 产品 key ID、物理 KEY5 action | HFP header/API、Classic scan、SCO、音频模块 |
| `rdx_hogp_key_action` | HOGP report transport | HFP、物理 GPIO、PC Agent |

编译期产品组合约束与源代码依赖必须分开理解：`rdx_hfp_mic` 可以在 HOGP 关闭时作为普通 HFP Mic binding 独立编译；一期 `rdx_voice_trigger` 和二期 `rdx_voice_ptt` 是 T2620 Windows 语音产品语义，启用时必须同时具备 HFP Mic 与 HOGP。该组合门禁不能通过让 HFP 模块 include HOGP、监听 HID 生命周期或在运行时联动开关两条链路实现。

### 4.4 复用门禁

以下任一情况出现即视为架构回退：

- 新增第二套 pairing timeout、page list 或 link key 存储；
- 新模块直接控制 Inquiry/Page Scan；
- 新模块直接打开或关闭 SCO、player、recorder；
- fork 或复制 `phone_call.c`、`dual_conn.c` 的逻辑；
- HFP 状态变化重建或切换 BLE RDX/HOGP 统一入口；
- KEY5 代码进入 HFP 状态监视模块。
- `rdx_hfp_mic` include/call HOGP，或 HOGP transport include/call HFP/voice trigger；

## 5. 只读 HFP 状态监视

### 5.1 定位

`bt_hfp_mic_status` 不是第二个状态机 owner。它只是把已经发生的 SDK 事件归一化为产品可查询的快照，用于日志、测试、LED 诊断和共存统计；二期 Agent 如有需要也只能读取这些事实，不能借此控制 SDK 音频状态机。

权威状态始终属于 JL BT Stack 和 `phone_call.c`。监视器不得根据快照发控制命令。

一期 API 明确是 **single-link observer**，与 T2620 的 `TCFG_BT_DUAL_CONN_ENABLE=0` 一致。SDK 的 `FIRST/SECOND` 是通用事件命名，不代表本模块保存两份 peer 状态。若其他产品需要一拖二复用，必须先把 API 升级为按地址查询的多 peer 模型；禁止让一份全局快照在两个地址之间覆盖。

### 5.2 快照

```c
typedef enum {
    BT_HFP_MIC_LINK_IDLE = 0,
    BT_HFP_MIC_LINK_ACL,
    BT_HFP_MIC_LINK_SLC,
    BT_HFP_MIC_LINK_AUDIO,
} bt_hfp_mic_link_state_t;

typedef enum {
    BT_HFP_MIC_CODEC_UNKNOWN = 0,
    BT_HFP_MIC_CODEC_CVSD,
    BT_HFP_MIC_CODEC_MSBC,
} bt_hfp_mic_codec_t;

typedef struct {
    bt_hfp_mic_link_state_t state;
    u8 acl_connected;
    u8 slc_connected;
    u8 audio_active;
    u8 addr_valid;
    u8 addr[6];
    bt_hfp_mic_codec_t codec;
    u16 raw_esco_type;
    u16 rx_packet_len;
    s32 last_reason;
} bt_hfp_mic_snapshot_t;
```

`state` 是事实位的派生展示值：

```text
audio_active  -> AUDIO
slc_connected -> SLC
acl_connected -> ACL
otherwise     -> IDLE
```

监视器不定义 `PAIRING`、`RECOVERING`、`ERROR` 等控制态，避免与 SDK 连接管理重叠。异常通过统计和日志表达。

### 5.3 事件映射

至少观察：

| SDK 事件 | 快照变化 |
|---|---|
| `BT_STATUS_FIRST/SECOND_CONNECTED` | ACL on，保存地址 |
| `BT_STATUS_FIRST/SECOND_DISCONNECT` | ACL/SLC/audio 全部清理 |
| `BT_STATUS_HFP_SERVICE_LEVEL_CONNECTION_OK` | ACL/SLC on，幂等 |
| `BT_STATUS_CONN_HFP_CH` | ACL/SLC on，幂等 |
| `BT_STATUS_DISCON_HFP_CH` | SLC/audio off |
| `BT_STATUS_SCO_STATUS_CHANGE` 且 `value != 0xff` | ACL/SLC/audio on；`value >> 16` 记录包长，`value & 0xffff` 记录 raw eSCO type；raw type 低字节为 0 派生 CVSD，否则派生 mSBC |
| `BT_STATUS_SCO_STATUS_CHANGE` 且 `value == 0xff` | audio off |
| `BT_STATUS_SCO_DISCON` | audio off，幂等 |

要求：

- 不保存 `struct bt_event *`，只同步复制必要字段；
- 重复事件幂等；
- 首次事实位 `0 -> 1` 才增加对应 connect/open 计数；相同事件重复到达只增加 `duplicate_event_count`，不能重复增加业务计数；
- 所有 disconnect/close 计数同样按事实位 `1 -> 0` 计数；ACL 断开导致 SLC/audio 被级联清理时，也要为实际发生的每个 `1 -> 0` 增加一次计数，后续迟到的 close 只算 duplicate；
- 上层事实可以补齐必需的下层事实：SLC 意味着 ACL 已建立，audio 意味着 ACL 与 SLC 均已建立；
- single-link 快照已绑定有效地址后，地址不匹配的迟到 SLC/SCO/断开事件只计为 stale/unknown 诊断，不得清除当前 peer；新的 ACL connected 只有在当前 ACL 已为空时才能绑定地址；
- 未知事件计数后忽略；
- 断开事件将下层事实一并清理；
- 不因事件错序发送任何恢复命令；
- status dump 只输出 HFP/Classic 快照和统计，不读取 HOGP；需要同屏比较两条链路时，由 `rdx_app` 组合入口分别查询后输出产品级日志；
- `codec` 是从 raw eSCO type 派生的规范化展示值，不能直接把 `bt->value` 或 `value & 0xffff` 当作 codec；原始字段单独保留用于诊断；
- 更新和查询默认都运行在 `app_core`。若未来允许其他任务调用 `get/stats_get`，必须用短临界区复制完整快照，不能让调用方读到撕裂的地址、计数或多字节字段。

### 5.4 API

```c
void bt_hfp_mic_status_init(void);
void bt_hfp_mic_status_reset(void);
void bt_hfp_mic_status_handle_event(const struct bt_event *event);
void bt_hfp_mic_status_get(bt_hfp_mic_snapshot_t *snapshot);
void bt_hfp_mic_status_stats_get(bt_hfp_mic_stats_t *stats);
void bt_hfp_mic_status_dump(void);
```

RDX binding 只负责从现有 `MSG_FROM_BT_STACK` handler 向公共 status 转发 HFP 相关事件。HFP/HOGP 组合诊断位于 `rdx_app`，不得反向下沉到 `rdx_hfp_mic` 或公共 status。

## 6. Classic 生命周期与产品开关

### 6.1 产品开关

```c
#ifndef TCFG_RDX_HFP_MIC_ENABLE
#define TCFG_RDX_HFP_MIC_ENABLE                  0
#endif

#ifndef TCFG_BT_HFP_MIC_STATUS_ENABLE
#define TCFG_BT_HFP_MIC_STATUS_ENABLE            TCFG_RDX_HFP_MIC_ENABLE
#endif

#ifndef TCFG_RDX_VOICE_TRIGGER_ENABLE
#define TCFG_RDX_VOICE_TRIGGER_ENABLE             0
#endif

#ifndef TCFG_RDX_VOICE_PTT_ENABLE
#define TCFG_RDX_VOICE_PTT_ENABLE                 0
#endif

#if TCFG_RDX_HFP_MIC_ENABLE && !TCFG_BT_SUPPORT_HFP
#error "RDX HFP mic requires Classic HFP"
#endif

#if TCFG_RDX_VOICE_TRIGGER_ENABLE && \
    (!TCFG_RDX_HFP_MIC_ENABLE || !TCFG_RDX_HOGP_ENABLE)
#error "Windows voice trigger requires RDX HFP mic and HOGP"
#endif

#if TCFG_RDX_VOICE_PTT_ENABLE && \
    (!TCFG_RDX_HFP_MIC_ENABLE || !TCFG_RDX_HOGP_ENABLE)
#error "Voice PTT requires RDX HFP mic and HOGP"
#endif

#if TCFG_RDX_VOICE_TRIGGER_ENABLE && TCFG_RDX_VOICE_PTT_ENABLE
#error "Voice trigger and voice PTT are mutually exclusive"
#endif
```

`TCFG_RDX_HFP_MIC_ENABLE` 控制 RDX 产品绑定和 Classic 保留策略；公共只读监视器默认跟随它。非 RDX 产品需要复用监视器时可以单独覆盖 `TCFG_BT_HFP_MIC_STATUS_ENABLE=1`。

`TCFG_RDX_HFP_MIC_ENABLE` 本身不要求 HOGP：普通 HFP Mic 配置可以只开启 HFP。`TCFG_RDX_VOICE_TRIGGER_ENABLE` 独立控制一期 KEY5 `Win+H` 源码路径，模块内部只依赖 RDX HOGP，不 include/call HFP；但作为 T2620 产品组合，启用 trigger 时必须同时开启 HFP Mic 与 HOGP。二期 PTT 遵循同一组合约束，并与一期 trigger 互斥，避免一次 LONG 同时发送 `Win+H` 和 F24。其他产品默认关闭 trigger/PTT。

### 6.2 启动行为

当 `TCFG_RDX_HFP_MIC_ENABLE=1`：

- 不调度 `rdx_app_bt_shutdown()`；
- 保留 `earphone.c` 和 `dual_conn.c` 的原生初始化、回连和扫描；
- 初始化只读 status/binding；
- 板级 SD/DAC 省电仍按独立 board power policy 执行。

当开关为 `0`：

- 保留非 HFP RDX 产品原有 Classic 关闭行为；
- 不编译或不调用新增 status/binding；
- 不改变现有 BLE/RDX 行为。

### 6.3 拆分旧 shutdown

旧函数必须拆成两个明确动作：

```text
rdx_classic_disable_for_product()
    -> dual_conn_close()
    -> USER_CTRL_POWER_OFF

rdx_board_idle_power_apply()
    -> 仅在对应资源确实 idle 时执行 SD/DAC 和其他板级省电
```

HFP 产品只跳过第一个动作，不能连带跳过板级省电。`rdx_board_idle_power_apply()` 也不能机械地无条件调用 `dac_power_off()`：必须确认没有 SCO/audio owner 正在使用 DAC，且后续 `phone_call` 正常打开音频时能够恢复。进入启动后 1 秒内快速回连并打开 SCO 是必测竞态。

`dual_conn_close()` 已负责清理 page list、扫描 timer 和 page 命令；拆分时不得把这些 Classic 状态误归到 board power。现有低功耗 target dump 保留为诊断动作或归入 board policy，但不能在两个动作中重复执行协议关闭。

### 6.4 DUT 退出恢复

DUT 进入当前会直接打开 Classic 扫描并切换 controller 模式。HFP 产品退出 DUT 时不能仅仅“跳过 `rdx_app_bt_shutdown()`”，否则可能遗留 DUT 的扫描状态。

退出顺序必须是：

```text
bt_bredr_exit_dut_mode()
rdx_spp_exit()
if TCFG_RDX_HFP_MIC_ENABLE:
    -> 调用 dual_conn owner 的公开状态重算/恢复入口
    -> 首选经 Phase 0 实测确认后的 dual_conn_state_handler()
else:
    -> rdx_classic_disable_for_product()
rdx_board_idle_power_apply()
```

HFP 恢复路径不得继续调用 `lmp_hci_write_scan_enable()` 猜测扫描状态；扫描、回连 timer 和 page list 仍由 `dual_conn` 决定。

### 6.5 配对和回连

一期直接采用 SDK 现有参数：

```text
TCFG_BT_PAGE_TIMEOUT              = 8 s
TCFG_BT_POWERON_PAGE_TIME         = 60 s
TCFG_BT_TIMEOUT_PAGE_TIME         = 120 s
TCFG_DUAL_CONN_INQUIRY_SCAN_TIME  = 120 s
TCFG_DUAL_CONN_PAGE_SCAN_TIME     = 0
```

SDK 已负责：

- 从已记录设备列表发起开机回连；
- 回连超时后恢复扫描；
- 120 秒 Inquiry Scan；
- 连接后关闭 Inquiry、保留需要的 Page Scan；
- 连接超时和 Link Key missing 处理。

若实机行为不符合产品需求，优先调整上述 SDK 配置或调用 `dual_conn.h` 的公开入口。禁止在 HFP 模块内增加第二个 timer/page list/bond 状态机。

Phase 0 必须在 `TCFG_BT_DUAL_CONN_ENABLE=0` 的实际产品配置下验证 `write_scan_conn_enable()`、`dual_conn_state_handler()` 和 `dual_conn_close()`，不能仅凭文件名或编译通过推断单连接行为。

如果后续需要“用户主动重新进入 120 秒配对模式”，应在现有 `dual_conn` 所有权内增加或完善公开 pairing API，由它复用现有 scan flags 和 timer；不得把配对 timer 放进 `rdx_hfp_mic`。

## 7. KEY5 语音触发与二期 PTT 演进

### 7.1 一期产品语义：Win+H 单次触发

```text
KEY5 KEY_ACTION_LONG（约 750 ms）+ gesture_owner == NONE
    -> 采样一次 HOGP ready
    -> ready：gesture_owner = ONLINE，消费 LONG，通过现有 key action click 发送一次 Win+H
    -> not ready：gesture_owner = OFFLINE，强制把 LONG 分发给既有离线 key table

KEY5 KEY_ACTION_HOLD / HOLD_1SEC/3SEC/5SEC 等
    -> owner == ONLINE：消费，不重复发送 Win+H
    -> owner == OFFLINE：继续强制分发给离线 key table

KEY5 KEY_ACTION_UP
    -> owner == ONLINE：清理 owner 并消费 UP，不再发送 HID report
    -> owner == OFFLINE：清理 owner，并把 UP 分发给离线 key table

KEY5 KEY_ACTION_CLICK
    -> 不建立 owner；按事件到达时的 HOGP ready 执行既有在线 keymap 或离线短按行为
```

一期不是 PTT。`Win+H` 的 down/up 由一次普通 HOGP click 完成，KEY5 物理松开不表示停止录音。Windows 可能将快捷键解释为打开、切换或聚焦语音输入面板，并可能在静默后自动停止；具体行为以 Phase 0 冻结的目标 Windows 版本为准，固件不维护或推断 Windows 听写状态。

`gesture_owner` 是一次 KEY5 长按手势的路由锁，取值为 `NONE/ONLINE/OFFLINE`。它在 LONG 到达时只采样一次 HOGP ready，并保持到对应物理 UP：在线手势即使 click 失败或中途丢失 ready，也不能把 HOLD/UP 泄漏到离线录音；离线手势即使中途获得 ready，也不能让在线路由截走 HOLD/UP。模块关机且确认不会再处理该 UP 时才可强制清理。

KEY5 离线默认表当前以 LONG `APP_MSG_RECORD_SWITCH`、UP `APP_MSG_LONG_PRESS_HOLDUP` 组成完整录音手势。如果离线 LONG 后、物理 UP 前 HOGP 变为 ready，而路由只看事件到达时的 ready，UP 会被在线路径吞掉。因此产品路由必须先让语音触发模块返回本次手势的强制路由结果，再考虑普通 HOGP/离线分流：

```text
KEY5 event
    -> route = rdx_voice_trigger_route_key(action, hogp_ready)
       -> owner == ONLINE：返回 CONSUME，持续到 UP，与当前 ready 无关
       -> owner == OFFLINE：返回 FORCE_OFFLINE，持续到 UP，与当前 ready 无关
       -> owner == NONE + LONG：按当前 ready 建立 ONLINE/OFFLINE owner
       -> CLICK/其他无 owner 事件：返回 DEFAULT
    -> CONSUME：*value = APP_MSG_NULL
    -> FORCE_OFFLINE：直接查既有 offline key table，禁止再按当前 ready 二次分流
    -> DEFAULT：执行现有 ready ? HOGP : offline 路由
```

禁止先按当前 ready 分流后才调用语音触发模块，也禁止 `FORCE_OFFLINE` 返回后再次读取 ready 决定目的地；否则 ready-loss 会让在线 UP 泄漏到离线表，ready-gain 会吞掉离线录音所需的 UP。

### 7.2 一期复用 HOGP click

现有 `rdx_hogp_key_action_click(u8 key_id)` 只能从当前物理 keymap 取 action。不能为了 LONG 触发而把 KEY5 的普通短按映射永久改成 `Win+H`。一期应在同一 executor 内提取通用入口：

```c
int rdx_hogp_key_action_click_action(
    const rdx_hogp_key_action_keyboard_t *action);
```

原 `rdx_hogp_key_action_click(key_id)` 取出 keymap action 后调用该入口，保持现有外部行为。`rdx_voice_trigger` 使用 `{ HID_KEYBOARD_MOD_LGUI, HID_KEYBOARD_USAGE_H }` 调用它；`hid_keyboard_usage.h` 补充标准 `HID_KEYBOARD_USAGE_H = 0x0B` 常量。注意：该头文件当前的 include guard 恰好占用了 `HID_KEYBOARD_USAGE_H` 这个符号，新增常量前必须先把 guard 改名为 `HID_KEYBOARD_USAGE_DEFS_H`（不得使用双下划线形式，那属于实现保留标识符），字母常量保持 `HID_KEYBOARD_USAGE_<letter>` 惯例。两条路径共享 action-to-report、notify、20 ms release timer 和错误返回，不直接构造 ATT payload，不直接调用 `app_ble_att_send_data()`，也不增加 F24 press/release API。

一期要求：

- LONG 按当时 HOGP ready 建立 `ONLINE/OFFLINE` owner；ONLINE 每次物理手势最多尝试一次 click，OFFLINE 完整走既有 key table；
- 全部 HOLD 家族事件沿用 owner：ONLINE 消费，OFFLINE 强制离线分发；
- UP 沿用并清理 owner：ONLINE 消费且不发送第二次 `Win+H`，OFFLINE 必须到达既有离线 key table；
- owner 建立后不受 ready-loss/ready-gain 改变；
- KEY5 三击不再承担 BLE 模式切换，并按既有离线 key table/产品按键策略处理；
- `click_action()` 不保存调用方 action 指针，必须在调用期间同步转换为 report；
- `click_action()` 校验 action 并沿用 transport ready 检查，但不依赖 active keymap；默认 keymap 为空时 KEY5 LONG 仍能触发 `Win+H`；
- 不新增底层物理 down/up observer、held report、PTT active、ready-loss observer 或 PTT 专用 ATT 通道；
- KEY1～KEY4 和现有自定义 keymap 行为不变。

`Win+H` 是普通组合键 click，其按下和 20 ms 后释放继续由现有 executor 唯一管理。若现有 executor 对任意组合键的 notify 失败或断连恢复存在通用缺陷，应作为 HOGP 基础能力修复并回归全部按键，不能为 KEY5 新建第二个 sender。

### 7.3 一期 Windows 边界

- 仅支持 Phase 0 冻结的 Windows 版本、显示语言和语音输入语言；
- 用户需在 Windows 中将本设备 HFP Mic 设为系统默认输入设备；固件不能选择音频端点；
- 当前焦点必须是 Windows 语音输入支持的文本输入位置；
- Windows 语音服务、隐私权限和可能的联网条件必须可用；
- 多台同型号设备或多个麦克风并存时，一期不保证自动选中与 KEY5 同一物理设备的 Mic；
- `Win+H` 被系统策略、应用快捷键或远程桌面截获时，固件不能补救或确认触发结果；
- HFP/SCO 状态只能证明音频链路事实，不能证明 Windows 已完成或正在保存听写。

一期用户说明和验收报告必须如实记录这些边界，不能把 Windows 原生语音输入描述为设备端真 PTT。

### 7.4 二期增强：F24 真 PTT + 指定麦克风

二期增加 `rdx_voice_ptt.*` 和 PC Agent，KEY5 LONG 发送 F24 down，UP 发送 F24 release。Agent 捕获并消费 F24，稳定关联 BLE Keyboard 与同一物理设备的 Classic HFP Mic，明确选择该端点，并按 down/up 控制采集、STT 和文本注入。

该增强必须单独评审以下状态机，不得提前带入一期：

- `gesture_owner` 与仅在 F24 press 成功后置位的 `ptt_active` 分离；ready-loss 清 active，但 ONLINE/OFFLINE owner 均保留到物理 UP；
- executor 统一维护持久 `held_report`、单个 `transient_report`、`desired_report`、`last_sent_report` 和 dirty/retry；
- KEY1～KEY4 click 与 held F24 合成，click timer 恢复 held；两个独立 transient 之间必须有明确 key-up；
- release 失败可重试，ready-loss 后不重放旧 F24；必要时 ready 恢复先通过全零 baseline 屏障；
- HOGP transport 只提供通用 lifecycle observer，不反向依赖 `rdx_voice_ptt`；
- Agent 不能只按显示名称匹配 Keyboard/Mic；必须使用经实测冻结的稳定标识或用户绑定流程；
- Agent 离线或 hook 失败时 F24 可能进入当前应用，但不能影响普通键盘或造成设备端卡键。

F24 真 PTT 的设备端和 PC 端测试在 Phase 5 执行；通过前不属于一期量产承诺。

## 8. 名称与 Windows 枚举

### 8.1 名称策略

沿用 T2620 客户定制名称：BLE 统一端点使用产品名，Classic HFP 端点增加 `MIC` 后缀以明确区分功能：

```text
BLE RDX + HOGP：Beanstalk RKB
Classic HFP：Beanstalk RKB MIC
```

该区分不是品牌拆分，而是双 transport 首次配置的识别要求。BLE HOGP 与 Classic HFP 分别维护连接和 bond，当前架构不能依赖一次 Windows 配对操作同时完成两条链路，使用完全相同的名称也不会把它们合并，反而会让用户无法判断正在配对哪个端点。因此保留共同产品名，并只给 Classic 端点增加 `MIC` 功能后缀。

上述名称分别对应当前 `BLE_LOCAL_NAME` 与 `BT_NAME`，不是占位示例。代码、文档、Windows 验收记录和用户说明必须保持一致；客户后续变更名称时，两条链路应作为同一项客户配置同步评审。

### 8.2 当前事实

- Classic 默认是 `Beanstalk RKB MIC`；
- BLE primary ADV 与 GAP Device Name `0x2A00` 都读取 RDX Server local name；
- Scan Response 保留 RDX Manufacturer Data，并追加 HID UUID `0x1812`；不存在 HOGP 专用名称或 Appearance 配置；
- BLE local name 可能已经保存在 VM；
- `bt_get_local_name()` 当前返回编译期 `BT_NAME`，Classic 动态改名必须实测 EIR/Windows 结果。

BLE 统一广播名与 GAP `0x2A00` 必须一致。一期名称只用于用户识别和手动选择默认麦克风；二期 PC Agent 不得仅通过名称关联 Keyboard 和 Mic。

Classic 名称验收必须覆盖：修改 `BT_NAME` 后 EIR 和 Windows 显示是否更新、旧 bond 是否继续显示缓存名、是否必须删除设备并重新配对，以及 RDX 动态改名路径能否真正调用本地名/EIR 更新。若动态改名不可靠，一期冻结为编译期产品名，不把 App 改名作为量产能力。

### 8.3 跨 transport 设备关联与分期边界

一期首次安装必须分别配对 `Beanstalk RKB`（BLE RDX + HOGP）和 `Beanstalk RKB MIC`（Classic HFP）。这表示首次建立两个 bond，不表示每次使用都要手动连接两次；配对完成后，两条链路应各自开机回连和超距回连。任一链路未连接时仅保留另一条链路的独立能力：只有 BLE 时可以发送 HOGP 按键但本设备 HFP Mic 不可用，只有 Classic HFP 时麦克风可用但 KEY5 不能通过 HOGP 发送 `Win+H`。

一期没有 Agent，也没有 BLE Keyboard 与 Classic Mic 的自动绑定：Windows 语音输入使用系统默认麦克风。存在两台及以上同型号设备或多个输入端点时，由用户在 Windows 设置中选择正确的 HFP Mic；该限制必须进入用户说明和一期验收。

二期 Agent 必须把某个 BLE HOGP 的 F24 与同一物理设备的 Classic HFP Mic 稳定关联，不能只比较显示名称。候选依据按可靠性实测选择：Windows Container ID/父设备关系、可稳定获取的 Classic 地址与 BLE 地址派生关系，或由 RDX 暴露且 Agent 可与音频端点属性关联的稳定设备 ID。必须记录休眠、删除 bond、重新配对和地址变化后的稳定性；若 Windows 无法提供可靠自动关联，二期必须提供用户确认、持久化和解绑流程。

### 8.4 Profile 枚举

Phase 0 记录当前 Windows 枚举。T2620 正式配置只关闭 Classic HID，避免与 BLE HOGP 重复枚举 Keyboard；A2DP、AVCTP、SPP、MAP、PNP、`TCFG_AUDIO_DUT_ENABLE` 和 `TCFG_UPDATE_BT_LMP_EN` 保持当前有效配置。SPP 是既有产测/DUT 通道：`rdx_dut.c` 进入/退出 DUT 时直接调用 `rdx_spp_init()/rdx_spp_exit()`，且音频 DUT 配置会强制启用 SPP。Classic 无线升级继续由 BT LMP update 能力承载，不能因 HFP 麦克风改造而关闭。

A2DP/AVCTP 会让 Windows 出现额外媒体端点，但在本方案中属于保留既有产品能力的已知结果，不作为缺陷或顺带精简项。未来若要裁剪，必须单独确认客户需求，并完整回归产测、DUT、无线升级、Windows 枚举和回连；HFP 本身仍是全双工，即使关闭 A2DP，Hands-Free 下行端点也可能继续存在。

## 9. HOGP 与 HFP 共存

### 9.1 固定原则

- HFP active 不暂停 HOGP Input Report；
- HFP 状态不重建或切换 BLE RDX/HOGP 统一入口；
- HOGP 状态不控制 SCO/eSCO；
- 任一链路断开不主动关闭另一条链路；
- RDX 与 HOGP 继续复用单 BLE link，按 capability 独立激活，不引入 owner；
- Classic HID 关闭；
- `phone_call.c` 继续唯一拥有 SCO 音频。

### 9.2 BLE high priority

`TCFG_BLE_HIGH_PRIORITY_ENABLE=1` 只是 A/B 测试候选，不是默认正确答案。必须对比 `0/1`：

- HOGP down/up notify 返回码、P50/P95/P99 时延；
- eSCO 上下行丢包、PLC、爆音、断续；
- 高频按键时 SCO 是否异常断开；
- HFP active 时 HOGP 断开后的回连；
- 近距离、临界距离和 2.4 GHz 干扰环境。

以键盘和音频双向数据决定最终值，不能只验证 HOGP。

### 9.3 HFP 下行

HFP 是全双工 Headset/Hands-Free，不是 Mic-only。当前工程配置了 DAC 和 `esco_dac_ch` 下行节点，量产硬件是否安装换能器必须结合原理图/BOM 和实机确认。

若产品不需要下行播放，在既有音频策略层静音或安全丢弃；不得修改 SDP、fork `phone_call.c` 或把该逻辑放进 status/binding。
