# OpenAI Codex Micro Windows 兼容接入方案（基于开源实现重新评估）

> 文档状态：重新评估后的方案提案，尚未实施
> 评估基线：`codex-micro-4-core2/`，commit `2ee23a4ab696f94bb78d250f28cc4a9b879ba079`（2026-07-16）
> 目标平台：Windows 11 + ChatGPT desktop app for Windows
> 当前产品基线：RDX 与标准 BLE HOGP 键盘共用一个 GATT Server，最多两条 Peripheral ACL
> 性质：非官方兼容性研究，不是 OpenAI 或 Work Louder 发布的协议规范

## 1. 重新评估结论

接入在协议和固件层面具有可行性，但 **Windows 上的 ChatGPT 发现能力仍是未决前置条件**。开源项目只证明一组 BLE Vendor HID 参数可在 macOS 上被某个 ChatGPT 桌面端版本识别和使用；它没有 Windows 实机记录，也未证明“标准键盘 + Vendor HID”复合 Report Map 一定会被 Windows 版 ChatGPT 识别。

OpenAI 官方 Codex Micro 页面说明设备可通过 USB-C 或 Bluetooth 连接“电脑”，并只对 macOS 补充 Input Monitoring 步骤；官方 Windows 应用页面确认 Windows 原生应用存在，但没有明确给出 Codex Micro 的 Windows 支持矩阵。不能把平台中性文案自动解释为 Windows HID 互操作已经验证。

因此 Windows 方案的第一结论不是“立即移植”，而是：**先完成 Windows 资格验证 Gate W0；若官方设备或参考等价固件在目标 Windows App Build 上都无法触发 Codex Micro 设置，则暂停 T2620 的 ChatGPT 直连实现，只保留自有 Windows Host 工具的协议验证。**

与旧方案相比，本次评估有六项关键修正：

1. 已验证开源实现使用完整字段 `method` / `params`，不是紧凑字段 `m` / `p`。
2. 设备发送 JSON 后追加单个 LF（`0x0A`），不是 CRLF。
3. 已验证 Vendor Report Descriptor 是 29 字节；追加到当前 70 字节键盘描述符后应为 99 字节，不是 106 字节。
4. 灯效字段 `b`、`s` 是浮点数，`e` 是字符串（如 `off`、`breath`），不是整数枚举。
5. 未知 RPC 方法返回 JSON-RPC 错误 `-32601 Method not found`，不是 404。
6. `0x303A:0x8360`、名称、制造商字符串、Usage Page 和 Report ID 是一组“共同验证成功”的身份参数；开源项目没有逐项消融，不能声称桌面端只过滤 VID/PID/Usage Page。

推荐区分两层目标：

| 层级 | 目标 | 结论边界 |
|---|---|---|
| Windows 协议兼容 | Windows HIDAPI/Win32 测试工具可通过 Report ID 6 双向通信 | 证明固件和 Windows HID 路径，不等于 ChatGPT 可发现 |
| Windows 桌面端互操作 | 目标 Windows ChatGPT App 可发现并处理 Agent Key | 必须先通过 Gate W0，再验证复合 Report Map |

这不是 OpenAI 云 API 接入，不使用 API Key、账号登录、网络请求或云端 SDK。

## 2. 证据等级与边界

### 2.1 可作为协议参考的开源结论

`codex-micro-4-core2` 的源码和实机记录给出以下基线：

| 项目 | 已验证值 |
|---|---|
| 已验证主机 | macOS + 支持 Codex Micro 的 ChatGPT 桌面端；Windows 未验证 |
| 传输 | BLE HOGP，单连接 |
| 设备名称 / Manufacturer | `Codex Micro` / `Work Louder` |
| PnP Source / VID / PID | `0x02` / `0x303A` / `0x8360` |
| Appearance / Service | Generic HID / HID `0x1812` |
| Vendor Usage Page / Usage | `0xFF00` / `0x01` |
| Report ID | `6` |
| Input / Output Report Body | 各 63 字节，不含 Report ID |
| JSON 字段 | `method`、`params`、`id`、`result`、`error` |
| 设备发送消息结尾 | 单个 LF |
| 配对 | Bonded Just Works |

参考项目记录了 2026-07-16 的 Core2 实机发现、连接、重连和控制验证，但没有记录 ChatGPT 桌面端 Build Number。它是有效的互操作证据，不是稳定规范。

### 2.2 仍未证明的部分

- Windows ChatGPT App 是否枚举、打开并订阅相同 Vendor HID；
- Windows HID API 是否按参考实现相同方式暴露 64 字节 host buffer；
- Linux、USB HID 或多主机兼容性；
- 标准键盘 Collection 与 Vendor Collection 共存时，ChatGPT 是否仍会发现设备；
- 名称、Manufacturer、VID、PID、PnP Source、Appearance 中每一项是否单独必要；
- 两条 BLE ACL、两个 wrapper、peer-scoped CCC 与该协议的组合行为；
- 目标桌面端升级后的长期兼容性；
- 第三方产品使用名称、商标和 VID/PID 的授权。

当前最大风险有两层：**Windows App 是否具备同等设备发现路径未知；即使具备，该路径对复合 HID 描述符和整组设备身份的依赖也未知。**

## 3. 当前 T2620 基线

现有实现位于 `rdx_hogp_profile.h/.c`、`rdx_hogp_keyboard.c`、`rdx_hogp_key_action.c` 和 `rdx_ble_server.c`。

| 能力 | 当前值 |
|---|---|
| HID Service | `0x1812`，句柄 `0x0016-0x0025` |
| Keyboard Input / Output | Report ID 1，8 字节 / 1 字节 |
| Report Map | 70 字节标准键盘描述符 |
| Device Information | `0x0026-0x002a` |
| PnP ID | Source `0x02`，VID `0x1234`，PID `0x0001`，Version `0x0001` |
| Manufacturer | `JieLi` |
| 安全 | 动态 HID 属性要求加密，Bonded Just Works |
| 拓扑 | 两个 wrapper、一个 GATT Server、全局最多一个 HID owner |

Codex 增量继续放在同一个 HID Service 内。不能新建第二个 GATT Server、独立 Codex 广播模式或新的 owner 类型。

## 4. 精确 HID 描述符

开源项目使用以下 29 字节 Vendor Application Collection：

```c
0x06, 0x00, 0xFF,  /* Usage Page (Vendor Defined 0xFF00) */
0x09, 0x01,        /* Usage (1) */
0xA1, 0x01,        /* Collection (Application) */
0x85, 0x06,        /*   Report ID (6) */
0x15, 0x00,        /*   Logical Minimum (0) */
0x26, 0xFF, 0x00,  /*   Logical Maximum (255) */
0x75, 0x08,        /*   Report Size (8) */
0x95, 0x3F,        /*   Report Count (63) */
0x09, 0x01,        /*   Usage (1) */
0x81, 0x02,        /*   Input (Data, Variable, Absolute) */
0x95, 0x3F,        /*   Report Count (63) */
0x09, 0x02,        /*   Usage (2) */
0x91, 0x02,        /*   Output (Data, Variable, Absolute) */
0xC0               /* End Collection */
```

目标复合 Report Map 为当前 70 字节 Report ID 1 Keyboard Collection 加上述 29 字节 Report ID 6 Vendor Collection，总计 **99 字节**。

MVP 应逐字节复用该片段。首次互操作验证不改写 Usage、不补 Feature Report，也不加入未实现的 Consumer、Mouse 或 Game Pad Collection。还应保留一个 Vendor-only 29 字节实验变体，用于判断失败来自 JL 平台差异还是复合 Report Map。

## 5. GATT 句柄布局

| 句柄 | 属性 | Report Reference |
|---|---|---|
| `0x0016-0x0025` | 现有 HID 属性 | ID 1 Input/Output |
| `0x0026` | Codex Input Characteristic Declaration | |
| `0x0027` | Codex Input Report Value，Read + Notify，63 字节 | |
| `0x0028` | Codex Input CCC | |
| `0x0029` | Codex Input Report Reference | ID 6, Type 1 |
| `0x002a` | Codex Output Characteristic Declaration | |
| `0x002b` | Codex Output Report Value，Read + Write + Write Without Response，63 字节 | |
| `0x002c` | Codex Output Report Reference | ID 6, Type 2 |
| `0x002d-0x0031` | 后移后的 Device Information Service | |

实施约束：

1. `HID_SERVICE_END_HANDLE` 更新到 `0x002c`；
2. 新 Value 与 CCC 沿用现有动态 HID 属性的加密边界；
3. Keyboard CCC 与 Codex CCC 独立维护；
4. 固件 ATT 回调只处理 63 字节 Report Body，不自行添加 Report ID；
5. Report Reference 负责把 OS HID API 的 Report ID 6 路由到对应 Characteristic；
6. 修改 GATT 数据库后必须删除旧 bond，不能把旧缓存复测当作有效结果。

63 字节 Characteristic Value 需要 ATT MTU 至少为 66。参考项目依赖 Arduino-ESP32 栈完成该路径且没有显式 MTU 检查；T2620 仍应记录 MTU Exchange、最终 payload、Notify 返回值和 Output 实际长度。MTU 是工程门槛，不是已证明的桌面端身份过滤条件。Write Without Response 在 MTU 不足时可能根本到不了 ATT callback，不能依赖固件“返回长度错误”；应由 Windows Host 工具的 write 结果、设备日志和 round trip 共同判定。

## 6. 传输与流式解码

Input 和 Output 的 ATT Value 固定为 63 字节：

```text
byte 0      0x02，数据消息类型
byte 1      N，本片有效数据长度，0..61
byte 2..    N 字节 UTF-8 JSON 分片
其余字节    0 填充到 63 字节
```

Windows HID class API 通常以 64 字节 host buffer 表示该报告：`[0x06][0x02][N][data...][padding]`。其中 `0x06` 是 Report ID；常规 HOGP ATT callback 应只看到后续 63 字节。MVP 必须用 Windows 实际枚举出的 `InputReportByteLength` / `OutputReportByteLength` 和一次 round trip 验证该边界，不能直接照搬 macOS 的 HIDAPI 观察。

参考实现发送紧凑 JSON 后追加单个 LF，再按 61 字节切片。其接收端不依赖 CRLF，而是在每次追加后尝试 JSON 解析，输入不完整则继续等待。

T2620 解码器应：

1. 接受 LF，并容忍 CRLF；
2. 不把换行作为唯一完成条件；
3. 用有界顶层 JSON 扫描或能区分“输入不完整”的解析器处理字符串、转义和嵌套；
4. 完整重组后再做 UTF-8/JSON 解析；
5. 将 RX 状态绑定到 link slot + generation；
6. 对 opcode 错误、`N > 61`、短写、溢出、断连和 owner 释放执行 fail-closed 清理；
7. 设置固定上限，建议 `RDX_CODEX_RX_MAX = 1024`，禁止无界拼接或 BLE 回调内无界分配。

TX 使用 worker/FIFO，不在 BLE 回调中固定延迟：一条逻辑消息的分片保持连续；`APP_BLE_BUFF_FULL` 时异步重试；每次发送核对 owner generation；断连后清理旧任务。现有 `ATT_EVENT_CAN_SEND_NOW` 主要服务 RDX owner，实施时必须显式接通 Codex TX 唤醒路径，并用强制 buffer-full 场景证明多分片不会静默丢失或交错。

Codex ready 条件独立定义为：

```text
connected && encrypted && codex_input_ccc_enabled
&& effective_att_payload >= 63 && !suspended
```

不要改变 `rdx_hogp_keyboard_is_ready()` 的现有语义。

## 7. JSON/RPC 最小协议

### 7.1 字段与方法

主路径使用完整字段：

```json
{"method":"device.status","id":1}
```

紧凑别名 `m/p` 只有取得独立抓包证据后才作为兼容扩展。

| 方向 | Method | 最小行为 |
|---|---|---|
| Device -> Host | `v.oai.hid` | Agent/Action/Encoder 事件 |
| Device -> Host | `v.oai.rad` | 有方向控件时发送；MVP 可不发送 |
| Host -> Device | `sys.version` | 返回固件版本 |
| Host -> Device | `device.status` | 返回版本、profile、layer、电池、充电状态 |
| Host -> Device | `v.oai.thstatus` | 解析任务灯状态 |
| Host -> Device | `v.oai.rgbcfg` | 解析环境灯和按键灯配置 |
| Host -> Device | `lights.preview` | 返回成功，MVP 不驱动物理灯 |
| Host -> Device | `host.focused_app` | 返回成功，MVP 不实现本地应用行为 |

未知方法返回：

```json
{"id":1,"error":{"code":-32601,"message":"Method not found"}}
```

`sys.bootloader`、`fs.*`、`mp.*`、`ui.*`、`wlsdk.*` 不进入 allowlist，也不得转交 RDX 或系统命令入口。

### 7.2 状态响应

参考实现使用 `profile_index = 0`、`layer_index = 1`：

```json
{"id":1,"result":{"version":"t2620-mvp","profile_index":0,"layer_index":1,"battery":87,"is_charging":false}}
```

`id` 原样回传；`battery` 限制为 `0..100`；`is_charging` 是 JSON boolean；版本使用 T2620 自身值。首次互操作按参考 profile/layer 值返回，确认语义后再映射产品状态。

### 7.3 输入事件

```json
{"method":"v.oai.hid","params":{"k":"AG00","act":1,"ag":0}}
{"method":"v.oai.hid","params":{"k":"AG00","act":0,"ag":0}}
```

| 类别 | 值 |
|---|---|
| Agent Keys | `AG00..AG05` |
| Command Keys | `ACT06..ACT10`、`ACT12` |
| 旋钮 | `ENC_CC`、`ENC_CW`、`ENC` |
| 普通按下 / 释放 | `act = 1` / `act = 0` |
| 旋钮步进 | `act = 2`，无 release |
| 方向 | `v.oai.rad`，`params.a` 为归一化角度，`params.d` 为 1.0/0.0 |

T2620 MVP 只映射一个物理键到 `AG00`，并抑制该键的 ID 1 扫描码。

### 7.4 灯效

```json
{"method":"v.oai.thstatus","params":[{"id":0,"c":3166206,"b":1.0,"e":"breath","s":1.0}],"id":2}
```

`id` 是 `0..5`；`c` 是 24 位 RGB；`b/s` 是浮点数；`e` 是如 `off`、`breath` 的字符串。`v.oai.rgbcfg` 的 `ambient` 和 `keys` 使用相同 `c/b/e/s` 结构。旧方案中的整数效果枚举、`sk`、`sa` 不属于本开源基线。

请求带 `id` 时返回 `{"id":...,"result":{"ok":true}}`；无 `id` 时按 notification 处理，不响应。

## 8. 标准键盘、双连接与生命周期

参考项目是 Vendor-only 控制器，不是通用键盘；复合路由属于 T2620 新设计。

产品化建议保留 Standard Keyboard、Codex、Split 三种显式模式。不能用 Codex CCC 自动切换模式，因为操作系统可能自动订阅 HID Input。切换时先释放旧路径 held key、取消 timer、清状态，再原子切换；首次升级默认 Standard Keyboard。MVP 只用实验编译开关重定向一个键，不做完整运行时模式系统。

Codex 继续复用 HID owner：

1. 同一 owner 可分别启用 Keyboard 与 Codex CCC；
2. 第二条 link 不得绕过 owner 订阅或写入 Codex Report；
3. RX、TX、request context 绑定 link slot + generation；
4. 断连只清理对应 generation；
5. 量产前将 peer-scoped CCC 扩展为 flags：bit 0 keyboard，bit 1 Codex；旧 schema 只迁移 bit 0。

MVP 固定一个 HID owner 和一台新鲜配对主机，不实现双连接并发功能；但必须验证第二 link/non-owner 不能订阅、写入或污染 ID 6 状态。实现不能使用无法归属的全局 RX buffer。

## 9. 身份与合规

参考项目共同使用名称 `Codex Micro`、Manufacturer `Work Louder`、PnP Source/VID/PID/Version `0x02:0x303A:0x8360:0x0101`、Generic HID Appearance、HID Service、Vendor Usage、Scan Response 和 preferred connection parameter 字段。它没有证明其中任何一项可省略。

JL ATT 表按 BLE PnP Characteristic 的 little-endian 字节序直接编码。参考身份的预期原始值为 `02 3A 30 60 83 01 01`；不要移植 Arduino-ESP32 为其自身序列化问题使用的 `swapBytes()`。Windows Host 工具同时断言逻辑 VID/PID/Version，实验记录保存原始 ADV、Scan Response 和 DIS 字节。

实验应先复现整组身份，再一次只恢复一个产品字段，并在每轮删除 bond、记录 App Build Number 和完整 HID/GATT 枚举。最终若合法产品身份无法被发现，应停止官方桌面端直连产品化，不能把第三方 VID/PID 固化到量产固件。

名称、Manufacturer、VID/PID 和品牌归各自权利人所有。MIT License 不授予第三方标识使用权。实验身份必须由专用编译开关隔离，不能进入量产、对外测试包或发布物。

## 10. 实现落点与资源门槛

新增 `rdx_codex_micro.c/.h`，职责仅包括有界 RX 重组、RPC allowlist、状态响应和 TX 分片。ATT callback 只校验、复制和投递，不在 Bluetooth task 中执行 cJSON 递归解析或灯效业务。

构建与配置要求：

1. 将 `rdx_codex_micro.c` 加入 `SDK/Makefile` 的显式 RDX 源文件列表；
2. 在 `t2620_project_config.h` 定义默认关闭的 `TCFG_RDX_CODEX_MICRO_MVP_ENABLE`，不修改生成的 `sdk_config.h/c`；
3. 开关关闭时 Report Map、ATT 表、句柄、PnP ID、名称和运行时行为必须逐字节保持现状；
4. 实验身份使用独立二级开关，并对发布镜像扫描 `0x303A:0x8360`、`Work Louder` 和 `Codex Micro`，防止进入量产包；
5. 若复制开源描述符或代码，保留其 MIT 版权与许可证信息；这不授予第三方商标或身份权利。

实施前记录基线，并在编码前冻结数值门槛。MVP 初始门槛建议为：Flash 增量不超过 32 KiB、BSS 增量不超过 4 KiB、连接态最小空闲堆不少于 12 KiB 且相对基线下降不超过 8 KiB、`app_core` 栈剩余不少于 1 KiB、Bluetooth task 栈剩余不少于 512 B、ATT callback 单次不超过 1 ms 且零动态分配。若平台 watermark 单位不是字节，记录时统一换算。RX 每 link 上限 1024 字节；TX 队列不超过 4 条消息和 2 KiB。cJSON 使用固定最大消息、方法白名单和深度门槛，禁止接受默认高递归上限作为产品边界。

## 11. Windows 分阶段实施

### Gate W0：Windows 产品资格验证

- 固定 Windows 11 版本、ChatGPT Windows App 版本/Build、账号/工作区、Bluetooth Adapter 和驱动版本；
- 优先用官方 Codex Micro；若不可得，再使用不改动的 `codex-micro-4-core2` 参考固件作为次级证据；
- 通过 Bluetooth 配对后确认 Windows 设备管理器出现 HIDClass 集合，并记录 `Get-PnpDevice` / `pnputil` 枚举；
- 启动 ChatGPT，确认首次出现 Codex Micro 设置入口并产生 Report ID 6 Output；
- 失败时保留 Windows PnP 属性、Report Descriptor、App Build 和设备侧写入日志。

Gate W0 失败时，不得把结果归因于 T2620 固件，也不继续做桌面端兼容承诺。可以继续自有 Windows Host 工具的 Report ID 6 round trip，但它只证明协议层。

### Phase 0：T2620 参考等价验证

- 使用 Vendor-only 29 字节 Report Map，并在实验 ATT 表中只暴露 ID 6 Report Characteristic；若仍保留 ID 1 Characteristic，就不能把该变体称为参考等价；
- 使用完整字段、LF framing、参考方法集和受控实验身份；
- 在首次多片 `device.status` 前完成有限 TX FIFO、可发送事件唤醒、buffer-full 重试和 generation 校验；
- 在 Gate W0 的同一 Windows 环境完成发现、`device.status`、AG00 down/up；
- 记录 Windows Build、App Build、Adapter/driver、MTU、CCC、GATT 和 HID 枚举。

若失败，先解决平台、身份或传输差异，不进入复合设备判断。

### Phase 1：目标复合设备

- 切换到 99 字节 Keyboard + Vendor Report Map；
- 添加 ID 6 独立 Input/CCC/Output/Reference；
- 保持 ID 1 句柄和语义；
- 新鲜配对并重复 Phase 0。

完成标准：ChatGPT 仍能发现，AG00 无普通键盘副作用，标准键盘和 LED Output 无回归。

### Phase 2：Windows 产品化加固

- 有界流式 JSON、非阻塞 FIFO、buffer-full 重试和 generation 隔离；
- Standard/Codex/Split 路由；
- 双连接、peer-scoped CCC、GATT 缓存迁移；

## 12. Windows 测试与完成定义

新增 `tests/host/test_codex_micro_contract.ps1`，至少冻结：

- 29 字节参考描述符和 99 字节复合 Report Map；
- ID 6 Input/Output Reference 与独立 CCC；
- ATT Value 固定 63 字节且固件不添加 Report ID；

- 危险方法不在 allowlist；

流式解码覆盖单片、多片、LF/CRLF、无换行完整 JSON、UTF-8 跨片、字符串转义、短帧、`N > 61`、溢出、两 link 交错、wrong-owner、未加密写和断连复用。TX 必须注入 buffer-full 并验证 generation token、重试和整条消息不交错。

Windows 主机侧至少提供一个小型 HID 测试工具，完成：

- 使用 SetupDi 枚举 HID interface，`HidD_GetPreparsedData` + `HidP_GetCaps` 读取 VID/PID/Usage 和报告长度；

- 以 `WriteFile` 作为 ID 6 Output 主路径，并单独记录 `HidD_SetOutputReport` 控制路径结果；禁止静默 fallback；
- 接收、重组并在 2 秒内断言 `device.status`；
- 记录每片时间、长度和原始十六进制，但不记录隐私数据。

PowerShell 的 `Get-PnpDevice -Class HIDClass` 和 `pnputil /enum-devices /class HIDClass /properties` 只用于确认枚举；它们不能替代 Report ID 6 round trip。
