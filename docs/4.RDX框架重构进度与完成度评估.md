# RDX 框架重构进度与完成度评估

> 日期：2026-07-12  
> 基线提交：`4d545ad 重构：收口 P5 record/ota timer 直连调用`  
> 评估范围：`SDK/apps/common/third_party_profile/rdx_protocol` 当前源码、`docs/1-3` 架构目标、`docs/13` P5 实施文档，以及本地静态边界检查结果。
> 文档定位：本文档取代旧版 `docs/9.RDX框架重构真实达成度评估.md` 的进度口径，按 P5 完成后的代码状态重新评估。

## 1. 总体结论

当前 RDX 框架重构已经从“骨架搭建 + 局部迁移”推进到 **P0-P5 静态边界收口完成** 的状态。

按最终目标“形成可长期维护的中间件边界”衡量，当前仍不能算完成；按“核心架构骨架、主要边界和静态防退化规则是否建立”衡量，当前已经有实质进展。综合判断，当前真实完成度建议按 **75% 左右** 对内管理：

- 比 `docs/9` 中 P0-P4 后的 68% 有明显提升，因为 P5 已完成 `rdx_record.c` / `rdx_ota.c` 的 timer 直连收口。
- 不能上调到 80% 以上，因为产品配置拆分、旧 BLE server 跨层调用、周期 timer 补漏和编译/目标板验证闭环仍未完成。

一句话状态：

> 新架构骨架已稳定，P0-P5 静态边界已收口；剩余工作从“继续建抽象”转为“清旧债 + 补验证”。

|---|---|---|

## 3. 已经真实落地的架构能力

### 3.1 service 容器和命令分发已落地

当前 `service/` 下已有：

- `rdx_command_dispatch.c`
- `rdx_device_service.c`
- `rdx_record_service.c`
- `rdx_storage_service.c`
- `rdx_info_service.c`
- `rdx_time_service.c`
- `rdx_clock_service.c`
- `rdx_wifi_service.c`
- `rdx_ble_service.c`
- `rdx_event_bus.c`
- `rdx_default_hooks.c`

`rdx_app.c` 中已经没有 `rdx_cmd_register()`；27 个协议 handler 由 service 注册：

- device service：10 个
- record service：7 个
- info service：6 个
- storage service：3 个
- time service：1 个

这说明命令注册中心已经从 `rdx_app.c` 迁出，`rdx_app.c` 不再承担协议命令注册职责。

### 3.2 port / OSAL / board 边界已成型

当前源码已有：

- `board/common`、`board/t2616_cc`、`board/t2616_ep`
- `port/jl/jl7018`、`port/jl/jl7018_shadow`
- OSAL timer、task callback、task msg array、periodic timer、task-attached timer wrapper
- WiFi transport vtable
- LED / Motor / DUT / Diag weak hooks

P5 后新增并落地的 OSAL API：

- `rdx_os_timer_periodic_add()`
- `rdx_os_timer_periodic_del()`
- `rdx_os_timer_add_to_task()`

`rdx_record.c` 的周期保活 timer 已走 periodic wrapper；`rdx_ota.c` 的 `sys_timeout_add_2_task()` 已通过 `rdx_os_timer_add_to_task()` 收口。

### 3.3 静态边界检查已覆盖 P0-P5

当前执行：

```powershell
pwsh -ExecutionPolicy Bypass -File tools/check_rdx_boundaries.ps1
```

结果：**24/24 PASS**。

新增 P5 检查项已经覆盖：

- `rdx_record.c` / `rdx_ota.c` 不得直接调用 `sys_timeout_add/del`
- `rdx_record.c` / `rdx_ota.c` 不得直接调用 `sys_timer_add/del/re_run`
- `rdx_record.c` / `rdx_ota.c` 不得直接调用 `sys_timeout_add_2_task`

这意味着 P5 的静态收口已有防退化规则，不再只依赖人工 review。

## 4. 当前未完成内容

### 4.1 产品配置拆分未落地

当前源码中未见 `rdx_protocol/config/` 三层目录，产品配置仍主要集中在：

- `rdx_app_config.h`

历史评估中曾记录过 `config/product`、`config/board`、`config/build` 为空目录；按当前工作区实际源码复核，这些目录已经不存在。因此本节以当前源码状态为准，判定为产品配置拆分未落地。

因此，“新增客户产品时主要修改 `config/product/*.h`，不需要在业务 `.c` 中增加 `#ifdef`”这一目标尚未达成。

### 4.2 旧 BLE server 仍存在跨层调用

`rdx_ble_service.c` 的 stop/cleanup 路径已经收口，但旧 `rdx_ble_server.c` 仍直接访问 record/protocol 状态：

- `rdx_record_get_status()`
- `RecordStatus`
- `rdx_protocol_record_state_indicate()`

这说明 BLE 边界只完成了新 service 局部路径，旧 server 全局边界仍未完成。

### 4.3 业务层周期 timer 仍有补漏项

P5 清掉了 `rdx_record.c` / `rdx_ota.c`，但全业务层仍有 4 个文件存在周期 timer 直连：

| 文件 | 剩余直连 |
|---|---|
| `rdx_charge.c` | `sys_timer_add/del` |
| `rdx_dut.c` | `sys_timer_add/del` |
| `rdx_led_ctrl.c` | `sys_timer_add/del` |
| `rdx_rtc.c` | `sys_timer_add/del` |

这些不属于 P5 范围，但会影响“业务层 timer 全清零”的最终口径。建议作为 P6 处理。

### 4.4 `rdx_app.c` 仍未退化为薄协调器

当前 `rdx_app.c` 为 **2184 行**。相比早期大文件已经下降明显，但仍未达到历史目标中的 `<= 2000` 行；同时函数数量仍偏多。

阶段 4/5 文档允许 ABI wrapper、生命周期协调器和产品入口保留在 `rdx_app.c`，因此行数不应作为唯一门禁。但它仍说明 `rdx_app.c` 尚未完全退化为薄协调器。

### 4.5 验证闭环未完成

当前只能确认静态边界检查通过；由于不在生产编译环境，本轮未做：

- 三组合 clean build
- `.map` 体积对比
- 目标板烧录
- BLE 录音 / OTA / WiFi / 断连重连 / 关机恢复等冒烟测试

因此当前状态不能按“最终验收完成”对外宣称。

## 5. 完成度重判

本节目标口径来自 `docs/3.RDX框架JL平台复用性优化大纲.md` 的整体成功标准，并结合当前源码状态重判；其中“最终可维护边界”是对 JL API 集中化、产品配置化、板级隔离、静态库边界、风险边界和可验证性几项目标的综合判断。

| 目标 | 当前状态 | 判定 |
|---|---|---|
| JL API 集中化 | service 层和 P5 范围已清零；仍有 4 个业务文件周期 timer 补漏 | 基本达成 |
| 板级差异隔离 | P0/P1 静态规则已通过，board config / HAL 已接管关键旧宏和 SPI | 基本达成 |
| service 化 | 命令注册已迁出 `rdx_app.c`，主要 service 容器存在 | 基本达成 |
| BLE 边界 | 新 `rdx_ble_service.c` 已局部收口，旧 `rdx_ble_server.c` 仍跨层 | 部分达成 |
| 产品配置化 | `config/` 三层拆分未落地 | 未达成 |
| 可验证性 | 静态边界 24/24 PASS；缺编译、map、目标板冒烟 | 部分达成 |
| 最终可维护边界 | 仍有旧代码和产品配置债务 | 未完成 |

### 5.1 距离 Doc 3 最终目标的实际差距

当前 `tools/check_rdx_boundaries.ps1` 的 24/24 PASS 代表 P0-P5 已定义边界没有退化，但它不能等同于 Doc 3 第 8 节的最终成功标准。按 Doc 3 的严格口径，仍需补齐以下差距：

| 差距 | 当前事实 | 影响 |
|---|---|---|
| JL API 全业务集中化尚未完成 | 严格扫描业务 `.c`，仍有 `rdx_app.c`、`rdx_battery.c`、`rdx_ble_server.c`、`rdx_charge.c`、`rdx_dut.c`、`rdx_key.c`、`rdx_led_ctrl.c`、`rdx_ota.c`、`rdx_record.c`、`rdx_rtc.c`、`rdx_spi.c`、`rdx_vm.c` 命中 `os_` / `gpio_` / `spi_` / `syscfg_` / `sys_timer_` 等直接调用或 include | 不能按“业务 `.c` 不再直接调用 JL SDK API”验收 |
| 产品配置化基本未启动 | 当前源码未见 `config/product`，产品配置仍集中在 `rdx_app_config.h` | 不能满足“新增客户产品主要改 config，不改业务 `.c`” |
| 旧 BLE server 全局边界未完成 | `rdx_ble_server.c` 仍直接访问 `RecordStatus`、`rdx_record_get_status()`、`rdx_protocol_record_state_indicate()` | BLE 边界只能算局部 service 收口，不能算全局完成 |
| P5 外周期 timer 仍需补漏 | `rdx_charge.c`、`rdx_dut.c`、`rdx_led_ctrl.c`、`rdx_rtc.c` 仍各有 `sys_timer_add/del` | 业务层 timer 还不能宣称全清零 |
| 验证闭环缺失 | 当前未完成 clean build、`.map` 对比、目标板冒烟 | 不能按最终验收完成态对外宣称 |

因此，当前状态可以称为 **P5 后静态收口完成态**，但距离 Doc 3 的最终目标仍有 P6-P9 四类收尾工作。

建议当前完成度口径：

- **静态边界重构完成度：约 80%**  
  P0-P5 已有规则和脚本防退化。
- **整体框架重构完成度：约 75%**  
  仍缺产品配置、旧 BLE server、周期 timer 补漏和验证闭环。
- **最终验收完成度：不能按完成宣称**  
  缺 clean build 和目标板冒烟。

## 6. 建议下一步

### P6：周期 timer 补漏

范围：

- `rdx_charge.c`
- `rdx_dut.c`
- `rdx_led_ctrl.c`
- `rdx_rtc.c`

目标：

- 将剩余 `sys_timer_add/del` 替换为 `rdx_os_timer_periodic_add/del`
- 增加全业务层周期 timer 边界规则：扫描 `rdx_protocol/**/*.c`，排除 `port/`、`service/` 等已封装层后，`sys_timer_add/del` 命中数应为 0

### P7：旧 BLE server 跨层调用收口

范围：

- `rdx_ble_server.c`

目标：

- 为 record/protocol 状态访问建立 service API
- 避免旧 BLE server 直接访问 `RecordStatus` 和 protocol indicate

### P8：产品配置拆分

范围：

- 新建 `config/product`
- 新建 `config/board`

目标：

- 新增客户产品主要改 config，不再扩散业务 `#ifdef`

### P9：验证闭环

范围：

- clean build
- `.map` 对比
- 目标板冒烟
- BLE / WiFi / record / OTA / power lifecycle 回归

目标：

- 形成可复现验收证据，再判断是否可以对外宣称框架重构完成。

## 7. 最终判断

当前 RDX 框架重构已经越过“只建目录和抽象”的阶段，P0-P5 已经通过代码迁移和静态规则形成可检查边界。尤其 P5 完成后，最复杂的 `rdx_record.c` / `rdx_ota.c` timer 直连已经静态清零，这是一个实质进展。

但剩余债务仍集中在最终完成所必需的几个方面：产品配置未拆、旧 BLE server 未全局收口、全业务层周期 timer 未清零、编译和目标板验证缺失。因此当前状态应定义为：

> **重构主体已完成约 75%，静态边界进入后半程收口；尚未达到最终验收完成态。**
