> 日期：2026-07-14

## 1. 总体结论

当前 RDX 重构已经完成了主要架构骨架和 P0-P6 静态边界收口，但尚未达到 `docs/3` 第 8 节定义的最终成功标准。

建议当前采用两套口径：

| 口径 | 建议结论 | 说明 |
|---|---|---|
| 架构/静态边界重构完成度 | 约 78% | service、board、port、OSAL、dispatch、event bus、P6 timer 收口和静态边界脚本已落地。 |
| `docs/3` 最终验收完成度 | 不按完成宣称 | 产品配置化、旧 BLE server 全局收口、目标板 timer 行为验证、clean build/map/目标板冒烟仍缺。 |
| 后续执行主线 | P7-P9 | P6 已完成静态收口；后续转向旧 BLE server、产品配置和验证闭环。 |

一句话状态：

> 新架构骨架已经成型，P0-P6 静态边界已有防退化规则；后续重点是 P7-P9 的剩余边界债务和验证闭环。

## 5. 当前未完成内容

### 5.1 产品配置拆分未落地

当前源码未见：

- `rdx_protocol/config/product`
- `rdx_protocol/config/board`
- `rdx_protocol/config/build`

产品差异仍主要集中在 `rdx_app_config.h`。因此 `docs/3` 的“新增客户产品时主要修改 `config/product/*.h`，不需要在业务 `.c` 中增加 `#ifdef`”尚未达成。

### 5.2 旧 BLE server 仍存在跨层调用

`rdx_ble_service.c` 的 stop/cleanup 路径已经局部收口，但旧 `rdx_ble_server.c` 仍直接访问 record/protocol 状态，包括：

- `rdx_record_get_status()`
- `RecordStatus`
- `rdx_protocol_record_state_indicate()`

这说明 BLE 边界只能算 service 局部收口，不能算全局完成。

### 5.3 P6 已静态完成，但缺目标板验证

P6 已将以下 4 个文件的周期 timer 直连替换为 OSAL wrapper：

| 文件 | P6 后状态 |
|---|---|
| `rdx_charge.c` | `sys_timer_add/del` 已替换为 `rdx_os_timer_periodic_add/del` |
| `rdx_dut.c` | `sys_timer_add/del/modify` 已替换为 `rdx_os_timer_periodic_add/del/modify` |
| `rdx_led_ctrl.c` | `sys_timer_add/del` 已替换为 `rdx_os_timer_periodic_add/del` |
| `rdx_rtc.c` | `sys_timer_add/del` 已替换为 `rdx_os_timer_periodic_add/del` |

当前 `sys_timer_*` / `sys_timeout_*` 只允许出现在 `port/jl/*/rdx_jl_osal.c` wrapper 层。仍需目标板验证充电满电检查、DUT 马达节奏、LED 刷新和 RTC restore 行为是否保持一致。

### 5.4 `rdx_app.c` 尚未退化为薄协调器

当前 `rdx_app.c` 为 2184 行，已明显低于早期大文件，但仍高于历史目标 `<= 2000`。考虑到 ABI wrapper、生命周期协调器和产品入口仍需保留，行数不应作为唯一门禁；但它仍说明 `rdx_app.c` 还不是薄协调器。

### 5.5 JL API 全业务集中化尚未完成

按 `docs/3` 第 8 节严格口径，业务 `.c` 文件不应直接调用 `os_`、`gpio_`、`spi_`、`syscfg_` 等 JL SDK API。P6 后 timer/timeout 已清零；当前根目录业务 `.c` 仍有以下文件命中其他直接依赖或 include：

- `rdx_app.c`
- `rdx_battery.c`
- `rdx_ble_server.c`
- `rdx_charge.c`
- `rdx_dut.c`
- `rdx_key.c`
- `rdx_ota.c`
- `rdx_record.c`
- `rdx_rtc.c`
- `rdx_spi.c`
- `rdx_vm.c`

其中部分命中属于历史兼容层或 transport 层遗留，不能简单一次性清零；后续需要按风险和归属拆分。

### 5.6 验证闭环未完成

当前只能确认静态边界脚本通过。以下最终验收证据仍缺：

- 三组合 clean build
- `.map` 体积对比
- 目标板烧录
- BLE 录音 / WiFi 在线录音 / OTA / 断连重连 / 关机恢复 / 恢复出厂冒烟
- host mock 在 macOS/64 位环境稳定通过

## 7. 后续重构任务建议

### P6：全业务周期 timer 补漏（已实现，待目标板验证）

范围：

- `rdx_charge.c`
- `rdx_dut.c`
- `rdx_led_ctrl.c`
- `rdx_rtc.c`

已完成：

- 将 `sys_timer_add/del/modify` 迁移到 OSAL periodic timer wrapper。
- 新增 `rdx_os_timer_periodic_modify()`，封装 `sys_timer_modify()`。
- 增加 P6 边界规则：`rdx_charge.c`、`rdx_dut.c`、`rdx_led_ctrl.c`、`rdx_rtc.c` 不得直接调用 `sys_timer_add/del/modify`。
- 修复两个 timer callback 签名隐患：保留原 ABI 函数签名，新增 `void (*)(void *)` 静态适配 callback。

验收：

- [x] 4 个文件不再直接调用 `sys_timer_add/del/modify`。
- [x] `tools/check_rdx_boundaries.ps1` 新增 P6 检查项并通过。
- [ ] 目标板确认 timer 相关原行为保持不变：充电满电检查、DUT 马达、LED 刷新、RTC restore。

风险：

- `rdx_dut.c` 的变周期马达测试依赖 `rdx_os_timer_periodic_modify()`，后续新增 port 时必须同步实现该 wrapper。
- LED/RTC timer 可能与低功耗路径有关，需做目标板冒烟。

### P7：旧 BLE server 跨层调用收口

范围：

- `rdx_ble_server.c`

目标：

- 旧 BLE server 不再直接访问 `RecordStatus`。
- 旧 BLE server 不再直接调用 `rdx_record_get_status()` 和 `rdx_protocol_record_state_indicate()`。
- 通过 record service / protocol facade / event bus 暴露最小必要接口。

验收：

- [ ] `rdx_ble_server.c` 中 `RecordStatus` 命中为 0，除非仅保留在兼容声明并有注释说明。
- [ ] `rdx_ble_server.c` 中 `rdx_record_get_status()` 命中为 0。
- [ ] `rdx_ble_server.c` 中 `rdx_protocol_record_state_indicate()` 命中为 0。
- [ ] BLE connect/disconnect、强制停止录音、断连清理行为通过目标板冒烟。

风险：

- 旧 BLE server 可能承担协议状态和 record 状态双重职责，直接替换为 event bus 可能改变时序。
- 建议先提供 thin service API，再逐步内部 event 化。

## 10. 最终判断

当前 RDX 框架已经越过“只建目录和抽象”的阶段，核心架构骨架、主要边界和 P0-P6 静态防退化规则已经建立。

但按最终可维护框架的标准，仍有四类必须补齐的工作：

1. P7：旧 BLE server 跨层调用收口。
2. P8：产品配置拆分。
