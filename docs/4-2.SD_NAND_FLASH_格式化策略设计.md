# SD NAND FLASH 格式化策略设计

> 本文档描述 T2620 当前固件的实际实现，不是独立于代码的理想方案。
> 主要依据：`SDK/apps/common/dev_manager/dev_manager.c`、
> `SDK/apps/earphone/mode/pc/pc.c`、
> `SDK/apps/earphone/include/t2620_project_config.h`、
> `SDK/apps/earphone/board/br28/board_ac701n_demo_cfg.h`，以及 RDX 的
> `rdx_uxfile.h` 接口和 `librdxApp.a`。
>
> **问题闭环状态（2026-08-19）**：新出厂机器 FAT 可挂载但没有
> `UXFILE.DAT`，原始 RDX 库在启动重建阶段卡入 `fscan()`，导致录音不可用。
> 当前补丁已通过“空索引初始化 -> 首次录音生成 DAT -> 关机重启加载 DAT ->
> App 读取列表”的实机闭环验证。

## 1. 适用范围与结论

T2620 使用板载 SD NAND 作为 `sd0`，由设备管理器挂载为 FAT 文件系统，根目录为：

```text
storage/sd0/C/
```

当前产品的策略有三条彼此独立的路径：

1. **开机自动恢复格式化**：`sd0` 首次挂载失败时执行。首次初始化和已有文件系统损坏都会格式化。
2. **USB MSC PC 存储**：PC 模式接管 `sd0` 的所有权，只卸载和恢复挂载，不主动格式化。
3. **RDX 运行时主动格式化**：由 UXFILE worker 异步执行，供 RDX 协议、解绑、DUT 等业务使用。

因此，VM 标志不是“是否允许格式化”的总开关，也不是所有格式化操作共用的状态位；它只服务于开机自动恢复路径的诊断和成功记录。

## 3. 设备注册与开机时序

### 3.1 SD0 注册

`dev_reg.c` 将 `sd0` 注册为：

```text
logo          = "sd0"
device name   = "sd0"
storage path  = "storage/sd0"
root path     = "storage/sd0/C/"
fs type       = "fat"
```

当 `TCFG_SD_ALWAY_ONLINE_ENABLE` 开启时，`dev_manager_task()` 在
`devices_init()` 后执行：

```c
force_set_sd_online("sd0");
dev_manager_add("sd0");
```

随后删除 SD 插拔检测定时器。这样 SD NAND 在 USB MSC 接管期间不会因为伪插拔事件被设备管理器重新挂载。

如果编译时启用了 `TCFG_RECORD_FOLDER_DEV_ENABLE`，`dev_manager_add("sd0")`
还会处理同一物理设备的 `sd0_rec` 逻辑目录设备；该逻辑设备与主 `sd0` 共用
`storage/sd0`，并不代表第二块存储介质。

### 3.2 一次性保护

开机自动格式化分支在 `__dev_manager_add()` 中由静态变量 `_sd0_fmt_done` 保护。
该变量在本次运行期间第一次处理 `sd0` 后即置 `1`，所以：

- 每次上电最多自动尝试一次格式化；
- 后续 `dev_manager_mount()` 或设备事件重新挂载不会再次走开机格式化分支；
- 重新上电后静态变量重新初始化，才会再次进行“首次挂载失败”判断。

这项保护不能替代 VM 标志。它只防止同一开机周期重复擦写 NAND。

## 4. 开机自动格式化流程

### 4.1 主流程

在 `__dev_manager_add(logo, need_mount)` 中，`sd0` 的实际顺序如下：

```text
申请设备节点
    |
mount("sd0", "storage/sd0", "fat", 3, NULL)
    |
    +-- 成功 --> 跳过自动格式化，登记 dev->fmnt/dev->valid
    |
    +-- 失败 --> 读取 CFG_SD0_FORMAT_DONE_FLAG
                    |
                    +-- VM == 0xA5 --> 按“文件系统损坏”处理
                    |
                    +-- 读取失败/值不是 0xA5 --> 按“首次初始化或 VM 被清除”处理
                    |
                  延时 50 tick
                    |
                  f_format("storage/sd0/C/", "fat", 0)
                    |
                    +-- 失败 --> 保持未挂载，不写 VM 完成标志
                    |
                    +-- 成功 --> 查询剩余空间并重新 mount
                                  |
                                  +-- remount 失败 --> SD0 仍不可用，不写 VM
                                  |
                                  +-- remount 成功 --> 写入 VM = 0xA5
```

挂载成功优先级高于 VM 标志：只要当前文件系统能正常挂载，就不会因为 VM 标志无效而格式化。

### 4.2 VM 标志的准确含义

VM 标志通过 `syscfg_read(CFG_SD0_FORMAT_DONE_FLAG, ...)` 读取，通过
`syscfg_write(...)` 写入。当前实现的语义是：

- `0xA5`：曾经完成过一次“格式化并重新挂载成功”；
- 不存在、读取长度不正确或值不是 `0xA5`：没有可验证的成功记录。

挂载失败时，两种 VM 状态都会执行格式化。差别仅体现在日志：

- 有效标志：`fs damaged, recover by format`；
- 无效标志：`first boot or vm cleared, format sd0`。

格式化成功但重新挂载失败，或者 VM 写入失败，都不会把这次操作当作完整成功。特别是 VM 写失败时，当前代码会保留已挂载的文件系统，但下一次开机若再次挂载失败，仍可能重复格式化。

### 4.3 格式化参数与返回值

调用为：

```c
f_format("storage/sd0/C/", "fat", 0);
```

`fs.h` 对接口的约定是：

- 设备路径 `sd0` 可格式化整个设备；当前代码使用的是 C 分区路径 `storage/sd0/C/`；
- `fs_type = "fat"`。当前调用没有显式请求 `fat32`；SDK 注释说明，对 C 分区路径，原文件系统为 FAT12/16/32 或 exFAT 时会格式化为对应的文件系统类型；
- `clust_size = 0`，使用设备默认簇大小；
- 返回值 `0` 表示成功，非 `0` 表示失败。

当前代码在格式化成功后调用 `fget_free_space()` 记录剩余空间，然后使用原设备注册参数重新挂载。`dev->valid` 在最终登记时由 `dev->fmnt != NULL` 决定。

### 4.4 失败后的可见状态

格式化失败或格式化后重新挂载失败时，`dev_manager_add()` 最终返回
`DEV_MANAGER_ADD_ERR_MOUNT_FAIL`，设备节点可能已进入链表但 `dev->fmnt == NULL`、
`dev->valid == 0`。上层必须把 SD0 视为不可用，不能仅依据“设备已注册”判断存储可访问。

## 5. USB MSC PC 模式与格式化的边界

### 5.1 产品约束

`TCFG_T2620_PC_STORAGE_ENABLE = 1` 时，overlay 校验并强制：

- 必须启用 SD0；
- 必须启用 USB MSC；
- `TCFG_APP_PC_EN = 1`；
- `TCFG_SD_ALWAY_ONLINE_ENABLE = 1`；
- 关闭 USB HID、USB 音频扬声器和 USB 音频麦克风；
- 其他 USB 类沿用 SDK 默认关闭值。

PC 模式导出的就是板载 `sd0`，不是独立的 U 盘设备。

### 5.2 接管前置条件

进入 PC 模式前，`pc_mode_try_enter()` 和 `pc_storage_prepare()` 会检查：

1. DIP 电源开关允许工作；
2. USB OTG 已处于从机在线状态；
3. RDX 存储活动为空闲。

`rdx_pc_storage_is_busy()` 会拒绝以下状态：录音未停止、录音 worker 忙、本地播放活动、文件传输或同步、DAT 扫描/列表加载、UXFILE 格式化、OTA、Wi-Fi 传输等。

### 5.3 所有权切换

`dev_manager_takeover("sd0")` 的顺序是：

1. 设置 `mount_blocked = 1`，阻止设备管理器自动重新挂载；
2. 卸载 `sd0`（启用录音目录设备时同步处理 `sd0_rec`）；
3. 成功后状态变为 `PC_STORAGE_HOST_OWNED`；
4. 只有 `PC_STORAGE_HOST_OWNED` 状态允许发送 `USBSTACK_START`。

因此 USB MSC 与固件 FAT 访问不会同时持有同一挂载点。`dev_manager_mount()` 和后台
`dev_manager_list_check_mount()` 都会尊重 `mount_blocked`。

退出 PC 模式时必须先发送 `USBSTACK_STOP`。USB 停止成功后调用
`dev_manager_restore("sd0")`，在仍被 blocked 的状态下先重新挂载，全部挂载成功后再解除 blocked。恢复失败时进入 `PC_STORAGE_RESTORE_FAILED`，SD0 保持 blocked，避免固件在未确认挂载成功时访问存储。

这条路径**不调用 `f_format()`**，也不修改 `CFG_SD0_FORMAT_DONE_FLAG`。用户可在 Windows 端对 MSC 盘重新格式化；下一次固件挂载成功后会直接跳过开机自动格式化流程。

## 6. RDX 运行时主动格式化

### 6.1 实现边界

RDX 的 UXFILE 实现来自：

```text
原始库：SDK/apps/common/third_party_profile/rdx_protocol/librdxApp.a
补丁库：SDK/apps/common/third_party_profile/rdx_protocol/librdxApp_patched.a
```

原始库并不是不可分析的加密机器码。它是 LLVM archive，成员为：

```text
rdx_encryption.c.o
rdx_protocol.c.o
rdx_queue.c.o
rdx_uxfile.c.o
xxpUart.c.o
```

其中 `rdx_uxfile.c.o` 的文件头为 `42 43 C0 DE`，属于 LLVM bitcode，保留了函数名、字符串和源码行调试信息。当前补丁只替换该成员，其他四个成员保持原样。原始库和补丁库的 SHA-256 分别为：

```text
librdxApp.a         4289EC0F6D923EC9337A5DBE57F8D720BCC4946601B7D8393F9E2878B16F5C7D
librdxApp_patched.a 271319DF37566E091C99E8A92563D91A04D4533E25159B03AA82AD23078FE570
```

`patch_librdxApp.ps1` 会先校验原始库哈希，再提取、反汇编、精确匹配补丁、回编译和校验 archive 成员/符号；它拒绝覆盖原始库。`SDK/Makefile` 当前链接补丁库。公开接口包括：

```c
int  rdx_uxfile_sd_format(uxfile_format_cb cb);
void rdx_uxfile_device_sd_format(uxfile_format_cb cb);
u8   rdx_uxfile_is_formatting(void);
```

回调结果常量定义为：`MEM_FORMAT_RESULT_OK = 0x01`，
`MEM_FORMAT_RESULT_FAIL = 0x10`。

### 6.2 当前主动格式化入口

| 入口 | 调用 | 格式化完成后的业务动作 |
| --- | --- | --- |
| RDX 普通格式化 | `rdx_app_format_handle()` -> `rdx_uxfile_sd_format(NULL)` | 本地播放列表先标记为 formatting；无回调业务处理 |
| RDX `PROTOCOL_EVENT_CMD_SD_FORMAT` | 空闲检查通过后调用 `rdx_uxfile_sd_format(NULL)` | 先发送接受 ACK；忙时发送失败 ACK |
| 解绑 | `rdx_vm_unbound_handle()` -> `rdx_uxfile_sd_format(rdx_vm_unbound_cb)` | 成功后清理绑定/名称/超时/录音参数并复位；失败回报失败 |
| 选择解绑并格式化 | `rdx_vm_choose_to_unbound_handle(..., format_en=1)` | 成功后清除绑定状态并复位；失败回报失败 |
| DUT 五击格式化 | `rdx_dut_format_start()` -> `rdx_uxfile_device_sd_format(rdx_dut_format_cb)` | 清除 DUT 当前功能并恢复 DUT 显示 |
| 出厂包装结束 | `rdx_dut_finalpack_end()` -> `rdx_uxfile_device_sd_format(...)` | 格式化回调后延时断开 BLE 并关机 |

### 6.3 主动格式化的保护

RDX 的存储忙判断会阻止 PC 接管和部分业务操作。协议 `SD_FORMAT` 入口额外拒绝：

- OTA 进行中；
- 录音处于 `START` 或 `RESUME`；
- 文件发送忙。

格式化期间，按键重映射会拒绝处理；长按录音、关机检查等路径也会查询格式化状态，避免在 UXFILE 正在操作 SD NAND 时继续使用或掉电。

这些保护属于 RDX 运行时路径，和 `TCFG_SD0_FORMAT_ON_BOOT` 的开机恢复分支是两套状态管理。RDX 主动格式化不会写入 `CFG_SD0_FORMAT_DONE_FLAG` 的 `0xA5`；该标志只在 `dev_manager.c` 的开机格式化成功且 remount 成功后写入。补丁库会把独立的 UXFILE 扫描标志（VM ID `159`）写为 `0xAA`，表示“格式化后已知为空盘，不需要下次启动再全盘重建 DAT”。

### 6.4 新机 `UXFILE.DAT` 异常的现场结论

异常现场输出不能证明 SD NAND 没有文件系统。相反，挂载结果已经明确表明 FAT 可用：

```text
[SD-FMT] sd0 mount ok, skip format on boot
```

真正的差异发生在 RDX 的业务索引层：

```text
[UPGRADE] DAT scan flag mismatch (vm_ret=-251, flag=0xFF, expect=0xAA), will rebuild
DAT file not found, init empty cache.
[SCAN] Start fscan: storage/sd0/C/
```

正常机器则为：

```text
[UPGRADE] DAT scan completed before (flag=0xAA), trust existing DAT
=== DAT cache loaded: 3 records ===
```

因此要区分三个层次：

1. SD NAND 块设备是否可读；
2. FAT 文件系统是否可挂载；
3. RDX 业务索引 `UXFILE.DAT` 是否已经建立，以及 VM ID `159` 是否记录了完成状态。

本次异常属于第 3 层的软件状态和并发缺陷，不是日志所能支持的 NAND 硬件故障，也不是“新 NAND 必须自带 `UXFILE.DAT`”。新出厂空盘没有该业务文件是正常初始状态；固件应把它当作空索引，并在第一次录音落盘时创建/保存，而不是要求产线手工复制一个空文件。

为避免后续讨论再次混淆，本文统一使用以下术语：

| 术语 | 判定 | 正确处理 |
| --- | --- | --- |
| 文件系统不可用 | SD NAND 块设备不可读，或 FAT 无法挂载 | 进入文件系统恢复/格式化路径 |
| 新机空索引 | FAT 可挂载，DAT 从未生成，也没有需要恢复的业务记录 | 初始化 0 条记录，不扫描整个 FAT；首次录音结束后生成 DAT |
| 索引丢失/损坏 | FAT 可挂载，DAT 无效，但盘上仍有 raw 录音 | 从 raw 文件恢复索引；这是数据恢复，不是新机初始化 |

因此，“DAT 不存在”本身不能直接表述为“DAT 丢失”。对新出厂机器，它通常表示
“业务索引尚未创建”；只有已经产生过 raw 录音后 DAT 再消失，才属于真正的索引丢失。

阶段性实机验证进一步确认，首次重建本身也不能作为新机启动的前置条件：

```text
[00:00:02.955][SCAN] Start fscan: storage/sd0/C/
[00:00:52.127][RDX_APP_RX] ASCII: *APP#record#1#0#1#
```

现场采集持续到约 92 秒仍没有 `fscan returned`、`Rebuild complete` 或扫描完成标志。旧补丁阻止了该次录音继续进入 `rdx_record_run_init()`，因而有避免 FAT 并发死锁的安全价值，但没有让新机完成初始化，功能结果仍不合格。问题由此收敛为：对“无 DAT + 空缓存”执行递归全盘 `fscan()` 的启动策略不成立。

“DAT 不存在就重建”只对盘上确实存在 raw 文件的恢复场景成立。新机空盘没有任何
记录可供重建，正确结果本来就是 0 条；将无超时的递归 `fscan()` 放在普通启动路径中，
既不能增加数据完整性，又会把底层扫描异常放大成整机不可录音。产线预置一个空 DAT
可以掩盖首次启动问题，但格式化、换盘或 DAT 损坏后仍会复发，所以不作为产品正确性的
前置条件。

### 6.5 原始库缺陷与补丁行为

对 `rdx_uxfile.c.o` 的 LLVM IR 分析确认了以下问题：

1. `rdx_uxfile_is_scan_active()` 原来是固定返回 `0` 的桩函数，即使 `g_sync_state` 正在 `RUNNING/PAUSING/PAUSED`，录音和 PC 存储保护也看不到扫描活动。
2. 成功扫描到 0 个录音文件时没有持久化 VM ID `159 = 0xAA`，空的新机可能在后续启动反复全盘扫描。
3. RDX 主动格式化成功后反而把 VM ID `159` 写成 `0`，人为制造了下一次启动的重建条件。
4. 扫描已处理记录但 `UXFILE.DAT` 保存失败时仍返回正的记录数，上层无法区分成功和失败。
5. 本地录音开始路径没有在修改 `record_status.run` 前检查 UXFILE 同步状态。异常现场中 `fscan()` 尚未完成就进入 `rdx_record_run_init()`，随后 `app_core` 与 `uxfile` 并发操作 FAT，并连续出现 `timer_no_response`。
6. SD0 已由常在线策略注册和挂载，录音初始化仍重复调用 `dev_manager_add("sd0")`，产生 `dev online aready` / `sd add fail`；它不是死锁主因，但会干扰诊断。
7. 即使阻止并发录音，部分新机的递归 `fscan()` 仍会长期不返回；等待或延长录音重试时间只能掩盖问题，不能建立空索引。

当前补丁采取以下行为：

- 当 DAT 不存在且缓存为空时，直接提交“0 条记录”的合法空索引，不再把递归全盘 `fscan()` 作为新机开机前置步骤；
- `rdx_uxfile_is_scan_active()` 同时检查 `g_sync_state` 和 `g_dat_need_upgrade_rebuild`：`RUNNING/PAUSING/PAUSED` 或待执行首次重建均为忙，避免 2 秒延迟同步尚未启动时出现空窗；
- 格式化成功后把空盘状态和 VM ID `159 = 0xAA` 一并提交；
- 扫描或从缓存重建返回非负值时写入 `0xAA`，失败时写 `0`；保存 DAT 失败返回 `-3`；
- App 发起的本地录音在 UXFILE 忙时使用已有 2 秒定时器延后，最多重试 5 次；等待期间收到 STOP 会取消待启动命令，STOP/PAUSE 不受阻塞；纯在线流式长按录音不访问 FAT，因此不受该门禁影响；
- 设备按键发起的本地录音在 UXFILE 忙时直接拒绝，由用户稍后重试；
- `TCFG_SD_ALWAY_ONLINE_ENABLE = 1` 时不再在录音初始化重复 `dev_manager_add("sd0")`。

这项修复不需要在镜像里预置或手工复制 `UXFILE.DAT`。空盘第一次启动保持“无 DAT + 空缓存”，快速提交 `0xAA`；首次录音结束时再按正常保存路径生成有效 DAT。

该策略有明确的数据恢复边界：如果用户盘上的 `UXFILE.DAT` 被单独删除或损坏，但仍保留 raw 录音文件，开机不会再自动递归扫描并找回这些孤立文件。此类恢复必须放在显式维护/售后操作中，并提供超时、取消和进度反馈；不能继续占用普通开机路径。当前策略优先保证新出厂空盘可启动、可录音且不会死锁，也不会主动格式化或删除遗留 raw 文件。

### 6.6 修复演进：从“避免并发”到“消除错误扫描前置条件”

本问题不是一次修改就得到最终结论，修复过程分为两个阶段：

1. **第一阶段：存储串行化。** 录音启动增加 UXFILE 忙判断，扫描/同步期间延后录音；
   常在线 SD0 不再重复执行 `dev_manager_add("sd0")`。该阶段消除了录音与 UXFILE
   同时操作 FAT 的风险，也消除了 `dev online aready` / `sd add fail` 干扰，但没有
   改变原始库必须执行 `fscan()` 的启动策略。
2. **第二阶段：空索引快速路径。** 阶段性实机验证证明，即使录音已被正确挡住，
   `fscan()` 在可挂载的新 NAND 上仍会长期不返回。因此最终补丁将
   “DAT 不存在且缓存为空”直接定义为合法的 0 条索引结果，跳过 `fscan()`，写入
   VM ID `159 = 0xAA`，再由第一次录音的正常保存流程创建真实 DAT。

这两个阶段不能相互替代：空索引快速路径解决新机启动，忙状态和录音门禁仍负责防止
以后同步、格式化或维护恢复期间出现 FAT 并发访问。

### 6.7 2026-08-19 实机回归闭环

#### 6.7.1 修复前：文件系统正常，业务索引初始化卡死

修复前实机采集到的关键顺序为：

```text
[SD-FMT] sd0 mount ok, skip format on boot
[UPGRADE] DAT scan flag mismatch (... flag=0xFF ...)
DAT file not found, init empty cache.
[UPGRADE] Old cache: 0 entries loaded
[SCAN] Start fscan: storage/sd0/C/
```

现场继续采集约 92 秒仍无 `fscan returned`。约 52 秒时 App 已下发录音命令，但
录音不能进入初始化。这组证据排除了“没有 FAT 文件系统”的判断，并确认旧的递归扫描
策略本身就是启动阻塞点。

#### 6.7.2 修复后首次启动：跳过扫描并生成首个 DAT

加入空索引快速路径后的首次启动输出为：

```text
[UPGRADE] Old cache: 0 entries loaded
=== DAT cache freed (stream mode active) ===
...
[RAW_WRITE] fileSize/offset: 15120
[PRIORITY_SAVE] Added entry: sn=8, name=42b595.raw
[DAT_SAVE] Stream OK: 163 bytes, 1 records (verified: 163 bytes on disk)
[DAT_SAVE] Record save completed: sn=8, name=42b595.raw
```

本次启动没有出现 `[SCAN] Start fscan`，录音文件与包含 1 条记录的 DAT 均成功落盘。
这证明空索引路径不要求镜像或产线预置 `UXFILE.DAT`。

#### 6.7.3 关机重启：持久化索引和 App 列表均恢复

关机重启后的输出完成了最终闭环：

```text
[UPGRADE] DAT scan completed before (flag=0xAA), trust existing DAT
=== Stream loading DAT (487 bytes) ===
=== DAT cache loaded: 3 records ===
=== total_count:3, total_size:33840, uxFileList.cur_num = 12

12 | 55a434.raw |  7680 | 0
10 | 88e8f9.raw | 11040 | 0
 8 | 42b595.raw | 15120 | 0

[GETLIST] Built JSON via sprintf: 3 entries, 487 bytes (buf=1924)
=====> record dat file send finish!
```

关机后 RAM 已丢失，因此这里恢复的不是“关机前内存缓存”，而是 SD NAND 上持久化的
`UXFILE.DAT`。这次实机验证同时确认：

- VM ID `159` 已持久化为 `0xAA`；
- 重启后没有再次进入 `fscan()` 或重建分支；
- 上一轮首个文件 `42b595.raw` 和后续录音均能从 DAT 恢复；
- App `getlist/listreq` 能分包读取完整的 3 条记录；
- 没有 `dev online aready`、`sd add fail` 或 DAT 保存失败。

激活机器、USB 角色切换和关机阶段的定时器超时为测试操作的已知现象，不属于
本次 UXFILE/FAT 缺陷判据。

#### 6.7.4 验收结论

本次缺陷的实机闭环已通过，可以关闭“新出厂机器无 DAT 导致启动扫描卡死、首次录音
不可用”问题。通过范围是新机空索引初始化和正常 DAT 持久化；“已使用设备 DAT
丢失但 raw 文件仍在”的显式数据恢复能力仍属于后续维护功能，不能由本次结论外推。

### 6.8 可复用的工程结论

1. FAT 挂载成功只能证明文件系统可用，不能证明应用业务文件已经初始化。
2. 新机没有应用索引是合法状态，应用必须具备自初始化能力。
3. “无索引”和“索引丢失”必须分流；前者创建空索引，后者才执行数据恢复。
4. 数据恢复不能无超时地阻塞普通启动，应限定目录、分批执行，并提供超时、取消和进度。
5. VM 标志是启动优化和完成记录，不是 SD 上业务数据的替代品；最终闭环必须通过掉电
   重启验证持久化文件。
6. 对无源码第三方库，保留原始 archive、固定输入哈希、使用精确 IR 匹配并验证最终
   链接来源，能够形成可复现、可审计的修复链路。

## 7. 强制格式化测试开关

`TCFG_SD0_FORCE_FORMAT_ON_BOOT` 当前为关闭，仅用于 bring-up/测试。打开后，代码会把一次成功的初始 mount 视为不可用并强制进入格式化分支。

该开关存在以下限制：

- 它是编译期测试开关，不是用户可配置功能；
- 它只作用于 `dev_manager.c` 的开机分支；
- 它不替代 PC MSC 接管，也不包含 RDX UXFILE 的忙判断、缓存处理或业务回调；
- 量产配置必须保持 `DISABLE_THIS_MOUDLE`。

## 8. 失败矩阵

| 场景 | 是否格式化 | 是否写 VM `0xA5` | 最终状态 |
| --- | --- | --- | --- |
| 首次 mount 成功 | 否 | 否 | SD0 可用 |
| VM 无效，mount 失败，format 失败 | 是（尝试） | 否 | SD0 不可用 |
| VM 无效，format 成功，remount 失败 | 是 | 否 | SD0 不可用 |
| VM 无效，format/remount 成功，VM 写失败 | 是 | 否 | 本次 SD0 可用，下次可能再次恢复格式化 |
| VM 有效，mount 失败，format/remount 成功 | 是 | 是 | SD0 可用 |
| PC 接管 | 否 | 否 | HOST_OWNED，固件 mount blocked |
| PC 退出恢复失败 | 否 | 否 | RESTORE_FAILED，SD0 继续 blocked |
| RDX 主动格式化成功 | 由 UXFILE 执行 | 否（不写格式化标志 `0xA5`） | 补丁库写 UXFILE 扫描标志 `0xAA`，空盘无需下次全盘扫描 |
| FAT 可挂载，新机无 DAT、无记录 | 否 | 否 | 提交 0 条空索引并写 UXFILE 标志 `0xAA`，不执行 `fscan()` |
| FAT 可挂载，DAT 有效 | 否 | 否 | 从 DAT 加载缓存和文件列表 |
| FAT 可挂载，DAT 丢失但 raw 仍存在 | 否 | 否 | 当前启动路径不自动恢复；raw 不删除，留待显式维护恢复 |

## 9. 维护与验证要求

### 9.1 修改规则

- 修改开机恢复策略时，优先修改 `dev_manager.c` 和 `board_ac701n_demo_cfg.h` 的对应源码；不要编辑生成文件。
- 修改项目 USB/SD 依赖时，只修改 `t2620_project_config.h`，保持 JL 工具生成配置的所有权边界。
- 不要把 `TCFG_SD0_AUTO_FORMAT_ON_MOUNT_FAIL_ENABLE` 重新引入产品配置；当前实现不依赖该旧宏。
- 任何会改变格式化、卸载、重新挂载或 VM 写入时序的改动，都必须重新检查 PC MSC 所有权闭环。
- 不要直接覆盖原始 `librdxApp.a`；原始库升级后必须先审查 IR 差异并更新补丁脚本的输入哈希和精确匹配，禁止对未知版本强行套补丁。

### 9.2 主机测试

从仓库根目录运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tests\host\run_host_tests.ps1
```

其中 `test_t2620_product_contract.ps1` 会验证：

- SD0、USB MSC、PC 存储 overlay 依赖；
- 开机自动格式化开关和强制测试开关；
- mount 失败时首次初始化与文件系统恢复都会调用 `f_format()`；
- PC 接管前的忙判断；
- `mount_blocked` 独占保护；
- USB 停止先于 SD0 恢复挂载；
- 掉电通过正常模式清理释放 PC 存储，而不是直接绕过清理流程。
- `librdxApp_patched.a` 的固定哈希、Makefile 链接目标、空索引快速路径、初始化忙状态、完成标志补丁，以及本地录音对 UXFILE 恢复的串行化。

主机测试不能证明真实 NAND 控制器、FAT 写入和电源时序；量产前仍需在目标 AC701N/BR28 硬件上覆盖首次启动、损坏文件系统、USB 重新格式化、PC 退出恢复失败和 RDX 主动格式化等场景。

新机专项验收至少应覆盖：

1. 使用空白或仅含可挂载 FAT 的 SD NAND，清除 UXFILE 相关 VM；
2. 首次启动允许出现一次 `flag=0xFF`，但“无 DAT + 空缓存”不得再打印 `[SCAN] Start fscan`，必须快速完成 0 条空索引提交；该路径可能打印 `[UPGRADE] No audio files found`；
3. 在空索引提交前发起本地录音只能看到 `[REC_DELAY]`，不能进入 `rdx_record_run_init()`；提交完成后待启动录音应自动继续；
4. 空索引提交或主动格式化完成后，下一次启动必须打印 `flag=0xAA`，不能再次进入全盘重建；
5. 首次录音开始/停止成功，生成录音文件和有效 `UXFILE.DAT`；
6. 除激活机器、USB 角色切换和正常关机阶段的已知测试现象外，不出现持续 `timer_no_response`；全过程不出现 `dev online aready` 或 `sd add fail`。
