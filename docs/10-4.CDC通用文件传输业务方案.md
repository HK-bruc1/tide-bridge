## 0. 当前实现与后续边界

本文前半部分保留真实录音文件业务的设计，不能理解为全部已实现。第 11 节为实验历史，最新状态以本节和第 11.11～11.13 节为准；历史中的旧宏名、默认开关与待测状态仅描述当时构建。

| 层次 | 当前职责与边界 |
|---|---|
| USB 驱动 cdc.c | 原生 USB CDC 端点和非阻塞提交；文件流 IN IRQ 每次最多续交一包 |
| 传输层 usb_factory_cdc.c/h | 有界队列、背压、会话代次隔离、超时、低水位补货与二进制流发送；沿用已有文件名，不另复制一套驱动 |
| 通用入口 rdx_factory_cdc.c | 共用命令解析、来源日志与任务唤醒；产测命令仍复用既有 DUT；file 命令不要求进入 DUT |
| 文件协议 rdx_cdc_file.c/h | CAPS、BENCH、CANCEL、CDF1 DATA/END/ERROR、CRC 与取消；当前数据源仅为内存模式，GET 返回 UNAVAILABLE(8) |
| 主机工具 | CDC-test.bat 菜单 3 复用 tools/cdc_file_transfer.py；默认 inline 校验，deferred 仅供诊断，不新增产品接收线程 |

当前没有已实现的存储数据源抽象，不以改名替代真实文件接入。后续 GET 应接入已有帧协议和流发送接口，并补充文件生命周期、存储互斥和失败清理，不复制现有吞吐调度。

配置统一放在 SDK/apps/earphone/include/t2620_project_config.h：

| 开关 | 默认 | 作用 |
|---|---|---|
| TCFG_T2620_CDC_FILE_ENABLE | 1 | 通用文件协议与流发送基础设施；替代旧 TCFG_T2620_CDC_FILE_MVP_ENABLE，不提供旧名兼容 |

queued 仅代表终止帧已入发送队列，不代表主机接收或校验完成。性能统计与普通日志分离；不开性能探针也必须保留背压、低水位重武装、超时与生命周期保护。文件功能关闭配置保留原有产测路径。所有配置切换使用统一 clean + all；正式开放基准命令及量产安全策略仍需后续决策。

## 1. 后续真实文件业务目标与原始设计

CDC 是开机状态下的通用 USB 通道，产测只是其中一类业务。枚举不依赖 DUT、BLE 连接或 SD 健康，实际仍受 USB 角色、配置、主机连接和关机状态约束。

内存链路 MVP 已完成；后续真实文件阶段回答的问题是：**本设备从存储读取已保存录音，经 CDC 发送到电脑，能否持续达到至少 600 KB/s，并且数据完整正确？**

本轮不实现新的登录、鉴权、物理确认、加密、列表快照系统或正式产品 UI。它们不是性能实验的前置条件。上一版 200～300 KB/s 目标由本版 600 KB/s 目标替代；该数字在内存链路已通过，在真实文件路径仍是待验证门槛。

### 1.1 最小功能

1. 不进入 DUT，不要求本次先录音，不依赖 BLE 登录。
2. 选择一个已保存、已关闭且身份明确的测试录音文件。
3. 打开一次、顺序读取、二进制连续发送，电脑接收并保存。
4. 校验长度、顺序和 CRC，输出可重复的吞吐报告。
5. 支持取消、拔插、主机停读和错误后的资源回收。

### 1.2 明确后置

量产鉴权及隐私交互、加密、完整文件列表和分页、跨会话稳定 file_id、断点续传、删除/上传、自动下载后删除、产测接口迁移、BLE 协议改版、多传输并行均后置。

真实文件验证阶段仅使用测试文件；通用基础设施当前默认开启，但不代表量产文件访问权限已开放。暂不鉴权是本次受控实验的范围选择，不代表量产可直接开放用户录音。仍禁止主机任意路径访问、越界读取和绕过关机。

64 字节 / 2 ms 对应约 32 KB/s 的定时推进量级，不是 USB CDC 上限，也不是严格软件硬上限。当前产测版速度不能用来判断优化版能否达到 600 KB/s。

### 2.3 CDC 波特率不限制当前 USB 文件传输速度

**当前实现保持主机串口参数 `115200` 即可；调高波特率不会据此提高 CDC 文件传输速度。** 波特率是 CDC 虚拟串口的配置参数，不是 USB 链路速率，也不是当前文件发送路径的限速值。

- 主机测速工具 `tools/cdc_file_transfer.py` 的 `--baud` 默认值为 `115200`。2026-10-08 报告 `output/cdc-file-reports/20261008-201408-133096-file-bench.json` 记录 COM6、baud=115200，普通模式十轮平均 719.88 KB/s，全部长度、数据模式与 CRC 校验通过；这是内存源结果，不代表真实录音文件读取速度。
- 固件 `SDK/apps/common/device/usb/device/cdc.c` 处理 `USB_CDC_REQ_SET_LINE_CODING` 时仅保存并打印参数，没有根据波特率调整 USB 发送时钟、端点包长或续包调度。初始化的 `dwDTERate=460800` 也是默认串口参数，不是发送速率上限。
- 当前数据直接通过 USB 端点发送，不经过按该波特率发送的实体 UART。因此改成 `921600` 或 `2000000` 不会改变现有文件传输执行路径，不能套用实体 UART 的波特率换算解释约 720 KB/s 的结果。
- 本项目约 450 KB/s 到 700+ KB/s 的主要提速来自文件流 IN 中断有界续包，而非提高波特率。后续性能分析应关注端点续包、任务/中断调度、主机读取及数据源供给。

可以把当前路径理解为：电脑串口 API → CDC 驱动 → USB Bulk 端点 → 固件业务。COM 口是软件接口，不是一个按 115200 发送的实体串口；没有将每个字节转换为 UART 起始位、数据位、停止位再传输的环节。CDC 转实体 UART 的桥接设备才会受到后级 UART 速率约束。

此结论限定于本项目当前实现，不泛指所有 CDC 设备；若以后增加 CDC 转实体 UART，或业务主动根据波特率限速，应重新评估。报告保留 baud 字段用于环境记录，不作为 USB 实际枚举速率证据。COM3 固件日志口与本次 COM6 文件传输口是两个不同用途的端口。

## 3. 600 KB/s 的预算与判定口径

### 3.1 单位和速率预算

本文 600 KB/s 明确定义为 **600,000 个文件有效字节/秒**，约 585.94 KiB/s；不把串口波特率、编码后长度或瞬时峰值作为有效吞吐。

以现有 64 字节端点包长计算，仅有效载荷就要求平均约 9,375 个包/秒，相当于每毫秒约 9.4 个包，尚未计入应用帧开销。因此：

- 每 2 ms 只提交一包肯定不能支撑目标。
- 把周期改成 1 ms 但仍只发一包也不能支撑目标。
- 必须验证驱动完成通知、持续续发以及上游数据供给能否跟上。
- 这只是预算推算，不证明 JL 控制器、驱动、存储和调度实际支持目标。

目标数据量约为每 10 ms 6,000 字节。现有 4 × 258 = 1,032 字节队列若只每 10 ms 填充一次，即使瞬间排空，供给量也仅约 103.2 KB/s，仍远低于目标。不能只优化 USB 包发送而保留低频补充队列。

开始实验前在电脑确认实际枚举速率、Bulk 端点和驱动信息；不凭“USB 2.0”名称推断速率。600 KB/s 是否可达由下面的分层实验决定。

### 3.2 三种测量，不能混为一谈

| 测量 | 计时范围 | 用途 |
|---|---|---|
| USB 内存源 | 主机收到首个数据帧到完整 END，另记录设备发送耗时 | 验证传输层上限，不作为文件业务通过证据 |
| 真实文件稳态 | 首个数据帧到完整 END，含接收期间的文件写入及在线校验 | 定位持续读取/发送性能 |
| 真实文件端到端 | 主机发出 GET 到校验通过、输出文件关闭 | MVP 600 KB/s 的正式判定口径 |

使用单调时钟；另外记录 OPEN/首字节延迟、设备读取时间、排队等待和关闭耗时。普通文件关闭不等于物理介质持久化；首轮不要求 fsync，若启用需在报告中明确并单列结果。

### 3.3 通过标准

- 主验收采用至少 10 MB 的合法已保存测试录音，连续独立下载至少 10 次。
- 每次端到端有效吞吐均不低于 600 KB/s，全部长度、顺序和 CRC 正确；报告均值、中位数、最小值、最大值及失败次数。
- 文件预计耗时可用 size / 600000 检查，例如 10,000,000 字节对应约 16.67 秒端到端预算。
- 1,403,120 字节文件用于 BLE/CDC 同文件对照，不以短文件或局部突发峰值替代大文件持续验收。
- 只有 USB 内存源达到目标，结论只能是“传输层可达”；真实文件不达标必须继续定位或明确报告未通过。
- 若仅稳态达到 600 KB/s 而端到端未达到，应同时报告两个结果，不标记 MVP 达标。

至少用一次独立基准读取或已知内容验证测试文件 CRC，防止固件发送错误内容却用同一错误数据计算 CRC 而被误判通过。CRC 不替代音频可解码检查。

实施检查点分开报告，不要求第一轮实验一次完成正式验收：

| 检查点 | 最小证据 | 允许的结论 |
|---|---|---|
| 链路可行 | 内存源持续发送至少 10 MB，校验正确，测量速度与余量 | 仅传输层达到目标，未证明文件业务 |
| 业务初证 | 一个真实历史录音完整下载，记录稳态及端到端速度 | 文件路径已打通；小文件或单次结果不是正式通过 |
| 正式通过 | 至少 10 MB 真实录音连续独立下载 10 次及异常回归 | 满足本节全部标准后认定 MVP 达标 |

## 4. MVP 架构：保留现有层次，最少新增业务

USB 层继续独占端点 I/O 和 DMA，app_core 处理控制状态，文件 worker 做阻塞文件 I/O。不在 ISR 做文件读取、CRC 扫描和打印，不绕过统一发送路径直接调用 cdc_write_data()。

只新增一个开发配置下的通用文件下载适配和独立电脑工具。先复用现有文件索引定位 SN/名称，不建设新的长期文件标识系统。MVP 可从开发日志或既有文件列表取得 SN 与名称，工具传入两者，设备按现有索引和元数据确认同一文件。

### 4.1 拆开公共文件能力与产测约束

从 rdx_record_format_factory_open() 抽取或复用身份校验、格式校验、只读打开及有效长度获取逻辑，不直接删掉原函数的产测保护。

- 产测适配层继续校验本轮录音归属、file_busy 和原有大小/格式规则。
- MVP 通用适配层接受明确的历史已保存文件，不受产测 40 KB 上限限制。
- MVP 首期仅支持可可靠识别的既有有效录音格式，未知或不完整文件明确拒绝；最大文件大小和偏移字段按第 5.4 节执行。
- 通用打开不全文件预扫 CRC；校验必要元数据后顺序读取，一边发送一边累计 CRC，结束报告。
- 原扫描里的逐 240 字节延迟不能直接搬入高速路径；改为有界块读取及合理让出调度，不能用忙等换吞吐。

FILE_BUSY 必须是公共文件服务占用而非伪造产测状态。先取得占用，再校验身份并打开，关闭完成才释放；禁止打开失败后回退到最新文件。

### 4.2 最小互斥不能后置

实验时仅下载一个文件，不并行录音、播放、BLE 文件下载、删除、格式化、包装和 MSC。入口检查和实验环境约束都要明确，不能仅靠操作员承诺不存在并发。

盘点现有公共准入机制，将新的下载占用纳入原有冲突检查；不能只在 CDC 入口检查别人，其他入口却能中途修改文件。BLE/HOGP 连接可保持；系统任务及关机保持响应，不开展并发性能优化。

拔插、超时和取消停止新生产，异步关闭句柄，关闭失败保留隔离状态。DIP OFF 不等待主机确认、不被文件服务否决，DMA 回收仍走原生 USB 生命周期。

## 5. 最小协议草案

以下是新 MVP 接口提案，当前固件尚不支持。APP 统一表示上位机，来源在日志及会话中单独标记。第 5.4 节给出阶段 A 两端共同采用的最小线格式；开工时先生成黄金向量并锁定测试，不各自定义格式。不以正式量产协议的完整性阻塞性能验证。

### 5.1 保留文本命令，能力查询无副作用

请求使用 ASCII + 实际 CRLF，维持现有命令长度上限。建议：

| 命令示例 | 作用 |
|---|---|
| *APP#file#caps# | 只查询 MVP 版本、块长、最大文件及忙闲状态，绝不切换模式 |
| *APP#file#get#<sn>#<name># | 校验并打开指定文件，异步开始一次连续二进制下载 |
| *APP#file#cancel#<transfer_id># | 取消当前传输 |

不新增 LIST、OPEN/START 两阶段交互、FINISH 确认或永久二进制会话模式。首期不做断点续传，失败后重新 GET，不盲目重发状态未知的请求。

GET 通过公共准入后，先返回完整文本受理行，包含 transfer_id 和版本；拒绝则只返回文本错误、不切换。受理后直到终止帧，设备到主机仅发送 DATA、END 或 ERROR 二进制帧，文件打开失败也通过 ERROR 终止该事务。

文本受理行和第一个二进制帧通过同一有序发送器交付，允许同一次主机 read 收到两者，主机按行边界切换解析而不按 read 边界猜测。旧待发应答必须先排空，旧产测实时流/文件业务活动时拒绝 GET，不允许旧业务输出插入文件帧。

END/ERROR 是明确的事务结束边界，之后恢复普通文本应答。主机到设备仍为文本；下载中仅处理 CANCEL，其他新请求记录为拒绝且不产生插入流中的文本响应，待终止帧后按既定顺序回复 BUSY。待处理控制数量有界，超额输入使会话失败，不无限积压。

### 5.2 二进制帧与不可交错规则

最小字段：魔数、版本、类型、transfer_id、offset、payload_length、payload、CRC。类型仅 DATA、END、ERROR。帧头固定大小，字节序、CRC 覆盖范围及上限按第 5.4 节执行并用黄金向量验证；不直接发送 C 结构体。偏移与有效长度严格连续，不需要再维护与偏移重复的包序号。

DATA 携带原始文件字节，不做十六进制或 Base64。END 携带实际总长度与完整文件 CRC；ERROR 携带失败原因。主机必须处理拆帧、粘帧、非法长度、错偏移、CRC 错和提前 EOF。

统一发送器持有一个当前应用帧；拆成多个队列元素后不能被其他帧/文本插入。队列满只暂停续交，不从头重发已有分片。正常取消停止预读，在完成当前应用帧后发 ERROR(CANCELLED)，然后回到文本；若主机不再读取则超时终止会话，不尝试无限等待半帧收尾。

取消时按提交边界处理，不把“当前帧”等同于正在组装的帧：

- 尚未向底层提交任何字节的帧及预读数据可丢弃；已发起的文件读取允许返回，但结果不再生成新帧。
- 已部分提交的应用帧必须补齐剩余字节与 CRC；已完整入队的帧保持原顺序排出，不能跳过或重发。
- ERROR(CANCELLED) 排在全部保留帧之后；正常取消不清空底层队列，不提前释放在途 DMA 或未完成读取使用的缓冲。
- 停止新生产、句柄关闭和终止帧送达分别记录。正常关闭完成后发送终止帧；关闭失败则进入隔离，不能伪装为可重试的取消成功。
- 无法收尾时使会话失效，禁止在残缺二进制帧后直接恢复文本；队列废弃及 DMA 回收仍走原生传输清理路径。

拔插/会话失效可直接中止半帧并丢弃旧队列，主机废弃本次临时文件。transfer_id 绑定 generation，旧命令及回调不得作用于新连接；同一事务 CANCEL 幂等，错误 ID 不取消其他事务。

### 5.3 完成与失败

正常状态：IDLE → OPENING → STREAMING → CLOSING → IDLE；资源归属无法确认或关闭失败时进入 QUARANTINED 隔离状态，不无条件返回 IDLE。文件读取结束后先完成资源关闭，正常关闭后再发送 END；失败则在可保持完整帧边界时发送 ERROR。终止帧尚未完成发送前不接纳下一次 GET。

设备日志“发送结束”只代表设备侧完成，不能声称主机已保存。**MVP 成功以电脑工具收到 END、长度/CRC 校验通过且输出文件关闭为准**，无需为性能实验新增主机 FINISH 握手。

保持现有底层 2 秒无发送进展超时；MVP 工具读取超时初始设为 5 秒，打开超时初始设为 10 秒，单次实验总时限初始设为 120 秒。支持文件上限需与总时限匹配。主机停读超过底层容忍期允许失败并重建会话，不承诺暂停续传。反复无效命令不得刷新有效进展时钟。

底层超时仅覆盖有待发或在途数据的情况，不能替代设备业务看门狗。业务计时由不执行阻塞文件 I/O 的控制任务维护，初始预算如下；这些值是待实测的 MVP 参数，不代表底层文件系统支持强制中断：

| 状态/操作 | 有效进展与初始预算 | 到期处理 |
|---|---|---|
| OPENING | 从受理至打开完成最多 8 秒，不因控制命令刷新 | 标记事务失效；晚到句柄只用于关闭，不启动发送 |
| STREAMING 读取 | 每次已发起读取最多 3 秒；等待空闲缓冲不算读取执行 | 停止新生产，等待在途调用退出并清理 |
| CLOSING | 从发起关闭至返回最多 3 秒 | 进入隔离，保留句柄/缓冲所有权，不强制复用 |
| 整个事务 | 从受理起最多 110 秒，不因局部进展延长 | 停止生产并进入失败清理；主机总时限仍为 120 秒 |

恢复规则：

- 普通拒绝，或资源已回收且完整 ERROR 已送达：可以在同一串口会话重新 GET。
- 半帧、发送超时或传输失效：主机废弃临时文件，关闭重开串口并清理接收解析状态；通过新 generation 和 CAPS 确认就绪后再试，不能在旧流中搜索魔数继续。
- 文件操作未返回或关闭失败：重新打开串口不解除公共文件占用。保持隔离，迟到操作返回后仅执行清理；只有能确认资源全部释放才恢复，否则需要设备恢复/重启。
- 工具超时不代表设备已清理；隔离期间文件请求返回不可用。DIP OFF 仍按原生关机执行，不等待上述预算，不强制释放仍被 I/O 或 DMA 使用的内存。

### 5.4 阶段 A 最小线格式约定

本节仅冻结开发 MVP v1，不承诺量产兼容。文本均为 ASCII，末尾为实际 CRLF，数字使用无符号十进制；名称沿用既有合法文件名校验，拒绝分隔符、路径和超长输入，不引入转义规则。

| 项目 | MVP v1 约定 |
|---|---|
| 能力回复 | `*DEV#file#caps#1#8192#16777216#<state>#`，依次为版本、最大 DATA 负载、最大文件字节数及状态 |
| 开发内存源启动 | `*APP#file#bench#<size>#<block>#`；size 为 1～16,777,216，block 仅 1024/2048/4096/8192，尾块可更短 |
| GET/bench 受理 | `*DEV#file#accepted#<transfer_id>#1#`；后续按二进制解析，bench 同样使用 CANCEL 终止 |
| 文本拒绝 | `*DEV#file#error#<code>#`；CAPS 的 state 为 IDLE/OPENING/STREAMING/CLOSING/QUARANTINED |
| transfer_id | 非零 u32，设备运行期间单调分配并绑定当前 generation；跨连接不重用，耗尽拒绝新事务，重启后主机必须清空旧会话 |
| 二进制帧头 | 固定 20 字节：magic[4]、version:u8、type:u8、header_length:u16、transfer_id:u32、offset:u32、payload_length:u32 |
| 固定值与字节序 | magic 为 ASCII `CDF1`（43 44 46 31），version=1，header_length=20；多字节整数均小端 |
| 帧类型 | DATA=1、END=2、ERROR=3；DATA 负载 1～8192 字节，offset 从 0 起连续累计有效文件字节 |
| 帧尾 | u32 小端 CRC，覆盖完整 20 字节帧头及负载，不含帧尾自身；最大整帧 8216 字节 |
| END 负载 | total_size:u32 + file_crc:u32，共 8 字节；头部 offset 等于总有效长度 |
| ERROR 负载 | code:u32，共 4 字节；头部 offset 等于此前完整保留 DATA 的累计有效长度，不含丢弃的预读数据 |
| CRC 定义 | CRC-32/ISO-HDLC：poly=0x04C11DB7，refin/refout=true，init=0xFFFFFFFF，xorout=0xFFFFFFFF；文件 CRC 只覆盖顺序原始字节 |
| 基础错误码 | 1=BAD_REQUEST、2=BUSY、3=NOT_FOUND、4=INVALID_FILE、5=IO_ERROR、6=CANCELLED、7=TIMEOUT、8=UNAVAILABLE、9=BAD_TRANSFER_ID |

GET 不增加块长参数，初始采用 4096 字节；实验固件可调整候选块长并在报告中记录，接收器按实际 payload_length 解析。文件有效大小上限为 16 MiB（16,777,216 字节），零长度拒绝；按 600 KB/s 约需 28 秒，低于总预算，但低速或停滞实验仍可能超时。后续若调整上限，必须同步 CAPS、边界测试和超时预算。

内存源第 offset 个字节为 `offset & 0xFF`，在线生成，不占用整文件 RAM。阶段 A 开始时先提交两端共享黄金向量：空内容 CRC=0x00000000、ASCII `123456789` CRC=0xCBF43926，以及完整 DATA/END/ERROR 帧的逐字节样例与期望 CRC；先用独立实现交叉验证再进行实板测速。文件 CRC 按完整流累计，不能把分块 CRC 简单相加。

下载中 CAPS 与其他非 CANCEL 请求同样按第 5.1 节延后拒绝，不插入文本。错误 transfer_id 的 CANCEL 不影响当前事务，按同样边界延后回复 BAD_TRANSFER_ID；重复有效 CANCEL 不重复生成终止帧。bench 仅开发配置可用，不新增独立停止协议。

## 6. 为 600 KB/s 改造数据通路

### 6.1 第一关：USB 纯传输实验

开发配置下使用可验证的内存模式数据，至少发送 10 MB，总大小不要求驻留 RAM。使用与文件模式相同的二进制封装和电脑接收器，校验固定模式、长度及 CRC。

核对当前 JL 驱动是否提供适用的 IN 完成通知；优先由完成事件唤醒 usb_stack 连续续发。每轮使用明确的工作预算，端点忙即退出，不能在任务或中断中忙等等待主机。

若完成事件不可用或逐包唤醒开销太高，应先评估驱动支持的缓冲/批量机制及安全的中断适配，不假定存在 DMA 链表或多包硬件队列。按实测选择路径，保留端点所有权和 DMA 生命周期。

本阶段内存源也达不到 600 KB/s，则停止扩展业务功能，先报告控制器/驱动/调度瓶颈。不能靠加大文件缓冲或降低验收标准掩盖问题。

### 6.2 第二关：存储读取实验

在公共文件占用保护下，对同一合法文件做只读顺序读取，测量纯读取和读取加 CRC 两种速度及每块延迟，不发送 USB。

以 4 KB 块为起点，测 1/2/4/8 KB 候选；缓冲总量根据链接 map 和实测可用内存确定，不默认可以无限增加。读取加 CRC 达不到 600 KB/s 时，先检查存储、文件访问和逐块让出调度，再做集成。

读取速度和 USB 速度单独达到目标仍不代表组合通过；两者会争用 CPU、内存和任务时间，需要留余量并实测流水线。

### 6.3 第三关：真实文件流水线

初始候选为两个 4 KB 缓冲：一个读入，一个发送，文件 worker 的完成事件和发送队列腾空事件推进生产，不依赖每 10 ms 才补一次数据。8 KB 仅是文件负载缓冲候选，不包含帧头、USB 队列和任务栈，需报告实际总 RAM 增量。

先使用所有权清楚的有界复制实现，测量 CPU 与吞吐后再考虑减少复制；不把零拷贝作为 MVP 前置条件。若采用缓冲引用，直到 USB 完成才归还，断线清理不得提前复用 DMA 使用的内存。

底层仍按 64 字节端点包长提交，任务和开发配置的流式 IN 中断共用该约束；应用层 4 KB 不等于 USB 单包 4 KB。不能只扩大 FACTORY_CDC_TX_MAX 而不审查队列内存、临界区复制长度、短包和 ZLP 行为。

### 6.4 控制接收不能被发送堵塞锁死

当前 usb_factory_cdc.c 在 TX 队列满时不再接收 RX，rdx_factory_cdc.c 在应答堵塞时不再解析命令。MVP 必须解开这两个耦合：

- 独立保留有界 RX 控制缓冲，TX 满时仍可接收 CANCEL。
- 文件模式下可处理取消，不因待发应答占满而停止控制解析。
- 接收取消后立即停止新读取，取消应答发送失败不影响本地停止与清理。
- 正常主机持续读取时，取消至停止新生产的目标为 100 ms 内；需实测并记录最坏值。终止帧送达与句柄关闭分别计时，不能混作同一指标。

## 7. 电脑 MVP 工具与日志

tools/cdc_file_transfer.py 维护唯一的通用文件二进制接收器，当前支持 caps/bench，download 后续接入。CDC-test.bat 增加菜单 3 作为交互入口，内部直接调用该模块，不复制协议实现，不运行普通产测/DUT 流程，也不先打开第二个串口。

工具输入 COM 口、SN、名称和输出目录；通过显式开发命令启动内存源测试，量产配置不暴露 bench。串口波特率保持默认 `115200` 即可，无需专门进行不同波特率对照；当前实现不按此参数限速，依据见第 2.3 节。

接收器连续读取、增量拆帧、在线 CRC，采用有界缓冲；先保证电脑消费端明显不构成瓶颈。不逐个 USB 包打印或逐块 flush，进度输出最多每秒一次。写入临时文件，校验与关闭成功后再改为最终文件名；设备名称不直接拼接为任意本机路径。

生成 JSON 报告：固件版本、协议版本、OS/驱动、USB 实际速率和连接拓扑、文件身份及大小、块长/缓冲量、各阶段耗时、每轮速度、CRC、失败原因和取消结果。

固件保留 [CDC_RX] 控制命令日志，不打印文件负载；记录开始/结束、长度、CRC、队列高水位、读延迟、端点空闲和错误。测量使用量产级日志密度，另做关闭非必要日志对照，不将现有 app_core timer_no_response 当作可忽略噪声。

## 11. 阶段 A 实施记录与实测入口（2026-10-08）

### 11.1 本次实现范围

- 功能开关现已统一命名为 TCFG_T2620_CDC_FILE_ENABLE，默认 1，VS Code 与命令行使用同一项目配置；当前配置及开放边界见第 0 节。必须配合 CDC 正式命令解析模式，禁止与历史字节回显测试同时启用。
- 启用后支持 CAPS、bench、CANCEL，采用第 5.4 节格式；GET 明确返回 UNAVAILABLE，尚不打开真实文件。电脑工具目前也仅提供 caps/bench。
- 命令经通用解析入口打印 [CDC_RX]，不打印文件负载；保留 CDC-test.bat 和原产测命令。DUT 或产测音频/文件未结束时拒绝 bench，避免旧音频尾包混入新二进制流。
- 第二轮优化允许文件流 IN 完成中断在校验会话与端点空闲后，最多提交一个已排队的 64 字节包，并重新使能通知；普通文本、ZLP、队列边界及异常回到 usb_stack。应用任务不操作端点，中断不执行文件业务、CRC、日志或回调，无忙等，2 ms/10 ms 定时器作补偿。详细边界见第 11.6 节。
- 开发配置 TX 队列为 32 项，每项最多复制 258 字节；二进制生产每次提交最多 256 字节，每轮最多 32 次。入队只在发送链路空闲时唤醒 usb_stack，已有在途包由 IN 完成通知推进。补货采用半深度水位边沿通知：队列回升到 16 项以上后重新武装，降至 16 项及以下通知一次；实际发送排空时另通知一次，避免低水位持续期间逐包唤醒 app_core。消息投递失败仍由定时器补偿。
- 应用帧缓冲最大 8216 字节。中间二进制片段不额外插入 ZLP，最终 END/ERROR 用短包结束；普通产测文本保留原 ZLP 行为。TX 满时仍接收独立 RX 控制数据。
- 取消停止新帧生产，丢弃未提交帧、补齐部分提交帧及 CRC，随后发 ERROR；保持队列顺序，不清活跃 DMA。保留 110 秒事务预算、底层 2 秒无进展超时及 generation 隔离。
- [CDC_FILE] queued 表示终止帧已入队，不表示电脑已收到；速率以电脑 JSON 为准。存储 worker、文件互斥、I/O 超时隔离及真实文件测速均待后续阶段。

软件验证：默认/开发配置构建通过，统一 host runner 扩展为 14 组。新增真实 C 生产器、通用解析器、传输队列和 Python 接收器测试，覆盖拆粘帧、CRC、尾块、满队列取消及过期会话。黄金向量位于 tests/host/fixtures/cdc_file_v1.json，由独立逐位 CRC 生成，C 查表算法与 Python zlib 交叉验证。软件测试不代替中断时序、拔插、DIP OFF、BLE/HOGP 及吞吐实板测试。

本轮选择低风险的任务调度优化，不修改协议、CRC、内存模式、块长默认值或主机计时口径，不增加缓存容量，不将文件业务或端点提交搬进中断。

| 问题/线索 | 已实施策略 | 保留的边界 |
|---|---|---|
| 每次入队都可能重复唤醒 USB 任务 | 仅发送链路空闲时由入队启动；有在途包时等待 IN 完成通知推进 | 通知仍合并，投递失败有定时补偿 |
| 持续低水位时每包都可能触发补货回调 | 队列从高于 16 项降至 16 项及以下时通知一次，回升后重新武装；实际排空另通知一次 | 维持 32 项有界队列，不依赖无限重试或忙等 |
| 每个完成包都遍历日志队列合并统计 | MVP 的 LOG_LEVEL=1 改为固定计数器累加，每秒输出 [CDC_TX] | 正常非 MVP 配置保留 TX_DONE；不打印数据负载 |
| 日志输出位于本轮端点处理之前 | 将日志输出移至本轮端点提交与回调完成之后 | 不在 IRQ 或关中断区打印，不取消必要错误日志 |

#### 11.4.4 新增统计的判读边界

[CDC_TX] 每秒最多输出一行，仅有完成数据或满队列事件时输出；字段含义如下：

| 字段 | 含义与限制 |
|---|---|
| gen / window_ms | 会话代次 / 实际统计窗口；窗口不能一律假定为 1000 ms |
| bytes / packets | 硬件已消费的非零包字节/包数，含协议和控制报文；不是文件有效吞吐 |
| dispatch / busy | 有效 USB 处理次数 / 处理时上个包仍未完成次数；busy 不单独证明主机慢或调度慢 |
| drained | 完成时队列和 ZLP 均为空次数，包含正常收尾；不能直接等同断粮 |
| refill / full | 补货回调次数 / 入队满队列次数；full 是背压，不能直接等同丢包 |
| kicks | 成功投递 USB 工作通知次数，不等于 IN 中断次数 |

会话失效会清空计数，这些日志不是完整事务字节账本，也不测量微秒级端点空闲间隙。最终速度与完整性仍以主机 JSON 为准；[CDC_FILE] queued 只表示入队完成。

### 11.6 第二轮优化（第三次调试）：文件流 IN 完成中断有界续包

#### 11.6.1 实验目的与改动

450.36 KB/s 仅是现有实现实测值，不是已证明的 CDC 或硬件上限。本轮不更换 CDC、不增加 WinUSB 接口、不修改文件协议、CRC、脚本计时口径、块长或队列容量。只验证减少逐包 USB 任务往返是否带来收益；尚未获得微秒级完成到提交间隔，不能把调度瓶颈写成已证明的根因。

- 仅 TCFG_T2620_CDC_FILE_ENABLE=1 开启快速路径。默认产品固件继续原任务路径。
- cdc_tx_wakeup 屏蔽本端点 IN 通知后调用 factory_cdc_tx_irq；仅 active/ready/configured 有效、前一包和下一项均为 stream、没有 ZLP、硬件不忙且未超时时，确认上一包完成并提交下一包。
- 单次中断最多复制和提交 64 字节已准备好的数据，不循环等硬件；不生成帧、不计算 CRC、不读存储、不打印、不调用上层补货函数。提交通过现有非阻塞 cdc_factory_write_packet 完成，同时重新使能 IN 通知。
- 低水位和队列边界合并通知 usb_stack；补货回调仍在任务内执行。RX 完成独立通知 USB 任务，不能因为持续 TX 而停止接收取消。
- 普通文本及 ZLP 仍由任务处理。最终包硬件完成后才计入 bytes/packets，不因 IRQ 已提交就提前认定完成；任务与 IRQ 不重复累计同一个包。

#### 11.6.2 生命周期审查与诊断

usb_config.c 的中断分发先处理 RESET 与 EP0，再调用数据端点回调。软件队列和 DMA 提交继续由本地 IRQ 排他保护；RESET/CONFIG/CLOSE 清除 ready、队列和在途软件状态，OFF 先 quiesce，STOP/释放仍在 usb_stack 路径完成。旧会话回调不能直接保留数据指针到下一会话；硬件忙时禁止覆盖 DMA。两秒无进展超时保留，快速路径不绕过到期检查。实际复位/拔插/关机竞争仍需实板验证。

[CDC_TX] 新增 irq_fast：本窗口在 IN 中断中成功续交的包数，属于提交计数，不是完成计数。bytes/packets 仍表示硬件已消费的数据；dispatch 仅统计 USB 任务处理次数。若快速路径有效，应观察到 irq_fast 持续增加、dispatch/packets 比例明显下降；这只能证明路径工作，吞吐达标仍以主机有效字节/总耗时判断。

#### 11.6.3 软件验证与复测顺序

真实 C 传输测试新增 IRQ 续包字节顺序、忙端点不重复提交、尾包只计一次、低水位任务回调、RX 可处理、文本/ZLP 边界、RESET/CONFIG/CLOSE/STOP/TIMEOUT 撤销、OFF quiesce、超时回退及通知失败定时补偿。真实驱动回调测试检查先屏蔽、提交再重新使能 IN 通知。模拟测试不代表真实中断时序或硬件吞吐通过。

#### 11.7.4 可复用的调试经验与后续边界

1. **先隔离变量，再引入业务。** 先用内存源区分 USB 传输与 SD 读取瓶颈；内存达到目标后再分别测读文件、读文件加 CRC、最终端到端 GET，不能把内存吞吐当作录音下载速度。
2. **同时看主机结果和底层计数。** 主机有效字节/总耗时决定达标；bytes/packets/dispatch/drained/refill/full/irq_fast 用来判断生产不足、调度开销或续包路径。queued 仅表示排队完成，baud 不表示 USB 链路速度。
3. **优化没有收益也要归档。** 第一轮保留了每包任务往返，未解决主要限制；如实记录 450.36 KB/s，避免以后重复只加缓存、调低水位或减少补货通知。
4. **改变关键路径，而不是先更换协议。** 本轮在同一 CDC、同一校验和计时口径下突破 700 KB/s，无需先引入 WinUSB 或维护新协议。真正有收益的是让准备好的下一包更及时进入端点。
5. **性能改动必须有明确上限和安全边界。** IRQ 每次最多一个 64 字节包，无忙等、文件 I/O、CRC、日志和业务回调；会话撤销、在途 DMA 保护、ZLP、RX 取消、超时不可为速度让步。默认产品配置仍不开放 MVP。
6. **成功报告不能覆盖失败报告。** 十轮成功证明该次运行达标，不自动关闭先前 invalid binary header。当前优先定位该异常并补停读、拔插、OFF 和 BLE/HOGP 共存回归，而非继续追求峰值。

### 11.8 第四次调试归档：合包生效，吞吐无明显收益，已撤回

#### 11.8.1 优化依据与范围

按用户要求继续探索同一 CDC 链路的吞吐空间，不引入其他 USB 类，不降低 CRC、模式或顺序校验，也不将 724.04 KB/s 当作硬件上限。前三次过程仍是已完成的历史记录，本节是第三轮优化、第四次调试候选，不预先宣称收益。

当前 DATA 帧有 20 字节头、有效负载和 4 字节 CRC。4096 字节负载对应 4120 字节帧；旧发送器每个队列项独立分包，256 字节分段后留下的 24 字节帧尾会单独提交。第三次日志平均每包约 63.38 字节，与存在短包的情况一致。已排队的下一帧可以与该帧尾共用一个 USB 包，CDF1 字节流本身不需要改变。

这只是值得验证的方向：减少包数不等于同等比例的有效吞吐增益，不能仅凭包长推算最终速度，也不能保证第四次必然超过第三次。

#### 11.8.2 候选实现与安全边界（历史记录，已撤回）

- usb_factory_cdc.c 中任务与 IN IRQ 共用流提交函数，每次仍只提交一个不超过 64 字节的包；最多查看三个相邻 stream 队列项，无循环等待、CRC、存储访问、日志格式化或应用回调。
- 常规满包直接使用原队列地址；跨片段包才在 64 字节局部缓冲中拼接。三个片段上限覆盖“前一项余量 + 24 字节帧尾 + 下一帧起始”情形，不扫描整个队列。
- 仅在驱动成功提交后推进队列偏移；拒绝提交不消费数据，违反驱动完整提交约定时撤销会话。保留单 DMA 缓冲忙检查、会话代际、超时、低水位通知和 RX 取消路径。
- 不跨非 stream 项合包。rdx_cdc_file.c 的 END（32 字节）和 ERROR（28 字节）通过普通队列接口独立发送，保持终止短包；接口名不表示内容必须是文本，二进制内容不变。不能将终止帧拼成满包后直接等待下一条命令。
- 不等待未来数据来凑满包：队列不足时立即发送已有数据，避免尾包或取消死等。文本回复及其 ZLP 行为保持原样。
- 新增 stream_join（本窗口成功跨队列项合包的提交数）和 stream_short（本窗口 stream 短包提交数）诊断计数；不含独立 END/ERROR，不与 bytes/packets 的完成口径混淆。
- 接收脚本遇到 invalid binary header 时，将期望 ID/偏移、原始 20 字节头、已缓存字节数和最多 32 字节后续内容写入原有错误报告；不额外读数据、不重同步、不自动重试或放宽校验。该改动用于留证，不宣称修复 18:04 异常。

#### 11.10.1 主机接收对照

原有 inline 模式保持默认：边读取、边解析/校验。新增 deferred 模式：先接收所有二进制帧到有界内存，再通过同一个解析器验证每帧 CRC、数据模式、连续偏移、传输 ID、END 总长度及文件 CRC；全部通过才报告成功或发布输出文件。接收阶段仍检查帧头、类型、ID、偏移和块长度，以识别终止/错误帧并限制内存占用；不是绕过协议的纯 USB 吞吐测试。内存上界由 MAX_SIZE、业务块数和每帧开销约束，不增加后台线程、不重同步、不自动重试。

- CDC-test.bat 菜单 3 中，原选项 1/2 为 inline 单轮/十轮，3 为原取消测试；新增 4/5 为 deferred 单轮/十轮。
- 命令行使用 `--mode file-bench --bench-receive-mode deferred`；底层 tools/cdc_file_transfer.py 的 bench 子命令使用 `--receive-mode deferred`。deferred 不支持取消，取消仍用原路径。
- 每轮 JSON 的 receive_mode 区分模式。原 elapsed_s、KBps、passes_600KBps 仍覆盖命令发出到完整校验/可选文件输出结束，口径不变。
- deferred 另报 receive_elapsed_s、receive_KBps（发命令到收到终止帧，分母包含 accepted 等启动时间）和 verification_s（后置校验及可选输出耗时）；仅完整成功后才把接收速率作为有效性能证据。
- capture_elapsed_s、capture_wire_bytes、captured_bytes 是接收诊断，不表示校验通过；错误仍记录 complete=false。deferred 的 steady_s/steady_bytes_per_s 留空，避免把内存回放当作 USB 稳态速度。

#### 11.10.2 固件续包抽样

当时诊断配置新增 TCFG_T2620_CDC_TX_TIMING_ENABLE，默认 1，仅在当时 MVP 与汇总日志均开启时计时；现已改为默认关闭，并由独立 STATS 开关控制，见第 0 节。需要无探针 A/B 时设为 0 后按统一命令 clean + all，量产不依赖此诊断。沿用 SDK jiffies_usec/jiffies_usec2offset，不占用额外硬件定时器。按 irq_fast 计数每 64 次续交抽样，记录 factory_cdc_tx_irq 关中断后到 cdc_factory_write_packet 返回的耗时；只统计成功提交。

每个 CDC_TX 汇总窗口额外输出一行 CDC_TX_TIME：gen、sample_every、samples、submit_us_sum、submit_us_max、clock_invalid。平均值为 submit_us_sum / samples（samples=0 时不计算）；负时间差只计 clock_invalid，不加入平均值。统计在任务中打印，IRQ 不格式化、不逐包输出。主机模拟回归覆盖计时开关两种配置，不能替代硬件计时精度验证。

该耗时包含状态检查、已有统计、64 字节以内拷贝、DMA 提交和部分计时开销；不包含硬件完成到回调被调度的中断响应延迟、不包含回调前的驱动处理，也不是总线包间隔或 CPU 占用率。抽样最大值不是所有包最大值，计时探针本身也可能扰动吞吐。若抽样耗时小而总速率不变，不能据此断言主机瓶颈；下一步仍需总线抓包或 GPIO/逻辑分析仪辨别 NAK、主机 IN 调度及真实中断延迟。
