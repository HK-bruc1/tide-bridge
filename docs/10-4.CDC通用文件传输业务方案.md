# 10-4. CDC通用文件传输业务方案

日期：2026-10-09（更新）
状态：CDC 通用文件传输基础设施已接入真实录音 LIST/GET、独立读取 worker 和菜单选文件。2026-10-09 实测同一 7,483,920 字节录音连续十轮全部完成且 CRC 通过，平均 636.36 KB/s；用户确认当前性能满足需求。独立原文件对照、至少 10 MB 基准及实机异常回归仍未完成。
最新结论：当前以基础设施整理为主，不强行统一 BLE/CDC 文件下载协议。真实录音实测见第 9.5 节；内存源历史基线仍为 2026-10-08 20:11 普通模式十轮平均 719.88 KB/s、后置校验模式十轮平均 718.18 KB/s，不能当作当前固件同环境对照或 CDC 理论上限。保留第三次 IN IRQ 有界续包，不保留跨队列合包。内存优化历史见第 11.11～11.13 节。
范围：受控主机上的传输基础设施、已保存录音只读下载及验证工具；不增加鉴权、BLE 登录或 DUT 前置步骤，量产稳定性仍待验收。

## 0. 当前实现与后续边界

本文前半部分包含设计与验收目标，不能理解为全部已通过实机验证。最新实现以本节、第 1.4 节、第 9.5 节及第 9.7 节为准；第 9.6 节为互斥实施基线，第 9.7 节记录本轮落地与实机步骤。第 9.1～9.4 节的软件验证和待测描述保留为对应阶段记录，第 11 节为内存测速历史，旧宏名、默认开关与待测状态仅描述当时构建。

| 层次 | 当前职责与边界 |
|---|---|
| USB 驱动 cdc.c | 原生 USB CDC 端点和非阻塞提交；文件流 IN IRQ 每次最多续交一包 |
| 传输层 usb_factory_cdc.c/h | 有界队列、背压、会话代次隔离、超时、低水位补货与二进制流发送；沿用已有文件名，不另复制一套驱动 |
| 通用入口 rdx_factory_cdc.c | 共用命令解析、来源日志与任务唤醒；产测命令仍复用既有 DUT；file 命令不要求进入 DUT |
| 文件协议 rdx_cdc_file.c/h | CAPS 查询能力，BENCH/LIST/GET 共用 CDF1 DATA/END/ERROR、CRC 与发送器，CANCEL 取消当前事务 |
| 录音源 rdx_cdc_source.c/h | 独立 `cdc_reader` 任务，两个 4096 字节缓冲，私有文件句柄；异步打开/读/关闭、取消与隔离 |
| 文件服务 rdx_record_format.c / 库补丁 | 复用 DAT/MTA/RAW 身份与格式校验；公共在途计数、下载占用及 DAT 缓存刷写交接 |
| 主机工具 | CDC-test.bat 菜单 3 → 6/7 自动列出设备录音，选序号下载单次/十次；复用 tools/cdc_file_transfer.py，真实文件只用 inline，deferred 仅供内存基准诊断 |

GET 已接入已有帧协议和流发送接口，不复制发送器，不修改 USB 驱动、IN IRQ 续交和低水位补货算法。文件资源独立于协议 generation，断线不会通过清零协议上下文丢失在途文件句柄。

正常开机且 CDC 已连接后，发送 `*APP#file#get#<sn>#<name>#` 加 CRLF 即可请求下载，不需要进入产测或先连 BLE。只保留文件身份/格式、存储冲突及关机清理保护；不引入登录、授权、配对或人为解锁。原产测适配层的本轮归属、格式、大小和 CRC 检查保持不变。

配置统一放在 SDK/apps/earphone/include/t2620_project_config.h：

| 开关 | 默认 | 作用 |
|---|---|---|
| TCFG_T2620_CDC_FILE_ENABLE | 1 | 通用文件协议与流发送基础设施；替代旧 TCFG_T2620_CDC_FILE_MVP_ENABLE，不提供旧名兼容 |
| TCFG_T2620_CDC_FILE_BENCH_ENABLE | 0 | 开发专用内存源测速入口；开启时要求 FILE_ENABLE=1，默认不受理 bench，空闲时返回 `*DEV#file#error#1#` |
| TCFG_T2620_CDC_TX_STATS_ENABLE | 0 | 可选 CDC_TX 性能统计，不影响发送算法 |
| TCFG_T2620_CDC_TX_TIMING_ENABLE | 0 | 可选 IRQ 续交抽样，要求 STATS=1；不是硬件中断响应时间 |
| TCFG_T2620_FACTORY_USB_CDC_LOG_LEVEL | 1 | 保留通用命令、生命周期及每次传输开始/终止入队摘要；禁止打印二进制负载 |

queued 仅代表终止帧已入发送队列，不代表主机接收或校验完成。性能统计与普通日志分离；不开性能探针也必须保留背压、低水位重武装、超时与生命周期保护。文件功能关闭配置保留原有产测路径。所有配置切换使用统一 clean + all。

内存测速通过独立编译门控管理，默认关闭；脚本保留开发入口（菜单 3 → 1～5），真实录音使用菜单 3 → 6/7。关闭 BENCH 不关闭 CAPS/LIST/GET/CANCEL、真实文件双缓冲或共享高速发送路径。传输中收到 bench 仍沿用忙请求延后拒绝规则，不向二进制流插入文本。性能诊断时显式开启 BENCH 并重新 clean + all，完成后恢复为 0；历史内存测速结果不代表默认固件仍开放该入口。

## 1. 后续真实文件业务目标与原始设计

CDC 是开机状态下的通用 USB 通道，产测只是其中一类业务。枚举不依赖 DUT、BLE 连接或 SD 健康，实际仍受 USB 角色、配置、主机连接和关机状态约束。

内存链路 MVP 已完成；后续真实文件阶段回答的问题是：**本设备从存储读取已保存录音，经 CDC 发送到电脑，能否持续达到至少 600 KB/s，并且数据完整正确？**

本轮不实现新的登录、鉴权、物理确认、加密、列表快照系统或正式产品 UI。它们不是性能实验的前置条件。上一版 200～300 KB/s 目标由本版 600 KB/s 目标替代；该数字在内存链路已通过，在真实文件路径仍是待验证门槛。

### 1.1 最小功能

1. 不进入 DUT，不要求本次先录音，不依赖 BLE 登录。
2. 选择一个已保存、已关闭且身份明确的测试录音文件。
3. 打开一次、顺序读取、二进制连续发送，电脑接收并保存。
4. 校验长度、顺序和 CRC，输出可重复的吞吐报告。
5. 支持取消、拔插、主机停读和错误后的资源回收。

### 1.2 明确后置

量产鉴权及隐私交互、加密、产品化列表分页、跨会话稳定 file_id、断点续传、删除/上传、自动下载后删除、产测接口迁移、BLE 协议改版、多传输并行均后置。当前补充只读 DAT 列表传输，仅用于工具选取已有录音。

真实文件验证阶段仅使用测试文件；通用基础设施当前默认开启，但不代表量产文件访问权限已开放。暂不鉴权是本次受控实验的范围选择，不代表量产可直接开放用户录音。仍禁止主机任意路径访问、越界读取和绕过关机。

### 1.3 真实录音接入：复用 BLE 文件业务，适配 CDC 传输（2026-10-09）

原则：复用已有录音文件的身份、元数据、定位及安全读取能力，不另建一套文件管理；通过已经验证的 CDC 通道发送同一文件内容。业务复用不等于直接调用 BLE 专用下载入口，也不等于两种传输的报文和调度已经相同。

本地证据 `BLE文件传输日志.log`（2026-10-08 15:43）显示：上位机先发送 `*APP#getlist#`、`*APP#listreq#...`，随后发送 `*APP#opusfile#0#3#1#0#0#` 并递增请求包号。固件日志包含 `rdx_protocol_handle_recordFileData_req`、`rdx_protocol_recordFileData_indicateByRequestNum_ble`，该文件大小为 1,403,120 字节、分为 58 个业务块，普通块数据量为 24,480 字节；读取侧使用持久化句柄和 49,152 字节缓存。这是 BLE 现有路径的证据，不代表 CDC 已接入或应该沿用这些块长。原始日志只作本地证据，不纳入源码提交。

| 层次 | 复用或适配决策 |
|---|---|
| 文件身份与元数据 | 沿用现有 DAT 索引和身份校验规则；通过 CDC 读取列表再选择已保存文件，不另建索引或分页系统 |
| 存储读取 | 优先复用已有定位、有效长度及只读打开能力；审核全局状态和句柄所有权后再决定直接调用或抽取公共辅助函数 |
| 生命周期 | 复用存储准入规则，补齐跨 BLE、CDC、录音、格式化和 MSC 的互斥；首期不支持两种媒介同时下载 |
| 下载语义 | 共用“选择同一文件、读取同一有效内容、取消与失败清理”的业务定义；不要求 BLE 登录或 DUT 状态 |
| 线上协议 | BLE 保持现有 getlist/listreq/opusfile；CDC 按第 5 节 GET/CDF1 设计接入，不在本阶段增加 opusfile 别名或改版 BLE 协议 |
| 发送调度 | BLE 保留原请求分块流程；CDC 保留连续供数、背压、有界 IRQ 续传，不机械照搬 BLE 的逐块请求往返 |

读取接口审核候选包括 `rdx_uxfile_get_file_data_by_sn()`、`rdx_uxfile_raw_read()`、`rdx_uxfile_close_read_file_handle()`，以及第 4 节已有的 `rdx_record_format_factory_open()` 相关能力。接口声明及日志不足以证明可安全直接复用；尤其需要确认是否依赖 BLE 全局下载上下文、是否修改共享游标，以及取消时是否可能关闭另一业务的句柄。若实现位于预编译库且无法核实，不盲目复用隐含状态；优先从可审查的现有只读路径抽取最小公共能力，保留原产测归属检查。不得复制整套 BLE 下载状态机或为了 CDC 删除既有保护。

实施顺序：

1. 审核文件定位、读取、关闭和存储准入接口，明确可复用部分与最小适配点；若与本方案冲突，先更新设计，不直接替换 BLE 发送函数。
2. 接入真实 GET 数据源，保持 CDF1、CRC、取消和 USB 发送算法不变；文件 I/O 在任务/worker 中完成，不在 USB IRQ 内读文件。
3. 在现有 CDC 测试脚本增加真实文件入口，保留内存基准；验证源文件身份、有效长度及接收内容一致，不能只凭 END 判成功。
4. 同环境比较内存源和真实大文件，回归 BLE 原下载路径及跨入口互斥，再验证取消、停读、断连和关机清理。真实文件至少 600 KB/s 仍是待验目标，内存源 700+ KB/s 不构成保证。

本阶段只统一文件业务与读取能力，不宣称 BLE/CDC 已共用完整协议解析入口。以后若需要统一上位机文件命令，应另行评审兼容性与封装，不与真实文件性能验证捆绑。

### 1.4 当前 BLE/CDC 差异、复用事实与维护决策（2026-10-09）

本节描述已接入实现；第 1.3 节中的接口候选与实施顺序保留为设计背景。准确定位是：**同一套录音文件体系，两套下载传输实现**。用户操作均为“获取列表 → 选择文件 → 下载”，不等于固件完整复用 BLE 下载状态机后仅替换发送函数。

| 对比项 | 现有 BLE | 当前 CDC |
|---|---|---|
| 列表命令 | `*APP#getlist#`、`*APP#listreq#...` | `*APP#file#list#` 加 CRLF |
| 下载命令 | `*APP#opusfile#...`，递增请求包号 | `*APP#file#get#<sn>#<name>#` 加 CRLF |
| 交互方式 | 沿用逐块请求/响应 | 一次 GET 后连续发送，下载中允许 CANCEL |
| 列表传输 | 原 BLE 列表请求与响应 | 刷写交接后读取现有 DAT，以 CDF1 传输 JSON；列表结束即释放占用 |
| 数据封装 | 既有 BLE 文件业务报文 | CDF1 DATA/END/ERROR、帧 CRC 与文件 CRC |
| 文件读取 | 原有 BLE 文件读取路径和共享读上下文 | 独立 `cdc_reader`、私有只读句柄和读取位置 |
| 缓冲 | 本地 BLE 日志显示 49,152 字节读取缓存、普通业务块 24,480 字节 | 两个 4096 字节读取缓冲，交给既有 CDC producer |
| 发送与生命周期 | BLE 请求包号、发送及连接清理机制 | 有界 USB 队列、背压、低水位补货、IN IRQ 有界续包；独立取消、代次隔离和关闭处理 |
| 业务前置 | 保持既有 BLE 应用流程，本轮不改版 | 无需 BLE 登录或 DUT；仍检查存储冲突、文件有效性和关机状态 |

上表中的缓存和业务块大小不是 BLE 空口包或 USB 端点包大小；BLE 数值来自第 1.3 节的实际日志，不是所有文件或版本的固定协议承诺。

复用必须区分数据、规则与代码，不能混称“流程全部复用”：

| 类别 | 当前事实 |
|---|---|
| 共用数据体系 | 使用已有 DAT 索引、MTA 元数据、RAW 录音及其 SN/名称/格式定义；不建立 CDC 专属录音库 |
| 复用基础能力并补充保护 | 沿用文件系统、存储供电和生命周期能力；补充公共下载占用、UXFILE 在途操作计数和 DAT 缓存刷写交接，不把 CDC 占用伪装成 DUT 会话 |
| 部分代码复用、部分新增 | 在 `rdx_record_format.c` 内复用 `rf_read_meta()`、`rf_open_verified_raw()` 等辅助能力；新增 `rf_read_index_identity()`、`rf_open_indexed_raw()` 和 `rdx_record_format_download_open()` 等通用下载入口，不宣称直接调用了 BLE 完整打开/读取流程 |
| CDC 独立实现 | `rdx_cdc_source.c` 管理自己的句柄、双缓冲和异步关闭；`rdx_cdc_file.c` 管理文件命令与 CDF1，不共享 BLE 下载游标、缓存或协议状态机 |
| CDC 内部复用 | LIST、真实 GET 与内存 BENCH 共用既有帧发送基础设施；LIST/GET 另外共用读取 worker、存储占用与资源清理，BENCH 不读盘 |

维护决策：**本阶段不再统一文件下载线上命令，不增加仅为外观一致的 BLE 命令别名，也不为统一交互将 CDC 改成逐块请求。** 已统一的产测命令和共享 DUT 入口保持不变，不能套用来说明通用文件下载已共用协议。后续只有发现实际重复业务逻辑或规则分叉时，才针对性抽取公共能力；不为抽象而共享句柄、游标或会话。保持 BLE 既有行为与 CDC 已验证发送路径，协议差异明确记录即可。

两种媒介指向同一录音文件，不自动证明实际导出的有效字节范围完全一致；仍需去掉 BLE 传输封装后，用独立 RAW 对照验证，见第 9.5 节。

## 2. 基线与已有证据

### 2.1 BLE 对照

本地日志 COM3_2026-10-08_15-43-01.log 的摘要：

| 项目 | 结果 |
|---|---|
| 文件有效长度 | 1,403,120 字节，第 761 行 |
| 常规应用层文件块 | 24,480 字节，第 768 行，不是单个 BLE 空口包 |
| 固件统计耗时 | 15,127 ms，第 1590 行 |
| 平均吞吐 | 92.76 KB/s，约 90.58 KiB/s |

这是固件发送过程计时，不包含电脑端最终落盘；原始日志不要求提交仓库。CDC 达到 600 KB/s 约为此参考吞吐的 6.47 倍，但不同计时口径不可直接当作正式倍速结论。

### 2.2 改造前限制与接入参考（历史基线）

下表记录内存链路优化前的问题，不代表当前发送器仍存在这些限制。通用流发送、IRQ 续包、背压下控制接收和菜单 3 已完成；真实文件读取及其占用管理本轮已接入，见第 9.3 节。不得据此重新实现已验证的 USB 调度。

| 代码位置 | 已确认限制 | MVP 改造方向 |
|---|---|---|
| SDK/apps/common/device/usb/device/cdc.c | 串口波特率只保存/打印；当前发送不按波特率限速 | 不靠调整波特率提速 |
| SDK/apps/common/device/usb/device/usb_factory_cdc.c | 每次调度最多提交 64 字节；忙时主要由 2 ms 定时器推进 | 验证完成事件驱动的连续续发 |
| SDK/apps/common/device/usb/device/usb_factory_cdc_internal.h | TX 队列深度 4，端点包长 64，传输超时 2 秒 | 有界缓冲、保留 DMA 生命周期和超时 |
| SDK/apps/common/device/usb/device/usb_factory_cdc.h | 单次全量复制入队，最大 258 字节 | 增加有界的大块传输适配，不能只改长度常量 |
| SDK/apps/common/third_party_profile/rdx_protocol/rdx_factory_cdc.c | 10 ms app_core 服务；应答堵塞时停止后续解析 | 数据供给事件驱动，取消入口不受 TX 堵塞影响 |
| SDK/apps/common/third_party_profile/rdx_protocol/rdx_factory_audio.c | 每块 80 字节、十六进制编码、绑定本轮产测录音 | 通用下载独立于产测实例，使用二进制连续流 |
| SDK/apps/common/third_party_profile/rdx_protocol/rdx_record_format.c | factory_open 要求产测 file_busy；文件不超过 40,000 字节；打开时扫描 CRC，每 240 字节让出调度 | 拆分公共校验/打开能力，通用路径不使用产测限制 |
| CDC-test.bat | 产测文件下载每块 FILE_READ 后等待再请求 | 保留产测流程，新增菜单 3 调用共享 MVP 接收模块 |

64 字节 / 2 ms 对应约 32 KB/s 的定时推进量级，不是 USB CDC 上限，也不是严格软件硬上限。当前产测版速度不能用来判断优化版能否达到 600 KB/s。

### 2.3 CDC 波特率不限制当前 USB 文件传输速度

**当前实现保持主机串口参数 `115200` 即可；调高波特率不会据此提高 CDC 文件传输速度。** 波特率是 CDC 虚拟串口的配置参数，不是 USB 链路速率，也不是当前文件发送路径的限速值。

- 主机测速工具 `tools/cdc_file_transfer.py` 的 `--baud` 默认值为 `115200`。2026-10-08 报告 `output/cdc-file-reports/20261008-201408-133096-file-bench.json` 记录 COM6、baud=115200，普通模式十轮平均 719.88 KB/s，全部长度、数据模式与 CRC 校验通过；这是内存源结果，不代表真实录音文件读取速度。
- 固件 `SDK/apps/common/device/usb/device/cdc.c` 处理 `USB_CDC_REQ_SET_LINE_CODING` 时仅保存并打印参数，没有根据波特率调整 USB 发送时钟、端点包长或续包调度。初始化的 `dwDTERate=460800` 也是默认串口参数，不是发送速率上限。
- 当前数据直接通过 USB 端点发送，不经过按该波特率发送的实体 UART。因此改成 `921600` 或 `2000000` 不会改变现有文件传输执行路径，不能套用实体 UART 的波特率换算解释约 720 KB/s 的结果。
- 本项目约 450 KB/s 到 700+ KB/s 的主要提速来自文件流 IN 中断有界续包，而非提高波特率。后续性能分析应关注端点续包、任务/中断调度、主机读取及数据源供给。

可以把当前路径理解为：电脑串口 API → CDC 驱动 → USB Bulk 端点 → 固件业务。COM 口是软件接口，不是一个按 115200 发送的实体串口；没有将每个字节转换为 UART 起始位、数据位、停止位再传输的环节。CDC 转实体 UART 的桥接设备才会受到后级 UART 速率约束。

此结论限定于本项目当前实现，不泛指所有 CDC 设备；若以后增加 CDC 转实体 UART，或业务主动根据波特率限速，应重新评估。报告保留 baud 字段用于环境记录，不作为 USB 实际枚举速率证据。COM3 固件日志口与本次 COM6 文件传输口是两个不同用途的端口。

## 3. 600 KB/s 的预算与判定口径

### 3.1 单位和速率预算

本文 600 KB/s 明确定义为 **600,000 个文件有效字节/秒**，约 585.94 KiB/s；不把串口波特率、编码后长度或瞬时峰值作为有效吞吐。

以现有 64 字节端点包长计算，仅有效载荷就要求平均约 9,375 个包/秒，相当于每毫秒约 9.4 个包，尚未计入应用帧开销。因此：

- 每 2 ms 只提交一包肯定不能支撑目标。
- 把周期改成 1 ms 但仍只发一包也不能支撑目标。
- 必须验证驱动完成通知、持续续发以及上游数据供给能否跟上。
- 这只是预算推算，不证明 JL 控制器、驱动、存储和调度实际支持目标。

目标数据量约为每 10 ms 6,000 字节。现有 4 × 258 = 1,032 字节队列若只每 10 ms 填充一次，即使瞬间排空，供给量也仅约 103.2 KB/s，仍远低于目标。不能只优化 USB 包发送而保留低频补充队列。

开始实验前在电脑确认实际枚举速率、Bulk 端点和驱动信息；不凭“USB 2.0”名称推断速率。600 KB/s 是否可达由下面的分层实验决定。

### 3.2 三种测量，不能混为一谈

| 测量 | 计时范围 | 用途 |
|---|---|---|
| USB 内存源 | 主机收到首个数据帧到完整 END，另记录设备发送耗时 | 验证传输层上限，不作为文件业务通过证据 |
| 真实文件稳态 | 首个数据帧到完整 END，含接收期间的文件写入及在线校验 | 定位持续读取/发送性能 |
| 真实文件端到端 | 主机发出 GET 到校验通过、输出文件关闭 | MVP 600 KB/s 的正式判定口径 |

使用单调时钟；另外记录 OPEN/首字节延迟、设备读取时间、排队等待和关闭耗时。普通文件关闭不等于物理介质持久化；首轮不要求 fsync，若启用需在报告中明确并单列结果。

### 3.3 通过标准

- 主验收采用至少 10 MB 的合法已保存测试录音，连续独立下载至少 10 次。
- 每次端到端有效吞吐均不低于 600 KB/s，全部长度、顺序和 CRC 正确；报告均值、中位数、最小值、最大值及失败次数。
- 文件预计耗时可用 size / 600000 检查，例如 10,000,000 字节对应约 16.67 秒端到端预算。
- 1,403,120 字节文件用于 BLE/CDC 同文件对照，不以短文件或局部突发峰值替代大文件持续验收。
- 只有 USB 内存源达到目标，结论只能是“传输层可达”；真实文件不达标必须继续定位或明确报告未通过。
- 若仅稳态达到 600 KB/s 而端到端未达到，应同时报告两个结果，不标记 MVP 达标。

至少用一次独立基准读取或已知内容验证测试文件 CRC，防止固件发送错误内容却用同一错误数据计算 CRC 而被误判通过。CRC 不替代音频可解码检查。

实施检查点分开报告，不要求第一轮实验一次完成正式验收：

| 检查点 | 最小证据 | 允许的结论 |
|---|---|---|
| 链路可行 | 内存源持续发送至少 10 MB，校验正确，测量速度与余量 | 仅传输层达到目标，未证明文件业务 |
| 业务初证 | 一个真实历史录音完整下载，记录稳态及端到端速度 | 文件路径已打通；小文件或单次结果不是正式通过 |
| 正式通过 | 至少 10 MB 真实录音连续独立下载 10 次及异常回归 | 满足本节全部标准后认定 MVP 达标 |

## 4. MVP 架构：保留现有层次，最少新增业务

USB 层继续独占端点 I/O 和 DMA，app_core 处理控制状态，文件 worker 做阻塞文件 I/O。不在 ISR 做文件读取、CRC 扫描和打印，不绕过统一发送路径直接调用 cdc_write_data()。

本轮在已有文件协议中新增真实录音与 DAT 列表数据源，并扩展现有电脑工具，不另建发送器或接收器。工具先通过 LIST 取得现有文件索引，操作员选择序号后自动把 SN/名称传给 GET；设备再次按当前索引和元数据确认同一文件。不建设新的长期文件标识系统，显式传入 SN/名称的命令行方式仍保留。

### 4.1 拆开公共文件能力与产测约束

从 rdx_record_format_factory_open() 抽取或复用身份校验、格式校验、只读打开及有效长度获取逻辑，不直接删掉原函数的产测保护。

- 产测适配层继续校验本轮录音归属、file_busy 和原有大小/格式规则。
- MVP 通用适配层接受明确的历史已保存文件，不受产测 40 KB 上限限制。
- MVP 首期仅支持可可靠识别的既有有效录音格式，未知或不完整文件明确拒绝；最大文件大小和偏移字段按第 5.4 节执行。
- 通用打开不全文件预扫 CRC；校验必要元数据后顺序读取，一边发送一边累计 CRC，结束报告。
- 原扫描里的逐 240 字节延迟不能直接搬入高速路径；改为有界块读取及合理让出调度，不能用忙等换吞吐。

FILE_BUSY 必须是公共文件服务占用而非伪造产测状态。先取得占用，再校验身份并打开，关闭完成才释放；禁止打开失败后回退到最新文件。

#### 4.1.1 首期格式与内容范围

首期以现有可审查只读路径支持的 `RECORD_FORMATE_OPUS_16K_MONO` 已保存录音为候选；必须先核实目标历史录音的元数据与实际格式一致，再开放 GET。未知格式、未完成录音、身份不匹配或无法确定有效长度的文件明确拒绝，不为测速猜测格式或修复文件。

- GET 维持 `SN/name` 参数，不增加主机任意路径或偏移。取得公共占用后，以当前有效 DAT 索引核实管理 SN/名称，再按名称、start、格式、元数据完整性与首帧指纹绑定 RAW。恢复流程可能重分配 DAT SN 而不重写 MTA，不能要求通用 GET 的 SN 无条件等于 MTA SN，也不能忽略索引只按名称打开。产测仍严格匹配本轮 SN/start，不取消原产测校验。
- MTA 的 `ready=1` 表示首帧指纹已持久化，**不表示录音已经结束或保存成功**。通用 GET 还须通过现有录音停止/收尾状态、索引交接和公共占用确认文件已关闭；不能把 ready 当作完成标记。
- 打开结果必须固定本事务的文件身份、物理读取起点和有效长度。CDF1 的 offset=0 表示首个有效录音字节，不自动等同于磁盘文件偏移 0；仅当审查确认 RAW 全部字节都是有效录音内容时，才使用 RAW 起点 0 和文件长度。
- 实施前核实 BLE 是否剥离文件头、跳过预留区、裁剪尾部或转换内容，明确 CDC 应输出的同一有效字节范围。不得仅凭扩展名、`flen()` 或 BLE 日志中的长度推定一致；不能确认时先停止该格式接入并更新设计。
- 首期不转码、不增加音频封装，也不携带 MTA/DAT 等索引元数据。长度对齐规则来自已核实的录音格式，不能照抄产测的 40 KB 上限或仅删除上限后默认历史录音都适用。
- 按固定有效长度顺序读取；提前 EOF、读取错误或检测到文件变化均失败，不用实际收到的较短长度生成成功 END。主机以独立基准验证长度和内容，BLE 对照应先去掉 BLE 传输封装，再逐字节或计算同范围摘要比较。

接口审核交付须记录“支持格式、身份校验来源、物理起点、有效长度来源、BLE 内容映射”五项。暂不能核实的项目标为阻塞项，不将本节候选约定写成已实现能力。

### 4.2 最小互斥不能后置

实验时仅下载一个文件，不并行录音、播放、BLE 文件下载、删除、格式化、包装和 MSC。入口检查和实验环境约束都要明确，不能仅靠操作员承诺不存在并发。

盘点现有公共准入机制，将新的下载占用纳入原有冲突检查；不能只在 CDC 入口检查别人，其他入口却能中途修改文件。BLE/HOGP 连接可保持；系统任务及关机保持响应，不开展并发性能优化。

拔插、超时和取消停止新生产，异步关闭句柄，关闭失败保留隔离状态。DIP OFF 不等待主机确认、不被文件服务否决，DMA 回收仍走原生 USB 生命周期。

#### 4.2.1 公共占用落点与双向检查

现有 `rdx_storage_lifecycle_business_blocked()` 查询文件服务、索引恢复与存储状态，不是可直接调用的完整占用申请/释放接口。本轮应在可审查的公共文件服务边界补齐最小所有权机制；不另建索引管理器，不直接把 `service_ready()` 当作可覆盖其他状态的互斥锁。

| 阶段 | 必须落实的行为 |
|---|---|
| GET 准入 | 在统一串行控制点或等效同步保护下，检查现有冲突并取得 CDC 事务占用；检查与取得不可被其他入口穿插。普通冲突返回 BUSY，存储不可用或隔离返回 UNAVAILABLE，不启动打开 |
| 占用期间 | BLE 下载、录音、播放、删除、格式化、产测文件业务、包装及 MSC 切换的相关入口必须反向检查；不能只在 CDC 侧检查别人 |
| 正常释放 | worker 确认文件及相关资源全部关闭后，由匹配事务的控制路径释放一次；保留存储既有故障状态，不无条件置为就绪 |
| 异常释放 | 打开失败也需确认无残留句柄；在途 I/O、迟到打开或关闭失败时保留占用/隔离，不能因串口重开释放 |

实施前列出上述各冲突入口的实际函数、现有保护及本轮最小改动；预编译库入口也必须找到可控的外层准入点。无法保证双向互斥时，不开放真实 GET，不能以操作员避免并发替代保护。允许 BLE/HOGP 连接保持，不等于允许 BLE 文件下载并发。

### 4.3 异步文件资源与串口会话分离

当前内存源在 `rdx_cdc_file_session()` 的 generation 改变时清空流上下文；真实文件接入后不能用同一次清零丢失仍在 worker 中使用的句柄、缓冲和占用。保留协议流的代次隔离，但文件资源必须有独立、可追踪的事务生命周期。

| 对象 | 所有者与释放边界 |
|---|---|
| 事务身份与公共占用 | 控制路径维护 generation、transfer_id 及内部事务标识；仅匹配事务可推进/释放，串口重连不等于旧事务清理完成 |
| 打开、读取、关闭与 FILE 句柄 | 文件 worker 串行执行；控制任务只提出停止请求，不并发 fclose 或强制中断正在执行的文件调用 |
| 读取缓冲 | 明确 FREE/READING/READY/CONSUMING 等等效所有权状态；读取返回且消费者不再引用后才能复用 |
| CDF1 帧及 USB 队列 | 沿用现有有界复制、背压及 DMA 生命周期；已部分提交的帧按第 5.2 节补齐，不能提前覆盖其未提交部分 |

事务状态和传输收尾分别跟踪：OPENING → STREAMING → CLOSING，资源确认释放且终止帧完成发送后才重新接纳 GET；传输失效则等待原生队列清理和文件资源回收。失败隔离不能直接转为 IDLE。

- 取消或断连立即禁止新读取；正在执行的调用允许返回，但结果只归属于旧事务。
- 迟到的打开成功只用于关闭；迟到的读取结果丢弃并清理，不产生新 DATA，不改变新连接状态。
- 旧资源回收前，新连接可以枚举，但不得启动新的文件事务；关闭失败或操作未返回时按第 5.3 节保持隔离。DIP OFF 仍由原生关机处理，不等文件看门狗到期。
- 文件系统阻塞调用不能承诺被超时强制打断。控制任务维护超时与停止标记，worker 返回后执行匹配事务的清理，不能通过清零上下文假装释放成功。

host 行为测试必须覆盖取消发生于打开/读取/关闭、generation 切换后迟到完成、关闭失败、新请求被拒绝及旧资源最终释放；同时验证每个句柄和占用最多释放一次、旧结果不进入新流。

## 5. 通用线协议与真实 GET 接入约定

CAPS、BENCH、CANCEL 和 CDF1 沿用原基线；GET 已接入真实文件打开、读取、关闭及隔离。APP 统一表示上位机，来源在日志及会话中单独标记。第 5.4 节保留两端共同采用的线格式，本轮复用既有黄金向量与解析测试，新增 GET 行为测试，不重新定义协议。不以正式量产协议的完整性阻塞性能验证。

### 5.1 保留文本命令，能力查询无副作用

请求使用 ASCII + 实际 CRLF，维持现有命令长度上限。建议：

| 命令示例 | 作用 |
|---|---|
| *APP#file#caps# | 只查询 MVP 版本、块长、最大文件及忙闲状态，绝不切换模式 |
| *APP#file#list# | 异步读取现有 DAT 索引，以同一 accepted/CDF1/CRC/END 链路发送 UTF-8 JSON 数组 |
| *APP#file#get#<sn>#<name># | 校验并打开指定文件，异步开始一次连续二进制下载 |
| *APP#file#cancel#<transfer_id># | 取消当前传输 |

LIST 是独立只读事务，结束后释放占用，GET 时重新校验身份；不新增 OPEN/START 两阶段交互、FINISH 确认或永久二进制会话模式。首期不做断点续传，失败后重新 GET，不盲目重发状态未知的请求。

GET 通过公共准入后，先返回完整文本受理行，包含 transfer_id 和版本；拒绝则只返回文本错误、不切换。受理后直到终止帧，设备到主机仅发送 DATA、END 或 ERROR 二进制帧，文件打开失败也通过 ERROR 终止该事务。

文本受理行和第一个二进制帧通过同一有序发送器交付，允许同一次主机 read 收到两者，主机按行边界切换解析而不按 read 边界猜测。旧待发应答必须先排空，旧产测实时流/文件业务活动时拒绝 GET，不允许旧业务输出插入文件帧。

END/ERROR 是明确的事务结束边界，之后恢复普通文本应答。主机到设备仍为文本；下载中仅处理 CANCEL，其他新请求记录为拒绝且不产生插入流中的文本响应，待终止帧后按既定顺序回复 BUSY。待处理控制数量有界，超额输入使会话失败，不无限积压。

### 5.2 二进制帧与不可交错规则

最小字段：魔数、版本、类型、transfer_id、offset、payload_length、payload、CRC。类型仅 DATA、END、ERROR。帧头固定大小，字节序、CRC 覆盖范围及上限按第 5.4 节执行并用黄金向量验证；不直接发送 C 结构体。偏移与有效长度严格连续，不需要再维护与偏移重复的包序号。

DATA 携带原始文件字节，不做十六进制或 Base64。END 携带实际总长度与完整文件 CRC；ERROR 携带失败原因。主机必须处理拆帧、粘帧、非法长度、错偏移、CRC 错和提前 EOF。

统一发送器持有一个当前应用帧；拆成多个队列元素后不能被其他帧/文本插入。队列满只暂停续交，不从头重发已有分片。正常取消停止预读，在完成当前应用帧后发 ERROR(CANCELLED)，然后回到文本；若主机不再读取则超时终止会话，不尝试无限等待半帧收尾。

取消时按提交边界处理，不把“当前帧”等同于正在组装的帧：

- 尚未向底层提交任何字节的帧及预读数据可丢弃；已发起的文件读取允许返回，但结果不再生成新帧。
- 已部分提交的应用帧必须补齐剩余字节与 CRC；已完整入队的帧保持原顺序排出，不能跳过或重发。
- ERROR(CANCELLED) 排在全部保留帧之后；正常取消不清空底层队列，不提前释放在途 DMA 或未完成读取使用的缓冲。
- 停止新生产、句柄关闭和终止帧送达分别记录。正常关闭完成后发送终止帧；关闭失败则进入隔离，不能伪装为可重试的取消成功。
- 无法收尾时使会话失效，禁止在残缺二进制帧后直接恢复文本；队列废弃及 DMA 回收仍走原生传输清理路径。

拔插/会话失效可直接中止半帧并丢弃旧队列，主机废弃本次临时文件。transfer_id 绑定 generation，旧命令及回调不得作用于新连接；同一事务 CANCEL 幂等，错误 ID 不取消其他事务。

### 5.3 完成与失败

正常状态：IDLE → OPENING → STREAMING → CLOSING → IDLE；资源归属无法确认或关闭失败时进入 QUARANTINED 隔离状态，不无条件返回 IDLE。文件读取结束后先完成资源关闭，正常关闭后再发送 END；失败则在可保持完整帧边界时发送 ERROR。终止帧尚未完成发送前不接纳下一次 GET。

设备日志“发送结束”只代表设备侧完成，不能声称主机已保存。**MVP 成功以电脑工具收到 END、长度/CRC 校验通过且输出文件关闭为准**，无需为性能实验新增主机 FINISH 握手。

保持现有底层 2 秒无发送进展超时；MVP 工具读取超时初始设为 5 秒，打开超时初始设为 10 秒，单次实验总时限初始设为 120 秒。支持文件上限需与总时限匹配。主机停读超过底层容忍期允许失败并重建会话，不承诺暂停续传。反复无效命令不得刷新有效进展时钟。

底层超时仅覆盖有待发或在途数据的情况，不能替代设备业务看门狗。业务计时由不执行阻塞文件 I/O 的控制任务维护，初始预算如下；这些值是待实测的 MVP 参数，不代表底层文件系统支持强制中断：

| 状态/操作 | 有效进展与初始预算 | 到期处理 |
|---|---|---|
| OPENING | 从受理至打开完成最多 8 秒，不因控制命令刷新 | 标记事务失效；晚到句柄只用于关闭，不启动发送 |
| STREAMING 读取 | 每次已发起读取最多 3 秒；等待空闲缓冲不算读取执行 | 停止新生产，等待在途调用退出并清理 |
| CLOSING | 从发起关闭至返回最多 3 秒 | 进入隔离，保留句柄/缓冲所有权，不强制复用 |
| 整个事务 | 从受理起最多 110 秒，不因局部进展延长 | 停止生产并进入失败清理；主机总时限仍为 120 秒 |

恢复规则：

- 普通拒绝，或资源已回收且完整 ERROR 已送达：可以在同一串口会话重新 GET。
- 半帧、发送超时或传输失效：主机废弃临时文件，关闭重开串口并清理接收解析状态；通过新 generation 和 CAPS 确认就绪后再试，不能在旧流中搜索魔数继续。
- 文件操作未返回或关闭失败：重新打开串口不解除公共文件占用。保持隔离，迟到操作返回后仅执行清理；只有能确认资源全部释放才恢复，否则需要设备恢复/重启。
- 工具超时不代表设备已清理；隔离期间文件请求返回不可用。DIP OFF 仍按原生关机执行，不等待上述预算，不强制释放仍被 I/O 或 DMA 使用的内存。

### 5.4 阶段 A 最小线格式约定

本节仅冻结开发 MVP v1，不承诺量产兼容。文本均为 ASCII，末尾为实际 CRLF，数字使用无符号十进制；名称沿用既有合法文件名校验，拒绝分隔符、路径和超长输入，不引入转义规则。

| 项目 | MVP v1 约定 |
|---|---|
| 能力回复 | `*DEV#file#caps#1#8192#16777216#<state>#`，依次为版本、最大 DATA 负载、最大文件字节数及状态 |
| 开发内存源启动 | 仅 `TCFG_T2620_CDC_FILE_BENCH_ENABLE=1` 时开放；`*APP#file#bench#<size>#<block>#`；size 为 1～16,777,216，block 仅 1024/2048/4096/8192，尾块可更短 |
| GET/bench 受理 | `*DEV#file#accepted#<transfer_id>#1#`；后续按二进制解析，bench 同样使用 CANCEL 终止 |
| 文本拒绝 | `*DEV#file#error#<code>#`；CAPS 的 state 为 IDLE/OPENING/STREAMING/CLOSING/QUARANTINED |
| transfer_id | 非零 u32，设备运行期间单调分配并绑定当前 generation；跨连接不重用，耗尽拒绝新事务，重启后主机必须清空旧会话 |
| 二进制帧头 | 固定 20 字节：magic[4]、version:u8、type:u8、header_length:u16、transfer_id:u32、offset:u32、payload_length:u32 |
| 固定值与字节序 | magic 为 ASCII `CDF1`（43 44 46 31），version=1，header_length=20；多字节整数均小端 |
| 帧类型 | DATA=1、END=2、ERROR=3；DATA 负载 1～8192 字节，offset 从 0 起连续累计有效文件字节 |
| 帧尾 | u32 小端 CRC，覆盖完整 20 字节帧头及负载，不含帧尾自身；最大整帧 8216 字节 |
| END 负载 | total_size:u32 + file_crc:u32，共 8 字节；头部 offset 等于总有效长度 |
| ERROR 负载 | code:u32，共 4 字节；头部 offset 等于此前完整保留 DATA 的累计有效长度，不含丢弃的预读数据 |
| CRC 定义 | CRC-32/ISO-HDLC：poly=0x04C11DB7，refin/refout=true，init=0xFFFFFFFF，xorout=0xFFFFFFFF；文件 CRC 只覆盖顺序原始字节 |
| 基础错误码 | 1=BAD_REQUEST、2=BUSY、3=NOT_FOUND、4=INVALID_FILE、5=IO_ERROR、6=CANCELLED、7=TIMEOUT、8=UNAVAILABLE、9=BAD_TRANSFER_ID |

GET 不增加块长参数，初始采用 4096 字节；实验固件可调整候选块长并在报告中记录，接收器按实际 payload_length 解析。文件有效大小上限为 16 MiB（16,777,216 字节），零长度拒绝；按 600 KB/s 约需 28 秒，低于总预算，但低速或停滞实验仍可能超时。后续若调整上限，必须同步 CAPS、边界测试和超时预算。

内存源第 offset 个字节为 `offset & 0xFF`，在线生成，不占用整文件 RAM。阶段 A 开始时先提交两端共享黄金向量：空内容 CRC=0x00000000、ASCII `123456789` CRC=0xCBF43926，以及完整 DATA/END/ERROR 帧的逐字节样例与期望 CRC；先用独立实现交叉验证再进行实板测速。文件 CRC 按完整流累计，不能把分块 CRC 简单相加。

下载中 CAPS 与其他非 CANCEL 请求同样按第 5.1 节延后拒绝，不插入文本。错误 transfer_id 的 CANCEL 不影响当前事务，按同样边界延后回复 BAD_TRANSFER_ID；重复有效 CANCEL 不重复生成终止帧。bench 仅开发配置可用，不新增独立停止协议。

## 6. 数据通路基线与真实文件验证

### 6.1 已完成：USB 内存源基线

开发配置下使用可验证的内存模式数据，至少发送 10 MB，总大小不要求驻留 RAM。使用与文件模式相同的二进制封装和电脑接收器，校验固定模式、长度及 CRC。

内存源已达到 700+ KB/s，沿用 IN IRQ 每次单包续交、低水位补货、背压和超时保护，不重做驱动完成通知或恢复已撤回的跨队列合包。端点忙即退出，不能在任务或中断中忙等等待主机。

接入真实文件后，同环境回归内存源，比较约 700+ KB/s 基线及完整性，而非仅看是否仍超过 600 KB/s。若内存源明显回退，先定位本轮改动，不靠放大文件缓冲或降低验收标准掩盖问题。

### 6.2 第二关：存储读取实验

在公共文件占用保护下，对同一合法文件做只读顺序读取，测量纯读取和读取加 CRC 两种速度及每块延迟，不发送 USB。

以 4 KB 块为起点，测 1/2/4/8 KB 候选；缓冲总量根据链接 map 和实测可用内存确定，不默认可以无限增加。读取加 CRC 达不到 600 KB/s 时，先检查存储、文件访问和逐块让出调度，再做集成。

读取速度和 USB 速度单独达到目标仍不代表组合通过；两者会争用 CPU、内存和任务时间，需要留余量并实测流水线。

### 6.3 第三关：真实文件流水线

初始候选为两个 4 KB 缓冲：一个读入，一个发送，文件 worker 的完成事件和发送队列腾空事件推进生产，不依赖每 10 ms 才补一次数据。8 KB 仅是文件负载缓冲候选，不包含帧头、USB 队列和任务栈，需报告实际总 RAM 增量。

先使用所有权清楚的有界复制实现，测量 CPU 与吞吐后再考虑减少复制；不把零拷贝作为 MVP 前置条件。若采用缓冲引用，直到 USB 完成才归还，断线清理不得提前复用 DMA 使用的内存。

底层仍按 64 字节端点包长提交，任务和开发配置的流式 IN 中断共用该约束；应用层 4 KB 不等于 USB 单包 4 KB。不能只扩大 FACTORY_CDC_TX_MAX 而不审查队列内存、临界区复制长度、短包和 ZLP 行为。

### 6.4 控制接收不能被发送堵塞锁死

内存源基础设施已具备背压下的控制接收和取消处理。本轮将其延伸到真实文件 worker 的停止与清理，不重新实现一套控制通道。须保持并回归：

- 独立保留有界 RX 控制缓冲，TX 满时仍可接收 CANCEL。
- 文件模式下可处理取消，不因待发应答占满而停止控制解析。
- 接收取消后立即停止新读取，取消应答发送失败不影响本地停止与清理。
- 正常主机持续读取时，取消至停止新生产的目标为 100 ms 内；需实测并记录最坏值。终止帧送达与句柄关闭分别计时，不能混作同一指标。

## 7. 电脑 MVP 工具与日志

tools/cdc_file_transfer.py 维护唯一的通用文件二进制接收器，主机端支持 caps/bench/download。CDC-test.bat 菜单 3 的子选项 6 为真实文件接收入口，内部直接调用该模块，保留内存基准和取消测试，不复制协议实现，不运行普通产测/DUT 流程，也不先打开第二个串口。**本轮 GET 已接通，烧录新固件后即可用该入口验证，实机速度待测。**

菜单工具只需输入 COM 口和文件序号，自动获取 SN/名称并生成输出路径；命令行仍可显式指定文件身份、输出及独立对照文件。通过显式开发命令启动内存源测试，量产配置不暴露 bench。串口波特率保持默认 `115200` 即可，无需专门进行不同波特率对照；当前实现不按此参数限速，依据见第 2.3 节。

接收器连续读取、增量拆帧、在线 CRC，采用有界缓冲；先保证电脑消费端明显不构成瓶颈。不逐个 USB 包打印或逐块 flush，进度输出最多每秒一次。写入临时文件，校验与关闭成功后再改为最终文件名；设备名称不直接拼接为任意本机路径。

生成 JSON 报告：固件版本、协议版本、OS/驱动、USB 实际速率和连接拓扑、文件身份及大小、块长/缓冲量、各阶段耗时、每轮速度、CRC、失败原因和取消结果。

固件保留 [CDC_RX] 控制命令日志，不打印文件负载；记录开始/结束、长度、CRC、队列高水位、读延迟、端点空闲和错误。测量使用量产级日志密度，另做关闭非必要日志对照，不将现有 app_core timer_no_response 当作可忽略噪声。

本轮固件烧录后，命令行入口如下；示例 SN/名称必须替换为实际索引，不能直接照抄：

```powershell
python -X utf8 -x CDC-test.bat --port COM6 --mode file-download --file-sn 7 --file-name abc123.raw --bench-repeat 10
```

可选 `--file-output` 指定新输出路径，默认与本轮报告同目录同名、扩展名为 `.raw`；多轮文件添加 `-1`、`-2` 等后缀。`--file-reference` 指向独立取得且去掉 BLE 封装的 RAW，按块逐字节对照；`--file-cancel-after 1048576` 在收到约 1 MiB 后请求取消。目标文件或 `.part` 已存在时拒绝覆盖，失败保留 `.part` 供排查，不生成成功文件，也不自动重试。

真实接收模式不预设总长度或要求固定 DATA 块长；逐帧限制 8192 字节，累计限制 16 MiB，最终要求 END 的长度、CRC 与接收结果一致，且符合首期 mono 40 字节帧对齐。报告区分 `crc_ok`、`reference_match`、每轮 SHA-256、`passes_600KBps` 与十轮吞吐结果；无独立对照时 `reference_match=null`，不能写成内容对照通过。小文件完整下载仍会返回未满足性能目标的退出码。`real_file_acceptance` 继续为 false，因为脚本无法代替解码、资源清理和异常实机验收。

### 9.3 阶段 B 接线：真实录音 GET（2026-10-09）

### 9.6 应用集成与跨业务互斥实施方案（2026-10-09）

本节是下一阶段实施基线，不代表下列入口整改及实机竞争测试已经完成。性能满足当前需求，后续优先完善资源互斥、冲突反馈和异常收尾，不修改 USB 高速发送路径，不强行统一 BLE/CDC 下载线协议。

#### 9.6.1 产品边界与原则

CDC 文件传输将集成到应用，用户在应用内已经完成登录鉴权。本阶段不再给 CDC LIST/GET 增加 BLE 登录、绑定、DUT 或额外鉴权前置条件。应用登录仅控制应用访问，不等价于设备端 CDC 已完成鉴权；直接连接串口仍可发送当前开放指令，这是本阶段明确接受的边界。

采用“连接共存、冲突资源串行、先到先服务”的策略：

1. CDC 枚举、串口连接和 BLE 连接本身不占用文件业务资源；只有实际 LIST/GET 才申请存储占用。
2. 已开始的业务继续运行；后来到达的冲突请求明确失败，不静默抢占、不自动排队、不自动重试。
3. 需要切换业务时，由应用取消原下载，待固件关闭文件并释放占用后，再提交新业务。取消已受理、终止帧已入队与存储已释放不是同一个时刻，不应以固定延时猜测释放。
4. BLE/HID 连接和不访问存储的普通查询不因下载而全局禁用。涉及音频场景、复位、电源或存储所有权的命令单独核查。
5. 内存 bench 不因本节新增真实文件存储锁；其与其他业务并发可能影响测速，但不等价于读写文件冲突。保留已有传输通道和产测约束。

#### 9.6.2 冲突矩阵

以下规则均要求双向检查，并覆盖几乎同时发起的情况，不仅在 CDC 入口做一次状态判断。

| 业务组合 | 处理规则 | 当前证据与待办 |
| --- | --- | --- |
| CDC 与 BLE 文件下载/列表同步 | 实际文件业务互斥，先开始者继续，后到请求失败 | CDC 已检查 BLE 发送/同步忙；反向由公共 UXFILE 门禁兜底，仍需补查 BLE 业务入口及明确反馈 |
| CDC 与录音开始/恢复 | 互斥，不自动中断录音或下载 | CDC 检查录音状态和 worker；录音入口已有存储门禁，部分直接返回，需核查 APP、物理按键及恢复路径的反馈 |
| CDC 与删除、清空、格式化 | 下载期间拒绝新存储修改，暂不做按文件细分并发 | 删除、格式化入口已有共享忙检查；需覆盖其他入口和异步交接窗口 |
| CDC 与本地播放/恢复播放 | 正在播放时不启动下载；下载期间不启动或恢复播放 | 当前允许已关闭音轨的暂停状态进入 CDC，需验证恢复播放不能绕过门禁 |
| CDC 与索引扫描/重建/后台刷盘 | 通过共享准入协调；快照先完成缓存交接，再开始读取 | 已有在途调用计数、下载占用和刷盘推迟，需验证后台路径及释放后恢复 |
| CDC 与 USB MSC 导出 | 固件文件读取与主机卷访问互斥 | 核查 PC/MSC 双向切换及存储归还，不以串口连接状态替代卷所有权 |
| CDC 与 DUT/产测音频或文件业务 | 保持互斥，不在下载中途切换产测资源 | CDC 入口已有检查，需回归反向 DUT 进入和产测命令 |
| 同一 CDC 通道第二个 LIST/GET | 拒绝覆盖活动事务 | 已有活动源/流检查；LIST 完成后释放存储，用户选择期间不持锁，GET 重新校验身份 |
| CDC 与 OTA | 不自动互相抢占；升级启动前必须协调活动下载 | CDC 已检查正在运行的 OTA；CDC 期间启动 OTA 的反向路径尚待审计 |
| CDC 与恢复默认设置/软件重启 | 明确拒绝冲突，或经已验证的统一安全停止路径执行，不直接破坏活动资源 | 恢复默认设置入口显式检查工厂音频，但未直接检查 CDC 下载；后续复位收尾链尚待审计 |
| CDC 与取消/主机停读/USB 断线或重置 | 撤销传输会话，等待 worker 安全结束；旧会话不得污染新会话 | 已有取消、超时、generation 和关闭隔离，仍需实机验证 |
| CDC 与物理 OFF/关机 | 保留原生关机及复位兜底，不把下载锁变成关机否决条件 | 有界收尾，不强杀同步文件调用、不提前释放文件及 DMA 资源 |

本节的业务互斥不改变原有停止、取消及清理命令的可达性。资源被占用时仍须允许合法清理，不能用一个全局 BUSY 把释放入口也封死。

#### 9.6.3 已有基础与真实缺口

当前 `rdx_record_format_download_acquire()` 在 IRQ 排他范围内检查文件服务、下载占用及 `rf_io_users`，成功后设置下载占用。公共 UXFILE 调用经 `rdx_record_format_io_enter()/leave()` 保护；下载占用期间，存储业务准入返回忙。`rdx_cdc_source` 持有私有文件句柄，等待关闭完成且事务释放后才归还占用；关闭异常保持隔离，不得为方便恢复而直接清零忙标志。

这能提供底层资源保护，但不代表所有业务入口、状态机及协议反馈已经完善：

- 公共库门禁的失败返回包括负值、零和空结构；上层可能表现成空列表、读取失败或超时，不能将它们统一宣称为明确的 BUSY 响应。
- 录音部分入口在存储忙时直接返回；应用和按键用户未必知道请求被拒绝。
- BLE 下载、OTA、恢复默认设置等需要审计反向入口：不能只证明“已有业务阻止 CDC”，还要证明“CDC 阻止新冲突业务”。
- 状态预检查不等于原子准入。必须核查异步投递、worker 启动及文件打开之间的窗口，避免双方检查通过后同时开始。
- BLE 无线断连、逻辑会话释放不得误清理 CDC 私有句柄；CDC 断连也不得释放另一业务持有的资源。

#### 9.6.4 实施顺序与改动边界

1. **审计入口与所有权。** 列出 BLE 下载/列表、录音 APP/按键、播放恢复、删除/格式化、DUT、MSC、OTA、复位的执行入口、任务上下文、现有应答及释放路径；区分已覆盖、需补齐和需实机确认。
2. **补齐双向准入。** 优先复用现有共享存储占用，不另建 CDC 专属全局锁。冲突检查放在会改变业务状态或投递异步操作之前；必要时补原子占用交接，不能仅增加一次非原子 busy 查询。
3. **明确冲突反馈。** CDC 沿用现有错误码；BLE 优先使用已有失败应答，不凭空添加未经上位机支持的新命令或码值。日志只记录被拒业务和资源原因，不输出文件负载；物理按键沿用合适的设备反馈机制。无法表达细分 BUSY 的旧协议须记录兼容边界。
4. **保留异常收尾。** 验证取消、关闭失败、停读、拔插、会话切换和 OFF；只有资源真正归还后才能接受下一业务。错误隔离与正常忙碌不能混为一个可随意解除的状态。
5. **软件回归与构建。** 增加现有 host 框架中的双向竞争和拒绝无副作用用例，再运行统一 host runner 与 `.vscode/winmk.bat all`。不改 USB 队列、IRQ 续发、合包、双缓冲及默认测速参数。
6. **实机验收。** 按下一节矩阵交给应用/脚本验证，保留原内存和真实文件性能对照。软件通过不能替代实机并发验收。

不在这一轮引入通用调度框架、等待队列、自动抢占或同时录音下载；如果审计发现需要改变 BLE 对外协议或增加新的产品交互，先明确兼容方案，不通过底层错误返回伪装成已经支持。

#### 9.6.5 验收要求

- 双向与近同时启动：CDC↔BLE 下载、CDC↔录音、CDC↔删除/格式化、CDC↔播放/产测，以及启用配置下的 MSC/OTA。确认只有一个冲突业务成功进入，失败者不遗留句柄、锁、任务忙状态或错误索引。
- 拒绝无副作用：原下载继续完成且 CRC 正确；被拒的录音不生成空录音/错误索引，被拒的删除/格式化不修改文件，BLE 不将忙误报成真实空列表。
- 切换与恢复：取消后立即请求新业务可暂时返回忙，但关闭完成后必须能成功；LIST 后等待选择不长期占用存储；后台刷盘能够恢复。
- 故障收尾：停读、串口关闭重开、拔插、USB reset、OFF、底层读/关闭失败；验证旧会话不能污染新流，关闭失败不提前解锁，关机不被下载永久阻止。
- 无关业务：BLE/HID 保持连接、按键及不访问存储的状态查询不被一刀切屏蔽。
- 性能：同固件、同主机、同文件对比内存源和真实文件吞吐、完成长度、CRC；历史约 719.88/636.36 KB/s 仅作参考，不作为不同环境下的硬性保证。独立原文件内容对照仍按第 9.5 节单独验收。

#### 9.7.1 实际改动

- **复用 BLE 原解析器的忙分支。** 新增可重现的 `patch_librdxApp_protocol.ps1`，使闭源协议库的 `_rdx_is_storage_busy()` 同时识别 CDC 下载占用，保留原格式化检查。getlist、listreq、opusfile、录音及 OTA 等沿用库中已有拒绝/状态响应，不在 GATT 原始分片上另造解析器，不新增 BLE 命令。
- **保护解析过程中的准入窗口。** 已组装命令的普通协议入口和 OTA 协议入口在执行期间计入公共在途计数；CDC 不能在这些入口检查忙状态之后、更新业务状态之前抢占存储。这个计数不拒绝普通电量/版本查询，也不代表它们获得文件读写权限；实际文件访问仍走原准入。
- **补异步列表执行检查。** BLE 列表请求经队列到达实际列表生成函数时，再次申请公共文件准入；若这时 CDC 已取得存储，返回原 `getlist` 失败应答，不继续生成一个假空列表。先收到请求或先发 accepted 不等于已占有资源；资源的实际取得顺序决定谁执行，未执行的排队请求可能随后失败。
- **CDC 取得占用后再检查其他业务。** `rdx_cdc_source_begin()` 保留原预检查，取得下载占用后重查录音、播放、BLE 传输/同步、索引、格式化及 OTA；冲突则立即归还占用，不启动读取 worker。新增 `rdx_uxfile_is_index_active()` 仅查询实际索引活动，避免复查把 CDC 自己导致的 file-service busy 误判成外部扫描；原含服务忙的扫描接口及其电源保护不变。
- **OTA 真正执行时再检查。** `rdx_ota_proc()` 的 BEGIN 分支在绑定会话、启动定时器和初始化升级之前取得公共准入。失败沿用 `*DEV#upgrade#1#`；绑定失败及正常返回均释放在途计数，原 OTA 停止入口不改。
- **补恢复默认设置反向保护。** app_core 上真正执行恢复默认设置时检查 CDC 下载占用，冲突返回原失败应答，不写默认配置、不安排重启。正常 OFF/关机仍沿原生有界收尾路径处理，不因 CDC 占用而禁止关机。
- **补冲突日志。** 通用拒绝日志为 `[STORAGE_BUSY] owner=CDC_FILE request=...`，当前请求标签包括 `BLE_STORAGE`、`RECORD_COMMAND`、`RECORD_START`、`RECORD_KEY`、`PLAYBACK`、`OTA_BEGIN`、`RESET` 及共享入口标签。只在拒绝时打印，不增加文件负载或逐包日志。有效 APP 录音请求在执行层被拒时上报现有录音状态；实体按键保留原拒绝行为并增加原因日志，不新增提示音或灯效。

删除/格式化、解绑、DUT、播放、MSC 的已有公共准入继续保留；本轮没有另建等待队列、自动抢占或第二套存储锁，没有改文件发送队列、IN IRQ、低水位补货、双缓冲大小及主机测速参数。没有新增鉴权或 BLE 登录前置条件。

协议兼容边界：getlist 使用已有非零结果，opusfile 使用已有停止传输通知，listreq 沿用原失败参数响应，录音沿用当前状态通知，**并非所有旧指令都新增了字面值 BUSY 或专用错误码**。原库有些日志仍写 `Format in progress`，CDC 场景以新增的 `owner=CDC_FILE` 及请求上下文辨别原因，不据旧日志误判为设备正在格式化。应用需要按已有失败/停止语义处理，不自动把失败当成零文件或自动重试。

#### 9.7.3 操作员实机步骤

先使用测试录音，备份有价值的数据。格式化、删除、包装或恢复默认设置测试若错过下载窗口，可能按正常业务执行；不能在唯一一份重要录音上尝试。尤其格式化与包装会清空存储，先验证非破坏性冲突，再单独验证破坏性场景。

1. **基线。** 烧录本次固件，先连接 BLE 应用并保持连接，打开固件日志口；运行 `CDC-test.bat` 菜单 3 → 6，选择足够大的真实录音，完成一次无干预下载，保存 JSON、CRC、大小和速率。
2. **CDC → BLE 文件业务。** 再启动同一文件下载，确认脚本已经开始接收后，在 BLE 应用刷新录音列表或发起下载。预期 BLE 请求失败/停止，不产生假成功；CDC 继续完成且 CRC 通过。不要把 BLE 保持连接本身当作冲突。
3. **CDC → 录音/播放。** 分别在下载中按实体录音键、由 APP 开始录音、恢复本地播放。预期新请求被拒，日志能定位原因，录音状态不进入运行、不增加空录音；CDC 不被打断。每次测试后重新下载确认资源仍可使用。
4. **反向。** 先通过 BLE 下载或启动录音，再请求 CDC LIST/GET。预期 CDC 返回现有忙错误（错误码 2），不影响已运行业务。停止原业务并等其收尾后，重新请求 CDC 应能成功，不要求重新插线或重启。
5. **存储修改/复位。** 只在已备份测试设备上，确认下载进行中后分别请求删除、格式化、恢复默认设置或进入 DUT。预期请求拒绝、原文件和配置不变、设备不因恢复默认设置请求重启、CDC 正常结束。每次单独做，保存请求时间，不连续盲发破坏性命令。
6. **取消与生命周期。** 在下载中取消，随后尝试录音或 BLE 下载；若仍在关闭文件可短暂失败，释放后应成功。另测拔插、主机停读、串口重开和 OFF：允许本次下载不完整，但不允许旧数据混入新会话、提前解锁或永久卡死。物理 OFF 应正常关机，而非返回普通业务 BUSY。
7. **非冲突与性能。** 下载期间查询电量/版本、使用已建立的 HID，验证没有被全局屏蔽。单独执行无干预真实文件连续十轮及内存基准，比较同环境吞吐和 CRC；主动制造冲突时的日志/无线操作开销不作为纯吞吐回退证据。

OTA/可选 MSC 使用相应环境单独验证。当前列表/文件命令没有新增鉴权，但新 BLE RDX 会话仍遵守原有重绑定安全规则，不能据此承诺下载期间的所有首次连接或重连时序均已验收。

交付证据：固件日志（含冲突发生前后完整片段）、CDC JSON、BLE 应用结果截图/日志、具体操作顺序及是否重启。验收重点是“新请求明确失败、原业务保持正确、释放后可恢复”，不是只有拒绝日志。收到实机证据后再关闭第 9.6 节对应验收项。

- 第二轮优化允许文件流 IN 完成中断在校验会话与端点空闲后，最多提交一个已排队的 64 字节包，并重新使能通知；普通文本、ZLP、队列边界及异常回到 usb_stack。应用任务不操作端点，中断不执行文件业务、CRC、日志或回调，无忙等，2 ms/10 ms 定时器作补偿。详细边界见第 11.6 节。
- 开发配置 TX 队列为 32 项，每项最多复制 258 字节；二进制生产每次提交最多 256 字节，每轮最多 32 次。入队只在发送链路空闲时唤醒 usb_stack，已有在途包由 IN 完成通知推进。补货采用半深度水位边沿通知：队列回升到 16 项以上后重新武装，降至 16 项及以下通知一次；实际发送排空时另通知一次，避免低水位持续期间逐包唤醒 app_core。消息投递失败仍由定时器补偿。
- 应用帧缓冲最大 8216 字节。中间二进制片段不额外插入 ZLP，最终 END/ERROR 用短包结束；普通产测文本保留原 ZLP 行为。TX 满时仍接收独立 RX 控制数据。
- 取消停止新帧生产，丢弃未提交帧、补齐部分提交帧及 CRC，随后发 ERROR；保持队列顺序，不清活跃 DMA。保留 110 秒事务预算、底层 2 秒无进展超时及 generation 隔离。
- [CDC_FILE] queued 表示终止帧已入队，不表示电脑已收到；速率以电脑 JSON 为准。存储 worker、文件互斥、I/O 超时隔离及真实文件测速均待后续阶段。

软件验证：默认/开发配置构建通过，统一 host runner 扩展为 14 组。新增真实 C 生产器、通用解析器、传输队列和 Python 接收器测试，覆盖拆粘帧、CRC、尾块、满队列取消及过期会话。黄金向量位于 tests/host/fixtures/cdc_file_v1.json，由独立逐位 CRC 生成，C 查表算法与 Python zlib 交叉验证。软件测试不代替中断时序、拔插、DIP OFF、BLE/HOGP 及吞吐实板测试。

| 问题/线索 | 已实施策略 | 保留的边界 |
|---|---|---|
| 每次入队都可能重复唤醒 USB 任务 | 仅发送链路空闲时由入队启动；有在途包时等待 IN 完成通知推进 | 通知仍合并，投递失败有定时补偿 |
| 持续低水位时每包都可能触发补货回调 | 队列从高于 16 项降至 16 项及以下时通知一次，回升后重新武装；实际排空另通知一次 | 维持 32 项有界队列，不依赖无限重试或忙等 |

| 日志输出位于本轮端点处理之前 | 将日志输出移至本轮端点提交与回调完成之后 | 不在 IRQ 或关中断区打印，不取消必要错误日志 |

#### 11.4.4 新增统计的判读边界

[CDC_TX] 每秒最多输出一行，仅有完成数据或满队列事件时输出；字段含义如下：

| 字段 | 含义与限制 |
|---|---|
| gen / window_ms | 会话代次 / 实际统计窗口；窗口不能一律假定为 1000 ms |
| bytes / packets | 硬件已消费的非零包字节/包数，含协议和控制报文；不是文件有效吞吐 |
| dispatch / busy | 有效 USB 处理次数 / 处理时上个包仍未完成次数；busy 不单独证明主机慢或调度慢 |
| drained | 完成时队列和 ZLP 均为空次数，包含正常收尾；不能直接等同断粮 |
| refill / full | 补货回调次数 / 入队满队列次数；full 是背压，不能直接等同丢包 |
| kicks | 成功投递 USB 工作通知次数，不等于 IN 中断次数 |

会话失效会清空计数，这些日志不是完整事务字节账本，也不测量微秒级端点空闲间隙。最终速度与完整性仍以主机 JSON 为准；[CDC_FILE] queued 只表示入队完成。

这些计数仍不测量 IN 完成到下一包提交的时间，不能单独区分设备任务调度延迟、驱动/FIFO 行为和主机 USB 调度；busy 占比也不是 CPU 时间占比。不能据此宣称已证明 USB 硬件上限或某一处函数耗时。

#### 11.5.3 下一轮策略调整（当时尚未实施，后续见 11.6～11.7）

1. 将重点从应用补货转向 CDC IN 完成与下一包提交之间的关键路径，检查当前单缓冲提交和每包任务往返；优先获得可用的高分辨率时序或总线证据，避免仅凭毫秒日志归因。
2. 评估有界的驱动层快速续传或预备缓冲，目标是减少连续数据流的逐包任务往返，而不是让同一次任务盲目循环写入忙端点。是否允许在完成中断中提交预备包，必须先核实驱动约束、并发与 DMA 生命周期；当前实现尚未改成此模式。
3. 任何续传改动都需保留 generation 隔离、RESET/CLOSE/OFF 撤销、在途 DMA 不覆盖/不提前释放、终止帧顺序、RX 取消与超时；中断中不执行协议解析、CRC、日志、存储或无界等待。
4. 保持相同主机脚本、4096 字节块和校验口径进行 A/B；必要时单独做直连/Hub、主机读取和日志密度对照。优化后仍先测内存源，不提前进入真实文件 GET。

本节仅归档复测及调整后的排查策略，没有将尚未实施的驱动优化记为完成。第一轮改动暂保留作诊断基础，不能标记为已验证的吞吐优化收益。

### 11.6 第二轮优化（第三次调试）：文件流 IN 完成中断有界续包

#### 11.6.1 实验目的与改动

450.36 KB/s 仅是现有实现实测值，不是已证明的 CDC 或硬件上限。本轮不更换 CDC、不增加 WinUSB 接口、不修改文件协议、CRC、脚本计时口径、块长或队列容量。只验证减少逐包 USB 任务往返是否带来收益；尚未获得微秒级完成到提交间隔，不能把调度瓶颈写成已证明的根因。

- 仅 TCFG_T2620_CDC_FILE_ENABLE=1 开启快速路径。默认产品固件继续原任务路径。
- cdc_tx_wakeup 屏蔽本端点 IN 通知后调用 factory_cdc_tx_irq；仅 active/ready/configured 有效、前一包和下一项均为 stream、没有 ZLP、硬件不忙且未超时时，确认上一包完成并提交下一包。
- 单次中断最多复制和提交 64 字节已准备好的数据，不循环等硬件；不生成帧、不计算 CRC、不读存储、不打印、不调用上层补货函数。提交通过现有非阻塞 cdc_factory_write_packet 完成，同时重新使能 IN 通知。
- 低水位和队列边界合并通知 usb_stack；补货回调仍在任务内执行。RX 完成独立通知 USB 任务，不能因为持续 TX 而停止接收取消。
- 普通文本及 ZLP 仍由任务处理。最终包硬件完成后才计入 bytes/packets，不因 IRQ 已提交就提前认定完成；任务与 IRQ 不重复累计同一个包。

#### 11.6.2 生命周期审查与诊断

usb_config.c 的中断分发先处理 RESET 与 EP0，再调用数据端点回调。软件队列和 DMA 提交继续由本地 IRQ 排他保护；RESET/CONFIG/CLOSE 清除 ready、队列和在途软件状态，OFF 先 quiesce，STOP/释放仍在 usb_stack 路径完成。旧会话回调不能直接保留数据指针到下一会话；硬件忙时禁止覆盖 DMA。两秒无进展超时保留，快速路径不绕过到期检查。实际复位/拔插/关机竞争仍需实板验证。

[CDC_TX] 新增 irq_fast：本窗口在 IN 中断中成功续交的包数，属于提交计数，不是完成计数。bytes/packets 仍表示硬件已消费的数据；dispatch 仅统计 USB 任务处理次数。若快速路径有效，应观察到 irq_fast 持续增加、dispatch/packets 比例明显下降；这只能证明路径工作，吞吐达标仍以主机有效字节/总耗时判断。

#### 11.6.3 软件验证与复测顺序

真实 C 传输测试新增 IRQ 续包字节顺序、忙端点不重复提交、尾包只计一次、低水位任务回调、RX 可处理、文本/ZLP 边界、RESET/CONFIG/CLOSE/STOP/TIMEOUT 撤销、OFF quiesce、超时回退及通知失败定时补偿。真实驱动回调测试检查先屏蔽、提交再重新使能 IN 通知。模拟测试不代表真实中断时序或硬件吞吐通过。

#### 11.7.4 可复用的调试经验与后续边界

1. **先隔离变量，再引入业务。** 先用内存源区分 USB 传输与 SD 读取瓶颈；内存达到目标后再分别测读文件、读文件加 CRC、最终端到端 GET，不能把内存吞吐当作录音下载速度。
2. **同时看主机结果和底层计数。** 主机有效字节/总耗时决定达标；bytes/packets/dispatch/drained/refill/full/irq_fast 用来判断生产不足、调度开销或续包路径。queued 仅表示排队完成，baud 不表示 USB 链路速度。
3. **优化没有收益也要归档。** 第一轮保留了每包任务往返，未解决主要限制；如实记录 450.36 KB/s，避免以后重复只加缓存、调低水位或减少补货通知。
4. **改变关键路径，而不是先更换协议。** 本轮在同一 CDC、同一校验和计时口径下突破 700 KB/s，无需先引入 WinUSB 或维护新协议。真正有收益的是让准备好的下一包更及时进入端点。
5. **性能改动必须有明确上限和安全边界。** IRQ 每次最多一个 64 字节包，无忙等、文件 I/O、CRC、日志和业务回调；会话撤销、在途 DMA 保护、ZLP、RX 取消、超时不可为速度让步。默认产品配置仍不开放 MVP。
6. **成功报告不能覆盖失败报告。** 十轮成功证明该次运行达标，不自动关闭先前 invalid binary header。当前优先定位该异常并补停读、拔插、OFF 和 BLE/HOGP 共存回归，而非继续追求峰值。

### 11.8 第四次调试归档：合包生效，吞吐无明显收益，已撤回

11.8.1–11.8.3 保留候选阶段的依据、实现与测试计划，非当前合包能力声明；当前清理决定见 11.8.4，异常帧头诊断继续保留。

#### 11.8.1 优化依据与范围

按用户要求继续探索同一 CDC 链路的吞吐空间，不引入其他 USB 类，不降低 CRC、模式或顺序校验，也不将 724.04 KB/s 当作硬件上限。前三次过程仍是已完成的历史记录，本节是第三轮优化、第四次调试候选，不预先宣称收益。

当前 DATA 帧有 20 字节头、有效负载和 4 字节 CRC。4096 字节负载对应 4120 字节帧；旧发送器每个队列项独立分包，256 字节分段后留下的 24 字节帧尾会单独提交。第三次日志平均每包约 63.38 字节，与存在短包的情况一致。已排队的下一帧可以与该帧尾共用一个 USB 包，CDF1 字节流本身不需要改变。

这只是值得验证的方向：减少包数不等于同等比例的有效吞吐增益，不能仅凭包长推算最终速度，也不能保证第四次必然超过第三次。

#### 11.8.2 候选实现与安全边界（历史记录，已撤回）

- usb_factory_cdc.c 中任务与 IN IRQ 共用流提交函数，每次仍只提交一个不超过 64 字节的包；最多查看三个相邻 stream 队列项，无循环等待、CRC、存储访问、日志格式化或应用回调。
- 常规满包直接使用原队列地址；跨片段包才在 64 字节局部缓冲中拼接。三个片段上限覆盖“前一项余量 + 24 字节帧尾 + 下一帧起始”情形，不扫描整个队列。
- 仅在驱动成功提交后推进队列偏移；拒绝提交不消费数据，违反驱动完整提交约定时撤销会话。保留单 DMA 缓冲忙检查、会话代际、超时、低水位通知和 RX 取消路径。
- 不跨非 stream 项合包。rdx_cdc_file.c 的 END（32 字节）和 ERROR（28 字节）通过普通队列接口独立发送，保持终止短包；接口名不表示内容必须是文本，二进制内容不变。不能将终止帧拼成满包后直接等待下一条命令。
- 不等待未来数据来凑满包：队列不足时立即发送已有数据，避免尾包或取消死等。文本回复及其 ZLP 行为保持原样。
- 新增 stream_join（本窗口成功跨队列项合包的提交数）和 stream_short（本窗口 stream 短包提交数）诊断计数；不含独立 END/ERROR，不与 bytes/packets 的完成口径混淆。
- 接收脚本遇到 invalid binary header 时，将期望 ID/偏移、原始 20 字节头、已缓存字节数和最多 32 字节后续内容写入原有错误报告；不额外读数据、不重同步、不自动重试或放宽校验。该改动用于留证，不宣称修复 18:04 异常。

#### 11.10.1 主机接收对照

原有 inline 模式保持默认：边读取、边解析/校验。新增 deferred 模式：先接收所有二进制帧到有界内存，再通过同一个解析器验证每帧 CRC、数据模式、连续偏移、传输 ID、END 总长度及文件 CRC；全部通过才报告成功或发布输出文件。接收阶段仍检查帧头、类型、ID、偏移和块长度，以识别终止/错误帧并限制内存占用；不是绕过协议的纯 USB 吞吐测试。内存上界由 MAX_SIZE、业务块数和每帧开销约束，不增加后台线程、不重同步、不自动重试。

- CDC-test.bat 菜单 3 中，原选项 1/2 为 inline 单轮/十轮，3 为原取消测试；新增 4/5 为 deferred 单轮/十轮。
- 命令行使用 `--mode file-bench --bench-receive-mode deferred`；底层 tools/cdc_file_transfer.py 的 bench 子命令使用 `--receive-mode deferred`。deferred 不支持取消，取消仍用原路径。
- 每轮 JSON 的 receive_mode 区分模式。原 elapsed_s、KBps、passes_600KBps 仍覆盖命令发出到完整校验/可选文件输出结束，口径不变。
- deferred 另报 receive_elapsed_s、receive_KBps（发命令到收到终止帧，分母包含 accepted 等启动时间）和 verification_s（后置校验及可选输出耗时）；仅完整成功后才把接收速率作为有效性能证据。
- capture_elapsed_s、capture_wire_bytes、captured_bytes 是接收诊断，不表示校验通过；错误仍记录 complete=false。deferred 的 steady_s/steady_bytes_per_s 留空，避免把内存回放当作 USB 稳态速度。

#### 11.10.2 固件续包抽样

当时诊断配置新增 TCFG_T2620_CDC_TX_TIMING_ENABLE，默认 1，仅在当时 MVP 与汇总日志均开启时计时；现已改为默认关闭，并由独立 STATS 开关控制，见第 0 节。需要无探针 A/B 时设为 0 后按统一命令 clean + all，量产不依赖此诊断。沿用 SDK jiffies_usec/jiffies_usec2offset，不占用额外硬件定时器。按 irq_fast 计数每 64 次续交抽样，记录 factory_cdc_tx_irq 关中断后到 cdc_factory_write_packet 返回的耗时；只统计成功提交。

每个 CDC_TX 汇总窗口额外输出一行 CDC_TX_TIME：gen、sample_every、samples、submit_us_sum、submit_us_max、clock_invalid。平均值为 submit_us_sum / samples（samples=0 时不计算）；负时间差只计 clock_invalid，不加入平均值。统计在任务中打印，IRQ 不格式化、不逐包输出。主机模拟回归覆盖计时开关两种配置，不能替代硬件计时精度验证。

该耗时包含状态检查、已有统计、64 字节以内拷贝、DMA 提交和部分计时开销；不包含硬件完成到回调被调度的中断响应延迟、不包含回调前的驱动处理，也不是总线包间隔或 CPU 占用率。抽样最大值不是所有包最大值，计时探针本身也可能扰动吞吐。若抽样耗时小而总速率不变，不能据此断言主机瓶颈；下一步仍需总线抓包或 GPIO/逻辑分析仪辨别 NAK、主机 IN 调度及真实中断延迟。
