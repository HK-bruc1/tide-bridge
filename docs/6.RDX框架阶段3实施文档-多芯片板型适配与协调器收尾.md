# RDX 框架阶段 3 实施文档：多芯片/板型适配与协调器收尾

> 版本：v1.1 (checkpoint)
> 日期：2026-06-27
> 对应大纲：`docs/3.RDX框架JL平台复用性优化大纲.md` 阶段 3
> 前置条件：阶段 2 服务层拆分已完成并归档，当前 `rdx_app.c` 已接入 `rdx_command_dispatch`，8 个 service 已落地。
> 约束：同阶段 0-2，**`librdxApp.a` 二进制不修改**。

---

## 1. 阶段目标

阶段 3 做两件事：

1. **JL 多芯片/多板型适配**：验证 core/service 代码在面对不同芯片族、不同板型时是否真正“零改动”。
2. **`rdx_app.c` 协调器收尾**：把阶段 2 延期剩余的 17 个协议查询 handler、WiFi handle、按键/DUT/LED/eMMC/idle 等具体实现迁出或 wrapper 化，使 `rdx_app.c` 最终退化为协调器。

阶段 3 不追求创建大量新 service，而是优先把已有架构（board config、port wrapper、dispatch、event bus、weak hook）用足。

## 3. 设计原则

1. **不换芯不碰 service/core**：新增板型/芯片族的修改只应出现在 `board/<name>/` 和 `port/jl/<chip_family>/`。
2. **协调器只保留无法归属的编排**：能明确归到 service 的就迁；不能明确归属的（如跨 service 的按键状态机）保留为薄编排层。
3. **不为了拆而拆**：没有真实新芯片时，用 shadow port 模拟 API 漂移验证隔离性，不硬造抽象层。
4. **保持 ABI**：所有阶段 2 遗留的旧符号继续保留 thin wrapper。

## 4. 任务分解

### 4.1 任务 A：`rdx_app.c` 协调器收尾

#### A.1 剩余 handler 分配

阶段 2 剩余的 17 个 handler 按领域拆入已有 service 或新建 `rdx_info_service`：

| 目标归属 | handler | 数量 |
|---|---|---|
| `rdx_info_service`（新） | BATTERY_QUERY、INCHARGE_QUERY、VERSION_QUERY、OS_TYPE、AUTH_SN、OFFTIME_QUERY | 6 |
| `rdx_device_service`（扩） | BT_NAME_QUERY/SET、BLE_NAME_QUERY/SET、OFFTIME_SET | 5 |
| `rdx_storage_service`（扩） | SD_MEM_QUERY、FILE_DELETE | 2 |
| `rdx_record_service`（扩） | RECORD_MODE_QUERY、AUDIO_STREAM、FLASHNOTE | 3 |
| `rdx_time_ops` / `rdx_time_service`（待定） | RTC | 1 |

**决策**：不把所有 handler 塞进一个 "info" service，避免语义混杂和第二次中心化。`rdx_info_service` 只保留设备信息与只读/轻量系统查询；名字类归 `device_service`、存储类归 `storage_service`、录音相关归 `record_service`。

**迁移前置检查**：

- `RTC` 不是纯查询：当前会设置 RTC，并在录音中修正 `uxfile start_time`。迁移前必须做依赖扫描，优先落到 `rdx_time_ops` / `rdx_time_service`，必要时由 record/storage 通过事件或明确 service API 协作。
- `OFFTIME_SET` 是设备生命周期/关机策略，不归入 `rdx_info_service`；优先迁到 `rdx_device_service` 或后续 lifecycle 层。
- 每个 handler 迁出前需记录依赖的旧符号、是否被 `librdxApp.a` 直接依赖、是否需要保留 `rdx_app_*` thin wrapper。

#### A.2 WiFi handle 收尾

阶段 3 checkpoint 状态：

- `rdx_wifi_power_on()` / `rdx_wifi_power_off()` 与 `RdxWifiInfo` 状态所有权已迁入 `rdx_wifi_service.c`。
- `rdx_app_wifi_handle()` 保留为 ABI/旧调用点兼容 wrapper，内部只转发到 `rdx_wifi_service_*`。
- `rdx_app.c` 仍保留 WiFi event consumer 与少量历史 `extern xxp_esp32_wifi_*` 声明，属于 Stage 4 清理项。

后续目标：

- 将新调用点逐步改为直接使用 `rdx_wifi_service_*`，减少对 `rdx_app_wifi_handle()` 的新增依赖。
- `xxp_esp32_wifi_*` 等直接硬件调用通过 `rdx_wifi_transport_ops_t` 小 vtable 隔离。

#### A.3 按键 / idle / DUT / LED / eMMC power 收尾

| 模块 | 当前位置 | 阶段 3 动作 |
|---|---|---|
| LED PT0807 | `rdx_app.c` + `led_pt0807.h` | 已接入 `rdx_hook_led_init()`；场景控制 full hook 转 Stage 4 |
| DUT mode | `rdx_dut.c` + `rdx_app.c` 按键分支 | 已将 DUT 进入/退出动作替换为 `rdx_hook_dut_*` |
| eMMC power check | `rdx_device_service.c` | 状态机已迁入 device service；`rdx_app.c` 保留 `rdx_app_emmc_*` thin wrapper |
| idle / auto shutdown | `rdx_app.c` | 保留为协调器状态机，但把进入/退出动作抽象为 `rdx_app_lifecycle` hook |
| 按键组合 | `rdx_app.c` | 保留协调器入口，按键映射表按产品配置化 |

#### A.4 硬编码 board include 清理

当前 `rdx_app.c` 和 `rdx_device_service.c` 仍直接 `#include "board/t2616_cc/rdx_board_config.h"`。阶段 3 第一批提交就要改为：

```c
#include "rdx_board_config.h"
```

由 Makefile 的 include path（`-Iapps/common/third_party_profile/rdx_protocol/board/$(RDX_BOARD)`）决定实际解析到的板型目录。这是板型隔离的前提。

#### A.5 目标

阶段 3 结束时：
- `rdx_app.c` 行数 ≤ 2000（收尾目标）。
- `rdx_app.c` 函数数 ≤ 50。
- `rdx_app.c` 只保留：系统初始化、service init/编排、生命周期状态机、 thin wrapper。

### 4.3 任务 C：多芯片族 port 分层

#### C.1 当前问题

当前 port 是扁平结构 `port/jl/rdx_jl_*.c/h`，所有芯片族实现混在同一目录。阶段 3 必须改为：

```text
port/jl/
├── include/            # 公共头（对外 API，可被所有 chip family 包含）
│   └── rdx_jl_*.h      # 声明 chip-independent 接口
├── jl7018/             # 当前主力芯片族实现
│   ├── rdx_jl_osal.c
│   ├── rdx_jl_storage.c
│   ├── rdx_jl_rtc.c    # 补齐当前缺失的实现
│   └── rdx_jl_gpio.c
└── jl7018_shadow/      # shadow port，验证隔离性
    ├── rdx_jl_osal.c
    ├── rdx_jl_storage.c
    ├── rdx_jl_rtc.c
    └── rdx_jl_gpio.c
```

业务/service 代码统一 `#include "rdx_jl_*.h"`，通过 Makefile include path 决定解析到的 chip family。

#### C.2 新增 `port/jl/jl7018_shadow/`

- 复制 `port/jl/jl7018/` 下 wrapper 文件到 `port/jl/jl7018_shadow/`。
- 在每个 wrapper 函数**内部**替换底层 JL SDK 调用路径或参数转换逻辑，**保持 wrapper 对外 API 签名不变**。
- service/core 代码不跟随修改，只通过 wrapper 接口调用。
- 该 shadow port 用于验证"实现可替换"的隔离性，而非 API 漂移。

#### C.3 补齐 `rdx_jl_rtc.c` 并接入 Makefile

当前 `rdx_jl_rtc.h` 接口存在但无 `.c` 实现，也未接入 Makefile。阶段 3 必须：

- 在 `port/jl/jl7018/` 下新增 `rdx_jl_rtc.c`，实现 header 中声明的接口。
- 在 Makefile 中显式加入 `port/jl/$(RDX_CHIP_FAMILY)/rdx_jl_rtc.c`。
- shadow port 同步提供一份 dummy/stub 实现，保证编译隔离验证可用。

#### C.4 构建矩阵验证

| 组合 | 目标 |
|---|---|
| `RDX_CHIP_FAMILY=jl7018 RDX_BOARD=t2616_cc` | 主力组合，必须正常工作 |
| `RDX_CHIP_FAMILY=jl7018_shadow RDX_BOARD=t2616_cc` | 验证 service/core 不随 chip port 漂移 |
| `RDX_CHIP_FAMILY=jl7018 RDX_BOARD=t2616_ep` | 验证 service/core 不随 board 漂移 |

### 4.4 任务 D：event bus 补齐

#### D.1 当前状态修正

当前 `rdx_storage_service` 自己订阅 `RDX_EVENT_STORAGE_FORMAT_DONE`（自发布自消费），已实现最小 publish/subscribe 闭环，但不是严格意义上的跨 service 业务通知。阶段 3 要补齐真正的跨 service 事件路径。

#### D.2 BLE connect/disconnect 业务订阅

当前 `rdx_ble_service` 直接调用 `rdx_record_on_ble_conn_changed()` 等兼容接口。阶段 3 目标：

1. `rdx_record_service` 订阅 `RDX_EVENT_BLE_CONNECTED` / `RDX_EVENT_BLE_DISCONNECTED`。
2. `rdx_ble_service` 移除直接调用，改为发布事件。
3. 保证连接/断开语义不变，不重复执行。

**迁移策略（防双执行）**：

- 第一步：在 `rdx_ble_service` 中保留现有直接调用，同时新增事件发布；`rdx_record_service` 订阅事件但只做 logging，不执行业务动作。
- 第二步：验证事件顺序和时序与直接调用一致后，在同一提交中把 record 行为迁移到事件回调，并删除 `rdx_ble_service` 中的直接调用。
- 禁止长期保留"直接调用 + 业务订阅"双路径，否则会双执行。

**风险**：这是同步语义变更，必须伴随 BLE 录音上传 30s 冒烟测试。

#### D.3 可选：FORMAT_DONE 订阅者扩展

当前 storage service 已订阅 FORMAT_DONE。可进一步让 record service 也订阅，用于录音状态重置。但优先级低于 BLE 事件订阅。

### 4.5 任务 E：port lifecycle hooks 与小 vtable

#### E.1 port lifecycle hooks

不同芯片族的低功耗/启动/唤醒行为差异是阶段 3 必须隔离的核心。在 port 层定义统一钩子：

```c
// port/jl/include/rdx_jl_lifecycle.h

/* 芯片早期初始化，在 main 入口调用 */
void rdx_jl_early_init(void);

/* 进入低功耗前调用，返回 0 允许 sleep，非 0 阻止 */
int  rdx_jl_pre_sleep(void);

/* 唤醒后调用 */
void rdx_jl_post_wakeup(void);

/* 软关机前调用 */
void rdx_jl_pre_poweroff(void);
```

业务代码只调用这些钩子，不直接调用芯片特定的低功耗 API。`jl7018` 和 `jl7018_shadow` 必须各提供一套实现，以验证隔离。

#### E.2 小 vtable 计划

阶段 3 只落地必要的小 vtable，避免过度抽象。

| vtable | 优先级 | 范围 | 说明 |
|---|---|---|---|
| `rdx_time_ops_t` | P0 | RTC 读/写、tick/ms 转换、闰年判断 | 和芯片差异强相关，必须落地 |
| `rdx_lifecycle_ops_t` | P0 | early_init/pre_sleep/post_wakeup/pre_poweroff | 见 E.1 |
| `rdx_wifi_transport_ops_t` | P1 | open/close/control/tx/rx_done | 配合 WiFi handle 收尾 |
| `rdx_ble_transport_ops_t` | P1/P2 | send/get_mtu/is_connected | 先保留设计草案；只有本阶段出现真实调用点时才落 public API |
| `rdx_storage_ops_t` | P2 | read/write/string_read/string_write | 当前 `rdx_jl_storage` 已足够；除非换 VM/flash 后端，否则 Stage 4 再扩展 |

**P0 vtable 必须在本阶段实现并接入启动流程**。P1/P2 只登记设计草案和预期调用点；除非本阶段有真实调用方，否则不新增未使用的 public header/API，避免形成空接口债。

## 7. 风险与缓解

| 风险 | 严重度 | 缓解 |
|---|---|---|
| 查询 handler 迁出后 librdxApp.a 仍依赖旧符号 | 高 | 保留旧函数名为 thin wrapper；迁出前先查符号依赖表。 |
| RTC / OFFTIME_SET 误归入 info service | 中 | 迁移前先做依赖扫描；RTC 优先走 time ops/time service，OFFTIME_SET 优先走 device/lifecycle。 |
| WiFi transport vtable 设计过度 | 中 | 只做必要抽象（open/close/control/tx/rx），不覆盖 xxpUart 内部。 |
| BLE 事件订阅改变同步语义 | 高 | 分两步：先 logging-only 订阅验证事件顺序，再在同一提交迁移 record 行为并删除 ble_service 直接调用。 |
| shadow port 与真实芯片差异脱节 | 低 | shadow port 只改 wrapper 内部实现，不改对外签名；不承诺真实移植性。 |
| `rdx_app.c` 行数仍难 ≤ 2000 | 中 | 允许把“≤ 2000”作为方向而非硬性门禁，优先保证架构正确。 |
