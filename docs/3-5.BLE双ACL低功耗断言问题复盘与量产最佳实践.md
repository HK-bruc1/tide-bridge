# BLE双ACL低功耗断言问题复盘与量产最佳实践

> 更新时间：2026-08-05
> 当前结论：问题已定位到预编译BLE controller的双ACL低功耗调度范围；产品侧局部低功耗门禁已完成一轮有效真机验证，但最终源码组合、零连接低功耗恢复、反向顺序、长稳和功耗仍待关闭。该状态属于“临时规避有效”，不等于controller根因已经修复。
> 边界说明：PC App关闭GATT对象后Windows因HOGP继续保留物理ACL、导致RDX owner无法释放，是应用会话与物理链路生命周期不一致的独立协议问题，不属于本controller低功耗缺陷；详见[五号三问题说明](./5-3.PC_APP逻辑断开无法释放RDX会话问题复盘与处理方案.md)。

## 1. 问题说明

### 1.1 复现拓扑

设备以BLE Peripheral身份同时服务两个Central，并由两个`app_ble` wrapper承载相同的RDX + HOGP复合Profile：

```text
Windows PC / HID  -> wrapper 0 -> ACL 0x0050
手机 RDX App      -> wrapper 1 -> ACL 0x0051
```

历史故障的稳定触发顺序为：

```text
PC/HID先连接并进入ready
  -> 空闲wrapper继续广播
  -> 手机App建立第二条Peripheral ACL
  -> controller低功耗计数断言
  -> HSB watchdog异常
  -> P33软复位
```

App先连接、PC后连接在早期测试中表现正常，但这不构成controller缺陷已消失的证明；最终回归仍必须覆盖两个连接顺序。

### 1.2 外部现象与内部故障

外部现象是手机App接入第二条ACL后设备复位。内部首个确定故障位于预编译`btctrler.a`：

```text
bb_le_power.c:352
ASSERT-FAILD: (interval_sleep_cnt - le_lp_interval_sleep_cnt) == 1 2, 0
```

断言值`2,0`表明controller内部interval sleep计数已经失配。该状态不能通过屏蔽断言继续运行，否则后续BLE时序与低功耗状态不可再被信任。

原始日志随后出现：

```text
JL_HEMU->MSG0 = 0x20
watchdog time out
P33_SOFT_RST
```

`【潮汐】AC701N用户手册V1.3.pdf`可确认断言后的复位链路：第52至54页说明WDT超时行为，第175页定义HSB `MSG0` bit 5为`WDT_EXCPT`，第36/137页说明`SOFT_RST`写1触发系统复位。手册没有公开BLE双ACL anchor或`bb_le_power.c`内部调度算法，因此无法仅靠手册修复controller计数。

## 2. 证据与根因边界

### 2.1 已确认事实

- 两条ACL均成功进入Connection Complete，wrapper与connection handle映射正确；
- PC初始参数为`interval=6`（7.5 ms）、`latency=4`、`timeout=600`（6 s）；
- 手机初始参数为`interval=24`（30 ms）、`latency=0`、`timeout=500`（5 s）；
- 断言发生在第二ACL建立后的首轮低功耗/anchor调度窗口；
- 断言前没有Connection Update、加密、ATT写入、RDX claim、RDX runtime ACTIVE或应用层参数请求；
- 全局关闭系统低功耗后，同一PC-first拓扑及双方重连可以运行；
- 恢复系统低功耗、只删除sleep enter/exit字符打印后，断言仍然复现；
- 使用正式`REGISTER_LP_TARGET`阻止风险窗口内的系统睡眠后，一轮PC-first、App重连和PC重连日志不再出现断言。

### 2.2 可以排除的方向

- RDX命令、录音、文件、OTA等业务逻辑不是首次触发源；
- 手机连接后的ATT写入和RDX capability claim不是首次触发源；
- 应用层Connection Parameter Update请求不是首次触发源；
- `sleep_enter_callback()` / `sleep_exit_callback()`中的`<`、`>`打印不是必要触发条件；
- wrapper路由冲突、跨链发送或session生命周期失败不是本次复位的首个故障。

### 2.3 尚不能声称的结论

由于`bb_le_power.c`和controller源码不可见，当前只能把根因冻结在“预编译controller的双Peripheral ACL低功耗/anchor计数调度范围”，不能从应用层证据进一步断言具体是哪一个controller变量、临界区或硬件事件实现错误。

## 3. 尝试过的方案

| 阶段 | 变更 | 结果 | 结论 |
|---|---|---|---|
| 原始复现 | PC/HID先连，手机App后连 | `bb_le_power.c:352`断言，随后watchdog和软复位 | 问题可稳定复现 |
| per-link诊断 | 增加`[RDX_BLE_PARAM]`初始/更新参数日志 | 连续两轮在第二ACL早期触发，业务尚未开始 | 故障窗口位于controller连接与低功耗调度 |
| 全局关闭低功耗A/B | 临时设置`TCFG_LOWPOWER_LOWPOWER_SEL=0` | 双连接、App重连、PC重连均通过 | 系统低功耗路径是必要触发条件 |
| trace-only A/B | 恢复低功耗，只移除`<`、`>`打印 | 同一断言、同一计数`2,0`再次出现 | UART字符打印不是根因 |
| 局部门禁 | 正常低功耗配置，双ACL风险窗口由`lp_target`返回busy | 约65秒内完成PC-first及双方重连，无断言或复位 | 产品侧局部规避可行 |

## 4. 当前产品侧规避方案

### 4.1 实现位置

门禁实现在[`rdx_ble_server.c`](../SDK/apps/common/third_party_profile/rdx_protocol/rdx_ble_server.c)，使用SDK正式低功耗扩展点：

```text
REGISTER_LP_TARGET(rdx_ble_dual_acl_lp_target)
```

低功耗查询函数只读取一个`volatile u8`状态，不在低功耗查询上下文调用BLE API。连接数、广播窗口和门禁状态只由现有BLE连接事件与广播控制路径更新。

项目继续使用工具配置中的正常低功耗值`TCFG_LOWPOWER_LOWPOWER_SEL=1`。不得为该问题修改生成文件`sdk_config.h`；临时项目覆盖只能放在`t2620_project_config.h`，且全局关闭低功耗不能进入量产配置。

### 4.2 门禁条件

| 运行状态 | `is_idle()` | 说明 |
|---|---:|---|
| 零ACL、正常广播 | `1` | 允许系统睡眠 |
| 一条ACL，第二连接入口已显式关闭 | `1` | 不存在第二ACL接入窗口时允许睡眠 |
| 一条ACL，空闲wrapper准备或正在接纳第二ACL | `0` | 覆盖广播终止到Connection Complete的过渡窗口 |
| 两条ACL同时在线 | `0` | 避免controller双ACL低功耗计数失配 |

典型状态日志：

```text
[RDX_BLE_LP] system_sleep_block=1 connected=1 second_acl_window=1 reason=connect
[RDX_BLE_LP] system_sleep_block=0 connected=0 second_acl_window=1 reason=advertising_on
```

在统一一拖二广播模型中，一条ACL在线时通常会继续开放另一个wrapper，因此单连接等待第二连接期间也会保持门禁。这是当前规避方案的主要功耗代价。

### 4.3 最新通过日志

`COM3_2026-08-05_17-24-17.log`提供以下证据：

- `2.650 s`：PC第一ACL建立后门禁切换为`system_sleep_block=1`；
- 所有`Sw[]`系统睡眠标记均发生在门禁生效前；
- `23.142 s`：手机第二ACL建立，随后参数更新并进入RDX `ACTIVE`；
- `30.116 s`：手机断开，runtime完成`QUIESCING -> FIFO barrier -> READY`；
- `36.059 s`：手机重连并再次进入`ACTIVE`；
- `45.375 s`：PC断开，HOGP状态按预期清理；
- `59.222 s`：PC重连，HOGP重新达到`ready=1`；
- 约65秒日志中，`bb_le_power`、`ASSERT-FAILD`、watchdog、异常复位、wrapper mismatch、claim reject和runtime FAILED均为零命中。

该日志始终至少保留一条ACL，因此没有出现`system_sleep_block=0`，尚不能证明零连接后低功耗恢复正确。

## 5. 当前状态

### 5.1 已完成

- 故障可重复，断言、watchdog、软复位证据链完整；
- 业务层、连接参数请求和UART字符打印已排除；
- 正常低功耗配置下的局部`lp_target`规避已完成一轮有效真机验证；
- PC-first下手机断开/重连与PC断开/重连均已覆盖；
- controller断言保持启用，没有用屏蔽断言掩盖计数失配。

### 5.2 尚未关闭

- 最新通过镜像使用了已移除`<`、`>`打印的代码；当前源码已恢复原始打印，最终源码组合尚未重新编译和复验；
- App-first、PC-second顺序尚未在最终源码组合上回归；
- 双方全部断开后的`system_sleep_block=0`与系统睡眠恢复尚未验证；
- 单连接等待第二连接、双连接在线、业务活跃状态的实测功耗尚未记录；
- 至少10轮双方交替重连、8小时长稳和低电量场景尚未完成；
- 杰理修正版`btctrler.a`尚未取得，controller根因仍然存在。

因此当前状态应表述为：

```text
产品侧临时规避：有效，待最终矩阵关闭
controller根因修复：未完成
量产功耗验收：未完成
```

## 6. 后续最佳实践

### 6.1 短期产品版本

1. 保持`TCFG_LOWPOWER_LOWPOWER_SEL=1`，禁止把全局低功耗关闭作为正式修复；
2. 保留`rdx_ble_dual_acl`局部门禁，只覆盖第二ACL接入窗口和双ACL在线期；
3. 恢复原始sleep enter/exit打印后重新执行完整矩阵，确保最终二进制与验证对象一致；
4. 保留`[RDX_BLE_PARAM]`与低频`[RDX_BLE_LP]`状态日志直至稳定性门禁关闭；
5. 对零连接、一条PC连接、一条App连接、两条连接和RDX业务活跃分别测量平均与峰值电流；
6. 把功耗结果、镜像SHA-256、controller库SHA-256和真机日志绑定到同一测试记录。

### 6.2 杰理问题单

向杰理提交最小可复现包时应包含：

- 芯片与平台：AC701N / BR28；
- SDK版本、`btctrler.a`文件SHA-256和构建配置；
- `config_le_hci_connection_num=2`、`config_le_gatt_server_num=1`及`config_btctler_le_hw_nums`配置；
- 两条ACL的初始连接参数与连接顺序；
- `bb_le_power.c:352`断言表达式和实际值`2,0`；
- 原始故障、trace-only失败、全局低功耗通过和局部门禁通过四组对照日志；
- 明确请求确认双Peripheral ACL支持边界，并提供修正版`btctrler.a`或官方低功耗限制说明。

### 6.3 获得修正版controller后

1. 固定应用层源码和连接参数，只替换controller库完成A/B；
2. 首先保留局部门禁验证新库的基本连接、业务和重连行为；
3. 增加项目级A/B开关，关闭局部门禁后重复完整矩阵与长稳测试；
4. 只有在门禁关闭、正常系统低功耗、功耗达标且无断言时，才删除临时门禁；
5. 保留per-link参数日志或可按诊断宏启用的等价能力，防止后续SDK升级回归；
6. 记录旧库与新库的hash、供应商问题单编号和验证镜像hash，避免库文件被静默替换。

### 6.4 禁止做法

- 不屏蔽或删除controller断言；
- 不把`TCFG_LOWPOWER_LOWPOWER_SEL=0`作为量产配置；
- 不通过固定延时假装等待controller稳定；
- 不依赖PC-first或App-first中的某一个顺序规避问题；
- 不在生成的`sdk_config.h`中写项目修复；
- 不用全局connection handle或业务owner状态代替实际wrapper连接数；
- 不把一次60秒左右的通过日志当成长稳和功耗验收。

## 7. 关闭标准

| 验证项 | 当前状态 | 关闭要求 |
|---|---|---|
| PC-first、App-second | 局部门禁镜像通过一次 | 最终源码组合连续10轮通过 |
| App-first、PC-second | 历史上正常，最终组合未复验 | 最终源码组合连续10轮通过 |
| App断开/重连，PC保持 | 通过一次 | 连续10轮，HID持续可用 |
| PC断开/重连，App保持 | 通过一次 | 连续10轮，RDX持续可用 |
| 双方全部断开 | 未覆盖 | 出现`system_sleep_block=0`且系统睡眠恢复 |
| 异常关键字 | 最新日志零命中 | 全矩阵无assert、watchdog、软复位和路由冲突 |
| 长稳 | 未完成 | 双连接至少8小时，业务与按键持续正常 |
| 功耗 | 未测量 | 零/单/双连接数据记录并满足产品预算 |
| controller根因 | 未修复 | 杰理修正版库在关闭门禁时通过同等矩阵 |

产品侧可以在除“controller根因”外的所有门禁通过后，将该问题标记为“已由局部规避关闭”；只有修正版controller在关闭局部门禁后通过完整矩阵，才能标记为“根因已修复”。
