# BLE 复合会话满占时的第二入口广播控制

> 更新：2026-11-09。单 ACL、仅单一 owner 的第二入口固定常开，120 秒快广播后转慢，业务唤醒后回快档；稳定快慢档均不占睡眠门禁。`COM3_2026-11-09_15-59-06.log` 已验证新策略：快档和慢档均入睡，慢档睡眠期间手机两次接入第二 ACL（连同前一轮共 3 次）未触发断言或异常复位；业务唤醒切快档时另有 1 次 `timer_no_response`，待分析。用户万用表实测 0.5–2.2 mA 跳动（尖峰 2.2 mA、粗估均值约 1 mA）。绑定重连与长稳仍待验证，见第 4、5 节。
> 更新：2026-11-06。已用 `COM3_2026-11-06_18-15-15.log` 完成首轮板测：复合会话关窗、`rdxclose` 后由第二 ACL 接管、关窗后睡眠及静置低于 1 mA 均已验证（第 5 节）。HOGP 输入服务事件化是复合会话能睡眠的另一必要条件，见 [6-2](6-2.T2620BLE连接后低功耗设计.md) 第 2.7 节。空口抓包、手机 + PC 双 ACL 及长稳仍待验证。

## 1. 问题与日志

两个 `app_ble` wrapper 共用一个地址、一个复合 GATT profile；正常情况下只有一个空闲 wrapper 在广播，并非两组广播同时发射。广播是否开启取决于空闲物理连接入口，而 RDX 和 HID owner 是另外一层全局唯一的业务资源。

`COM3_2026-11-06_14-58-28.log` 中：

1. 第一条 ACL `0x0050` 建立后，空闲 wrapper 开启第二入口；随后同一链路形成 HID + RDX 复合 owner。
2. 第二入口到期并确认关闭后，PC 上的 `getlist` 业务又唤醒了 120 秒入口。
3. 随后第二条 ACL `0x0051` 建立，RDX claim 返回 `4`（runtime 不是 READY），之后该 ACL 断开。仅凭这份日志不判断第二个连接端的具体身份。

根因是原入口策略只考虑物理 ACL 数量，没有考虑同一 ACL 已持有两个全局 owner。此时继续开放入口会让另一设备看到设备、甚至建立 ACL，却无法取得已被占用的 HID 或 RDX。

日志还出现一次 `timer_no_response`。其原因和影响需要单独分析，本次不把它归因于复合 owner，也不宣称已经解决。原始日志包含安全相关信息，分享时应先脱敏。

## 2. 新的准入规则

| 物理拓扑和 owner | 第二入口行为 |
| --- | --- |
| 零 ACL | 保持原有统一广播及既有抑制条件。 |
| 一条 ACL，仅持有 HID 或仅持有 RDX | 入口常开：120 秒快广播后转慢广播，慢档真实业务唤醒后回快档，供另一能力接入。 |
| 一条 ACL，同一链路持有 HID + RDX | 立即禁止新开入口，并通过现有控制器确认流程关闭正在广播的空闲 wrapper；业务活动和广播刷新不再重开。 |
| 两条 ACL | 不开放新的连接入口。已有两条链路继续按原规则运行。 |
| 第二条无关 ACL 断开，但第一条仍持有复合 owner | 不因物理连接数从二变一而重开入口。 |

> 2026-11-09：仅持有单一 owner 的单 ACL 场景固定为常开第二入口（120 秒 100 ms 快广播后转 500 ms 慢广播且不关闭，慢档遇到真实业务唤醒回升一轮快广播），不再提供 `TCFG_T2620_BLE_SECOND_ENTRY_ALWAYS` / `TCFG_T2620_BLE_SECOND_ENTRY_SLEEP` 开关。单 ACL 快慢档均不占睡眠门禁；复合 owner 的关闭规则不变。见 [6-2 第 4.2.1 节](6-2.T2620BLE连接后低功耗设计.md)。

HID 先到、RDX 先到以及加密后恢复已绑定 HID 订阅都使用实际 owner 认领结果。CCC 暂时关闭、加密状态变化或 HID suspend 不是 owner 释放事件，不能据此重开窗口。

控制器关闭广播期间保留原广播句柄及睡眠保护，等待现有两阶段完成确认；关闭过程中已被控制器接纳的连接仍按原物理 ACL 流程处理，不主动踢掉。关闭失败、超时等异常继续遵循原有保守故障保护。

## 3. PC App 释放 RDX 后的接管

PC App 不再使用 RDX 时，必须在仍持有 RDX owner 的连接上发送 `*APP#custom#rdxclose#1#`。仅关闭 Windows GATT 对象或取消 CCC 订阅，不能代替该命令。报文分片和无专用回包等约束见 [3-4](3-4.PC_APP逻辑断开无法释放RDX会话问题复盘与处理方案.md)。

复合链路处理顺序：

1. RDX 进入 `QUIESCING` 并释放 RDX owner，PC 的 ACL、HID owner、HID CCC 和加密状态不因这条命令被主动清除。此时第二入口仍关闭。
2. 旧接收队列到达认证 FIFO 屏障，重新中止旧工作后进入 `RESETTING`；只有记录、文件、OTA 和发送等旧工作满足原有空闲条件，才能完成缓冲区重置。
3. 实际进入 `READY` 时，按该时刻启动 120 秒快广播，到期转慢广播而不关闭入口；若此时已有两条 ACL，仍不广播。DUT、关机、USB、Wi-Fi 等现有抑制条件优先，快档期限不会因此延长。
4. 手机可在入口开放期间扫描并尝试认领空闲的 RDX。该入口不是手机预留：PC 或其他已接入设备也可能先认领 RDX；同一 PC 若重新成为复合 owner，入口重新关闭。

`READY` 和入口容量在短临界区中一起发布，并通过 runtime epoch 排除旧释放回调。该临界区同时屏蔽本核中断并使用硬件 `testset` 跨核锁：当前 SDK 的普通 `spin_lock()` 配置仅关闭本核中断，不足以单独保护双核状态。锁内不做广播、排队或耗时清理。会话重置集中在 `app_core`，避免 parser、ATT 和 USB 同时执行重置。旧工作暂忙时，复合及普通 RDX 会话释放均进行退避重试：先 250 ms，再 1 秒、5 秒，最终降至每 30 秒一次；原 ACL 断开或入口容量变化不会取消尚未完成的重试，也不会以超时冒充 `READY`。若定时器创建持续失败，复合会话释放的第二入口保持关闭并打印 `rearm timer unavailable; activity retries`，后续业务/按键或其他入口事件会再次尝试安排或执行恢复；单独的恢复定时器故障不会关闭已稳定开启的零 ACL 广播。若运行时进入 `FAILED`，不能重新认领 RDX，需整机重启后重新建立会话。重试期间有额外唤醒，实际功耗待测。

空口关闭不保证手机扫描列表立即移除 Windows/手机系统缓存的旧结果，应以空口抓包和实际建链结果判定。

## 4. 睡眠保护边界

本次只改变第二入口是否值得开放，不改变双 ACL controller 保护的基本判定依据：

- 按 wrapper 的真实物理 ACL 数、广播关闭/重开是否在途以及故障状态决定 `system_sleep_block`；广播速率不再参与判定。
- 单 ACL 的快档与慢档均允许睡眠，广播稳定开启本身不再阻止睡眠；能否实际休眠仍取决于其他低功耗投票。
- 单 ACL 时广播准备、关闭/清理/重开提交在途仍阻止睡眠；两条 ACL 与故障锁定始终阻止，不能仅凭 owner 状态解除双 ACL 保护。零 ACL 沿用原策略。

**2026-11-09 板测补充**：旧版入口常开且慢档仍持有门禁时实测约 3 mA；`COM3_2026-11-09_14-28-21.log` 显示慢档只在关闭确认到重开准备之间放开约 2 ms，系统没有稳定睡眠窗口。放行单 ACL 睡眠后共两轮板测：`COM3_2026-11-09_14-51-35.log` 慢档睡眠中手机接入 1 次；`COM3_2026-11-09_15-59-06.log` 快档与慢档均出现持续 `S<>w[]`，慢档睡眠中手机两次接入并在 `0x0051` 上认领 RDX，2→1 后回快档、120 秒再转慢，复合 owner 关闭与 `rdxclose` 重开正常。两版日志合计 3 次接入未触发 `bb_le_power.c:352` 断言或异常复位；用户反馈新策略测试了三次，但本次日志中可核实第二 ACL 接入为两次。业务唤醒切快档的同时记录 1 次 `timer_no_response`（app_core）；日志中的回调地址在当前 ELF 对应 `input_service`，不能据此认定任务当时的 PC 或告警根因，需单独定位。用户万用表实测单连接低功耗 **0.5–2.2 mA 跳动，尖峰 2.2 mA、目测粗估约 1 mA**；这是整机读数，未按广播档位分别记录或积分。同条件 A/B、快档睡眠期间接入、绑定重连、双 ACL 业务并发与长稳仍未验证；若后续出现断言/复位，须回退到保守版本并等待修正版 controller。复合 owner 的关闭规则与此独立。

控制器问题与历史功耗证据见 [3-5](3-5.BLE双ACL低功耗断言问题复盘与量产最佳实践.md) 和 [6-2](6-2.T2620BLE连接后低功耗设计.md)。
