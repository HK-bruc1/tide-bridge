## 1. 问题与日志

两个 `app_ble` wrapper 共用一个地址、一个复合 GATT profile；正常情况下只有一个空闲 wrapper 在广播，并非两组广播同时发射。广播是否开启取决于空闲物理连接入口，而 RDX 和 HID owner 是另外一层全局唯一的业务资源。

`COM3_2026-11-06_14-58-28.log` 中：

1. 第一条 ACL `0x0050` 建立后，空闲 wrapper 开启第二入口；随后同一链路形成 HID + RDX 复合 owner。
2. 第二入口到期并确认关闭后，PC 上的 `getlist` 业务又唤醒了 120 秒入口。
3. 随后第二条 ACL `0x0051` 建立，RDX claim 返回 `4`（runtime 不是 READY），之后该 ACL 断开。仅凭这份日志不判断第二个连接端的具体身份。

根因是原入口策略只考虑物理 ACL 数量，没有考虑同一 ACL 已持有两个全局 owner。此时继续开放入口会让另一设备看到设备、甚至建立 ACL，却无法取得已被占用的 HID 或 RDX。

日志还出现一次 `timer_no_response`。其原因和影响需要单独分析，本次不把它归因于复合 owner，也不宣称已经解决。原始日志包含安全相关信息，分享时应先脱敏。

### 1.1 `HID关了_BLE传输断开_LATENCY49_带诊断日志.txt` 判读

该日志是关闭 HOGP 的对照，不代表 PC HID + PC RDX 复合会话占满两条 ACL：

- `0x0050` 是残留的 PC 自动重连 ACL，断开快照为 `rdx=0 hid=0`。
- `0x0051` 建立后成为唯一的 RDX owner，始终没有 HID owner。
- 日志只有 `Just Works ... provisional HID candidate`，没有 HID owner
  建立记录；关闭 HOGP 的构建也不含 HID Service 和 `0x1812` 广播数据。

`00:00:07.311` 两条 ACL 并存时，固件记录
`connected_count=2; defer idle-wrapper advertising`，说明当时没有开放
第二入口。`00:00:35.972`，`0x0051` 以 reason `0x13` 断开；
`00:00:35.976` 的断开快照仍是清理前快照，显示 `links=2 rdx=1 hid=0`，
随后 `00:00:35.995` 的物理连接数已变为 `links=1`。旧策略在二变一后
重新开放第二入口，于是产生：

```text
00:00:35.996 [BLE_ENTRY] topology entry=persistent
00:00:35.999 [RDX_BLE_SESSION] runtime READY: FIFO drained and workers idle
00:00:36.001 [RDX_BLE_LINK] advertising restart on released wrapper
00:00:36.006 [BLE_ENTRY] open ret=0 wrapper=1 adv_interval=160
```

因此，这份日志证明的是“旧策略在 RDX ACL 断开、只剩一条无 owner ACL
时重开入口”，并未证明复合 owner 满占两条 ACL 时违规广播。

日志随后在 `00:00:36.009` 收到旧广播集清理的
`close confirmed status=0x42`，并在 `00:00:36.015` 重新打开。`0x42`
表示该广播集已不存在或被连接消耗，属于断开清理与重开之间的短时序
抖动。临时单路策略会直接阻止 `links=1` 时的这次重开，不再出现该段。

## 2. 当前准入规则（2026-11-16 临时单路）

| 物理拓扑和 owner | 当前行为 |
| --- | --- |
| 零 ACL | 允许统一的 RDX + HOGP 广播，继续遵守关机、DUT、格式化、Wi-Fi 等既有抑制条件。 |
| 任意一条 ACL | 不开放第二入口。无论它只持有 HID、只持有 RDX、没有 owner，还是同时持有 HID + RDX，都不广播。 |
| 逻辑释放 RDX、但原 ACL 和 HID 仍在 | 保持第二入口关闭；`READY` 不构成重开理由。 |
| 第二入口关闭边界竞态中出现第二条 ACL | 不建立 RDX/HID 会话，并在 Connection Complete 中主动断开新链路。 |
| 最后一条 ACL 断开并完成物理入口清理 | 回到零 ACL 后才允许统一广播重新发现设备。 |

临时开关定义在 `SDK/apps/earphone/include/t2620_project_config.h`：

```c
#define TCFG_T2620_BLE_SECOND_ENTRY_ENABLE 0
```

`0` 为当前单路策略，`1` 恢复历史第二入口策略。第二入口的复合 owner、
关闭确认、故障保护和 runtime epoch 代码仍保留，因此回退不需要重做底层
广播生命周期。

在单路策略下，PC HID 与 PC RDX 必须复用同一条复合 ACL。PC 用两个不同
BLE 身份建立两条 ACL 时，后到链路会被断开。这是本次临时方案的明确限制。

复合 owner 的历史关闭规则仍然有效，但当前已由“任意 ACL 即关闭入口”的
更严格条件覆盖。HID 先到、RDX 先到、CCC 暂时关闭、加密状态变化或 HID
suspend 都不会重开第二入口。

广播关闭期间继续保留原广播句柄及睡眠保护，等待控制器完成确认。关闭
失败、超时和无可信句柄继续进入保守故障保护。广播已被连接消耗、而该
连接在 `app_core` 处理前断开时，仍按正常消耗处理，不误报故障（第 5.3 节）。

## 3. PC App 释放 RDX 后的接管

PC App 不再使用 RDX 时，必须在仍持有 RDX owner 的连接上发送 `*APP#custom#rdxclose#1#`。仅关闭 Windows GATT 对象或取消 CCC 订阅，不能代替该命令。报文分片和无专用回包等约束见 [3-4](3-4.PC_APP逻辑断开无法释放RDX会话问题复盘与处理方案.md)。

复合链路处理顺序：

1. RDX 进入 `QUIESCING` 并释放 RDX owner，PC 的 ACL、HID owner、HID CCC 和加密状态不因这条命令被主动清除。临时单路策略下第二入口仍关闭。
2. 旧接收队列到达认证 FIFO 屏障，重新中止旧工作后进入 `RESETTING`；只有记录、文件、OTA 和发送等旧工作满足原有空闲条件，才能完成缓冲区重置。
3. 实际进入 `READY` 时，只要仍存在任意 ACL，就不广播。只有最后一条 ACL 断开并完成 wrapper 清理、连接数变为零后，统一广播才可恢复。
4. 单路期间不允许另一设备认领空闲的 RDX。若连接竞态仍产生第二条 ACL，新链路会被主动断开，不能进入 ATT 认领阶段。

`READY` 和入口容量在短临界区中一起发布，并通过 runtime epoch 排除旧释放回调。该临界区同时屏蔽本核中断并使用硬件 `testset` 跨核锁：当前 SDK 的普通 `spin_lock()` 配置仅关闭本核中断，不足以单独保护双核状态。锁内不做广播、排队或耗时清理。会话重置集中在 `app_core`，避免 parser、ATT 和 USB 同时执行重置。旧工作暂忙时，复合及普通 RDX 会话释放均进行退避重试：先 250 ms，再 1 秒、5 秒，最终降至每 30 秒一次；原 ACL 断开或入口容量变化不会取消尚未完成的重试，也不会以超时冒充 `READY`。若定时器创建持续失败，复合会话释放的第二入口保持关闭并打印 `rearm timer unavailable; activity retries`，后续业务/按键或其他入口事件会再次尝试安排或执行恢复；单独的恢复定时器故障不会关闭已稳定开启的零 ACL 广播。若运行时进入 `FAILED`，不能重新认领 RDX，需整机重启后重新建立会话。重试期间有额外唤醒，实际功耗待测。

空口关闭不保证手机扫描列表立即移除 Windows/手机系统缓存的旧结果，应以空口抓包和实际建链结果判定。

## 4. 睡眠保护边界

本次同时关闭第二入口并拒绝第二条 ACL，睡眠保护边界调整为：

- 零 ACL：沿用原有广播和低功耗投票；广播本身能否睡眠仍取决于其他低功耗条件。
- 一条 ACL：不运行第二入口广播；连接本身不触发双 ACL 睡眠门禁。
- 第二路连接竞态或拒绝断开尚未完成：暂时保留门禁，避免控制器在硬件连接仍存在时进入不受保护的睡眠。
- 广播关闭/清理或故障保护在途：继续阻止相关风险窗口内睡眠。故障锁定不能仅凭 owner 状态解除。

上述关于“单 ACL 第二入口快慢档均可睡眠”的 2026-11-09 数据属于历史策略实测；当前临时单路版本仍需重新做板测确认。

**2026-11-09 板测补充**：旧版入口常开且慢档仍持有门禁时实测约 3 mA；`COM3_2026-11-09_14-28-21.log` 显示慢档只在关闭确认到重开准备之间放开约 2 ms，系统没有稳定睡眠窗口。放行单 ACL 睡眠后共两轮板测：`COM3_2026-11-09_14-51-35.log` 慢档睡眠中手机接入 1 次；`COM3_2026-11-09_15-59-06.log` 快档与慢档均出现持续 `S<>w[]`，慢档睡眠中手机两次接入并在 `0x0051` 上认领 RDX，2→1 后回快档、120 秒再转慢，复合 owner 关闭与 `rdxclose` 重开正常。两版日志合计 3 次接入未触发 `bb_le_power.c:352` 断言或异常复位；用户反馈新策略测试了三次，但本次日志中可核实第二 ACL 接入为两次。业务唤醒切快档的同时记录 1 次 `timer_no_response`（app_core）；日志中的回调地址在当前 ELF 对应 `input_service`，不能据此认定任务当时的 PC 或告警根因，需单独定位。用户万用表实测单连接低功耗 **0.5–2.2 mA 跳动，尖峰 2.2 mA、目测粗估约 1 mA**；这是整机读数，未按广播档位分别记录或积分。同条件 A/B、快档睡眠期间接入、绑定重连、双 ACL 业务并发与长稳仍未验证；若后续出现断言/复位，须回退到保守版本并等待修正版 controller。复合 owner 的关闭规则与此独立。

控制器问题与历史功耗证据见 [3-5](3-5.BLE双ACL低功耗断言问题复盘与量产最佳实践.md) 和 [6-2](6-2.T2620BLE连接后低功耗设计.md)。

1. 手机 RDX 先连、PC HID 后连的建立顺序，以及双 ACL 下 PC 断开或两端均断开的剩余组合；PC HID 先连、手机后接入已覆盖两次。
2. 用空口抓包确认关闭边界上的在途建链不被误踢，以及关窗后空口确实不再广播。
3. 长时间业务、持续忙碌重试、抑制状态、异常关闭及反复重连；精确电流需仪器测量。不能把主机模拟、编译成功或历史测量当成这些结果。

### 5.3 2026-11-11 超距长时间离开后回连不再广播

**现象**：PC HID 与 PC RDX 共用一条 ACL 时，超出距离使 ACL 断开，此时设备的 RDX 会话已释放，并开启广播。如果马上回来，PC HID 能自动回连，PC APP 也能扫描到第二入口。如果等几分钟再回来，PC HID 不再自动回连，PC APP 也扫描不到设备，只能重启设备恢复。

**根因**（`COM3_2026-11-11_15-17-26.log`，含授权信息，本地保留不入库）：

1. 15:21:02 第二次超距断开（reason `0x08`）。断开清理正常，RDX 回到 READY，零 ACL 广播重开。
2. 15:23:03 零 ACL 超过 120 s，广播转为慢档（`ADV_POLICY state=3`），并切断 PA4 外设电源（`POWER_CUT`）。
3. 15:24:16 PC 在 wrapper0 上回连。连接回调在 btstack 任务中同步恢复 PA4（SD io、LED 重新初始化），阻塞约 400 ms。在这期间链路以 `0x3e`（建链失败）断开。
4. app_core 处理时，wrapper0 已没有连接，但它的广播集已被这次连接用掉，`app_ble_adv_handle_get()` 返回 `0xff`。原代码仍把 wrapper0 当作正在广播，进入关闭流程，并因句柄失效判为 `radio fault reason=invalid_adv_handle`，按故障保护锁定到重启（protection retained until reboot）。
5. 此后设备再也不广播，PC HID 与 PC APP 都无法连接。

快速返回时不会出现：此时外设电源未切断，连接回调不阻塞，链路也没有建链失败。

**修改**（`rdx_ble_server.c`）：

- 在 Connection Complete 中，如果连接发生在正在广播的 wrapper 上，登记"该 wrapper 的广播集已被连接用掉"。
- `rdx_ble_entry_radio_apply()` 遇到已登记、当前无连接且广播句柄无效的 wrapper 时，按正常情况处理：打印 `[BLE_ENTRY] advertising consumed by released link wrapper=N`，只清除广播记录，随后在空闲 wrapper 上重开广播。这与"连接仍在线时只清记录"的已有分支一致。
- 未登记的无效句柄仍按原故障保护处理。登记在该 wrapper 重开广播或退出复位时清除。
- 不改 `0x3e` 本身：设备重新广播后，PC 再回连一次即可。

**验证**：

| 项目 | 结果 |
| --- | --- |
| 主机测试 | `test_ble_entry.py` 新增 `check_released_connection_consumed_advertising`：连接用掉广播后，在 app_core 处理前即断开，不应锁定故障，并应在空闲 wrapper 上重开 100 ms 广播；未登记的无效句柄仍判为故障。去掉修复时该用例失败，加上修复后通过 |

| 修复后超距 | `COM3_2026-11-11_15-46-49.log`。第一次断开后马上返回：14 s 后 PC HID 回连，PC APP 接入复合会话，录音正常。第二次离开约 4.5 min，其间已慢广播并切断外设电源：回连时同样阻塞约 400 ms，但链路未断开，PC HID 回连、PC APP 接入，全程无 `radio fault`、assert 或复位 |

**留给压力测试**：PC HID + PC APP 复合连接下，反复离开超过 3 min（确认日志出现 `ADV_POLICY state=3` 与 `POWER_CUT`）后返回。如果出现 `0x3e`，应看到 `advertising consumed by released link`，随后 `open ret=0`，PC 自动回连成功，且不出现 `radio fault`。
