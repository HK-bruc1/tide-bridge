# 10-14. CDC 传输速度排查与优化方案

> 状态：方案待定，**未实施**。客户确认需要提速后再安排。日期：2026-11-19。
>
> 结论：CDC 文件下载的瓶颈在 USB 发送端每次只挂一个 64 B 包，包与包之间有空档。PC 主机程序、SD 读速和 CPU 占用都不是瓶颈。分两阶段处理：先优化内存测速（只看 USB 发送链路），再优化真实文件（只看读盘对发送的干扰）。在单缓冲方式下，理想上限约 800～850 KB/s。要达到 1 MB/s 以上，必须 BR28 的 USB 发送端支持双缓冲或多包 DMA，这一点需要先找 FAE 确认。
>
> 相关文档：[10-4 CDC 通用文件传输业务方案](10-4.CDC通用文件传输业务方案.md)（§7.3、§8、附录 A.1–A.7 记录了历史优化过程与维护规则）。

## 2. 瓶颈分析

### 2.1 时间花在哪

USB 1.1 全速的设备描述符 `bcdUSB=0x0110`，Bulk 包长 64 B。规范上每 1 ms 帧最多 19 包，即约 1,216,000 B/s。

| 项目 | 数值 |
| --- | --- |
| 内存测速 664,303 B/s，加 4120/4096 帧头开销 | 约 10,440 包/s |
| 平均每包耗时 | 约 96 µs |
| 一个 64 B 包在线上的时间（令牌 + 数据 + 握手 + 包间隔 + 位填充） | 约 52～56 µs |
| **每包空档** | **约 40～46 µs** |

当前发送路径是单缓冲、串行的（`SDK/apps/common/device/usb/device/cdc.c` 中的 `cdc_factory_write_packet()`，以及 `SDK/apps/common/device/usb/device/usb_factory_cdc.c` 中的 `factory_cdc_tx_irq()`）：

1. 主机取走包 N，并回 ACK。
2. 设备进入 USB 中断，经 `usb0_g_isr` → `usb_isr` → `cdc_tx_wakeup` → `factory_cdc_tx_irq` 层层分发。
3. 中断里拷贝 64 B 到 DMA 缓冲，写 DMA 地址和长度，置位 `TxPktRdy`。
4. 在这之前主机来取数据只会收到 NAK，要等主控下一次重试。
5. 包 N+1 这时才开始发送。

吞吐 = 64 B ÷（线上时间 + 中断响应与处理 + 主机 NAK 重试间隔）。真实文件下载时，读盘又会干扰中断，再损失约 10%（664 → 594）。

### 2.2 疑点：中断热路径全部在 Flash 中执行

用 `C:/JL/pi32/bin/llvm-nm.exe` 查当前 `SDK/cpu/br28/tools/sdk.elf`。代码区从 `CODE_BEG = 0x6000100` 开始，是 Flash 映射，经 cache 执行；`0x001xxxxx` 是 RAM。

```
06003178 t usb0_g_isr                ← Flash
06002de6 t cdc_tx_wakeup             ← Flash（factory_cdc_tx_irq 已内联）
06002d88 t cdc_factory_write_packet  ← Flash
06002d64 t cdc_factory_tx_busy       ← Flash
06002d30 t cdc_factory_configured    ← Flash
06094766 t usb_read_txcsr            ← Flash（cpu.a）
0609455e t usb_write_txcsr           ← Flash（cpu.a）
0609452e t usb_set_dma_taddr         ← Flash（cpu.a）
06094776 t usb_write_ep_cnt          ← Flash（cpu.a）
06094592 t usb_clr_intr_txe          ← Flash（cpu.a）
06087504 t sys_timer_get_ms          ← Flash
00121f5c T jiffies_usec              ← RAM（对照）
```

每秒约 1 万次的中断都要走这条路径。路径上有 7～8 次跨函数的寄存器访问，和 SD、FAT、蓝牙、音频代码共用 I-cache；一旦 cache 未命中，就要等 SPI Flash 取指。

旁证（**尚未证实**）：

- 内存测速时 cpu0 占 26%。按每秒约 10,440 次中断平摊，每次中断加配套任务约 25 µs，相当于 160 MHz 下约 4000 个周期，对这么少的工作量来说偏大。
- 10-08 测到 724，今天是 664。这期间固件增加了 HOGP、BLE、充电等代码，cache 压力变大。但也可能是 PC 或 USB 口不同，需要用同一环境排除。

### 2.3 理论天花板估算（推算，非实测）

| 方式 | 每包耗时 | 预期吞吐 |
| --- | --- | --- |
| USB 规范上限（包间无空档） | 约 52 µs | 约 1,210 KB/s，仅为理论值 |
| 发送双缓冲或多包 DMA | 约 55～60 µs | **约 1,000～1,100 KB/s** |
| 单缓冲，固件优化到理想状态 | 约 75～80 µs | **约 800～850 KB/s** |
| 10-08 历史最好 | 约 87 µs | 724 KB/s |
| 当前 | 约 96 µs | 664 KB/s |

单缓冲的空档由两部分组成：

- **设备侧**：中断响应和处理。可以压缩，理想情况下约 3～8 µs。
- **主机侧**：NAK 后 xHCI 什么时候重试，固件控制不了，不同 PC 差别较大。

所以只靠固件优化，到不了 1 MB/s。

## 3. 第 0 步：测量基线（必做，不改业务逻辑）

1. 固定测试环境：同一台 PC、同一个 USB 口，不经过 Hub，同一个主机脚本。每个版本跑 3 轮内存测速（`*APP#file#bench#10000000#4096#`）取均值；文件下载固定用 SN18 同一个文件。
2. 打开 `TCFG_T2620_CDC_TX_STATS_ENABLE` 和 `TCFG_T2620_CDC_TX_TIMING_ENABLE`（在 `t2620_project_config.h` 中，默认都是 0），记录每秒中断次数、`submit_us` 的均值和最大值。
3. 新增诊断统计（仅调试开关下生效）：**两次 IN 完成中断的间隔分布**。用 RAM 中的 `jiffies_usec` 采样，分为 <60、60～80、80～100、100～200、>200 µs 几档，每秒汇总打印一次，**中断里不打印**。后面每一步都用这个分布衡量空档变化。
4. 记录统计开关本身对吞吐的影响。最终验收以关闭统计后的数据为准。

## 4. 第一阶段：内存测速优化（目标 664 → 720 以上，争取 800）

每一项单独提交、单独测，没有收益就撤回。

| 编号 | 改动 | 涉及文件 | 预期 | 风险 |
| --- | --- | --- | --- | --- |
| 1.1 | **中断热路径放 RAM**：`usb0_g_isr`、`usb_isr`、`cdc_tx_wakeup`、`factory_cdc_tx_irq`、`cdc_factory_write_packet`、`cdc_factory_tx_busy`、`cdc_factory_configured` 加 `AT(.volatile_ram_code)`（`SDK/cpu/br28/sdk.ld:655` 放入 RAM 的 `.data_code`，现有用法见 `msd_upgrade.c:31`）。用编译后的 `llvm-nm` 地址确认生效 | `usb_config.c`、`cdc.c`、`usb_factory_cdc.c` | 回到约 720 | 低。代价是 RAM 多占几百字节，需要核对 RAM 余量 |
| 1.2 | **热路径直接读写寄存器**：在热路径上不再调用 `cpu.a` 中的 `usb_read_txcsr`、`usb_write_txcsr`、`usb_set_dma_taddr`、`usb_write_ep_cnt`、`usb_set_intr_txe`、`usb_clr_intr_txe`，改用 RAM 内联实现；非热路径不动。中断里的 `sys_timer_get_ms()` 改为读 RAM 变量，或把超时判断移回任务 | `cdc.c`、`usb_factory_cdc.c` | +3～5% | 低。寄存器语义要和 `cpu.a` 实现逐一核对（反汇编 `sdk.lst`） |
| 1.3 | **零拷贝**：DMA 地址直接指向队列项 `item->bytes + offset`，去掉每包 64 B 的 `memcpy` | `cdc.c`、`usb_factory_cdc.c` | +1～3% | 低～中。需确认 DMA 对齐要求和缓冲区是否在 RAM，还要确认队列项在 DMA 完成前不会被改写 |
| 1.4 | **中断快速分发**：`usb_isr()` 入口先判断"只有 CDC IN 完成中断"，直接调用发送函数，不走通用分发 | `usb_config.c` | +2～5% | 中。不能影响 EP0、复位、挂起处理 |
| 1.5 | **评估 USB 中断优先级**：当前 `usb_g_isr_reg(usb_id, 3, 0)`（`usb_device.c:62`）。可以适当提高，但不能高于蓝牙控制器 | `usb_device.c` | 看蓝牙负载 | 中。需要回归 BLE 连接态、HOGP 和录音 |
| 1.6 | **生产端背压**：查清队列满（`TX_REJECT rc=-2`，每秒 225～300 次）后的重试机制。如果是轮询重试，改为低水位事件唤醒，减少调度和 CPU 占用 | `usb_factory_cdc.c`、`rdx_cdc_file.c` | 间接收益 | 低 |
| 1.7 | **确认硬件能力**：问 FAE，或做最小实验（挂 128 B、计数设为 128，看主机是否收到两个正确的 64 B 包）。确认 BR28 的 USB 发送端点是否支持双缓冲 FIFO，或 DMA 长度大于 maxp 时由硬件自动分包。接收方向有 `usb_set_dma_dual_raddr`，发送方向没有对应接口 | — | 支持的话能到 1.0～1.1 MB/s | 高。取决于芯片能力 |

1.7 不依赖其他项，可以先发给 FAE 问。

## 5. 第二阶段：真实文件优化（目标：与内存测速相差 5% 以内，当前约 10%）

读盘本身速度够用（约 1.4 MB/s）。真实文件变慢，是因为读盘干扰了 USB 中断，不是读得慢。

| 编号 | 改动 | 目的 |
| --- | --- | --- |
| 2.1 | **诊断**：查 SD 驱动和 FAT 读路径中是否有长时间关中断（`local_irq_disable`、OS 临界区、忙等 DMA 完成）。对比读盘时和不读盘时的中断间隔分布（第 3 节第 3 步） | 区分是关中断造成的，还是 cache 被挤掉造成的 |
| 2.2 | **USB 中断和读盘分到不同核**：USB 中断在 cpu0；`cdc_reader` 由 `rdx_cdc_source.c:136` 的 `os_task_create(source_worker, NULL, 2, 2048, 0, "cdc_reader")` 创建，先查它实际跑在哪个核，再考虑绑到 cpu1 | 读盘不再挡住中断 |
| 2.3 | **加大单次读盘块**：当前 `file_stream.block = 4096`（`rdx_cdc_file.c:113`）。读盘可以改成一次 16～32 KB 走多块连续读，再按 4096 B 切成 CDF1 帧，**协议块大小不变** | FAT 调用次数和每次读的固定开销降到 1/4～1/8，cache 抖动也减少。代价是 RAM |
| 2.4 | **读和发的流水**：确认现有队列是否已经做到"发第 N 块时同时读第 N+1 块"。如果没有，改成乒乓或预读 | 让 USB 一直有数据可发 |
| 2.5 | 查当前 SD 时钟配置，视情况提高 | 缩短每次读盘占用总线的时间 |

## 7. 约束（沿用 10-4 §8）

- 中断里不打日志、不读盘、不组帧、不算 CRC、不写无界循环；中断里每次最多续交一个包，1.7 落地后再重新评估。
- 不能为了提速去掉 CRC、DMA 忙保护、generation、取消或超时。
- 不能为了提速提高串口波特率：CDC 不经过实体 UART，改了没用。
- 跨队列合包（10-4 附录 A.5，只快了 0.067%）不再重做。
- 每一项改动都要回归：取消、拔线、超时、RX 命令并发、录音抢占文件服务、BLE 连接态低功耗。2026-10-08 18:04 的 `invalid binary header` 故障一直没有关闭，仍需单独回归。

## 8. 待确认事项

1. 客户是否真的需要提速；目标是"回到约 720"、"约 800"，还是"≥ 1 MB/s"。目标不同，工作量相差很大。
2. FAE：BR28 的 USB 发送端点是否支持双缓冲或多包 DMA（对应 1.7）。
3. 在同一环境下复测 10-08 的 724，确认 724 → 664 是固件变化引起的，还是测试环境不同。
