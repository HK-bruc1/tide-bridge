# 10-5. 录音满盘保护与 APP 格式化恢复

> 更新日期：2026-10-14。
> 状态：固件修复已实现，14 组主机测试和目标固件 ELF 编译链接通过；现场故障盘恢复、近满盘长录音及 APP 交互仍待实机验收。
> 本文记录本次缺陷、实现和验证，不代表已烧录设备或完成实机闭环。

## 1. 范围与产品原则

本次处理两个相互关联但不能互相替代的问题：

1. 长时间离线录音没有主动空间预留，写到介质耗尽后，RAW 收尾、元数据及 DAT 索引更新缺少可用空间。
2. 文件服务已经故障时，APP 显式格式化也被“文件服务必须健康”的门禁挡住，用户无法通过清空存储恢复使用。

产品原则：**正常录音应在预留空间耗尽前有序停止；默认不自动删除用户数据，但用户明确选择格式化后，不得为了保留异常旧数据而封死恢复入口。**

这里的“满盘停录”指触及固件预留门槛，不要求底层剩余空间真的降到 0。物理 I/O 错误仍是故障，不能伪装成正常容量用尽。

本文不改变录音 RAW 编码或 APP DAT 协议，不引入自动覆盖最老录音，也不承诺修复前已经写满设备上的全部录音都可恢复。

- [4-2. SD NAND FLASH 格式化策略设计](4-2.SD_NAND_FLASH_格式化策略设计.md)：启动保护、显式格式化准入、成功定义及失败策略。

- 本文：本次满盘与 APP 格式化缺陷的证据、修复细节、软件验证和板测清单。

## 3. 根因与修复目标

### 3.1 录音保护过晚

原实现并非完全没有保护：短写、写入失败、元数据失败和队列溢出已有故障停录。但这些处理发生在问题已经出现之后，缺少“为已接收音频和索引事务预留空间”的主动准入与运行时预算。

修复目标不是忽略写失败，而是将可预期的空间耗尽提前转为正常 STOP，使已接收的完整帧、尾块和索引有机会正常落盘。

### 3.2 恢复操作误用了健康服务门禁

旧补丁把 `rdx_uxfile_sd_format()` 与普通文件读写一起包装在 `rdx_record_format_io_enter()` 后面。该入口要求服务状态为 0，因此 `file service=-1` 时连格式化函数体也无法进入。

修复将格式化定义为独立的恢复操作：历史故障可以放行，真实并发占用仍必须拒绝。不能简单删除全部门禁。

### 3.3 完成结果与旧缓存交接不可靠

- APP 原入口未使用格式化返回值，可能把底层拒绝当作成功接受。
- 物理擦除后若仍按普通失效流程刷写旧的脏 DAT 缓存，可能把擦除前的索引重新写回空盘。
- 仅以物理擦除成功为准，无法覆盖 VM 标记失败、新索引初始化或库缓存重载失败。

修复要求“物理擦除 + 空索引初始化与缓存加载 + UXFILE VM 标记写入”全部成功，才对外返回成功；失败保持文件服务不可用，并允许用户再次显式重试。

## 4. 录音容量预算与正常停录

### 4.1 预留计算

`rdx_record_format_space()` 读取已挂载分区、剩余空间和当前 DAT 大小，计算：

```text
reserve_bytes = max(1048576, 2 * (DAT_bytes + 640) + 65536)
audio_budget  = max(0, free_KiB * 1024 - reserve_bytes)
```

- 最低保留 1 MiB；DAT 较大时，按两份增长后的索引事务空间提高预留门槛。
- 每份索引额外计入 640 字节条目预算；64 KiB 余量用于元数据、目录、簇分配及已接收音频。
- 当前最大音频在途缓冲为 `128 * 80 + 8000 = 18240` 字节，不到 19 KiB。这是工程预算，不是对任意介质故障或无限阻塞的保证。
- JL `fget_free_space()` 的输出单位是 KiB，其函数返回值按 SDK 说明无意义；检查输出哨兵、分区总容量及 `free <= total`，而不是把返回值当作标准文件系统错误码。
- 分区不可用、查询输出无效、DAT 无法读取或关闭失败均拒绝录音，不把未知空间当作可用空间。
- 计算使用 64 位整数，导出的录音预算上限为 `UINT32_MAX`，避免 KiB 换算和索引增长溢出。

这里预留的是录音不得使用的容量，不会预先创建一个占满预留空间的大文件。

### 4.2 启动与恢复录音准入

**准入必须在音频流创建之前。** 2026-10-22 现场日志 `满储存几率卡死.log` 证明：原先唯一的门禁位于 sink 的 `NODE_IOC_START`（`rdx_record_run_init()`）中，触及预留时错误返回给 `jlstream_start()`，JL 回滚半启动的多线程流时写已释放内存（`cpu0 write hmem excption`，USP 落在 `jlstream_1` 栈内），芯片软复位，BLE 随之断开。

现行规则：

1. `rdx_record_local_storage_admit()` 在 app_core 的三个入口准入，任何会话代次、按键上下文、开始提示音、LED、停止播放、APP 触发及音频流变更之前执行：
   - APP 命令 `rdx_record_cmd_handle_internal()`（含延迟重试；索引忙先延迟，空闲后才查询）；
   - 按键/HID `rdx_app_device_record_set()`；
   - DUT/CDC `dut_accept()`，在 ID/LAST 预留前返回 `STATE`。
2. 判据：本地落盘的 START，以及本地落盘会话 PAUSE 后的 RESUME。只有在线 F19 灵感纯推流豁免；离线 F19 与会议录音均需准入。重复命令、PAUSE、STOP 不查询空间。
3. `rdx_record_storage_admit()` 在存储 worker 未创建/仍活跃、故障锁存或文件服务失败时一律拒绝（`-1`）；扣除预留后不足一个 8000 字节聚合块返回 `-2`。
4. 反馈：`-2` 播放 `tone_en/no_sd.*`（`not_enough_storage.mp3`），**不播开始提示音、不切录音灯**；`-1` 仅日志。APP 收到现有状态回执：START 被拒为 STOP，RESUME 被拒保持 PAUSE，原文件仍可 STOP 正常保存。不新增协议错误码。

两个产品录音初始化分支仍在生成文件之前调用 `rdx_record_storage_check_start()` 作为纵深防御，返回值原样交给 sink。sink 初始化失败**不再**向 `jlstream_start()` 返回错误：节点照常启动、丢弃音频帧，由 `rdx_record_run_init_failed()` 按 `-2` 正常满盘或其它故障走既有可重试 STOP，不触发启动失败撤销绑定。该路径只覆盖准入后的竞态，此时开始提示音可能已播。

存储 worker 的 `rdx_record_storage_begin()` 再次检查空间。查询和 worker 活跃状态发布受文件 I/O 准入保护；格式化只能观察到“仍持有 I/O 准入”或“录音 worker 已活跃”，不能从两者交接间隙插入擦盘。

纯在线、不落本地盘的流式录音不适用本地写盘预算。

### 4.3 运行时预算

1. 音频回调只检查/扣减内存预算并投递完整帧，不在回调中查询文件系统。
2. 存储 worker 每次成功写出 RAW 块后复核空间，减去 `accepted - persisted` 的在途字节。
3. 复核只允许缩小当前预算，不能根据可能滞后的剩余空间快照把已经消耗的预算补回来。
4. 最后一帧接收后若不足再接收一帧，立即标记 `full` 并请求停录。即使同时用尽最后一个 FIFO 槽位，也应判为正常低空间停录，而非队列溢出。

`rdx_record_storage_push()` 的内部返回值为：

| 返回值 | 含义 |
| --- | --- |
| `0` | 完整帧已接收 |
| `1` | 空间预算不足/已触及门槛，本帧未接收；按正常满盘 STOP 收尾 |
| `-1` | 存储状态、输入或队列等故障；走错误停录 |

### 4.4 STOP 与再次录音

低空间调用 `translation_ear_recoder_storage_full()`，通过既有可重试 app_core STOP 通道处理，内部原因值为 `-27`。它不设置永久存储 I/O 故障。

收尾时排空已接收帧，写出剩余完整尾块，再按原流程保存索引。正常容量停录应看到：

```text
[REC_SPACE] reserve reached: draining accepted audio
[REC_STORE] ... accepted=... persisted=... ... full=1 error=0
```

部分停录由音频回调直接发现，未必打印第一行；以最终统计和索引结果共同判定。`accepted` 与 `persisted` 是字节数，正常停录应相等；这组统计本身不能替代 DAT 保存、掉电重启和实际下载验证。

删除文件释放空间后可再次录音，不要求重启或格式化。若同时出现真实短写、元数据失败、容量复核失败或队列溢出，仍应报告故障，不得因为 `full=1` 就忽略错误。

## 5. APP 显式格式化恢复

### 5.1 准入规则

| 状态 | 处理 |
| --- | --- |
| 文件服务健康且无实际占用 | 允许显式格式化 |
| 旧索引/历史存储错误导致 `file service=-1`，无实际占用 | 允许显式格式化，不要求先恢复旧 DAT |
| 正在初始化/整理索引、普通文件 I/O 或另一轮擦除 | 拒绝，不能并发修改文件系统 |
| 录音未 STOP、录音 worker 活跃、播放尚未释放、下载/同步、CDC 文件租约或工厂文件操作 | 拒绝后端擦除，等待业务真正释放资源 |
| PC 模式、OTA、已接受关机，或启用 Wi-Fi 传输时的活动传输 | 拒绝，保留原有所有权和生命周期约束 |

APP 路径可以先使播放列表失效并请求停止播放，但这不等于后端允许擦除仍被播放器占用的介质。后端执行时的 `rdx_app_format_is_busy()` 与 `rdx_record_format_erase_enter()` 必须再次检查实际状态。

`rf_erasing` 在整个恢复期间独占；即使内部索引初始化暂时发布 ready，普通文件访问和 CDC 下载也不能在擦除事务完成前进入。

### 5.2 擦除与重建顺序

1. 取得专用擦除准入，并锁定 `dat_opera_mutex`。
2. 关闭库读句柄，释放旧列表快照，再调用原格式化函数体。
3. 只有 `f_format()` 成功后，才清除旧 DAT 的 dirty 标记、历史库 I/O/PC 刷新错误及固件旧恢复事务状态；禁止在缓存失效时刷回擦除前的 DAT。
4. 初始化空索引并加载新缓存，检查 UXFILE VM ID `159` 的 `0xAA` 标记写入结果；不使用开机通用分支的 VM ID `63` 代替它。
5. 全部成功才清除录音 worker 的故障及旧失败启动清理状态，恢复文件服务；否则保持失败状态。
6. 释放独占状态，向有回调的调用者恰好回调一次；成功为 `MEM_FORMAT_RESULT_OK`，失败为 `MEM_FORMAT_RESULT_FAIL`。

分区查询改为判空安全的 `rdx_record_format_capacity()`；无分区对象时返回 0，不再因格式化失败路径读取空指针。

**物理擦除是不可逆操作。** 若擦除已成功而后续 VM 或缓存加载失败，对外仍应报失败，但不能把这理解为旧录音仍在。重试可以重新初始化空盘，不会恢复已经擦掉的数据。

### 5.3 APP 结果处理

`rdx_app_format_handle()` 返回 `rdx_uxfile_sd_format()` 的实际状态，APP 格式化处理不再无条件发送成功接受 ACK。请求分配/投递失败、业务忙、后端拒绝或执行失败均不能回报成功。

协议完成结果也在索引加载及 VM 写入判定后生成，而不是在物理擦除后提前成功。现有会话 token 校验仍有效，过期会话的请求/ACK 不应作用于新连接。

本次没有另造新的格式化协议或 APP UI。真实 APP 对 ACK、完成结果及容量刷新的处理顺序，尤其长耗时格式化下的超时表现，仍列入板测。
