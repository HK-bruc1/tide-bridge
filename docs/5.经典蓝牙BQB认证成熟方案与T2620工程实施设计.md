# 经典蓝牙 BQB 认证成熟方案与 T2620 工程实施设计

> 更新时间：2026-09-05<br>
> 文档状态：方案设计，尚未实施<br>
> 适用工程：T2620 / AC701N（BR28）/ RDX + HOGP 复合 BLE 产品<br>
> 核心结论：使用同一受控源码生成独立的产品、PTS 和 RF BQB 构建产物；由一个经典蓝牙策略模块在启动时锁存人格并统一控制 BR/EDR，量产产物默认且不可切换地保持经典蓝牙关闭。<br>
> 认证边界：打开 Inquiry Scan/Page Scan、让手机搜到设备或通过八击进入 RDX 产测 DUT，只能说明某个测试入口可用，不能据此判定已经满足或通过 BQB 认证。

## 1. 文档目标

当前产品只把经典蓝牙用于 DUT 产测。正常启动时，BR/EDR 协议栈完成初始化后会被主动关闭，RDX 与 HOGP 继续通过 BLE 工作。该产品策略本身合理，但会阻断 BQB 实验室需要的经典蓝牙可发现、可连接、标准 HCI 或 DUT 测试路径。

本文依次回答三个问题：

1. 行业成熟产品如何隔离量产运行与蓝牙认证能力；
2. 当前 JL SDK 已经提供哪些原生 BQB、标准 HCI 和 DUT 支持；
3. 如何在不破坏 T2620 默认产品行为的前提下，为本工程建立可审计、可测试、无定时器竞态的经典蓝牙门控。

本文是工程设计，不代替 Bluetooth SIG 当期资格流程、实验室测试计划、PICS/PIXIT/ICS 填写或 JL 针对当前 SDK 版本给出的认证指导。最终测试范围必须由产品声明范围、采用的 Qualified Design、实验室要求和 JL 交付资料共同确认。

## 2. 术语先行

### 2.1 统一语言

本文同时作为本方案的术语表。下列称呼用于统一产品运行、产测与蓝牙认证之间的边界：

| 标准术语 | 定义 | 避免称呼 |
|---|---|---|
| 产品人格（Production Personality） | T2620 面向最终用户的默认启动身份；RDX 与 HOGP 按产品规则工作，BR/EDR 不作为用户连接入口。 | 正常测试模式、普通 BQB 模式 |
| 认证人格（Qualification Personality） | PTS 人格与 RF DUT 人格的统称；只用于实验室蓝牙资格测试，与产品人格使用同一份受控源码，但采用独立构建配置和产物。它不是可在运行时选择的第四种人格。 | 广播开关、隐藏用户模式 |
| PTS 人格（PTS Personality） | 认证专用启动人格之一；保持正常 BR/EDR Host/Profile 行为，并按用例控制可发现、可连接状态。 | DUT 模式、经典蓝牙广播模式、PTS 可见模式 |
| RF DUT 人格（RF DUT Personality） | 认证专用启动人格之一；由测试仪通过标准或厂商测试接口控制 BR/EDR Controller/Radio，不代表正常 Profile 可用。 | PTS 模式、普通配对模式 |
| RDX 量产 DUT 状态（RDX Manufacturing DUT State） | 产品人格下为工厂生产测试临时开放的经典蓝牙测试状态，结束后返回产品人格的经典蓝牙关闭状态。它不是启动人格。 | BQB 认证人格、PTS 模式 |
| 经典蓝牙门控（Classic Bluetooth Gate） | 根据启动人格统一决定 BR/EDR 关闭、PTS 可见或 RF DUT 的产品策略边界；它提供测试入口，不代表资格测试通过。 | 经典蓝牙广播开关 |
| 测试入口就绪（Test Access Ready） | 测试端已经能够发现、连接或通过指定传输控制样机；这是执行相应测试的前置条件，不是 Bluetooth Qualification 的通过结论。 | BQB 已打开、已经过 BQB |

### 2.2 “BQB 认证”是行业俗称

工程沟通中常把 Bluetooth Qualification 统称为“BQB 认证”。严格来说，BQB 是 Bluetooth Qualification Body 角色名称，产品实际经历的是 Bluetooth SIG 的资格与声明流程。本文沿用“BQB”这一工程俗称，但不把它理解成单一的射频测试模式。

### 2.3 经典蓝牙没有 BLE 意义上的广播

本需求里所说的“控制经典蓝牙广播”，应拆成两个独立能力：

| 能力 | BR/EDR 术语 | JL 接口 |
|---|---|---|
| 允许测试端搜索到设备 | Inquiry Scan，可发现 | `USER_CTRL_WRITE_SCAN_ENABLE/DISABLE` |
| 允许测试端向设备发起连接 | Page Scan，可连接 | `USER_CTRL_WRITE_CONN_ENABLE/DISABLE` |

底层 `lmp_hci_write_scan_enable()` 接受的也是经典 HCI `Scan_Enable` 语义：`0x00` 全关、`0x01` Inquiry Scan、`0x02` Page Scan、`0x03` 两者都开。方案和日志统一使用“可发现/可连接门控”，不再使用“经典蓝牙广播开关”。

### 2.4 三种测试场景必须分开

| 场景 | 需要的协议栈状态 | 主要控制者 | 是否等同于正常 Profile 设备 |
|---|---|---|---:|
| PTS / Host / Profile 测试 | 正常 Host/Profile 运行，可按用例控制可发现、可连接 | PTS 与 IUT 控制面 | 是 |
| RF / Controller BQB | 标准 HCI 或厂商测试接口、DUT/测试仪控制 | RF 测试仪 | 否 |
| RDX 量产 DUT | 产品固件临时开放 DUT 和 SPP 产测能力 | 工厂工具/RDX 产测流程 | 否 |

不能因为三个场景都可能出现“DUT”字样，就让它们共用一个无边界的布尔变量。尤其不能用 `bredr_set_dut_enble()` 代替 PTS 所需的正常 Profile 状态。

### 2.5 可发现、可连接不是 BQB 通过条件的全集

经典蓝牙可发现和可连接解决的是“测试端如何接触 IUT”，属于测试入口条件。BQB 是否通过还取决于本次声明和测试范围，以及对应测试套件是否全部通过。以下现象的证明力必须严格区分：

| 观察到的现象 | 能够证明 | 不能证明 |
|---|---|---|
| 手机能够搜索到设备 | Inquiry Scan 和基本射频接收路径可用 | Page Scan、DUT、标准 HCI、Profile 一致性或 BQB 通过 |
| 手机或测试仪能够连接 | Page Scan 和某条 ACL 建链路径可用 | RF/BB 全套用例、异常流程、Profile PTS 或资格声明完成 |
| `bredr_set_dut_enble()` 已执行 | JL DUT 能力已被请求 | 测试仪已成功接管、标准 HCI 已打开或全部 RF 用例通过 |
| 八击后产测 SPP 可用 | RDX 量产 DUT 业务链路可工作 | PTS、BLE BQB、JL `BT_BQB` 专用路径或完整 Qualification 通过 |
| PTS/RF 报告全部通过 | 对应版本和声明范围内的测试结果满足要求 | 未申报功能、其他固件版本或后续变更天然继承结果 |

因此，本方案中的“门控打开”应表述为“测试入口就绪”，不得在测试报告、提交记录或发布说明中写成“打开经典蓝牙后即可通过 BQB”。

## 3. 行业成熟方案

### 3.1 同一源码，独立构建人格

成熟方案通常不维护一条长期分叉的“认证代码分支”，而是在同一提交、同一 SDK 和同一板级代码上，通过受控构建配置生成不同人格的产物：

```text
同一源码提交
  ├─ Production Personality  -> 量产镜像
  ├─ PTS Personality         -> Profile/Host 测试镜像
  └─ RF DUT Personality      -> Controller/RF 测试镜像
```

这样既避免认证代码和量产代码长期漂移，也能明确记录每个镜像相对产品构建的配置差异。实验室镜像不能与量产镜像同名、混放或共用发布标识。

### 3.2 编译期资格 + 启动时锁存

行业常用两层门控：

1. **编译期资格门控**：量产镜像不编译认证切换入口；认证镜像才包含测试控制能力。
2. **启动时人格锁存**：设备在蓝牙初始化前确定本次启动的人格；运行期间不把 PTS、RF DUT 和产品人格互相热切换。

若实验室确实需要一份镜像在 PTS 与 RF DUT 间选择，成熟做法是由物理测试口或夹具命令写入受校验的启动请求，然后复位并重新锁存，而不是在协议栈已经运行时直接翻转多个全局开关。

### 3.3 一个模块拥有经典蓝牙生命周期

所有影响 BR/EDR 生命周期的动作应由一个策略模块串行执行：

- `USER_CTRL_POWER_ON/OFF`；
- Inquiry Scan / Page Scan；
- 自动回连与 Page Cancel；
- DUT 进入/退出；
- 测试用 SPP；
- 与认证互斥的 BLE 广播；
- 延时关闭定时器。

业务模块只能提出“进入 RDX 产测 DUT”“退出产测”“蓝牙栈初始化完成”等意图，不能直接争夺上述底层接口。这样才能避免一个模块刚打开扫描，另一个遗留定时器又把经典蓝牙关闭。

### 3.4 默认关闭与失败关闭

面向用户的产品人格必须是默认值。任何未知模式、VM 读取失败、校验失败、命令超时或状态机异常，都必须回到产品策略，而不是意外开放 BR/EDR。

对编译期非法组合，优先使用 `#error` 阻止生成镜像；对运行期非法请求，记录原因并拒绝。如果异常发生在认证专用镜像，可停留在不可连接状态等待复位，但不能继续执行一个来源不明的混合测试状态。

### 3.5 测试人格必须可观察

认证样机应至少具备以下可观察信息：

- 启动日志打印人格、`CONFIG_BT_MODE`、经典扫描状态和构建标识；
- 明显且不会与量产灯效混淆的 LED 指示；
- 认证镜像文件名、版本信息或设备名能够被实验室识别；
- 每次人格应用、可见性变化、DUT 进入/退出和拒绝原因都有低频日志；
- 测试记录绑定固件 SHA-256、源码提交、JL 库文件 SHA-256 和配置清单。

### 3.6 退出测试以复位收口

RF DUT、固定频点、标准 HCI 等路径可能改变 Controller 内部状态、时钟、低功耗和连接资源。成熟方案通常把“复位/重新上电”定义为退出认证状态的唯一可靠边界。热退出只能用于明确验证过的量产 DUT 流程，不能推断为所有 BQB 场景都可无损恢复。

### 3.7 常见但不成熟的做法

- 在 `BT_STATUS_INIT_OK` 处临时注释关闭调用，随后人工记得改回来；
- 只判断一个 `bqb_enable`，把 PTS 和 RF DUT 当成同一种状态；
- 在普通 BLE Characteristic 中暴露无认证的 BQB 开关；
- 量产镜像永久保留可远程开启经典蓝牙的隐藏命令；
- 不保存定时器 ID，也不在回调中重验策略；
- 为了保留 BR/EDR，直接跳过同时包含 SD/DAC 断电的整个函数；
- 用不同源码分支制作认证固件，却没有记录与量产版本的差异；
- 只验证手机能搜到设备，就认为 RF BQB、标准 HCI 和 PTS 条件都已满足。

## 4. JL 原生 BQB 与 DUT 支持

### 4.1 `CONFIG_BT_MODE` 模式体系

JL 在 [`btcontroller_mode.h`](../SDK/interface/btctrler/btcontroller_mode.h) 中定义：

| 模式 | 值 | JL 注释给出的用途 |
|---|---:|---|
| `BT_NORMAL` | `0x01` | 正常产品运行 |
| `BT_BQB` | `0x02` | 实验室 RF BQB |
| `BT_FCC` | `0x04` | FCC 测试 |
| `BT_FRE` | `0x10` | 固定频点测试 |
| `BT_PER` | `0x20` | 性能测试 |
| `BT_QUA` | `0x40` | SDK 已定义，当前可见代码没有给出用途说明 |

同一文件明确说明：

- RF BQB 使用 `BT_BQB`；
- `BT_NORMAL` 下也可由外部操作调用 `bredr_set_dut_enble()` 做量产性能测试；
- 进入测试时应关闭快速回连，并开启可发现、可连接；
- 某些测试状态需要复位或重新上电才能恢复。

因此，JL 原生设计本身也区分“专用 BQB 构建模式”和“正常固件运行时进入 DUT”。

### 4.2 非 NORMAL 模式会改变整机构建行为

[`app_config.h`](../SDK/apps/earphone/include/app_config.h) 对 `CONFIG_BT_MODE != BT_NORMAL` 做了成组覆盖，包括：

- 关闭双连接和 TWS；
- 强制打开 BLE；
- 关闭自动关机、系统低压和系统低功耗；
- 关闭部分 LED、ADKEY、IOKEY 功能；
- 强制自动开机。

这说明 `BT_BQB` 不是单纯的“打开经典蓝牙可见性”开关，而是 JL 提供的整机测试人格。它适合 RF/Controller 认证路径，不应直接用于要求正常产品 Profile 行为的 PTS 构建。

### 4.3 标准 HCI 支持

[`lib_btctrler_config.c`](../SDK/apps/earphone/log_config/lib_btctrler_config.c) 当前逻辑为：

```c
#if (CONFIG_BT_MODE != BT_NORMAL)
const int config_btctler_hci_standard = 1;
#else
const int config_btctler_hci_standard = 0;
#endif
```

即非 NORMAL 构建会打开 Controller 的标准 HCI 能力。[`btcontroller_mode.h`](../SDK/interface/btctrler/btcontroller_mode.h) 同时提示 BLE 测试串口默认使用 USB，工程必须保证该 USB 口没有被其他功能占用。

另外，[`user_cfg.c`](../SDK/apps/earphone/user_cfg.c) 会在非 NORMAL 构建中把经典蓝牙名称改为 `AC693x_DUT`，地址改为固定测试地址 `12:34:56:56:34:12`。这再次证明 JL 的非 NORMAL 模式是专用测试人格；PTS 若要验证产品身份、配对数据库或正常 Profile 行为，不应未经评估直接使用该固定名称和地址。

当前仓库能确认“标准 HCI 能力随非 NORMAL 模式打开”，但 HCI 传输的具体实验室接线、驱动、工具版本和 JL 私有测试命令仍应以当前 SDK 配套资料及 JL 支持答复为准。

### 4.4 JL 启动阶段的 BQB 分支

在 [`earphone.c`](../SDK/apps/earphone/mode/bt/earphone.c) 的 `BT_STATUS_INIT_OK` 路径中：

1. `TCFG_NORMAL_SET_DUT_MODE` 打开时，调用 `bredr_set_dut_enble(1, 1)`，并打开可发现、可连接；
2. `BT_MODE_IS(BT_BQB)` 时调用 `ble_bqb_test_thread_init()`；
3. 第三方协议开启时仍会调用 `multi_protocol_bt_init()`；
4. 编译模式为 `BT_BQB` 或 `BT_PER` 时，随后提前结束正常产品启动流程。

这里有两个边界：

- `BT_BQB` 会启动 JL 的 BLE BQB 测试线程，不能假定它只影响经典蓝牙；
- 第三方协议初始化发生在 BQB/PER 的 `break` 之前，因此 RDX 仍有机会注册事件处理并执行自己的产品策略。

### 4.5 原生运行时 DUT API

JL 提供两层可见接口：

- [`hci_lmp.h`](../SDK/interface/btctrler/classic/hci_lmp.h) 中的 `bredr_set_dut_enble(u8 en, u8 phone)`；
- [`earphone.c`](../SDK/apps/earphone/mode/bt/earphone.c) 中的 `bt_bredr_enter_dut_mode(u8 mode, u8 inquiry_scan_en)` 包装。

当前包装最终调用 `bredr_set_dut_enble(1, 1)`。`mode == 1` 时还会清理回连状态，并在 TWS 构建中进入测试扫描流程；`mode == 0` 只使能 DUT，保留原流程。

可发现和可连接的上层命令定义位于 [`avctp_user.h`](../SDK/interface/btstack/avctp_user.h)：

```text
USER_CTRL_WRITE_SCAN_ENABLE  -> 打开可发现
USER_CTRL_WRITE_CONN_ENABLE  -> 打开可连接
USER_CTRL_POWER_OFF          -> 蓝牙关闭
USER_CTRL_POWER_ON           -> 蓝牙开启
```

### 4.6 当前可见源码没有完整 PTS 专用适配层

仓库中可以确认 RF BQB、标准 HCI、BLE BQB 线程和经典 DUT 接口，但没有发现明确命名的 PTS、PICS、PIXIT 或 TSPX 适配模块。因此不能把 `CONFIG_BT_MODE=BT_BQB` 表述成“JL 已自动完成所有经典 Profile PTS 支持”。

若认证范围包含 A2DP、AVRCP、HFP、SPP、HID 等 Host/Profile 项，仍需逐项确认：

- 对应 Profile 是否编译并注册；
- IUT 如何进入测试所需状态；
- 配对、鉴权、角色、Codec 和异常场景如何受控；
- 是否需要实验室提供的 IUT 控制脚本或 JL 专用补丁；
- PICS/PIXIT 与量产声明是否一致。

## 5. 当前 T2620 工程事实

### 5.1 当前编译配置

[`sdk_config.h`](../SDK/apps/earphone/board/br28/sdk_config.h) 当前关键值为：

```text
CONFIG_BT_MODE                 = BT_NORMAL
TCFG_NORMAL_SET_DUT_MODE       = 0
TCFG_USER_TWS_ENABLE           = 0
TCFG_USER_BLE_ENABLE           = 1
TCFG_THIRD_PARTY_PROTOCOLS_ENABLE = 1
HFP / AVRCP / A2DP / HID / SPP = 1
```

虽然工具生成的 `TCFG_THIRD_PARTY_PROTOCOLS_SEL` 为 `0`，[`app_config.h`](../SDK/apps/earphone/include/app_config.h) 会在第三方协议总开关开启且选择值为零时，把它覆盖为 `RDX_EN`。因此当前实际运行 RDX，并由 `multi_protocol_bt_init()` 调用 `rdx_app_all_init()`。

### 5.2 当前产品关闭链路

RDX 注册了全局 `MSG_FROM_BT_STACK` 处理器。收到 `BT_STATUS_INIT_OK` 后，[`rdx_app.c`](../SDK/apps/common/third_party_profile/rdx_protocol/rdx_app.c) 当前无条件执行：

```c
sys_timeout_add(NULL, rdx_app_bt_shutdown, 1000);
```

一秒后 `rdx_app_bt_shutdown()`：

1. 清除 Page 回连列表；
2. 关闭 `dual_conn` 或 `tws_dual_conn`；
3. 发送 `USER_CTRL_POWER_OFF`；
4. 执行 `sd_set_power(0)`；
5. 执行 `dac_power_off()`；
6. 打印低功耗 target 状态。

这条链路体现了当前产品要求，但存在三个工程问题：

- 没有检查 `CONFIG_BT_MODE`，所以即使切换 JL 原生 `BT_BQB`，RDX 仍会安排关闭；
- `sys_timeout_add()` 返回的 timer ID 被丢弃，后续无法可靠取消；
- 一个名为“BT shutdown”的函数同时承载了经典蓝牙、SD、DAC 和诊断职责，门控不能安全地跳过整个函数。

### 5.3 当前 RDX 量产 DUT 链路

[`rdx_dut.c`](../SDK/apps/common/third_party_profile/rdx_protocol/rdx_dut.c) 当前进入 DUT 时依次执行：

```text
检查录音和 OTA
  -> 关闭 Wi-Fi 传输
  -> rdx_app_bt_open()，底层直接写 Scan_Enable=0x03
  -> bt_bredr_enter_dut_mode(0, 0)
  -> 断开 RDX App 并关闭统一 BLE 广播
  -> 禁用自动关机
  -> rdx_spp_init()
```

退出时执行：

```text
bt_bredr_exit_dut_mode()
  -> rdx_spp_exit()
  -> rdx_app_bt_shutdown()
  -> 恢复统一 BLE 广播和自动关机
```

这条路径是“产品人格下的 RDX 量产 DUT”，不是完整的 BQB 认证人格。它可以复用底层 DUT 能力，但不能作为 PTS 与 RF BQB 的统一入口。

#### 八击进入 DUT 的认证边界

当前普通八击最终走上述 RDX 量产 DUT 路径。它打开 `Scan_Enable=0x03` 并调用 `bredr_set_dut_enble(1, 1)`，所以测试仪有可能发现、连接样机并执行部分 BR/EDR DUT/RF 测试；但“有可能被测试仪接入”不等于“可以通过 BQB”。

| 测试范围 | 当前八击 DUT 的结论 |
|---|---|
| 部分 BR/EDR 非信令/DUT RF 测试 | 可能具备入口，必须由目标测试仪和实验室逐项确认 |
| JL 标准 HCI BQB 流程 | 不充分；当前产品构建是 `BT_NORMAL`，`config_btctler_hci_standard=0` |
| 经典 Profile PTS | 不充分；DUT 状态不能代替正常 HFP/A2DP/AVRCP/SPP/HID Profile 状态和 IUT 控制 |
| BLE BQB | 不充分；八击路径不是 JL BLE BQB 测试人格，并且当前会关闭 RDX/HOGP 产品广播 |
| 完整 Bluetooth Qualification | 不能据此判断，必须以确认的声明范围和实验室正式结果为准 |

此外，八击通常发生在产品的一秒关闭动作已经执行之后。当前 `rdx_app_bt_open()` 只直接写 `Scan_Enable=0x03`，可见代码没有先发送 `USER_CTRL_POWER_ON`。即使现有量产仪器能够连接，也只能证明该产测组合可用，不能推导出协议栈已恢复到 JL 专用 `BT_BQB` 构建的标准 HCI、低功耗、USB 传输和测试线程状态。

如果实验室书面确认本次范围只要求通过按键进入某组 BR/EDR DUT 测试，八击可以作为认证样机的候选进入方式，但仍须同时满足：测试仪可稳定 Inquiry、建立测试 ACL、下发所需命令、覆盖全部目标用例，并且测试期间不存在 RDX 延时关闭或其他业务干扰。未完成这些验证前，八击 DUT 只能标记为“预检查入口”，不能标记为“BQB 方案已通过”。

### 5.4 USB 资源冲突

[`t2620_project_config.h`](../SDK/apps/earphone/include/t2620_project_config.h) 当前默认：

```text
TCFG_T2620_PC_STORAGE_ENABLE = 1
TCFG_APP_PC_EN               = 1
TCFG_USB_SLAVE_MSD_ENABLE    = 1
```

而 JL 的测试模式说明指出测试串口默认使用 USB。RF BQB 镜像如果需要 USB HCI，就不能同时让 PC Storage/MSC 占用同一 USB Device 资源。认证构建必须在编译期关闭 T2620 PC Storage 和实际 USB MSC 注册，或者取得 JL 明确支持的其他 HCI 传输方案。

只关闭 `TCFG_APP_PC_EN` 而保留底层 MSC 初始化并不足以证明端口已释放；必须以枚举描述符、USB 模式初始化路径和真机枚举结果为准。

### 5.5 当前冲突总结

```text
JL BT_BQB / 标准 HCI
         │
         ├─ 非 NORMAL 测试人格、默认 USB 测试通道
         ├─ 仍可能初始化 third-party / RDX
         │                         │
         │                         └─ BT_INIT_OK 后无条件延时关闭 BR/EDR
         │
         └─ 与当前 USB MSC 产品配置存在资源冲突
```

因此，本项目不能只把 JL Studio 的模式从 `BT_NORMAL` 改成 `BT_BQB` 就交付实验室。

## 6. T2620 实际方案设计

### 6.1 设计目标

1. 量产默认行为不变：BR/EDR 初始化后关闭，BLE RDX/HOGP 正常工作；
2. PTS 构建保留正常经典 Host/Profile，并可独立控制可发现、可连接；
3. RF 构建走 JL 原生 `BT_BQB`、标准 HCI 和实验室要求的 DUT 路径；
4. RDX 量产 DUT 继续可用，但不能越权改变认证人格；
5. 经典蓝牙只有一个生命周期所有者；
6. 延时关闭可取消、回调重验、重复调用幂等；
7. 不因认证门控误跳过 SD/DAC 等外围电源动作；
8. 构建产物、配置差异和验证结果可追溯。

### 6.2 推荐人格模型

```c
enum t2620_bt_personality {
    T2620_BT_PERSONALITY_PRODUCT = 0,
    T2620_BT_PERSONALITY_PTS,
    T2620_BT_PERSONALITY_RF_DUT,
};

enum t2620_classic_state {
    T2620_CLASSIC_BOOT_WAIT = 0,
    T2620_CLASSIC_CLOSE_PENDING,
    T2620_CLASSIC_OFF,
    T2620_CLASSIC_PTS_VISIBLE,
    T2620_CLASSIC_RF_DUT,
    T2620_CLASSIC_RDX_MFG_DUT,
    T2620_CLASSIC_FAILED,
};
```

“人格”在启动时锁存，正常运行期间不可修改；“状态”由该人格和受控事件驱动。RDX 量产 DUT 是产品人格下的临时状态，不是第四种启动人格。

### 6.3 三个正式构建产物

| 构建 | `CONFIG_BT_MODE` | 经典策略 | RDX/HOGP | USB 策略 | 用途 |
|---|---|---|---|---|---|
| `t2620_product` | `BT_NORMAL` | 延时关闭 BR/EDR | 保持产品配置 | PC Storage/MSC 保持 | 量产与日常回归 |
| `t2620_bqb_pts` | `BT_NORMAL` | 正常栈；受控 Inquiry/Page Scan | 保持与申报对象一致，是否停 BLE ADV 按用例 | 不占用 PTS/IUT 控制通道 | Host/Profile PTS |
| `t2620_bqb_rf` | `BT_BQB` | JL BQB/标准 HCI；应用不得关闭 | 默认抑制产品 BLE 业务，具体听从 JL/实验室 | 关闭 MSC，USB 交给 HCI，或明确改用其他通道 | Controller/RF BQB |

三个产物必须来自同一源码提交。认证产物不能作为量产镜像发布，量产升级流程也不能选择认证产物。

### 6.4 编译配置归属

建议在 [`t2620_project_config.h`](../SDK/apps/earphone/include/t2620_project_config.h) 增加项目人格配置，默认固定为产品人格：

```c
#define T2620_BT_PERSONALITY_PRODUCT     0
#define T2620_BT_PERSONALITY_PTS         1
#define T2620_BT_PERSONALITY_RF_DUT      2

#ifndef TCFG_T2620_BT_PERSONALITY
#define TCFG_T2620_BT_PERSONALITY        T2620_BT_PERSONALITY_PRODUCT
#endif
```

构建目标只允许覆盖 `TCFG_T2620_BT_PERSONALITY`。配置头根据人格完成以下静态约束：

- `PRODUCT` 与 `PTS` 必须使用 `BT_NORMAL`；
- `RF_DUT` 必须使用 `BT_BQB`；
- `RF_DUT` 必须关闭 `TCFG_T2620_PC_STORAGE_ENABLE`，并验证 USB MSC 未注册；
- 非法值直接 `#error`；
- 量产发布流水线只接受 `PRODUCT`；
- 认证构建输出文件名必须带 `bqb_pts` 或 `bqb_rf`。

`CONFIG_BT_MODE` 是影响 LTO、标准 HCI和整机功能裁剪的编译期配置，不允许从 VM 动态决定。若要通过命令在 PTS 和 RF 间切换，必须预先构建一个明确支持两者且经过单独验证的认证镜像；本项目第一阶段不采用该复杂路径。

### 6.5 新增唯一策略模块

建议新增：

```text
SDK/apps/common/third_party_profile/rdx_protocol/
  rdx_classic_bt_policy.c
  rdx_classic_bt_policy.h
```

当前经典关闭和量产 DUT 都在 RDX 产品逻辑内，因此第一阶段放在该目录改动最小。若后续 RDX 被多个产品复用，再把它提升为 `apps/earphone` 的 T2620 产品策略模块。

建议公开的最小接口：

```c
void rdx_classic_bt_policy_init(void);
void rdx_classic_bt_policy_on_stack_ready(void);

int rdx_classic_bt_policy_set_pts_visibility(bool discoverable,
                                             bool connectable);

int rdx_classic_bt_policy_request_mfg_dut(bool enable);
void rdx_classic_bt_policy_on_system_poweroff(void);

enum t2620_bt_personality rdx_classic_bt_policy_get_personality(void);
enum t2620_classic_state rdx_classic_bt_policy_get_state(void);
```

模块内部拥有：

- 启动人格；
- 当前经典状态；
- 关闭定时器 ID；
- 栈是否完成初始化；
- 当前 Inquiry/Page Scan 目标值；
- DUT 是否由 RDX 产测持有；
- 最后一次状态变化原因。

其他模块不得新增对 `USER_CTRL_POWER_OFF/ON`、经典 Scan Enable 或 `bredr_set_dut_enble()` 的直接调用。

### 6.6 状态机

```text
上电
  -> policy_init() 锁存编译人格
  -> 等待 BT_STATUS_INIT_OK
       ├─ PRODUCT -> CLOSE_PENDING --1 s且策略复核通过--> OFF
       │                 │
       │                 └─ RDX产测请求 -> RDX_MFG_DUT
       │                                      │
       │                                      └─ 退出 -> OFF
       ├─ PTS     -> PTS_VISIBLE <-> 调整 Inquiry/Page Scan
       └─ RF_DUT  -> RF_DUT，由 JL HCI/测试仪控制

系统关机：任何状态 -> 取消 timer -> 执行统一关机清理
非法事件：记录并拒绝；严重不一致 -> FAILED/等待复位
```

只有产品人格接受 RDX 量产 DUT 请求。PTS 或 RF 人格收到 RDX DUT 按键/命令时必须明确拒绝，不能覆盖实验室控制状态。

### 6.7 `BT_STATUS_INIT_OK` 改造

把 [`rdx_app.c`](../SDK/apps/common/third_party_profile/rdx_protocol/rdx_app.c) 当前的无条件定时器改为：

```c
case BT_STATUS_INIT_OK:
    rdx_classic_bt_policy_on_stack_ready();
    break;
```

策略模块按人格执行：

#### 产品人格

1. 保存 `sys_timeout_add()` 返回的 timer ID；
2. 一秒回调首先把 ID 清零；
3. 回调再次确认人格仍是 `PRODUCT`、状态仍是 `CLOSE_PENDING`；
4. 幂等执行经典关闭；
5. 状态转为 `OFF`。

#### PTS 人格

1. 不创建经典关闭 timer；
2. 停止产品自动 Page 回连，避免已记忆手机抢占 PTS；
3. 通过 `bt_cmd_prepare()` 串行打开所需 Inquiry/Page Scan；
4. 不调用 `bredr_set_dut_enble()`；
5. 可由认证专用控制面修改二位可见性，但不能切换人格。

默认可见性建议为 `discoverable=1, connectable=1`，具体 PTS 用例需要的其他组合由认证控制命令设置。

#### RF DUT 人格

1. 不创建经典关闭 timer；
2. 不由 RDX 应用层周期性写 Scan Enable；
3. 保持 JL `BT_BQB`、标准 HCI 和测试线程拥有测试流程；
4. 按 JL/实验室要求决定是否显式进入 BR/EDR DUT；
5. 默认停止会抢占射频或 USB 资源的产品业务。

### 6.8 拆分经典关闭与外围断电

当前 `rdx_app_bt_shutdown()` 应拆成职责单一的函数，例如：

```c
static void rdx_classic_bt_product_close(void);
static void rdx_post_init_peripheral_power_trim(void);
static void rdx_low_power_target_dump(void);
```

建议保持现有一秒时序，但由策略明确调用：

- 产品人格：执行经典关闭，同时保留当前 SD/DAC 断电策略；
- PTS/RF 人格：跳过的只能是经典关闭部分；SD/DAC 是否断电仍按产品硬件需求执行，任何差异必须单独记录；
- 系统正式关机：继续走完整关机清理，不能被认证人格阻断。

不能在 `rdx_app_bt_shutdown()` 函数入口简单判断 BQB 后 `return`。

### 6.9 RDX 量产 DUT 接入策略模块

[`rdx_dut.c`](../SDK/apps/common/third_party_profile/rdx_protocol/rdx_dut.c) 不再直接调用：

```text
rdx_app_bt_open()
bt_bredr_enter_dut_mode()
bt_bredr_exit_dut_mode()
rdx_app_bt_shutdown()
```

改为：

```c
rdx_classic_bt_policy_request_mfg_dut(true);
rdx_classic_bt_policy_request_mfg_dut(false);
```

策略模块负责：

- 进入前取消尚未触发的产品关闭 timer；
- 清理自动回连后打开可发现、可连接；
- 进入经典 DUT；
- 退出 DUT 后恢复产品 `OFF`；
- 拒绝认证人格下的量产 DUT 请求；
- 确保重复进入、重复退出幂等。

BLE 广播关闭、RDX App 断连、SPP 生命周期、录音/OTA/Wi-Fi 互斥仍由 `rdx_dut.c` 管理，但它们必须在经典策略请求成功后才能提交状态；若策略拒绝，业务层不得继续显示“已进入 DUT”。

### 6.10 PTS 可见性控制面

第一阶段建议只在 `t2620_bqb_pts` 构建中提供物理测试口命令：

```text
BTQ STATUS
BTQ VIS 0    # 不可发现、不可连接
BTQ VIS 1    # 可发现、不可连接
BTQ VIS 2    # 不可发现、可连接
BTQ VIS 3    # 可发现、可连接
BTQ RESET
```

实现应转为 `app_core` 消息，再由策略模块调用 `bt_cmd_prepare()`，不要在 UART 中断或协议接收回调里直接操作协议栈。

不建议把该命令挂在普通 RDX BLE 用户协议上，原因包括：

- 量产镜像容易留下远程开放 BR/EDR 的隐藏入口；
- 测试控制依赖另一条 BLE ACL，会给 PTS/RF 场景引入额外状态；
- RF 人格可能需要关闭 RDX BLE 广播；
- BLE 命令与一秒关闭 timer 更容易形成跨任务竞态。

如果实验室只能通过现有 RDX App 操作，可在认证专用构建中临时提供经过鉴权的“写启动请求并复位”命令，但不能把它带入量产镜像。

### 6.11 是否使用 VM

首选方案不需要 VM：三个构建各自固定人格，最简单、最可追溯。

只有在实验室明确要求同一认证镜像可选人格时，才增加认证专用 VM 记录，并至少包含：

```c
struct btq_boot_request {
    u32 magic;
    u8  version;
    u8  requested_personality;
    u8  one_shot;
    u8  reserved;
    u32 crc32;
};
```

约束如下：

- 量产构建不读取、不写入该 VM ID；
- 非法 magic/version/CRC 一律回到产品人格或拒绝启动认证；
- 请求只在冷启动/复位早期读取；
- 建议 one-shot，成功锁存后立即清除；
- 人格变化必须复位，禁止热切换；
- VM ID 必须在 [`syscfg_id.h`](../SDK/interface/utils/syscfg_id.h) 中独立分配，不复用现有 `VM_RDX_KEY_DUT_DISABLED` 或 HOGP 存储项。

### 6.12 BLE 与经典认证的共存策略

| 人格 | RDX/HOGP BLE 建议 |
|---|---|
| PRODUCT | 按当前统一广播和双 ACL 产品策略运行 |
| PTS | 默认保留与申报对象一致的编译内容；若用例要求纯经典环境，可由认证控制面停止 BLE ADV，不能改 GATT 数据库结构后假装仍是同一测试对象 |
| RF_DUT | 默认断开 BLE ACL、停止 RDX/HOGP 产品广播和高频业务；JL BLE BQB 线程是否保留由本次 RF 测试范围与 JL 指导决定 |
| RDX_MFG_DUT | 保持当前做法：关闭统一 BLE 广播并启动产测 SPP |

RF 认证时不能在不知道 JL `ble_bqb_test_thread_init()` 用途的情况下直接删除它。应先向 JL/实验室确认当前测试镜像是双模 Controller 测试还是仅 BR/EDR 测试，再固定配置。

### 6.13 USB/HCI 与 PC Storage 仲裁

RF BQB 构建必须在预处理期形成明确约束：

```text
若 RF_DUT 且 HCI 使用 USB：
  TCFG_T2620_PC_STORAGE_ENABLE 必须为 0
  USB MSC/HID/UAC 产品 Class 不得枚举
  PC mode 不得抢占 USB
否则构建失败
```

如果决定改用 UART HCI，则需单独确认：

- JL 当前库是否支持该 HCI transport；
- UART 引脚与调试口、产测口及板上器件是否冲突；
- 波特率、流控、电平和驱动；
- 实验室工具是否支持；
- 认证镜像是否仍需关闭 USB MSC 以减少非测试业务。

在这些条件没有确认前，方案默认使用 JL 注释指向的 USB 测试通道，并在 RF 构建关闭 PC Storage/MSC。

## 8. 实施顺序

### 阶段 0：冻结认证范围

在编码前由认证负责人、实验室和 JL 确认：

1. 本次是 Controller/RF、Host/Profile，还是二者都有；
2. 测试仪和 HCI transport；
3. 是否测试 BLE 与 BR/EDR 双模；
4. 需要测试的经典 Profile；
5. 设备名、地址、Class of Device、IO Capability 和配对要求；
6. 实验室是否要求运行期切换 Inquiry/Page Scan；
7. JL 是否提供专用库、补丁、脚本或测试工程。

这一阶段没有关闭前，不应把“手机能搜到经典蓝牙”当成完整需求。

### 阶段 1：建立静态人格和策略模块

1. 增加 `PRODUCT/PTS/RF_DUT` 编译人格；
2. 把 RDX 无条件延时关闭迁入策略模块；
3. 保存 timer ID，增加取消和回调重验；
4. 拆分经典关闭与 SD/DAC 动作；
5. 让 RDX DUT 通过策略模块进入/退出；
6. 增加构建期非法组合检查。

阶段 1 只做独立构建，不引入 VM，优先把架构边界和量产安全性做对。

### 阶段 2：打通实验室控制面

1. PTS 构建增加认证专用 `VIS 0..3` 命令；
2. RF 构建释放 USB 并验证标准 HCI 枚举；
3. 根据 JL 指导确认 DUT、BLE BQB 线程和测试工具；
4. 增加认证 LED/日志；
5. 只有实验室确有需要时才加入受校验的 VM 启动请求。

### 阶段 3：冻结认证镜像

记录并归档：

- Git commit；
- JL SDK/库版本及 SHA-256；
- `sdk.elf`、`app.bin`、最终烧录镜像 SHA-256；
- 构建人格与宏清单；
- 测试样机 MAC/序列号；
- PICS/PIXIT、实验室脚本和测试报告；
- 认证镜像与量产镜像的唯一配置差异。

## 9. 验证矩阵

### 9.1 主机合同测试

建议新增 `test_bt_qualification_contract.ps1`，至少检查：

### 9.2 构建验证

三个构建分别执行：

```powershell
cd SDK
.\.vscode\winmk.bat all
```

实际落地构建目标后应替换为明确的 `product`、`bqb_pts`、`bqb_rf` 命令。每次构建后检查 map/ELF 符号、编译宏摘要和 USB 描述符，不能只看链接成功。

### 9.3 真机验证

| 场景 | 关键验收 |
|---|---|
| PRODUCT 冷启动 | 一秒后经典蓝牙不可发现、不可连接；RDX/HOGP BLE 正常 |
| PRODUCT 长稳 | 不出现经典蓝牙重新开放；功耗保持原基线 |
| PRODUCT 进入/退出 RDX DUT | DUT 可被仪器访问；退出后经典蓝牙关闭；BLE 广播恢复 |
| PRODUCT 八击 DUT 预检查 | 记录 Inquiry、测试 ACL 和目标 DUT 命令结果；通过只代表候选测试入口可用 |
| PTS 默认启动 | 正常设备名/MAC/Profile；可发现、可连接；不会在一秒后消失 |
| PTS `VIS 0..3` | 四种 Inquiry/Page 组合与抓包、手机/PTS 观察一致 |
| PTS 配对/断连/重连 | 无产品自动回连抢占；测试用例可重复 |
| RF USB 枚举 | 只出现预期 HCI/测试接口，不出现 MSC/UAC/HID 产品 Class |
| RF 测试仪连接 | 标准 HCI/DUT 命令稳定，无 RDX 延时关闭干扰 |
| RF 退出 | 复位/重新上电后状态确定 |
| 非法配置 | 编译失败或启动失败关闭，不开放未知混合状态 |

### 9.4 回归重点

- 产品 BLE 双 ACL 与 HOGP 已有生命周期合同必须继续通过；
- PC Storage 产品构建必须继续通过现有存储所有权测试；
- RF 构建关闭 PC Storage 不得反向修改产品默认宏；
- RDX 量产 DUT 的录音、OTA、Wi-Fi、LED 和 SPP 互斥保持原行为；
- 睡眠、自动关机、充电启动和低电量策略分别按人格验证；
- 构建模式切换后必须 clean build，避免 LTO 或生成文件残留。

## 10. 方案关闭标准

| 项目 | 关闭要求 |
|---|---|
| 认证范围 | 实验室/JL 已明确 RF、PTS、BLE/BR/EDR 和 Profile 范围 |
| 架构 | 所有经典开关、扫描和 DUT 调用由 policy 统一拥有 |
| 产品安全 | 量产构建不包含远程认证入口，默认经典关闭 |
| 定时器 | 可取消、回调重验、重复操作幂等，无一秒后误关闭 |
| 外围电源 | SD/DAC 行为与经典门控解耦并分别验证 |
| USB | RF HCI 与 MSC/UAC/HID 无资源和枚举冲突 |
| PTS | 正常 Profile 和四种扫描组合可控，且不进入 DUT |
| RF | JL BQB/HCI 路径通过测试仪验证，RDX 不干扰 |
| 量产 DUT | 进入/退出完整，退出回到产品 OFF |
| 结论口径 | 不以手机可见、ACL 建链或八击 DUT 成功替代正式测试报告 |
| 回归 | 统一 host suite、三构建和真机矩阵通过 |
| 追溯 | 固件、源码、配置、库和测试记录 hash 完整 |

## 11. 最终决策建议

本工程应采用以下正式策略：

```text
量产：BT_NORMAL + PRODUCT Personality
      -> RDX/HOGP BLE 正常
      -> BR/EDR 初始化后一秒关闭

经典 Profile/Host 认证：BT_NORMAL + PTS Personality
      -> 不进入 DUT
      -> Inquiry Scan / Page Scan 由认证控制面独立控制

Controller/RF 认证：BT_BQB + RF_DUT Personality
      -> 使用 JL 原生标准 HCI/BQB 路径
      -> RDX 不得执行产品延时关闭
      -> USB HCI 与 PC Storage/MSC 强制互斥

工厂产测：PRODUCT Personality 内临时进入 RDX_MFG_DUT
      -> 退出后恢复 BR/EDR OFF
```

第一阶段只实现三个固定构建人格，不引入 VM 和远程热切换。这样改动面最小、认证状态最确定、量产风险最低，也最符合 JL 原生 `BT_NORMAL` 与 `BT_BQB` 的职责划分。
