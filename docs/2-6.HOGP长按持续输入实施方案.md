# 2-6. HOGP 长按持续输入实施方案

> 2026-09-21 更新：HID 边沿通道已从 KEY1～KEY4 扩展为 KEY1～KEY5。正文按当前五键行为更新。KEY5 仍保留独立录音手势：RDX 就绪时长按开始在线录音、松开停止；无 BLE 连接时保留原有本地录音／播放行为。HID 就绪且映射非零时，KEY5 与其他键一样在物理按下时上报配置键值，松开时释放；无需等待录音长按阈值。两条路径可同时工作，HID 上报不表示录音已启动或成功；全零映射只禁用 HID，不禁用录音。按键适配层仍只消费 KEY1～KEY4 的在线手势，避免吞掉 KEY5 的录音事件。实机需验证同链路和分离链路下的 HID 与录音并行行为。

日期：2026-09-20。状态：软件实现已落地，实机验收待完成。当前代码和主机行为测试不能替代第 8.2 节的刷机验收。

复评结论：单键长按方案可行，但不是仅增加 Down 回调即可完成。复评已补充厂测过滤下的状态采样、旧手势归属、重新接纳条件、配键事务回滚及释放失败的保证边界，并明确路由快照、扫描确认和独立 HID 生命周期约定。下述边界属于首版实现要求。

关联文档：[2-4 配键方案 A1](2-4.HOGP_APP按键键值下发方案A1.md)、[2-5 配键协议 A2](2-5.HOGP_APP端配键协议对齐文档A2.md)。

## 1. 目标与输入原理

解决 KEY1～KEY5 映射为普通键盘键后，不能像 PC 键盘一样长按持续输入的问题。实施后，HID 按键使用真实按下/释放语义：

```text
物理按下 → 消抖确认 → 发送 Down → PC 可立即输入一次 a
持续按住 → 保持按下状态        → PC 在重复延迟后自动输入 aaaa…
物理松开 → 消抖确认 → 发送 Up   → PC 收到释放后停止重复
```

PC 收到 Down 就可以产生首次输入，不必等 Up。Down 与 Up 构成一次完整敲击；只有保持按下超过主机重复延迟，且系统及应用支持自动重复时，才会持续输入。重复速度由主机决定，固件不周期性模拟敲击。

当前固件在物理短按松开、单击确认后才发送 Down，约 20 ms 后自动发送 Up；物理长按还会被事件路由过滤。问题在固件事件路由和状态维护，现有 HOGP 报告能表达目标行为，不需要 PC APP 增加重复输入命令。

## 4. 物理事件通道

### 4.1 从消抖后的状态变化产生事件

建议增加独立通知，例如 `key_state_changed(type, previous, current)`，默认弱实现为空，由产品层接入。通知点应位于消抖完成后、普通 CLICK/LONG/HOLD 判定之前，并遵守厂测消费边界。

具体顺序应为：消抖完成 → 调用现有厂测过滤一次并保存结果 → 更新产品可见的稳定物理状态（包括被过滤的样本）→ 依据过滤结果决定是否允许普通输入 → 执行原驱动逻辑。厂测过滤返回 true 时当前代码会直接跳至 `__scan_end`；如果新通知仅放在该分支之后，会漏掉厂测期间的松开。被过滤样本只用于取消、状态同步和重新接纳判断，不生成 HID Down，也不重复调用有副作用的厂测过滤函数。

| 状态变化 | HID 处理 |
|---|---|
| NO_KEY → KEY1～KEY5 | 尝试接纳本次按下 |
| KEY1～KEY5 → NO_KEY | 释放对应已接纳的键，不区分短按或长按 |
| A 键值 → B 键值 | 先处理 A 释放，再按业务条件处理 B 按下，包括切换到 KEY5 的情况 |
| 键值不变 | 不产生额外边沿，LONG/HOLD 不触发 HID 脉冲 |

不能只使用现有 `KEY_ACTION_UP`，它不覆盖短按释放。也不能直接覆盖现有 `key_down_event_handler()`，否则会影响按键音和在线电量提示。

### 4.2 扫描层只传递事件，app_core 处理业务

扫描由定时器驱动。扫描上下文只复制小型事件、更新受同步保护的物理状态，并唤醒 app_core，不直接发送 ATT、访问配键存储或操作共享业务资源。事件携带键类型、前后键值、顺序号及生命周期标识；不得投递指向栈上临时对象的指针。

正常路径使用有界 FIFO 保持边沿顺序，尤其是快速的 Down→Up→Down，不能仅保存最新状态而吞掉中间敲击。队列满时进入异常恢复：记录溢出、保留待清理标志、通过可重试唤醒或工作定时器让 app_core 执行释放清理，并要求重新松开后再接纳。不能仅打印日志后丢弃 Up；过载期间允许丢失输入，但必须避免继续输出和遗留按住状态。

溢出恢复必须使已排队事件整体失效，推进输入代次并清空/跳过旧 FIFO；否则清理后仍可能重放队列中的旧 Down。扫描生产者与 app_core 消费者之间的 FIFO、代次和状态快照需采用 SDK 支持的短临界区或等效同步，`volatile` 不能代替一致性保护。恢复工作源不能只依赖那个已经投递失败的队列通知。

### 4.3 接纳与归属

物理按下时先确定周期路由归属；接纳 Down 前再检查 HID ready、映射、存储保护、格式化、PC 模式及厂测状态，保持现有业务边界。周期归属与 Down 是否发送成功分别记录：归属决定后续手势能否进入原业务，发送成功才建立该次按下的释放责任。

KEY1～KEY4 的周期归属至少区分 HID、离线和丢弃。HID 路由下的禁用映射、Down 发送失败、释放屏障拒绝均继续消费本周期，不能因未建立 HELD 状态而退回离线业务；已有 BLE ACL 但 HID 未就绪、业务保护或厂测消费的周期归为丢弃。只有原离线策略允许时才归为离线。同一周期后续的 CLICK/LONG/HOLD/UP 不得再次触发旧 HID 脉冲；归属失效后只能丢弃，不能重新归类。未成功发送 Down 的周期不凭空建立释放责任，但也不能清除此前遗留的释放责任或会话恢复零状态屏障。

尚未接纳给 HID 的物理按住，不得因中途连接成功而突然补发 Down。ready 恢复、路由切换后先观察到稳定松开，再接纳新的按下；延迟到达的旧 CLICK 也应按周期归属丢弃。归属需要覆盖多击层可能延迟输出的消息，不能只在松开时立即清掉标记。

现有 `multi_clicks_translate()` 只有共享的 `click_cnt/notify_value`，最终消息没有物理周期编号，因此不能假定在 `rdx_app_earphone_key_remap()` 中比较当前 ready 就能识别旧 CLICK。实现必须在多击转换之前给源事件确定路由归属，并让延迟输出保留该归属，或使 HID 周期从源头不进入多击累积。不同归属/路由代次的点击不能合并；离线旧手势进入 ready 后不得触发 HID，HID 旧手势失去 ready 后不得落入离线表。不得通过每个 HID 边沿调用全局 `key_event_reset()` 粗暴处理，它还会清除 KEY5 等业务共享的手势状态。具体元数据应放在产品私有结构，避免未经审计修改 SDK 公共 `struct key_event` 布局。

“等待松开”是状态条件，不是一定等待下一次 Up 边沿：如果切换时已经是稳定 NO_KEY，应在取得当前代次的有效扫描确认且释放屏障解除后重新接纳；如果仍按住，则必须等之后的稳定 NO_KEY。否则空闲时连接也可能吞掉用户第一次点击。屏障期间发生但尚未消费的 Down 即使在屏障解除后出队，也必须依据采集代次/接纳标记丢弃。

释放已接纳的键属于清理操作，即使当前业务禁止新 Down，也不能被同一个提前返回条件吞掉。进入厂测或其他消费模式前，必须主动取消已有 HID 状态，不能依赖之后还能收到物理 Up。

### 4.4 路由快照与消息归属的实现约定

首版采用“app_core 发布路由快照、扫描层捕获周期归属、app_core 消费时复核”的路径。产品私有快照包含 KEY1～KEY5 路由、输入代次、HID 代次、映射代次及新 Down 接纳开关；扫描层只读取受同步保护的快照，不读取配键存储或临时调用业务接口决定归属。KEY5 的 HID 边沿使用同一 FIFO，同时保留原录音手势业务路径。

```text
app_core 更新路由/屏障并发布快照
  → 扫描层完成消抖、保存厂测过滤结果
  → 捕获快照，为新周期分配 cycle_id、归属和采集时接纳标记
  → 边沿进入产品 FIFO；源手势按相同周期归属过滤
  → app_core 验证事件代次、归属及当前业务条件
  → 有效 HID 边沿执行 press/release；失效输入丢弃并按需清理
```

KEY1～KEY4 的 HID 和丢弃周期的源手势在 `multi_clicks_translate()` 之前消费，不进入共享点击累积。离线周期保留原手势转换，但累积状态必须绑定输入代次/归属；延迟输出以产品私有消息封装携带这些元数据，app_core 验证后才能进入离线映射。不得把封装直接强转为公共 `struct key_event`；应由专用处理入口解包。路由切换时仅作废受影响的 KEY1～KEY4 累积，不能清除 KEY5 的手势状态。`KEY_ACTION_NO_KEY` 应按其待结束的累积归属处理，不能按当时快照推断来源。

消费时的复核只能否决事件，不能把采集时不允许的 Down 升级为有效输入，也不能把旧离线消息改送 HID。业务、owner 或 ready 在其他上下文发生变化时，应同步关闭新输入入口、使相关旧代次失效，再通知 app_core 完成清理和快照更新；通知失败沿用第 4.2 节的恢复机制。最终发送的目标解析和代次验证须与生命周期更新协调，避免验证后 owner 已切换却仍使用全局当前 owner 发送。

### 4.5 无边沿时的稳定松开确认

仅有 `key_state_changed()` 不足以重新接纳：设备一直处于 NO_KEY 时，连接完成后不会产生新边沿。产品层另维护 IO 扫描确认快照，每次通过消抖的采样均更新 `scan_seq`、稳定键值、观察到的输入代次及过滤结果；消抖尚未完成的采样不能作为稳定松开确认。其他按键驱动的 NO_KEY 不能覆盖 IO 状态。

进入重新接纳流程时关闭接纳开关，并记录所需输入代次和扫描序号基线。扫描层观察到该代次后，在稳定 NO_KEY 样本上发布确认；即使键值没有变化或样本被厂测消费，也更新物理状态。app_core 在确认序号晚于基线、代次匹配、当前仍为稳定 NO_KEY、业务允许且零状态屏障已解除时，原子地复核并开放新输入。厂测样本只能证明已松开，不能绕过厂测及其他业务禁入条件。

该确认通过共享快照和可重试唤醒/工作定时器完成，不把每次扫描都放入边沿 FIFO。若屏障期间已出现新的按下，即使其事件随后才出队，也按采集时的禁入标记丢弃，等待之后稳定松开。应验证“始终空闲且无任何边沿”也能完成重新接纳，不能通过测试先补一个人工 Up 掩盖问题。

## 5. HID 状态机与发送顺序

建议动作层提供 `press(key_id)`、`release(key_id)`、`cancel(reason)` 三类接口；生命周期和配键操作也使用同一套取消逻辑。所有状态变更在同一业务上下文串行处理；其他上下文回调通过投递或明确同步进入。

最少记录：当前接纳的物理键、按下时映射快照、会话代次、最近成功提交的报告、待释放状态以及重新接纳门槛。成功提交只表示发送接口接受报告，不代表 PC 应用已处理。

| 状态 | 输入 | 动作与下一状态 |
|---|---|---|
| IDLE | 合法按下 | 用映射快照发送 Down；成功后 HELD |
| IDLE | 禁用映射或本周期禁止 Down | 消费本周期，不发送报告，不新增释放责任；保留已有恢复屏障 |
| IDLE | Down 发送失败 | 记录失败，本周期不补发迟到的 Down，等待物理松开后重新接纳 |
| HELD | 相同键持续按住、LONG/HOLD | 保持状态，不启动自动释放，不重复执行动作 |
| HELD | 对应物理松开 | 发送全零报告；成功后 IDLE，失败后 RELEASE_PENDING |
| HELD | 逻辑键切换 | 先释放旧报告，成功后才能发送新键 Down |
| RELEASE_PENDING | 重试可发送 | 重发全零报告；成功后结束释放屏障 |
| 任意 | 会话失效或业务取消 | 取消旧输入、进入清理及重新松开门槛；旧事件不得作用于新会话 |

释放屏障期间不接纳新的 Down，并取消期间到达的新按下周期，等待再次松开后重按，避免在恢复后补发迟到输入。正常情况下按 FIFO 顺序处理每个周期，尤其同键再次按下前必须完成前一次释放提交。

固定 20 ms 释放计时器必须退出真实按键路径。若保留旧 `click()` 供其他明确用途使用，必须核对所有调用者，并保证脉冲定时器不能释放正在保持的物理键；优先避免两种执行模式并行共享状态。

## 6. 异常释放、连接与配键切换

### 6.1 发送失败

Up 发送失败后保留释放责任，在同一有效 HID 会话中以有界频率重试；可优先使用发送可用事件，并以受控定时器兜底，禁止忙循环。重试参数在实现时确定并测试，不能到达次数上限后就清除待释放状态、允许新 Down。

如果会话仍有效但持续不可发送，保持输入阻塞并记录错误，直到释放成功或会话失效。断链后无法保证把 Up 送到旧 PC；本地清理应取消旧任务，主机侧恢复依赖连接状态处理，需实机验证。

保证边界：阻止新的 Down 并不能让已收到 Down 的 PC 立即停止重复；只有主机收到释放或自行清理连接状态才会停止。因此不得宣称“任意发送故障下都不会卡键”。本次保证可恢复发送故障下持续承担释放责任、恢复后优先释放；永久传输故障下停止新输入并暴露错误，不自动断开可能同时承载 RDX 的共享 ACL。若产品要求有界时间强制停止，需要另行确定会话终止策略。

### 6.2 会话失效与恢复

断连、HID owner 切换、CCC 关闭、安全条件丢失、Suspend、reset/deinit 均应纳入清理。能发送时先尝试释放，再清理；不能发送时记录恢复所需的零状态屏障。恢复 ready 后先确保零报告成功提交，再允许新的物理按下，并要求稳定松开后重新接纳。

事件、重试及定时回调需携带或校验会话代次，不能只比较连接句柄，因为句柄可能复用。旧会话的报告、重试和释放不能发送给新 owner；新会话的初始零报告属于新的清理流程。核对现有 ready-drop/reset 调用关系，避免取消和 ready 检查互相递归。

HID 会话代次必须独立于 RDX 运行时和通用 transport epoch。现有 `rdx_ble_session_release_rdx()` 会推进 RDX runtime epoch，并间接推进 transport epoch；现有 RDX 异步 token 不能直接充当 HID 按住、释放和重试的有效性凭据。HID 凭据应包含 owner 所在 slot、该 slot 的连接实例 generation 及独立 `hid_epoch`，发送前验证它们仍指向同一有效 HID owner。

| 标识 | 推进或失效条件 | 约束 |
|---|---|---|
| 连接实例 generation | slot 断开、释放后重用，沿用连接管理规则 | 相同连接句柄不能代表同一连接实例 |
| HID 代次 `hid_epoch` | HID owner 更换、HID 能力失效、模块 reset/deinit，以及建立新的 HID 会话 | CCC 关闭、加密丢失、Suspend 均使旧输入和重试失效；恢复时创建新的清理流程 |
| 输入代次 | 路由/业务准入切换、溢出恢复、配键切换及 HID 生命周期切换 | 作废旧输入及手势；同一有效 HID 会话内的待释放责任不能随输入代次被抹除 |
| 映射代次 | 每次有效 apply，包括事务回滚 apply | 旧 Down 不得读取新映射；回滚仍保留释放责任 |

仅执行 `rdxclose` 或 RDX owner 交接，且 HID owner、连接实例和 HID ready 均未改变时，不推进 HID 代次，不取消 HELD，不清除 RELEASE_PENDING，也不为 HID 强加重新松开的门槛。输入快照若刷新，不能仅因 RDX epoch 改变就作废有效 HID 周期。RDX 配键事务继续使用原 RDX token；其失效导致回滚时按第 6.3 节处理。该隔离同时适用于同链 RDX_HID 和分链 RDX/HID 拓扑。

### 6.3 配键热应用

按住 A 时将映射改为 B，不允许立刻把当前按住变为 B。应用新映射时取消旧周期，并先处理旧报告释放；释放未成功时允许保存新映射，但禁止以新映射发送 Down。用户松开后再次按下，才使用 B。

报告快照与映射代次用于防止旧动作读到新映射。配键提交成功的含义仍按原协议，不把存储成功冒充为主机已经接收释放；内部输入屏障负责处理发送异常。

现有提交顺序是 `store_prepare → RAM apply → token 检查 → store_commit`，token 失效或持久化提交失败会再次 apply 旧映射。此次改造保持事务顺序：apply 负责安装映射并建立输入屏障，不等待主机确认，也不因 Up 暂时失败破坏已定义的返回语义；回滚再次 apply 必须幂等地保留待释放责任。禁止回滚重放之前按住的 Down，禁止第二次 apply 清除第一次留下的 RELEASE_PENDING。现有契约验证的是释放调用先于映射替换，并不是已确认主机收到释放，测试说明应同步明确这一点。

## 11. COM3 断言修复与 JL 任务上下文约束（2026-09-21）

### 11.1 根因与原生依据

`COM3_2026-09-21_11-00-59.log` 在 11:02:21 记录
`app_ble_module_manage.c:515 ASSERT-FAILD`，随后看门狗超时重启。
当时构建的 `sdk.lst` 显示：`app_ble_att_send_data()` 在第 513～515 行检查
`cpu_in_irq()` / `cpu_irq_disabled()`，第 535 行调用 `os_mutex_pend()`。
异常栈地址 `0x0600ad24` 对应原 `rdx_hogp_report_send_for_input()` 第 593 行，
调用发生在关中断区；上层为新 HID 会话的全零报告屏障，因此无需按键也能触发。
这些地址仅属于故障版构建，不能用于修复版地址解析。

原 host 桩将关中断操作实现为空操作，无法发现这一 SDK 合约违例。
修复参考 JL `SDK/apps/common/debug/dlog_config.c` 的
`os_taskq_post_type("btstack", Q_CALLBACK, ...)` 用法、原生
`custom_protocol_demo/custom_protocol.c` 的任务态发送，以及本项目已有
`rdx_session_control.c` 对 btstack 的 token 校验和投递方式。
不访问库内私有互斥量，不用关调度/关中断替代 SDK 互斥量。

### 11.2 最终实现

- `app_core` 仍拥有按键动作、FIFO、配键与释放重试；最终 HOGP token 校验及 ATT
  提交放在 `btstack`，与常规 HCI/ATT/SM 连接所有权更新串行执行。
  两处发送入口先拒绝 IRQ/关中断调用；短临界区只用于快照和 mailbox 状态。
- 固定一个在途 mailbox，复制 8 字节 report、HID token、输入代次与 ticket。
  不投递栈指针、不动态分配、不让 app_core 同步等待 btstack，也不依赖可能丢失的
  完成消息。原 10 ms app_core 定时器轮询结果。
- `RDX_HOGP_SEND_PENDING` 仅表示等待任务执行；只有实际 ATT 返回成功才确认完成。
  队列满/ATT 失败继续保留欠下的 Up；同一请求等待期间不会重复投递。
- 排队中的 Down 在执行时复核 HID epoch、owner slot/generation、ready 与输入代次。
  断连后同一个 wrapper/ACL 数值被复用，也不能发送旧 Down。RDX release 不改变
  独立 HID token，组合和分离链路继续保留 HID。
- 输入失效发生在提交之前时拒绝 Down；若失效与已开始的 ATT 提交重叠，动作层仍
  保留在途 Down 的完成结果和欠下的 Up，随后释放，不能将 pending 当失败直接遗忘。
- 正常异步等待暂停 FIFO 消费，Up 完成后才消费对应边沿并处理下一个 Down，保留快速
  Down→Up→Down 顺序。真正的队列/ATT 失败和 FIFO 溢出进入旧输入失效、释放、
  新代次稳定 NO_KEY 后重新接纳的恢复流程。
- mailbox 不在会话复位时强行重用；排队回调完成后才允许覆盖，防止旧回调操作新请求。

提交前/提交中取消、溢出和释放重试。此类测试仍不替代 JL OS/蓝牙库及 PC 主机实测。

CCC/Suspend、RDX release、BLE 与录音并行压力。额外记录异步发送/释放延迟及空闲功耗。
