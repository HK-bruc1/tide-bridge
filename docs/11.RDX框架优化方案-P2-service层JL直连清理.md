# RDX 框架优化方案 — P2：service 实现层 JL 直连清理

> 依据：`docs/10.RDX框架优化方案-P0P1-板级与SPI收口.md` 附录 C 依赖关系图 — P0/P1 已完成，P2 可独立推进。
> 定位：面向开发者的技术执行方案，包含差距清单 + 具体改造步骤 + 验证方式。
> 范围：`service/*.c` 实现层中直接调用 JL SDK OS 原语（`os_taskq_post_type`、`sys_timeout_*`、`sys_timer_re_run`）的清理，以及残余 JL SDK 头文件依赖的剪除。
> 不包含：`rdx_app.c`、`rdx_charge.c`、`rdx_dut.c`、`rdx_ble_server.c` 等业务 `.c` 中的 JL SDK 直连（属于 P3+ 范围）。

---

## 术语表

| 术语 | 含义 |
|---|---|
| **JL 直连** | service 实现层 `.c` 中直接调用 `os_taskq_post_type()`、`sys_timeout_add()`、`sys_timer_re_run()` 等 JL SDK OS 原语，绕过 OSAL 封装层 |
| **OSAL 封装** | `port/jl/include/rdx_jl_osal.h` 中声明的 `rdx_os_timer_add()`、`rdx_os_task_post_*()` 等平台抽象接口，内部调用 JL SDK，对 service 层暴露语义化 API |
| **Q_CALLBACK 模式** | `os_taskq_post_type("app_core", Q_CALLBACK, N, msg)` 的标准用法：`msg[0] = 函数指针`，`msg[1..N-1] = 参数`，由 app_core 任务调度执行 |
| **boundary check** | `tools/check_rdx_boundaries.ps1` 静态边界检查脚本 |

# Part 2 — 改造方案

## 2.1 总体思路

改造顺序：
1. 补齐 `rdx_jl_osal.h` 中缺失的 OSAL API 声明（`rdx_os_task_post_callback`、`rdx_os_timer_re_run`）
2. 在 port/jl 实现层补齐实现
3. 逐文件替换 service/*.c 中的 JL 直连调用
4. 剪除残留的 JL SDK 头文件 include
5. 扩展 boundary check 规则

## 2.2 OSAL API 补齐

### 2.2.1 `rdx_os_task_post_callback`（新增）

将 `os_taskq_post_type("app_core", Q_CALLBACK, 2, msg)` 的标准模式封装为语义化 API：

```c
// rdx_jl_osal.h 新增声明
rdx_err_t rdx_os_task_post_callback(const char *task_name,
                                    void (*callback)(void *),
                                    void *arg);
```

实现（`port/jl/jl7018/rdx_jl_osal.c` 和 `port/jl/jl7018_shadow/rdx_jl_osal.c`）：

```c
rdx_err_t rdx_os_task_post_callback(const char *task_name,
                                    void (*callback)(void *),
                                    void *arg)
{
    int msg[2];
    msg[0] = (int)callback;
    msg[1] = (int)arg;
    int ret = os_taskq_post_type(task_name, Q_CALLBACK, 2, msg);
    return (ret == 0) ? RDX_OK : RDX_ERR_IO;
}
```

**回调签名约定**：

JL SDK Q_CALLBACK 调度实现在预编译库中，无法查看源码，但从现有调用点的两种模式可以推断调度行为：

| 模式 | 回调签名 | msg[1] 用法 | 示例 |
|---|---|---|---|
| A | `void cb(void)` | msg[1]=0，不使用 | `rdx_device_service_factory_reset` |
| B | `void cb(void *priv)` | msg[1] 传实际指针 | `rdx_event_publish_async_cb` |

无论调度器是 `((void(*)())msg[0])()` 无参调用还是 `((void(*)(void*))msg[0])(msg[1])` 单参调用，现有代码已在两种模式下正常运行（依赖 ARM/MIPS 调用约定上额外压栈参数被 callee 忽略的特性）。

`rdx_os_task_post_callback` 声明 `callback` 参数为 `void (*)(void *)`，对模式 A 的调用点使用显式强转 `(void (*)(void *))actual_func` — 这和当前代码 `msg[0] = (int)actual_func` 的强转是同一性质的操作。类型不安全但行为不变，封装层不做更"聪明"的适配。

**设计决策**：`rdx_os_task_post_callback` 仅封装 2 参数的 Q_CALLBACK 模式（覆盖 7/10 个调用点）。`rdx_record_service.c` 中 3 个 4 参数调用点（274/348/454 行）使用 `Q_CALLBACK` + 4 元素数组，参数数量不同但模式相同 — 这些调用点使用下节的 `rdx_os_task_post_msg_array()`。

### 2.2.2 `rdx_os_task_post_msg` 与 `rdx_os_task_post_msg_array`

**现状**：

- `rdx_jl_osal.h:40` 已声明两参数版本 `rdx_os_task_post_msg(const char *task_name, u32 msg, u32 arg)`，保留不动。
- `rdx_record_service.c` 的 4 参数 Q_CALLBACK 调用点（274/348/454 行）使用 4 元素 msg 数组，需要单独的封装。
- **命名策略**：新增 `rdx_os_task_post_msg_array` 处理多参数场景，避免破坏已有两参数声明的签名兼容性。

```c
// rdx_jl_osal.h 新增声明
rdx_err_t rdx_os_task_post_msg_array(const char *task_name, u32 msg_type,
                                     u32 argc, int *argv);

// port/jl/jl7018/rdx_jl_osal.c 实现
rdx_err_t rdx_os_task_post_msg_array(const char *task_name, u32 msg_type,
                                     u32 argc, int *argv)
{
    int ret = os_taskq_post_type(task_name, msg_type, argc, argv);
    return (ret == 0) ? RDX_OK : RDX_ERR_IO;
}
```

jl7018_shadow 的 `rdx_jl_osal.c` 同样补齐了上述所有 API（实现与 jl7018 一致，内部调用相同的 `os_taskq_post_type()`）。参见 §2.2.4 — `SDK/Makefile` 中 `service/*.c` 是公共源文件列表，shadow 与 service 层确实会一起编译，因此 shadow 必须补齐。

**API 命名总览**：

| API | msg 元素数 | 用途 |
|---|---|---|
| `rdx_os_task_post_msg(task_name, msg, arg)` | 2（简单消息） | 原声明保留，P2 不改造调用点但补齐实现 |
| `rdx_os_task_post_callback(task_name, cb, arg)` | 2（Q_CALLBACK） | 封装 `Q_CALLBACK` + func ptr 模式 |
| `rdx_os_task_post_msg_array(task_name, type, argc, argv)` | N（任意） | 封装 4 参数 Q_CALLBACK 等非标场景 |

### 2.2.3 `rdx_os_timer_re_run`

`rdx_clock_service.c:66` 使用 `sys_timer_re_run()` 重置定时器而不重新创建。新增 OSAL wrapper：

```c
// rdx_jl_osal.h 新增声明
void rdx_os_timer_re_run(rdx_timer_t id);

// 实现
void rdx_os_timer_re_run(rdx_timer_t id)
{
    sys_timer_re_run(id);
}
```

### 2.2.4 `jl7018_shadow` timer 时间换算修复

**背景**：`SDK/Makefile` 第 492 行 `port/jl/$(RDX_CHIP_FAMILY)/rdx_jl_osal.c` + 第 499-509 行 `service/*.c` 是公共源文件列表，不做 chip family 区分。即 `RDX_CHIP_FAMILY=jl7018_shadow` 时，service 层**确实会**和 shadow OSAL 一起编译。

**P2 引入的问题**：shadow/rdx_jl_osal.c 的 `rdx_os_timer_add` 原先有 `timeout_ms * 10` 换算（注释 "chip-specific tick conversion"，无 HW 手册引用）。P2 将 `rdx_clock_service.c` 从直接 `sys_timeout_add(NULL, ..., 5000)` 迁移为 `rdx_os_timer_add(..., 5000)`，在 shadow 上会导致 5000ms → 50000ms 的行为变化。

**修复**：移除 shadow 的 `rdx_os_timer_add` 中 `* 10` 换算，与 jl7018 实现一致（直接透传 `timeout_ms`）。P2 新增的 `rdx_os_timer_re_run` 无时间参数，不受影响。

**遗留**：shadow 的 `rdx_os_mutex_lock` 仍有 `timeout_ms / 2` 换算（已有行为，非 P2 引入），同样无 HW 手册引用。本次 P2 不改变 mutex 调用路径，留待后续 shadow 验证时统一处理。

## 2.3 逐文件迁移步骤

### 步骤 1：`service/rdx_device_service.c`（1 处代码 + 2 个残留 include）

`rdx_device_service_factory_reset` 实际签名为 `rdx_err_t rdx_device_service_factory_reset(void)`（无参，返回 rdx_err_t）。
按照 2.2.1 节的约定，使用显式强转适配 `rdx_os_task_post_callback` 的 `void (*)(void *)` 签名。
这等价于当前代码 `msg[0] = (int)rdx_device_service_factory_reset` 的强转行为，不改变运行时行为。

```c
// 行 351-357，当前
int msg[2];
msg[0] = (int)rdx_device_service_factory_reset;
msg[1] = 0;
if(os_taskq_post_type("app_core", Q_CALLBACK, 2, msg)){
    log_info("[APP CMD] sys_reset taskq post err\r");
}

// 替换为
if (rdx_os_task_post_callback("app_core",
     (void (*)(void *))rdx_device_service_factory_reset, NULL) != RDX_OK) {
    log_info("[APP CMD] sys_reset taskq post err\r");
}
```

删除残留 include：`#include "gpio_config.h"`（P0 后已无引用）和 `#include "rdx_jl_gpio.h"`（P2 确认零引用）。

> `#include "poweroff.h"` 保留，`sys_enter_soft_poweroff(POWEROFF_NORMAL)` 属于电源管理边界，不在本次 OSAL wrapper 覆盖范围。

### 步骤 2：`service/rdx_clock_service.c`（3 处）

| 行号 | 当前 | 替换为 |

| 56 | `sys_timeout_del(g_clock_lock_timer)` | `rdx_os_timer_del(g_clock_lock_timer)` |
| 66 | `sys_timer_re_run(g_clock_lock_timer)` | `rdx_os_timer_re_run(g_clock_lock_timer)` |
| 70 | `sys_timeout_add(NULL, rdx_clock_service_unlock_timer_cb, 5000)` | `rdx_os_timer_add(rdx_clock_service_unlock_timer_cb, NULL, 5000)` |

添加 `#include "rdx_jl_osal.h"`。

### 步骤 3：`service/rdx_event_bus.c`（1 处）

## 2.4 边界检查脚本扩展

在 `tools/check_rdx_boundaries.ps1` 中增加 P2 规则：

```powershell
# P2: service .c must not call os_taskq_post_type directly
$serviceCFiles = $allRdxFiles | Where-Object {
    $_.FullName -match "[/\\]service[/\\]" -and $_.Name -like "*.c"
}
$taskqHits = Find-Pattern -Files $serviceCFiles `
    -Pattern "\bos_taskq_post_type\b"
Assert-NoHits "service .c has no direct os_taskq_post_type calls" $taskqHits

# P2: service .c must not call sys_timeout_* directly
$sysTimeoutHits = Find-Pattern -Files $serviceCFiles `
    -Pattern "\bsys_timeout_(add|del)\b"
Assert-NoHits "service .c has no direct sys_timeout_add/del calls" $sysTimeoutHits

# P2: service .c must not call sys_timer_re_run directly
$sysTimerHits = Find-Pattern -Files $serviceCFiles `
    -Pattern "\bsys_timer_re_run\b"
Assert-NoHits "service .c has no direct sys_timer_re_run calls" $sysTimerHits
```

1. `t2616_cc` + `t2616_ep` 两个 board 配置均编译通过。

## 3.3 目标板冒烟

1. **系统复位命令**：APP 发送 `sys_reset` 命令 → 设备通过 `rdx_os_task_post_callback` 投递到 app_core → 正常执行 factory reset。
2. **时钟锁定/解锁**：录音场景下 `rdx_clock_service_lock_with_timer()` 正常锁定时钟，超时后 `rdx_os_timer_re_run` 正确续期或 `rdx_os_timer_del` 正确释放。
3. **录制控制**：BLE 发送录制备忘录开始/停止命令 → `rdx_record_service.c` 的 taskq post 正常投递 → 录制状态正确切换。
4. **事件总线**：`rdx_event_bus.c` 事件分发正常，`rdx_os_task_post_callback` 投递成功。
