# OpenAI Codex Micro Windows MVP 快速验证方案

> 文档状态：Windows-first 实验方案，尚未实施
> 目标平台：Windows 11 + ChatGPT desktop app for Windows
> 协议参考：`codex-micro-4-core2/` commit `2ee23a4ab696f94bb78d250f28cc4a9b879ba079`
> 边界：仅限受控实验构建、新鲜配对和一台固定 Windows 主机；不是量产方案或官方协议规范

## 1. 先回答 Windows 资格问题

开源参考项目只记录了 macOS 实机成功，没有 Windows 验证。OpenAI 官方 Codex Micro 页面说明可通过 USB-C 或 Bluetooth 连接电脑，并单列 macOS Input Monitoring；官方 Windows 应用文档没有明确给出 Codex Micro 的 Windows 支持矩阵。

因此 MVP 分成两个互不混淆的结论：

| 结论 | 成功条件 | 失败含义 |
|---|---|---|
| Gate W0：Windows App 具备设备路径 | 官方设备或已验证参考固件能在目标 Windows App Build 中出现 Codex Micro 设置，并发生 ID 6 通信 | Windows App/账号/版本/环境不满足，暂不能评价 T2620 |
| T2620 MVP：复合设备可互操作 | T2620 的标准键盘 + ID 6 Vendor HID 被同一 Windows App 发现，`device.status` 和 AG00 生效 | 再区分身份、JL BLE、复合描述符或协议实现问题 |

若没有官方 Codex Micro 或 M5Stack Core2 参考硬件，可以继续 T2620 实验，但 Gate W0 记为“未验证”，任何失败都不能直接归因于固件。

这不是 OpenAI API 接入，不使用 API Key、网络请求或云端 SDK。

## 2. MVP 成功定义

固定以下闭环：

```text
Windows 11 新鲜配对
    -> HIDClass 枚举 Report ID 6，host report 长度为 64
    -> 设备侧 effective ATT payload >= 63
    -> Windows Host 工具完成 device.status round trip
    -> ChatGPT Windows App 首次显示 Codex Micro 设置
    -> App 向 ID 6 Output 写入至少一条有效 RPC
    -> T2620 发出 AG00 down/up
    -> App 执行预期 Agent Key 动作
    -> 同一物理键不产生 Report ID 1 副作用
```

前四项证明 Windows HID 和协议路径；后四项证明 ChatGPT 互操作。只完成 Host 工具 round trip 不能宣称 ChatGPT 兼容。

## 3. 固定测试环境

每次记录以下信息，任一变化都视为新的测试矩阵：

- Windows edition、版本和 OS Build；
- ChatGPT Windows App 版本/Build、安装来源、账号方案和 workspace；
- Bluetooth Adapter 型号、硬件 ID、驱动版本；
- 连接方式固定为 Bluetooth LE，不混入 USB；
- T2620 firmware Git commit、构建时间、实验开关和身份变体；
- 配对前是否删除旧设备、是否重启固件与 App；
- Windows 显示的设备实例 ID、HID collection 路径和报告长度。

Windows 不执行 macOS Input Monitoring 步骤。若 App 没有出现 Codex Micro 设置，先判断 Gate W0，不能用 macOS 权限排障替代 Windows 证据。

## 4. 三个构建变体

只通过编译开关改变一个变量集，禁止现场随意改多个字段：

| 变体 | Report Map | 用途 |
|---|---|---|
| C0 Current | 当前 70 字节 ID 1 Keyboard | 证明现有标准键盘基线 |
| V1 Vendor-only | 只暴露参考项目原始 29 字节 ID 6 Vendor Collection 和对应 Report Characteristic，不暴露 ID 1 | 隔离 JL/Windows/身份/协议问题 |
| C1 Composite | 70 字节 Keyboard + 29 字节 Vendor，共 99 字节 | 最终 MVP 目标 |

V1 与 C1 在受控实验身份模式下使用同一组逻辑身份：

```text
Device Name     Codex Micro
Manufacturer    Work Louder
PnP Source      0x02
VID:PID         0x303A:0x8360
PnP Version     0x0101
Appearance      Generic HID
HID Service     0x1812
Usage Page      0xFF00
Usage           0x01
Report ID       6
```

这些字段只是一组共同验证成功的参考值，不代表每项都是 Windows 发现必要条件。JL 的 PnP Value 应按 little-endian 原始字节 `02 3A 30 60 83 01 01` 编码，并由 Windows 断言逻辑 Source/VID/PID/Version；不要复制 Arduino-ESP32 的 `swapBytes()` workaround。V1/C1 还要保存原始 ADV 与 Scan Response，比较 Generic HID、HID UUID、名称、RDX Manufacturer Data 和 preferred connection parameter 字段。它们不属于本产品；实验身份开关必须默认关闭，禁止进入量产或对外发布物。

## 5. HID 与 GATT 最小改动

### 5.1 Vendor Report Descriptor

逐字节复用参考项目的 29 字节片段：

```c
0x06, 0x00, 0xFF,  /* Usage Page 0xFF00 */
0x09, 0x01,        /* Usage 1 */
0xA1, 0x01,        /* Collection Application */
0x85, 0x06,        /* Report ID 6 */
0x15, 0x00,        /* Logical Minimum 0 */
0x26, 0xFF, 0x00,  /* Logical Maximum 255 */
0x75, 0x08,        /* Report Size 8 */
0x95, 0x3F,        /* Report Count 63 */
0x09, 0x01,        /* Input Usage 1 */
0x81, 0x02,        /* Input */
0x95, 0x3F,        /* Report Count 63 */
0x09, 0x02,        /* Output Usage 2 */
0x91, 0x02,        /* Output */
0xC0
```

V1 长度为 29，且实验 ATT 表不保留 ID 1 Input/Output Report Characteristic；C1 长度为 99，并恢复完整 ID 1 + ID 6 布局。只替换 Report Map 却保留 ID 1 Characteristic 的构建不属于 V1。MVP 不加入 Feature、Consumer、Mouse、Game Pad，也不把 Usage 改成另一组“语义更直观”的值。

### 5.2 C1 句柄布局

| 句柄 | 属性 | 说明 |
|---|---|---|
| `0x0016-0x0025` | 现有 HID | ID 1 Input/Output 原样保留 |
| `0x0026` | Characteristic Declaration | Codex Input |
| `0x0027` | Report Value | Read + Notify，63 字节 |
| `0x0028` | CCC | Codex Input 独立 CCC |
| `0x0029` | Report Reference | ID 6, Input Type 1 |
| `0x002a` | Characteristic Declaration | Codex Output |
| `0x002b` | Report Value | Read + Write + Write Without Response，63 字节 |
| `0x002c` | Report Reference | ID 6, Output Type 2 |
| `0x002d-0x0031` | DIS | 原 DIS 整体后移 |

新动态 Value/CCC 使用现有 HOGP 加密边界。修改 GATT 后必须在 Windows 设置中删除设备再配对；MVP 不把旧 bond/GATT 缓存迁移算进范围。

## 6. Windows 报告边界与 framing

固件 ATT Value 固定为 63 字节，不含 Report ID：

```text
[0x02][N][N 字节 UTF-8 JSON][zero padding]
```

`N` 范围为 `0..61`。设备发送紧凑 JSON 后追加单个 LF，再按最多 61 字节切片。

Windows Host 工具使用 64 字节 report buffer：

```text
[0x06][0x02][N][data...][zero padding]
```

工具必须从 Windows HID capabilities 读取实际 `InputReportByteLength` 和 `OutputReportByteLength`。若不是 64，先保存枚举证据，不强行截断或补成假定长度。

RX 解码同时接受 LF、CRLF 和无换行但已完整闭合的顶层 JSON。它按 JSON 完整性派发，而不是只扫描 CRLF；字符串、转义、嵌套和 UTF-8 跨片必须正确处理。每个 link 使用独立 1024 字节上限和 generation token。

63 字节 ATT Value 需要 ATT MTU 至少 66。Windows 主机工具通常无法直接替代设备侧 MTU 证据，因此以设备日志中的 exchange 结果、63 字节 write callback 和 round trip 共同判定。

## 7. MVP RPC

### 7.1 Windows Host 到设备

请求使用完整字段：

```json
{"method":"device.status","id":1}
```

响应：

```json
{"id":1,"result":{"version":"t2620-mvp","profile_index":0,"layer_index":1,"battery":87,"is_charging":false}}
```

`layer_index` 固定为 1，与参考实现及 OpenAI 官方“Codex uses layer 1”一致。`id` 原样回传，电量是 `0..100`，充电状态是 JSON boolean。

还需支持：

- `sys.version`：返回自身版本；
- `v.oai.thstatus`：校验数组中的 `id/c/b/e/s`，MVP 不驱动物理灯；
- `v.oai.rgbcfg`：校验 `ambient` / `keys` 的 `c/b/e/s`；
- `lights.preview`、`host.focused_app`：带 `id` 时返回 `ok`；
- 未知方法：返回 `-32601 Method not found`。

灯效类型为：`id` 整数、`c` 24 位整数、`b/s` 浮点、`e` 字符串（如 `off`、`breath`）。无 `id` 的 notification 不响应。危险方法和 `fs.*` 不进入 allowlist。

### 7.2 设备到 Windows Host/App

只映射一个物理键：

```json
{"method":"v.oai.hid","params":{"k":"AG00","act":1,"ag":0}}
{"method":"v.oai.hid","params":{"k":"AG00","act":0,"ag":0}}
```

该键在 C1 实验构建中不再发送对应 ID 1 扫描码。其余键保持现有键盘行为。MVP 不实现更多 AG/ACT 键、`v.oai.rad`、旋钮或实际灯效。

## 8. 最小固件实现

| 位置 | 修改 |
|---|---|
| `t2620_project_config.h` | 增加默认关闭的 MVP 与实验身份开关 |
| `rdx_hogp_profile.h/.c` | ID 6 常量、句柄、Reference、29/99 字节 Map |
| `rdx_ble_server.c` | 新 Report Characteristic、DIS 后移、ATT 分发、Codex TX 唤醒 |
| `rdx_codex_micro.c/.h` | 有界 RX、RPC allowlist、status、63 字节 TX 分片、CCC 状态 |
| `rdx_hogp_key_action.c` | 实验开关下重定向一个键到 AG00 |
| `SDK/Makefile` | 显式加入 `rdx_codex_micro.c` |
| `tests/host/run_host_tests.ps1` | 加入 `test_codex_micro_contract.ps1` |

Codex 复用现有 HID owner。ATT callback 只校验、复制、入队；cJSON 解析在 `app_core` 执行。TX 使用有限 FIFO 和 `ATT_EVENT_CAN_SEND_NOW`/等价可发送事件重试，必须处理 `APP_BLE_BUFF_FULL`，不得用阻塞 delay 模拟参考项目的 4 ms 间隔。该 FIFO 是 V1 首次多片 `device.status` 的前置实现，不是 C1 之后的可选加固。

开关关闭时，原 Report Map、ATT 表、PnP 字节和行为保持不变。发布镜像增加实验身份字节扫描。

## 9. MVP 资源与安全门槛

构建前先冻结以下 pass/fail 门槛，构建后记录实测：

- Flash 与 BSS 增量；
- 连接态最小空闲堆；
- `app_core` 和 Bluetooth task 栈最低水位；
- ATT callback 最大执行时间；
- RX/TX 队列峰值和丢弃计数；
- `APP_BLE_BUFF_FULL` 次数与最终恢复结果。

MVP 初始门槛为：Flash 增量不超过 32 KiB；BSS 增量不超过 4 KiB；连接态最小空闲堆不少于 12 KiB 且相对 C0 下降不超过 8 KiB；`app_core` 栈剩余不少于 1 KiB；Bluetooth task 栈剩余不少于 512 B；ATT callback 单次不超过 1 ms 且零动态分配。平台 watermark 若不是字节，必须换算后记录。

固定上限：每 link RX 1024 字节；TX 不超过 4 条消息和 2 KiB；JSON 深度、方法名长度和数组元素数单独限制。断连、owner 释放、非法 framing 和 overflow 清除对应 generation，不执行未知系统动作。

## 10. Windows 主机工具

MVP 必须提供一个 Windows 原生 HID 小工具或测试程序，并配套 `BluetoothLEAdvertisementWatcher`/BLE sniffer 采集广播；二者都不依赖 ChatGPT：

1. 用 SetupDi 枚举 HID interface，以 `HidD_GetPreparsedData` + `HidP_GetCaps` 读取 top-level Usage 和报告长度；
2. 打印设备路径、VID/PID/Version、Usage、Input/Output Report Byte Length；
3. 以 `WriteFile` 作为 ID 6 Output 主路径；另行测试并记录 `HidD_SetOutputReport`，禁止静默 fallback；
4. 用 overlapped `ReadFile` 接收 ID 6 Input notification，不能用 `HidD_GetInputReport` 替代 Notify 路径；
5. 按 `[02][N]` 重组并在 2 秒内验证 `device.status`；
6. 对 LF、CRLF、多片、非法长度和 timeout 给出明确结果；
7. HID 工具保存脱敏 report/DIS trace，BLE 采集侧保存 ADV 与 Scan Response data sections，作为仓库 fixture。

PowerShell 枚举命令仅作辅助：

```powershell
Get-PnpDevice -Class HIDClass | Format-Table Status, FriendlyName, InstanceId
pnputil /enum-devices /class HIDClass /properties
```

这些命令不能读写 Vendor Report，不能替代主机工具 round trip。

## 11. 验收步骤

### 11.1 Gate W0

1. 固定并记录 Windows/App/Adapter/driver 版本；
2. 用官方设备或参考硬件新鲜配对；
3. 确认 HIDClass 枚举与 ID 6 collection；
4. 打开 ChatGPT，确认首次出现 Codex Micro 设置；
5. 记录设备侧是否收到 `device.status`、`thstatus`、`rgbcfg` 或其他 ID 6 Output；
6. 触发一个 Agent Key，确认 App 行为。

### 11.2 T2620 C0

1. 运行现有五项 host contract；
2. 编译、刷写 C0；
3. 确认标准键盘、LED Output、回连和 RDX 无回归。

### 11.3 T2620 V1

1. 编译 Vendor-only + 实验身份；
2. Windows 删除旧设备并新鲜配对；
3. 用 Windows Host 工具完成 `device.status` 多片 round trip；
4. 确认 App 发现和 AG00 down/up；
5. 保存 PnP、HID caps、原始 ADV/Scan Response、MTU、CCC 和 trace。

### 11.4 T2620 C1

1. 编译 99 字节复合 Map；
2. 再次删除旧设备并配对；
3. 重复 V1 全部步骤；
4. 验证 AG00 无 ID 1 副作用，其余键仍是标准键盘；
5. 注入 TX buffer-full，验证多片响应最终完整且不交错；
6. 验证未加密、wrong-owner、第二 link 和旧 generation 均 fail-closed；
7. 完成 3 次删除设备后的新鲜配对；
8. 完成 100 次多片 `device.status` round trip 和 100 次 AG00 down/up；
9. 完成 20 次生命周期循环：设备断连、Windows 睡眠/唤醒、Bluetooth 重启、App 重启各至少 5 次。

所有循环要求 0 丢片、0 交错、0 stuck key、0 ID 1 副作用、0 wrong-owner 成功访问；从 encrypted + CCC ready 起，`device.status` 必须在 2 秒内完成。

固件验证命令：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tests\host\run_host_tests.ps1
Set-Location .\SDK
.\.vscode\winmk.bat all
```

## 12. 判定矩阵

| 结果 | 结论 | 后续动作 |
|---|---|---|
| Gate W0 失败 | Windows App 支持资格未建立 | 停止 ChatGPT 直连判断，核对 App Build/账号/官方支持 |
| W0 成功，V1 Host round trip 失败 | JL HID/MTU/GATT/framing 问题 | 先修平台传输，不改复合 Map |
| V1 Host 成功，App 不发现 | 身份或 Windows App 枚举条件不匹配 | 一次只 A/B 一个身份字段并保留日志 |
| V1 App 成功，C1 App 失败 | 复合 Report Map/collection 影响发现 | 比较 Windows HID collection 与 top-level usage 枚举 |
| C1 App 发现，status 失败 | Output/RX/TX/CCC/MTU 问题 | 用 Host 工具和设备日志定位具体层 |
| C1 AG00 生效且无键盘副作用 | Windows MVP 成功 | 进入完整方案 Phase 2 加固 |

## 13. MVP 完成定义

只有以下条件全部满足，才能标记 Windows MVP 成功：

- Gate W0 在目标 Windows App Build 上通过；
- C0 标准键盘与现有五项 contract 无回归；
- V1 和 C1 都被 Windows HID 正确枚举并完成 Host 工具 round trip；
- C1 被 ChatGPT 发现，`device.status` 和 AG00 down/up 生效；
- AG00 无 ID 1 副作用；
- 多片 TX 在 buffer-full 后可恢复，断连/owner/generation fail-closed；
- Windows 睡眠、Bluetooth 重启、App 重启和设备回连通过；
- 资源预算已记录且无堆/栈告警；
- 实验身份默认关闭，未进入量产输出。

若 Gate W0 未验证，只能记录“Windows HID 协议 MVP 成功”，不能记录“ChatGPT Windows 兼容成功”。
