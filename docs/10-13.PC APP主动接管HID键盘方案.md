# 10-13. PC APP 主动接管 HID 键盘方案

> 状态：方案定档，未实施、待真机联调。日期：2026-11-18。
>
> 结论：保留现有「最多两条 ACL、一个 HID owner、一个 RDX owner」架构。**PC APP 的一次「连接」以同一台 PC、同一条 ACL 上 HID 和 RDX 都可用为完成条件。** 如果旧测试 PC 只回连占住了 HID，客户 APP 在本机 RDX 就绪后通过现有 `custom` 通道自动发起接管。固件让旧 PC 交出 HID，在客户 PC 已有的 RDX 链路上补齐 HID；不弹二次确认，不用按设备键。后台自动重连、Windows 历史回连和手机 RDX 接入不触发接管。
>
> 相关文档：[3-3 双连接多服务共存](3-3.BLE一拖二双连接多服务共存实施方案_RDX私有服务与HOGP.md)、[3-4 PC APP 逻辑释放 RDX](3-4.PC_APP逻辑断开无法释放RDX会话问题复盘与处理方案.md)、[3-6 第二入口控制](3-6.BLE复合会话满占时第二入口广播控制方案.md)、[6-2 连接态低功耗](6-2.T2620BLE连接后低功耗设计.md)。

## 1. 复现与根因

已配对的测试 PC A 自动回连，先占用 HID。此时只有一个 owner，空闲 wrapper 继续广播。客户 PC B 能从第二入口连上并使用 RDX，但 Windows 无法在该连接上启用 HID，表现为不显示键盘图标，或已有设备记录却显示「驱动程序错误」。

| 日志 | 关键证据 |
| --- | --- |
| `COM3_2026-11-18_15-50-14.log:244695`、`:244958` | 16:51:46，第一条链路 `0x0050` 成为 HID owner。16:52，第二条 `0x0051` 已加密并读到 HID Report Map，但反复出现 `claim rejected result=1`，随后由对端断开。 |
| `我们自己的内测PCDEMO可以连接上，但是PC系统不显示键盘图标.log:408`、`:643`、`:674`、`:736` | 16:55:54，A 的 `0x0050` 恢复 HID。B 的 `0x0051` 在 16:56:14–16 多次申请 HID 被拒；16:56:18，同一链路建立 RDX 并报告固件 `1.2.4`。 |

`result=1` 是 `RDX_BLE_CLAIM_BUSY`。两份日志均能定位到 **HID 被占用后的拒绝**，不能据此认定新库使 HID 服务消失。第二份日志还说明 Windows 可能在 APP 建立 RDX **之前**就完成一轮失败的 HID 申请。因此不能只在下一次 Input CCC 写入时检查优先级：Windows 不一定再写一次。

## 2. 产品规则

优先级只用于一次明确的接管：**由本次用户主动连接发出的 `hidtake take` > 已占用的纯 HID**。固件不根据 ACL 或 RDX 刚连上就自动换主机，也不按最后写 CCC 或最近一次配对选主机。

这里「一起接管」指**最终由客户 PC B 在同一条 ACL 上同时使用 HID 和 RDX**，不是要求两项在同一时刻建链。Windows 可能先申请 HID，APP 也可能先建立 RDX。原场景中 A 只占 HID，RDX 并未被 A 占用，因此交接时只需让出 HID，不需要断开或重建 B 已经可用的 RDX。

| 场景 | 首版行为 |
| --- | --- |
| PC HID + 手机 RDX，任意连接顺序 | 继续支持双 ACL。手机连接和发业务命令不触发接管，键盘仍发给 PC。 |
| 同一台 PC 的 HID 和 PC RDX，任意连接顺序 | 共用一条 ACL。不需要接管或主动断链；复合 owner 就绪后按原逻辑关闭第二入口。 |
| 测试 PC A 仅持有 HID，客户 PC B 主动连接 | B 的 APP 建立 RDX 并发出 `take`；固件通过准入检查后断开 A 的纯 HID ACL，保留 B 的 RDX。B 的同一条 ACL 上 HID 和 RDX 均就绪才算接管完成。 |
| 旧 PC 已同时持有 HID 和 RDX | 复合 owner 关闭第二入口，B 无法用本方案先建立 RDX 并发送 `take`。需原 APP 先通过 `rdxclose` 释放 RDX，或原 ACL 实际断开。本方案不强制接管已被旧 PC 同时占用的两项服务。 |
| 后台自动重连、普通 RDX 业务、未发 TAKE 或请求已失效 | 保持原 owner；不因第二入口接入、加密成功、历史 CCC 恢复或 `os_type=3` 踢掉旧主机。 |

复用已验证的 RDX `custom` 通道，只新增 `hidtake` 业务指令与应答。不修改 RDX 帧格式、广播数据、GATT handles、HID Report Map 或 APP 绑定状态；不新增第二个 HID 实例，固件不删除旧 SM bond，不清全局 CCC，也不改 100 ms 第二入口与双 ACL 低功耗保护。

### 2.1 接管成功后，测试 PC 会不会抢回

| 客户 PC B 的状态 | 第二入口与测试 PC A 的行为 |
| --- | --- |
| B 在同一条 ACL 上持有 HID + RDX | 复合 owner 关闭第二入口。即使还有空闲 ACL 名额，A 仅凭历史配对记录也没有正常回连入口。 |
| B 的 APP 正常发 `rdxclose`，Windows HID 继续持有 ACL | 只释放 RDX。清理完成、RDX 回到 `READY` 后第二入口重开；A 可能建立第二条 ACL，但写 Input CCC 或恢复历史订阅时，HID 认领返回 `RDX_BLE_CLAIM_BUSY`，按键仍只发给 B。A 若连上，可能占用第二条物理链路；这不等于抢回键盘，也不保证手机此时一定连得进来。 |
| B 的 ACL 实际断开，或设备重启 | B 的 HID owner 不再保留。关闭 PC 蓝牙、移除设备、离开范围等都可能让 ACL 断开；除第 4.4 节显式重配窗口外，A 和 B 都按普通回连规则重新竞争。 |

因此不需要为了保护在线的 B 永久屏蔽 A，也不在首版跨断链或重启记忆「首选 PC」。**APP 断开不等于 Windows 键盘断开**；正常退出要先发 `rdxclose`，仅关闭 GATT 对象或进程异常退出不保证释放 RDX。判断是否让出 HID 以设备侧 owner/链路事件为准，不以 APP 页面或系统图标为准。

## 3. PC APP 交互与接管权限

1. 用户点现有的「连接」，目标是本机同时使用 HID 和 RDX，不新增「只连接 RDX」的模式。RDX 就绪后 APP 查询本链路 HID 状态：`own` 表示两项都已就绪；`none` 或 `own_wait` 继续等普通 HID 启用，不发 `take`。
2. `get` 返回 `other` 时，APP 在**本次主动连接建立的 RDX 会话**上自动发一次 `take`，无需用户再点按钮或操作设备。主动连接的意图只用于这次尝试；用户取消、尝试结束或会话失效即丢弃，后台连接恢复和断线自动重连不沿用。被拒时显示原因，不等业务结束后再自动换机。
3. 设备确认旧链路已退出后，APP 显示「正在连接 Windows 键盘」。若设备已按合法的历史 CCC 恢复就绪，可直接完成；否则先在当前 ACL 上等待 Windows 启用 HID。仅当 Windows 已有错误记录且不再重试时，才引导用户选「重新配对」，并在收到第 4.4 节的 `recover` 应答后提示移除 Windows 设备记录。
4. RDX 先就绪时显示「正在连接键盘」；若 HID 启用失败，提示「RDX 可用，键盘未连接」，不显示整机连接成功。只有当前 RDX 会话有效且同链 HID 已就绪，APP 才显示「已连接」，任一项失效后清除该状态。`ready` 表示本次交接完成；重传返回的缓存 `ready` 不代表键盘此刻仍就绪，恢复界面时以当前 `get` 为准。Windows 键盘图标和真实按键均纳入板测，不用 RDX 连接成功、系统设备记录或断开请求已提交替代。

固件只受理当前有效 RDX owner 显式发出的 `take`，并绑定发起方的 RDX token（slot、连接代次、runtime epoch）及请求 ID。旧链路另外持有独立 ACL token。原请求不得授权给同 handle 的新连接或其他 peer。普通交接本身不主动断开 B；移除 Windows 记录可能断开 B 的 ACL 和 RDX，需要重新发起连接和请求。

「用户主动点连接」由 PC APP 保证，固件看不到点击，也不能用 `os_type`、绑定标志或对端自报地址证明命令来自官方 PC APP。**本方案的权限边界是：能取得有效 RDX 会话并发送有效 `take` 的客户端，可以申请接管纯 HID。** 正常手机 APP 和后台连接流程不发此命令。若量产要求阻止第三方 RDX 客户端仿发，则上线前须另做可信客户端授权；不能把已验证的 `custom` 收发当作鉴权。

## 4. 固件交接流程

```text
空闲 → TAKE 准入通过 → 冻结旧 HID 输入、发送全键释放
     → 提交旧 ACL 断开 → 确认旧 owner 已释放 → 目标启用 HID → 键盘就绪
                                             ↘ 显式重配：仅保留限时防竞争窗口
```

### 4.1 准入与旧主机释放

- 复用 `rdx_app_custom_command_parse()` 和 owner-scoped RDX token，在 `app_core` 上推进状态。受理请求、处理异步回调和提交断开前均重验 token、拓扑与忙状态。若 A 已自然断开且 HID 无 owner，直接为 B 保留 HID；若 A 变为复合 owner，或原 owner 换成另一条仍在线的链路，本次不继续强断。
- 关机、OTA、录音、文件传输及 DUT/工厂等忙状态拒绝换机，不排队等业务结束。TAKE 通过准入后冻结新的 HID report admission，不冻结目标的 RDX。使旧手势、发送重试和按住态失效，不把已经按住的键迁移到 B；B 就绪后等该键释放再接受新按压。
- 若 A 有已发出或可能已发出的按键，保留旧 HID token 和 CCC，在 `btstack` 串行发送全零 release；release 的提交应排在已获准的旧 report 之后，禁止冻结后再提交旧按下。等待发送路径受理并留出有界的释放机会，**受理不等于 Windows 已收到或处理**。不能完成时，若未提交断开且 A 仍在线，按第 4.3 节回滚；若 A 已自然断开，按正常断链清理继续。
- 旧 ACL 的断开也在 `btstack` 串行提交。执行点重验 A 的 ACL/HID token、纯 HID 状态、B 的请求 token 和截止时间，不凭旧 handle 或投递成功执行。只向 A 发断开；以匹配 A 连接代次的 `HCI_EVENT_DISCONNECTION_COMPLETE` **且原 owner 已清理**为让位依据，不把 B 填进未释放的 HID slot。若 A 已自然断开，复用其正常清理结果，不重复发命令。

### 4.2 目标保留与完成

- 从 TAKE 受理起，为目标保留 HID 名额。**Input CCC 启用与加密完成后恢复历史 CCC 两条入口都要检查保留**，统一走 `rdx_ble_server_phase2_hid_attach()` 的准入；否则旧 PC 可能在第二入口重新开放后自动恢复 CCC，抢先拿回 HID。保留只限制 HID，不关闭或改变现有第二广播策略，也不主动断开普通手机 RDX。
- 若 Windows 还需配对，保留期间的临时 HID 配对资格也只给目标 ACL；配对等待、Just Works 回调和后续加密完成仍须按对应链路校验。严禁因为正在交接就放开所有连接的 Just Works，或先对实际未安装的 Input CCC 回成功。
- 旧 owner 已释放后，目标可通过新的 Input CCC 写入进入 HOGP；对已绑定目标，可按现有规则重新检查该 peer 的持久订阅，不能因为它已经加密就强行启用通知。此前失败的 CCC 写入不是有效订阅。完成条件为 **目标 ACL 的 RDX 会话仍有效，且同一 ACL 持有 HID、已加密、Input CCC 有效、未 suspend**。
- 接管路径必须把「认领 HID」与「装载有效 CCC」作为一次提交。当前代码先认领，再处理 CCC，后者可能因 VM 写入失败而撤销订阅。若实现需先临时认领，临时状态不得路由按键、标记 `ready` 或对外宣告复合满占；写入/恢复失败、待就绪超时或请求失效时，按 token 回滚**本次新增**的 HID capability、输入状态和本次 CCC 变更，并重算广播状态。不能回滚本就有效的 HID owner，不能断 B 的 ACL、清 B 的 RDX 或清其他 peer 的订阅和 bond。
- CCC 写入按实际安装结果应答，不能让 ATT 写请求等待 Windows 退出 suspend。若已安装 CCC 但尚未就绪，保留事务标识直到就绪或回滚。B 就绪时提交 owner、按既有复合 owner 流程关闭第二入口，并结束交接预留和期限。若已建立其他连接，不因复合 owner 就绪而强断它；后续回连边界见第 2.1 节。

### 4.3 超时和取消

- 建议首轮联调值：从 TAKE 受理起，整笔交接（含等待 Windows）最多 60 秒。采用按需一次性期限，不在稳定空闲时增加轮询定时器；旧链路断开和 release 等待各有有界检查，不无限重试。
- 目标掉线、关闭 RDX 应答 CCC、`rdxclose`、关机、任务投递失败或超时均使该次授权失效；第 4.4 节的恢复窗口不继承授权。待执行的异步命令必须重验，不得在取消后继续提交。
- **断开尚未提交，或得到明确的「未受理且不会生效」结果：**若 A 的同代 ACL 仍是原 HID owner，可解冻其键盘路由。旧手势和队列不重放，按住键等松开后才能产生新按下；若全键释放尚未完成，先按原 HID 路径补齐释放。
- **断开已受理或结果不明：**超时只结束这笔 TAKE，不能因暂未收到断开事件就恢复 A 的输入，也不能假定 A 已释放。该代 A 保持断开待确认标记并冻结键盘，拒绝重复提交；匹配的迟到事件只走正常断链清理，不再续接过期请求。仅当栈能确认同代 ACL 存续且没有挂起断开时才可解冻；若无法判定，APP 提示检查系统连接，必要时由用户断开该链路，不做反复强断或重试。
- 失败后撤销 B 的交接预留，B 的 RDX 若仍有效则保留；A 若已断开，恢复普通 HID 准入，不承诺 A 立即回来。APP 显示失败原因或「RDX 可用，键盘未连接」，不自动重新接管。

### 4.4 Windows 移除记录前的限时恢复

1. 仅在 A 已退出、B 仍持有原 RDX token 且处于 `pair` 时，由用户在 PCDEMO 显式开启恢复窗口；收到 `recover` 后才提示到 Windows 移除记录。设备从此撤销旧 ACL 的接管资格，改为暂缓未重新授权的 HID 认领及历史 CCC 恢复。恢复窗口只留防竞争状态，不冻结 RDX，也不关闭现有广播或为 B 保留物理 ACL 名额。A 可能接入 ACL，但不能在窗口内凭 bond 先认领 HID。
2. 移除记录可能打断 B 的 ACL。断开后旧 token 一律失效；恢复窗口可在原期限内继续，但不携带可供新连接使用的授权。回到 PC APP 主动点「连接」，在当前有效 RDX 会话上发新的 `take`；处于已开启的重配流程时，即使 `get` 返回 `none` 也要发，用来为当前 ACL 申请 HID 名额。收到 `pair` 后再提示用户在 Windows 中添加设备。仍不需要按设备键；后台重连不发新请求。只认当前有效 token 和实际链路上的安全状态，不用旧 ID、地址、Windows 名称或相同 handle 判定为 B；其他设备不因窗口开放而获配对放行。
3. Windows 可能先尝试 HID、后让 PCDEMO 建立 RDX。无授权的早期尝试不占 HID，也不回成功伪造订阅；须板测验证 PCDEMO 能否先接入、Windows 在新授权后是否会重新枚举。恢复窗口与新请求共用一个固定上限（建议 60 秒，从开启时计），重试不续期；成功、取消、超时或设备关机均清理窗口，恢复普通准入。
4. 若 A 占住第二条 ACL、普通 RDX owner 还未释放，或 Windows 授权后仍不重试，不能强断其他业务或承诺自动修复。PCDEMO 联调先验证上述两种 Windows 接入顺序；无法走通时，受控验证可先让测试 PC 关闭蓝牙或移除其测试记录，再为 B 正常配对，不将此操作当作客户量产的自动恢复能力。

## 5. RDX 对接草案

复用 `custom` 通道，建议命令名 `hidtake`；以下为联调草案，现有固件没有该接口。APP 不从固件版本号或 `os_type` 推断支持；旧固件未回复查询时，不发 TAKE，不阻塞连接，保留现有 RDX 功能。

```text
查询：*APP#custom#hidtake#get,<id>#
申请：*APP#custom#hidtake#take,<id>#
重配准备：*APP#custom#hidtake#repair,<take_id>#
应答：*DEV#custom#hidtake#<id>,<state>#
```

| `state` | 含义 |
| --- | --- |
| `own` / `other` / `none` / `own_wait` | GET：本链键盘就绪 / 另一链持有 HID / 无 HID owner / 本链持有 HID 但未就绪。GET 不触发接管。 |
| `switch` | TAKE 已受理，正在释放旧按键或等待旧 ACL 退出；此时不要移除 Windows 设备记录。 |
| `pair` | 旧 HID 已退出，目标有临时独占接入资格；需要时提示用户完成 Windows 配对。 |
| `recover` | 原请求的接管授权已撤销，恢复窗口已开启；可移除 Windows 记录，重连后需新请求。 |
| `ready` | 本链 RDX 有效且 HID 就绪，复合连接完成；两项本就就绪的 TAKE 可直接返回。 |
| `busy` / `conflict` / `timeout` / `failed` / `stale` | 当前业务或请求繁忙 / 不满足当前操作准入 / 等待超时 / 发送、断开或其他交接步骤失败 / 请求 ID 过旧，不再执行。 |

`id` 为 `1..65535` 的十进制请求编号。同一 RDX 会话只允许一笔 TAKE 进行；同一有效 token 重发当前或最近一笔已受理 TAKE 的 ID，返回当前阶段或缓存终态，不重复 release/断开、不延长期限。TAKE ID 在同一 RDX 会话内递增且不回绕；旧结果被更新后再收到更早的 ID，只返回 `stale`，不当作新请求。在途时不同新 ID 不替换现有请求。`repair` 只针对当前 `pair` 的 TAKE ID；重复请求不重新开启或延长窗口。`recover` 仅在窗口仍有效时重报，过期后不能用缓存结果再次提示移除记录。

应答只发给仍有效的请求 token，不转发给后来的 RDX owner。丢阶段应答时，同一会话可用原 TAKE ID 查询交接进度；GET 只读实时 HID 状态，不能区分交接或重配阶段。新会话可查询状态，但没有新的用户主动连接操作就不发 TAKE。实际收发长度、分片和未知自定义命令兼容性需用现有协议库验证。

## 6. 实施与验收

**设备端：** `rdx_app.c` 接收 `hidtake` 请求；`rdx_ble_server.c` 处理交接状态、两条 HID 准入路径及断开确认；`rdx_ble_session.c` 继续作为唯一 owner 仲裁入口；HOGP 输入/键盘模块提供旧键释放与代次清理。不增加按键确认，不换 JL 库或改生成文件。

**客户端：** 先用 PCDEMO 接入 `get`、`take` 和状态提示，验证 A 让位后 B 的 RDX 持续可用、Windows 键盘能正常启用；再联调 `repair`。板测通过后，客户 APP 在现有「主动连接」流程后增加 `custom` 指令和状态处理，不改底层协议、绑定流程或后台回连。

| 验收项目 | 通过条件 |
| --- | --- |
| 原问题复现后接管 | 两台 PC 保持蓝牙打开。A 先自动回连；用户在 B 的 APP 只点一次「连接」，APP 建立 RDX 后自动发 TAKE，不弹二次确认、不按设备键。仅 A 被断开；B 的 RDX 保持，同一 handle 出现 HID+RDX，Windows 正常识别键盘，实际按键只到 B。 |
| 接管窗口内旧 PC 回连 | A 保持蓝牙开启并保留配对记录。覆盖 A 已断开、B 的 HID 尚未就绪时 A 成功重建 ACL 的情况；A 恢复历史订阅或重写 Input CCC 均不能认领 HID。B 的 RDX 不断，最终同一条 ACL 上 HID 和 RDX 均可用，实际按键只到 B。 |
| 复合连接状态 | 只就绪 RDX 或只就绪 HID 时，APP 不显示整机连接成功；同一 ACL 两项就绪才显示成功。若 HID 启用失败，保留可用的 RDX 并提示键盘未连接；任一项失效时不再显示复合连接成功。 |
| 普通连接不抢占 | A 持有 HID 时，覆盖 B 的后台自动重连、Windows 历史回连和手机 RDX 接入，均不发 TAKE、不踢 A。覆盖 HID 已在本链路和旧固件不响应 `get`，均不发 TAKE，现有功能可用。 |
| B 保持复合 owner | A 保留原配对记录并尝试回连；第二入口关闭，A 不拿到新的正常接入机会，也不改变 HID owner。 |
| B 的 APP 正常退出 | B 发 `rdxclose` 后 HID 和 ACL 保留，RDX 清理完成后入口重开；若 A 建起第二条 ACL，历史订阅恢复及重新写 CCC 都不能抢 HID，按键仍只到 B。A 不占 ACL 时验证手机可接入 RDX。 |
| B 的 HID 链路断开 | 关闭 B 的蓝牙或制造实际断链，确认 B 的 HID owner 已释放，窗口外 A/B 可按原规则竞争，不误拦旧 bond。 |
| Windows 错误记录与重配 | 收到 `recover` 后才移除 B 的设备记录；A 保持蓝牙开启并尝试回连，不能在窗口内认领 HID。旧 token 不可重用，后台重连不发 TAKE；用户主动点「连接」后用当前会话发新 TAKE。覆盖 Windows 先申请 HID、APP 先建 RDX 两种顺序；失败的 CCC 不算就绪，窗口超时恢复普通准入；若 Windows 不再尝试，记录板测阻塞。 |
| 原有两种拓扑 | PC HID + 手机 RDX 双 ACL 在两种接入顺序下均能工作；同一 PC HID + PC RDX 在两种顺序下复用 ACL；复合关广播、`rdxclose` 重开入口与低功耗行为保持原状。 |
| 按键和断开边界 | A 按住键、全键释放失败、断开明确未提交、断开已受理但回调迟到。验证不重放旧键、不双发，结果不明时不恢复 A 路由，迟到回调不续接过期请求。 |
| HID 临时认领回滚 | 注入 CCC/VM 失败及 suspend 等待超时；确认不会残留临时 HID owner 或误关广播，B 可继续使用 RDX，无跨 peer CCC/bond 改动。 |
| 请求重传与拒绝 | 丢阶段应答、重复同 ID（含终态）、在途不同 ID、旧 ID、slot 重用，以及无有效 RDX owner 的请求、旧复合 owner、业务忙。验证阶段可重查且不重复副作用、无非预期断链、无跨 peer 应答、无残留保留或空闲周期定时器。 |

主机侧先验证状态机、两条认领入口及 token/定时器竞态，再跑现有 RDX 传输、HOGP 和第二入口回归；实板复验 Windows 枚举、两种拓扑、真实按键和断链时序。**发布验收看实际按键路由，不只看键盘图标，也不把现有两份复现日志当成修复已经通过。**
