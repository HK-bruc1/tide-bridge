# RDX 私有 GATT + 标准 HID 键盘 + Codex Micro 复合方案

> 文档状态：产品化架构与分阶段验证方案
>
> 已知进展：Windows 上的 Codex 客户端已经能识别一个当前实验构建；该次证据尚须补录准确 persona、编译宏和固件 commit。在证据补齐前，只记录“实验构建已被发现”，不能默认视为 composite/C1 已通过。RPC、按键、回连和压力场景仍须逐项验证。
>
> 边界：本方案基于受控实验构建和开源兼容实现得出的互操作设计，不是 OpenAI 公开发布的第三方设备协议规范。参考身份只允许存在于实验镜像中。

## 1. 目标与结论

目标产品不是以 Codex 替换整个 BLE 服务，而是在一个共享的 BLE ATT 数据库中并存：

```text
RDX 私有 GATT                 私有 APP 配置、数据与既有业务
        +
HID over GATT Service 0x1812
        +-- 标准键盘 Report ID 1    Windows 标准键盘 Usage
        +-- Codex Vendor Report ID 6  Codex JSON-RPC 传输
```

两种 HID Report 可以在同一条 BLE 连接上并存；不同的 Report ID、Report Characteristic、Report Reference 和 Input CCC 将它们隔离。二者报文格式不同不是不能共存的原因，反而正是 HID Report Map 要解决的问题。

产品的五个物理按键继续由 RDX 私有 GATT 上的 APP 配置。但配置模型从“只保存 HID 键值”升级为“保存带类型的动作”。一次物理按下只路由到一个动作类型，因此不会同时发送普通键盘输入和 Codex 动作。

## 2. 名词与边界

| 名词 | 含义 |
|---|---|
| RDX 私有 GATT | 既有 RDX UUID 服务、APP 命令、配置和业务数据；不是 HID。 |
| 标准键盘 | HID Usage Page `0x07`、Report ID `1`、8 字节键盘报告。Windows 键盘驱动直接解释。 |
| Codex Report | Vendor Defined Usage Page `0xFF00`、Report ID `6`、63 字节输入/输出报告。Codex 客户端解析其 framing 和 JSON-RPC。 |
| HID core | 共享的 HID Service、加密、owner、CCC、Protocol Mode、Control Point 和生命周期层。 |
| 动作映射 | 一个物理键到一个“键盘动作 / Codex 动作 / 禁用”的持久化配置。 |

Codex 的 `AG00` 不是标准 HID usage，也不是可写入标准键盘 report 的键值；它是 Codex JSON 消息中的逻辑动作名称。例如设备通过 ID 6 发送：

```json
{"method":"v.oai.hid","params":{"k":"AG00","act":1,"ag":0}}
```

因此 APP 不能把 `AG00` 当作标准 HID usage 下发，也不应直接下发任意 JSON 或方法名。

## 3. 目标运行拓扑

### 3.1 连接与 owner

保持当前固定的两 wrapper、最多两条 Peripheral ACL 的架构：

```text
Link A ── RDX 私有 GATT owner
       └─ 可同时成为 HID owner

Link B ── 可成为 HID owner（若 A 未占用）
```

只保留两个 capability：`RDX` 和 `HID`。Codex 是 HID 内的 report provider，**不得**新增 `CODEX owner`。同一 link 同时拥有 RDX 和 HID 时是 `RDX_HID` 复合会话；RDX 私有 APP 可以配置全局键映射，HID link 则承载键盘和 Codex 上报。

全局键映射允许由手机上的 RDX link 配置、由电脑上的 HID link 执行，但写入权限不得仅依赖“存在一个 RDX owner”。SET/RESET 必须同时满足：当前 RDX runtime active、request token 仍属于该 owner、产品绑定/认证成功、非 OTA/关机/录音等禁止状态。发布构建必须提供 fail-closed 的产品授权实现，不能继续依赖默认允许的 weak hook。

HID 发送的前提保持不变：正确 HID owner、连接有效、链路加密、相应 Input CCC 已启用、未 suspend、generation token 未过期。每个 report 都有独立 CCC：键盘 ID 1 的订阅不能视为 Codex ID 6 的订阅，反之亦然。

### 3.2 共享与独立内容

| 可复用 | 必须独立 |
|---|---|
| HID Service `0x1812`、BLE link、MTU、加密、配对、owner、generation token、ATT 可发送事件、断连清理 | Report ID、Input/Output Report characteristic、Input CCC、报告长度、payload 编码、键盘按下状态、Codex RX/TX 队列与 RPC 状态 |
| Protocol Mode、HID Information、Control Point、peer identity、订阅持久化框架 | Report Map 中各 collection 的定义和各 report 的 Report Reference |

ATT 是串行传输，两个 report 的 notify 会在同一链路上按顺序发出；这不影响应用层同时具备“标准键盘”和“Codex”两种能力。

## 4. HID Profile

### 4.1 Composite 为目标产品配置

最终目标配置使用 composite Report Map：

```text
Keyboard Collection (Usage Page 0x07, Report ID 0x01)
    +
Vendor Collection   (Usage Page 0xFF00, Report ID 0x06)
```

目前 ID 6 Vendor Collection 固定为 29 字节：

```c
0x06, 0x00, 0xFF,  /* Usage Page 0xFF00 */
0x09, 0x01,        /* Usage 1 */
0xA1, 0x01,        /* Collection Application */
0x85, 0x06,        /* Report ID 6 */
0x15, 0x00, 0x26, 0xFF, 0x00,
0x75, 0x08, 0x95, 0x3F,
0x09, 0x01, 0x81, 0x02, /* 63-byte Input */
0x95, 0x3F,
0x09, 0x02, 0x91, 0x02, /* 63-byte Output */
0xC0
```

Composite Report Map 总长为 99 字节：70 字节标准键盘 collection + 29 字节 Codex collection。

### 4.2 固定句柄布局

保持一个静态 ATT 数据库和一套稳定句柄。目标 composite 布局如下：

| 句柄 | 属性 | 归属 |
|---|---|---|
| `0x0016-0x0025` | HID 通用属性及 ID 1 Input/Output Report | HID core + keyboard provider |
| `0x0026-0x0029` | ID 6 Input Report、CCC、Report Reference | HID core + Codex transport |
| `0x002a-0x002c` | ID 6 Output Report、Report Reference | HID core + Codex transport |
| `0x002d-0x0031` | Device Information Service | profile aggregate |

修改 Report Map、Service 或 Attribute 布局后，Windows 必须删除旧设备并重新配对。运行时不得改变 ATT 表或 Report Map；如果产品需要切换键盘行为，只切换键的动作映射，不切换描述符。

### 4.3 三种构建 persona

| Persona | 当前映射 | 私有 GATT | ID 1 键盘 | ID 6 Codex | 用途 |
|---|---|---:|---:|---:|---|
| `keyboard` | C0 / mode 0 / `all` | 是 | 是 | 否 | 现有产品回归基线 |
| `codex-only` | V1 / mode 1 / `codex-v1` | 是 | 否 | 是 | 隔离 Codex/Windows/传输问题 |
| `composite` | C1 / mode 2 / `codex-c1` | 是 | 是 | 是 | 目标产品与兼容性验证 |

`codex-only` 是诊断 persona，而不是 composite 的替代品。目标产品默认采用 `composite`，每个物理键由动作映射决定是否发送 ID 1 或 ID 6。

## 5. 模块化架构

JL SDK 只允许一份 ATT 数据库，所以模块化应体现在 Profile 片段、handle 分发和明确 API 边界，而不是让多个模块各自注册 `app_ble_profile_set()`。

```text
rdx_ble_server                 JL wrapper、广播和 SDK callback 桥接
        |
        +-- rdx_ble_session    两 link、owner、加密、MTU、token、epoch
        |
        +-- rdx_gatt_profile   静态 ATT 表与按 handle 的模块分发
              |
              +-- rdx_private_gatt
              +-- rdx_hid_service
                    +-- rdx_hid_keyboard
                    +-- rdx_codex_transport
                          +-- rdx_codex_rpc
                          +-- rdx_codex_app
        |
        +-- rdx_input_router   五个物理键到一个动作的独占路由
```

### 5.1 `rdx_ble_server`

只承担 SDK 适配职责：wrapper 创建/释放、连接事件、ATT read/write 入口、`ATT_EVENT_CAN_SEND_NOW`、广播和 profile 注册。它不得继续包含 Codex RPC、按键策略或大量 HID 细节。

### 5.2 `rdx_gatt_profile`

拥有唯一的 `rdx_profile_data[]` 和句柄常量；使用编译期 profile fragment 组合 RDX 私有服务、HID 片段和 DIS。ATT dispatcher 按 handle range 转发到私有 GATT 或 HID core，模块不直接依赖 server 的大 `switch`。

### 5.3 `rdx_hid_service`

拥有 HID 共有状态：Protocol Mode、HID Information、Control Point、HID owner、加密检查、suspend、各 report CCC、peer-scoped 订阅恢复及所有 ready-drop 清理。它向 report provider 暴露受限 API，例如：

```c
int rdx_hid_report_notify(report_id, value_handle, data, len);
u8  rdx_hid_report_is_ready(report_id);
void rdx_hid_report_release_all(void);
```

ID 1 和 ID 6 使用独立的 `ready` 判断；任一 CCC 的变化都只影响其对应 provider。

### 5.4 `rdx_hid_keyboard`

只处理标准 8 字节键盘报告和 LED Output Report。它不理解 Codex、APP keymap 协议或物理键策略。

### 5.5 `rdx_codex_transport`、`rdx_codex_rpc`、`rdx_codex_app`

| 模块 | 责任 |
|---|---|
| `rdx_codex_transport` | ID 6 的 63 字节 framing、RX 重组、TX FIFO、`APP_BLE_BUFF_FULL` 重试、link token 与 timeout。 |
| `rdx_codex_rpc` | 完整 JSON 边界、解析、allowlist、参数验证、JSON-RPC result/error 序列化。 |
| `rdx_codex_app` | `device.status`、`sys.version`、受支持灯效、Agent Key 等产品语义；不直接操作 ATT。 |

ID 6 ATT Value 固定为 63 字节，不含 Report ID：

```text
[0x02][N][N 字节 UTF-8 JSON][zero padding]
```

其中 `N` 为 `0..61`。TX 消息以 LF 结束后分片；ATT callback 只校验、复制和入队，cJSON 解析只在 `app_core` 执行。队列、深度、字符串、JSON nesting、超时和 generation 必须保持有界，未知方法必须 fail-closed。

63 字节 ATT Value 要求 effective ATT MTU 至少为 `66`。Windows HID capabilities 中 `InputReportByteLength` 和 `OutputReportByteLength` 必须均为 `64`，其中第一个字节是 Report ID `0x06`，后续 63 字节才是 ATT Value。若任一条件不满足，先保存 MTU/HID caps 证据并停止 Codex RPC 判断，禁止用截断或软件补齐伪造成功结果。

### 5.6 `rdx_input_router`

物理键事件只能调用统一入口：

```c
int rdx_input_router_click(u8 physical_key_id);
```

它读取当前动作映射并用 `switch(kind)` 路由。业务代码不得直接从 `rdx_app.c` 调用 `rdx_hogp_keyboard_report_send()` 或 `rdx_codex_micro_agent_key_click()`。

固件内部键号固定为零基：用户可见键 1～5 分别对应 `physical_key_id=0..4`。因此硬编码 Codex 键 5 必须落在 `key_id=4`；当前 `num_idx==0` 的临时 Codex 旁路必须删除，不能仅把判断改成另一个数字后继续保留旁路。

切换映射、HID owner 释放、CCC disabled、suspend、断连和 generation 更新时，router 必须先取消所有 pending timer，并向对应 provider 发送 release；不得出现 stuck keyboard key 或 stuck Codex key-up。

## 6. 五键动作映射与私有 APP 协议

### 6.1 为什么要升级协议

当前 `hogpkm` V1 每键存储：

```text
[modifier][usage1][usage2][usage3][usage4][usage5][usage6]
```

五键共 35 字节，只能表示标准键盘 usage。它应继续作为 legacy ABI，而不能把 Codex 名称硬编码进 usage 字节数组。

V2 使用固定 8 字节 union entry：

```text
[kind][data0][data1][data2][data3][data4][data5][data6]
```

| `kind` | 名称 | `data` 解释 |
|---:|---|---|
| `0x00` | `NONE` | 所有 data 必须为 0。 |
| `0x01` | `KEYBOARD` | `data0=modifier`，`data1..6=标准 HID keyboard usages`。 |
| `0x02` | `CODEX_AGENT` | `data0=Agent index`，其余 data 必须为 0。测试阶段只允许 `index=0`，固件转换为 `AG00`、`ag=0` 的 down/up。参考实现保留 `0..5` 对应 AG00～AG05，后续必须经实测和 capability 放行。 |

V2 五键 payload 是 40 字节。继续使用私有命令 `hogpkm`，wire header 的 version 为 `0x02`，现有 opcode、request ID、base revision、payload length、little-endian 编码和 CRC32 语义保持不变。新旧协议均必须先验证完整 frame，再进入 `app_core` 的 token-bound 事务。

V2 的长度上限必须按下表冻结，不能继续沿用 V1 的 49/98 和 50/100：

| 内容 | 计算 | 二进制长度 | hex 长度 |
|---|---:|---:|---:|
| V2 SET request | `10 header + 40 map + 4 CRC` | 54 | 108 |
| V2 GET response | `10 header + 1 status + 40 map + 4 CRC` | 55 | 110 |
| 完整 GET uplink | `*APP#hogpkm#` wrapper + 110 hex + 尾部分隔符 | 130 | 不适用 |

因此实现至少需要 `MAX_REQUEST_FRAME_LEN=54`、`MAX_REQUEST_HEX_LEN=108`、`MAX_RESPONSE_FRAME_LEN=55`、`MAX_RESPONSE_HEX_LEN=110`，完整 uplink 静态缓冲至少为 131 字节（含 NUL）。这些 workspace 继续放在模块 BSS，不能压入 `app_core` 小栈；host contract 必须断言计算关系而不是只断言孤立常量。

`GET_CAPS` 使用不超过 8 字节的紧凑 payload，至少编码：status、wire-version mask、physical key count、entry length、action-kind mask、允许的 Agent index mask 和 test-mode flag。测试阶段 Agent mask 只有 bit 0；未实测的 AG01～AG05 不得提前宣告。

V1/V2 共用一个 canonical V2 runtime map 和同一个 revision 域，兼容行为固定为：

1. V1 SET 中全零 legacy entry 转换为 `NONE`；其余 entry 转换为 `KEYBOARD`，然后原子替换 canonical map。
2. V1 GET 仅在当前 map 全部为 `NONE/KEYBOARD` 时允许降级编码。
3. 当前 map 含任一 Codex action 时，V1 GET 返回新的 `MAP_NOT_REPRESENTABLE` status，不能伪造为零 usage、截断或静默丢弃。
4. 测试宏开启时，所有 SET/RESET 返回新的 `TEST_MODE_ACTIVE` status，GET 返回 built-in canonical map，不能写 VM。
5. V2 收到未知 kind、未宣告 Agent index、非零 reserved data 或错误长度时返回 `INVALID_KEYMAP`。

新 status 从当前 `0x00..0x0C` 之后分配：`MAP_NOT_REPRESENTABLE=0x0D`、`TEST_MODE_ACTIVE=0x0E`。APP 必须显式处理，不能归并成通用失败。

### 6.2 先使用硬编码测试路径

在实现和联合调试 APP V2 协议之前，先通过现有测试宏启用一份固定的 composite 动作映射，验证标准键盘与 Codex 的底层链路和独占路由。继续复用标准 HOGP 初期已经使用的 `RDX_HOGP_KEY_ACTION_TEST_ENABLE`，不新增第二个测试开关：

```c
#ifndef RDX_HOGP_KEY_ACTION_TEST_ENABLE
#define RDX_HOGP_KEY_ACTION_TEST_ENABLE 0
#endif
```

该宏目前定义在 `rdx_app_config.h`，默认值为 `0`，现有 `rdx_hogp_key_action.c` 已用它选择内置标准键盘 test map。Composite 测试阶段只扩展这份 test map 和执行器，使其支持 typed action，不改变宏的所有权和默认值。

测试构建使用唯一可复现目标 `codex-c1-keytest`：构建前执行 clean，并固定启用 composite/C1、laboratory identity 和 `RDX_HOGP_KEY_ACTION_TEST_ENABLE=1`。发布构建必须扫描并拒绝测试宏与参考身份；不得用开发者本地临时 CFLAGS 作为正式验证证据。

第一版固定测试映射建议为：

| 物理键 | 硬编码动作 | 预期上报 |
|---:|---|---|
| 1 | `KEYBOARD / Ctrl+C` | 仅 ID 1 键盘 down/up |
| 2 | `KEYBOARD / Ctrl+V` | 仅 ID 1 键盘 down/up |
| 3 | `KEYBOARD / Backspace` | 仅 ID 1 键盘 down/up |
| 4 | `KEYBOARD / Enter` | 仅 ID 1 键盘 down/up |
| 5 | `CODEX_AGENT / Agent 1` | 仅 ID 6 的 `AG00`、`ag=0` down/up |

键 5 的用户语义固定为“选择 Codex Agent 1 / 第一个任务槽”，不描述为含义不明确的“启动 Codex”。参考工程同时定义了 Agent Keys `AG00..AG05` 和 Command Keys Fast、Approve、Decline、Fork、Mic、Send；本阶段选择 AG00，是因为它最符合 Agent 键定位，也不会像 Approve、Decline 或 Send 那样执行具有上下文副作用的命令。测试前应在 Codex Micro 设置中为 Agent 1 完成分配，否则客户端可能接收到事件但没有明显的任务切换效果。

硬编码测试只替换“动作映射的来源”，不能建立旁路：

```text
生产路径：APP V2 / VM ──> canonical action map ──> input router ──> provider
测试路径：built-in map ──> canonical action map ──> input router ──> provider
```

两条路径必须调用同一个 `rdx_input_router_click()`、同一套 ID 1/ID 6 ready 判断、同一套 release cleanup 和同一套 ATT transport。禁止在物理键 callback 中使用测试宏直接调用 Codex 或 keyboard send API，否则测试无法证明正式架构可用。

测试宏开启时，built-in map 是唯一动作来源。现有 APP/VM 键映射不得在运行中覆盖它；配置写入应被明确拒绝或标记为 test-mode unavailable，避免测试结果受旧 VM 数据影响。启动日志和 `GET_CAPS`/诊断信息应显示 `action_map_source=TEST`。

硬编码阶段的通过条件是：

1. Composite 设备仍被 Windows 和 Codex 客户端识别。
2. 物理键 1～4 只产生预期标准键盘事件，且无任何 ID 6 消息。
3. 物理键 5 连续触发 `AG00`、`ag=0`，且无任何 ID 1 副作用。
4. ID 1 或 ID 6 任一 report 未 ready 时，仅对应类型失败，不回退、不串到另一 provider。
5. 断连、CCC disable、suspend 和重连过程中无 stuck keyboard key 或缺失的 Codex key-up。

只有该阶段通过后，才开始 APP V2 的 wire protocol、VM migration 和 UI 联合调试。这样能把问题明确分为“Composite HID/路由问题”和“APP 配置协议问题”。

### 6.3 APP 合约

APP 先请求 `GET_CAPS`，再决定 UI 和 wire version。V2 capability payload 固定为 8 字节：

```text
byte0 status
byte1 wire_version_mask   bit0=V1, bit1=V2
byte2 physical_key_count  固定 5
byte3 entry_len           V2 固定 8
byte4 action_kind_mask    bit0=NONE, bit1=KEYBOARD, bit2=CODEX_AGENT
byte5 codex_agent_mask    测试阶段仅 bit0=1
byte6 flags               bit0=TEST_MODE_ACTIVE
byte7 reserved            必须为 0
```

APP 的每键 UI 是“动作类型选择器”，而不是只能选择键盘键值：

```text
物理键 N
  - 标准键盘快捷键（修饰键 + 1..6 个标准 usage）
  - Codex Agent 1
  - 禁用
```

APP 只下发稳定的 typed value，例如 `CODEX_AGENT/index=0`，永远不下发任意 Codex JSON、任意 RPC method、任意 `AGxx` 字符串或未经固件 capability/allowlist 放行的参数。固件是 Codex 协议适配器，负责将 index 0 生成实际的 `AG00`、`ag=0` JSON 消息。

### 6.4 兼容与存储迁移

V2 使用新的 VM IDs 和新的 record magic，不覆盖现有 51 字节 `HKM1/HKC1` 记录。V2 data record 固定为 56 字节：12 字节 header + 40 字节 canonical map + 4 字节 record CRC；commit record 继续为 20 字节，但使用新的 magic/schema。新 IDs 暂记为 `VM_RDX_INPUT_MAP_SLOT_A/B` 和 `VM_RDX_INPUT_MAP_COMMIT_A/B`，实施前必须在 `syscfg_id.h` 冻结真实编号并加入冲突检查。

启动选择顺序固定为：

1. 优先读取并验证 V2 A/B data + commit，选择 revision 更新的有效槽。
2. 没有有效 V2 时读取 V1 A/B，将全零项转换为 `NONE`、其余项转换为 V2 `KEYBOARD` entry。
3. 转换后先写入并读回验证新的 V2 槽和 commit，成功后才发布 canonical runtime map；旧 V1 记录保留作为回滚证据，不原地覆盖。
4. V1/V2 都无效时加载产品默认 canonical map。

所有写入继续保持现有顺序：验证 request/token → prepare 非活动槽 → 读回验证 → release 旧动作 → apply RAM → 再次验证 token → commit → 发布 revision/active slot。任一步失败都恢复旧 runtime map，不能留下半发布状态。

旧 APP 仍可通过 V1 SET 配置纯标准键盘；V1 GET 的可表示性规则按 6.1 执行。新 APP 优先使用 V2，且必须识别 `MAP_NOT_REPRESENTABLE`、revision conflict、storage error 和 test-mode status。

### 6.5 双 Report CCC 存储迁移

当前 HOGP subscription record 只保存 peer 是否订阅，不能表示 Composite 中两个独立 CCC。存储 schema 升级为 `HCS2`，每个 peer entry 保持 8 字节并复用原 reserved byte：

```text
byte0 valid
byte1 subscription_bits  bit0=Keyboard ID1, bit1=Codex ID6
byte2..7 SM peer identity
```

`HCS1` 有效 entry 迁移为 `subscription_bits=KEYBOARD_ID1`；历史实现没有持久化 Codex CCC，因此不得猜测并设置 bit1。任一 CCC 写入只更新自己的 bit 并保留另一 bit；加密完成后分别恢复对应 handle。恢复、禁用、bond reset 和 peer eviction 都必须写后读回验证，并确保一个 peer 的 bitmask 不会应用到另一个 peer。

### 6.6 按键运行规则

| 映射类型 | 条件 | 行为 |
|---|---|---|
| `NONE` | 任意 | 消费事件，不发送报告。 |
| `KEYBOARD` | ID 1 ready | 仅发送标准键盘 down/up。 |
| `CODEX_AGENT` | ID 6 ready | 仅发送 AG00 down/up JSON。 |
| `KEYBOARD` / `CODEX_AGENT` | 对应 report 未 ready | 消费事件、记录诊断，不隐式回退到另一种类型。 |

“不隐式回退”是安全与可预测性要求：配置成 Codex 的键在 Codex 不可用时不能变成 Enter、A 或其他普通键盘输入。

## 7. 身份、广告与安全边界

Codex 能力、HID personality 与设备身份必须是三个独立维度：

```text
Capability:  private GATT / keyboard report / Codex report
Personality: keyboard / codex-only / composite
Identity:    product identity / laboratory reference identity
```

实验参考名称、Manufacturer、VID/PID、PnP、Appearance 和广告字段只能通过明确的 laboratory guard 启用。不得因 Codex 模块存在就自动将参考身份带入产品镜像；发布构建应扫描这些参考字节。

Composite 广播维持单一广告 owner：Primary ADV 保留 Flags + 本地名称；Scan Response 保持 RDX Manufacturer Data 在前并追加 HID UUID `0x1812`。每个修改都保存原始 ADV/Scan Response 证据。

HID 动态属性继续要求加密的 Just Works bond，不虚假宣称 MITM。ID 1 和 ID 6 的 CCC intent 都必须按 SM peer identity 分别持久化，不能从一个 peer 泄漏到另一个 peer。

## 8. 分阶段实施

### Phase 0：冻结已识别基线

建立 evidence session，保存已被 Windows Codex 客户端识别的固件 commit、构建时间、`TCFG_RDX_CODEX_MICRO_MODE`、identity guard、key-test macro、完整编译命令、Report Map、ATT 布局、PnP/DIS、ADV/Scan Response、Windows/App/Adapter 版本、HID caps、MTU 和串口 ID 6 trace。

如果无法确认当时是 codex-only/V1 还是 composite/C1，基线状态必须写成“persona unknown”；补做一次可复现的 `codex-c1` 新鲜配对，不能把未知 persona 的识别结果当成 composite 证据。

### Phase 1：最小 typed router 垂直切片

- 保持当前 C1 Profile、server、HID/Codex 模块和 APP/VM V1 不动。
- 定义 canonical typed action entry/map 和 `rdx_input_router_click()`。
- 将现有键盘 test map 转成 canonical map；新增 `CODEX_AGENT/index=0` executor。
- 删除 `rdx_app.c` 中 `num_idx==0` 的 Codex 直接旁路；所有五键只进入 router。
- 用户键 1～5 显式映射到内部 `key_id=0..4`，Codex 固定为 `key_id=4`。
- provider 仍可暂时调用现有 keyboard/Codex API，但 router 必须是唯一上层入口。

### Phase 2：硬编码 composite 实机 Gate

- 实现并固化 `codex-c1-keytest` 构建目标。
- 复用 `RDX_HOGP_KEY_ACTION_TEST_ENABLE=1`，固定键 1～4 为 ID 1、键 5 为 AG00/ID 6。
- 验证 MTU ≥66、Windows Input/Output Report length=64、两个 CCC 独立 ready。
- 完成新鲜配对、100 次键盘 click、100 次 AG00 down/up、断连和 CCC disable；要求零双发、零 stuck key。
- Gate 未通过时只修垂直链路，不开始 APP V2、VM V2 或大规模文件拆分。

### Phase 3：行为保持的模块拆分

- 将 `TCFG_RDX_CODEX_MICRO_MODE` 整理为 HID personality，保留 keyboard、codex-only、composite。
- 将实验 identity policy 从 Codex capability 中解耦，但 laboratory guard 继续默认关闭。
- 提取 `rdx_gatt_profile`、`rdx_hid_service`、keyboard provider、Codex transport/RPC/app。
- 保持当前 session、owner、token、MTU、handle 和 report-map fixture 不变。
- 每个小步都重跑 Phase 2 的硬编码 fixture；完成后 `rdx_ble_server.c` 只做 profile/register/dispatch/SDK bridge。

### Phase 4：Composite 状态与产品身份加固

- 实现 `HCS2` 双 report CCC bitmask、HCS1 migration、bond reset 和不同 peer 隔离。
- 验证两条 ACL 上独立 RDX/HID owner、同 link composite owner、wrong-owner 和 stale generation。
- A/B 测试 laboratory identity 与合法 product identity；一次只改变一个身份字段并保存原始证据。
- 在 product identity 尚未被目标 Codex 客户端识别前，只能宣称 laboratory compatibility，不能进入产品完成定义。
- 冻结产品授权 hook；未认证 RDX owner 的 SET/RESET 必须 fail-closed。

### Phase 5：APP V2 动作映射

- 保持相同的 canonical action-map/runtime router，只把映射来源从 built-in test map 切换到 APP V2 + VM。
- 关闭 `RDX_HOGP_KEY_ACTION_TEST_ENABLE`，验证没有测试数据残留。
- 实现精确的 V2 codec、GET_CAPS、长度上限、status 和 V1 可表示性规则。
- 分配新的 VM IDs，实现 56 字节 V2 A/B record、V1 migration、读回验证和 rollback。
- APP 更新为动作类型 UI，并在缺少 V2 capability 时隐藏 Codex 动作。
- 完成 V1 old APP、V2 new APP、V1 data、V2 data 四组兼容矩阵。

### Phase 6：互操作与压力验证

- Composite 为产品主验证；keyboard/codex-only 只保留为诊断 persona。
- 验证标准键盘、Codex RPC、AG00、APP V1/V2 keymap 写入和回读同时工作。
- 完成两条 ACL、不同 peer、CCC 恢复、Windows 睡眠/唤醒、蓝牙重启、APP/Codex 客户端重启。
- 记录资源预算、watermark、队列峰值、buffer-full 恢复和发布镜像扫描。

## 9. 验证与验收

### 9.1 构建与静态 contract

每次修改运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tests\host\run_host_tests.ps1
Set-Location .\SDK
.\.vscode\winmk.bat all
```

硬编码 Gate 只能使用仓库内固定目标：

```powershell
Set-Location .\SDK
.\.vscode\winmk.bat codex-c1-keytest
```

该 target 尚待在 Makefile/wrapper 中实现；实现后 VS Code task、命令行和 evidence session 必须调用同一入口。

新增/更新的 host contract 至少覆盖：

- composite Report Map、Report Reference、句柄和 DIS 位移；
- ID 1 与 ID 6 各自的 CCC、加密、HCS2 bitmask、HCS1 migration 与 peer 隔离；
- V2 action-map 的 frame/CRC/enum validation，以及 54/108、55/110、130/131 长度关系；
- V1 GET 可表示/不可表示、V1 SET 转换、V2 status 和统一 revision 域；
- V1 到 56 字节 V2 VM record 的 migration、独立 IDs、A/B 回读和断电恢复；
- map 热更新前 keyboard/Codex release 的顺序；
- 用户键 1～5 到内部 key ID 0～4 的映射、Codex 必须是 key ID 4；
- 每种 `kind` 的唯一分发，禁止直接 Codex 旁路和双发；
- test map 和 APP/VM map 必须进入同一 router/provider 路径，测试宏默认关闭；
- test mode 下旧 VM/APP 写入不能覆盖 built-in map；
- 未认证 RDX owner、wrong-owner 和 stale token 的 SET/RESET 必须 fail-closed；
- Codex framing、FIFO、buffer-full、wrong-owner、stale generation fail-closed；
- 实验身份和 key-test 宏默认关闭且不进入 release image。

### 9.2 Windows 与 APP 手工矩阵

Windows Host 工具必须用 SetupDi/HidP 读取真实 top-level Usage 和 report lengths，以 `WriteFile` 发送 ID 6 Output、以 overlapped `ReadFile` 接收 ID 6 Input；`HidD_GetInputReport` 不能替代 notify。设备侧必须同时记录 MTU exchange、63 字节 write callback、两个 CCC 和 owner/token。PowerShell HIDClass 枚举只能作为辅助证据。

| 场景 | 成功条件 |
|---|---|
| 基线身份 | evidence 明确记录 persona、commit、宏、PnP/DIS、ADV/Scan Response；persona unknown 不计 composite 成功。 |
| HID/MTU | Input/Output Report length 均为 64，effective ATT MTU ≥66，Host 工具完成多片 round trip。 |
| 硬编码 test map | 不连接或不改造私有 APP，也能验证键 1～4 仅发 ID 1、键 5 仅发 AG00/ID 6。 |
| 标准键盘映射 | APP 配置 Ctrl+C 等 usage 后，只出现 ID 1 的预期键盘行为。 |
| Codex 映射 | APP 配置 `CODEX_AGENT` 后，只出现 ID 6 AG00 down/up，绝不产生 ID 1 副作用。 |
| 混合五键 | 五键可以分别设置 keyboard、Codex、disabled，按键逐项符合映射。 |
| 双 CCC | 分别开关 ID 1/ID 6 CCC，只影响对应 provider；重连按 peer 恢复相同 bitmask。 |
| APP 配置 | V1/V2 GET/SET/RESET、不可表示 status、revision conflict、断连重连和 VM 重启后行为一致。 |
| 授权 | 未绑定 APP、非 RDX owner、旧 token 和第二 link 均不能修改 action map。 |
| Codex RPC | `device.status` 在 encrypted + ID 6 CCC ready 后 2 秒内完成；已支持 RPC 返回合法响应。 |
| 产品身份 | 合法 product identity 被目标客户端识别；laboratory identity 成功不能替代此项。 |
| 连接恢复 | 删除配对后新鲜配对、设备回连、Windows 睡眠/唤醒、蓝牙和 Codex 客户端重启均无 stuck key。 |
| 压力 | 100 次多片 status、100 次 Codex Agent click、100 次键盘 click 无丢片、交错、错误 owner 或双发。 |

### 9.3 资源门槛

以 keyboard/C0 基线和最终 composite build 做同工具链对比，并冻结以下初始门槛：

- Flash 增量不超过 32 KiB，BSS 增量不超过 4 KiB；
- 连接态最小空闲堆不少于 12 KiB，且相对基线下降不超过 8 KiB；
- `app_core` 栈剩余不少于 1 KiB，Bluetooth task 栈剩余不少于 512 B；
- ATT callback 单次不超过 1 ms，且零动态分配；
- Codex RX 每 link 不超过 1024 字节；TX 不超过 4 条消息和 2 KiB；
- 记录 RX/TX 峰值、drop count、`APP_BLE_BUFF_FULL` 次数及最终恢复结果。

平台 watermark 若不是字节，报告中必须给出换算方式。任一门槛未达到都不能以“功能可用”替代资源验收。

### 9.4 完成定义

只有以下条件全部满足，才能标记为“RDX 私有 GATT + Composite HID 产品方案完成”：

- Windows Codex 客户端在目标环境稳定识别 composite 设备；
- 识别证据明确来自合法 product identity，而不是 laboratory reference identity；
- 私有 APP 能发现 V2 capability 并可靠配置全部五个物理键；
- 在 APP 联调前，硬编码 typed test map 已独立证明 ID 1/ID 6 的唯一分发和生命周期清理；
- 每个键按映射只进入一种 report provider；
- 标准键盘 ID 1、Codex ID 6 和私有 GATT 同时存在且无互相干扰；
- V1 legacy 数据可安全迁移，V2 A/B 持久化可在掉电后恢复；
- owner、双 CCC、加密、授权、断连和 generation 在双链路下均 fail-closed；
- MTU、HID caps、资源预算、stack watermark、队列峰值和 buffer-full 恢复均达到门槛；
- 实验参考身份未进入产品输出镜像；
- `RDX_HOGP_KEY_ACTION_TEST_ENABLE` 在产品构建中为 `0`，built-in test map 未进入有效产品配置路径。
